## Что и зачем

Часть [LT-091](LT-091-game-library-starter.md), решения — [LT-092](LT-092-starter-design.md).
Подготовить первый релиз, который можно проверить и одобрить как конкретный набор артефактов.

## Приёмка

- [ ] Проверены package names, лицензии, версии, exports, содержимое tarball и публичные зависимости.
- [ ] Установлен точный порядок выпуска пакетов и совместимость с зависимостями @letar/forms.
- [ ] Чистый внешний запуск до CRUD и учебный маршрут воспроизведены по README.
- [ ] Пройден LT-101; changelog/инструкции/теги согласованы по версиям.
- [ ] Подготовлены release notes, проверяемый commit и команды/артефакты публикации.
- [ ] Фактический push/публикация происходят только после предусмотренного правилами одобрения.

## План

1. Собрать итоги дочерних задач и закрыть оставшиеся разрывы между README, шаблоном и реальностью.
   Убедиться, что app/lib принадлежат пользователю, а зависимости доступны вне Letar.
2. Проверить лицензии кода, seed и визуальных материалов; исключить секреты, приватные данные,
   внутренние пути и лишние файлы через анализ npm pack.
3. Сверить registry names, доступ владельца, версии совместимых пакетов, peerDependencies,
   OIDC/provenance и существующую процедуру npm-публикации Letar.
   Не менять dist-tag или механизм релиза всего монорепо без необходимости.
4. Добавить пакеты в принятый реестр/порядок публикации и release workflow, если это предусмотрено
   LT-092. Подготовить версии, changelog, lock и теги; проверить целостность зависимостей.
5. Из конкретных tarball/кандидата релиза в чистом каталоге пройти создание → БД → seed →
   вход → поиск → личная запись → изменение статуса/оценки → проверки.
6. Повторить учебное расширение и сценарий обновления. Зафиксировать команды, окружение,
   результаты и фактические ограничения первого выпуска.
7. Подготовить краткие release notes: что получает новичок, prerequisites, стартовая команда,
   поддерживаемые версии, путь обновления и известные ограничения.
8. Создать scoped-коммиты и представить владельцу конкретный релиз на одобрение.
   До разрешения не делать git push, теги на origin и npm publish.
   Если разрешение не дано, оставить reviewable-результат и явно отразить ожидание в статусе.
9. После одобренной публикации проверить установку из registry и конечный путь пользователя,
   записать ссылки/версии и закрыть родительскую LT-091 только при выполнении её приёмки.

## Проверки и границы изменений

- Владение: release metadata/workflow/документация/версии затронутых пакетов и lock.
- Перед выпуском — пакетные проверки, общий integrity gate для зависимостей, security-review
  auth/пользовательских данных и smoke из опубликованного кандидата.
- Для версии внутри submodule сначала соблюдать правила его push, затем фиксировать SHA Letar.
- Не маскировать подготовку релиза как состоявшуюся публикацию.
