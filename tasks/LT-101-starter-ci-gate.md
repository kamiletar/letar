## Что и зачем

Часть [LT-091](LT-091-game-library-starter.md), решения — [LT-092](LT-092-starter-design.md).
Собрать сквозной gate, который проверяет именно то, что получит внешний пользователь.

## Приёмка

- [ ] CI устанавливает упакованные create/plugin-пакеты в изолированный workspace.
- [ ] Чистое создание, генерация, build и scoped проверки реально выполняются.
- [ ] Пройден пользовательский CRUD-путь и серверные проверки изоляции/фильтров.
- [ ] Проверен upgrade baseline N-1 → N с пользовательскими правками.
- [ ] Прогон не зависит от приватных submodule, локальных БД и секретов Letar.
- [ ] Есть доступные артефакты сбоя без паролей/cookies/env в trace и логах.

## План

1. Составить матрицу проверок из итогов LT-093–LT-100.
   Unit/интеграционные тесты остаются у своих пакетов; здесь не откладывать их впервые.
2. Добавить CI-сборку и pack, установку tarball-зависимостей во внешний workspace и проверки
   отсутствия workspace/private-зависимостей. Локальный link не заменяет такую установку.
3. Поднимать изолированный PostgreSQL, применять реальные миграции/seed и проверять повторный seed.
   Приложение запускать по принятому в Letar e2e/staging-паттерну; не использовать чужой dev-порт.
4. Через Playwright проверить регистрацию/вход, справочник, игру с несколькими версиями,
   добавление в личную библиотеку, статус/оценку/заметку и удаление с ограничениями.
5. Проверить ошибки формы и сервера, сохранность ввода, dirtyGuard, несколько строк версий,
   состояния списка, URL/reload/Back/Forward и клавиатурный основной сценарий.
6. Проверить фильтр одной версии на контрпримере LT-098, OR/AND, totals и стабильную пагинацию.
   Негативные права проверить через сервер/ORM, а не только отсутствие UI-кнопок.
7. Добавить переход N-1 → N из LT-100: пользовательские правки и данные, миграции,
   повторные проверки, читаемые ошибки и отсутствие перезаписи исходников.
8. Проверить основной пользовательский запуск на поддержанных Windows и Linux сценариях;
   если полная DB/E2E-матрица запускается только на одной ОС, явно указать покрытие.
9. Подключить gate к PR/релизному workflow с ограниченными правами.
   Хранить screenshots/reports/логи в артефактах; секреты и auth-state не публиковать.

## Проверки и границы изменений

- Владение: профильные CI workflows и внешние smoke/E2E fixtures; исходники менять только
  для выявленного дефекта, фиксируя отдельную задачу/связь с этапом.
- Применить e2e-test-writer и правила .claude/docs/e2e-testing.md по доступным инструкциям.
- Получить один полный зелёный прогон; отсутствие запущенных тестов не считать успехом.
- Scoped format/lint/typecheck и профильные тесты. Публикация не входит в задачу.
