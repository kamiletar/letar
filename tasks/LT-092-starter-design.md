## Что и зачем

Часть [LT-091](LT-091-game-library-starter.md). Первая отдельная сессия должна превратить
согласованный продукт в конкретные границы пакетов и контрактов, не создавая весь стартер сразу.
Последующие задачи опираются на раздел «Принятые решения» этой задачи.

## Приёмка

- [ ] Зафиксированы имена пакетов, Nx-проектов, пути исходников, экспорты и порядок публикации.
- [ ] Проверено, какие нужные пакеты доступны внешнему пользователю через npm и какие только локальны.
- [ ] Определено, что переиспользуется из генераторов Letar и где остаются внутренние интеграции.
- [ ] Выбрана одна проверенная комбинация версий и описан порядок её дальнейшего обновления.
- [ ] Зафиксированы модели, матрица прав CRUD, правила удаления/уникальности и семантика фильтров.
- [ ] Разделены управляемые стартером и пользовательские файлы; определён формат версии проекта.
- [ ] Уточнены планы LT-093–LT-102, если аудит выявил ограничения. Код стартера не реализован.

## План

1. Прочитать libs/generators/README.md, package.json/generators.json и код new-app/new-lib;
   scripts/data/npm-published-packages.json, правила релиза и актуальные задачи по зависимостям.
   Учитывать намеренные пины ZenStack и известные регрессии; не выбирать latest автоматически.
2. Через Nx MCP получить доступную карту проектов/документацию. Если nx_workspace недоступен,
   использовать nx show project для нужных проектов и записать ограничение.
   Через Context7/официальные документы сверить preset, publishable plugin и migrations.
3. Составить таблицу «решение Letar → общий пакет / шаблон / внутренняя интеграция».
   Проверить прямые и транзитивные workspace-зависимости, приватные пути, Windows/Unix-скрипты,
   обязательные env и hooks. Публичность репозитория не означает доступность пакета в npm.
4. Определить минимальный набор: тонкий create-пакет, Nx-плагин с конфигами/генераторами/миграциями,
   шаблон app, небольшая используемая app библиотека и начальные инструкции агентам.
   Записать точные пути владения для последующих сессий и допустимые направления зависимостей.
5. Уточнить предметную модель Game / PlatformRelease / LibraryEntry и справочники Genre / Studio /
   Platform. Объяснить области уникальности и пользовательское поведение при удалении ссылок.
   Выбрать политику управления общим каталогом без скрытого права менять чужие данные.
   Личные статусы, оценки и заметки доступны только владельцу.
6. Зафиксировать, можно ли иметь несколько версий одной игры для одной платформы, несколько
   личных записей, диапазон оценок и года, трактовку неизвестного кооператива и maxPlayers.
   Выбрать доступную в текущих формах реализацию повторяемых групп и зависимой валидации.
7. Выбрать локальный запуск PostgreSQL, регистрацию/вход без обязательного внешнего сервиса,
   идемпотентный seed и поведение seed в production. Указать реальный путь от создания до CRUD.
8. Описать контракты: фильтр/URL, работа формы/серверных ошибок, обновление списка,
   manifest версии стартера и структура общих/локальных агентских инструкций.
   Собственная lib не импортирует apps или generated приложения.
9. Выбрать границы поддержки версий, правила semver и минимальную проверку N-1 → N.
   Сверить планы зависимых задач и записать результат в этой задаче.

## Принятые решения

Заполняется исполнителем. Имена create-letar и пути будущих пакетов в родительской задаче
пока рабочие, их доступность в npm не проверена.

## Проверки и границы изменений

- Владение: эта задача, уточнения LT-091 и LT-093–LT-102; новая документация только при необходимости,
  с соблюдением индекса документации. Реализационные файлы не менять.
- Проверить очередь, локальные ссылки и dprint только по изменённым Markdown-файлам.
- Записать источники проверки API/версий и конкретные риски переносимости в результат.
- Завершить отдельным scoped-коммитом; push и публикация не входят в задачу.
