## Что и зачем

Часть [LT-091](LT-091-game-library-starter.md), решения — [LT-092](LT-092-starter-design.md).
Сделать создание самостоятельной монорепы: CLI вызывает preset общего плагина.
Финальный CRUD добавляется задачами LT-095–LT-098.

## Приёмка

- [ ] Одна документированная команда создаёт независимый workspace из упакованных пакетов.
- [ ] Созданы app и собственная lib, которую app реально импортирует; нет обратной зависимости.
- [ ] Установлены совместимые зависимости, зафиксирован lock-файл, доступны dev и проверки.
- [ ] Повторный запуск в непустой каталог завершается понятной ошибкой без потери файлов.
- [ ] Каркас не требует исходного Letar, приватных сервисов или глобального Nx;
      prerequisites пакетного менеджера явно описаны.

## План

1. По LT-092 определить точные файлы create-пакета и preset. Создать проекты через штатные
   генераторы и зарезервировать пути. Установку проверять как внешний пользователь.
2. Реализовать тонкую CLI: имя/путь проекта, ограниченный набор вопросов, понятные ошибки
   prerequisites и итоговые команды. Не заставлять новичка выбирать десятки стеков.
3. Вызвать preset выбранной версии плагина. Согласовать версии create-пакета и плагина;
   во время генерации не брать случайные latest-версии.
4. Сгенерировать корневые workspace/Nx/TypeScript/dprint/lint-конфиги, package scripts,
   gitignore, env.example и краткий README. Скрипты нового проекта используют локальные binaries.
   При этом команды в исходном Letar выполнять по его правилам глобального nx/bun.
5. Сгенерировать app на принятом стеке и отдельную пользовательскую lib.
   Реализовать полезный минимальный контракт lib из LT-092; app должен её использовать.
   Не копировать все внутренние библиотеки и правила Letar.
6. Подготовить точки интеграции БД, шаблонов приложения и agent context; бизнес-функции
   появятся в последующих задачах. Описать, как изменения примера попадут в preset.
7. Создать версионный manifest проекта и перечень управляемых/пользовательских файлов по LT-092.
   Сгенерированные личные исходники не должны обновляться простой заменой шаблона.
8. Проверить запуск в чистом каталоге из tarball и записать полную последовательность команд.

## Проверки и границы изменений

- Владение: create-пакет, preset, шаблоны root/app/lib и их проверки.
- Проверить корректное имя, конфликт путей, установку из tarball, импорт app → lib,
  доступность dev/build/lint/typecheck/test; исключить зависимость от корневого node_modules Letar.
- Использовать временные каталоги внутри .claude/artifacts; не форматировать весь checkout.
- Выполнить scoped проверки пакетов. Публичный релиз не входит в задачу.
