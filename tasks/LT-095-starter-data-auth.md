## Что и зачем

Часть [LT-091](LT-091-game-library-starter.md), решения — [LT-092](LT-092-starter-design.md).
Подготовить рабочий локальный фундамент CRUD: БД, auth, модели, политики, миграции и данные.

## Приёмка

- [ ] Чистый проект получает рабочую БД, миграции и seed по документированным командам.
- [ ] Регистрация, вход и выход работают локально без обязательного внешнего OAuth/email-сервиса.
- [ ] Модели отражают игру, платформенную версию, личную запись и справочники.
- [ ] Политики проверены на двух пользователях и не позволяют менять владельца/FK в обход прав.
- [ ] Генерируются схемы форм из @meta("form.*", ...); файлы generated не правятся вручную.
- [ ] Шаблон стартера содержит эти изменения, а не только внутренний демонстрационный app.

## План

1. Прочитать правила БД/auth, навыки zenstack-helper, better-auth, form-pipeline и README форм.
   Сверить текущие API/совместимость по документации; учесть ограничения ZenStack из LT-092.
2. В принятом app/шаблоне добавить PostgreSQL-конфигурацию и env.example.
   Дать одну понятную последовательность запуска с изолированной dev-базой; не обращаться
   к рабочим локальным или production-БД Letar.
3. Настроить Better Auth по контракту LT-092: регистрация, вход, выход, серверная сессия
   и пользовательский контекст ZenStack. Не подменять auth глобальным demo-пользователем.
4. Описать модели и связи; год/режимы хранить у платформенной версии, оценку/заметку — в личной
   записи. Добавить индексы и ограничения уникальности по решениям LT-092.
5. Явно реализовать матрицу прав каталога, справочников и личных записей.
   Учитывать nested writes, перепривязку FK, неизменяемость ownerId и доступ по relation.
6. Добавить метаданные форм, генерацию и типизированную серверную границу.
   Для мутаций валидировать вход на сервере; владельца брать из сессии, а не доверять payload.
7. Создать миграцию чистой БД и идемпотентный seed: разные годы/платформы/жанры/студии/режимы,
   включая контрпример для фильтров одной версии. Указать происхождение демонстрационных данных;
   старт не должен зависеть от внешнего игрового API или загрузки чужих изображений.
8. Ограничить демо-учётные данные локальным сценарием; не вводить production seed-endpoint.
   Обновить preset, env.example и краткую инструкцию запуска.

## Проверки и границы изменений

- Владение: schema/auth/db/seed/migrations и соответствующие файлы шаблона; UI CRUD — позже.
- Реальные проверки политики: чужая личная запись не читается/не меняется/не удаляется,
  ownerId и relation FK нельзя переставить в обход; сервер отклоняет неподходящий payload.
- Проверить чистую миграцию, повторный seed и сохранность пользовательских записей.
- После @@allow/@@deny применить auth-policy-validator; после auth — security-auditor
  по доступным инструкциям/инструментам, сохранив вывод в задаче.
- Запустить generate и scoped format/lint/typecheck/test; не выполнять db:push на чужих базах.
