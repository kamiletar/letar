## Что и зачем

Клиентские отчёты об ошибках уходят прямо на `errors.s3.letar.best` (`libs/glitchtip/src/client/index.ts`, `initClient`, опции `tunnel` нет). Brave Shields и другие блокировщики режут такой адрес по шаблону: он похож на Sentry-ingest (запрос `ERR_BLOCKED_BY_CLIENT`). У посетителей с блокировщиком ошибки страницы не доходят до GlitchTip, и о них никто не узнаёт. Обнаружено 2026-10-13 на production domwellbes.

Решение — туннель: SDK шлёт отчёт на свой же домен (например `/monitoring`), роут приложения проверяет, что отчёт предназначен нашему GlitchTip, и пересылает его на сервер. Для браузера это запрос к тому же домену, блокировщик его не трогает.

## Приёмка

- [ ] `initClient` принимает опцию `tunnel`, по умолчанию выключена (другие приложения не затронуты)
- [ ] Общий обработчик роута-приёмника в `libs/glitchtip` (проверка DSN/хоста назначения по разрешённому списку, лимит размера, без открытого прокси)
- [ ] Включено на domwellbes; в Brave с включёнными Shields отчёт доходит (проверка по тестовому событию в GlitchTip)
- [ ] Отдельно решено, включать ли на остальных приложениях

## План

1. Согласовать с владельцем библиотеки (изменение общей `libs/glitchtip`, много потребителей).
2. Опция `tunnel` + обработчик роута, тесты на проверку назначения.
3. Пробное включение на domwellbes (`/monitoring`), проверка в Brave.
4. Смежно: форма, которая бросает `throw` после отказа, создаёт ложные отчёты «необработанный отказ промиса» (4 формы domwellbes: клиенты, склады, смета, чертежи) — завести отдельной задачей после туннеля.
