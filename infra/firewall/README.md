# Firewall — docker-user-firewall

Скрипт default-deny для цепочки `DOCKER-USER` (IPv4, `FORWARD`) и, где нужно, `ip6tables INPUT`
(IPv6) на трёх production-серверах (s2, s3, mail). Почему это вообще нужно и почему `ufw` тут не
работает — [.claude/docs/firewall.md](/.claude/docs/firewall.md). История решения и разбор по
серверам — `PLAN-INFRA.md` §49, §57, §60.

## Зачем этот каталог

До 2026-08-08 три копии этого скрипта существовали **только на живых серверах**
(`/usr/local/sbin/docker-user-firewall.sh` + systemd-юнит `docker-user-firewall.service`), без
версии в git — как и `animatrona-pin-queue`/`animatrona-relay` из §60, ровно тот же класс проблемы:
конфигурация сетевой защиты трёх прод-серверов не имела истории правок и ревью, и при потере
сервера восстанавливалась бы по памяти.

## Структура

| Файл                           | Назначение                                                                 |
| ------------------------------ | -------------------------------------------------------------------------- |
| `docker-user-firewall.sh`      | общая логика — одна на все три сервера, параметризуется env-переменными    |
| `docker-user-firewall.service` | systemd-юнит (`oneshot`, `After=docker.service`), читает `EnvironmentFile` |
| `ports.s2.env`                 | allow-list s2                                                              |
| `ports.s3.env`                 | allow-list s3 + точечный host-deny для `ipfsstor4:42080`                   |
| `ports.mail.env`               | allow-list mail-сервера, IPv6-блок ОТКЛЮЧЁН (там свою роль играет ufw)     |

Раньше на каждом сервере был отдельный файл-скрипт с зашитым allow-list внутри. Здесь логика и
конфигурация разделены: один скрипт, три `.env`. Так различия между серверами видны построчно в
diff `.env`-файлов, а не потонут в трёх копипастах скрипта, которые придётся синхронизировать
руками при любой правке общей логики.

## ⚠️ Статус сверки с реальностью — ОТКРЫТЫЙ ВОПРОС

Содержимое `docker-user-firewall.sh` и трёх `ports.*.env` **реконструировано по документации**
(`PLAN-INFRA.md` §49/§57, `.claude/docs/firewall.md`), а не скопировано побайтово с серверов.
Причина: изменения на живых production-серверах делает только Deploy Agent (BlackCove) —
см. [deploy-coordination.md](/.claude/rules/deploy-coordination.md), эта сессия по правилам
монорепо не заходит на серверы по SSH сама.

Запрошена сверка у BlackCove через Agent Mail (тред `firewall-versioning`, 2026-08-08). До
получения ответа считать эти файлы **черновиком, не источником истины** — если понадобится
деплоить правку прямо сейчас, сначала получить реальное содержимое с сервера и сравнить построчно.

Известные пробелы в реконструкции:

- точный внешний интерфейс на mail-сервере не задокументирован в PLAN-INFRA (только s2 → `eth0`,
  s3 → `ens3`); оставлено на автоопределение;
- нет подтверждения, что реальный скрипт на серверах уже вынесен в переменные окружения так же,
  как здесь — вероятнее, что три копии на серверах хардкодят порты внутри себя без `.env`, и это
  первое расхождение, которое обнаружится при сверке.

## Деплой — пока ручная процедура, не автоматизировано

**Автодоставки через `deploy-affected.sh` пока нет.** Решение сознательное: не раздувать объём
этой задачи полной автоматизацией, когда версионированная копия сама по себе уже закрывает
основной риск (потеря конфигурации при потере сервера). Зафиксировано как открытый пункт в
`PLAN-INFRA.md`.

Текущая процедура обновления сервера после правки в этом каталоге — **через BlackCove**, вручную:

1. Правишь `docker-user-firewall.sh` и/или нужный `ports.<server>.env` в этом каталоге, коммитишь.
2. Просишь BlackCove скопировать обновлённый `docker-user-firewall.sh` →
   `/usr/local/sbin/docker-user-firewall.sh`, соответствующий `ports.<server>.env` →
   `/etc/docker-user-firewall.env`, `docker-user-firewall.service` →
   `/etc/systemd/system/docker-user-firewall.service` на нужном сервере.
3. **Обязательная подстраховка перед применением** — как везде в этом треке:
   `echo 'iptables -F DOCKER-USER' | at now + 10 min` (и `ip6tables -F INPUT`, если
   `ENABLE_IPV6_INPUT=1`) до `systemctl daemon-reload && systemctl restart docker-user-firewall`.
4. Проверка **снаружи**, с контрольным закрытым портом (`59999`) — см.
   [firewall.md](/.claude/docs/firewall.md#как-проверять-что-закрыто). Чтение `-S` ничего не
   доказывает, см. там же про IPv6-ловушку.
5. Только после подтверждения — снять подстраховку (`atrm`).

Это не входит в hard e2e gate и не автоматизировано нарочно — сетевые правила меняются редко и
рискованны при автоприменении без наблюдения.
