# infra/migrations — ручные скрипты переноса данных

Разовые/повторно запускаемые скрипты для операций с боевыми данными, которые не укладываются в
обычный `nx db:migrate` (перенос данных между `User`, склейка аккаунтов, owner-миграции при
смене email и т.п.). Запускаются вручную оператором (владельцем), не автоматизированы в
`deploy-affected.sh`.

## Конвенции

### Клиент БД — `ZenStackClient` напрямую, не через `lib/db.ts` приложения

```typescript
import { ZenStackClient } from '@zenstackhq/orm'
import { PostgresDialect } from 'kysely'
import { Pool } from 'pg'
import { schema } from '../../apps/<app>/src/generated/schema'

const prisma = new ZenStackClient(schema, {
  dialect: new PostgresDialect({
    pool: new Pool({ connectionString: process.env.DATABASE_URL }),
  }),
})
```

Импорт схемы — **относительный путь**, не алиас `@/generated/schema`: алиас резолвится только
внутри tsconfig самого приложения, при запуске `bun run infra/migrations/<file>.ts` вне
контекста приложения он не гарантированно резолвится.

Не использовать `getEnhancedPrisma()`/enhanced policy-клиент — access-policy (`@@deny('all',
true)` на core Better Auth моделях типа `Account`/`Session`) заблокирует нужные операции.
Не использовать encryption-прокси приложения (если есть, напр. `apps/auth-hub/src/lib/db.ts`),
если скрипт не расшифровывает/не перешифровывает данные, а только переносит `userId` FK —
зашифрованное содержимое остаётся непрозрачной строкой, трогать его не нужно.

### `DATABASE_URL` — inline при запуске, не из `.env`

Скрипт не грузит dotenv. Переменная передаётся явно в команде запуска на сервере:

```bash
cd /home/deploy/letar
DATABASE_URL="postgresql://user:pass@localhost:<port>/<db>" \
  bun run infra/migrations/<script>.ts
```

### `DRY_RUN` — семантика зависит от риска операции

- **Owner-migrations** (перенос данных на предсказуемо пустые/предвиденные дубли, напр.
  `kami-owner-migration.ts`): `DRY_RUN === '1'` включает dry-run. Без переменной — скрипт
  **применяет** изменения по умолчанию. Приемлемо, когда результат предсказуем и риск низкий.
- **Более рискованные/необратимые операции** (напр. `auth-hub-merge-accounts.ts` — слияние
  двух потенциально живых аккаунтов с активными сессиями): **инверсия дефолта** —
  `DRY_RUN !== '0'` считается dry-run, то есть без явного `DRY_RUN=0` ничего не меняется.

Каждый новый скрипт должен явно решить и задокументировать в своём докстринге, какую из двух
семантик он использует — не полагаться на то, что оператор помнит конвенцию по умолчанию.

### Идемпотентность

Скрипт должен безопасно переживать повторный запуск: если целевые данные уже перенесены/
удалены — ранний `console.log(...)` + `process.exit(0)`, без ошибок и без повторных мутаций.
Проверяется до открытия транзакции.

### Транзакционность

Все мутации — внутри одной `prisma.$transaction(async (tx) => { ... })` (или, при работе через
сырой `pg`, ручной `BEGIN`/`COMMIT`/`ROLLBACK` с `client.release()` в `finally`). Частичное
применение при ошибке недопустимо для операций с боевыми данными.

### Docstring в начале файла

Каждый скрипт начинается с докстринга: назначение, что переносится/удаляется, обработка
конфликтов (unique-constraints), пример команды запуска (dry-run и реальный), требование
бэкапа БД перед запуском необратимых операций.

### Бэкап — ответственность оператора, не скрипта

`pg_dump` не встраивается в TypeScript-скрипт (лишняя зависимость на наличие `pg_dump` в PATH
среды запуска). Вместо этого — явное требование в докстринге + текстовый warning в консоли при
старте необратимых операций.

### Аудит

В большинстве приложений нет отдельной `AuditLog`-модели, покрывающей ручные infra-скрипты —
заводить её ради разовой операции непропорционально. Вместо этого — structured консоль-лог
(`✅`/`⚠️`/`❌`-префиксы) с рекомендацией перенаправлять stdout в файл при реальном запуске:

```bash
... | tee infra/migrations/logs/<script>-$(date +%Y%m%d-%H%M%S).log
```

## Существующие скрипты

- `kami-owner-migration.ts`, `dashboard-owner-migration.ts`, `archetest-owner-migration.ts`,
  `animatrona-tracker-owner-migration.ts` — перенос данных владельца со старых email-аккаунтов
  на `kami@letar.best` (Этап 8.5 корневого `PLAN.md`, разовая операция, уже выполнена).
- `auth-hub-merge-accounts.ts` — параметризованный merge двух существующих аккаунтов в
  auth-hub (Этап 8.5, переиспользуемый инструмент, не одноразовый).
