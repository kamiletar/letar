# acme-dns

Крошечный авторитативный DNS-сервер, который умеет ровно одно: отдавать `TXT`-записи для
ACME-челленджей. Нужен, чтобы выпускать wildcard-сертификат `*.letar.best` через DNS-01, **не
обращаясь к API регистратора** — ни при выпуске, ни при продлении каждые 90 дней, ни при
добавлении нового поддомена.

Трек и обоснование выбора — [PLAN-INFRA.md §48](/PLAN-INFRA.md).

## Как это работает

В зоне `letar.best` (панель Dynadot) однократно создаются три записи:

| Поддомен          | Тип     | Значение                 | Зачем                                                      |
| ----------------- | ------- | ------------------------ | ---------------------------------------------------------- |
| `acme`            | `NS`    | `ns-acme.letar.best`     | делегирует подзону нашему acme-dns                         |
| `ns-acme`         | `A`     | IP сервера с acme-dns    | адрес самого сервера имён                                  |
| `_acme-challenge` | `CNAME` | `<uuid>.acme.letar.best` | уводит челлендж в acme-dns; `<uuid>` — из шага регистрации |

⚠️ **Имя сервера имён (`ns-acme`) намеренно не совпадает с делегируемой зоной (`acme`).** README
самого acme-dns предлагает self-delegation — `A` и `NS` на одном имени, где `A` работает glue-записью.
В панели Dynadot это не проходит: «Невозможно устанавливать NS-запись и A-запись одновременно для
одного поддомена» (проверено 2026-08-06). Разнесение по двум именам решает запрет и заодно снимает
нужду в glue вообще — `ns-acme.letar.best` резолвится из родительской зоны `letar.best` как обычная
`A`-запись, а не как склейка внутри делегированной подзоны.

Если будешь переносить схему на другого регистратора — сначала проверь, разрешает ли он `A`+`NS`
на одном имени; вариант с двумя именами работает везде, поэтому он и выбран основным.

После этого Let's Encrypt при проверке `_acme-challenge.letar.best` идёт по `CNAME` в acme-dns, а
ACME-клиент (lego внутри Traefik) кладёт туда `TXT` через HTTP API. Регистратор в этой цепочке не
участвует вообще.

Один `CNAME` покрывает и `*.letar.best`, и апекс `letar.best` — LE проверяет для обоих одно и то же
имя `_acme-challenge.letar.best`.

## Развёртывание

Деплой — **только через BlackCove** ([deploy-coordination.md](/.claude/rules/deploy-coordination.md)).

```bash
cd /home/deploy/letar/infra/acme-dns
docker compose up -d
```

### ⚠️ Правка `config.cfg` требует `docker restart`, а не `up -d`

Конфиг смонтирован read-only volume'ом (`./config:/etc/acme-dns:ro`). Файл на хосте меняется сразу,
но `docker compose up -d` контейнер **не пересоздаёт** — compose сравнивает только описание сервиса
в `docker-compose.yml`, содержимое смонтированных файлов ему безразлично. Живой процесс продолжает
работать на конфиге, прочитанном при старте.

```bash
docker restart acme-dns
docker logs acme-dns | grep 'Using config file'   # должна появиться новая строка со свежим временем
```

Коварство в том, что `up -d` отрабатывает без ошибок и выглядит успешным. Прецедент 2026-08-06:
после переключения `disable_registration = true` первый `POST /register` ещё прошёл бы на старом
конфиге — то есть проверка «регистрация закрыта?» дала бы ложный результат в опасную сторону.
**Любую правку `config.cfg` заканчивать рестартом и проверять по логу, что конфиг перечитан.**

### Порт 53 может быть занят

На Ubuntu `systemd-resolved` держит 53 на stub-интерфейсе и мешает биндингу `0.0.0.0:53`:

```bash
ss -ulnp | grep ':53'
```

Если занят — в `/etc/systemd/resolved.conf` выставить `DNSStubListener=no`, затем
`systemctl restart systemd-resolved`. Проверить, что резолвинг на сервере не сломался.

### Firewall

```bash
ufw allow 53/tcp
ufw allow 53/udp
```

HTTP API наружу **не открывать** — он опубликован только на `127.0.0.1:8053`.

## Регистрация аккаунта (однократно)

⚠️ В рабочем конфиге стоит `disable_registration = true` — чтобы завести аккаунт, сначала временно
вернуть `false` и **сделать `docker restart`** (см. врезку выше про `up -d`).

```bash
mkdir -p /home/deploy/lego && chmod 700 /home/deploy/lego
curl -s -X POST http://127.0.0.1:8053/register
```

Ответ содержит `username`, `password`, `fulldomain`, `subdomain`. Из него нужны:

- `fulldomain` — в `CNAME`-запись `_acme-challenge` (см. таблицу выше);
- весь JSON — в файл аккаунтов lego `/home/deploy/lego/acme-dns-accounts.json` (`chmod 600`), формат —
  объект, где ключ это домен: `{"letar.best": { ...ответ регистрации... }}`.

Не сохранять ответ во временный файл «пока разберусь» и не пересылать в переписку агентов —
писать сразу в целевой файл. Прецедент 2026-08-06: первый аккаунт пришлось ротировать именно
из-за этого.

⚠️ Учётные данные из этого ответа — секрет: кто ими владеет, тот подменяет ACME-челленджи всей
зоны. Хранить как остальные секреты ([secret-manager.md](/.claude/docs/secret-manager.md)), в
публичный репозиторий не коммитить.

После регистрации выставить `disable_registration = true` в `config/config.cfg` и передеплоить.

## Аккаунт на одно имя (не на зону)

Нужен, когда сертификат требуется серверу, которому ключ зоны давать нельзя. Первый такой случай —
`media.letar.best` на s3: сервер staging'овый, а имя продакшен-домена. Ключ `letar.best` там дал бы
компрометации s3 валидный сертификат на **весь** `letar.best`; аккаунт на одно имя сжимает худший
случай до этого одного имени. Решение владельца 2026-08-08,
[PLAN-INFRA.md §48 M2](/PLAN-INFRA.md).

Отличий от зонного аккаунта ровно два, и оба легко перепутать:

| Что                             | Аккаунт зоны      | Аккаунт на одно имя     |
| ------------------------------- | ----------------- | ----------------------- |
| `CNAME` у регистратора          | `_acme-challenge` | `_acme-challenge.media` |
| Ключ в `acme-dns-accounts.json` | `letar.best`      | `media.letar.best`      |

⚠️ **Ключ обязан совпасть с именем, на которое заказывается сертификат, буквально.** Поиск в файле
аккаунтов точный, без подъёма по иерархии — у нас это уже проверено провалом: роутер дашборда
просил `traefik.s3.letar.best`, в файле лежал `s3.letar.best`, lego ключа не нашёл, полез
регистрировать новый аккаунт и получил `404` (регистрация закрыта). Симптом выглядит как проблема
доступа к acme-dns, хотя на деле это несовпадение ключа.

### Порядок

1. **На s2** временно вернуть `disable_registration = false` и **`docker restart acme-dns`**
   (не `up -d` — см. врезку выше, иначе следующий шаг отработает на старом конфиге и соврёт).
2. Зарегистрировать аккаунт и **сразу** записать ответ в целевой файл на целевом сервере. Не в
   промежуточный файл «пока разберусь» и не в переписку агентов — первый аккаунт пришлось
   ротировать именно из-за этого (2026-08-06).
   ```bash
   curl -s -X POST http://127.0.0.1:8053/register
   ```
3. Вернуть `disable_registration = true` и **снова** `docker restart acme-dns`. Проверить, что
   закрылось, а не «должно было закрыться»:
   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:8053/register   # ждём 403
   ```
4. У регистратора завести `CNAME _acme-challenge.media.letar.best` → `fulldomain` из ответа.
   Дождаться распространения:
   ```bash
   dig +short CNAME _acme-challenge.media.letar.best @1.1.1.1
   ```
5. **На s3** добавить ключ в существующий файл, не перезаписывая его — там уже лежит
   `s3.letar.best`, и потерять его значит остановить продление всех staging-доменов:
   ```bash
   python3 - <<'PY'
   import json, os
   p = '/home/deploy/lego/acme-dns-accounts.json'
   d = json.load(open(p))
   d['media.letar.best'] = json.loads(os.environ['ACC'])   # ответ из шага 2
   json.dump(d, open(p, 'w'))
   PY
   chmod 600 /home/deploy/lego/acme-dns-accounts.json
   ```
6. Traefik перечитает файл при следующем заказе сертификата — роутер `media` уже несёт
   `tls.certresolver=dns` (`infra/media-server/docker-compose.production.yml`).

ℹ️ **`allowfrom` при регистрации сознательно не используем.** acme-dns умеет ограничивать аккаунт
списком source-IP, но здесь это второй экземпляр той же самой защиты: API уже закрыт access-list'ом
NPM ровно на IP s3. От смены IP s3 обе развалятся одинаково, а поломка вылезет через 90 дней при
продлении — то есть цена «ещё одного места, где записан IP» есть, а выигрыша нет. Если API когда-то
станет доступен шире одного адреса — пересмотреть.

## Проверка (DoD милестона M1a)

Цепочка делегирования проверяется **без Traefik**, голым lego. Ставить его на сервер не нужно и не
надо — постоянным ACME-клиентом будет Traefik, а отдельный бинарь на s2 станет мусором, который
никто не обновляет. Запускаем одноразовым контейнером:

```bash
docker run --rm \
  --network host \
  -v /home/deploy/lego:/acme-data \
  -e ACME_DNS_API_BASE=http://127.0.0.1:8053 \
  -e ACME_DNS_STORAGE_PATH=/acme-data/acme-dns-accounts.json \
  goacme/lego:v4 \
  --dns acme-dns \
  --server https://acme-staging-v02.api.letsencrypt.org/directory \
  --email kami@letar.best --accept-tos \
  --path /acme-data \
  -d '*.letar.best' -d letar.best run
```

- `--network host` обязателен: API acme-dns слушает `127.0.0.1:8053`, из bridge-сети контейнер туда
  не достучится.
- Монтируется **каталог**, а не одиночный файл аккаунтов: lego может переписать хранилище, а bind
  одиночного файла на такое реагирует плохо.
- ⚠️ **Точка монтирования — `/acme-data`, а не `/lego`.** В образе `goacme/lego` путь `/lego` уже
  занят: это ELF-бинарь самого lego, его entrypoint. Монтирование каталога поверх файла падает с
  `not a directory` — runc жалуется именно на это, просто из текста ошибки неочевидно, про какую
  из двух сторон (источник или назначение) речь. Правило общее: **прежде чем выбирать destination
  для `-v`, проверить, что этот путь в образе свободен**:
  ```bash
  docker run --rm --entrypoint sh <image> -c 'ls -la / '
  ```
- Файл аккаунтов лежит под `/home/deploy/`, а не в `/root/`, потому что долгосрочный потребитель —
  Traefik, тоже контейнер, и держать секрет там, куда ему удобно смотреть, разумнее. Права от
  этого не слабее: каталог `root:root 700`, файл `600` — пользователь `deploy` владеет родительским
  каталогом, но внутрь не войдёт и файл не прочитает.
- ⚠️ **Сначала staging-директория Let's Encrypt**, как в команде выше. У боевой жёсткие лимиты на
  неудачные попытки, а это первый прогон цепочки. На боевую переключаться (убрать `--server`)
  только после зелёного staging-прогона.

Почта ACME-аккаунта — `kami@letar.best` (решение владельца 2026-08-06). На неё приходят
уведомления Let's Encrypt об истечении сертификатов, поэтому доставку на этот ящик стоит
проверять — см. canary-мониторинг почты, `PLAN.md` Этап 0.7.

Промежуточные проверки, если что-то не сходится:

```bash
# делегирование работает? должен ответить сам acme-dns, не Dynadot
dig +short NS acme.letar.best
dig @acme.letar.best TXT test.acme.letar.best

# CNAME на месте?
dig +short CNAME _acme-challenge.letar.best
```

⚠️ Пока идёт отладка, использовать staging-директорию Let's Encrypt
(`--server https://acme-staging-v02.api.letsencrypt.org/directory`) — у боевой жёсткие лимиты на
неудачные попытки, и упереться в них посреди отладки очень легко.

## Бэкапы

От этого сервиса зависит **продление всех сертификатов зоны**. Если он тихо умрёт, выяснится это
через 90 дней в худший момент.

Бэкапит **dashboard-agent** (с версии 0.10.0, 2026-08-07), cron-задача `acme-dns-backup-s2` в 03:30:

- `data/` — база выданных поддоменов;
- `/home/deploy/lego/acme-dns-accounts.json` — файл аккаунтов lego, без него клиент не сможет обновить
  `TXT`. Восстановить его нельзя: `disable_registration = true`, а даже с открытой регистрацией
  новый аккаунт даст новый `fulldomain`, то есть потребует правки боевой `CNAME`-записи в зоне.

Оба источника обязательны — при отсутствии любого бэкап падает с ошибкой, а не создаёт неполный
архив. Результат — `/home/deploy/letar/backups/acme-dns/acme-dns_<type>_<timestamp>.tar.gz`
(`chmod 600`, ротация 14), дальше уезжает через Resilio вместе с остальными бэкапами.

Отдельная cron-задача `acme-dns-backup-freshness-check` (раз в 6 часов) алертит `BACKUP_FAILED`,
если свежего архива нет дольше 30 часов — бэкапы имеют свойство переставать идти молча (урок
Maddy, дважды за месяц). Механизм, ручной прогон и порядок восстановления —
[backup-architecture.md](/.claude/docs/backup-architecture.md#бэкап-acme-dns-s2).

⚠️ Архив содержит учётные данные и **не шифруется** — как `nginx_*.tar.gz` (приватные ключи всех
сертификатов) и `maddy_*.tar.gz` (DKIM). Это следование существующей политике, а не недосмотр:
шифровать один бэкап из трёх непоследовательно, а в момент аварии добавляет зависимость от
age-ключа. Вопрос «шифровать ли бэкапы на покое» — общий для всех трёх, см. §48.

## Версия образа

Пин `joohoi/acme-dns:v1.0`. **Не поднимать до v2.x.**

В образе `v2.0.2` сломана поддержка sqlite: бинарь собран без драйвера, и всё выглядит здоровым до
первого обращения к базе. Контейнер стартует, DNS-листенеры на `0.0.0.0:53` поднимаются, HTTP
отвечает — а `POST /register` возвращает пустой ответ, потому что горутина запроса паникует:

```
error sql: unknown driver "sqlite3" (forgotten import?)
panic serving ...: runtime error: invalid memory address or nil pointer dereference
database/sql.(*DB).conn(0x0, ...)
```

Известный баг апстрима — [acme-dns#403](https://github.com/acme-dns/acme-dns/issues/403), на `v1.0`
не воспроизводится. Проверено вживую на s2 2026-08-06.

Коварство в том, что `docker ps` показывает `Up`, healthcheck (если его навесить на TCP-порт) тоже
зелёный, и сломанность проявляется **только** на запросе к БД. Если когда-нибудь будешь поднимать
версию — проверяй не запуском контейнера, а именно `POST /register`.
