# Дублирование одного и того же дерева для мобильного/десктопного варианта

## Симптом

Компонент рендерит ОДИН И ТОТ ЖЕ контент дважды — два соседних JSX-блока с одинаковыми детьми
(тот же текст, та же кнопка/ссылка), переключаемые видимостью через `display={{ base: '...',
md: '...' }}` (responsive-пропы Chakra UI). Внешне на экране всё выглядит правильно — виден ровно
один вариант. Но в DOM физически присутствуют ОБА: Chakra `display` компилируется в CSS
media-query, а не в условный рендер — скрытый вариант остаётся в дереве с `display: none`.

Playwright-локаторы, которые ищут элемент по роли/тексту/aria-label, матчат оба экземпляра.
Дальнейшее поведение зависит от того, есть ли в тесте `.first()`:

- без `.first()` — `strict mode violation: resolved to 2 elements`;
- с `.first()` — резолвится в порядке DOM, который не обязан совпадать с видимым вариантом
  (мобильный блок обычно идёт первым в разметке); `toBeVisible()` падает, `.click()` таймаутится
  на скрытом элементе.

Баг воспроизводится одинаково на всех браузерах, но при параллельных workers чаще всего первым
проявляется на одном конкретном (в прецеденте ниже — webkit из-за порядка запуска) — это может
привести к неверной первоначальной диагностике «баг только в этом браузере».

## Root cause

Разработчик рассуждает в терминах «два визуальных варианта под разные экраны» и пишет два JSX-
блока — по одному на `Flex`/`Box`/`HStack` с противоположными `display`. Это адаптивный CSS-
паттерн для _разного_ контента (например гамбургер-меню vs полная навигация), скопированный по
аналогии на случай, когда контент на самом деле _один и тот же_, просто с другой раскладкой
(перенос строк, порядок элементов).

Не каждое дублирование `display={{ base:`/`md:` — баг. Отличать по содержимому дублируемых
блоков:

- **Разный контент** (иконка гамбургера vs список ссылок навигации, таблица vs карточки для того
  же списка через общий компонент) — легитимный паттерн, ничего чинить не надо.
- **Тот же компонент/то же поддерево с интерактивными элементами** (ссылки, кнопки, чекбоксы,
  инпуты), вызванный дважды подряд с противоположными `display` — это и есть баг: одинаковый
  функциональный элемент существует в DOM в двух экземплярах.

Визуальные/декоративные дубли (иконки, разделители) технически тот же паттерн, но безопасны —
локаторы Playwright на них обычно не ставятся.

## Фикс

Один источник разметки, адаптивность — через CSS-пропы на конкретных под-элементах, а не через
дублирование всего дерева:

```tsx
// ❌ Два Flex-блока с одинаковыми детьми
<Flex display={{ base: 'flex', md: 'none' }}>
  <Badge>{tag}</Badge>
  <BookmarkButton article={article} />
</Flex>
<Flex display={{ base: 'none', md: 'flex' }}>
  <Badge>{tag}</Badge>
  <Text>{title}</Text>
  <BookmarkButton article={article} />
</Flex>

// ✅ Один рендер, раскладка меняется через wrap/order
<Flex wrap="wrap" gap={2}>
  <Badge order={{ base: 1, md: 1 }}>{tag}</Badge>
  <BookmarkButton order={{ base: 2, md: 3 }} article={article} />
  <Text order={{ base: 3, md: 2 }} w={{ base: '100%', md: 'auto' }}>{title}</Text>
</Flex>
```

Если раскладки действительно несовместимы для общего дерева (не просто перенос/порядок) — выносить
общую интерактивную часть (кнопку, ссылку) в отдельный компонент/переменную и рендерить её
**один раз**, оборачивая вокруг неё разный по вёрстке контейнер, а не копируя саму интерактивную
часть в оба блока.

⚠️ Chakra UI v3 не имеет отдельных компонентов `Hide`/`Show` (они были в v2 и удалены) — способ
переключения видимости в v3 только через `display`/`hideFrom`/`hideBelow` style-пропы на самом
элементе. Это не отменяет правило: пропы применяются к ОДНОМУ элементу, а не создают повод
рендерить дерево дважды.

## Где встречалось

- **pravda** — `apps/pravda/src/app/_components/mdx/article.tsx` рендерил каждую статью дважды
  (отдельный `Flex` для мобильного лейаута, отдельный для десктопного, оба с копией `{children}`
  и своим `<BookmarkButton>`). Ломало `bookmarks.spec.ts` и `cross-refs.spec.ts` (strict mode
  violation на вложенных `<CrossRef>`, таймаут клика по скрытому дублю). Исправлено в
  `bbc5aad2` (2026-08-12) — единственный рендер, адаптивность через `wrap`/`order`.
- **mandala** — `apps/mandala/src/app/(admin)/admin/layout.tsx` (строки 38-46 на момент находки,
  2026-08-13) вызывал `<AdminBreadcrumbs pathNames={PATH_NAMES} />` дважды: внутри мобильного
  `<HStack display={{ base: 'flex', md: 'none' }}>` рядом с гамбургер-меню и внутри десктопного
  `<Box display={{ base: 'none', md: 'block' }}>`. `AdminBreadcrumbs`
  (`libs/admin-ui/src/layout/admin-breadcrumbs.tsx`) рендерит реальные `<a>`-ссылки через
  Chakra `Breadcrumb.Link`/`Link` — те же ссылки существовали в DOM в двух экземплярах. На момент
  находки e2e-тестов на breadcrumbs в `mandala-e2e` не было, поэтому баг ничего не ломал видимо,
  но представлял собой ту же мину замедленного действия, что и в pravda: первый же локатор без
  `.first()` на breadcrumb-ссылку упал бы с strict mode violation.
- Точечная проверка ~53 файлов монорепо с похожим `display={{ base:`/`md:`-паттерном (2026-08-13)
  других случаев не выявила — весь остальной найденный код оказался легитимным (гамбургер vs
  полная навигация, таблица vs карточки через общий `AdminResponsiveList`, скрытие текстовой
  подписи рядом с иконкой внутри одного экземпляра компонента).

## Чеклист при ревью похожего кода

- Два соседних JSX-блока с противоположными `display={{ base:`/`md:` — открой оба и сравни
  содержимое построчно. Если совпадают компонент и интерактивные дочерние элементы (не просто
  оба «что-то показывают») — это дубль, а не адаптивность.
- Есть e2e-локатор на элемент внутри такого блока без `.first()`/`.filter()` — под подозрением
  в первую очередь: skipped/failed тест на strict mode violation почти наверняка означает именно
  это дублирование, а не проблему конкретного браузера.
