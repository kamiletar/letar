# `@letar/electron-storage`: мутация фолбэка портила `defaultValue` на весь процесс

⚠️ Класс ловушки: выглядит как рабочий код, ломается только на «чистом» состоянии (нет
файла / файл не читается) и только если вызывающий код мутирует результат `load()`/`loadSync()`
на месте. До 2026-09-09 баг был реальным — найден при аудите потребителей после миграции
восьми JSON-хранилищ `apps/animatrona/main/services/**` на `createJsonStore`.

## Механизм (до фикса)

`createJsonStore<T>(filename, defaultValue, options)` на фолбэке (файла нет либо
чтение/парсинг упали) возвращал значение так:

```ts
function fallbackValue(): T {
  return mergeDefaults ? { ...defaultValue } : defaultValue
}
```

Копия делалась **только** при `mergeDefaults: true`. Без этой опции (значение по умолчанию для
`createJsonStore`) фолбэк отдавал **саму ссылку** на `defaultValue`, которую держит замыкание
стора — общую для всех вызовов `load()`/`loadSync()` за время жизни процесса.

Если `defaultValue` — объектный литерал или массив (`{ items: [] }`, `[]`, `{ counter: 0 }`), а
вызывающий код мутирует результат на месте (`data.items.push(x)`, `data.field = y`,
`Array.prototype.sort()`, `data.items = data.items.filter(...)` — переприсваивание поля тоже
мутация родительского объекта), эта мутация необратимо портит `defaultValue` для всех
последующих вызовов **в этом процессе**.

### Почему не ловится сразу

Первая мутация обычно происходит перед первым `save()` — то есть в момент, когда файла ещё нет.
После `save()` файл появляется, и `load()` дальше читает с диска, а не фолбэк — баг не
проявляется. Он всплывает только когда фолбэк вызывается **повторно** после того, как
`defaultValue` уже был мутирован: файл удалили/сбросили настройки, файл стал нечитаем (битый
JSON), либо тот же `defaultValue`-литерал использован в нескольких сторах.

## Конкретные найденные случаи

Реальные потребители `createJsonStore` без `mergeDefaults`, мутирующие результат на месте, на
момент аудита (2026-09-09):

- **`apps/label-printer-desktop/main/ipc/profiles.handlers.ts`** — `profiles:create` делает
  `data.profiles.push(newProfile)`, `profiles:delete` — `data.profiles.splice(index, 1)`. Оба
  мутируют `data`, полученный из `profilesStorage.load()`, на месте.
- **`apps/label-printer-desktop/main/ipc/database.handlers.ts`** — `database:addJob` делает
  `data.jobs.push(newJob)`; `database:history` вызывает `data.jobs.sort(...)`
  (`Array.prototype.sort` — тоже мутация на месте, не создаёт новый массив);
  `database:deleteJobs` — `data.jobs = data.jobs.filter(...)` (переприсваивание поля мутирует
  родительский объект `data`, даже если сам массив новый).
- **`apps/label-printer-desktop/main/ipc/export.handlers.ts`** — отдельный `createJsonStore` на
  тот же файл (`STORAGE_FILES.history`) с собственным литералом `{ jobs: [] }`; сам по себе не
  делит `defaultValue` с `database.handlers.ts`, но подвержен тому же классу через свои ридеры.

До фикса библиотеки (ниже) правильный обход был ручным — восемь хранилищ
`apps/animatrona/main/services/**`, смигрированные на `createJsonStore` ранее (коммит
`be64ea94`), брали копию на своей стороне при чтении: `[...store.loadSync()]` для массивов,
`{ ...store.loadSync() }` для объектов (`history-store.ts`, `subscription-store.ts`,
`templates-store.ts`, `federation/stores/federation-store.ts`, `bonus/bonus-store.ts`). Эти
заплатки безвредны и после фикса ниже (двойное копирование, не баг), убирать их не обязательно.

## Фикс (2026-09-09)

`fallbackValue()` теперь **всегда** отдаёт свежую глубокую копию через `structuredClone`,
независимо от `mergeDefaults`:

```ts
function fallbackValue(): T {
  return structuredClone(defaultValue)
}
```

`structuredClone` даёт глубокую копию (в отличие от прежнего `{ ...defaultValue }`, который
копировал только верхний уровень — вложенный массив/объект внутри дефолта всё равно остался бы
общей ссылкой). Оправдано тем, что значение стора всегда JSON-совместимые данные (то, что
реально проходит через `JSON.parse`/`JSON.stringify` при работе с файлом) — ограничения
`structuredClone` на функции/DOM-узлы/etc. здесь не применимы.

Тест-регрессия — `libs/electron-storage/src/lib/json-store.spec.ts`:
«без mergeDefaults отсутствие файла ТОЖЕ отдаёт свежую копию — два loadSync() подряд не
возвращают одну ссылку» и «мутация fallback-значения не переживает даже после того, как файл
появился и снова пропал».

## Что не переносилось

Сами найденные потребители (`label-printer-desktop`) не переписывались — фикс на уровне
библиотеки закрывает баг для них автоматически (следующий `load()`/`loadSync()` после фикса
получает независимую копию). Правка их internal-логики (например, замена `sort()` на
`toSorted()`, чтобы не мутировать даже переданный объект) не требуется для устранения этого
конкретного класса бага и не делалась.

## Аудит: как искать этот класс бага у других потребителей

```bash
git grep -n "createJsonStore" -- 'apps/*' 'libs/*'
```

Для каждого найденного вызова:

1. Какой `defaultValue` — примитив (`null`, число, строка) неуязвим по построению;
   объект/массив — потенциально уязвим (уже не после фикса библиотеки, но полезно понимать
   природу риска при написании нового кода поверх `JsonStore`).
2. Мутирует ли вызывающий код результат `load()`/`loadSync()` **на месте**, вместо `{ ...data }`/
   `[...data.items]` при чтении. После фикса библиотеки это уже не портит `defaultValue`
   безвозвратно, но по-прежнему может тихо портить закешированное значение при `cacheTtlMs > 0`
   (кеш хранит ту же ссылку, что вернул `load()`) — так что писать новый код лучше сразу без
   мутации на месте, независимо от того, что библиотека теперь подстраховывает фолбэк.
