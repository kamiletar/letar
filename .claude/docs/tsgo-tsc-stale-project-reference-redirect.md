# tsgo/tsc: project-reference редирект уводит typecheck на устаревший/несуществующий `.d.ts`

Оба варианта ниже — следствие одного механизма: `tsgo --noEmit`/`tsc --noEmit -p` для импорта
библиотеки идёт не по `paths`, а по графу `references` из `tsconfig.json` приложения-потребителя,
и подставляет вместо исходника скомпилированный `.d.ts`.

## Вариант A: `tsgo` — устаревший `libs/<name>/dist/*.d.ts`

Верно, что «`references` не используются приложениями» (см. `libs.md` § «Подключение к
приложению»), пока у библиотеки нет **локального** `dist/` (генерируется её собственным
таргетом `typecheck`, не `typecheck:tsgo` — см. `libs/ui/project.json`). Если `dist/*.d.ts`
физически существует и разошёлся с `src/index.ts`, `tsgo --noEmit` приложения-потребителя
делает project-reference редирект на устаревший скомпилированный `.d.ts` вместо исходника —
новый экспорт из библиотеки тихо не виден (`TS2305: has no exported member`), а при удалении
`dist/` — требует его пересборки (`TS6305`).

`tsc` (не `tsgo`) в такой ситуации ведёт себя иначе и на новый экспорт не жалуется — поэтому баг
всплывает только в быстром `typecheck:tsgo`, который и гоняют приложения.

Наступили 2026-08-04 при добавлении `FileTrigger` в `@letar/ui` — `dist/index.d.ts` библиотеки
был собран ранее (кем/чем — не установлено, `dist/` не в git) и не содержал новый экспорт.

**Фикс:** после добавления/переименования публичного экспорта в библиотеке, у которой уже есть
локальный `dist/`, пересобрать декларации — `nx typecheck <lib>` (не `typecheck:tsgo`, у него
нет `--emitDeclarationOnly`). Проверить наличие `dist/` быстро: `ls libs/<name>/dist`.

## Вариант B: обычный `tsc` — редирект в `out-tsc/spec/`, который никто не собирает

Оговорка «`tsc` ведёт себя иначе» из варианта A касается только _устаревшего_ `.d.ts`. От
_отсутствующего_ обычный `tsc --noEmit -p` не застрахован ровно так же — и промахивается ещё
неприятнее.

Ссылка вида `{ "path": "../../libs/<name>" }` ведёт на **solution-конфиг** библиотеки
(`files: []` + `references` на `tsconfig.lib.json` и `tsconfig.spec.json`). Оба подпроекта
включают `src/**/*.ts`, то есть претендуют на один и тот же исходник, и TypeScript выбирает
**последний** в списке. Порядок в `libs/*/tsconfig.json` никем не выровнен:

- `libs/email` — `spec`, затем `lib` → редирект в `dist/` (лежит рядом, собирается таргетом
  `typecheck` библиотеки);
- `libs/redis-client` — `lib`, затем `spec` → редирект в `out-tsc/spec/`, **который не собирает
  ни один таргет вообще**.

Второй случай — вечно красный `TS6305: Output file '…/out-tsc/spec/src/index.d.ts' has not been
built`. Первый зелёный только по случайности: `dist/` в `.gitignore`, так что на свежем клоне он
падает точно так же.

Дальше идёт каскад, который легко принять за отдельные баги: провалившийся редирект делает весь
модуль `any`, и любой колбэк по его значению получает `TS7006: implicitly has an 'any' type`.
**Аннотации типов в этих местах — не починка, а маскировка**: они гасят симптом и оставляют
библиотеку нетипизированной. Проверяется позитивным контролем — присвоить результат функции
библиотеки заведомо неверному типу и убедиться, что `tsc` ругается по существу (`TS2322`), а не
молчит.

**Фикс (`dashboard-agent`, 2026-08-07): убрать `references` на библиотеки из
`apps/<app>/tsconfig.json`** — тогда редиректа нет, библиотека проверяется по исходникам, и
никаких предварительно собранных артефактов не требуется. Это совпадает и с тем, как приложение
собирается в проде (esbuild/Next.js бандлят исходники через `customConditions`).

⚠️ Вместе с `references` придётся убрать и `rootDir` — исходники библиотек лежат вне него, и
включённые в программу файлы дают `TS6059: not under 'rootDir'`. Триггер именно `rootDir`;
`outDir` заставляет TypeScript вывести `rootDir` самостоятельно, поэтому уходит следом.
`declaration` при этом **оставить**: `@nx/esbuild` без него не резолвит entry point, и таргет
`build` падает с `Could not resolve "apps/<app>/src/index.ts"`.

Дальнейший каскад этого же фикса на приложениях, наследующих `outDir`/`rootDir` из общего
пресета (а не задающих их напрямую) — отдельный, ещё более разветвлённый случай, см.
[tsconfig-preset-rootdir-outdir-cascade](/.claude/docs/tsconfig-preset-rootdir-outdir-cascade.md).
