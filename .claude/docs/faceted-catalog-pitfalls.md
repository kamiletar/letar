# Каталог с фильтрами: грабли фасетной навигации

Любой каталог товаров с фильтрами (цвет, размер, бренд, категория и т.п.) на Next.js + PostgreSQL
рано или поздно упирается в три технические проблемы. Все три не видны на маленьком каталоге
(десятки-сотни товаров) и проявляются только при росте — поэтому проще заложить решение сразу,
чем чинить постфактум. Документ описывает проблему и решение общо, без привязки к конкретному
приложению — применимо к любому будущему e-commerce каталогу в монорепо (`studio`, `aboi` и т.д.).

## 1. SEO-катастрофа комбинаторной фасетной навигации

Если каждая комбинация фильтров живёт на своём URL (`?color=red&size=L&brand=X`), число
потенциальных страниц растёт **комбинаторно**: 10 фильтров по 5 значений каждый — это уже
≈9.7 млн теоретических URL. Поисковый краулер не отличает такую страницу от «настоящей» — он
просто ходит по ссылкам и тратит краулинговый бюджет на мусорные комбинации, вместо того чтобы
переиндексировать страницы с реальным спросом.

**Симптом:** в Google Search Console растёт число проиндексированных/просканированных страниц,
но органический трафик не растёт пропорционально; частота обхода "полезных" страниц падает.

### Решение — белый список индексируемых комбинаций

Разделить комбинации фильтров на две категории:

| Категория                                                       | Пример                                                         | SEO-обработка                                                                                            |
| --------------------------------------------------------------- | -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Есть реальный поисковый спрос (проверено частотностью запросов) | `/catalog/krasnye-divany` (категория + один устойчивый фильтр) | Полноценная индексация: свой `h1`, уникальный вводный текст, `canonical` на себя, запись в `sitemap.xml` |
| Произвольная комбинация фильтров без спроса                     | `?color=red&size=L&material=X&price=100-200`                   | `noindex`, либо `canonical` на родительскую страницу категории без фильтров                              |

```typescript
// app/catalog/[category]/page.tsx — упрощённо
export function generateMetadata({ searchParams }): Metadata {
  const isWhitelistedCombo = isIndexableFacetCombo(searchParams) // список ведёт SEO/маркетинг, не хардкод в коде

  return {
    robots: isWhitelistedCombo ? { index: true, follow: true } : { index: false, follow: true },
    alternates: {
      canonical: isWhitelistedCombo
        ? buildCanonicalUrl(searchParams)
        : buildCategoryBaseUrl(), // без query-параметров фильтров
    },
  }
}
```

Белый список — это данные (таблица/конфиг), а не код: он должен обновляться по мере появления
спроса на новые комбинации, без деплоя.

## 2. Дорогие счётчики значений фильтров

UI фильтров обычно показывает, сколько товаров найдётся при выборе значения — «Цвет: Красный
(42)». Наивная реализация — `COUNT(*) GROUP BY` по каждому атрибуту с уже применёнными
остальными фильтрами при каждом рендере страницы каталога. Это N дополнительных агрегирующих
запросов на каждый page view, и стоимость растёт с размером таблицы фактов (товары × атрибуты).

**Ориентир:** PostgreSQL нормально держит такой live-подсчёт «на лету» примерно до ~1 млн строк
в таблице, по которой считается агрегация. Дальше запросы фильтров начинают заметно тормозить
рендер страницы каталога — и это тормозит именно ту страницу, где пользователь принимает решение
о покупке.

### Решение — денормализация и/или кеш с допустимой задержкой

- **Материализованное представление / отдельная агрегированная таблица** вида
  «товар/сущность-каталога × атрибут × значение → count», обновляемая по расписанию или по
  триггеру, вместо подсчёта COUNT() по фактовой таблице на каждый запрос.
- **Кеширование счётчиков** (Redis / встроенный кеш Next.js) с TTL в единицы минут. Счётчик,
  отставший на минуту, не вводит пользователя в заблуждение сильнее, чем обычная задержка между
  добавлением/распродажей товара и обновлением каталога — в отличие от отсутствия счётчика вовсе
  или зависшей страницы.

```sql
-- пример материализованного представления вместо live COUNT() на каждый рендер
CREATE MATERIALIZED VIEW facet_value_counts AS
SELECT category_id, attribute_key, attribute_value, count(*) AS product_count
FROM products
GROUP BY category_id, attribute_key, attribute_value;

-- обновление по расписанию (cron / после массового импорта), не на каждый HTTP-запрос
REFRESH MATERIALIZED VIEW CONCURRENTLY facet_value_counts;
```

Выбор между «материализованное представление» и «кеш в Redis» зависит от того, как часто меняется
каталог: частые точечные изменения (наличие товара) — ближе к кешу с коротким TTL; редкие
массовые обновления (импорт прайса) — ближе к `REFRESH` по завершении импорта.

## 3. Пустые результаты при совместном использовании поиска и фильтров

Наивная реализация применяет полнотекстовый поиск и фасетные фильтры **независимо**: сначала
поиск сужает выборку, потом фильтры сужают ещё раз. Если пересечение оказывается пустым — хотя
по отдельности и поиск, и каждый фильтр непусты — пользователь видит голое «ничего не найдено» и
не понимает, что произошло: сам ли поисковый запрос ни с чем не совпал, или это комбинация с
фильтром убила результат.

### Решение — три взаимодополняющих механизма

**(а) Счётчики фильтров относительно текущего поиска.** Значения фильтров, которые в сочетании
с текущим поисковым запросом дают ноль результатов, должны показываться неактивными (или
скрываться) — а не предлагаться пользователю как рабочий вариант, который на самом деле обнулит
выдачу.

**(б) Конструктивное пустое состояние вместо голого «ничего не найдено».** При пустом результате
подсказывать, какой конкретно фильтр стоит снять и сколько результатов появится без него:

```
Ничего не найдено с фильтром «Цвет: Красный».
→ Без этого фильтра: 34 товара
```

Это требует отдельного запроса «что будет, если снять фильтр X» — дороже, чем просто
«ничего не найдено», но именно это удерживает пользователя на странице вместо ухода.

**(в) Терпимость поиска к опечаткам и словоформам.** Точное совпадение по подстроке (`contains`
/ `ILIKE '%...%'`) не прощает ни опечаток, ни словоформ — и человек, который ищет «яблоко» вместо
«яблоки» или ошибся на одну букву, получает пустую выдачу там, где семантически результат есть.

В этом стеке для этого есть готовый инструмент — **ZenStack v3.7+ `@fullText`/`@fuzzy`**
(Postgres-only, требует расширение `pg_trgm` для `@fuzzy`):

```zmodel
model Product {
  id          String  @id @default(cuid())
  name        String  @fuzzy    // короткое поле, устойчивость к опечаткам: "Aple" → "Apple"
  description String  @fullText // длинный текст, токенизированный поиск словоформ и релевантности
}
```

```typescript
await db.product.findMany({
  where: { name: { fuzzy: { search: userQuery } } },
})
```

`@fullText` — для длинных связных текстовых полей (описания, статьи); `@fuzzy` — для коротких
полей, где важна устойчивость к опечаткам (названия, артикулы). Подробный синтаксис и примеры —
[database.md § Full-Text и Fuzzy Search](/.claude/docs/database.md#новые-возможности-v370--full-text-и-fuzzy-search-только-postgres).

## 4. EAV-атрибуты: справочник не создаётся сам по себе

Если фасетные фильтры устроены как EAV (`AttributeDefinition` на категорию + `AttributeValue` на
товар, а не жёсткие колонки в схеме — например `siding.color`), добавление UI/импорта, умеющего
писать в `AttributeValue`, **не создаёт** сами `AttributeDefinition`. Категория без определений
атрибутов молча не покажет ни одной характеристики и ни одного фильтра — не потому что данные не
заполнили, а потому что писать было некуда: и импорт, и форма редактирования просто не находят
атрибутов для этой категории и ничего не делают, без ошибки.

**Симптом:** каталог «работает» — импорт зелёный, карточка товара открывается, — но у 15 из 20
категорий нет ни одной характеристики, хотя товары этих категорий явно имеют измеримые свойства
(диаметр арматуры, сечение кабеля, класс бетона). Проверка «структура готова» (миграция прошла,
UI рендерится) не ловит это — нужна проверка **покрытия**: `count(AttributeDefinition) GROUP BY
categoryId`, а не просто «таблица существует».

Прецедент — domwellbes, 2026-08-19: импорт материалов расширили на `attr:<название>` (запись в
`MaterialAttributeValue`), протестировали на 4 категориях, где `AttributeDefinition` уже были
заведены руками раньше. Остальные 18 из 22 категорий с товарами остались с нулём характеристик —
обнаружено только явным запросом `count(AttributeDefinition) per category`, не по логам импорта
и не визуальным осмотром интерфейса.

**Что проверять при работе с EAV-каталогом:** после любой фичи, читающей/пишущей
`AttributeValue` (импорт, форма, фильтр), — свериться отдельным запросом, что
`AttributeDefinition` есть **для всех** категорий с товарами, а не только для тех, на которых
фича тестировалась.

## 5. Независимые href-билдеры расходятся при третьем измерении состояния

Каталог с фильтрами почти никогда не останавливается на одних фасетах — рано или поздно
добавляются сортировка, полнотекстовый поиск, сравнение выбранных позиций, пагинация. Каждое
такое измерение кодируется в query string. Наивный путь — у каждого измерения свой билдер
ссылки-переключателя, который сам собирает `URLSearchParams` из того, что ему передали явно
(`buildFacetToggleHref(basePath, filters, ...)`, `buildSortHref(basePath, sort)` и т.п.).

Пока измерений два, авторы вручную прокидывают состояние соседа в `extraParams` каждого билдера
и это работает. При добавлении **третьего** независимого измерения число пар «билдер X должен
не забыть про билдер Y» растёт быстрее, чем авторы успевают их синхронизировать вручную — один
переключатель начинает молча терять состояние другого (например, смена сортировки сбрасывает
выбранные фасеты, потому что её билдер никогда не знал про фильтры).

**Решение — единая функция сборки ссылки от полного объекта состояния, с patch-семантикой.**
Не «билдер получает явные параметры и сам решает, что включить», а «билдер получает текущее
полное состояние + частичный patch того, что меняется, остальное берёт из state»:

```typescript
// houses/_lib/query-state.ts — образец
export interface HousesQueryState {
  filters: HouseFacetFilters
  compareSlugs: readonly string[]
  q: string
  sort: HouseSort
}

export function buildHousesHref(
  state: HousesQueryState,
  patch: Partial<HousesQueryState> = {},
): string {
  const next = { ...state, ...patch } // остальные измерения — из state, не забыты по построению
  // ... сборка URLSearchParams из next.filters/compareSlugs/q/sort
}

// Частные переключатели — тонкие обёртки над единой функцией, а не независимые сборщики
export function buildFacetToggleHref(
  state: HousesQueryState,
  facetKey: keyof HouseFacetFilters,
  value: string,
): string {
  const filters = { ...state.filters, [facetKey]: /* toggle */ value }
  return buildHousesHref(state, { filters }) // patch только то, что реально меняется
}
```

Ключевое свойство: добавление **четвёртого** измерения не требует трогать существующие
переключатели — только добавить поле в `HousesQueryState` и один новый тонкий wrapper. Билдеры,
существовавшие до рефакторинга (`facets.ts`, `compare.ts`), не расходятся дальше, потому что
больше не строят `URLSearchParams` самостоятельно.

**Второй живой пример в том же приложении, пока не мигрированный на паттерн** —
`materials/[slug]/page.tsx`: фасеты (`facets.ts`), сортировка и пагинация (`sort.ts`) строятся
тремя независимыми билдерами (`buildMaterialFacetToggleHref`/`buildMaterialSortHref`/
`buildMaterialPageHref`), каждый вручную прокидывает соседей через явные параметры. На практике
расхождения нет — сброс страницы при смене фильтра/сортировки на страницу 1 задокументирован как
осознанное поведение (комментарий в `sort.ts`: «Смена сортировки возвращает на первую страницу»),
а не забытый параметр. Риск ниже, чем был у каталога домов до рефакторинга, потому что измерений
всего три (без `compare`/`q`) и они добавлялись не одновременно — авторы успевали руками
синхронизировать каждую пару. Если у каталога материалов появится четвёртое измерение (поиск,
сравнение), стоит мигрировать на тот же паттерн `query-state.ts`, не дожидаясь, пока
переключатели разойдутся по-настоящему.

## Когда применять этот документ

- Проектируете каталог товаров/сущностей с фильтрами для нового или существующего приложения.
- Каталог растёт (число товаров, число атрибутов фильтрации) и страница фильтров начинает
  тормозить.
- Подключаете полнотекстовый/фасетный поиск и сталкиваетесь с пустыми пересечениями поиска и
  фильтров.
