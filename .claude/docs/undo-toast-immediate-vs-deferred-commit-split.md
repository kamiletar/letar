# `@letar/undo-toast`: один контракт не покрыл оба реальных случая отмены

## Симптом

Библиотека `libs/undo-toast` спроектирована и покрыта тестами заранее, единственная функция —
`triggerUndoableAction(toaster, { message, onCommit, onUndo }, vars)`: коммит откладывается на
время жизни тоста, «Отменить» просто отменяет таймер. Контракт выглядел универсальным — под него
подпадает любое «удалить и дать отменить». При интеграции первых 11 реальных вызовов (аудит
`confirm()`, `apps/domwellbes/PLAN_CROSSCUTTING.md` § «Единообразие админки») всё сошлось: типы,
тесты, lint — зелёные.

`nx typecheck:tsgo domwellbes` неожиданно упал на файле, который эта сессия не трогала:

```
src/app/(admin)/admin/houses/_components/house-form.tsx:222:9 - error TS2353:
Object literal may only specify known properties, and 'action' does not exist
in type 'UndoToastOptions<string>'.
```

## Причина

Параллельная сессия (`house-form.tsx`) уже использовала библиотеку — со старой сигнатурой
`action`/`undo`, где мутация уходит на сервер **сразу** по клику, а «Отменить» вызывает настоящий
обратный запрос (`restoreHouse`, реальный `deletedAt: null`). Это не баг того файла и не забытая
миграция — это второй реальный сценарий, для которого единый `onCommit`/`onUndo`-контракт в
принципе не годится:

- **Есть soft-delete + restore на сервере** (`deletedAt`/аналог) → commit должен идти немедленно:
  ждать окно тоста незачем, откат — это отдельный настоящий запрос.
- **Есть только жёсткое удаление** (восстановить после коммита нечем) → commit обязан быть
  отложен, иначе «Отменить» ничего не отменяет по-настоящему.

Один API, подогнанный под первый найденный набор кейсов (все 11 — жёсткое удаление), выглядел
готовым к общему случаю, пока не столкнулся со вторым реальным потребителем в том же репозитории.

## Фикс

Разделить на две явно поименованные функции вместо одной параметризуемой:

- `triggerUndoableAction`/`useUndoableAction` — немедленный commit (`action`/`undo`), для записей
  с настоящим restore.
- `triggerDeferredUndoableAction`/`useDeferredUndoableAction` — отложенный commit
  (`onCommit`/`onUndo`) + обязательный `pagehide`/`beforeunload`-safety, для записей без
  восстановления.

Обе сосуществуют в одном приложении по признаку «есть ли restore на сервере», а не по вкусу
вызывающего кода. Полный контракт и примеры — `libs/undo-toast/README.md`.

## Урок

Если библиотека делает первый шаг в проде на основе ОДНОГО найденного набора реальных вызовов
(здесь — аудит выделил только «безопасные к жёсткому удалению» случаи), не считать её контракт
финальным до проверки на **второй** независимый реальный кейс с другим инвариантом (здесь —
наличие/отсутствие restore). Расхождение в общем монорепо чаще всего обнаруживается не
проектированием заранее, а падением typecheck на файле, который текущая сессия не трогала —
это не косвенный баг, а сигнал, что упрощение контракта было преждевременным.
