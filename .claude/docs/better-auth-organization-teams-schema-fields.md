# Better Auth: плагин `organization` с `teams` требует ещё два поля схемы

## Симптом

После минорного апгрейда `better-auth` контейнер не стартует вовсе — не отложенная ошибка на
конкретном запросе, а падение на старте:

```
[BetterAuthError]: Prisma schema mismatch
  Missing columns: team.memberCount, teamMember.membershipKey
  code: 'SCHEMA_MISMATCH'
```

Затронуты только приложения, у которых плагин организаций подключён с `teams: { enabled: true,
... }` — это опциональная суб-фича `organization()`, не обязательная часть плагина. На
2026-09-22 её включает только одно приложение монорепо.

## Причина

Тот же класс бага, что в [[better-auth-1.7-account-issuer-field]] (обобщение — [[runtime-
invariant-missing-from-select]]): минорный апгрейд `better-auth` тихо расширяет набор полей,
которые плагин считает обязательными в схеме БД, а общий ZenStack-фрагмент их не объявлял.

В `better-auth` 1.7.5 плагин `organization` с включёнными `teams` требует у моделей:

- **`Team.memberCount`** — `Int @default(0)`, обязательное поле. Значение пишет **сам адаптер
  плагина**, инкрементируя/декрементируя при добавлении/удалении участника команды — не
  приложение.
- **`TeamMember.membershipKey`** — `String? @unique`, необязательное для существующих строк.
  Плагин вычисляет его как `base64Url(sha256([teamId, userId]))` — идемпотентный ключ для
  дедупа при `create`/`find` новых записей; у строк, созданных до апгрейда, остаётся `null`, и
  это ожидаемо, отдельный backfill не нужен (в отличие от `issuer` в другом инциденте той же
  причины).

Источник истины по типам и семантике — **исходник плагина**, не документация better-auth (она
не описывает внутреннюю схему `teams` явно): `node_modules/better-auth/dist/plugins/
organization/organization.mjs`, поиск по `memberCount`/`membershipKey` (`teamSchema`).

## Отличие от `better-auth-1.7-account-issuer-field` — по форме отказа, не по причине

Причина идентична (минорный апгрейд неявно расширяет обязательную схему), но симптом
противоположный:

- `Account.issuer` сравнивается **в памяти рантайма** во время конкретного запроса
  (`sign-in.mjs`) — отсутствие поля не бросает исключение, а тихо проваливает сравнение;
  внешне неотличимо от обычного «неверный пароль».
- Отсутствие `Team.memberCount`/`TeamMember.membershipKey` ловит **собственный валидатор схемы
  better-auth при старте** — процесс не поднимается вовсе, с именами таблицы и колонки прямо в
  тексте ошибки.

Громкий отказ здесь — лучший исход из двух (сразу видно, что чинить), но диагностика всё равно
неочевидна: сообщение об ошибке называет только `table.column`, не плагин и не фичу, которая их
требует — идти сразу в исходник плагина быстрее, чем гадать по тексту ошибки или искать в общих
доках better-auth (`teams` там задокументирована слабо).

## Решение

Добавить оба поля в общий ZenStack-фрагмент/схему приложения для моделей `Team` и `TeamMember`
с типами и обязательностью, как в исходнике плагина выше, и сгенерировать миграцию
(`nx zenstack:generate <app>` → `nx db:migrate <app>`). В отличие от `issuer`-инцидента,
отдельный backfill-шаг не нужен — `memberCount` получает дефолт `0` для существующих строк,
`membershipKey` у них остаётся `null` легитимно (плагин сам заполнит его при следующем
изменении членства).

## Практический вывод

При включении **любой** опциональной суб-фичи better-auth-плагина (не только базового набора
полей плагина) — перечитывать исходник плагина на предмет полей, которые он ожидает от схемы
именно для этой суб-фичи, а не только от плагина в целом. `SCHEMA_MISMATCH` при старте — сигнал
делать это сразу, без промежуточных попыток гадать по тексту ошибки.
