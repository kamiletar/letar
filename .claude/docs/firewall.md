# Firewall и сетевая граница серверов

Главное, что нужно знать до того, как трогать firewall на серверах letar:
**`ufw` не защищает порты, опубликованные Docker'ом.** Это не особенность нашей настройки,
а устройство Docker. Из этого следует всё остальное в этом файле.

## Почему `ufw` бесполезен против Docker-портов

Docker публикует порт (`ports:` в compose, `-p` в `docker run`) через DNAT в таблице `nat`:

1. пакет приходит на внешний интерфейс и попадает в `PREROUTING`;
2. там Docker переписывает адрес назначения на IP контейнера;
3. дальше пакет для ядра — **транзитный**, и идёт по цепочке `FORWARD`;
4. правила `ufw` живут в `INPUT` — куда этот пакет уже не попадёт никогда.

Официальная формулировка Docker (docs.docker.com → «Packet filtering and firewalls» →
«Docker and ufw»): трафик контейнера отводится раньше, чем доходит до настроек ufw, поэтому
конфигурация firewall фактически игнорируется.

Практические следствия:

- `ufw deny 5441/tcp` для опубликованного контейнерного порта **не делает ничего**;
- `ufw status` → `active` при этом выглядит убедительно и создаёт ложное чувство закрытости.
  Включённый ufw без понимания этого факта **хуже** выключенного: он скрывает проблему;
- `ufw` всё ещё нужен и полезен — но только для того, что слушает **сам хост**: SSH, службы вне
  Docker. Это меньшая часть поверхности.

⚠️ **`systemctl` тоже врёт.** На s2 (2026-08-06) одновременно наблюдалось
`systemctl is-enabled ufw` → `enabled`, `systemctl is-active ufw` → `active` —
и при этом `ufw status` → `inactive`, а цепочек `ufw-*` в `iptables -S`/`nft list ruleset`
не было вообще. Юнит поднят, правила не применены.

**Проверять состояние только так:**

```bash
ufw status verbose            # единственный достоверный ответ
iptables -S | grep -c 'ufw-'  # 0 → правил нет, что бы ни говорил systemctl
```

## Что работает вместо этого

### 1. Публикация порта на loopback — основной приём

```yaml
ports:
  - '127.0.0.1:5441:5432' # ✅ снаружи порта нет вовсе
  # - '5441:5432'          # ❌ = 0.0.0.0, доступно всему интернету
```

DNAT создаётся только для `127.0.0.1`, поэтому порт недоступен извне **без всякого firewall**.
Работает всегда, едет в git рядом с кодом, не зависит от состояния сервера.

Кому и так хватает: приложениям в одной docker-сети друг с другом (`kami-network`) — они
резолвят соседей по имени контейнера, хостовая публикация им не нужна **вообще**, даже на
loopback. Публикация нужна только тому, к чему ходят **с самого хоста** или через SSH-туннель:

- миграции и сид в `deploy-affected.sh` — идут с хоста на `localhost:${DB_PORT}`;
- `dashboard-agent` — его достаёт SSH-туннель `deploy-mcp`;
- `postgres-*` MCP-серверы, если подключаются через туннель.

Разбор `DB_PORT` в `deploy-affected.sh` форму с адресом переваривает — проверено на обеих
записях, `127.0.0.1:5441:5432` и `5441:5432` одинаково дают `5441`.

### 2. Цепочка `DOCKER-USER` — default-deny (на s2 применено)

Единственное место в `FORWARD`, которое Docker гарантированно просматривает **раньше** своих
ACCEPT-правил и не перетирает при рестарте демона. Точечный `DROP` на конкретный порт работает,
но не масштабируется — правильнее default-deny: наружу разрешено только то, что перечислено.

**Действующая конфигурация s2** (применена 2026-08-07, `PLAN-INFRA.md` §49). `RETURN` = «дальше
по обычной логике Docker», финальный `DROP` — всё остальное:

```
-A DOCKER-USER -i eth0 -m conntrack --ctstate RELATED,ESTABLISHED -j RETURN
-A DOCKER-USER -i eth0 -p tcp -m multiport --dports 80,443,53 -j RETURN
-A DOCKER-USER -i eth0 -p udp -m udp --dport 53 -j RETURN
-A DOCKER-USER -i eth0 -j DROP
```

Три обязательных условия — без любого из них получится ложное чувство закрытости:

1. ⛔ **IPv6 через `DOCKER-USER` не закрывается вообще — нужен `ip6tables INPUT`.** Docker
   публикует и на IPv6 (`[::]:3101->80/tcp` в `docker ps`), но если в демоне не включён
   `ip6tables` (дефолт, `daemon.json` у нас нет), DNAT-правил для v6 он **не создаёт**, и порт
   обслуживает userland-процесс `docker-proxy` — он слушает `[::]:<порт>` как обычная программа
   на хосте. Соединение терминируется хостом и идёт в `INPUT`, а `DOCKER-USER` висит в `FORWARD`
   и такого трафика не видит. Правила в `ip6tables -A DOCKER-USER` при этом **применяются без
   ошибок и выглядят правильно в `-S`, но не делают ничего.** См. раздел про IPv6 ниже.
2. ⚠️ **Персистентность — НЕ через `netfilter-persistent save`.** Он сохранит заодно динамические
   правила Docker, и при загрузке они восстановятся протухшими. На s2 сделано скриптом
   `/usr/local/sbin/docker-user-firewall.sh` + юнитом `docker-user-firewall.service`
   (`After=docker.service`, `Type=oneshot`, `RemainAfterExit=yes`); скрипт идемпотентен — `-F`
   перед добавлением, поэтому повторный запуск не плодит дубли. Голый `iptables -I` перезагрузку
   не переживает: именно так в §37 потерялись прежние точечные `DROP`.
3. ⚠️ **`-i <внешний интерфейс>`, а не глобально.** Иначе отрежется трафик между контейнерами.
   Интерфейс определять командой, а не хардкодом `eth0`:
   `ip route get 8.8.8.8 | sed -n 's/.* dev \([^ ]*\).*/\1/p'`.

**Что не задевается этим правилом** (полезно знать, чтобы не бояться зря):

- **SSH-туннели** — приходят по loopback, `-i eth0` на них не срабатывает. Поэтому
  `postgres-*-prod` MCP и `deploy-mcp` продолжают работать;
- **трафик от прокси к приложениям** — идёт по docker-сети, а не через внешний интерфейс;
- **внутриконтейнерный форвард** — например NPM с 443 на собственный `localhost:81`.

Порядок применения на живом проде — как у `ufw enable` ниже: сначала взвести откат
(`echo 'iptables -F DOCKER-USER; ip6tables -F DOCKER-USER' | at now + 10 min`), потом применить,
потом проверить **снаружи**, и только затем `atrm`.

### 2b. IPv6 — отдельная история, и она ловит на ложном «закрыто»

**Обнаружено 2026-08-07 на s3, после того как оба сервера уже отчитались зелёными.** Это самая
коварная часть темы, потому что неверная конфигурация выглядит как верная.

Что происходит: правило `ip6tables -A DOCKER-USER ... -j DROP` применяется без ошибок,
показывается в `ip6tables -S DOCKER-USER`, и **не блокирует ничего**. Порт остаётся открыт из
интернета по IPv6.

Проверить, что попались именно на это:

```bash
ps aux | grep docker-proxy
# root ... /usr/bin/docker-proxy -proto tcp -host-ip :: -host-port 5499 ...
#                                            ^^^^^^^^^^^ слушает [::] на хосте
```

`-host-ip ::` означает, что порт по IPv6 обслуживает userland-процесс, а не ядерный DNAT.
Значит трафик идёт в `INPUT`, а не в `FORWARD`.

**Лечится правилами в `ip6tables INPUT` на внешнем интерфейсе:**

```bash
ip6tables -A INPUT -i "$EXT" -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT
ip6tables -A INPUT -i "$EXT" -p ipv6-icmp -j ACCEPT      # ⚠️ обязательно, см. ниже
ip6tables -A INPUT -i "$EXT" -p tcp --dport 22 -j ACCEPT # ⚠️ SSH, иначе потеряешь доступ
ip6tables -A INPUT -i "$EXT" -p tcp -m multiport --dports 80,443 -j ACCEPT
ip6tables -A INPUT -i "$EXT" -j DROP
```

⚠️ **ICMPv6 разрешать обязательно.** Это не «пинг ради удобства» — это NDP (аналог ARP) и Path
MTU Discovery. Заблокируешь — IPv6-связность деградирует или отваливается, причём не сразу и
трудновоспроизводимо.

⚠️ **SSH по IPv6 разрешать явно.** Если ходишь на сервер по AAAA-записи, забытый `22` в
allow-list отрежет тебя. Доступ по IPv4 останется как запасной, но проверять надо до снятия
отката.

**Структурная альтернатива** — включить `"ip6tables": true` в `/etc/docker/daemon.json`, тогда
Docker создаст для v6 полноценный DNAT и `DOCKER-USER` заработает единообразно для обеих версий.
Правильнее по сути, но требует рестарта docker-демона, то есть перезапуска **всех** контейнеров
на сервере — плановая операция, не походя.

### Как проверять IPv6 — с контролем

Проба «порт не ответил» ничего не стоит без контроля: она даёт тот же результат при обрыве сети,
неверном адресе и опечатке. Всегда прогоняй рядом заведомо закрытый порт:

```bash
for p in 5441 59999; do   # 59999 — контроль, обязан быть refused и до, и после
  timeout 3 bash -c "</dev/tcp/<AAAA-адрес>/$p" 2>/dev/null && echo "$p открыт" || echo "$p закрыт"
done
```

Именно контрольная проба отличила настоящую находку от «наверное, просто не достучались».

### 3. `ufw` — для хостовых служб, последним шагом

Включать только после того, как из `ss -tulnp` понятно, что слушает сам хост.

⚠️ **`ufw enable` с дефолтной политикой обрывает SSH.** Порядок без потери связи:

```bash
ufw allow 22/tcp                       # СНАЧАЛА SSH
ufw allow 80,443/tcp                   # Nginx Proxy Manager / Traefik
ufw allow 53                           # acme-dns (tcp+udp) — см. ниже
ufw allow 3100/tcp                     # dashboard-agent, если не на loopback
echo 'ufw disable' | at now + 10 min   # подстраховка ДО включения
ufw enable
# проверить SSH из НОВОГО окна, затем снять подстраховку: atrm <job>
```

## Порты, которые обязаны быть открыты всему интернету

| Порт       | Что                 | Почему нельзя сузить                                                                               |
| ---------- | ------------------- | -------------------------------------------------------------------------------------------------- |
| 80, 443    | Nginx Proxy Manager | публичный веб + HTTP-01 челлендж Let's Encrypt                                                     |
| 53 tcp+udp | `acme-dns`          | валидаторы Let's Encrypt приходят с произвольных адресов; сужение по IP ломает выпуск сертификатов |
| 22         | SSH                 | деплой; сузить можно по IP, но тогда нужен запасной канал доступа                                  |

Всё остальное по умолчанию считается закрытым. `acme-dns` при этом свой HTTP API держит на
loopback (`127.0.0.1:8053:80`) — открыт только DNS, но не управление.

## Чек-лист при заведении сервиса с `ports:`

- [ ] Порт вообще нужен на хосте? Если потребители в той же docker-сети — `ports:` не нужен
- [ ] Если нужен — записан как `127.0.0.1:<port>:<port>`, а не `<port>:<port>`
- [ ] Рядом комментарий, **кто** ходит на этот порт с хоста (образец —
      `apps/dashboard-agent/docker-compose.s3.yml`)
- [ ] Если порт обязан быть публичным — причина задокументирована и он в таблице выше
- [ ] Пароль/аутентификация есть независимо от того, публикуется порт или нет — сетевая граница
      это второй слой, а не единственный (см. [redis-security.md](redis-security.md))

## Как проверять, что закрыто

```bash
ss -tulnp                                  # что слушает; 0.0.0.0 vs 127.0.0.1
docker ps --format '{{.Names}}\t{{.Ports}}' # 0.0.0.0:5441->5432 = публично
                                           # просто 5432/tcp    = только EXPOSE, снаружи нет
iptables -S DOCKER-USER                    # v4: что реально блокируется
ip6tables -S INPUT                         # v6: блокировка живёт ЗДЕСЬ, не в DOCKER-USER
ps aux | grep docker-proxy                 # -host-ip :: → порт по v6 идёт мимо FORWARD
```

⚠️ `ss` с самого сервера **не доказывает**, что порт закрыт снаружи — он показывает только
сокеты. Финальная проверка — скан извне, **и по IPv4, и по IPv6**, с контрольным портом.

⚠️ Наличие правила в выводе `-S` тоже ничего не доказывает: правило может быть синтаксически
верным, применённым и при этом нерабочим — ровно случай `ip6tables -A DOCKER-USER` выше.
Доказательство — только проба снаружи.

## История

- **§37** (`PLAN-INFRA.md`) — `letar-redis` был опубликован на `0.0.0.0:6379` без пароля,
  захвачен извне через `REPLICAOF`, сломал OIDC-вход во все приложения через Ключницу.
  Закрыт правильно: **сняли публикацию порта совсем**, а не правилом firewall. Разбор и
  чек-лист по Redis — [redis-security.md](redis-security.md).
- **§49** (`PLAN-INFRA.md`) — аудит firewall на s2 после находки `ufw status: inactive`.
  Выяснилось, что 17 инстансов PostgreSQL опубликованы на `0.0.0.0`, а включение `ufw`
  ничего бы из этого не закрыло. Отсюда этот файл.

  Закрыто в два приёма: правки `ports:` на `127.0.0.1` во всех compose (приём №1, вступают в
  силу по мере деплоев) и **default-deny в `DOCKER-USER`** (приём №2, закрыл всё сразу).
  Второй понадобился именно потому, что первый доезжает медленно: через сутки после правки
  реально закрылась деплоем **одна база из семнадцати** — остальные ждали своей очереди, а пять
  приложений из них под hard e2e-gate, где один цикл занимает до семи прогонов (§51).

  **Урок:** правка в git ≠ закрытый порт. Контейнер держит привязку с момента создания и не
  перечитывает compose. Если дыру надо закрыть _сегодня_ — это уровень сети (`DOCKER-USER`),
  а не уровень репозитория.
