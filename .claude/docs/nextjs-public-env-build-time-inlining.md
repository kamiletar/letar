# `NEXT_PUBLIC_*` литерал в `docker-compose.yml` — молча не попадает в клиентский бандл

## Симптом

Клиентская фича, читающая `process.env.NEXT_PUBLIC_X`, на проде ведёт себя так, будто переменная
не задана — без ошибки, без предупреждения в логах сборки или рантайма. Если `X` — DSN
трекера ошибок, ключ аналитики или любой другой SDK с внутренним `if (!x) return`, симптом ещё
тише: фича просто не работает, и узнать об этом можно только целенаправленной проверкой (открыть
сеть в devtools, проверить БД сервиса на другом конце).

Найдено на `@letar/glitchtip` в `studio` (2026-08-11, PLAN-INFRA.md §70): серверная часть
интеграции (`instrumentation.ts`, читает `process.env.GLITCHTIP_DSN` в рантайме) работала сразу,
клиентская (`instrumentation-client.ts`, читает `process.env.NEXT_PUBLIC_GLITCHTIP_DSN`) — нет,
хотя переменная стояла в `docker-compose.production.yml` `environment:` рядом с остальными и
была видна внутри контейнера (`docker exec studio-app printenv` её показывал).

## Причина

Next.js инлайнит `NEXT_PUBLIC_*` в клиентский бандл **на этапе сборки** (`next build`/`nx build`),
подставляя буквальное значение вместо `process.env.NEXT_PUBLIC_X` в момент компиляции. Дальше в
рантайме браузер видит уже готовую строку — обращения к `process.env` в клиентском коде не
существует физически, весь `process.env` в браузере не работает.

`docker-compose.yml` `environment:` — это переменные **контейнера в рантайме**, они появляются
только при `docker compose up` (`docker exec` их видит) и вообще не участвуют в отдельном шаге
сборки, который для standalone Next.js-приложений в этом монорепо выполняется **до** `docker
build`:

```
nx build <app>              # ← NEXT_PUBLIC_* инлайнится здесь, на хосте
docker build …               # копирует уже собранный .next/standalone
docker compose up            # ← только теперь читается environment: compose-файла
```

`deploy-affected.sh` перед первым шагом делает `set -a; source .env.docker; set +a` (или
`.env.staging` для staging) — именно **этот** файл, и только он, доступен `nx build` как
`process.env`. Литерал в `docker-compose.yml` до этой команды не долетает никак.

## Как проверить, что баг именно этот

1. `docker exec <app>-app printenv | grep NEXT_PUBLIC_X` — переменная **есть** в контейнере
   (доказывает, что дело не в опечатке имени или отсутствии в compose).
2. `grep -r "<значение>" apps/<app>/.next/static/chunks/` (или пересобрать локально с тем же
   `set -a; source .env.docker` перед `nx build`, если `.next` уже не сохранился с прод-сборки) —
   значения **нет** ни в одном чанке, хотя п.1 его подтвердил.
3. Оба результата вместе — расхождение «переменная есть в рантайме контейнера, но не в
   скомпилированном клиентском коде» — однозначно указывает на этот класс бага.

## Фикс

Переменная должна жить в `.env.docker`/`.env.docker.enc` (прод) или `.env.staging` (staging) —
том же файле, что сорсируется перед сборкой, — а `docker-compose.yml` читает её через `${VAR}`,
не задаёт литералом:

```yaml
environment:
  NEXT_PUBLIC_X: ${NEXT_PUBLIC_X}
```

Так значение одновременно интерполируется в текст compose-файла (`--env-file`/подстановка) **и**
попадает в рантайм контейнера (`environment:` его явно перечисляет) — оба пути закрыты одной
строкой. Готовый пример в репозитории — `NEXT_PUBLIC_VAPID_PUBLIC_KEY` в `apps/studio/.env.docker`
(комментарий там же объясняет то же самое своими словами, ещё до находки с GlitchTip).

⛔ Не путать с `.claude/rules/env-files.md` § «Новая переменная окружения — ДВА места
обязательно» — то правило про **обычные** (не `NEXT_PUBLIC_`) серверные переменные, где второе
место — `environment:` compose-файла (`--env-file` даёт только интерполяцию текста, не рантайм
контейнера). Для `NEXT_PUBLIC_*` действуют **оба** правила сразу: нужен `${VAR}`-паттерн в
`environment:` (как в общем правиле) **и** физическое присутствие значения в `.env.docker`/
`.env.staging` до сборки (это правило) — упустить второе так же легко, как первое, симптомы
неразличимы на глаз (переменная «вроде бы правильно объявлена»).

## Для новых приложений

Любая клиентская фича, которой нужен конфиг из окружения (DSN трекера ошибок, публичный ключ
аналитики, ID виджета и т.п.) — заводить переменную **сразу** в `.env.docker`/`.env.staging`
(не только в `docker-compose.yml`), даже если значение не секрет и кажется, что литерала в
compose «и так достаточно». Чек-лист при добавлении новой `NEXT_PUBLIC_*`:

1. Значение — в `apps/<app>/.env.docker` (и `.env.docker.enc` через `sops --encrypt`) для прода,
   в `.env.staging` на сервере — для staging (см. `.claude/rules/env-files.md` § про
   `.env.staging`, живёт только на сервере, не в этом чекауте).
2. `docker-compose.production.yml`/`docker-compose.staging.yml` — `${VAR}`, не литерал.
3. После первого деплоя — живая проверка именно клиентского пути (не только серверного): открыть
   приложение в браузере, убедиться, что значение реально попало в исполняемый код, а не только
   в `printenv` контейнера.
