# Таймер studio: как теряется время — разборы

Правило («когда стартовать, переключать, останавливать») —
[.claude/rules/time-tracking.md](/.claude/rules/time-tracking.md). Здесь — почему оно
сформулировано именно так: четыре разных способа потерять время, каждый найден на практике и ни
один не ловится автоматикой.

Общая черта всех четырёх: **о пропаже узнаёт пользователь, а не агент**. Хуки
(`time-heartbeat.js` на `PostToolUse`, `time-stop-check.js` на `Stop`) продлевают и проверяют
**уже идущую** запись — закрытую они не воскрешают и не предупреждают о её отсутствии.

## 1. Хук на `Stop` заставлял останавливать таймер после каждой реплики (2026-07-30)

`Stop` в Claude Code срабатывает **в конце каждого ответа агента**, а не при завершении сессии.
Первая версия `time-stop-check.js` блокировала `Stop` при живом таймере с текстом «останови
перед завершением сессии» — и агент честно останавливал таймер после каждой реплики. Одна работа
превращалась в десяток огрызков по три минуты.

Блокировка снята. Забытый таймер ловится не приставанием, а `time-heartbeat.js` (обновляет
`lastSeenAt` при каждом вызове инструмента) и серверным автозакрытием по простою
(`autoClosedIdle`).

## 2. Смена предмета работы без `time_switch` — межпроектная (2026-08-10, domwellbes)

Таймер переключили на «форма заявки + согласие», задача оказалась уже сделана в коде — отставали
доки. Дальше без единого `time_switch` два часа делалась совсем другая задача: генерация и
привязка фото материалов (ChatGPT → скачивание → сопоставление SKU → сид). Заметил пользователь.

Этот случай **ловится эвристикой хука** («число задетых `apps/<x>/` ≠ число `time_switch`»),
потому что задевал разные приложения.

## 3. Та же смена, но внутри ОДНОГО приложения — хук слеп (2026-08-18, aboi)

P9.1 (цена за м²) закрыта и закоммичена, пользователь тут же предложил новую фичу — реестр
бумаги. Работа над ней (уточняющие вопросы, exploration, Plan Mode) шла без `time_switch`, пока
пользователь не напомнил.

Хук здесь бессилен по построению: всё время работа внутри одного `apps/aboi/`, «продолжаю P9.1»
и «начал реестр бумаги» для него неразличимы. Единственная защита — правило «другой пункт плана
→ переключайся в момент, когда это стало понятно», применённое и к внутриприкладным пивотам.
Триггер — пользователь сформулировал новую задачу, **даже если её ещё предстоит уточнять**.

## 4. Автозакрытие по простою (`autoClosedIdle`) — два разных окна

### 4а. После сжатия/разрыва контекста (2026-08-25, domwellbes)

Разговор был сжат и продолжен инструкцией «Continue... Pick up the last task as if the break
never happened». Агент последовал ей буквально: сразу начал работать инструментами, предположив,
что старый `time_start` жив. Сервер к тому моменту уже закрыл запись по простою в разрыве между
последним инструментом до сжатия и первым после.

Heartbeat молчит: обновлять нечего, запись закрыта, новую он не создаёт.

**Вывод в правило:** «продолжай как будто разрыва не было» — про нить задачи, не про пропуск
проверки таймера. Первым действием после возобновления, **до** любого Bash/Read/Edit —
`time_status`.

### 4б. Внутри активной работы, без всякого разрыва (2026-08-27, domwellbes)

Таймер закрылся по простою в середине рабочей сессии. Между вызовами инструментов реально
проходило больше времени, чем кажется по числу сообщений: `AskUserQuestion` ждёт ответа
пользователя (минуты), `nx typecheck`/`lint`/`test` на реальной БД — 15–25 секунд каждый. Если
следующий вызов начинается уже после серверного порога простоя, heartbeat не успевает продлить
запись.

**Вывод в правило:** во время длинной работы (серия проверок, ожидание `AskUserQuestion`,
делегирование субагенту) не полагаться на случайные вызовы инструментов как на heartbeat —
периодически вызывать `time_status`, это дешёвый вызов, который заодно перезапускает таймер при
`autoClosedIdle`.

## Смежное: `time_pause` раньше означал не паузу

До 2026-07-30 инструмент `time_pause` останавливал запись и помечал её небиллируемой — то есть
ничего не «приостанавливал». Имя освобождено под настоящую паузу, а прежнее поведение живёт в
`time_discard`. Встретишь в старых текстах `time_pause` в смысле «останови и не считай» — это
`time_discard`.

## 5. Хуки не находились из подкаталога — heartbeat «срабатывал редко» (2026-09-26, flora)

Сессия `/flora` стартует с рабочим каталогом `apps/flora` (submodule). Команды хуков в
`settings.json` были записаны как `node .claude/hooks/X.js` — относительный путь от **текущего**
каталога, а не от корня репозитория. Из `apps/<app>` файл не находится (`MODULE_NOT_FOUND`), хук
падает молча. Следствие: heartbeat из такой сессии не доходил вовсе, запись закрывалась по простою
с `lastSeenAt == startedAt` (в таблице 0:00, «автозакрыто»), а барьеры `validate-bash.js` и
`time-stop-check.js` в этих сессиях тоже не работали.

**Признак:** запись с нулевой длительностью и `autoClosedIdle`, хотя работа шла. Проверка:
`echo '{"session_id":"x"}' | node .claude/hooks/time-heartbeat.js` из `apps/<app>` — до фикса
падает с `MODULE_NOT_FOUND`.

**Что сделано:**

1. Команды всех хуков в `settings.json` идут через однострочный загрузчик: ищет
   `.claude/hooks/<имя>` вверх от текущего каталога и подключает найденное. Работает из любого
   подкаталога и submodule; stdin доходит до хука, потому что процесс тот же.
2. `time-resume-reminder.js` на `SessionStart` (`compact|resume`) кладёт в контекст напоминание
   «первым действием `time_status`» — правило перестало держаться на памяти модели.
3. `mcpHeartbeat` (studio) возобновляет запись сессии, закрытую по простою (`autoClosedIdle`),
   если агент снова вызывает инструменты (окно 6 часов). Зазор уходит в `pausedSec`, то есть время
   простоя **не** засчитывается: возобновление сохраняет непрерывность записи, а не выставляет
   счёт за паузу. Ручно остановленные (`time_stop`/`time_discard`), выставленные в счёт и записи
   без `sessionRef` не трогаются.

⚠️ Новый хук в `settings.json` — только через загрузчик (скопируй существующую команду и замени имя
файла в конце), не `node .claude/hooks/...` напрямую.
