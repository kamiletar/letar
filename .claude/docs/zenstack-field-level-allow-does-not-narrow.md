# ZenStack: field-level `@allow` не сужает модельную `@@allow` — только добавляет разрешение поверх

## Симптом

Нужно защитить одно чувствительное поле модели (роль пользователя, ссылку на сверенный платёж,
факт расхождения приёмки) от редактирования тем кругом ролей, которому модельная `@@allow`
разрешает `update` в целом. Интуитивный первый фикс — field-level `@allow` с более узким условием:

```zmodel
model Payment {
  settlementId String?

  settlementId String? @allow('update', auth().isAdmin)

  @@allow('create,update', auth().isStaff)
}
```

Выглядит как «обычные пользователи не смогут менять `settlementId`, только admin». На практике
не защищает вообще: любой `isStaff` по-прежнему может проставить/снять `settlementId` через
`db.payment.update()`, в обход сверки, которая должна быть единственным писателем поля.

## Причина

Field-level `@allow` в ZenStack не _сужает_ право, разрешённое `@@allow` модели — он _добавляет_
ещё один путь получить доступ, поверх уже разрешённого. Итоговое разрешение на запись поля — это
объединение (OR) условий: «модельная `@@allow` разрешает» ИЛИ «field-level `@allow` разрешает».
Если модельная policy уже пускает всех `isStaff`, добавление `@allow('update', auth().isAdmin)`
на поле ничего не отнимает у остальных `isStaff` — оно им и не было нужно, доступ уже был.
Field-level `@allow` полезен только в обратной ситуации: когда нужно **разрешить** более узкому
полю то, что модель в целом не разрешает.

## Решение

Сужение — это `@deny`, не `@allow`. `@deny` побеждает `@@allow` независимо от порядка объявления,
поэтому field-level `@deny('update', <условие не-исключения>)` действительно вычитает право у
части ролей, которым модель его дала:

```zmodel
model Payment {
  settlementId String? @deny('update', auth() == null || !auth().isAdmin)

  @@allow('create,update', auth().isStaff)
}
```

Тот же приём для «поле неизменяемо после создания вообще для всех» — `@deny('update', true)` без
условия:

```zmodel
model DeliveryDiscrepancy {
  expectedQty Int @deny('update', true)
  actualQty   Int @deny('update', true)
  note        String? @deny('update', true)
}
```

`nx zenstack:generate <app>` не требуется отдельной миграции — это policy-уровень, не изменение
схемы БД.

## Как искать этот паттерн

Грепом по `schema.zmodel` (или составным файлам схемы) на `@allow(` **на уровне поля** (не
`@@allow` — двойной `@@` это модельная policy, единичный `@` внутри тела модели рядом с типом
поля — field-level). Для каждого найденного:

1. Найти модельную `@@allow`/`@@deny` для того же действия (`create`/`update`/`delete`).
2. Если модельная policy уже разрешает операцию более широкому кругу ролей, чем условие
   field-level `@allow` — это баг: намерение «сузить» не сработало, поле фактически защищено
   только настолько же широко, насколько модель в целом.
3. Единственный корректный способ сузить — field-level `@deny` с инвертированным условием (или
   `@deny(..., true)` для полной неизменяемости).

Пустой field-level `@allow` без соответствующей широкой модельной `@@allow` под этот паттерн не
подпадает — там нечего сужать, разрешение реально новое.

## Известные случаи в монорепо

Все три — `domwellbes` (`schema/retail-shop.zmodel` и связанные), найдены `auth-policy-validator`
при аудите волны M8A, 2026-08-27:

- **`User.roles`/`supplierId`/`counterpartyId`/`retailCustomerId`** — модельная self-update
  policy (`@@allow('read,update', auth().id == this.id)`) без field-level защиты позволяла
  авторизованному пользователю дописать себе роль ADMIN/DIRECTOR/ACCOUNTANT через
  `db.user.update()` (mass-assignment/privilege escalation). Первая попытка фикса использовала
  `@allow`, не сработала; исправлено на `@deny` на все четыре поля (пишут только ADMIN,
  `counterpartyId` — ещё и SALES, не на себя).
- **`Payment.settlementId`** — модельная `@@allow('create,update', auth().isStaff)` пускала
  любого кассира/курьера проставить/снять `settlementId` в обход сверки эквайринга
  (`importAcquiringSettlementAction`). Тот же порядок фикса: `@allow` не сработал, заменён на
  `@deny`.
- **`DeliveryDiscrepancy.{expectedQty,actualQty,note}`** — должны быть неизменяемы после создания
  (доказательная запись расхождения приёмки), `@allow('update', false)` не отнимал уже
  разрешённый моделью путь у ADMIN/SALES/PROCUREMENT. Заменено на `@deny('update', true)`.

## Как проверять при ревью новой policy

1. Грепнуть новый/изменённый `schema.zmodel` на `@allow(` внутри тела модели (не `@@allow`).
2. Для каждого найденного — сверить с модельной `@@allow`/`@@deny` того же действия: реально ли
   условие поля **уже** — но менее широкое подмножество того, что разрешено моделью в целом.
3. Если да — это не сужение, баг. Заменить на `@deny` с инвертированным условием.
4. `auth-policy-validator` ловит этот класс при регулярном прогоне — не полагаться только на
   ручной греп, но и не считать «валидатор не позвал» доказательством отсутствия проблемы в
   свежедобавленном поле до первого прогона.
