# Ловушки `@meta("form.*")` и атрибутов валидации в `schema.zmodel`

Найдено 2026-09-19 при переводе справочных форм (модели вида `Supplier`, `Machine`) с ручных
`_schemas/*.schema.ts` на схемы, которые `@letar/zenstack-form-plugin` генерирует из
`schema.zmodel`. Все ловушки объединяет одно: **ничего не падает** — `zenstack generate` зелёный,
`typecheck` зелёный, форма рисуется. Расхождение всплывает только на живом вводе.

Общий порядок работы с директивами — [forms](/.claude/docs/forms.md), полный справочник ключей —
`libs/zenstack-form-plugin/README.md`, разница `@meta` и `///` —
[zmodel-comment-directives-vs-ast](/.claude/docs/zmodel-comment-directives-vs-ast.md).

## 1. `@email` не принимает `''` — необязательный email не очистить

`Field.String` в `onChange` отдаёт сырую строку (`field.handleChange(value)`, без превращения
пустого значения в `undefined`). Пользователь стёр необязательное поле — в схему приходит `''`.
`@email` порождает `.email()`, а Zod v4 пустую строку как email отвергает, даже если поле
`.optional()`:

```typescript
z.string().email().optional().safeParse('').success // false
```

Итог: форма не сохраняется, а ошибка «Некорректный email» висит на поле, которое выглядит пустым.

**Для необязательного email — `@regex` с допустимой пустой строкой** вместо `@email`:

```zmodel
model Supplier {
  // необязательный: '' допустим, непустое — похоже на адрес
  email String? @regex("^([^@\\s]+@[^@\\s]+\\.[^@\\s]+)?$", "Некорректный email")
    @meta("form.title", "Email")

  // обязательный — обычный @email, пустая строка там и должна падать
  billingEmail String @email("Введите настоящий email") @meta("form.title", "Email для счетов")
}
```

Внешняя группа `( … )?` в паттерне и даёт «пусто или адрес». Проверено на Zod:
`''` и `a@b.ru` проходят, `a b` — нет.

Тот же класс ловушки у любого строкового атрибута с непустым требованием (`@url`, `@length(min, …)`,
`@regex` без `?`): очищенное необязательное поле — это `''`, не `undefined`.

## 2. Обратный слэш в строках ZModel съедается — в `@regex` пиши `\\`

Строковый литерал ZModel разбирается Langium как строка с escape-последовательностями: `\\`
превращается в один `\`, а **неизвестный escape теряет слэш** — `\s` становится буквой `s`.
Паттерн с одиночным слэшем остаётся синтаксически валидным, генерация проходит, но регулярка
теперь другая. Замеры на `loadDocument` из `@zenstackhq/language` (слева — то, что лежит в
`.zmodel` на диске, посередине — значение, которое получает плагин):

| В файле `.zmodel` | Значение для плагина   | Итог                                          |
| ----------------- | ---------------------- | --------------------------------------------- |
| `\s`              | `s`                    | ❌ буква `s` вместо пробельного класса        |
| `\d`, `\w`        | `d`, `w`               | ❌ буквы                                      |
| `\.`              | `.`                    | ❌ любой символ вместо точки                  |
| `\b`              | `<U+0008>` (backspace) | ❌ управляющий символ вместо границы слова    |
| `\\s`             | `\s`                   | ✅ пробельный класс                           |
| `\\d`, `\\.`      | `\d`, `\.`             | ✅                                            |
| `\\\\s`           | `\\s`                  | ❌ литеральный `\` и `s` — обратная крайность |

Правило: **в `.zmodel` каждый слэш регулярки записывается парой `\\`**, ровно два символа на диске
(не четыре). `\n`/`\t` в паттерне «случайно» работают — Langium превращает их в настоящие перевод
строки/табуляцию, и это то же, что видит регулярка, — но полагаться на это не стоит.

⚠️ Чужой текст (чат, тикет, JSON-экранированный фрагмент) часто показывает слэши уже
удвоенными. Сверяйся с тем, что реально лежит в файле, а не с тем, что вставлено в реплику:
проверка ниже. Обратное тоже бывает: heredoc в Bash-инструменте агента (замерено; `Edit` с
`old_string`, где есть слэши, тоже не находил на вид совпадающий текст) **схлопывает** `\\` в `\` — скрипт с регулярками, записанный так, падает `SyntaxError`, а
замер по нему врёт. Считай слэши в файле по байтам (`0x5c`), а не по выводу в терминал; скрипт
пиши инструментом `Write`, слэш в его коде бери как `String.fromCharCode(92)`.

**Проверка.** Как выглядит паттерн в сгенерированном `src/generated/form-schemas/<Model>.form.ts`,
зависит от того, откуда он взялся:

- **Нативный `@regex("…")`** (основной путь) — плагин передаёт значение в
  `ZodUtils.addStringValidation` через `JSON.stringify`, то есть это **TS-строка**, а не литерал
  `/…/`. Верный паттерн `[^@\s]` выглядит там как `"…[^@\\s]…"`: два слэша в исходнике = один в
  рантайме. Слэш потерян — увидишь `[^@s]`, лишний — `[^@\\\\s]`.
- **`@meta("form.props.pattern", "…")`** (escape hatch) — плагин пишет `.regex(/…/)`; здесь слэши
  видны так, как их получит `RegExp`: `\s`, а не `s`.

```bash
grep -n "@regex\|\.regex(" src/generated/form-schemas/Supplier.form.ts
```

Чтобы поймать это на уровне схемы, добавь тест, который прогоняет паттерн через сгенерированную
схему на положительном и отрицательном примере (адрес с пробелом внутри должен отвергаться).
Плагин с v4.1.3 экранирует в regex-литерале (`form.props.pattern`) только `/` и переводы строк
(`quoteRegexLiteral`), а в нативном пути сериализует строку как есть; пары `\x` не трогает ни
один, поэтому потерянный слэш плагин восстановить не может: к моменту генерации его уже нет.

**Аудит 2026-09-21.** По всем `.zmodel` репозитория (включая приватные submodule и `libs/*`)
`@regex` со слэшем нашёлся один — email-паттерн из примера выше. В файле у него ровно по два
слэша на каждый (верно), в сгенерированной схеме рантайм-значение содержит `\s`/`\.`; проверено
прогоном на положительных и отрицательных примерах. Форм «одиночный слэш» и «четыре слэша» в
репозитории нет.

## 3. Подсказки поля: `form.tooltip.*` (`zenstack-form-plugin` 4.1.0+)

```zmodel
model Machine {
  hourlyRate Int @meta("form.title", "Стоимость часа")
    @meta("form.tooltip.title", "Стоимость часа")
    @meta("form.tooltip.description", "Сколько стоит час работы машины")
    @meta("form.tooltip.impact", "Попадает в расчёт себестоимости заказа")
    @meta("form.props.minorUnitScale", 100)
}
```

- **`description` обязателен.** Без него `impact`/`title`/`example` подсказку **не создают**, а
  `zenstack generate` печатает warning с моделью и полем — только в консоли, exit code 0. Заголовок
  `title` без `description` тоже пустая трата: (?)-иконки не будет. Ищи в выводе генерации строку
  `[zenstack-form-plugin] <Model>.<field>: @meta("form.tooltip.*") без …`.
- **Подключи — закрытый набор:** `title`, `description`, `impact`, `example`. Опечатка
  (`form.tooltip.impakt`) даёт warning, а не молчаливую потерю.
- **Не путай с `form.description`:** та рисуется текстом **под** полем, тултип — (?)-иконкой рядом
  с лейблом. Часто нужны оба, с разным текстом.
- ⚠️ **Тексты подсказок не попадают в файлы переводов i18n-режима** (там только
  `title`/`placeholder`/`description`). В мультиязычном приложении тултип остаётся на языке
  схемы — переводить его придётся отдельно.
- Значение сериализуется `JSON.stringify`, поэтому кавычки и апострофы в прозе безопасны.

### `form.props.minorUnitScale` — деньги в копейках

`@meta("form.props.minorUnitScale", 100)` попадает не в constraints, а в `ui.fieldProps`, и
доезжает до `Field.Currency`/`Field.Percentage` (пользователь видит рубли, в БД лежат копейки).
С `@letar/forms-react` 0.7.0 это работает и в явных типизированных тегах
(`<AppForm.Field.Currency>`), не только через `Form.Field.Auto`. В сгенерированной схеме ищи
`fieldProps: {"minorUnitScale":100}`.

## 4. Сервер разбирает вход тем же классом, что и форма

Не заводи вторую, ручную Zod-схему для server action. Тот же сгенерированный класс валидирует и
форму на клиенте, и вход на сервере — иначе правила (включая обходы из пп. 1–2) расходятся:

```typescript
'use server'

import { SupplierCreateFormSchema } from '@/generated/form-schemas/Supplier.form'

// .strip() — по правилу безопасности: поля вне схемы отбрасываются, а не доезжают до БД
const CreateSupplierInput = SupplierCreateFormSchema.strip()

export async function createSupplier(input: unknown) {
  const parsed = CreateSupplierInput.safeParse(input)
  if (!parsed.success) {
    return { error: parsed.error.flatten() }
  }
  // ...запись через enhanced-клиент ZenStack
}
```

Для правки (`update`) — `SupplierUpdateFormSchema` (все поля `.partial()`).

## Чеклист после правки директив

1. `nx zenstack:generate <app>` и внимательно прочитать вывод: warning плагина — единственный
   сигнал по п. 3.
2. Открыть `src/generated/form-schemas/<Model>.form.ts`: паттерны `.regex(/…/)` без потерянных
   слэшей, `tooltip` у нужных полей, `fieldProps` с `minorUnitScale`.
3. Живой прогон: очистить необязательное поле с email/URL и сохранить — форма должна уходить.
