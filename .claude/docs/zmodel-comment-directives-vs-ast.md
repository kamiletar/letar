# `@meta`-атрибут vs `///`-комментарий: почему это два разных парсера, а не один

`libs/zenstack-form-plugin` с Фазы 3 (v3.0.0) умеет читать метаданные форм из **двух**
принципиально разных источников на одном и том же поле ZModel — важно понимать разницу, потому
что она объясняет, почему у плагина два независимых парсера, а не один общий, и почему кодмод
(`scripts/codemods/codemod-form-directives.mjs`) работает построчно, а не через AST.

## Источник 1 (legacy, deprecated): `///`-комментарий

```zmodel
/// @form.title("Название")
title String
```

Это **не часть языка ZModel** в грамматическом смысле — Langium (парсер, на котором построен
ZenStack) хранит doc-комментарии как обычный текст, привязанный к следующему за ним элементу
AST. Плагин читает `field.comments` (массив строк) и разбирает их **регулярными выражениями**
(`parseFormMeta` в `libs/zenstack-form-plugin/src/parser.ts`) — грамматика ZModel вообще не
знает о существовании `@form.title`, для неё это просто текст комментария.

Следствие: привязка комментария к полю — это соглашение Langium («doc-comment привязывается к
следующему объявлению»), не гарантия плагина. Классическая ловушка:

```zmodel
// ❌ Неправильно — комментарий привяжется к СЛЕДУЮЩЕМУ полю, не к title
title String
/// @form.title("Название")
```

## Источник 2 (основной, Фаза 3): `@meta` field-атрибут

```zmodel
title String @meta("form.title", "Название")
```

Это **настоящий узел AST** — `DataFieldAttribute` в грамматике ZModel, тот же тип узла, что и у
`@id`/`@default`/`@gte`/любого другого атрибута поля. Плагин читает его через
`parseMetaAttributes` (тот же файл `parser.ts`) — напрямую по `field.attributes`, без regex,
без обращения к тексту комментария вообще.

Следствие: `@meta` не подвержен ловушке привязки к «не тому» полю — он физически стоит на
строке поля, неоднозначности в порядке нет.

## Почему это два независимых парсера, а не один общий

Наивная идея «раз оба описывают одни и те же ключи (`form.title`, `form.props.*`...), пусть один
парсер строит единую плоскую структуру» не работает, потому что источники данных синтаксически
несовместимы на входе:

- Источник 1 — `string[]` (текст комментариев), разбирается regex'ом по паттерну
  `@form\.(\w+)\(...\)`.
- Источник 2 — `readonly DataFieldAttribute[]` (структурированный AST), разбирается по полям
  `attr.name` / `attr.args[0].value.$type` (`StringLiteral`/`NumberLiteral`/`BooleanLiteral`/
  `ArrayExpr`).

Оба парсера возвращают один и тот же тип `FormFieldMeta`, и дальше в дело вступает
`mergeFormMeta(commentMeta, metaAttrMeta)` — слияние **по каждому полю метаданных отдельно**
(`title`/`placeholder`/`fieldType`/... через `??`, `constraints`/`props` — key-by-key spread), с
приоритетом `@meta` при конфликте на одном ключе. Слияние происходит **после** обоих парсеров
независимо друг от друга — не в процессе общего прохода по дереву.

## Почему объектный литерал ломает именно `@meta`, а не comment-директиву

Ключевая асимметрия между источниками — не в удобстве синтаксиса, а в том, **кто выполняет
парсинг раньше**:

- Comment-директива — это просто текст. `@form.props({ min: 1, max: 100 })` внутри `///`-строки
  для парсера ZModel — обычный doc-комментарий, синтаксис его содержимого языку безразличен.
  Наш собственный regex-парсер спокойно вытаскивает JSON-подобный объект оттуда.
- `@meta("key", value)` — настоящий вызов атрибута, и **upstream-генератор TS-схемы самого
  ZenStack** (не наш плагин) обрабатывает аргументы атрибутов раньше, чем наш плагин получает
  управление. Обнаружив `ObjectExpr` в качестве значения аргумента атрибута, он падает:

  ```
  $ nx zenstack:generate (@meta с объектным литералом) → Unhandled error:
    Unsupported attribute arg value: ObjectExpr
  $ nx zenstack:generate (@meta("form.title", "…") @meta("form.fieldType", "…")) → успех
  ```

  Проверено живым прогоном (не из документации ZenStack — она этот случай не описывает).
  Грамматика ZModel формально допускает `ObjectExpr` как `Expression` (значит атрибут с объектом
  в аргументе парсится успешно), но реального обработчика для превращения его в TS-значение у
  upstream-генератора нет — падение происходит на шаге кодогенерации, не парсинга.

Отсюда обязательный вывод для `form.props`/`form.relation`: только плоский dot-path
(`@meta("form.props.min", 1) @meta("form.props.max", 100)`), никогда объект. У comment-варианта
(`/// @form.props({ min: 1, max: 100 })`) этого ограничения нет и не будет — но это deprecated
путь, новый код на нём не пишется.

## Почему кодмод построчный, а не через AST

`scripts/codemods/codemod-form-directives.mjs` конвертирует `///`-директивы в `@meta`-атрибуты
**текстовой обработкой строк**, не парсингом AST. Причина простая: Langium-грамматика ZModel не
экспортирует публичный AST-парсер для сторонних Node-скриптов вне самого пакета `@zenstackhq/*` —
она внутренняя часть ZenStack CLI. Написать «настоящий» codemod, парсящий `.zmodel` в AST и
сериализующий обратно, означало бы либо тянуть внутренности ZenStack как нестабильную
зависимость, либо писать собственный парсер грамматики — оба варианта несоразмерны задаче
«переписать один вид синтаксиса в другой».

Поэтому кодмод сознательно консервативен: конвертирует только однозначно узнаваемые построчные
паттерны (`/// @form.title("...")` перед полем и т.п.), а всё, что не укладывается в жёсткий
regex (позиционные аргументы, директива не сразу перед полем, нераспарсенный объект), оставляет
как есть и печатает в блок «ТРЕБУЕТ РУЧНОЙ ПРОВЕРКИ» — не угадывает семантику там, где текстовый
анализ не может быть уверен. Идемпотентность (не задваивать `@meta`-ключ, если он уже есть на
целевой строке) держится на той же текстовой проверке: `line.includes('@meta("<key>"')`.

## Практический вывод

- Пишешь новый код — используй `@meta`, у него нет ловушки привязки комментария и он единственный
  синтаксис, для которого этот документ не нужен как объяснение сюрприза.
- Читаешь старый `.zmodel` с `///`-директивами — они рабочие, деprecated, `nx zenstack:generate`
  печатает подсказку с готовой заменой на каждое поле.
- Мигрируешь схему целиком — используй кодмод, не переписывай вручную (пропустишь позиционные
  формы вроде мёртвого `@form.relation("Model", "field")`, которые парсер плагина никогда не
  поддерживал — кодмод такие ловит и явно помечает на ручную проверку, а не молча переносит).
- Видишь `Unsupported attribute arg value: ObjectExpr` на `zenstack generate` — это не баг
  плагина и не баг твоей схемы в общем смысле, это `@meta` с объектным литералом где-то в файле;
  ищи `@meta(` с `{` сразу после запятой.
