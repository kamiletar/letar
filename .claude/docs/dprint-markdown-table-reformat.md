# dprint переформатирует markdown-таблицы целиком — Edit падает на «верном» тексте

## Симптом

Последовательное редактирование одной таблицы в плане (`PLAN.md` и т.п.) внутри одной сессии:

1. `Edit` по строке таблицы — проходит успешно.
2. Между правками (по чеклисту `app-workflow.md § После завершения задачи`) прогоняется
   `nx run-many -t format --projects=<app>`.
3. Следующий `Edit` по соседней строке той же таблицы падает с `String to replace not found`
   — хотя `old_string` скопирован из текста, который только что был прочитан этим же
   инструментом чуть раньше в разговоре.

Файл при этом не тронут вручную и выглядит визуально как та же таблица — разница не в
содержимом ячеек.

## Причина

dprint форматирует markdown-таблицы не построчно, а **всей таблицей целиком**: при каждом
прогоне он заново пересчитывает ширину каждого столбца (по самой длинной ячейке столбца на
текущий момент) и заново расставляет отступы-разделители `---`/пробелы для выравнивания. Любое
изменение длины содержимого одной ячейки (даже на один символ) сдвигает ширину столбца — и
значит, меняет байт-в-байт представление **всех остальных строк** этой таблицы, не только той,
что редактировалась.

`Edit` матчит `old_string` точно, посимвольно. Текст строки, прочитанный до прогона `format`, и
текст той же строки после — разные строки на уровне байтов (другое число пробелов-заполнителей),
даже если визуально в отрендеренном markdown это неразличимо.

## Как распознать

- Ошибка `String to replace not found` у `Edit`, где `old_string` содержит `|` (строка
  markdown-таблицы).
- Между моментом, когда текст был прочитан, и моментом `Edit` в истории есть вызов
  `nx run-many -t format` / `nx lint` (которые тоже форматируют) / любой другой прогон dprint.
- `git diff` по файлу (если он уже был закоммичен раньше) показывает изменение только
  пробелов/выравнивания в строках таблицы, которые сессия не редактировала намеренно — это
  подтверждает, что сдвиг вызван форматтером, а не ручной правкой.

## Как жить с этим

- **Перечитывать актуальный текст строки непосредственно перед каждым `Edit`**, если между
  предыдущим чтением и этим `Edit` был прогон `format` (или любая другая операция, которая могла
  запустить dprint). Не полагаться на текст, прочитанный раньше в разговоре — использовать `Read`
  точечно на нужный диапазон строк, либо `grep -n` для координат, прямо перед вызовом `Edit`.
- **Альтернатива — группировать правки одной таблицы.** Если несколько строк одной таблицы нужно
  изменить, делать все правки этой таблицы подряд, одним заходом, до следующего прогона `format`
  — тогда сдвига ширины столбцов между правками не происходит и повторное чтение не требуется.
- Это не баг и не повод отключать форматирование — таблица, отформатированная dprint, читается
  человеком лучше (выровненные столбцы). Проблема ровно в том, что автоматизация читает файл
  быстрее, чем успевает узнать о произошедшем сдвиге.
