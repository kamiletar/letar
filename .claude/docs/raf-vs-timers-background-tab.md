# requestAnimationFrame vs setInterval/setTimeout — выбор небезобиден

## Симптом

Выбор между `requestAnimationFrame` и `setInterval`/`setTimeout` для анимации выглядит как деталь
реализации, взаимозаменяемая. На деле оба механизма ошибаются в **противоположные стороны**, и
обе ошибки invisible: код компилируется, работает на глаз в фокусе вкладки, и врёт только в
конкретном сценарии — уход в фоновую вкладку.

Найдено дважды в одной сессии над `apps/studio` независимо друг от друга — один и тот же класс
ошибки, две противоположные манифестации.

## Правило выбора

**`requestAnimationFrame` — для всего, что человек видит прямо сейчас.** Синхронизирован с
перерисовкой экрана, в фоновой вкладке браузер его полностью останавливает (не throttling — ноль
кадров), поэтому не жжёт батарею и не тратит CPU впустую там, где всё равно ничего не видно.

**`setInterval`/`setTimeout` — для того, что должно происходить, даже когда вкладка в фоне.**
Индикатор состояния во вкладке (favicon, title), фоновая синхронизация, таймер обратного отсчёта —
всё, что имеет смысл именно для человека, который **ушёл** с вкладки.

Смешение — источник обоих багов ниже: `setTimeout` там, где нужен был `rAF` (пункт видим на
экране, но задача завязана на реальные секунды), и `rAF` там, где нужен `setInterval` (пункт нужен
именно в фоне, а `rAF` в фоне не запускается вовсе).

## Баг 1: `setTimeout`-анимация на переднем плане душится в фоне

Полоса прогресса считала шаги через `setTimeout(45мс)` на каждый следующий шаг. В фокусе — 24 шага
по 45 мс, ожидаемо ~1 секунда. При уходе в фоновую вкладку браузер троттлит `setTimeout` до ~1 раза
в секунду (защита от фонового спама таймеров) — те же 24 шага растянулись на ~22 секунды.
Наблюдаемо как «загрузка зависла», хотя код ни разу не упал и не залогировал ошибку.

Фикс — `requestAnimationFrame`, время считать **не от начала анимации**, а по разнице между
соседними кадрами, с зажимом:

```js
function animate(dur, onFrame, onDone) {
  var prev = performance.now(), t = 0
  ;(function frame() {
    var now = performance.now()
    t += Math.min(now - prev, 100) // скачок больше зажима = возврат из фона
    prev = now
    var p = Math.min(1, t / dur)
    onFrame(p)
    if (p >= 1) { return onDone() }
    requestAnimationFrame(frame)
  })()
}
```

Зажим (`CAP = 100 мс`) решает две задачи одновременно:

- **Верная длительность на любой частоте обновления.** Счёт кадров вместо счёта времени дал бы на
  144 Гц экране анимацию вдвое быстрее, чем на 60 Гц — кадров за секунду вдвое больше.
- **Пауза на время отсутствия, а не скачок.** `rAF` в фоновой вкладке не вызывается вовсе — когда
  вкладка снова активна, `now - prev` может оказаться минутами. Без зажима это одним махом
  провалило бы анимацию до конца (`t` сразу больше `dur`). С зажимом скачок засчитывается как один
  обычный кадр — анимация продолжается с места остановки, а не телепортируется в конец и не рвётся.

## Баг 2 (спроектирован, не реализован): `rAF` не годится для фонового индикатора

Для фавикона-индикатора (иконка вкладки браузера меняется, показывая состояние — например «идёт
процесс») выбор **обратный**: `setInterval`, не `rAF`. Индикатор существует ровно для того, кто
**ушёл** на другую вкладку — а `rAF` там полностью заморожен и не нарисует ни кадра. Взять сюда
`rAF` «по аналогии с остальной анимацией» — значит построить индикатор, который никогда не
сработает в момент, ради которого его писали.

Но и `setInterval` здесь не панацея: Chrome через несколько минут в фоне душит таймеры до **раза в
минуту** (не раза в секунду, как для `setTimeout` в баге 1 — троттлинг фоновых таймеров у Chrome
нарастает со временем нахождения в фоне). Полагаться на равномерное мигание как единственный
носитель информации нельзя — за минуту между тиками человек может не увидеть смену состояния
вовремя.

Вывод: состояние обязано читаться **со стоячего кадра** — постоянный цвет/форма иконки, не
требующие смены кадра, чтобы быть понятыми. Мигание — украшение поверх уже читаемого состояния,
включается только когда браузер даёт кадры, а не механизм передачи самого факта.

## Чеклист при выборе механизма

- Элемент виден на экране прямо сейчас и должен быть синхронизирован с реальным временем (не
  количеством кадров) → `rAF` + накопление по разнице кадров с зажимом (~100 мс), не от начала.
- Элемент должен продолжать работать, когда вкладка в фоне (индикатор в favicon/title, фоновая
  синхронизация) → `setInterval`/`setTimeout`, и состояние не должно зависеть от того, сработает
  ли конкретный тик — троттлинг фоновых таймеров в Chrome доходит до раза в минуту.
- Не смешивать: `setTimeout` для того, что видно на экране, ловит троттлинг как баг 1;
  `rAF` для того, что нужно в фоне, не сработает вовсе, как в баге 2.
- `prefers-reduced-motion` — отдельная ось, не подмена этого выбора: движение отключается, но
  состояние всё равно должно быть закодировано не только движением (цветом/формой), иначе оно
  теряется вместе с анимацией.
