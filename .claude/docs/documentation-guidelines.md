# Правила документации приложений

**Эталонный проект:** `apps/driving-school` - используй его структуру документации как образец для других приложений.

## Обязательная структура документации

Каждое приложение должно иметь следующие файлы документации:

| Файл                   | Назначение                                                                        |
| ---------------------- | --------------------------------------------------------------------------------- |
| **README.md**          | Главная страница проекта: обзор, версия, быстрый старт, навигация по документации |
| **PLAN.md**            | Техническое задание: текущее состояние, планируемые фичи, roadmap                 |
| **PLAN_COMPLETED.md**  | Выполненные задачи: детали всех реализованных фич, исправленные баги              |
| **PLAN_TESTING.md**    | План тестирования: статистика тестов, планы по фазам                              |
| **CHANGELOG.md**       | История изменений в формате [Keep a Changelog](https://keepachangelog.com/)       |
| **docs/README.md**     | Оглавление технической документации (если есть папка docs/)                       |
| **docs/\*.md**         | Техническая документация по темам (DATABASE, API, SECURITY, и т.д.)               |
| **docs/testing/\*.md** | Детальные планы тестирования по фазам (если есть большой объём тестов)            |

## Обновление документации при изменениях

При внесении изменений в проект **обязательно** обновляй соответствующие файлы документации:

| Изменение                    | Файлы для обновления                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------ |
| **Новая фича**               | `PLAN.md`, `PLAN_COMPLETED.md`, `CHANGELOG.md`, `PLAN_TESTING.md`, `package.json` (версия) |
| **Баг-фикс**                 | `CHANGELOG.md`, `package.json` (patch версия)                                              |
| **Изменения БД**             | `docs/DATABASE.md` (если есть), `schema.zmodel`                                            |
| **Новые тесты**              | `PLAN_TESTING.md`, `docs/testing/PHASE*.md` (если есть)                                    |
| **Изменения безопасности**   | `docs/SECURITY.md` (если есть)                                                             |
| **Изменения деплоя**         | `DEPLOY.md` (если есть)                                                                    |
| **Изменения API**            | `docs/API.md` (если есть), страница `/developers` (если есть)                              |
| **Общие улучшения/прогресс** | `README.md` (секция прогресса, статистика тестов)                                          |

## Порядок обновления при завершении фичи

1. **Обновить `package.json`** — версия (semver: patch для фиксов, minor для фич, major для breaking changes)
2. **Обновить `PLAN.md`** — отметить фичу как выполненную (✅ + версия)
3. **Перенести детали фичи в `PLAN_COMPLETED.md`** — сразу после завершения, чтобы PLAN.md оставался компактным
4. **Обновить `CHANGELOG.md`** — добавить запись о релизе
5. **Обновить `PLAN_TESTING.md`** — если были добавлены или обновлены тесты
6. **Обновить `README.md`** — если изменилась статистика прогресса или тестов
7. **Обновить другие файлы по необходимости** — `docs/DATABASE.md`, `docs/API.md`, и т.д.

## Структура README.md

README.md должен содержать:

1. **Заголовок и описание** — название приложения, краткое описание
2. **Версия и стек** — текущая версия, технологический стек
3. **Структура документации** — таблицы с навигацией по всей документации
   - Основная документация (корневая папка)
   - Дополнительная документация (`docs/`)
   - Документация по тестированию (`docs/testing/`)
4. **Быстрый старт** — команды для разработки, тестирования, деплоя
5. **Прогресс разработки** — таблица с прогрессом по фазам
6. **Основные разделы ТЗ** — роли, функции, и т.д.
7. **Тестирование** — статистика тестов, покрытие
8. **Полезные ссылки** — ссылки на монорепо документацию
9. **Как работать с документацией** — пошаговая инструкция
10. **Методология разработки** — TDD, планирование, коммиты, версионирование
11. **Обновление документации при изменениях** — таблица с правилами (см. выше)
12. **Последнее обновление** — дата последнего обновления документации

## Версионирование (Semver)

Используй семантическое версионирование для всех приложений:

- **Major (1.0.0 → 2.0.0)**: Breaking changes - изменения несовместимые с предыдущей версией
- **Minor (1.0.0 → 1.1.0)**: Новые фичи - добавление новой функциональности
- **Patch (1.0.0 → 1.0.1)**: Баг-фиксы - исправление ошибок

## Формат CHANGELOG.md

Используй формат [Keep a Changelog](https://keepachangelog.com/):

```markdown
# Changelog

## [Unreleased]

### Added

- Новая фича

### Changed

- Изменение существующей функциональности

### Fixed

- Исправление бага

## [1.2.0] - 2025-12-13

### Added

- Добавлена поддержка экспорта в PDF

### Fixed

- Исправлена ошибка валидации формы
```

## .claude/rules/ — Path-specific правила

Claude Code автоматически загружает правила из `.claude/rules/` для соответствующих путей.

### Структура

```
.claude/rules/
├── nextjs-apps.md         # Общие правила для Next.js apps
├── forms.md               # Правила для форм (*-form.tsx, schemas/)
├── database.md            # Правила для работы с БД (schema.zmodel)
├── testing.md             # Правила для тестов (specs/, *-e2e/)
├── premium-rosstil.md     # Специфика premium-rosstil
├── driving-school.md      # Специфика driving-school
└── libs.md                # Правила для библиотек (libs/)
```

### Формат правила

```markdown
---
paths: apps/premium-rosstil/**/*
---

# Правила для Premium Rosstil

## Фирменный стиль

- Золотой цвет: `#CA9E67`
- Используй `colorPalette="fg"` для кнопок
```

### Преимущества

- **Модульность** — правила загружаются только для нужных файлов
- **Компактный CLAUDE.md** — детали вынесены в отдельные файлы
- **Автозагрузка** — Claude Code сам подхватывает правила

## Язык документации

- Вся документация пишется на **русском языке**
- Используй профессиональный, но понятный язык
- Избегай жаргона где возможно
