# Правила документации приложений

**Эталонный проект:** `apps/driving-school` - используй его структуру документации как образец для других приложений.

## Обязательная структура документации

Каждое приложение должно иметь следующие файлы документации:

| Файл                   | Назначение                                                                        |
| ---------------------- | --------------------------------------------------------------------------------- |
| **README.md**          | Главная страница проекта: обзор, версия, быстрый старт, навигация по документации |
| **PLAN.md**            | Техническое задание: текущее состояние, планируемые фичи, roadmap                 |
| **PLAN_COMPLETED.md**  | Выполненные задачи: детали всех реализованных фич, исправленные баги              |
| **PLAN_TESTING.md**    | План тестирования: статистика тестов, планы по фазам                              |
| **CHANGELOG.md**       | История изменений в формате [Keep a Changelog](https://keepachangelog.com/)       |
| **docs/README.md**     | Оглавление технической документации (если есть папка docs/)                       |
| **docs/\*.md**         | Техническая документация по темам (DATABASE, API, SECURITY, и т.д.)               |
| **docs/testing/\*.md** | Детальные планы тестирования по фазам (если есть большой объём тестов)            |

## Обновление документации при изменениях

При внесении изменений в проект **обязательно** обновляй соответствующие файлы документации:

| Изменение                    | Файлы для обновления                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------ |
| **Новая фича**               | `PLAN.md`, `PLAN_COMPLETED.md`, `CHANGELOG.md`, `PLAN_TESTING.md`, `package.json` (версия) |
| **Баг-фикс**                 | `CHANGELOG.md`, `package.json` (patch версия)                                              |
| **Изменения БД**             | `docs/DATABASE.md` (если есть), `schema.zmodel`                                            |
| **Новые тесты**              | `PLAN_TESTING.md`, `docs/testing/PHASE*.md` (если есть)                                    |
| **Изменения безопасности**   | `docs/SECURITY.md` (если есть)                                                             |
| **Изменения деплоя**         | `DEPLOY.md` (если есть)                                                                    |
| **Изменения API**            | `docs/API.md` (если есть), страница `/developers` (если есть)                              |
| **Общие улучшения/прогресс** | `README.md` (секция прогресса, статистика тестов)                                          |

## Порядок обновления при завершении фичи

1. **Обновить `package.json`** — версия (semver: patch для фиксов, minor для фич, major для breaking changes)
2. **Обновить `PLAN.md`** — отметить фичу как выполненную (✅ + версия)
3. **Перенести детали фичи в `PLAN_COMPLETED.md`** — сразу после завершения, чтобы PLAN.md оставался компактным
4. **Обновить `CHANGELOG.md`** — добавить запись о релизе
5. **Обновить `PLAN_TESTING.md`** — если были добавлены или обновлены тесты
6. **Обновить `README.md`** — если изменилась статистика прогресса или тестов
7. **Обновить другие файлы по необходимости** — `docs/DATABASE.md`, `docs/API.md`, и т.д.

## Структура README.md

README.md должен содержать:

1. **Заголовок и описание** — название приложения, краткое описание
2. **Стек** — технологический стек. Версию **не дублировать в прозе** — она уже есть в
   `package.json` и топ-записи `CHANGELOG.md`, а ручное число в README расходится с ними при
   каждом релизе (см. эталон `apps/animatrona-landing/README.md` — ссылка на
   [CHANGELOG.md](../../apps/animatrona-landing/CHANGELOG.md) вместо статичной строки)
3. **Структура документации** — таблицы с навигацией по всей документации
   - Основная документация (корневая папка)
   - Дополнительная документация (`docs/`)
   - Документация по тестированию (`docs/testing/`)
4. **Быстрый старт** — команды для разработки, тестирования, деплоя
5. **Прогресс разработки** — таблица с прогрессом по фазам
6. **Основные разделы ТЗ** — роли, функции, и т.д.
7. **Тестирование** — статистика тестов, покрытие
8. **Полезные ссылки** — ссылки на монорепо документацию
9. **Как работать с документацией** — пошаговая инструкция
10. **Методология разработки** — TDD, планирование, коммиты, версионирование
11. **Обновление документации при изменениях** — таблица с правилами (см. выше)
12. **Последнее обновление** — дата последнего обновления документации

## Версионирование (Semver)

Используй семантическое версионирование для всех приложений:

- **Major (1.0.0 → 2.0.0)**: Breaking changes - изменения несовместимые с предыдущей версией
- **Minor (1.0.0 → 1.1.0)**: Новые фичи - добавление новой функциональности
- **Patch (1.0.0 → 1.0.1)**: Баг-фиксы - исправление ошибок

## .claude/rules/ — Path-specific правила

Claude Code автоматически загружает правила из `.claude/rules/` для соответствующих путей.

### Структура

```
.claude/rules/
├── nextjs-apps.md         # Общие правила для Next.js apps
├── forms.md               # Правила для форм (*-form.tsx, schemas/)
├── database.md            # Правила для работы с БД (schema.zmodel)
├── testing.md             # Правила для тестов (specs/, *-e2e/)
├── driving-school.md      # Специфика driving-school
└── libs.md                # Правила для библиотек (libs/)
```

### Формат правила

```markdown
---
paths: apps/driving-school/**/*
---

# Правила для Driving School

## Фирменный стиль

- Используй `colorPalette="fg"` для кнопок
```

### Преимущества

- **Модульность** — правила загружаются только для нужных файлов
- **Компактный CLAUDE.md** — детали вынесены в отдельные файлы
- **Автозагрузка** — Claude Code сам подхватывает правила

### ⚠️ Правило без `paths:` грузится в КАЖДУЮ сессию

Frontmatter `paths:` — это не украшение, а единственное, что отличает path-scoped правило от
always-on. Файл без него попадает в контекст любой сессии целиком, независимо от темы работы;
на 2026-09-16 таких файлов десять и весят они ~96 КБ поверх `CLAUDE.md`.

Отсюда два требования к содержимому always-on правила:

- **Императив, а не разбор.** «Делай так / не делай так» + одна строка «почему» остаются в
  правиле. Реконструкция инцидента («прецедент 2026-08-19: агент сделал X, потерялись файлы
  Y…») переезжает в `.claude/docs/` и цитируется ссылкой.
- **Правило без `paths:` — сознательное решение, а не забывчивость.** Оно оправдано, когда
  запрет должен действовать в момент, когда агент ещё не открыл ни одного подходящего файла
  (`git.md`, `security.md`, `formatting.md`). Если правило касается работы с конкретным типом
  файлов — у него обязан быть `paths:`.

⚠️ Path-scoped правило инжектится при **чтении** подходящего файла и **не** инжектится при
`Write` ([claude-code#23478](https://github.com/anthropics/claude-code/issues/23478)) — правило,
которое должно действовать в момент создания нового файла, `paths:` получать не должно.

## Индекс документации монорепо — два уровня

Доки `.claude/docs/` индексируются дважды, и это не дублирование по недосмотру:

| Файл                                              | Что там                                    | Цена                       |
| ------------------------------------------------- | ------------------------------------------ | -------------------------- |
| `CLAUDE.md` § «Документация»                      | строка на док: ссылка + 5–10 слов + ⚠️/⭐   | контекст **каждой** сессии |
| [`.claude/docs/INDEX.md`](/.claude/docs/INDEX.md) | развёрнутая аннотация с механизмом ловушки | читается по требованию     |

**Новый док → две записи**, в одинаковый по названию тематический раздел обоих файлов.
Длинную аннотацию писать **только** в `INDEX.md`; в `CLAUDE.md` — одна строка, без переносов.

**Почему так:** до 2026-09-16 индекс жил только в `CLAUDE.md`, аннотации разрослись до 5–8 строк
и пересказывали док целиком — раздел занял 912 строк из 1120 (81% файла, ~126 КБ в каждой
сессии). Пересказ при этом хуже оригинала: его хватает, чтобы решить, будто тема знакома, и не
хватает, чтобы починить. Разросшаяся строка в `CLAUDE.md` — сигнал, что содержимое пора
переносить в `INDEX.md`, а не повод сокращать смысл.

**Автоматическая проверка:** правило «новый док → две записи» и лимит длины строки держатся не
только на дисциплине — `bun scripts/check-all.mjs --only=docs-index-integrity` (уровень `gate`)
сверяет, что каждый `.claude/docs/*.md` упомянут ссылкой и в `CLAUDE.md`, и в `INDEX.md`, что все
локальные ссылки `](/путь)` в обоих файлах ведут на существующие файлы, и предупреждает (`warn`),
если строка дока в `CLAUDE.md` длиннее 200 символов — это единственный сигнал, что аннотация
снова начала разрастаться. Входит в общий раннер `bun scripts/check-all.mjs`.

## ⚠️ Раздел устарел — `nx format` (Prettier) убран из канонического пути (2026-08-06)

> **§32 закрыт:** dprint выбран единственным форматтером репозитория, `.prettierrc` удалён,
> канонической командой форматирования стала `nx run-many -t format --projects=<проекты>`. Раздел ниже описывал порчу плановых
> файлов встроенной командой `nx format` (Prettier) — при канонической dprint-команде она не
> воспроизводится (`dprint fmt` на плановых файлах идемпотентен). Оставлено как историческая
> запись; предупреждение о ручной перепроверке анкеров после **любого** форматтера остаётся
> разумной привычкой, но раздел больше не описывает актуальный шаг перед коммитом.

Плановые файлы (`PLAN.md`, `PLAN_COMPLETED.md`, `CHANGELOG.md` и т.д.) попадают под общий
`**/*.md` и форматируются наравне с прочим markdown. На больших планах с ручной вложенной
структурой (список пунктов, где подпункты оформлены текстом внутри жирного пункта, а не
настоящим markdown-списком с отступом) форматтер может:

- сжать многострочные подпункты в одну строку;
- перестроить ширину столбцов таблицы, сдвинув видимые границы ячеек;
- **снять отступ у строки-продолжения**, если внутри пункта есть inline-код, разорванный
  переносом строки (``(`No`` … ``skipping...`)``). Строка выпадает из пункта списка и
  начинает рендериться как отдельный абзац. Воспроизводится только на полном файле — на
  вырезанном фрагменте нет, поэтому «проверю кусок» не помогает.

**Прецедент (2026-07-28):** в `apps/aboi/PLAN.md` таблица §M.10 после `dprint` потеряла
выравнивание столбцов при следующей правке того же блока — Edit-анкер, скопированный из
не отформатированного состояния, перестал совпадать с текстом файла. В
`poster-microtext-desktop/PLAN.md` похожая история: подпункты задачи «Режим календаря»
(разные буллеты с описанием года/раскладки/выходных) слиплись в одну строку ещё раньше.

**Что делать:** после автоформатирования (`nx run-many -t format --projects=<проекты>`, или PostToolUse-хук)
планового файла — **перечитать (Read) отредактированный участок перед следующей правкой**, не
полагаться на текст, скопированный до форматирования.
Для длинных вложенных списков внутри пункта плана предпочитать настоящие markdown-подпункты
(с отступом и `-`/`1.`), а не текст-с-переносами внутри одного жирного буллета — так меньше
шанс, что dprint схлопнет структуру непредсказуемо.

## Язык документации

- Вся документация пишется на **русском языке**
- Используй профессиональный, но понятный язык
- Избегай жаргона где возможно
