# Взаимные post-update политики не сериализуют связанные строки

Проверено на ZenStack ORM/policy 3.9.7 и PostgreSQL READ COMMITTED (2026-10-16).

## Когда читать

Инвариант зависит от двух таблиц: изменение состояния родителя проверяет дочерние строки,
а запись в дочерней таблице проверяет состояние родителя. Последовательные тесты и сервисы
с блокировкой проходят, но прямой enhanced ORM остаётся самостоятельным путём записи.

## Гонка

1. Исходно родитель открыт, у дочерней строки разрешение false.
2. Первая транзакция закрывает родителя; post-update не видит незакоммиченное разрешение второй.
3. Вторая ставит разрешение true; её проверка ещё видит старое открытое состояние родителя.
4. Обе могут завершиться: инвариант нарушен, хотя каждая политика по отдельности корректна.

Обычный тест последовательных update этого не проверяет. Общая блокировка только внутри
серверных сервисов тоже не защищает прямые ORM-вызовы.

## Защита

Все пути изменения зависимого разрешения должны блокировать одну строку родителя.
Для прямого ORM это можно обеспечить BEFORE INSERT/UPDATE триггером: перед разрешающей
записью `SELECT ... FOR UPDATE`, затем проверка актуального состояния. Отсутствующий родитель
тоже считается отказом: использовать `IS DISTINCT FROM`, а не неравенство с SQL NULL.

Post-update политика родителя сохраняется. Сырой клиент остаётся доверенным серверным
интерфейсом; если гарантия требуется и для произвольного raw SQL, нужна отдельная DB-защита
перехода родителя. Это границу доверия следует назвать явно.

Сервисы берут блокировки в одном порядке: родитель, затем дочерние строки. Прямой update
может взять дочернюю строку раньше триггера: возможен deadlock с откатом одной транзакции.
Такой откат не разрешает автоматически повторять пользовательское согласие при новом статусе.

## Проверка

Нужны два реальных соединения. Первое меняет состояние родителя, не коммитит; второе пробует
разрешающую дочернюю запись. Дождаться либо завершения запроса, либо Lock в `pg_stat_activity`,
затем завершить первую транзакцию и проверить отказ второй и итоговые данные. До защиты
тест должен воспроизвести запрещённую комбинацию. Отдельно проверить обратный порядок,
обычный сервисный путь и обработку возможного отката.

Не обещать сериализацию при другом уровне изоляции без отдельного DB-теста.
