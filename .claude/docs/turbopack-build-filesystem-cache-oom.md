# `next build` (Turbopack) убит OOM на компиляции после правки `next.config` — постоянный кеш сборки

⚠️ Выглядит как «на хосте кто-то съел память» или «приложение разрослось», а корень — в
постоянном кеше сборки Turbopack (`experimental.turbopackFileSystemCacheForBuild`), который **с
Next.js 16.3.0 включён по умолчанию**. Пока кеш тёплый, сборка проходит быстро и дёшево много
дней подряд. Первая же правка, которая этот кеш сбрасывает (`next.config`, зависимости), делает
сборку кратно тяжелее обычной холодной, и она падает.

Соседний, но другой класс — [nextjs-build-worker-count-oom-shared-host](nextjs-build-worker-count-oom-shared-host.md):
там OOM на фазе «Collecting page data» и лечится `experimental.cpus`. На компиляцию
`experimental.cpus` не влияет вообще.

## Симптом

Production-хост s2 (15 ГБ RAM + 8 ГБ swap, ~40 контейнеров). Приложение монорепо: ~185
`page.tsx` + 39 `route.ts`, Next.js 16.3.5, Turbopack, `experimental.cpus: 2` уже стоит.

- Две попытки деплоя подряд убиты на одной точке: `Creating an optimized production build ...`
  → `Killed`, ни строки диагностики от Next.
- `dmesg`: жертва — сам `next-build (v16)`, **anon-rss 10.6 и 10.7 ГБ**. Базовая нагрузка хоста
  в тот момент ~5.5 ГБ RAM + ~5.3 ГБ в swap (`VmSwap` по процессам), то есть на сборку остаётся
  ~11 ГБ.
- Первичный диагноз «хост перегружен параллельными сборками» — ложный след: `free -h` в момент
  падения показывает 14/15 ГБ, но почти всё это сам `next-build`.
- Накануне тот же хост собрал то же приложение без проблем. В `.next/trace-build` той сборки
  `run-turbopack` — **108 с**, есть span `turbopack-persistence` (`task_count`, `bytes_written`) —
  то есть сборка шла на тёплом кеше (`.next/cache/turbopack`, 2.2 ГБ).
- Между двумя сборками в `next.config.mjs` добавили одну библиотеку в `transpilePackages`.

## Замер

Локально (Windows, 31 ГБ RAM), чтобы сравнить варианты при прочих равных. Сборка в отдельный
`distDir` (`NEXT_DIST_DIR=.next-memcheck`, шаблон `.next*` уже в `.nxignore`), параллелизм
Turbopack прижат к числу vCPU сервера переменной `TURBO_TASKS_AVAILABLE_PARALLELISM=8` (её
разбирает `turbopack/crates/turbo-tasks/src/parallel.rs`). Метрика — сумма `PrivatePageCount` по
дереву процессов сборки, опрос каждые ~2 с (`Win32_Process`), с аварийной остановкой при
исчерпании commit-памяти машины.

| Вариант                                                           | Компиляция              | Вся сборка       | Пик памяти    |
| ----------------------------------------------------------------- | ----------------------- | ---------------- | ------------- |
| Кеш включён, в кеше снимок **до** правки конфига (как на сервере) | не закончилась за 312 с | прервана защитой | **> 23.1 ГБ** |
| Кеш включён, пустой (чистая холодная сборка)                      | 147 с                   | 164 с            | **14.9 ГБ**   |
| `turbopackFileSystemCacheForBuild: false`                         | 103 с                   | 110 с            | **8.2 ГБ**    |
| то же + `turbopackInputSourceMaps: false`                         | 114 с                   | 124 с            | **7.0 ГБ**    |
| итог: оба флага + `turbopackIgnore` на рантаймовых fs-путях       | 118 с                   | 132 с            | **6.6 ГБ**    |

Последняя строка — после того как рантаймовый путь к каталогу загрузок в одном модуле получил
`/* turbopackIgnore: true */` (см. [nextjs-dynamic-fs-path-tracing](nextjs-dynamic-fs-path-tracing.md)):
пропали два предупреждения «The file pattern ... matches N files» (12 и 48 тыс. файлов), пик
снизился ещё на ~0.4 ГБ.

Без кеша сборка не только в ~2 раза легче чистой холодной с кешем и в 3+ раза легче сборки
на сброшенном кеше, но и **быстрее** холодной с кешем. После компиляции основной процесс с
включённым кешем продолжает держать ~13.5 ГБ, без кеша падает до ~2.2 ГБ.

Абсолютные цифры Windows (`PrivatePageCount`) и Linux (`anon-rss`) напрямую не сравнимы, важно
соотношение вариантов. Для ориентира: сборка на сброшенном кеше убита на сервере при 10.7 ГБ,
локально дошла до 23 ГБ и не закончила компиляцию.

## Механизм

`node_modules/next/dist/build/turbopack-build/impl.js`:

```js
const persistentCaching = config.experimental?.turbopackFileSystemCacheForBuild || false
// ...
isPersistentCachingEnabled: persistentCaching,
// ...
const sharedTurboOptions = {
  turbopackMemoryEviction: config.experimental.turbopackMemoryEvictionMode,
  dependencyTracking: persistentCaching || hasDeferredEntries,
  isShortSession: true,
  // ...
}
```

Включённый кеш сборки включает и **отслеживание зависимостей между задачами** turbo-tasks — граф,
по которому при следующей сборке понятно, что можно взять из кеша. Для разовой сборки без кеша
этот граф не нужен и не строится, отсюда разница 14.9 → 8.2 ГБ на чистой холодной сборке.

Почему сборка на **сброшенном** кеше ещё тяжелее чистой холодной (> 23 ГБ против 14.9 ГБ) —
по исходникам не проверялось, это наблюдение. Правдоподобно: в памяти одновременно
восстановленные из кеша данные задач и их пересчёт после инвалидации.

## Что не помогает

- **`experimental.turbopackMemoryEviction`** (`'auto'` по умолчанию, `'full'`, `false`) — по
  документации Next (`dist/docs/.../turbopackMemoryEviction.md`) действует только в `next dev`:
  вытеснение опирается на уже записанный на диск снимок, а сборка пишет его один раз, в конце.
- **`experimental.cpus`** — ограничивает воркеры «Collecting page data», компиляцию не трогает.
- **`NODE_OPTIONS=--max-old-space-size`** — основная память Turbopack в нативной (Rust) части,
  а не в куче V8. Если бы упиралось в кучу V8, процесс падал бы с `JavaScript heap out of memory`,
  а не убивался ядром.
- **Повтор «в менее загруженное время»** — нагрузка хоста тут вторична, сборка сама не влезает.

## Фикс

В `next.config.*` приложения:

```js
experimental: {
  turbopackFileSystemCacheForBuild: false,
  // опционально, ещё −15% пика (8.2 → 7.0 ГБ в замере выше)
  turbopackInputSourceMaps: false,
},
```

Цена первого флага — каждая сборка холодная, тёплого ускорения больше нет. Для приложения выше
это 110 с на всю сборку локально.

Цена второго — Turbopack не читает `.map`, приложенные к готовым пакетам в `node_modules`. Кадры
стека внутри сторонних библиотек в трекере ошибок остаются в собранном виде, без маппинга на
исходники библиотеки. Собственный код и workspace-либы компилируются из исходников и маппятся как
раньше; клиентские sourcemap (`productionBrowserSourceMaps`) продолжают строиться. Документация Next сама предлагает этот флаг, если окружение не сохраняет
`.next/cache` между сборками. Старый каталог `.next/cache/turbopack` на сервере после этого не
читается и занимает только диск.

Флаг — ответ на реальный профиль памяти конкретного хоста, не универсальная рекомендация.
Приложения с меньшим числом маршрутов или хосты с запасом памяти спокойно живут с кешем
по умолчанию и получают быстрые тёплые сборки.

## Почему это ловушка

- Кеш по умолчанию **включён молча** (16.3.0), в `next.config` его не видно.
- Пока кеш тёплый, всё зелёное и быстрое. Бомба срабатывает на следующей правке `next.config` или
  на обновлении зависимостей — то есть на коммите, который к памяти никакого отношения не имеет.
  Для репо, где `/infra:deps-update` бампает зависимости всем приложениям разом, это означает
  падение сборки у всех крупных приложений в следующий деплой после бампа.
- Убитый ядром процесс не пишет ни `trace`, ни снимок кеша — кеш на сервере остаётся в состоянии
  «до правки», и каждая повторная попытка снова стартует со сброшенным кешем.

## Диагностика

- `dmesg -T | grep -i "killed process"` — жертва `next-build`, момент — до `Compiled successfully`.
- Лог обрывается на `Creating an optimized production build ...` — фаза компиляции, не сбор
  данных страниц.
- В `.next/trace-build` последней успешной сборки есть span `turbopack-persistence` — кеш сборки
  включён; очень короткий `run-turbopack` — сборка шла на тёплом кеше.
- `git diff <коммит успешной сборки>..HEAD -- next.config.* package.json` и корневой `bun.lock`:
  что могло сбросить кеш.
- Числа по вариантам проще всего получить локально в отдельном `distDir` — см. метод выше.

## Аудит других приложений (2026-09-15)

Приложение из инцидента выше собирается на s2 — том же хосте, что держит ещё несколько
Next.js-приложений монорепо, тоже на Turbopack (не `next build --webpack`) и тоже без флага
`turbopackFileSystemCacheForBuild: false`. Проверялось: список приложений, собирающихся
Turbopack, у каждого — число `page.tsx`+`route.ts` и наличие флага в `next.config.*`.

Из приложений, реально деплоящихся production-сборкой на **s2** (не Electron/десктоп — у тех
сборка идёт локально у разработчика или в CI, другой профиль памяти хоста, не разбирался
здесь), нашлось ещё три без флага. Два крупнейших из них измерены тем же методом (пустой
`distDir`, `TURBO_TASKS_AVAILABLE_PARALLELISM=8`, сумма `PrivateMemorySize` дерева процессов
сборки, Windows/31 ГБ):

| Размер (page+route) | Пустой кеш (пик) | Кеш выключен (пик)       | Решение                   |
| ------------------- | ---------------- | ------------------------ | ------------------------- |
| ~180                | 11.2 ГБ          | 5.9 ГБ (−47%, и быстрее) | флаг выключен превентивно |
| ~134                | 11.7 ГБ          | 6.3 ГБ (−46%, и быстрее) | флаг выключен превентивно |
| ~30                 | не измерялось    | —                        | флаг НЕ трогали           |

Тот же паттерн, что в основном инциденте: пик на пустом (холодном, но кеш-совместимом) кеше
уже на грани бюджета хоста (~11 ГБ на сборку, см. «Симптом» выше) сам по себе — а сборка на
**сброшенном** кеше (после правки `next.config`/зависимостей, не пустом) канонически ещё
тяжелее пустого, см. замер выше (> 23 ГБ против 14.9 ГБ). То есть margin «пока помещаемся»
для этих двух приложений — ложное спокойствие ровно того же типа, что уронило приложение из
инцидента: тёплая/пустая сборка проходит, первая же сброшенная — не проходит.

`turbopackInputSourceMaps: false` (второй флаг из фикса выше, ещё ~−15% пика) сюда **не**
добавлялся — у обоих запас с одним выключенным кешем уже достаточный (5.9–6.3 ГБ из ~11 ГБ
бюджета хоста), а цена флага (частичная потеря маппинга стектрейсов сторонних библиотек в
трекере ошибок) не окупается без реальной нужды.

Третье, самое маленькое приложение (~30 page+route, на порядок меньше остальных) флагом не
тронуто и не измерялось отдельно — экстраполяция по обоим измеренным (соотношение пика к
размеру у них расходится, 62–87 МБ на page/route) даёт грубую верхнюю оценку в пределах
3–5 ГБ на холодной сборке, далеко от бюджета хоста; **не копировать флаг бездумно в маленькие
приложения** — для них тёплый кеш даёт быстрые повторные сборки без риска, который флаг снимает.

Точные имена приложений, коммиты правки `next.config.*` и учёт времени — приватный журнал
(эта запись сознательно не называет приватные submodule-приложения, см.
`.claude/rules/public-repo-hygiene.md`).

### Метод измерения — уточнение к разделу «Замер» выше

Постройка через прямой вызов `next build` (не `nx build`) из корневого
`node_modules/.bin/next.exe` с `cwd` внутри приложения — обходит обвязку Nx, которая не
нужна для замера и не влияет на память самого Turbopack. Приложениям с обращением к БД на
этапе «Collecting page data» (через `getEnhancedPrisma`/социальные провайдеры и т.п.) для
чистого замера нужен поднятый локальный dev-контейнер БД — без него сборка падает на этой
фазе `ECONNREFUSED` уже после того, как компиляция (интересующая эту ловушку фаза) завершилась,
так что частичный пик компиляции всё равно виден в логе, но для сопоставимого end-to-end числа
проще поднять `docker compose -f docker-compose.dev.yml up -d db` на время замера.
