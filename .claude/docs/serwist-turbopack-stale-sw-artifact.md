# ⚠️ `@serwist/next` не поддерживает Turbopack, а `public/sw.js` в `.gitignore` — воркер вечно висит в `installing`

**Кратко:** `@serwist/next` встраивается в **webpack**. Собери приложение Turbopack'ом — воркер
не пересоберётся, при этом на диске останется `public/sw.js` от прошлой webpack-сборки. Он
отдаётся как ни в чём не бывало, регистрируется, и навсегда застревает в состоянии `installing`,
потому что его прекеш-манифест ссылается на чанки, которых в новой сборке нет.

Найдено 2026-09-03 на `studio` при проверке оффлайн-режима.

## Как выглядит

`navigator.serviceWorker.getRegistrations()` возвращает регистрацию, но она мёртвая:

```js
{ installing: 'installing', waiting: null, active: null }   // и так навсегда
navigator.serviceWorker.controller // → null
```

Из этого вытекает целый веер симптомов, каждый из которых уводит в свою сторону:

- **оффлайн-режим «не работает»** — воркер не активируется, значит страницы не контролирует;
- **выключение оффлайн-режима «сломано»** — `unregister()` на воркере в состоянии `installing`
  **не резолвится вовсе**, висит, пока другая операция SW не протолкнёт очередь заданий;
- в сети — пачка `404` на `_next/static/chunks/...`, среди них характерные
  `webpack-*.js` и `polyfills-*.js`, **которых Turbopack не выпускает в принципе**.

Последний пункт — самый быстрый признак: если приложение собрано Turbopack'ом, а прекеш просит
`webpack-*.js`, значит `sw.js` приехал из другой, старой сборки.

## Почему артефакт выживает

`public/sw.js` — в `.gitignore` (иначе он попадал бы в коммит после каждой сборки). Поэтому:

- git его не подчищает и не показывает в `git status`;
- Turbopack-сборка его не трогает — ей нечем, плагина serwist в графе нет;
- `next start` отдаёт `public/` с диска как есть.

Итог: файл живёт между сборками неограниченно долго и переживает смену бандлера.

## Диагностика одной командой

Serwist сам предупреждает — но в логе сборки, среди прочего вывода:

```
[@serwist/next] WARNING: You are using '@serwist/next' with `next dev --turbopack`,
but it doesn't support Turbopack.
```

Прямая проба, не полагающаяся на чтение лога: удалить и посмотреть, вернётся ли.

```bash
cd apps/<app>
rm public/sw.js
bun x next build --webpack   # ← именно та команда, что в project.json
ls public/sw.js              # есть → воркер собирается; нет → serwist в этой сборке не участвует
```

## ⚠️ Ловушка проверки: `next build` ≠ команда сборки приложения

Отдельно стоит того, чтобы её назвать, потому что она порождает **ложный баг-репорт о коде
приложения**. В Next.js 16 Turbopack — сборщик по умолчанию, поэтому голый

```bash
bun x next build        # ⛔ Turbopack, serwist молчит
```

в приложении, у которого в `project.json` стоит `next build --webpack`, воспроизводит ровно
описанную поломку — и она выглядит как дефект оффлайн-режима самого приложения. Так и вышло
2026-09-03: «воркер застревает в installing даже на прод-сборке» было следствием того, что
проверяющий собрал не той командой, а не свойством кода. На честной `--webpack`-сборке тот же
сценарий проходит полностью: `active: 'activated'`, `controller: 'activated'`, выключение
снимает и регистрацию, и кеши.

**Правило:** команду сборки брать из `apps/<app>/project.json`, а не по памяти и не из привычки.
Это частный случай общего принципа из
[webpack-only-app-silent-export-drift](/.claude/docs/webpack-only-app-silent-export-drift.md).

## Что делать, если приложение переводят на Turbopack

Просто снять `--webpack` у приложения с serwist нельзя — оффлайн-режим тихо перестанет
существовать (сборка при этом зелёная). Варианты, которые предлагает сам serwist:

- `@serwist/turbopack` — экспериментальная поддержка;
- configurator mode — поддерживает Turbopack;
- следить за [serwist/serwist#54](https://github.com/serwist/serwist/issues/54).

Приложения с serwist на 2026-09-03: `studio`, `grandslamcup`, `archetest` — все на `--webpack`,
и это не случайность, а именно это ограничение.

## Соседняя ловушка того же конфига: `register: false` обязателен при консент-гейте

Не про Turbopack, но всплывает ровно там же и проверяется тем же прогоном. По умолчанию
`withSerwistInit` инжектит **собственный** скрипт, который регистрирует `/sw.js` со scope `/`
на **каждой** странице сайта безусловно — в обход `useOfflineConsent` и любого своего
`ServiceWorkerRegistration`. То есть гейт согласия становится декоративным: воркер и кеш
появляются раньше, чем пользователя вообще спросили.

```js
const withSerwist = withSerwistInit({
  swSrc: 'src/app/sw.ts',
  swDest: 'public/sw.js',
  register: false, // ← регистрирует приложение, по согласию пользователя
  disable: process.env.NODE_ENV === 'development',
})
```

⚠️ **В dev не воспроизводится вовсе** — там `disable: true`, serwist отключён целиком. Ловится
только на прод-сборке, замером в свежем контексте браузера до какого-либо согласия:

```js
await navigator.serviceWorker.getRegistrations() // должно быть [] до согласия
await caches.keys() // ⚠️ кеш `pages` создаёт сам Next.js (клиентский роутер-кеш), он тут ни при чём
```

Найдено в `archetest` 2026-07-28, а `studio` и `grandslamcup` тот же пропуск донесли до
2026-09-03 — фикс однострочный, но сам по себе он ниоткуда не всплывает.
