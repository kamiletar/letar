# Служебный флаг данных, который начал управлять отображением

## Симптом

Пользователь загружает картинку (или заполняет поле) через админку — и не видит результата на
сайте. Ошибки нет, запись в БД появилась, файл на диске лежит. Просто на экране по-прежнему
заглушка.

Второй симптом того же бага, менее заметный: сид исправно генерирует файлы-плейсхолдеры, которые
физически невозможно увидеть ни при каком состоянии интерфейса. Работа выполняется, результат
никуда не попадает.

## Причина

Служебный флаг записи (`isDemo`, `isDraft`, `isArchived`, `isTest`, `isSeed`) попал в условие
рендера и стал решать не только «что это за запись», но и «что показывать».

Прецедент — `apps/domwellbes`, компонент `houses/_components/house-visual.tsx` (исправлено
коммитом `fda7dbd` в приватном submodule, 2026-08-04):

```tsx
// ❌ было: флаг записи решает, показывать ли загруженное изображение
{!isDemo && image
  ? <Image src={image.url} … />
  : <Placeholder … />}
```

Поле `isDemo` задумывалось как пометка «эту запись потом заменим на настоящую». Но у **всех**
демо-записей `isDemo = true`, поэтому загруженная картинка не показывалась **никогда**. Владелец
контента загрузил бы фото через админку и не увидел бы его, пока кто-нибудь не полез бы в БД
снимать флаг руками.

Ошибка возникает естественно: во время разработки на демо-данных «демо-запись» и «нет реального
контента» — это одно и то же множество записей. Условие пишется по флагу, потому что в этот момент
флаг и наличие контента совпадают. Расходятся они позже, когда контент начинают наполнять — и
именно тогда, когда починить сложнее всего, потому что до кода уже никому нет дела.

## Почему не ловится проверками

- **Типы сходятся.** `isDemo: boolean` и `image: Image | null` — оба поля существуют, условие
  валидно.
- **Линт молчит.** Синтаксически это обычная тернарка.
- **Тесты не пишутся.** Кейс «а что если у демо-записи появилась настоящая картинка» не приходит в
  голову ни автору кода, ни автору тестов — в их картине мира это невозможное состояние.
- **E2E на сиде зелёные.** Сид создаёт записи с `isDemo = true` и без загрузок, интерфейс
  показывает заглушку — ровно то, чего ждёт тест.

Обнаруживается только руками и только если специально попробовать наполнить реальными данными
**именно демо-сущность**, а не создать новую.

## Правило

**Показывай то, что есть. Флаг используй только для пометок.**

Разведи две роли, которые слиплись:

1. **Что рендерить** — определяется наличием данных, а не флагом. Приоритет строится по факту:
   загруженное → типовая заглушка → нейтральная заливка.
2. **Что подписать** — вычисляется отдельным хелпером из того, что реально попало на экран.

Как это выглядит после починки:

```tsx
// ✅ приоритет по факту наличия данных
export function HouseVisual({ slug, name, image, … }: Props) {
  if (image) return <Image src={image.url} … />

  const atlasPosition = atlasPositionBySlug[slug]
  if (!atlasPosition) return <Box bg="brand.100" role="img" aria-label={`… пока не загружено`} />

  return <Box role="img" aria-label={`Визуализация проекта «${name}»`} … />
}

// ✅ подпись зависит от того, ЧТО на экране, а не от служебного флага записи
export function isVisualisation(image?: { kind: string } | null): boolean {
  if (!image) return true
  return image.kind === 'RENDER'
}
```

Обрати внимание на `isVisualisation`: подпись «Визуализация» теперь считается по полю `kind`
самого изображения. Это работает в обе стороны — демо-запись с загруженным фото покажет фото без
подписи, а реальный проект с рендером до окончания стройки получит подпись честно.

## Где ещё искать тот же баг

Класс повторяемый: любое приложение, где есть демо/черновые данные **и** загрузка контента, имеет
ту же развилку. Проверять стоит:

- `isDemo` / `isSeed` — «это демонстрационная запись»;
- `isDraft` / `isPublished` — «черновик» вместо «нет прав смотреть»;
- `isArchived` — «в архиве» вместо «не показывать данные»;
- `isTest` — тестовая запись, которую отфильтровали из выдачи целиком вместо того, чтобы просто
  не индексировать.

Быстрый греп по приложению — искать флаг рядом с рендером, а не рядом с запросом:

```bash
rg -n "isDemo|isDraft|isArchived|isTest" apps/<app>/src --glob '*.tsx'
```

Каждое попадание в `.tsx` (не в `_actions/`, не в `schema.zmodel`, не в фильтре запроса) —
кандидат на разбор. Флагу место в `where` запроса и в бейдже админки, а не в условии показа
контента.

## Как проверять

Одна проверка руками, которую нужно делать при заведении любой пары «демо-данные + загрузка»:

1. Возьми **существующую демо-сущность** (не создавай новую — весь смысл в том, что у неё уже
   стоит флаг).
2. Наполни её реальными данными через тот же интерфейс, которым будет пользоваться владелец
   контента: загрузи картинку, впиши текст, прикрепи файл.
3. Открой публичную страницу и убедись, что видишь именно загруженное.

Если данные не видны — флаг управляет отображением, чини по правилу выше.

Побочный признак того же бага, который видно без ручной проверки: сид генерирует артефакты
(файлы-плейсхолдеры, записи), которые ни при каком состоянии интерфейса не показываются. Если
сгенерированного больше, чем достижимого глазами — где-то в рендере стоит лишнее условие.
