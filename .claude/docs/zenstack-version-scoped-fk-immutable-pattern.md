# ZenStack: FK на copy-on-write версию нужно `@deny('update', true)`, даже если policy ничего не проверяет

## Симптом

Child-модель, входящая в состав/конфигурацию версионированного объекта (FK на версию-родителя
напрямую, либо транзитивно — через другую child-модель, у которой такой FK уже есть), пишется
исключительно через общий app-level хелпер вида:

```typescript
// apps/<app>/src/lib/*-version.ts
export async function getEditableXxxVersion(xxxId: string) {
  const current = await db.xxxVersion.findUniqueOrThrow({ where: { id: xxxId } })
  if (!current.isFrozen) { return current }
  // Финализация (например продажа) зафиксировала версию — клонируем перед правкой
  return db.xxxVersion.create({ data: cloneFrom(current) })
}
```

Server actions вызывают хелпер перед записью в дочерние модели, получают (возможно новый)
`versionId` и пишут его в `create`/`update`. Выглядит безопасно — редактирование замороженной
версии невозможно, потому что хелпер всегда возвращает свежий клон. На практике сама схема
ZenStack ничего не проверяет: FK-поле дочерней модели обычным образом принимает любое значение в
`update()`. Ни `@@allow`, ни `@@deny` этой child-модели не упоминают состояние родительской версии
вообще — иммутабельность держится только на дисциплине «все server actions идут через хелпер», а
не на access control policy. Payload с прямым `xxxVersionId` в `data` того же `update()`/`create()`
(баг, будущий server action, ручной скрипт) переносит запись на другую — в том числе замороженную —
версию в обход клонирования, и ни одна policy этого не остановит.

## Причина

Copy-on-write реализован целиком на уровне приложения (TypeScript-хелпер), а не как ZenStack
access policy. Из-за этого паттерн-детектор «relation-traversal в `@@allow`/`@@deny` до поля
состояния parent'а» (см.
[zenstack-relation-traversal-fk-repoint-bypass](/.claude/docs/zenstack-relation-traversal-fk-repoint-bypass.md))
на такие FK не срабатывает и не должен срабатывать — в схеме действительно нет условия, которое
можно было бы обойти репойнтом. Но отсутствие условия не значит отсутствие риска: ZenStack по
умолчанию разрешает менять любое поле, для которого нет явного запрета, а «иммутабельность после
заморозки» здесь — инвариант, который знает только код хелпера, не схема. Любой путь записи,
вызывающий `update()`/`create()` дочерней модели в обход хелпера, тихо ломает инвариант — ни
typecheck, ни policy-тест этого не поймают, потому что формально всё разрешено.

## Решение

Тот же приём, что и для relation-traversal варианта, но по другой причине: field-level
`@deny('update', true)` на самом FK-поле child-модели. Не «обойти условие через одновременный
repoint», а «условия вообще нет, поэтому поле нужно закрыть безусловно»:

```zmodel
model HouseItem {
  /// Immutable после создания — запись обязана идти через getEditableHouseVersion(),
  /// которая клонирует версию при первом редактировании после заморозки; без deny
  /// прямой update() мог бы перенести item на чужую (в т.ч. замороженную) версию
  houseVersionId String @deny('update', true)
  houseVersion   HouseVersion @relation(fields: [houseVersionId], references: [id])
}
```

`@deny` — чисто policy-уровень: `nx zenstack:generate <app>` + `nx db:push <app>` регенерируют
клиент без миграции DDL. Там, где payload реально может долетать до поля из клиентского запроса
(не только внутренний вызов с доверенными данными) — добавить `.strip()`/явный
`.omit({ houseVersionId: true })` в Zod-схему server action: deny — последний рубеж, не единственный.

Транзитивный случай — child-модель B, чей FK указывает не на саму версию, а на другую child-модель
A того же состава (`B.aId → A.id`, `A.houseVersionId → HouseVersion.id`) — защищать напрямую
бессмысленно: A уже не даст себя перенести, но B можно репойнтнуть на запись A из чужой версии,
минуя A вообще. Deny нужен на прямых FK каждой модели в цепочке, а не только на самом дальнем
родителе.

## Как искать этот паттерн

Не грепом по `@@allow`/`@@deny` (там условия может не быть вовсе) — искать нужно от самого
copy-on-write хелпера:

1. Найти функцию вида `getEditable<Что-то>Version`/`getOrCloneEditable<Что-то>` — обычно в
   `apps/<app>/src/lib/*-version.ts`, с докстрингом/комментарием, перечисляющим модели, которые
   обязаны идти через неё.
2. Для каждой перечисленной модели (и любой child-модели, транзитивно ссылающейся на неё)
   проверить, что её FK-поле на версию несёт `@deny('update', true)`.
3. Новая модель добавлена в докстринг хелпера, но `@deny` на её FK забыли — самый частый способ,
   которым паттерн воспроизводится: докстринг обновили как документацию, а схему — нет.
4. Модель пишется исключительно через хелпер, но НЕ входит в докстринг вообще — тоже кандидат:
   список в докстринге актуален настолько, насколько его поддерживают вручную, отсутствие записи
   не доказательство безопасности.

## Отличие от zenstack-relation-traversal-fk-repoint-bypass

[zenstack-relation-traversal-fk-repoint-bypass](/.claude/docs/zenstack-relation-traversal-fk-repoint-bypass.md)
— тот же фикс (`@deny('update', true)` на FK), но другая причина уязвимости: там policy
**пытается** enforced иммутабельность через `parent.status == X` в `@@allow`, и её обходят
одновременным repoint'ом FK в том же `update()`. Здесь policy вообще ничего не проверяет —
иммутабельность держится только на дисциплине вызова app-level хелпера, а не на условии в схеме.

Практическое следствие: модели, которые аудит по тому паттерну пометил «не подпадает — write-policy
не проверяет состояние parent'а, значит обходить нечего», нужно перепроверять по другому критерию —
«пишется ли модель через copy-on-write хелпер» вместо «есть ли relation-traversal условие в
policy». Именно так в domwellbes нашлись три волны FK, которые прежний аудит уже проверял и
ошибочно счёл безопасными (см. ниже).

## Известные случаи в монорепо

- **domwellbes** — child-модели состава версии дома, пишущиеся через общий app-level хелпер
  клонирования версии (`apps/domwellbes/src/lib/house-version.ts`). Закрыты тремя волнами
  2026-09-22: FK на саму версию напрямую (`houseVersionId` у нескольких моделей состава), FK
  транзитивно через другую child-модель того же состава (`groupId`, `optionId`,
  `replacesItemId`). Каждая волна сопровождалась spec-тестом, вызывающим
  `getEnhancedPrisma().<model>.update({ data: { <fk>: чужойVersionId } })` напрямую и проверяющим
  `.rejects.toThrow()`. Деталей схемы (конкретные имена моделей, состав) — в `PLAN.md`
  приложения, не здесь: [public-repo-hygiene](/.claude/rules/public-repo-hygiene.md).

## Как проверять при ревью новой version-scoped модели

1. Есть ли в приложении copy-on-write хелпер для версионированной сущности (`getEditable*Version`
   или аналог)? Если да — найти его полный список защищаемых моделей.
2. Для новой child-модели, добавленной в состав версии: несёт ли её прямой FK на версию (или на
   другую child-модель того же состава) `@deny('update', true)`?
3. Обновлён ли докстринг хелпера со списком моделей — не разошёлся ли он со схемой?
4. `nx zenstack:generate <app>` + `nx db:push <app>` (не миграция), `nx typecheck:tsgo <app>`,
   spec-тест напрямую на enhanced-клиент.
