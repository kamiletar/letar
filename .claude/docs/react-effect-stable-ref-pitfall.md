# React-эффекты, которые не перезапускаются, когда ждёшь их перезапуска

## Симптом

Эффект с зависимостью на ref/DOM-элемент компилируется и типизируется без единой ошибки, работает
на первом рендере — а потом молча перестаёт реагировать на события, ради которых был написан.
Никакого исключения, никакого предупреждения React — просто «второй раз не сработало».

Оба случая ниже нашлись в одной сессии над `apps/animatrona`, независимо друг от друга, и
оказались конкретными проявлениями одного и того же класса ошибки.

## Случай 1: эффект навешивается ДО монтирования реального узла (условный skeleton-рендер)

`useVirtualizedGrid` ([use-virtualized-grid.ts](/apps/animatrona/renderer/src/lib/hooks/use-virtualized-grid.ts))
подключал `ResizeObserver` через:

```ts
// ❌ containerRef.current в момент первого эффекта — null
const containerRef = useRef<HTMLDivElement | null>(null)

useLayoutEffect(() => {
  if (!containerRef.current) return
  const observer = new ResizeObserver(...)
  observer.observe(containerRef.current)
  return () => observer.disconnect()
}, []) // пустые deps — эффект живёт один раз за весь жизненный цикл компонента
```

`AnimeGrid.tsx`/`FranchiseView.tsx` при `isLoading === true` рендерят скелетон — дерево вообще без
элемента с `ref={containerRef}`. React вызывает эффект с пустыми deps один-единственный раз, именно
на этом первом (skeleton) рендере — `containerRef.current` в этот момент `null`, `ResizeObserver`
не создаётся. Когда позже приходят данные и монтируется реальный контейнер, эффект **уже
отработал** и повторно не запустится — зависимостей, которые бы это спровоцировали, нет.

Фикс — callback-ref вместо `useRef` + `useLayoutEffect([])`:

```ts
// ✅ вызывается заново при каждом реальном (re)монтировании DOM-узла
const [containerEl, setContainerEl] = useState<HTMLDivElement | null>(null)
const containerRef = useCallback((el: HTMLDivElement | null) => {
  setContainerEl(el)
}, [])

useLayoutEffect(() => {
  if (!containerEl) return
  const observer = new ResizeObserver(...)
  observer.observe(containerEl)
  return () => observer.disconnect()
}, [containerEl])
```

## Случай 2: эффект зависит от объекта, который создаётся один раз и переживает много логических событий

`VideoPlayer.tsx` ([VideoPlayer.tsx:130-166](/apps/animatrona/renderer/src/components/player/VideoPlayer.tsx#L130-L166))
вызывал автоплей внутри эффекта:

```ts
// ❌ globalVideoElement создаётся один раз в GlobalVideoProvider и никогда не меняется —
// перемещается между контейнерами через appendChild, сам объект стабилен всё время жизни приложения
useEffect(() => {
  const video = globalVideoElement
  ...
  if (video.readyState > 0) {
    ...
    if (autoPlayRef.current && video.paused) video.play()
  }
}, [globalVideoElement, autoPlay, setDuration])
```

Разработчик рассуждал в терминах «эффект должен сработать на каждую смену эпизода» — но
зависимость `globalVideoElement` физически не меняется никогда, поэтому эффект реально
перезапускается **один раз**, при первом монтировании `VideoPlayer`. На странице `/watch` это
маскировалось: переход между сериями там — навигация на другой route, которая полностью
ремонтит `VideoPlayer` (и тем самым «бесплатно» перезапускает все его эффекты). В папочном режиме
плеера (`/player`, `goNext()` меняет только state внутри того же смонтированного компонента —
ремаунта нет) следующая серия молча грузилась и оставалась на паузе: старый эффект просто не
получал сигнала о новом логическом событии «сменился src».

Фикс — источником повторного срабатывания сделан не сам стабильный объект, а его **событие**:
подписка на `loadeddata` вынесена в отдельный эффект без `{ once: true }`, слушатель остаётся
навешанным на весь жизненный цикл `video` и стреляет заново на каждую смену `src`:

```ts
// ✅ слушатель живёт всё время жизни video-элемента, срабатывает на каждый новый src
useEffect(() => {
  const video = globalVideoElement
  if (!video) return

  const onLoadedData = () => {
    setIsVideoReady(true)
    setIsLoading(false)
    setDuration(video.duration)
    if (autoPlayRef.current && video.paused) {
      video.play().catch(() => {})
    }
  }

  video.addEventListener('loadeddata', onLoadedData)
  return () => video.removeEventListener('loadeddata', onLoadedData)
}, [globalVideoElement, setDuration])
```

(Плюс отдельная ветка на `video.readyState > 0` в эффекте перемещения контейнера — для случая,
когда видео уже было готово ДО монтирования компонента и `loadeddata` в принципе не прозвонит
повторно.)

## Обобщённый паттерн

React-эффект с зависимостью на ref или DOM/внешний объект перестаёт быть надёжным сигналом
«что-то изменилось» в двух зеркальных ситуациях:

1. **Объект в deps появляется ПОЗЖЕ, чем срабатывает эффект** — потому что в момент первого
   рендера компонент рисует другое дерево (skeleton/loading-состояние) без нужного узла. Эффект
   с пустыми/стабильными deps срабатывает один раз именно в этот момент и не подхватывает узел,
   смонтированный позже.
2. **Объект в deps не пересоздаётся, хотя происходящее с ним логически меняется много раз** —
   персистентный DOM-элемент/сервис, живущий дольше одного «события» (смена эпизода, смена
   данных, смена src). Разработчик мысленно связывает срабатывание эффекта с событием, а React
   связывает его со ссылочным равенством зависимости — и если объект пережил уже десять событий
   без пересоздания, эффект отработал только один раз, при первом появлении этого объекта.

В обоих случаях типизация, `nx build`/`lint`/`typecheck:tsgo` проходят чисто — баг воспроизводится
только в рантайме, на конкретной последовательности взаимодействий (первая загрузка со скелетоном,
переключение серии без ремаунта), и в другом сценарии (сразу есть данные, навигация между route)
маскируется, создавая ложное ощущение, что код работает.

## Чеклист при ревью похожего кода

- Эффект зависит от ref (`someRef.current`) внутри тела эффекта, а не от значения в массиве
  deps? → он никогда не перезапустится при смене этого значения. Если компонент в некоторых
  состояниях (loading/skeleton) не рендерит DOM-узел, на который смотрит ref — переводи на
  callback-ref (`useState<T | null>` + `useCallback`) и клади получившееся значение в deps.
- Объект в deps — **персистентный** (создан один раз в контексте/сторе/провайдере и живёт весь
  жизненный цикл приложения, а не пересоздаётся на каждое логическое событие)? Явно проверь: то,
  ради чего написан эффект — реакция на «объект появился» (тогда стабильных deps достаточно) или
  реакция на «с объектом что-то произошло» (тогда нужен слушатель/эффект, срабатывающий на
  каждое такое происшествие — например `addEventListener` без `{ once: true }`, а не сам факт
  наличия объекта в зависимостях)?
- Поведение отличается между двумя путями навигации к одному и тому же экрану (полный ремаунт
  route vs смена state внутри уже смонтированного компонента)? Это сильный сигнал ровно этого
  бага — ремаунт «бесплатно» перезапускает все эффекты и маскирует то, что при обычном
  обновлении state эффект не сработал бы повторно.
- Если чинишь через доп. ветку кода для «уже готово к моменту монтирования» (как
  `video.readyState > 0` в случае 2) — не забывай, что это отдельная ветка, а не замена
  слушателю: она покрывает «эффект уже произошёл до монтирования», слушатель — «эффект
  произойдёт после».
