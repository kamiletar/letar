# Bind-mount'ы Docker: две ловушки, дающие ложноположительную проверку

Обе найдены вживую 2026-08-06 при развёртывании `infra/acme-dns` и подготовке `infra/traefik`
([PLAN-INFRA.md §48](/PLAN-INFRA.md)). Ни одна не ловится линтером, типами или сборкой, и обе
опасны не сами по себе, а тем, что **выглядят как успех**.

## 1. `docker compose up -d` не перечитывает смонтированный конфиг

Конфигурационный файл смонтирован volume'ом:

```yaml
volumes:
  - ./config:/etc/acme-dns:ro
```

Правишь файл на хосте, делаешь `docker compose up -d` — команда отрабатывает без ошибок и рапортует
об успехе. **Контейнер при этом не пересоздан, и процесс внутри продолжает работать на конфиге,
прочитанном при старте.**

Причина: compose сравнивает **описание сервиса** в `docker-compose.yml` (образ, порты, переменные,
список volume'ов). Содержимое смонтированных файлов в это сравнение не входит вовсе — с точки
зрения compose ничего не изменилось, пересоздавать нечего.

### Чем опасно

Не тем, что правка не применилась, а тем, что **проверка результата может соврать в опасную
сторону**.

Прецедент: у `acme-dns` переключали `disable_registration = false → true`, чтобы закрыть публичную
регистрацию поддоменов. После `up -d` проверка «регистрация закрыта?» (`POST /register`) прошла бы
на **старом** конфиге и показала бы, что всё ещё открыта — или, при обратном порядке правок,
показала бы закрытую регистрацию там, где она открыта.

### Как правильно

```bash
docker restart <container>
docker logs <container> | grep -i 'config'   # сверить, что время строки свежее
```

**Любую правку смонтированного конфига заканчивать рестартом и сверкой по логу.** Не «перезапустить
на всякий случай», а именно убедиться, что в логе появилась новая строка о чтении конфига.

⚠️ Это касается и статической конфигурации Traefik (`traefik.yml`), и любого другого сервиса, чей
конфиг приезжает файлом. Динамическая конфигурация Traefik (`dynamic/`) — исключение: её провайдер
следит за файлами сам (`watch: true`) и рестарта не требует.

### ⛔ Зеркальная ловушка: `docker restart` не применяет правку самого `docker-compose.yml`

Правило выше легко запомнить как «всегда `restart`, никогда `up -d`» — и это **неверно ровно
наполовину**. Команды не взаимозаменяемы, у них разные предметы:

| Что изменил                                                             | Что применит                          | Что будет no-op'ом     |
| ----------------------------------------------------------------------- | ------------------------------------- | ---------------------- |
| **содержимое** смонтированного файла (`traefik.yml`, `config.cfg`)      | `docker restart`                      | `docker compose up -d` |
| **описание сервиса** (`extra_hosts`, `ports`, `volumes`, `environment`) | `docker compose up -d` (пересоздание) | `docker restart`       |

`extra_hosts` и прочее из описания фиксируются в момент **создания** контейнера. `restart`
перезапускает существующий контейнер с его старым `HostConfig` — compose-файл при этом не читается
вообще.

Обе команды при этом отрабатывают без ошибок и выглядят успешными — то есть ошибиться можно в
любую сторону, и обе ошибки молчаливые.

**Пойман вживую 2026-08-08 (BlackCove, s3):** я написала в задании «нужен `docker restart`, не
`up -d`» — по инерции от правила выше, хотя правка была именно в `docker-compose.yml`
(`extra_hosts` для Traefik). После `restart` проверка показала пустоту:

```bash
docker inspect traefik --format '{{json .HostConfig.ExtraHosts}}'   # []
```

Помог только `docker compose up -d`. Формулировка «не `up -d`» была скопирована из правила про
смонтированные файлы в ситуацию, где верно обратное.

**Проверять результат, а не команду.** У каждой правки есть свой способ убедиться: для
смонтированного конфига — свежая строка в логе, для описания сервиса — `docker inspect` по тому
самому полю, которое менял.

### ⛔ Третья грань: метка в git — не то же самое, что метка на запущенном контейнере

Обе ловушки выше — про расхождение файла на диске и того, что реально читает Docker. Эта — про
расхождение ещё на шаг раньше: **закоммиченный `docker-compose.yml` — не факт, что он вообще
доехал до `up -d` на сервере.** Найдено дважды за один день переезда s3 на Traefik (2026-08-08,
[PLAN-INFRA.md §48 M2](/PLAN-INFRA.md)), в двух разных приложениях, по двум разным причинам:

- **`aboi`** — деплой упал на шаге миграций **до** пересоздания контейнера с новыми
  Traefik-метками. Коммит с метками существовал, был запушен, даже отображался в `git log` на
  сервере — но `docker compose up -d`, который бы их применил, не дошёл до выполнения.
- **media-server** — стек ни разу не пересоздавали после того, как метки в
  `docker-compose.yml` добавили. Файл на диске сервера был свежим, git-история чистой — контейнер
  просто никогда не перезапускали этой командой.

В обоих случаях грепом по `docker-compose.yml` (или по git-истории) всё выглядело правильно —
метки на месте, коммит смёрджен. Ошибка была не в конфигурации, а в том, что между «метка в
файле» и «метка в живом контейнере» стоит операция (`up -d` с успешным пересозданием), и её
пропуск ничем не сигнализирует.

**Единственная надёжная проверка:**

```bash
docker inspect <container> --format '{{json .Config.Labels}}'
```

Не `cat docker-compose.yml`, не `git show HEAD:docker-compose.yml` — оба ответят на вопрос «что
должно быть», а не «что есть». Прямое следствие правила «проверяй тем же путём, которым ходит
настоящий потребитель» из
[verification-pitfalls.md](/.claude/docs/verification-pitfalls.md): настоящий потребитель меток
Traefik — не git и не файл, а сам запущенный контейнер, у которого Traefik читает `.Config.Labels`
через Docker API.

## 2. Точка монтирования может быть занята файлом внутри образа

```
docker: Error response from daemon: ... error mounting "/home/deploy/lego" to rootfs at "/lego":
not a directory
```

Каталог-источник существует, `stat` это подтверждает, права верные. Ошибка — про **назначение**:
`/lego` внутри образа `goacme/lego` это ELF-бинарь самого lego, его entrypoint. Монтирование
каталога поверх файла и даёт `not a directory`.

Коварство в формулировке: runc не говорит, про какую из двух сторон (`src` или `dst`) он жалуется,
и первый рефлекс — искать проблему в источнике.

### Как правильно

Перед выбором `dst` для любого нового `-v` посмотреть, что в образе по этому пути:

```bash
docker run --rm --entrypoint sh <image> -c 'ls -la /'
```

Выбирать заведомо свободное имя (`/acme-data`, `/app-config`), а не совпадающее с названием
инструмента — именно на совпадении «имя проекта = имя бинаря в корне» эта ловушка и срабатывает.

## Отдельный урок: как НЕ надо диагностировать

Первый диагноз по ловушке №2 был **неверным** — «docker-демон не видит `/root`, вероятно из-за
snap-конфайнмента». Он продержался несколько итераций и попал в коммит, потому что проверочный тест
менял **две переменные разом**:

```bash
# было (падало):      -v /root/lego:/lego
# тест (проходил):    -v /home/deploy/lego-test:/test
```

Поменялись и источник (`/root` → `/home/deploy`), и назначение (`/lego` → `/test`, свободный путь).
Тест «подтвердил» гипотезу про источник, хотя виновато было назначение.

Развалилось это ровно тогда, когда исполнитель воспроизвёл ошибку **из нового источника со старым
назначением** — и она повторилась один в один.

**Правило:** проверочный тест меняет ровно одну переменную. Если тест поменял две и «сработал» —
он не подтвердил гипотезу, а совпал с ней.
