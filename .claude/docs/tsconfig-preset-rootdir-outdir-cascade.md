# Удаление `references` на приложении с унаследованным `outDir`/`include` — три побочных эффекта

Продолжение [tsgo-tsc-stale-project-reference-redirect](/.claude/docs/tsgo-tsc-stale-project-reference-redirect.md)
(вариант B): фикс «убрать `references` + `rootDir`» там показан на `dashboard-agent`, где
`rootDir`/`outDir` были заданы прямо в `apps/<app>/tsconfig.json` и просто удалялись. Прогон
того же фикса на шести Next.js/Electron-приложениях (`aboi`, `aira-web`, `animatrona-landing`,
`animatrona-tracker`, `animatrona`, `aprel8008`, 2026-08-07) вскрыл три варианта, специфичных
для приложений на `../../tsconfig.next-app.json` — там `outDir` унаследован из пресета, и
убрать его без порчи остальных приложений на том же пресете нельзя. Нужен обходной путь на
уровне `apps/<app>/tsconfig.json` самого приложения.

## 1. `TS6059: not under rootDir` без собственного `rootDir` в файле

`outDir` из пресета всё равно форсирует строгую проверку `rootDir`, даже если приложение его не
переопределяло — TypeScript выводит `rootDir` из общего предка входных файлов программы.

~~Первый фикс — явный `"rootDir": "../.."` (корень репо) в `compilerOptions` приложения, не
трогая пресет.~~ **Устарело (2026-08-07):** правило «`rootDir` не выносится в пресет, ни на что
не влияет при `noEmit`» (см. [tsconfig-presets](/.claude/docs/tsconfig-presets.md)) оказалось
неверным именно для этого случая — `TS6059` работает и при `noEmit: true`. Точечный `rootDir`
был продублирован в 16 `apps/*/tsconfig.json`, все на одинаковой глубине
(`apps/<app>/tsconfig.json` → пресет в корне репо).

Консолидировано в сам пресет: `"rootDir": "${configDir}/../.."` в `tsconfig.next-app.json` —
`${configDir}` резолвится относительно наследующего конфига приложения, поэтому одна строка в
пресете эквивалентна `"../.."` в каждом из 19 приложений на пресете. Проверено `typecheck:tsgo`
на всех 19 (после `rm -rf libs/*/dist apps/*/dist` и `--skip-nx-cache`) + `build` на 3
репрезентативных (`aboi`, `driving-school`, `kami`) — падений от `rootDir` не найдено.
`declaration`/`outDir` из пресета не мешают: `noEmit: true` там уже стоит, реального вывода
файлов нет.

## 2. `TS6307: File is not listed within the file list`

Возникает, когда путь-алиас на библиотеку раньше резолвился только через снятый `references`, а
не через `include` — в отличие от остальных библиотек этого же приложения, уже включённых
«смешанной моделью» через `../../libs/X/src/**/*.ts`.

**Фикс:** добавить такой же glob для этой библиотеки в `include`, не полагаясь на то, что
`paths` в `compilerOptions` сама протащит файл в программу.

## 3. Взрыв на сотни посторонних ошибок компиляции `*.spec.ts(x)` библиотек

Проявляется, если приложение уже использовало «смешанную модель»
(`include: ["../../libs/X/src/**/*.ts"]`) до фикса. Раньше `*.spec.ts(x)`-файлы библиотек не
заходили в программу приложения — их отсекал сам механизм `references` (компилировался только
`tsconfig.lib.json`-таргет), а `include`-glob'ы приложения тем временем формально совпадали и с
тестовыми файлами. Без `references` эта защита исчезает, и `*.spec.tsx` библиотек компилируются
в контексте приложения — там нет тестового `tsconfig.spec.json` со своими типами
(`@testing-library/jest-dom` и т.п.), отсюда `TS2339`/`TS2593`/`TS2304` пачками.

**Фикс:** добавить `../../libs/**/*.spec.ts(x)` и `*.test.ts(x)` в `exclude` приложения, тем же
паттерном, что уже обычно стоит для `src/**/*.spec.ts(x)` самого приложения.

## Вывод

Ни один из трёх пунктов не специфичен библиотеке — это общие следствия перехода с
project-references-модели на путь-алиасы, применимые к любому приложению со схожим пресетом.
