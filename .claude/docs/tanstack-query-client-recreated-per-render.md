# ⚠️ QueryClient, созданный в теле провайдера, обнуляет кеш на каждом ре-рендере

**Симптом со стороны пользователя:** первое действие в списке применяется и видно на экране,
все последующие «не срабатывают» — хотя сервер отрабатывает каждое, и после перезагрузки
страницы все изменения на месте.

**Где найдено:** `studio`, `/owner/time`, кнопка «Утвердить» в журнале записей времени
(2026-09-03). Причина оказалась не в списке и не в мутации, а в общей библиотеке
`@letar/query-provider` — то есть потенциально во всех её потребителях.

## Механизм

```tsx
// ❌ было — libs/query-provider/src/lib/query-provider.tsx
export function QueryProvider({ children, showDevtools, ...config }: QueryProviderProps) {
  const queryClient = createQueryClient(config) // новый клиент на КАЖДЫЙ ре-рендер
  return <QueryClientProvider client={queryClient}>{children}</QueryClientProvider>
}
```

`createQueryClient()` в теле компонента выглядит как обычное вычисление, но `QueryClient` —
это хранилище состояния. Каждый ре-рендер провайдера выдаёт **новый пустой** клиент:

- весь кеш запросов выбрасывается;
- уже запущенная мутация продолжает держать ссылку на **старый** клиент, который получила
  через `useQueryClient()` в момент своего создания. Её `onMutate`/`onSettled` пишут
  `setQueryData` и `invalidateQueries` в выброшенный объект — они физически применяются, но
  их никто не читает;
- смонтированные `useQuery`/`useInfiniteQuery` в этот момент наблюдают уже другой клиент.

Отсюда и внешний вид бага: оптимистичная правка первого клика успевает лечь в тот же клиент,
который сейчас на экране, — она видна. Дальше провайдер перерисовывается, клиент подменяется, и
следующие правки уходят «в никуда».

## Почему ре-рендер провайдера — не редкость

Провайдер стоит в `layout.tsx`, то есть в дереве над всеми страницами раздела. Его
перерисовывает:

- любая мягкая навигация (`router.replace` при синхронизации фильтров с URL — то есть **каждое
  нажатие клавиши** в поле поиска);
- любой `revalidatePath()` из server action — Next отдаёт новый RSC-payload, и клиентские
  компоненты layout получают новые `children`.

То есть в приложении с server actions подмена клиента происходит после **каждого** действия
пользователя, а не в экзотическом углу.

## Почему это не ловится обычными проверками

- `typecheck`, `lint`, `oxlint` — код полностью валиден, это вопрос семантики, а не типов.
- Тесты компонента — проходят: внутри одного рендера всё согласовано.
- Глаз на скриншоте — первое действие работает, а именно его обычно и проверяют.
- Ручная проверка «нажал, обновил страницу — всё на месте» — тоже зелёная: сервер-то
  отработал.
- Ложный след: `@tanstack/react-virtual` с его кешем измерений строк. В `studio` до этого уже
  чинили похожий на вид симптом через `getItemKey` — и это была настоящая, но **другая**
  проблема, из-за чего второй раз искали снова в виртуализаторе.

## Фикс

```tsx
// ✅ стало
const [queryClient] = useState(() => createQueryClient(config))
```

Ленивый инициализатор `useState` — штатный способ из документации TanStack Query для React;
`useMemo` для этого не годится, React вправе сбросить его кеш.

То же касается любого другого объекта с состоянием, создаваемого рядом, — в
`PersistQueryProvider` так же чинится `createIDBPersister()` (персистер держит соединение с
IndexedDB).

Исправлены все три провайдера библиотеки: `QueryProvider`, `PersistQueryProvider`,
`ZenStackQueryProvider`.

## Сторож на рецидив

`libs/query-provider/src/lib/stable-query-client.spec.ts` читает исходники всех
`*-provider.tsx` библиотеки и требует, чтобы `createQueryClient(` / `createIDBPersister(`
встречались только внутри `useState(() => …)`. Тест намеренно проверяет форму кода, а не
поведение: у библиотеки окружение `node` без jsdom, а регрессией является именно голый вызов в
теле компонента. Позитивный контроль прогнан — при возврате старой формы тест краснеет и
называет файл со строкой.

## Смежное: server action возвращает отказ значением, а не исключением

Тот же экран вскрыл вторую ловушку рядом. Server action вида `deleteEntryAction` сообщает об
отказе **значением** (`{ error: 'Запись уже выставлена в счёт' }`), а не `throw`. Если
`mutationFn` просто вернёт этот объект, TanStack сочтёт мутацию успешной: `onError` не
вызовется, откат оптимистичной правки не сработает — строка останется стёртой с экрана, хотя
на сервере она жива, и «воскреснет» только при следующей загрузке списка.

```tsx
mutationFn: async (id: string) => {
  const result = await deleteEntryAction(id)
  if ('error' in result) {
    throw new Error(result.error)
  }
  return result
},
```

Проверять это нужно в каждом `mutationFn` поверх server action, который умеет отвечать
`{ error }` — сигнатура таких экшенов в монорепо стандартная (`{ data } | { error }`), и
именно поэтому промах легко не заметить.
