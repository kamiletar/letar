# CI: изоляция unit-теста, бьющего в настоящий Postgres

**Проблема.** `.github/workflows/ci.yml` держит job-level `DATABASE_URL` только ради
`prisma generate` (нужна синтаксически валидная строка, реальный коннект не делается) — в CI нет
настоящего Postgres вообще. Большинство unit-тестов мокают `@/lib/db` и это не задевает, но
первый тест, который делает настоящие запросы (`animatrona-tracker/route.spec.ts` — дедуп гонки
по уникальному полю через реальный `23505` от Postgres, замокать без потери смысла теста нельзя),
падает `ECONNREFUSED :5432` на каждом прогоне, где приложение affected.

**Почему нельзя просто одну общую БД на всех.** Несколько публичных приложений используют
одинаковые имена моделей (`animatrona-tracker` и `svoichuzhie` оба тащат Better Auth
`User`/`Account`/`Session`/`Verification` + свой `ConsentLog`) — общая плоская БД в CI рискует
коллизией схем между параллельно проверяемыми приложениями.

## Решение: именованная БД на приложение + `test.env` в `vitest.config.mts`

1. **`services.postgres`** в job — один сервер на весь `quality` job (образ `postgres:16-alpine`,
   healthcheck `pg_isready`).
2. **Отдельный шаг** перед `Unit tests` создаёт именованную БД (`<app>_ci`) через `psql` и
   накатывает схему через `nx run <app>:db:push` (после явного `zenstack:generate`, если у
   приложения ZenStack — `db:generate`/`db:push` не тянут его сами через `dependsOn`, а без него
   `prisma generate` падает на отсутствующем `src/generated/schema.prisma`). DATABASE_URL для
   этой команды передаётся на сам шаг, не в job-level env — не задевает остальные проекты.
3. **`vitest.config.mts` этого приложения** переопределяет `DATABASE_URL` через `test.env`,
   включается только при `CI=true`:

   ```ts
   test: {
     env: process.env.CI ? { DATABASE_URL: 'postgresql://ci:ci@localhost:5432/<app>_ci' } : {},
   }
   ```

## Почему именно `test.env`, а не что-то ещё

`process.env.DATABASE_URL` в `ci.yml` **уже установлена** до того, как Vitest успевает что-либо
загрузить — это ключевое отличие от обычного Nx per-project `.env`-каскада
([nx_docs](https://nx.dev), поведение задокументировано так: «если переменная уже загружена в
процесс — Nx её игнорирует», первый загруженный побеждает). Если бы изоляция строилась на
project-level `.env.test`/`.env.local`, шаг `ci.yml`'а всё равно победил бы — Nx его не тронет.

Vitest устроен иначе: `test.env` (он же `project.config.env`) спредится **последним** поверх
`process.env` в момент, когда Vitest формирует env для воркер-пула — проверено чтением исходника
(`node_modules/vitest/dist/chunks/cli-api.*.js`):

```js
env = { ...process.env, ...options.env, ...ctx.config.env, ...project.config.env }
```

То есть `project.config.env` (наш `test.env`) реально перебивает уже установленную переменную —
никакого «первый побеждает» тут нет. Это специфика самого Vitest, не Nx, и не документировано
явно в его доках так подробно — проверять по исходнику, если версия Vitest в репо когда-нибудь
сильно изменится.

**Guard на `process.env.CI`** — GitHub Actions сам выставляет `CI=true` каждому job, отдельную
переменную заводить не пришлось. Без guard'а локальный `nx test` тоже переключился бы на
несуществующую CI-БД и сломал бы обычную локальную разработку (у разработчика своя БД в
`.env.local`, на другом порту/имени).

## Чек-лист для нового приложения с этим же паттерном

Новому приложению-кандидату нужны те же три шага: `CREATE DATABASE <app>_ci` в шаге `Prepare
test databases`, `nx run <app>:db:push` там же, `test.env` в его `vitest.config.mts`. Один шаг
`ci.yml` расширяется построчно на каждое новое такое приложение — не заводить отдельный сервис
Postgres на приложение, один сервер вполне держит несколько баз.

Тиражировано на `svoichuzhie` (`admin-product.action.spec.ts`) 2026-09-03 — второе приложение
после `animatrona-tracker`, отдельная БД (не общая) из-за одноимённых Better Auth моделей
(`User`/`Account`/`Session`/`Verification`) у обоих.

## Проверка перед тем, как считать фикс рабочим

Локальный прогон **не может** дословно воспроизвести `services:` GitHub Actions (это не
docker-compose, а отдельный механизм раннера) — но саму логику override можно проверить и без
него: временно подставить в `test.env` реальный локальный Postgres (например уже поднятый
dev-контейнер приложения на другом порту/БД) и прогнать `nx test` с `CI=1` и намеренно **неверным**
shell-уровневым `DATABASE_URL` (имитация job-level плейсхолдера) — если тест зелёный, override
реально работает, а не совпал по счастливой случайности с уже правильным значением в окружении.
