# Pessimistic row lock против оверселла capacity-ресурса

Первый прецедент `SELECT ... FOR UPDATE` в монорепо (svoichuzhie, `buyTicket`, 2026-08-26;
на момент внедрения — грепом по всему репо совпадений не было).

## Когда применять

Ограниченный ресурс (`capacity`/quota/остаток мест) и **несколько разных акторов**
конкурируют за последние единицы — двое покупателей одновременно берут последний билет, два
клиента одновременно резервируют последний слот и т.п.

Идемпотентного ключа одного актора здесь **недостаточно**: `idempotencyKey` защищает от дубля
запроса того же самого покупателя (двойной клик, повтор после разрыва соединения) — у него один
и тот же ключ на все свои попытки. Два _разных_ покупателя приходят с двумя _разными_ ключами —
`@unique` на `idempotencyKey` их конфликт не видит вообще. Без блокировки строки ресурса обе
транзакции читают `count()` занятых мест независимо, обе видят место свободным и обе проходят
проверку вместимости — оверселл.

## Как реализовано

```typescript
const order = await prisma.$transaction(async (tx) => {
  // Блокируем строку ресурса — сериализует конкурентные транзакции РАЗНЫХ акторов на уровне БД.
  // Без этого две транзакции могут независимо прочитать count() ДО того, как любая из них
  // закоммитит свои строки, и обе пройти проверку вместимости.
  await tx.$queryRaw`SELECT id FROM "Event" WHERE id = ${event.id} FOR UPDATE`

  const soldCount = await tx.ticket.count({
    where: { eventId: event.id /* ...живые билеты... */ },
  })
  const available = event.capacity - soldCount
  if (available < quantity) {
    throw new Error() /* ... */
  }

  const newOrder = await tx.ticketOrder.create({/* ... */})
  // ...создание дочерних строк (билетов) в том же tx...
  return newOrder
})
```

Механизм: первая транзакция берёт `FOR UPDATE` на строку `Event` и держит её до конца транзакции.
Вторая, пришедшая параллельно, блокируется на том же `SELECT ... FOR UPDATE` и ждёт — её
`count()` выполнится только после коммита/отката первой, увидит уже актуальные занятые места и
корректно откажет, если мест не осталось.

## Отличие от соседних паттернов — не путать назначение

- [client-idempotency-key-order-creation.md](/.claude/docs/client-idempotency-key-order-creation.md) —
  решает повтор **одного и того же** запроса одного актора (двойной клик, back/reload, retry сети).
  Ключ детерминирован на стороне клиента для одной попытки покупки. Не защищает от гонки между
  разными покупателями за общий ресурс — у них разные ключи, конфликта на `@unique` не возникает.
- [zenstack-append-only-terminal-event-pattern.md](/.claude/docs/zenstack-append-only-terminal-event-pattern.md) и
  [idempotency-key-terminal-transition-pattern.md](/.claude/docs/idempotency-key-terminal-transition-pattern.md) —
  про терминальные переходы статуса одной сущности (не более одного раза перевести конкретную
  запись в конечное состояние), не про то, что несколько разных сущностей конкурируют за общий
  ограниченный пул.

Три паттерна закрывают три разных гонки; в одном и том же action может понадобиться сразу два
(как в svoichuzhie: `idempotencyKey` — против дубля своего запроса, `FOR UPDATE` — против
оверселла между чужими).

## Предостережение

`SELECT ... FOR UPDATE` бессмысленен, если нарушено любое из двух условий:

- **Блокируемая строка обязана существовать до блокировки.** Если ресурс ещё не создан (или
  запрос идёт по несуществующему `id`), `FOR UPDATE` ничего не блокирует — блокировать нечего.
  В svoichuzhie строка `Event` уже гарантированно существует (загружена чуть выше по `findFirst`)
  до входа в транзакцию.
- **Блокировка и последующий `count()`/`create()` обязаны идти строго в одной транзакции.**
  `tx.$queryRaw` с `FOR UPDATE` вне транзакции — это блокировка на время одного `SELECT`, которая
  снимается сразу после его выполнения и ничего не сериализует. Блокировка держится ровно до
  конца транзакции (`COMMIT`/`ROLLBACK`), в которой была взята — вынести проверку вместимости или
  создание в отдельный вызов `prisma.$transaction` уже ломает гарантию.
