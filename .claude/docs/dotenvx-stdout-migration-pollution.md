# dotenvx: маркетинговые "tip"-строки в stdout ломают сгенерированные SQL-миграции

## Симптом

Команда вида

```bash
bun x prisma migrate diff --from-empty --to-config-datasource --script > migration.sql
```

генерирует файл, который `prisma migrate deploy` отказывается применять:

```
Error: P3018

A migration failed to apply.
...
syntax error at or near "◇"
```

Открыв `migration.sql`, в первых строках находишь не SQL, а что-то вроде:

```
◇ injected env (3) from .env.local // tip: encrypt with dotenvx: https://dotenvx.com
```

## Причина

Если `bun x`/`npx` в этом окружении резолвит Prisma CLI через обёртку `dotenvx` (подключена
глобально или через `package.json`/`bunfig`), `dotenvx` при загрузке env-переменных печатает свою
рекламную "tip"-строку. Инструмент пишет её **в stdout, а не stderr** — поэтому она проходит
редирект `> file.sql` наравне с настоящим выводом `prisma migrate diff` и оказывается первой
строкой сгенерированного файла. Валидного SQL-парсера, который проглотил бы произвольный текст
перед первым `CREATE`/`ALTER`, не существует — отсюда P3018.

Уже дважды воспроизведено в сессии `domwellbes` (agent-mail тред `domwellbes-m1-infra`, сообщения
BlackCove/OliveWaterfall от 2026-07-30 ~23:00–23:04 UTC) — оба раза при первой генерации
`prisma/migrations/` для приложения, у которого раньше была только `db:push`-схема без истории
миграций.

## Как обнаружить

После любой генерации миграции через `> file.sql`-редирект — прежде чем коммитить файл:

```bash
head -5 migration.sql
```

Если видно `injected env` / `tip:` — файл загрязнён, нужна чистка перед коммитом и применением.

## Решение

Надёжного флага, гарантированно подавляющего именно эту tip-строку у `dotenvx`, на момент
написания не найдено. Рабочий обходной путь — вручную вырезать загрязнённые строки в начале файла
перед коммитом (обычно 1 строка, но проверяй `head`, а не полагайся на фиксированное число).

Более надёжный вариант, если он доступен в среде — не давать `dotenvx` попадать в stdout вообще:
запускать генерацию без `dotenvx`-обёртки (например, `DATABASE_URL` уже проставлен явно в
окружении шага, а не подтягивается через `dotenvx run --`), либо перенаправить его собственный
вывод (`2>&1` не поможет, раз это уже stdout — нужен именно флаг тишины у `dotenvx`, если такой
появится в будущей версии).

## ⚠️ Последствие починки: checksum миграции перестаёт сходиться

Всё вышеописанное про чистку файла верно **до** применения миграции. Если файл почистили уже
**после** того, как миграция была применена к базе, Prisma при следующем `migrate dev` падает:

```
The migration `20260730223355_init` was modified after it was applied.
```

Prisma хранит в таблице `_prisma_migrations` sha256 применённого файла и сверяет его при каждом
запуске. Убранная из файла строка `injected env` меняет байты — хеш перестаёт совпадать.

⛔ **Рука тянется к `prisma migrate reset` — это снос базы.** Здесь он не нужен: схема БД
правильная, разошлась только контрольная сумма. Данные при правильной починке целы.

### Перед починкой: убедиться, что расхождение косметическое

Обновлять checksum можно, только если БД действительно соответствует миграции. Проверь два факта:

```sql
SELECT migration_name, finished_at, rolled_back_at
FROM _prisma_migrations
WHERE migration_name = '<имя>';
```

- `finished_at` не `null` и `rolled_back_at` — `null` (миграция доехала до конца);
- таблицы из миграции физически на месте.

Если хоть одно не так — расхождение не косметическое, и чинить надо не хеш, а состояние схемы.

### Починка: обновить checksum записи

sha256 считается от **байтов файла** `migration.sql`:

```bash
sha256sum prisma/migrations/<имя>/migration.sql
```

На Windows без coreutils — через PowerShell (Prisma хранит хеш в нижнем регистре, `Get-FileHash`
возвращает верхний):

```powershell
(Get-FileHash prisma/migrations/<имя>/migration.sql -Algorithm SHA256).Hash.ToLower()
```

Полученное значение вписать в запись:

```sql
UPDATE _prisma_migrations
SET checksum = '<sha256 файла>'
WHERE migration_name = '<имя>';
```

После этого `prisma migrate dev` снова видит согласованное состояние и спокойно добавляет
следующую миграцию.

### Как не нарваться

Чистить сгенерированный файл **до** первого применения — тогда этой развилки не возникает вовсе.
Проверка `head -5 migration.sql` из раздела выше должна стоять между генерацией и `migrate deploy`,
а не «когда-нибудь потом при код-ревью».

## Известные случаи в монорепо

- **`domwellbes`** — первая генерация `prisma/migrations/` через
  `prisma migrate diff --from-empty --to-config-datasource --script` (970 строк), первая строка
  файла — `injected env`. Вычищено вручную перед коммитом (2026-07-30).
- **`domwellbes`**, продолжение той же истории — миграция `20260730223355_init` была почищена
  коммитом `adc300c` уже после применения. Расхождение checksum всплыло 2026-08-04, при попытке
  добавить следующую миграцию. Починено `UPDATE _prisma_migrations`, база не сбрасывалась.
