# dprint без явного скоупа не различает границы git worktree/submodule

## Симптом

Запуск `dprint fmt`/`dprint check` без ограничения по путям (`bunx dprint fmt` из корня, или
косвенно через `nx run-many -t format --dry-run` — см. ниже) переформатирует не только публичный
`letar`, но и всё, что физически лежит в дереве: приватные submodule-приложения, чужие
`.claude/worktrees/*`, orphaned worktree других сессий. dprint обходит файловую систему
рекурсивно и понятия не имеет о `.git`/gitlink-границах — для него это просто директория с
файлами.

Симптомы конкретно этого класса инцидента:

- `git status` внезапно показывает сотни изменённых файлов в submodule-приложении, которое
  сессия не открывала.
- Диффы в затронутых файлах — чисто стилевые (висячие запятые, кавычки, реиндентация), без
  содержательных изменений, вперемешку по всему дереву.
- Если в затронутом submodule/worktree в этот момент есть **чужая незакоммиченная работа**,
  слепой `git checkout -- <файлы>` для отката форматирования рискует унести её вместе с
  косметикой — увидеть разницу между «только dprint» и «dprint + реальный код» на глаз можно
  только построчным `git diff`.

## Причина

`includes`/`excludes` в `dprint.json` — единственный механизм, которым dprint ограничивает себя.
Без явных `excludes` он честно обходит всё дерево от текущей рабочей директории вниз, включая
директории, которые физически являются отдельными git-репозиториями (submodule, worktree).
Никакой встроенной эвристики «здесь начинается чужой репозиторий, дальше не ходить» у dprint нет.

## Постоянный фикс, уже применённый

`dprint.json` в корне `letar` содержит явные `excludes` на каждый submodule-путь и на
`.claude/worktrees`:

```json
"excludes": [
  "...",
  ".claude/worktrees",
  ".claude/private",
  "apps/aboi",
  "apps/aboi-e2e",
  "apps/aprel8008",
  "apps/domwellbes",
  "apps/domwellbes-e2e",
  "apps/driving-school",
  "apps/driving-school-e2e",
  "apps/dsperevod",
  "apps/poster-microtext-desktop",
  "apps/studio",
  "apps/studio-e2e",
  "apps/svoichuzhie",
  "libs/driving-school-db"
]
```

Это закрывает прогон **из корня `letar`** для перечисленных путей. Он не защищает: (1) прогон из
корня после того, как заведён новый submodule, ещё не попавший в этот список; (2) прогон внутри
самого submodule, если у него появится собственный вложенный worktree (см. ниже); (3) **прогон,
чей `cwd` находится внутри исключённого пути** — а это ровно то, что делает `nx run-many -t
format` (см. следующий раздел).

## ⛔ `excludes` не действуют, если `cwd` внутри исключённого пути — а `nx run-many -t format` туда заходит

Замерено 2026-08-06. `excludes` в `dprint.json` сопоставляются с путями относительно каталога
конфига (корень `letar`). Когда dprint запускают **из подкаталога**, он поднимается вверх и
находит тот же корневой `dprint.json`, но обходить начинает от своего `cwd` — и запись
`"apps/driving-school"` в `excludes` на этот обход уже не влияет:

```bash
cd apps/driving-school && dprint output-file-paths | wc -l   # 1100, а не 0
```

Это не теория: **семь submodule-приложений объявляют таргет `format` с `cwd` внутри себя** —
`aboi`, `aprel8008`, `domwellbes`, `driving-school`, `dsperevod`, `studio`, `svoichuzhie`. Команда
у всех одна и та же:

```json
{ "command": "bunx dprint fmt \"**/*.{ts,tsx,js,jsx,json,md}\"", "cwd": "apps/<app>" }
```

Значит **`nx run-many -t format` без `--projects` форматирует внутри этих семи submodule** —
2089 файлов суммарно (aboi 182, aprel8008 58, domwellbes 132, driving-school 1100, dsperevod 160,
studio 222, svoichuzhie 235). А именно эту команду `CLAUDE.md` предписывает выполнять **перед
каждым коммитом**.

⚠️ **Обратная сторона той же медали — мёртвый таргет.** `apps/poster-microtext-desktop` был
объявлен наоборот: запуск из корня воркспейса с явным путём в аргументе, без `cwd`.

```json
{ "command": "dprint fmt apps/poster-microtext-desktop/**/*.{ts,tsx,json}" }
```

Здесь корневые `excludes` сработали штатно — и вырезали ровно те файлы, которые таргет должен был
обрабатывать: `dprint output-file-paths` по этому шаблону возвращал **0 файлов из 62**. Таргет
существовал, отчитывался успехом и не делал ничего. Починен 2026-08-06 приведением к форме с
`cwd` (коммит `4dc69b3` в его репозитории).

**Мораль:** для submodule-пути, перечисленного в корневых `excludes`, у таргета `format` ровно два
исхода — либо запуск с `cwd` внутри (excludes не применяются, форматирует по-настоящему, но
достижим из родительского прогона), либо запуск из корня (excludes применяются, таргет мёртв).
Третьего нет, пока путь остаётся в `excludes`. Выбран первый вариант — форматирование должно
работать; достижимость из родителя закрывается хуком, см. ниже.

**Практический вывод:** `cwd` внутри проекта — удобная и почти повсеместная форма таргета
`format` (так объявлены все 44 библиотеки и 44 приложения), и для обычных проектов публичного
репо она безопасна. Опасна она ровно там, где путь одновременно перечислен в `excludes`, то есть
у submodule.

### Что с этим сделано (2026-08-06, решение владельца)

Выбран вариант «каждому submodule — собственный `dprint.json`». Все 14 submodule (13 кодовых +
`.claude/private`) получили свой конфиг: те же три плагина тех же версий, те же правила
`typescript`/`json`/`markdown`, минус `excludes`, специфичные для монорепо. В `excludes` каждого
оставлен `.claude/worktrees` — превентивно, под сценарий из следующего раздела.

Что это дало:

- **Submodule стал самодостаточным.** Раньше `dprint fmt` внутри него поднимался по дереву и
  находил конфиг `letar` — форматирование работало только при работе внутри монорепо и молча
  меняло поведение, если репозиторий склонировали отдельно.
- **Прогон из родителя стал гарантированно нулевым.** `nx run-many -t format` по семи
  submodule-приложениям после этого — ноль изменённых файлов (проверено). Конфиги совпадают,
  поэтому переформатировать нечего.
- **У каждого submodule появилось место для своих `excludes`** — раньше их некуда было писать.

⛔ **Чего это НЕ дало:** сама запись в чужое рабочее дерево осталась. `nx run-many -t format` без
`--projects` по-прежнему запускает dprint с `cwd` внутри семи submodule и трогает их файлы —
просто теперь без изменений.

### Остаток закрыт хуком, а не конфигом (2026-08-06)

Переписать семь таргетов на запуск из корня было нельзя — это превратило бы их в мёртвые (см.
разбор `poster-microtext-desktop` выше). Поэтому остаток закрыт на уровне команды: правило в
`.claude/hooks/validate-bash.js` (уже висел на `PreToolUse: Bash`) блокирует

- `nx run-many -t format` **без** `--projects`/`--exclude` — единственную форму, которая
  дотягивается до submodule;
- встроенную команду Nx для форматирования (ту, что без `run-many`) — она запускает Prettier
  мимо dprint, второй вектор из §32.

Форма `:check` и одиночный `nx run <проект>:format` не блокируются. Законный путь для прогона по
всему публичному репо — `dprint fmt` из корня: у него `cwd` в корне, поэтому `excludes` работают.

⚠️ **Правила привязаны к позиции команды** (начало строки, после `&&`/`||`/`;`/`|`), а не ищутся
по всей строке. Без этого хук блокирует сам себя: обе команды постоянно встречаются в тексте —
в сообщениях коммитов через heredoc, в документации, в `echo`. На это наступили дважды за одну
сессию, пока писали само правило. У старых правил хука (разрушительные git-операции) якоря нет —
там ложная блокировка сочтена меньшим злом, чем пропуск.

## ⚠️ Ловушка не привязана к `letar` — она воспроизводится в любом репозитории с dprint.json

Если у любого приватного submodule-приложения (aboi, driving-school, studio и т.д.) когда-нибудь
появится собственный `git worktree` — например, чтобы параллельный агент работал над веткой этого
приложения в отдельной директории — тот же класс бага повторится уже внутри submodule, потому что
`dprint.json` внутри submodule ничего не знает про свой worktree, если для него не добавлен
`excludes` симметрично корневому.

**Если заводишь worktree внутри submodule-приложения:** открой его `dprint.json` (с 2026-08-06 он
есть у всех 14 — см. раздел выше) и добавь путь worktree в `excludes` — **до** первого прогона
`dprint fmt` в этом submodule, а не после инцидента. Стандартный `.claude/worktrees` там уже
прописан, так что достаточно класть worktree именно туда; отдельная запись нужна только под
нестандартное расположение.

## Как не нарваться

- **Никогда не запускать `dprint fmt`/`dprint check` без scope из корня монорепо** — либо
  `--config` + явный список путей, ограниченный публичным репо, либо `nx run-many -t format
  --projects=...` с явным перечислением своих проектов.
- ⛔ **`nx run-many -t format` без `--projects` — заходит в семь submodule-приложений**
  (проверено замером, см. раздел выше). Всегда ограничивай прогон теми проектами, которые
  действительно трогал. Список проектов с таргетом — `nx show projects --with-target format`.
- **`nx run-many -t format --dry-run` — не настоящий dry-run.** Executor `nx:run-commands` не
  умеет имитировать выполнение произвольной shell-команды — флаг `--dry-run` не подавляет реальный
  запуск dprint/prettier. Если нужно только узнать, какие проекты имеют таргет `format`, — используй
  `nx show projects --with-target format:check` (безопасный, ничего не выполняет).
- **Перед массовым прогоном** — убедиться, что в затронутых путях нет незакоммиченной работы
  других агентов (`git status` по каждому submodule), и делать прогон отдельным коммитом
  `style: dprint fmt`, не смешанным с содержательными изменениями.

## Известные случаи

- **2026-08-06** (агент TealHill) — `bunx dprint fmt` без ограничения по пути из корня `letar`
  задел два `.claude/worktrees/*` (473 и 92 файла) и все 10 приватных submodule-приложений.
  Основной репозиторий и один orphaned worktree откачены; риск потери чужого незакоммиченного
  WIP в другом worktree (`jovial-bhabha-baae8b`) — впоследствии признан владельцем неважным, но
  сам факт риска подтверждён. `apps/domwellbes` содержал смешение стилевых правок с реальным
  незакоммиченным кодом (`COMPANY_ADMIN_ROLES`) — разбирался построчным `git diff`, слепой
  checkout не применялся. Постоянный фикс — `excludes` в `dprint.json` (коммит `76ad89b3`), после
  которого повторный прогон (1736 файлов, `c7a2924b`) submodule/worktree не задел. Подробности —
  `PLAN-INFRA.md` §32.
- **2026-08-06** (эта сессия) — при проверке гипотезы «nx.json уже даёт формат через
  targetDefaults» команда `nx run-many -t format --dry-run` оказалась не настоящим dry-run:
  реально прогнала dprint/prettier по `libs/forms`, `libs/ui`, `libs/zenstack-form-plugin` и
  submodule `apps/studio`, изменив десятки файлов. Откачено полностью через `git checkout --` в
  каждом месте, включая submodule; проверено `git submodule foreach --recursive` — чисто. Урок
  добавлен в раздел «Как не нарваться» выше.
