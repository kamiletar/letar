# bun изолированный линкер — алиас в devDependencies не защищает от общего bucket

**Короткий вывод:** npm-alias-схема для сосуществования двух версий одного пакета
(`"typescript": "npm:@typescript/typescript6@^6.0.2"` + `"@typescript/native": "npm:typescript@^7.0.2"`)
рассчитана на классический (плоский/npm) `node_modules`, где ключ в `devDependencies` реально
управляет тем, что резолвит `require(<пакет>)`. Под bun с изолированным линкером это не так —
схема с двумя алиасами одного пакета в общий isolated bucket не работает вообще, а не работает
частично или в редких случаях.

## Симптом

При попытке применить официальную схему совместимости TypeScript 6/7
(https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/) через алиасы в корневом
`package.json`:

```json
{
  "devDependencies": {
    "typescript": "npm:@typescript/typescript6@^6.0.2",
    "@typescript/native": "npm:typescript@^7.0.2"
  }
}
```

`nx lint` начинает падать **на всём монорепо разом** — ошибки вида
`tsModule.readConfigFile is not a function`, `Cannot read properties of undefined (reading
'CommonJS')` в десятках `apps/*-e2e/playwright.config.ts`, затем падение самого плагина Nx
project-graph. Не единичный проект — все, у кого в графе есть хоть один прогон `@nx/js`.

## Причина

Изолированный линкер bun (`node_modules/.bun/node_modules/<name>`) резолвит **общий** bucket по
имени пакета **внутри самого тарболла** (полю `package.json.name` реально скачанного пакета), а
не по ключу-алиасу из корневого `devDependencies`.

Реальный пакет `typescript@7.0.2` (установленный под алиасом `@typescript/native`) внутри себя
имеет `"name": "typescript"` — так его назвал сам издатель на npm, это неотделимо от содержимого
тарболла. Поэтому под изолированным линкером он забирает общий слот резолва `"typescript"` в
`node_modules/.bun/node_modules/typescript` — тот же самый слот, который должен был достаться
алиасу `@typescript/typescript6@6.0.2` (API-совместимой версии 6.0, реэкспортированной под другим
именем специально ради этой схемы).

Итог: любая транзитивная зависимость, резолвящая `require('typescript')` через этот общий bucket
(а не через специфичный для конкретного package.json symlink) — получает `typescript@7.0.2`
(compiler-only, без программного API до TS7.1) вместо ожидаемого API-совместимого `6.0.2`.
Пострадавшая зависимость в этом случае — не только предполагаемый `typescript-eslint`
(единственный кандидат, который рассматривался заранее), но и **сам Nx**: плагин `@nx/js`
(`dependencies-and-lockfile`, используется для построения графа проектов, вызывается на каждый
`nx lint`) сам дёргает `require('typescript')` программно (`readConfigFile`, `ModuleKind` и
т.п.).

## Почему это не то же самое, что классический npm/yarn

В плоском (не изолированном) `node_modules` каждый `package.json` в дереве получает **свой**
резолв через `require.resolve` с учётом собственных `dependencies`/алиасов — Node module
resolution поднимается по дереву `node_modules` от файла, который делает `require`, и находит
ближайший подходящий каталог, который может быть индивидуально симлинкнут на алиас. В bun
isolated-режиме сам смысл в том, что физические копии пакета лежат в одном общем сжатом
хранилище (`node_modules/.bun`), а top-level `node_modules/<name>` — просто symlink на слот в нём
по имени пакета. Официальная схема алиасов Microsoft этого не учитывает — она документирована
универсально для npm/pnpm/yarn/bun одинаково, но реально проверена (судя по формулировке в
анонсе) только на классическом резолве.

## Диагностика

Если после применения alias-схемы что-то в монорепо резолвит не ту версию пакета — проверять не
`bun.lock` (он корректно резолвит алиас на нужную версию), а физический top-level путь:

```bash
ls -la node_modules/.bun/node_modules/typescript
# или на Windows:
readlink node_modules/.bun/node_modules/typescript
```

Если это ведёт к каталогу версии, ожидаемой под **другим** алиасом — коллизия подтверждена.

## Фикс / вывод

Рабочего обхода под bun isolated linker не найдено — эту конкретную схему (два алиаса одного и
того же реального npm-имени пакета, один из них — «настоящий» пакет под чужим ключом) применять
на bun-изолированной установке нельзя, пока в bun не появится алиас-aware резолв bucket'а
(резолв по ключу `devDependencies`, а не по `package.json.name` тарболла).

Практический вывод для похожих задач: если два пакета из `devDependencies`/`dependencies`
физически являются **одним и тем же** npm-именем внутри тарболла (алиас "переупаковывает" готовый
пакет под новым ключом, не публикуя отдельный пакет с собственным именем) — под bun они всегда
попадут в один и тот же isolated bucket и один перезапишет резолв другого. Безопасно алиасить
можно только пакеты, которые физически различны (разные `package.json.name` внутри тарболла) —
тогда у каждого свой слот bucket'а независимо от ключа в `devDependencies`.

В летар это привело к решению **не тиражировать** схему совместимости TS 6/7 до выхода
TypeScript 7.1 GA (обещан с полноценным программным API — тогда `typescript-eslint` и `@nx/js`
смогут работать напрямую на 7.x, вся схема с двумя алиасами станет не нужна). Подробности решения
и контекст пилота — [PLAN-INFRA-1.md §19](/PLAN-INFRA-1.md), коммит `f4ffc9a3`.

Эксперимент был полностью и немедленно откачен (`git checkout -- package.json bun.lock` +
`bun install --force`), `nx lint` подтверждён зелёным после отката — блокировка длилась только во
время локальной проверки, в общий `main` ничего не попало.
