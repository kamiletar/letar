# Несовместимость версии bun на сервере с форматом `bun.lock`

**Короткий вывод:** старый bun на сервере не просто «дрейфует» относительно закоммиченного
`bun.lock` — он физически не умеет прочитать lockfile новой версии. Это блокирует **все**
деплои на сервере разом, не только то приложение, чей коммит принёс новый формат.

## Симптом

```
bun install v1.3.14 (...)
2 |   "lockfileVersion": 3,
                         ^
error: Unknown lockfile version
    at bun.lock:2:22
UnknownLockfileVersion: failed to parse lockfile: 'bun.lock'
warn: Ignoring lockfile
Resolving dependencies
Resolved, downloaded and extracted [11606]
...
1737 packages installed [50.08s]
❌ bun.lock изменился после фолбэка — версии пакетов разошлись с закоммиченными (см. PLAN-INFRA.md §50):
 bun.lock | 3968 ++++++++++++++++++--------------------------------------------
 1 file changed, 1132 insertions(+), 2836 deletions(-)
❌ Деплой остановлен: обнови bun.lock локально (bun install), закоммить и запушь.
```

Существующая защита `deploy-affected.sh` (фолбэк на `bun install` без `--frozen-lockfile` +
сравнение diff, см. [bun-lockfile-private-submodules.md § Как воспроизвести](bun-lockfile-private-submodules.md))
сработала штатно и корректно остановила деплой — но диагноз, который она даёт («версии пакетов
разошлись»), в этом случае **обманчив**: реальные версии пакетов не разошлись, разошёлся формат
самого lockfile. Локальный `bun install` не может это исправить, потому что расхождение не в
дереве зависимостей.

## Механизм

Локальный dev bun (1.4.1) пишет `bun.lock` с `"lockfileVersion": 3`. Сервер с bun 1.3.14
парсер этого формата вообще не содержит — не «читает неточно», а падает на второй строке файла.
Дальше `deploy-affected.sh` игнорирует нечитаемый lockfile и резолвит зависимости с нуля
(`warn: Ignoring lockfile`), что даёт совершенно другое дерево (в наблюдавшемся случае —
1737 пакетов установлено вместо использования существующего лока), и фолбэк-проверка видит
это как драматический дрейф на тысячи строк diff.

Отсюда и подтверждение старой открытой загадки в
[bun-lockfile-private-submodules.md § Смежное](bun-lockfile-private-submodules.md): падение
именно на **s3** (где submodule выкачаны полностью, значит объяснение про приватные submodule
не подходит) было тем же самым — версия bun на s3 в этот момент тоже была 1.3.14.

## Диагностика: где реально резолвится `bun` на сервере

Деплой выполняется в контексте `nsenter -t 1 -m -u -n -i -- sudo -u deploy bash -lc '...'`
(вход в PID-1 namespace хоста, затем sudo под пользователя `deploy`). `bun` в этом контексте
резолвится через `/usr/local/bin/bun`, который на обоих серверах — **симлинк на
`/root/.bun/bin/bun`**, а не на `~deploy/.bun/bin/bun`. Апгрейд bun только для пользователя
`deploy` (`ssh deploy@server "curl ... | bash"`) ничего не меняет — деплой всё равно найдёт
старый `bun` через `/usr/local/bin/bun` → `/root/.bun/bin/bun`.

```bash
# найти реальную цель символической ссылки
ssh root@<server> "readlink -f /usr/local/bin/bun"
# → /root/.bun/bin/bun
```

## Фикс

Обновить bun **от имени root**, не от `deploy`:

```bash
ssh root@<server> "curl -fsSL https://bun.sh/install | bash"
```

⚠️ **`bun upgrade` (self-upgrade) ненадёжен для этого сценария** — дважды подряд обрывал SSH-
соединение посреди скачивания нового бинарника (`Connection to <host> closed by remote host`,
exit 255), не завершив апгрейд. Официальный install-скрипт (`curl ... | bash`) отработал чисто
в обоих случаях — переустанавливает бинарник заново, а не пытается заменить работающий процесс
на лету.

**Обязательная проверка после апгрейда** — не голым `ssh`, а точно тем же контекстом, что
использует деплой:

```bash
ssh root@<server> "nsenter -t 1 -m -u -n -i -- sudo -u deploy bash -lc 'which bun && bun --version'"
```

Плоский `ssh deploy@<server> "which bun"` здесь **вводит в заблуждение**: он найдёт
`~deploy/.bun/bin/bun`, если такой существует (например, из более ранней ошибочной попытки
фикса «от deploy»), но это не тот бинарник, который резолвит `nsenter`-контекст. Только
проверка через реальный execution path подтверждает, что фикс применился там, где нужно.

## Почему это репо-широкий блокер, а не баг одного приложения

Любой коммит, где `bun.lock` переписан bun-ом более новой версии, чем стоит на сервере, кладёт
**все** последующие деплои на этом сервере — независимо от того, какое приложение деплоится.
Первый симптом обычно всплывает на случайном приложении из очереди (в найденном случае — сначала
`studio` на s3, затем `domwellbes` на s2), но причина не в этих приложениях.

## Что делать

- Синхронизировать версию bun на серверах с локальной dev-версией **после любого апгрейда bun
  в dev-окружении** — не дожидаться, пока это всплывёт как падение произвольного деплоя.
- При виде `Unknown lockfile version` / `UnknownLockfileVersion` в логе деплоя — сразу проверять
  версию bun на сервере (`bun --version` через `nsenter`-контекст), а не тратить время на
  предположение о реальном дрейфе версий пакетов.
- Такая проверка — кандидат на попадание в `scripts/check-all.mjs` (сравнение локальной версии
  bun из `package.json`/`.bun-version`, если появится, с версией на серверах через deploy-mcp) —
  на 2026-09-05 не реализовано, только зафиксировано здесь.
