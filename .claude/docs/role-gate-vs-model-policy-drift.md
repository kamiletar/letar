# Проверка роли в действии шире политики модели, которую действие пишет

⚠️ Класс бага, а не единичный случай: в одном приложении монорепо найден четырежды за месяц,
каждый раз — в новом контуре. Дыры в безопасности он не создаёт (периметр держит ZenStack), но
даёт худший из возможных отказов и тиражируется копипастой.

## Как выглядит

Server action делает две независимые проверки доступа:

```typescript
const { user } = await requireRole(SOMETHING_ADMIN_ROLES) // 1. гейт роли
const db = getEnhancedPrisma(user as never) // 2. политика модели в ZenStack
await db.someModel.create({ ... })
```

Если список ролей в (1) шире, чем `@@allow('create,update,delete', ...)` модели в (2), роль из
разницы **проходит гейт и падает на записи**. Снаружи это:

- страница пускает, кнопки видны, форма заполняется;
- на «Сохранить» — необработанное исключение или пустой результат без объяснения;
- в production Next.js маскирует текст серверной ошибки, так что пользователь не узнает даже
  причины;
- ни typecheck, ни lint, ни тесты с замоканным клиентом БД этого не видят — расхождение живёт
  между двумя файлами, а не внутри одного.

**Обратное направление тоже встречается и заметно хуже диагностируется:** политика разрешает
запись роли, которую гейт страницы/действия не пускает вовсе. Тогда жалоб нет — просто функция
не работает у тех, для кого её задумывали, и это годами читается как «так и было задумано».

## Почему возникает

Константа ролей заводится под **родительскую** сущность («у кого есть доступ к разделу»), а потом
переиспользуется для всех вложенных — их политики почти всегда уже. Особенно легко пропустить, если
запись идёт не в ту модель, что упомянута в имени действия:

- действие пишет несколько моделей сразу (сама сущность + её события/снапшоты/лог);
- запись идёт через общий хелпер, который **сам** создаёт или клонирует родителя (версию,
  ревизию, документ) — тогда права нужны и на родителя, а по имени вызова это не видно;
- транзакция трогает соседнюю модель ради инварианта («снять флаг у остальных»).

⚠️ Хелпер, создающий родителя лениво, даёт **отказ, зависящий от данных**: у одной записи
родитель уже есть — сработает, у другой нет — упадёт. Это выглядит как плавающий баг, а не как
запрет. Поэтому гейт такого действия равняется на права по родителю, даже если политика самой
целевой модели шире.

## Как чинить

1. Для каждого потребителя константы ролей — сверить со всеми `@@allow` моделей, в которые
   действие **реально** пишет (включая те, что пишет вызванный хелпер).
2. Где расхождение — брать более узкий набор. Отдельная константа с честным комментарием, а не
   переиспользование чужой по совпадению состава: списки совпадают сегодня и разъедутся завтра,
   а комментарий над константой — единственное место, где записан её смысл.
3. Действию с контрактом `{ error?: string }` — широкий `requireRole` как входной фильтр плюс
   узкая проверка отдельной строкой, возвращающая текст:

```typescript
const { user } = await requireRole(SECTION_ROLES)
if (!hasAnyRole(user.roles, NARROW_ROLES)) {
  return { error: 'Недостаточно прав: …' }
}
```

Так отказ доезжает до пользователя словами. Узкий `requireRole` для этого не годится:
`createRoleGuards` (`@letar/auth/server`) на отказе делает `redirect`, а не бросает — в server
action это молча уводит на главную.

4. Проверить и **страницу**, а не только действия. Если раздел пускает роль, которая ничего в нём
   изменить не может, — либо не показывать ей секции редактирования, либо не пускать вовсе.
   Скрывать вкладку честнее, чем показывать режим чтения, если данные роли не нужны.
   Скрыл вкладку — не забудь про прямую ссылку на неё (`?tab=…`): резолвер активной вкладки должен
   откатываться на дефолтную, иначе получится пустая панель.
5. Тест на отказ писать **на реальной БД**, а не с моком клиента. Суть бага — в связке двух
   проверок; мок клиента её не воспроизводит по определению. Полезный кейс сверх «вернулась
   ошибка»: после отказа не осталось побочных записей (той самой лениво созданной родительской).
