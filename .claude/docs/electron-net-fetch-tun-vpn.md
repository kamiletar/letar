# Electron `net.fetch` падает под TUN-VPN, хотя обычный Node fetch/сокет проходит

## Проблема

Electron предоставляет два независимых сетевых стека в main-процессе:

- `net.fetch()` (из `import { net } from 'electron'`) — идёт через **сеть Chromium**
  (тот же сетевой сервис, что и у страниц в браузере).
- Глобальный `fetch()` (Node.js/undici) — идёт через **сеть Node.js**, полностью независимую
  от Chromium.

Под VPN/прокси-клиентами, работающими в **TUN-режиме** (Clash, FlClash, mihomo и аналоги —
перехват пакетов на уровне виртуального сетевого адаптера ОС, а не через настройки прокси
приложения), эти два стека могут вести себя **по-разному для одного и того же домена**: TUN-клиент
различает трафик по TLS-отпечатку (ClientHello) и может резать только Chromium-стек, пропуская
Node.js-стек (или наоборот, в зависимости от правил конкретного клиента).

Симптом: `net.fetch()` бросает `net::ERR_FAILED` (или другой `net::ERR_*` код) на конкретном
домене, при этом:

- DNS резолвится нормально.
- Тот же самый запрос (метод, путь, заголовки, тело) через `node:https`/`fetch()` **проходит
  с 200 OK**.
- `session.resolveProxy(url)` возвращает `DIRECT` — то есть с точки зрения Chromium прокси
  вообще не настроен, поэтому `session.setProxy()`/`proxyBypassRules` **не могут помочь**:
  блокировка происходит НИЖЕ уровня прокси-конфигурации Chromium, на уровне сетевого адаптера.

## Как отличить от реальной блокировки на уровне сети/DNS/DPI провайдера

Если есть диагностика вида `describeNetErrorWithDiagnostics()` (см.
`apps/animatrona/main/utils/net-error.ts`) — она специально зондирует хост напрямую через
`node:dns`/`node:tls`/`node:https`, повторяя упавший запрос через тот же путь/заголовки/тело.
Если такое зондирование **проходит успешно**, а `net.fetch()` — нет, причина почти наверняка в
разнице сетевых стеков, а не в блокировке хоста как такового.

```
Диагностика: Реальный запрос (POST /api/graphql) через обычный сокет прошёл успешно,
сервер ответил 200 — блокировка, вероятно, непостоянна (rate-limit) либо проблема
была временной, попробуйте ещё раз
```

Формулировка про "непостоянна/временная" в общем `describeNetErrorWithDiagnostics()` — это
дефолтная интерпретация для любого сайта с антибот-защитой (DDoS-Guard и т.п.). Если ошибка
воспроизводится **стабильно** (не разово) и именно под TUN-VPN — это не про антибот-защиту
сайта, а про разницу сетевых стеков Electron, описанную выше.

## Что НЕ работает

- ❌ `session.setProxy({ mode: 'system', proxyBypassRules })` — Chromium в режиме `'system'`
  просто напрямую делегирует `ProxyConfigService` операционной системы и **полностью
  игнорирует** `proxyBypassRules` (он учитывается только для `'fixed_servers'`/`'pac_script'`).
- ❌ Пересборка системного прокси через `session.resolveProxy()` → `fixed_servers` +
  `proxyBypassRules` — не поможет, если `resolveProxy()` уже возвращает `DIRECT`
  (TUN-перехват не регистрируется как системный прокси, поэтому Chromium не видит его вообще
  и не может обойти).
- ❌ `app.configureHostResolver({ secureDnsMode: 'off' })` чинит только Fake-IP DNS десинхрон
  с TUN (см. ниже) — не относится к этому классу ошибки, если DNS резолвится нормально.

## Что работает — сменить сетевой стек для конкретного клиента

Если запросы к конкретному внешнему API (не требующему VPN пользователя — заблокирован в РФ
может быть только сам домен-источник контента, а не сторонний API) стабильно падают именно
через `net.fetch()`, а через `node:https`/`fetch()` проходят — просто не используйте
`net.fetch()` для этого клиента:

```typescript
// ❌ Chromium network stack — уязвим к TUN-VPN TLS-фингерпринтингу
import { net } from 'electron'
const response = await net.fetch(url, { method: 'POST', headers, body })

// ✅ Node.js/undici — независимый стек, TUN-клиент видит другой TLS-отпечаток
const response = await fetch(url, { method: 'POST', headers, body })
```

Прецедент: `apps/animatrona/main/services/shikimori/{client,anime-api,franchise-api}.ts` —
GraphQL и REST клиенты Shikimori переведены с `net.fetch` на глобальный `fetch`.

**Компромисс:** этот способ теряет для конкретного клиента честное отслеживание системного
прокси Chromium (`session.defaultSession`'s прокси-конфигурация), если он реально нужен для
данного домена. Для внешних API, которые НЕ требуют VPN пользователя (в отличие от источника,
ради которого VPN вообще настроен), это не потеря — они и не должны идти через прокси/VPN.

## Смежная проблема — Secure DNS (DoH) и Fake-IP TUN

Отдельная (но похожая по симптомам) причина рассинхрона: Chromium по умолчанию может включить
`automatic` upgrade на публичный DoH-резолвер, если распознаёт текущий DNS-провайдер. Fake-IP
TUN-прокси (домен-based маршрутизация по правилам) перехватывает системные DNS-запросы, чтобы
привязать TCP/TLS-соединение к домену и применить правило; DoH резолвит домен напрямую в обход
этого перехвата — привязка теряется, трафик уходит не туда. Чинится явным отключением:

```typescript
app.whenReady().then(async () => {
  app.configureHostResolver({ secureDnsMode: 'off' })
})
```

Эта проблема **предшествует** TLS-фингерпринтинг-проблеме выше по конвейеру диагностики —
проверяйте DNS-часть первой (симптом обычно `ERR_NAME_NOT_RESOLVED` или резолв в неожиданный
IP), только потом переходите к разнице сетевых стеков (`ERR_FAILED` при нормальном DNS).

## Чеклист диагностики `net::ERR_FAILED`/`net::ERR_*` в Electron main-процессе

- [ ] DNS резолвится верно? (`node:dns.resolve4` вручную или через диагностику)
- [ ] `secureDnsMode: 'off'` уже установлен?
- [ ] Тот же запрос через `node:https`/глобальный `fetch()` проходит?
- [ ] `session.resolveProxy(url)` возвращает `DIRECT` или реальный прокси-адрес?
- [ ] Если п.3 проходит, а `net.fetch()` — нет: переключить конкретный клиент на глобальный
      `fetch()`, не пытаться чинить через `session.setProxy()`.
