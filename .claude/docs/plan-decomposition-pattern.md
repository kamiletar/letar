# Декомпозиция больших плановых файлов

Когда `PLAN.md`, `ROADMAP.md` или похожий плановый файл приложения разрастается настолько, что
слабый исполнитель-агент в нём тонет — есть рабочий рецепт разреза на части с точкой входа.
Выработан на одном из приложений монорепо при разрезе плана объёмом ~2500–2600 строк на три
файла; здесь описан переиспользуемый процесс, без деталей той предметной области.

## Когда это нужно

Эмпирический порог — не строгое число, а сигнал: агент реально путается, переспрашивает
структуру, теряет раздел при правке. На практике это обычно происходит уже за пределами
~1000 строк, и почти всегда — за пределами ~1500–2000. Замер по монорепо на 2026-08-18
(`wc -l apps/*/PLAN.md`) показал несколько файлов за 1500 строк — они кандидаты, но
декомпозиция не обязательна, пока агент с планом справляется. Не режь план профилактически —
это лишняя навигационная нагрузка на всех, кто читает план целиком нечасто.

## Пошаговый процесс

1. **Резать по заголовкам** (`## Фаза N`, `## Mxx`, `### N.N`), а не по номерам строк. Номера
   строк съезжают после первого же прогона форматтера — dprint перестраивает markdown-таблицы,
   сдвигая всё, что ниже. Разрез по номерам строк, снятый один раз, начинает врать при следующей
   правке.
2. **Сохранять исходную нумерацию разделов** в новых файлах. Если раздел назывался §3.4, он
   остаётся §3.4 в новом файле — не перенумеровывается с 1. Это единственный способ, которым
   старые внутритекстовые ссылки на «§3.4» остаются интерпретируемыми без переписывания текста
   вокруг них.
3. **В каждой получившейся части — таблица маршрутизации сверху**: «куда ведут ссылки вида §N» со
   ссылками на все части. Читатель, попавший в часть не с головного файла (например, по прямой
   ссылке из чужого документа), должен сразу увидеть карту, а не только свой фрагмент.
4. **Головная часть — только координация, не контент.** После разреза головной файл
   (`PLAN.md`/`PLAN_SHOP.md` и т.п.) содержит: правила исполнения, ключевые решения и статус,
   таблицу-карту со ссылками на все части. Его читают все, независимо от темы задачи — поэтому в
   нём не должно остаться содержательных разделов, которые уехали в части.
5. **Переписать точечные ссылки на конкретную новую часть.** Ссылки вида «см. PLAN.md Фаза 7»,
   разбросанные по другим файлам приложения (в том числе в других планах), нужно найти и
   поправить на файл, куда эта фаза уехала. Ссылка на существующий файл, которая ведёт не туда,
   не выглядит битой ни для грепа, ни для читателя — а по факту это порча навигации, которую
   заметят не сразу.
6. **Точка входа** (`PLAN_INDEX.md` или аналог) держит: дерево всех частей с кратким «о чём
   каждая», и отдельно — «первый час нового исполнителя»: что прочитать первым (три-четыре файла,
   не «прочитать всё»), какая первая задача, конкретный критерий приёмки для неё. Не «выбери
   задачу из плана сам» — единственная явно выбранная задача с обоснованием, почему именно она
   блокирует больше всего остального.

## Проверка целостности после разреза

Два измерения, оба обязательны:

- **Число заголовков совпадает.** Количество `##`/`###`/`####` в исходном файле до разреза равно
  сумме таких же заголовков во всех получившихся частях вместе. Расхождение — потерянный или
  задвоенный раздел.
- **Ноль битых относительных markdown-ссылок** между файлами приложения. Проверяется грепом по
  `\]\(([^)#\s]+\.md)` с проверкой существования каждого найденного файла — этот же грепп ловит
  как классические битые ссылки (файл не существует), так и повод перепроверить п.5 (файл
  существует, но это не то же самое, что ссылка ведёт на правильный раздел внутри него — это уже
  проверяется глазами, автоматически не ловится).

## Антипаттерны

- **Резать по номерам строк, а не по заголовкам.** Разрез, актуальный на момент создания,
  ломается при первом же прогоне форматтера или правке выше по файлу — привязка к номеру строки
  ничем не защищена от сдвига.
- **Забыть переписать точечные ссылки на разделы из других планов.** Тихая порча навигации:
  ссылка не битая (файл существует), но ведёт не в тот раздел — обнаруживается не сразу, а когда
  кто-то читает «§7» и находит там не то.
- **Перенумеровать разделы при разрезе.** Рвёт все существующие ссылки на старые номера сразу,
  вместо того чтобы рвать только те, что действительно указывают не туда.
- **Резать профилактически, пока план ещё читаем.** Каждая дополнительная часть — это ещё один
  файл в таблице маршрутизации и ещё один источник рассинхрона ссылок. Резать по факту, когда
  агент уже путается, а не заранее «на всякий случай».
- **Головная часть, в которой осталось много контента.** Если после разреза головной файл всё
  ещё большой — разрез не выполнил свою задачу: агент, обязанный прочитать головную часть первой,
  снова тонет в объёме до того, как доберётся до своей части.

## Пример

Пример полного цикла (разрез, точка входа, «первый час нового исполнителя», карта разделов) —
`PLAN_INDEX.md` и связанные `PLAN*.md`/`ROADMAP*.md` одного из приложений монорепо. Файлы
приложения приватны ([public-repo-hygiene](/.claude/rules/public-repo-hygiene.md)), поэтому здесь
не даётся прямая ссылка и не описывается их предметное содержимое — только сам процесс выше,
который воспроизводим без доступа к оригиналу.
