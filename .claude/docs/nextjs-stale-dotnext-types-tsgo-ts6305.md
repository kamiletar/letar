# Устаревший `.next/types` даёт ложный `TS6305` в `typecheck:tsgo` — не связано с текущими правками

## Симптом

`nx typecheck:tsgo <next-app>` падает десятками ошибок вида:

```
apps/animatrona/renderer/.next/types/app/api/image/route.ts:2:24
  - error TS6305: Output file '.../route.d.ts' has not been built from source file '.../route.ts'.
```

По одной ошибке на каждый файл под `.next/types/app/**` (в `animatrona-renderer` — 76 ошибок на
~26 файлов), при полностью корректном коде самих `src/app/**/page.tsx`/`route.ts`.

## Причина

`.next/types/**/*.ts` — сгенерированные Next.js файлы для type-check API-роутов/страниц
(`checkFields<...>` против сигнатуры `GET`/`POST`/`generateStaticParams` и т.п.). Их формат и
типы-хелперы, которые они импортируют из `next/dist/build/segment-config/...`, привязаны к
**версии Next.js, которой они были сгенерированы** (`next dev`/`next build`). Дефолтный tsconfig
Next.js включает `".next/types/**/*.ts"` в `include` без проверки актуальности — обычная сборка
полагается на то, что `next dev`/`next build` регенерирует их перед каждым запуском.

Если каталог `.next` — старый (сгенерирован более ранним запуском `next dev`/`next build`, ещё
до того, как `bun update`/`bun install` подняли версию `next` в `node_modules`), сгенерированные
файлы рассинхронизируются с текущей установленной версией Next — и tsgo даёт **не обычную
ошибку типов, а TS6305** (сообщение как будто про project references, хотя `references` тут ни
при чём — это единственный проект, без `--build` режима).

`.next/**` и `tsconfig.tsbuildinfo` — оба в `.gitignore` (корневой `.gitignore:75`, и
`apps/animatrona/.gitignore:6` для `tsbuildinfo`). Значит это **чисто локальный артефакт
рабочей копии**, не зафиксированный конфиг — ни один коммит его не создаёт и не чинит.

## ⚠️ Почему бисекция по git-коммитам это не ловит

`.next` не отслеживается git — переключение между коммитами (`git checkout <sha>`,
`git bisect`) никак его не трогает. Если ошибка воспроизводится «и на чистом HEAD, и после
апдейта зависимостей» — это ожидаемо для стороннего локального артефакта, а не доказательство,
что дело не в зависимостях: артефакт one и тот же на любом коммите рабочей копии, пока его не
удалили руками. Тот же класс методологической ловушки, что описан в
[verification-pitfalls.md § grep по копиям репо](/.claude/docs/verification-pitfalls.md) — только
здесь причина «врёт» не рекурсивный grep, а неотслеживаемый build-кеш.

## Почему конкретно `animatrona-renderer`, а не любой другой Next-app

Обычные веб-приложения монорепо гоняются через `nx dev <app>` часто (в каждой сессии разработки),
поэтому их `.next` почти всегда свежий относительно установленного `next`. `animatrona/renderer` —
Next.js-рендерер Electron-приложения (см. [animatrona.md](/.claude/rules/animatrona.md)) — обычно
запускается через полный Electron dev-цикл, а не напрямую `nx dev animatrona-renderer`; его
`.next` может пролежать нетронутым неделями, пережив несколько `bun update` версии `next` в
корневом `package.json`. Ни у одного проверенного Next-app в репозитории (`aboi`, `aira-web`,
`animatrona-landing`) таргет `typecheck:tsgo` не зависит от `build`/`dev` (`dependsOn`) — эта
проблема системная для всех, просто обычно не успевает материализоваться.

## Фикс — локальный, без правок конфигурации

```bash
cd apps/animatrona/renderer
rm -rf .next tsconfig.tsbuildinfo
nx typecheck:tsgo animatrona-renderer --skip-nx-cache
```

После удаления `.next` глоб `.next/types/**/*.ts` в `include` просто ничего не матчит (не
ошибка) — typecheck зелёный. Подтверждено: 76 ошибок → 0 сразу после `rm -rf .next`, без единой
правки кода или `project.json`.

## Почему НЕ нужно чинить `project.json` (`dependsOn: ["build"]`/`["dev"]`)

Рассматривалось и отклонено:

- **Ни один другой Next-app в репозитории так не делает** — единообразный паттерн ценнее точечного
  фикса одного приложения.
- **`build` этого приложения — тяжёлый `next build --webpack` в статический `out/`** (не обычный
  `.next`-сервер), навешивать его перед каждым typecheck сделало бы таргет на порядки медленнее
  ради проблемы, которая на CI/чистом клоне не воспроизводится вовсе — там `.next` просто
  отсутствует, и в `include` нечему матчиться.
- **Проблема — свойство состояния локальной рабочей копии, не конфигурации.** Официальная модель
  Next.js and так предполагает регенерацию `.next/types` перед проверкой; лечить нужно гигиену
  (свежий `.next` или его отсутствие), а не переусложнять граф задач Nx.

Если увидишь `TS6305` под `.next/types/**` в любом Next-приложении монорепо (не только
`animatrona-renderer`) — тот же диагноз, тот же фикс: `rm -rf .next tsconfig.tsbuildinfo` и
перезапуск typecheck.
