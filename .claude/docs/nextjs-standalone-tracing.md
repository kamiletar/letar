# Next.js standalone + bun: пропущенные файлы при трассировке

## Симптом

Docker-билд (`nx build <app>` → `docker build`) проходит **без единой ошибки**, деплой
отчитывается `exitCode 0`, но в проде контейнер падает на первом же запросе:

```
ERR_DLOPEN_FAILED: Error loading shared library libvips-cpp.so.8.18.3: No such file or directory
```

или

```
Error: Cannot find module '.../node_modules/@prisma/adapter-pg/dist/index.js'
```

или запрос к БД падает с `ECONNREFUSED`, хотя строка подключения и сеть проверены вручную
и работают.

## Причина

Next.js `output: 'standalone'` использует file tracer (`@vercel/nft`), который статически
анализирует код и копирует только файлы, которые он смог обнаружить как зависимости. Трейсер
надёжно ловит обычные `require()`/`import`, но **не всегда** видит:

- нативные `.so`/`.node`-библиотеки, загружаемые динамически через `dlopen()` (так делает
  `sharp`/`libvips`) — трейсер не парсит бинарный код, чтобы найти такую зависимость;
- пакеты, чей `package.json` `main`/`exports` указывает на файл, которого при трассировке не
  оказалось в копии (например, только `.mjs` скопировался, `.js` — нет, или наоборот);
- вложенные dot-scope пакеты вроде `.prisma/client` (сгенерированный Prisma-клиент), особенно
  когда они генерируются в общий корневой `node_modules`, а не рядом с приложением.

Это усугубляется bun-специфичным layout: в монорепо на bun пакеты физически лежат в
изолированном хранилище `node_modules/.bun/<pkg>@<version>+<hash>/node_modules/<pkg>`, а
обычные пути в `node_modules/<pkg>` — это симлинки на них. Next.js для `standalone`-вывода
иногда создаёт **свою** per-chunk alias-копию под `.next/node_modules/<pkg>-<hash>/`
(отдельно от `node_modules/.bun/...`), и именно она может оказаться неполной — при этом сам
`node_modules/.bun/...` в собранном образе полный, но приложение резолвит модуль через alias,
не через него.

Баг **латентный**: не проявляется, пока образ пересобирают инкрементально (Docker/Nx-кеш),
и всплывает только при первой полной пересборке с нуля — например, после смены конфигурации
деплоя, апдейта `bun.lock` или через много дней без передеплоя.

## Диагностика

1. Проверить, действительно ли файл физически отсутствует в контейнере:
   ```bash
   docker exec <container> find /app -iname '*<искомый-пакет>*'
   ```
   Сравнить с содержимым исходного `node_modules/.bun/<pkg>@.../node_modules/<pkg>/` — какие
   файлы пропали.
2. Проверить, симлинк ли `.next/node_modules/<pkg>-<hash>` указывает на полный путь, или это
   частичная копия конкретных файлов:
   ```bash
   docker exec <container> ls -la /app/apps/<app>/.next/node_modules/<scope>/
   ```
3. Воспроизвести падение вручную внутри контейнера тем же кодом, что использует приложение
   (не абстрактным тестом) — `docker exec <container> node --input-type=module -e "..."`,
   импортируя ровно те файлы, что использует рантайм.

## Фикс

Добавить `outputFileTracingIncludes` в `next.config.ts` приложения — явный глоб, который
форсирует полное копирование нужного пакета в `.next/standalone`:

```typescript
const config: NextConfig = {
  output: 'standalone',
  outputFileTracingIncludes: {
    '/**': ['../../node_modules/.bun/<pkg>+@*/node_modules/<scope>/<pkg>/**/*'],
  },
}
```

⚠️ **Пути относительны директории приложения**, не корня монорепо. В Nx-монорепо на bun у
приложения обычно **нет собственного** `node_modules` (всё хоистится в корень) — значит от
`apps/<app>/` до `node_modules/` нужно подняться на 2 уровня (`../../node_modules/...`), а не
писать `./node_modules/...` (не найдёт ничего, тихо смолчит, тайминг билда не изменится и
проблема не решится — легко пропустить эту ошибку).

⚠️ **Не используй широкие wildcard-глобы** (`@pkg+*/**/*` без сужения) — трейсер начинает
сканировать намного больше файлов, что может увеличить время сборки на порядок (в одном
случае — с 17с до 2.6мин без какого-либо выигрыша, если паттерн не попал в цель). Указывай
путь максимально точно — конкретное имя пакета, при необходимости с версией через `*`
только в позиции версии, не во всём пути.

⚠️ **`transpilePackages` этот класс багов не лечит** и в этом документе больше нигде не
упоминается. Он действует на фазе компиляции (снимает запрет компилировать `node_modules`), а
трассировка идёт после неё — на содержимое `.next/standalone` он не влияет вообще. Проверено
удалением записи из `transpilePackages` у `animatrona-tracker`: состав
`.next/standalone/node_modules` и набор серверных чанков с кодом библиотеки после сборки те же,
что и с записью. Workspace-библиотекам `@letar/*` он не нужен и сам по себе — см.
[lib-entry-points.md](/.claude/docs/lib-entry-points.md), раздел «`transpilePackages` — НЕ нужен».

## ⚠️ Повторный провал того же фикса — глубина `./` вместо `../../` (сессия №72, 2026-07-13)

Фикс `outputFileTracingIncludes` из сессии №71 задеплоился на `mandala` и **воспроизвёл ту же
самую ошибку** `ERR_DLOPEN_FAILED`. Причина: во всех пяти применённых конфигах
(`mandala`, `kami`, `grandslamcup`, `driving-school`, `aboi`) глоб был записан как
`./node_modules/.bun/@img+sharp-libvips-*/**/*.so*` — с `./`, а не `../../` — то есть именно
та ошибка, от которой это же правило предупреждает выше (п. «⚠️ Пути относительны директории
приложения»). Глоб тихо не находил файлов, фикс не работал, но билд проходил без единой ошибки
и без изменения времени сборки — характерный симптом этого класса багов.

**Почему предыдущий тест (сессия №71) не поймал баг:** фикс проверялся на изолированном
минимальном Next.js-проекте, где `next.config.js` лежал прямо в корне проекта (глубина 0) —
там `./node_modules/...` действительно работал, потому что `node_modules` был рядом. В
монорепо `apps/<app>/next.config.js` находится на 2 уровня ниже корня, где физически лежит
`node_modules/.bun/...` — несовпадение глубины воспроизводится только при тестировании именно
в структуре монорепо, не в одиночном проекте.

**Как было исправлено и проверено (сессия №72):** реальная Turbopack-сборка в
`oven/bun:alpine` Docker-контейнере (тот же стек, что на сервере — bun store + Next 16.2.10 +
Turbopack), с фиктивным `.so`-файлом в `node_modules/.bun/@img+sharp-libvips-linuxmusl-x64@.../`
корня и `next.config.js` на глубине `apps/testapp/` (та же вложенность, что в `apps/mandala/`).
Результат: `./node_modules/...` — файл в `.next/standalone` отсутствует; `../../node_modules/...`
— файл присутствует. Билд обоих вариантов проходит без единой ошибки в обоих случаях — отличить
их можно только фактической проверкой содержимого `.next/standalone`, не логами билда.

**Вывод:** тестировать `outputFileTracingIncludes` только на изолированном проекте с плоской
структурой (`next.config.js` в корне) **недостаточно** — обязательно воспроизводить реальную
глубину вложенности приложения в монорепо (`apps/<app>/`, 2 уровня от корня) и физически
проверять содержимое `.next/standalone` после сборки, а не полагаться на успешное завершение
билда.

## ⚠️ Не всякий рантайм-ECONNREFUSED — это баг трассировки

Инцидент `form-example` (2026-07-12) изначально выглядел как классический случай этой статьи —
`ECONNREFUSED` в `prisma.product.findMany()`, строка подключения проверена и рабочая. Была
применена попытка фикса через `outputFileTracingIncludes` для `@prisma/adapter-pg`
(коммиты `5df6e1e` → `d3423eb`) — **не помогло**, откачено в `16471b4`.

Реальная причина оказалась другой и вообще не про трассировку файлов: в bun-хостинге
монорепо параллельно установлено несколько версий `pg` (hoisting — 8.20.0/8.21.0/8.22.0
одновременно в `node_modules/.bun/`). Код приложения создавал `new Pool({connectionString})`
через одну резолвнутую версию `pg`, а `@prisma/adapter-pg` **внутри себя** резолвит свою,
отдельную версию `pg` (свой изолированный dependency tree). `instanceof Pool`-проверка внутри
адаптера между двумя разными классами (разные версии пакета = разные классы, даже
структурно идентичные) не проходит → адаптер не распознаёт переданный `Pool` как валидный →
тихо создаёт свой собственный `Pool` без `connectionString` → дефолтится на `localhost:5432`
→ `ECONNREFUSED`. Реальная ошибка при этом маскируется внутри `performIO` (WASM query
compiler) под generic `ECONNREFUSED`, не показывая, что дело в другом — это известный
открытый баг Prisma, [prisma/prisma#28055](https://github.com/prisma/prisma/issues/28055).

**Диагностика, которая отличает этот случай от бага трассировки:** воспроизвести падение
внутри контейнера напрямую тем же кодом (см. п.3 «Диагностика» выше), но вызвать
`adapter.queryRaw()` **в обход обёртки Prisma Client**, чтобы увидеть настоящее исключение —
`handleRequestError`/`PrismaClientKnownRequestError` глотает реальную причину:

```bash
docker exec -w /app/apps/<app>/.next <container> node -e "
(async()=>{
  const { PrismaPg } = await import('@prisma/adapter-pg-<hash>')  // имя из логов
  const { Pool } = await import('pg-<hash>')
  const pool = new Pool({ connectionString: process.env.DATABASE_URL })
  const adapter = await new PrismaPg(pool).connect()
  try { await adapter.queryRaw({ sql: 'SELECT 1', args: [], argTypes: [] }) }
  catch(e) { console.log(e) }  // реальная ошибка, не обёрнутая
})()"
```

Если реальная ошибка указывает на `localhost`/`127.0.0.1`/`::1` вместо ожидаемого хоста —
это конфликт версий `pg`, не проблема трассировки. **Фикс** — передавать `connectionString`
(или `PoolConfig`) напрямую в конструктор адаптера вместо готового `Pool`-инстанса, чтобы
адаптер сам создавал `Pool` через свою резолвнутую версию `pg`:

```typescript
// ❌ Может сломаться при нескольких версиях pg в hoisting
const pool = new Pool({ connectionString: process.env.DATABASE_URL })
const adapter = new PrismaPg(pool)

// ✅ Адаптер создаёт Pool сам — конфликта версий классов нет
const adapter = new PrismaPg({ connectionString: process.env.DATABASE_URL })
```

Коммит фикса: `apps/form-example/src/lib/db.ts` (`bd498ed`). Если у приложения несколько
версий `pg` в `bun.lock` (`grep -A1 '"pg"' bun.lock` или смотри `node_modules/.bun/pg@*`) и
используется `@prisma/adapter-pg` — превентивно применяй тот же паттерн.
