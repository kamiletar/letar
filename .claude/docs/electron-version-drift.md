# Дрейф версий electron между приложениями

## Почему версия electron в приложении — точная, а не диапазон

`electron-builder` при сборке скачивает бинарник Electron под целевую платформу и должен точно
знать, какую версию качать — с диапазоном (`^44.0.0`) он не может однозначно выбрать конкретный
релиз для кэша/офлайн-сборки. Поэтому в `devDependencies` каждого Electron-приложения версия
всегда точная (`"electron": "44.0.0"`), а не диапазон.

Корневой `package.json` при этом держит `electron` в `devDependencies` как диапазон
(`"^44.0.0"`) — это общая договорённость репозитория для версий зависимостей
(см. [[feedback_root_only_dependency_versions]] в памяти и корневой `CLAUDE.md`
§ «Версии зависимостей»). Из этих двух правил разных уровней и получается расхождение:
корень задаёт диапазон, приложение — конкретную версию внутри него.

## Как дрейф на практике возникает и почему его не видно сразу

Приложение обновляет свою точную версию electron независимо от корня (например при security-фиксе
конкретного релиза) — и с этого момента у приложения и у корня разные версии electron, хотя обе
формально попадают в диапазон корня, если он ещё не сдвинут. Если приложений несколько и каждое
обновляется своим темпом, они расходятся и между собой: 2026-08-20 ручной аудит нашёл четыре
Electron-приложения (`animatrona`, `label-printer-desktop`, `poster-microtext-desktop`,
`kami-key-the`), независимо застрявших на `43.3.0`, при корневом диапазоне `^43.4.1`.

Ни `bun install`, ни typecheck, ни lint на это расхождение не падают — версия внутри диапазона
формально валидна, сборка каждого приложения по отдельности проходит. Единственный способ увидеть
дрейф — сравнить точные версии всех `apps/*/package.json` между собой и с корнем.

## Как дрейф виден в `bun.lock`

Пока все версии совпадают, в `bun.lock` для `electron` только одна запись верхнего уровня —
секция `packages`:

```
"electron": ["electron@44.0.0", "", { ... }, "sha512-..."],
```

а в блоке каждого workspace-приложения — просто ссылка на точную версию:

```
"apps/animatrona": {
  ...
  "devDependencies": {
    "electron": "44.0.0",
  },
},
```

Если версии расходятся, `bun` резолвит и хранит **обе** версии как отдельные записи
верхнего уровня в `packages` (`"electron@43.3.0"` и `"electron@43.4.1"` одновременно) — то есть
физически два разных бинарника electron в дереве зависимостей вместо одного. Обнаружить это —
`grep -c '"electron@' bun.lock`: если результат больше 1, версии разошлись. Сам факт, какое
приложение на какой версии, определяется по `devDependencies` внутри блока `apps/<app>` (как
в примере выше), а не по секции `packages`.

## Механическая проверка

[`scripts/check-electron-drift.sh`](/scripts/check-electron-drift.sh) сравнивает точную версию в
`devDependencies.electron` каждого `apps/*/package.json` (там, где эта зависимость вообще есть) с
версией из диапазона корневого `package.json`. Печатает список расхождений и возвращает
ненулевой код при любом дрейфе.

```bash
bash scripts/check-electron-drift.sh
```

Не подключена ни к pre-commit хуку, ни к CI — запускать вручную после апдейта electron в любом
приложении или при плановом аудите зависимостей. Решение не встраивать её в обязательный
пайплайн — ниже.

### Почему не CI-гейт

Дрейф electron — редкое событие (обновления electron в приложениях происходят не чаще пары раз
в год, нашлось единственный раз за всё время репозитория), не блокирует сборку и не является
багом времени выполнения — только источником лишнего веса в `bun.lock` и потенциальной путаницы
при следующем ручном апдейте. Заводить для этого отдельный CI-таргет или pre-commit хук — овчинка
не стоит выделки: обычного `nx run-many` для линта/тайпчека это не заденет, а вписывать ещё один
обязательный шаг в путь каждого коммита ради события раз в полгода — накладнее находки. Скрипт
существует для быстрой ручной сверки (например в рамках `infra:deps-update` skill при апдейте
electron) — этого достаточно.

## Затронутые приложения на 2026-08-25

`animatrona`, `label-printer-desktop`, `kami-key-the`, `poster-microtext-desktop` (приватный
submodule — правки версии коммитятся внутри самого submodule, затем bump SHA в `letar`
отдельным коммитом `chore: bump poster-microtext-desktop submodule`, см.
[git.md § Работа с приватными submodule](/.claude/rules/git.md)). Новые Electron-приложения,
заведённые через `nx g @letar/generators:new-app` с Electron-шаблоном, автоматически попадают
под тот же риск дрейфа — специальной защиты от генератора нет.
