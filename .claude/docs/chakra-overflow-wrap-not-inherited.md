# `overflow-wrap` не наследуется — у потомка уже есть своё явное значение

⚠️ Правило «поставь `overflow-wrap: normal` на предке — унаследуется вниз по дереву» не работает
для элементов, которые Chakra уже стилизует явно через свой CSS reset (preflight).

## Симптом

Нужно отключить перенос по слогу/разрыв слов для отдельной локали (в конкретном случае — японской
типографики, где посимвольный перенос ломает пиксельную сетку шрифта). Стиль ставится на общий
предок (`Box`, оборачивающий всё дерево страницы), с расчётом на обычное CSS-наследование.

Не сработало ни через `css`-проп:

```tsx
<Box css={{ overflowWrap: 'normal' }}>
  ...
</Box>
```

ни через настоящий React inline-стиль (буквальный DOM-атрибут `style`, а не `css`-проп):

```tsx
<Box style={{ overflowWrap: 'normal' }}>
  ...
</Box>
```

Во втором случае DOM-инспекция подтвердила, что стиль реально применился к самому предку —
`getComputedStyle(box).overflowWrap` возвращал `'normal'`. При этом у элемента-потомка
(`<header>`/`<Heading>`/`<Text>` и т.п.) `getComputedStyle(header).overflowWrap` всё равно
возвращал `'break-word'`. Наследование выглядело как будто не работает вообще — хотя CSS-каскад
тут ни при чём.

## Причина

Chakra UI v3 включает CSS reset (`preflight`), который явно выставляет `overflow-wrap: break-word`
на заголовках и параграфах:

```js
// node_modules/@chakra-ui/react/dist/esm/styled-system/preflight.js
"p, h1, h2, h3, h4, h5, h6": { overflowWrap: "break-word" },
```

CSS-наследование работает только тогда, когда у потомка **нет собственного явного значения**
свойства — тогда он берёт вычисленное значение родителя. Если у потомка есть explicit-правило
(неважно какого источника — reset, recipe, инлайн-стиль, `!important` не нужен), явное значение
всегда побеждает унаследованное. Это не конкуренция specificity/layer-порядка между предком и
потомком — предок и потомок вообще не конкурируют за одно и то же правило, потомок просто не
доходит до шага «наследовать», у него уже есть готовый ответ.

Поэтому любой узел, который рендерится как `<Heading>`/`<Text>` (или ecли смотреть шире — как
`<p>`/`<h1>`–`<h6>`) внутри дерева, будет игнорировать `overflow-wrap`, поставленный на предка,
сколько бы уровней вложенности между ними ни было.

## Фикс: явный селектор на потомков в `css`-пропе предка

```tsx
<Box
  css={{
    // Обычное наследование не работает: у p/h1-h6 Chakra уже задаёт своё явное значение
    // overflow-wrap в preflight — оно перебивает то, что унаследовано бы от предка.
    // Только явный селектор на потомков решает.
    '& *': { overflowWrap: 'normal' },
  }}
>
  ...
</Box>
```

`'& *'` даёт каждому потомку собственное явное правило с более специфичным/поздним источником
(inline style-tag компонента), которое перебивает reset-правило preflight тем же механизмом
«explicit beats inherited» — только теперь уже в свою пользу.

Рабочий пример — [layout.tsx](/apps/studio/src/app/(public)/[locale]/layout.tsx), ищи `isJa`.

## Для каких ещё свойств это актуально

Не только `overflow-wrap`. Тот же эффект будет для **любого** CSS-свойства, которое Chakra/Panda
уже явно выставляет на конкретных элементах через reset (`preflight`) или через recipe/slot-recipe
темы приложения — обычное наследование через предка для таких элементов не работает, нужен явный
селектор на потомков (`'& *'` или более узкий, если известен конкретный тег/data-атрибут).

Проверить, задаёт ли reset нужное свойство явно, можно грепом по `preflight.js`:

```bash
grep -n "<CSS-свойство-в-camelCase>" node_modules/@chakra-ui/react/dist/esm/styled-system/preflight.js
```

Найденный селектор в найденной строке — это и есть тот набор тегов, для которых наследование от
предка сломано.

Проверено на Chakra 3.36.1 (2026-08-19, REDESIGN_PLAN.md Э10b — японская локаль).
