# Барабанный реэкспорт библиотеки требует `dom` в `lib` потребителя, даже если сам потребитель `window` не использует

## Симптом

`tsc --build` (таргет `typecheck`, не `typecheck:tsgo`) библиотеки/приложения падает с пачкой
`TS2304: Cannot find name 'window'`/`'StorageEvent'` на файлах **чужой** библиотеки — не на
своих исходниках, и без единой строки `window`/`document` в самом потребителе.

Найдено на `libs/chakra-provider` (2026-09-04): `use-color-mode.ts` заменил локальную
`useSyncExternalStore`-идиому на `useIsHydrated()` из `@letar/hooks` — единственный новый
импорт, ноль обращений к DOM в самом файле. `tsc --build` упал 61 ошибкой в
`libs/hooks/src/lib/utility/use-local-storage.ts`, `use-window-size.ts`, `use-polled-data.ts` —
файлах, которые `use-color-mode.ts` вообще не импортирует напрямую.

## Причина

`@letar/hooks` — один барабанный `src/index.ts`, реэкспортирующий **все** хуки библиотеки.
Импорт `import { useIsHydrated } from '@letar/hooks'` резолвится (через `customConditions`,
см. [libs.md](/.claude/rules/libs.md)) в `hooks/src/index.ts` целиком — `tsc` включает в
программу компиляции весь барабан, а не только использованный экспорт (barrel-файлы не
дерево-трясутся на уровне типов, только бандлерами в рантайме).

Включённый файл чужой библиотеки типизируется **компилятором опциями программы, в которую его
затянуло**, а не своими собственными. `libs/hooks/tsconfig.lib.json` держит
`"lib": ["dom", "dom.iterable", "esnext"]` — но это не имеет значения, если файл компилируется
не как часть программы `hooks`, а как часть программы потребителя. Если у потребителя
`lib` не включает `"dom"` (как у `chakra-provider/tsconfig.lib.json` — только унаследованный из
`tsconfig.base.json` `"es2022"`), браузерные глобалы (`window`, `StorageEvent`, `localStorage`
как поле `window`) в затянутых файлах не резолвятся.

Тот же механизм, что описан в [libs.md](/.claude/rules/libs.md) для устаревшего `dist/*.d.ts` и
для solution-config редиректа — «резолвер компилирует по графу, файл получает опции текущей
программы» — но здесь источник расхождения не версия артефакта и не порядок `references`, а сам
факт барабанного экспорта библиотеки с многоцелевым набором хуков (не все из них
браузерно-нейтральны).

## Когда это всплывает

Только у **потребителей библиотеки, использующих `tsc --build`** (таргет `typecheck` с
`--emitDeclarationOnly`, характерно для `libs/*`, у которых есть свой `dist/`). Приложения на
`typecheck:tsgo` этому не подвержены — `tsgo` резолвит модули иначе и не даёт такой ошибки
(проверено на `driving-school`/`pravda`/`dashboard`/`label-printer-desktop` — все зелёные с тем
же импортом). Симптом специфичен библиотекам-потребителям с собственным `tsc --build`.

## Фикс

Добавить `"dom"`/`"dom.iterable"` в `lib` того `tsconfig.lib.json`, который упал — не трогать
`tsconfig.base.json` (иначе Node-only библиотеки без DOM получат браузерные глобалы там, где их
специально не должно быть) и не трогать саму библиотеку-источник (`@letar/hooks` уже настроена
верно для себя):

```json
// libs/chakra-provider/tsconfig.lib.json
{
  "compilerOptions": {
    "lib": ["dom", "dom.iterable", "es2022"]
  }
}
```

Обоснованно для `chakra-provider` конкретно — это изначально браузерная библиотека (`next-themes`,
клиентский `useColorMode`), ей `dom` нужен по своей природе, а не только из-за реэкспорта.

## Не путать с

- [libs.md § «устаревший `libs/<name>/dist/*.d.ts`»](/.claude/rules/libs.md) — там причина в
  рассинхроне артефакта, не в компиляторных опциях программы.
- [libs.md § «редирект под обычным `tsc`»](/.claude/rules/libs.md) — там причина в порядке
  `references` solution-конфига, не в наборе `lib`.

Общее у всех трёх — источник ошибки лежит не в том файле, где на первый взгляд ищется, и
диагностировать нужно по графу компиляции (`tsc --build --verbose`/`--listFiles`), а не по
содержимому упавшей строки.
