# Regex-сторож запрещённых импортов для клиент-серверного движка

Когда чистая функция обязана оставаться исполнимой в браузере **и одновременно** быть тем же
кодом, что считает сервер (превью на клиенте должно совпадать с сохранённым результатом по
построению, не по совпадению), а соседние файлы в том же каталоге — обычный серверный код,
typecheck и lint это не защищают. `tsgo`/ESLint не знают, что именно этот файл обязан оставаться
браузеро-безопасным — импорт `@/lib/db` или `node:crypto` в чистой функции пройдёт оба чисто и
проявится только на `nx build` (модуль утёк в клиентский чанк) или в рантайме браузера.

## Решение — тест читает исходник как текст, не собранный бандл

Образец: `apps/domwellbes/src/lib/projects/schedule/schedule-engine-core.browser-safe.spec.ts`.
Архитектурное решение, которое тест защищает, — Р11 в `apps/domwellbes/ROADMAP_GANTT.md`: движок
расписания один на клиент и сервер, чистая логика лежит в `src/lib/projects/schedule/` отдельно
от UI, который её потребляет.

```typescript
const CHECKED_FILES = ['schedule-engine-core.ts', 'types.ts', 'calendar-date-math.ts' /* ... */] as const

const FORBIDDEN_SPECIFIER_PATTERNS: readonly RegExp[] = [
  /^node:/,
  /^@\/lib\/db$/,
  /^@\/lib\/canonical-hash$/,
  /^server-only$/,
  /^@\/generated\/prisma/,
]
```

Тест берёт `readFileSync` по каждому файлу из `CHECKED_FILES`, регуляркой выделяет операторы
`import` (и `from`-форму, многострочную тоже, и side-effect `import 'server-only'`), и падает,
если специфайр совпал со списком запрещённых **и не является `import type`** — типовый импорт
стирается компилятором и не тянет рантайм-зависимость, `export ... from '...'` тоже не считается
(транзитная реэкспортная форма, не создаёт своего рантайм-импорта в этом файле).

## Почему регуляркой, а не AST-парсером

Тест — это конечный список запрещённых специфайров конкретного приложения (свои `@/lib/db`,
`@/lib/canonical-hash`), не универсальный линтер импортов. Регулярка дешева в Vitest без лишней
зависимости на TS-парсер и достаточно надёжна для практических форм импорта, которые реально
встречаются в этом каталоге. Плата за простоту — состав `CHECKED_FILES` держится вручную: новый
файл в каталоге чистой логики не попадёт под проверку сам, пока его не дописали в список.

## Сторож тестирует сам себя

Отдельный `describe` перед проверкой реальных файлов гоняет `extractImportStatements`/
`findForbiddenRuntimeImports` на синтетических строках — находит все пять запрещённых
специфайров разом, не считает запрещённым `import type` того же специфайра, разбирает
многострочный именованный импорт. Без этого блока баг в самой регулярке (например, «схлопнулся»
на многострочном импорте) выглядел бы как пройденная проверка файлов движка — ложная зелень
неотличима от «импортов действительно нет».

## Ограничения

- Не ловит динамический `await import('node:crypto')` — только статические операторы `import`.
- Не ловит утечку через реэкспорт другого локального файла того же каталога, если сам реэкспорт
  не входит в `FORBIDDEN_SPECIFIER_PATTERNS` (транзитивная утечка через `./types` с запрещённым
  импортом внутри `./types` поймается только потому, что `types.ts` тоже в `CHECKED_FILES` — при
  расширении движка новый файл нужно добавлять в список, тест не обходит каталог автоматически).
- Список специфайров — не переиспользуемый экспорт, живёт внутри самого spec-файла; при копировании
  паттерна в другое приложение список нужно переписать под его серверные специфайры (свой путь к
  db-клиенту, свой генератор Prisma и т.д.), `server-only`/`node:*` универсальны.

## Где ещё применимо

Паттерн нужен только там, где один и тот же модуль обязан одинаково исполняться и на сервере,
и в браузере (не «есть client-компонент с расчётами», а именно общий чистый код без дублирования
логики). Проверено по всему монорепо (2026-09-23, `grep` на общие движки/калькуляторы вне
`node_modules`) — второго такого случая сейчас нет: `apps/synth` весь клиентский (Web Audio,
серверной копии логики нет в принципе — сравнивать не с чем), `apps/grandslamcup/src/lib/bracket.ts`
и `swiss-bracket.ts` используются только из server actions, клиентские `bracket-*.tsx` считают
только геометрию раскладки (`bracket-layout.ts`, `use-bracket-positions.ts`), не результат турнира.
Если в другом приложении появится настоящий дубль (движок, который агент решил синхронно
пересчитывать и на клиенте, и на сервере ради превью=результату) — копировать этот спек как
шаблон, не изобретать новый механизм проверки.
