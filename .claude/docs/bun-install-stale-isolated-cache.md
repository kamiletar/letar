# `bun install` не прунит устаревшие isolated-копии в `node_modules/.bun`

**Короткий вывод:** несколько версий одного пакета в `node_modules/.bun` после снятия локального
пина — не признак того, что резолюция зависимостей не схлопнулась. `bun.lock` может резолвить уже
одну версию; обычный `bun install` физические копии старых версий по себе не удаляет. Проверять
факт резолюции — по `bun.lock`, а не по `node_modules/.bun`; чинить лишние копии — `bun install --force`.

## Симптом

Убрали локальный пин версии пакета из `package.json` конкретного приложения (например
`"react": "19.2.3"` в `apps/animatrona-mobile/package.json` и `apps/animatrona-tv/package.json`),
чтобы версия бралась только из корневого `package.json` (`"react": "^19.2.8"`). После обычного
`bun install` в `node_modules/.bun` всё ещё физически лежат несколько версий пакета (в конкретном
случае — 19.2.3/19.2.6/19.2.7/19.2.8 одновременно). Выглядит так, будто снятие пина не подействовало
и резолюция зависимостей всё ещё не сошлась к одной версии.

## Причина

Bun ставит зависимости в изолированном режиме (isolated installs) — `node_modules/.bun` хранит
физически раздельные копии пакета для разных peer-контекстов workspace-члена, а не единую
плоскую версию на всё дерево, как npm/yarn classic. Это устройство хранилища, а не признак
незавершённого резолва.

`bun.lock` при этом может уже резолвить единственную версию пакета — снятие пина сработало
корректно. Но обычный `bun install` (запуск без изменений, влияющих на сам резолв) не гарантирует
прунинг физических копий, ставших неиспользуемыми в `node_modules/.bun`: устаревшие каталоги могут
остаться на диске, даже когда ни один package.json в дереве больше на них не ссылается.

## Диагностика

Не полагаться на `ls node_modules/.bun` как на источник истины о резолюции. Сверять реальный
резолв через `bun.lock`:

```bash
grep -n '"react@' bun.lock
```

Если в выводе одна запись версии пакета (например только `"react@19.2.8"`) — резолюция уже верна,
несмотря на то что `node_modules/.bun` показывает несколько версий на диске.

## Фикс

```bash
bun install --force
```

Принудительно пересобирает `node_modules` с нуля и оставляет на диске только те копии пакета,
которые реально нужны по текущему `bun.lock`.

## ⚠️ `bun install --force` не универсален — иногда нужен полный `rm -rf node_modules`

Фикс выше (`bun install --force`) закрывает случай, когда `bun.lock` уже резолвил верную версию,
а на диске просто остались лишние копии. Но встречается и другой случай, где `--force`
**не помогает вообще**, и решает только полное удаление `node_modules` перед переустановкой.

**Симптом:** `tsc --build` (не `tsgo` — см. ниже) детерминированно падает на конкретной библиотеке
(например `libs/auth`) с ошибкой типов, которая не воспроизводится ни `nx typecheck:tsgo`, ни
`tsc --build` в чистом локальном окружении. Проверка версий пакетов в `node_modules` против
`bun.lock` (`better-auth`, `@better-auth/oauth-provider`, `typescript`) показывает полное
совпадение — расхождения версий нет. Удаление `.tsbuildinfo`/`dist/` (инкрементальный кеш самого
`tsc --build`, отдельный от кеша Nx) тоже не помогает — ошибка воспроизводится идентично.

**Найдено (2026-08-25, s2, деплой `grandslamcup`):** ни `bun install --force`, ни чистка
`.tsbuildinfo`/`dist/`, ни сверка версий по файлам не устранили ошибку. Помог только полный цикл:

```bash
rm -rf node_modules
bun install --frozen-lockfile
```

(255с на удаление + 33с на установку 7449 пакетов). После этого сборка прошла чисто. Что именно
было испорчено в `node_modules` — не установлено; `--force` переустанавливает поверх существующей
структуры, а полный `rm -rf` гарантированно стирает любое повреждённое состояние, которое
`--force` по какой-то причине не затрагивает.

Тот же паттерн независимо подтверждён пользователем на отдельном, более раннем локальном
инциденте: после снятия версийного пина с `better-auth` в `package.json` конкретного приложения
`bun install --force` тоже не привёл `node_modules` в рабочее состояние — потребовалось руками
удалить `node_modules` целиком.

**Вывод:** `--force` — первая попытка (дешевле, быстрее), но если ошибка воспроизводится
детерминированно и версии по всем файлам совпадают — не тратить время на дальнейшую точечную
диагностику, сразу переходить к полному `rm -rf node_modules && bun install --frozen-lockfile`.
Специфично ли это для `better-auth`/`@better-auth/oauth-provider`, или это общий класс
проблемы — не выяснено, оба известных случая касаются именно этого пакета.

⚠️ **Не путать `tsc --build` с `tsgo`.** `nx typecheck:tsgo <app>` использует `tsgo` (быстрый
типчекер) и в этом инциденте не воспроизвёл ошибку вообще — ложноуспокаивающий сигнал. Реальный
таргет, упавший на сервере, — `@letar/auth:typecheck`, который запускает классический
`tsc --build tsconfig.lib.json --emitDeclarationOnly`, часть графа зависимостей `nx build
grandslamcup`. Если приложение на сервере падает, а `typecheck:tsgo` локально зелёный — проверять
именно `tsc --build`, не полагаться на `tsgo`.

## ⚠️ Другой симптом того же класса: верхнеуровневый симлинк пакета вообще отсутствует

**Симптом (2026-09-01, aboi):** `nx typecheck:tsgo aboi` и `nx theme:typegen aboi --skip-nx-cache`
падают на шаге `bunx @chakra-ui/cli typegen` (esbuild) с ~183 ошибками вида
`Could not resolve "@ark-ui/react"` / `"@ark-ui/react/accordion"` и т.д. — все пути резолва внутри
`@chakra-ui/react/dist/esm/*.js`. При этом `ls node_modules/@ark-ui` даёт «No such file or
directory», хотя `ls node_modules/.bun | grep ark-ui` показывает физически скачанные изолированные
копии пакета (в конкретном случае — сразу две версии, `5.37.2` и `5.39.0`). Отличие от основного
случая этого документа: там на диске несколько **лишних** копий при верном резолве в `bun.lock`,
здесь — резолв в `bun.lock` тоже верный (одна версия, `5.39.0`, тянется как зависимость
`@chakra-ui/react@3.37.0`), но верхнеуровневого симлинка на неё в `node_modules/@ark-ui/react` нет
вообще ни одного — тот самый путь, который резолвит `require`/esbuild.

**Причина в этом случае — не устаревший кеш, а прерванный `bun install`.** В рабочем дереве уже
лежал незакоммиченный бамп `@chakra-ui/react` (3.36.1 → 3.37.0: новый файл патча, обновлённый
`patchedDependencies` в корневом `package.json`), то есть кто-то ранее запускал `bun install`,
но он не дошёл до конца. Повторный `bun install` в этой сессии подтвердил механизм — он дважды
падал на постинсталл-скрипте `@letar/animatrona` с:

```
error: EBUSY: resource busy or locked, open '...\node_modules\.bun\ntsuspend@1.0.2\...\win32-x64_lib.node'
```

затем со второй попытки — `ERR_DLOPEN_FAILED` на том же файле («The process cannot access the file
because it is being used by another process»). `ntsuspend` — нативный модуль, который тянет
`@letar/animatrona`; его `.node`-бинарник оказался залочен каким-то процессом на машине (не
электрон — `Get-Process electron` пуст; вероятно один из множества фоновых `node.exe` от других
параллельных агентских сессий на этой же машине, держащий устаревший чекаут пакета). Прямая
проверка через `[System.IO.File]::Open(...)` подтвердила: файл был залочен на момент первых двух
попыток и свободен на третьей — лок оказался временным, не постоянным.

**Диагностика чужого процесса, если EBUSY повторяется:**

```powershell
Get-Process node -ErrorAction SilentlyContinue | ForEach-Object {
  try {
    $mods = $_.Modules | Where-Object { $_.ModuleName -match 'ntsuspend' }
    if ($mods) { Write-Output "PID $($_.Id): $($mods.FileName)" }
  } catch {}
}
```

Точечная проверка лока конкретного файла (без падения всего `bun install` ради диагностики):

```powershell
$path = 'C:\web\letar\node_modules\.bun\ntsuspend@1.0.2\node_modules\ntsuspend\win32-x64_lib.node'
try { ([System.IO.File]::Open($path,'Open','ReadWrite','None')).Close(); 'NOT LOCKED' }
catch { "LOCKED: $($_.Exception.Message)" }
```

**Фикс:** просто повторить `bun install` (без `--force`, без `rm -rf`) — как только сторонний
процесс отпускает файл, установка проходит целиком и восстанавливает пропавший верхнеуровневый
симлинк:

```
bun install
# → "Checked 3596 installs across 3925 packages (no changes)" — не No changes, а полноценный install,
#   пропавшие top-level симлинки (в т.ч. @ark-ui/react) восстанавливаются как часть обычного прогона.
```

Подтверждено зелёным `theme:typegen`/`typecheck:tsgo` не только на `aboi`, но и на `domwellbes` и
`driving-school` — баг был репо-широким (общий `node_modules` в монорепо), а не специфичным для
одного приложения, хотя обнаружился через `aboi`.

⚠️ Если EBUSY/`ERR_DLOPEN_FAILED` на постинсталл-скрипте повторяется стабильно (не разово) —
это не тот же случай: искать конкретный держащий процесс через модульный поиск выше, а не ретраить
`bun install` бесконечно.

## ⚠️ Не путать с реальной лишней зависимостью в дереве

**Симптом (2026-09-03):** три версии `@tanstack/store` в `node_modules/.bun`
(0.7.7/0.11.0/0.11.1) — на первый взгляд похоже на этот класс проблемы. Но `bun.lock` показывал
0.7.7 не как сироту без ссылок, а как реально зарезолвленную транзитивную зависимость: корневой
`package.json` держал неиспользуемый `@tanstack/zod-form-adapter@^0.42.1` (легаси `validatorAdapter`
API TanStack Form до Standard Schema, запрещён правилами `.claude/rules/forms.md` — везде только
`@letar/forms`), который тянул `@tanstack/form-core@0.42.1` → `@tanstack/store@^0.7.0`. Ноль
импортов `zod-form-adapter` во всём репозитории (`git grep` по всем apps/libs).

Это не кеш-артефакт — это была настоящая, хоть и мёртвая, запись в дереве зависимостей. Проверка
по методу этого документа (сверять `bun.lock`, не `ls node_modules/.bun`) как раз и вскрыла
разницу: 0.7.7 была не осиротевшей физической копией, а живым резолвом от реального (хоть и
неиспользуемого) пакета. Фикс — не `bun install --force`, а удаление самой зависимости из
`package.json` + `bun install`. После этого `grep "@tanstack/store" bun.lock` показывает только
0.11.x. Физическая копия 0.7.7 в `node_modules/.bun` при этом может продолжать лежать на диске
даже после `--force` (см. симптом выше) — это ожидаемо и не требует дальнейших действий, раз
`bun.lock` её больше не резолвит.

Побочный эффект: эта же 0.7.7 была причиной невидимого бага в `apps/driving-school` — typecheck
резолвил типы `subscribe()` в старую 0.7 (bare-функция), пока в рантайме бандлилась 0.11
(`{ unsubscribe }`), из-за чего `const unsubscribe = form.store.subscribe(...); return unsubscribe`
падал `TypeError` при размонтировании. Тот же класс бага уже чинили в `libs/forms`,
`libs/admin-ui/src/form-fields/seo-field.tsx` и `apps/aboi` — разбор корневой причины версии
там же, где и здесь.

**Урок:** несколько версий пакета в `node_modules/.bun` — не всегда «прунинг не сработал».
Сначала выяснить по `bun.lock`, реальный это резолв или нет; если реальный — искать, какая
корневая зависимость его тянет (`grep` по `bun.lock` вокруг версии пакета), и не является ли она
сама неиспользуемым легаси, который проще удалить, чем объяснять почему две версии сосуществуют.
