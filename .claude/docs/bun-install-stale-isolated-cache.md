# `bun install` не прунит устаревшие isolated-копии в `node_modules/.bun`

**Короткий вывод:** несколько версий одного пакета в `node_modules/.bun` после снятия локального
пина — не признак того, что резолюция зависимостей не схлопнулась. `bun.lock` может резолвить уже
одну версию; обычный `bun install` физические копии старых версий по себе не удаляет. Проверять
факт резолюции — по `bun.lock`, а не по `node_modules/.bun`; чинить лишние копии — `bun install --force`.

## Симптом

Убрали локальный пин версии пакета из `package.json` конкретного приложения (например
`"react": "19.2.3"` в `apps/animatrona-mobile/package.json` и `apps/animatrona-tv/package.json`),
чтобы версия бралась только из корневого `package.json` (`"react": "^19.2.8"`). После обычного
`bun install` в `node_modules/.bun` всё ещё физически лежат несколько версий пакета (в конкретном
случае — 19.2.3/19.2.6/19.2.7/19.2.8 одновременно). Выглядит так, будто снятие пина не подействовало
и резолюция зависимостей всё ещё не сошлась к одной версии.

## Причина

Bun ставит зависимости в изолированном режиме (isolated installs) — `node_modules/.bun` хранит
физически раздельные копии пакета для разных peer-контекстов workspace-члена, а не единую
плоскую версию на всё дерево, как npm/yarn classic. Это устройство хранилища, а не признак
незавершённого резолва.

`bun.lock` при этом может уже резолвить единственную версию пакета — снятие пина сработало
корректно. Но обычный `bun install` (запуск без изменений, влияющих на сам резолв) не гарантирует
прунинг физических копий, ставших неиспользуемыми в `node_modules/.bun`: устаревшие каталоги могут
остаться на диске, даже когда ни один package.json в дереве больше на них не ссылается.

## Диагностика

Не полагаться на `ls node_modules/.bun` как на источник истины о резолюции. Сверять реальный
резолв через `bun.lock`:

```bash
grep -n '"react@' bun.lock
```

Если в выводе одна запись версии пакета (например только `"react@19.2.8"`) — резолюция уже верна,
несмотря на то что `node_modules/.bun` показывает несколько версий на диске.

## Фикс

```bash
bun install --force
```

Принудительно пересобирает `node_modules` с нуля и оставляет на диске только те копии пакета,
которые реально нужны по текущему `bun.lock`.

## ⚠️ `bun install --force` не универсален — иногда нужен полный `rm -rf node_modules`

Фикс выше (`bun install --force`) закрывает случай, когда `bun.lock` уже резолвил верную версию,
а на диске просто остались лишние копии. Но встречается и другой случай, где `--force`
**не помогает вообще**, и решает только полное удаление `node_modules` перед переустановкой.

**Симптом:** `tsc --build` (не `tsgo` — см. ниже) детерминированно падает на конкретной библиотеке
(например `libs/auth`) с ошибкой типов, которая не воспроизводится ни `nx typecheck:tsgo`, ни
`tsc --build` в чистом локальном окружении. Проверка версий пакетов в `node_modules` против
`bun.lock` (`better-auth`, `@better-auth/oauth-provider`, `typescript`) показывает полное
совпадение — расхождения версий нет. Удаление `.tsbuildinfo`/`dist/` (инкрементальный кеш самого
`tsc --build`, отдельный от кеша Nx) тоже не помогает — ошибка воспроизводится идентично.

**Найдено (2026-08-25, s2, деплой `grandslamcup`):** ни `bun install --force`, ни чистка
`.tsbuildinfo`/`dist/`, ни сверка версий по файлам не устранили ошибку. Помог только полный цикл:

```bash
rm -rf node_modules
bun install --frozen-lockfile
```

(255с на удаление + 33с на установку 7449 пакетов). После этого сборка прошла чисто. Что именно
было испорчено в `node_modules` — не установлено; `--force` переустанавливает поверх существующей
структуры, а полный `rm -rf` гарантированно стирает любое повреждённое состояние, которое
`--force` по какой-то причине не затрагивает.

Тот же паттерн независимо подтверждён пользователем на отдельном, более раннем локальном
инциденте: после снятия версийного пина с `better-auth` в `package.json` конкретного приложения
`bun install --force` тоже не привёл `node_modules` в рабочее состояние — потребовалось руками
удалить `node_modules` целиком.

**Вывод:** `--force` — первая попытка (дешевле, быстрее), но если ошибка воспроизводится
детерминированно и версии по всем файлам совпадают — не тратить время на дальнейшую точечную
диагностику, сразу переходить к полному `rm -rf node_modules && bun install --frozen-lockfile`.
Специфично ли это для `better-auth`/`@better-auth/oauth-provider`, или это общий класс
проблемы — не выяснено, оба известных случая касаются именно этого пакета.

⚠️ **Не путать `tsc --build` с `tsgo`.** `nx typecheck:tsgo <app>` использует `tsgo` (быстрый
типчекер) и в этом инциденте не воспроизвёл ошибку вообще — ложноуспокаивающий сигнал. Реальный
таргет, упавший на сервере, — `@letar/auth:typecheck`, который запускает классический
`tsc --build tsconfig.lib.json --emitDeclarationOnly`, часть графа зависимостей `nx build
grandslamcup`. Если приложение на сервере падает, а `typecheck:tsgo` локально зелёный — проверять
именно `tsc --build`, не полагаться на `tsgo`.
