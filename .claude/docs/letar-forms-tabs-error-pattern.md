# Автопереключение на вкладку с ошибкой в многовкладочной форме

Применим, когда одна `@letar/forms`-форма разбита на несколько `Tabs.Content` (визуальная
группировка длинной формы редактирования), и хотя бы одно обязательное поле живёт не на первой
вкладке.

## Корневая причина

`Tabs.Content` из Chakra UI v3 (Ark UI) по умолчанию монтирует **все** панели сразу —
`lazyMount: false` — и просто скрывает неактивные через CSS, а не убирает их из DOM. Это
дефолт библиотеки, не осознанный выбор конкретной формы. Следствие: поле на неактивной вкладке
всё равно участвует в состоянии формы, в валидации и в черновике `useFormPersistence`. При
неудачном сабмите `Form.Errors` показывает текст ошибки, но не говорит, на какой вкладке её
искать — пользователь видит «есть ошибка» и не видит, где именно.

## Устройство решения

Хук `useFormErrorTab(tabs, defaultTab)`:

1. Переводит `Tabs.Root` в управляемый режим (`value`/`onValueChange` вместо `defaultValue`).
2. Принимает карту «вкладка → список имён полей» (`{ value: string; fields: string[] }[]`).
3. Подписывается на `form.store.subscribe` (`useDeclarativeForm()` из `@letar/forms`); при росте
   `submissionAttempts` ищет по карте первую вкладку, где `fieldMeta` содержит ошибку, и
   переключает на неё активную вкладку.
4. Срабатывает только на попытке сабмита, не на каждое изменение значения — не дёргает активную
   вкладку во время обычного заполнения.

## Единственный текущий пример

`apps/domwellbes/src/app/(admin)/_lib/use-form-error-tab.ts` — используется в трёх формах
редактирования (материал, работа, дом), каждая передаёт свою карту `ERROR_TABS`.

## Статус: не в `@letar/forms`

Проверено по всему монорепо 2026-09-22 (33 файла с `Tabs.Root`, 97 файлов с
`useAppForm`/`useDeclarativeForm`/`createForm`) — ни один другой `Tabs.Root` не оборачивает
единую `@letar/forms`-форму с обязательными полями на разных вкладках. Там, где `Tabs.Root`
соседствует с формой в других приложениях, это либо независимые формы на каждой вкладке
(`apps/domwellbes/.../stock-document-forms.tsx` — четыре разных документа склада, у каждого свои
поля целиком внутри своей вкладки), либо вкладки разделяют разные сущности, а не поля одной формы
(`apps/aboi/.../admin/products/[id]/page.tsx` — «Описание»/«Галерея», вторая вкладка вообще не
форма), либо форма вне `@letar/forms` (`apps/driving-school/.../template-editor-form.tsx`,
`apps/grandslamcup/.../add-player-dialog.tsx` — сырой `useState`).

Паттерн реализован вручную в приложении, не как переиспользуемый компонент библиотеки — на
2026-09-22 у него один клиент (`domwellbes`, три формы). Появится такой же кейс во втором
приложении — не изобретать заново: скопировать хук напрямую (API уже обкатан на трёх формах), а
при третьем применении — оформить запрос `forms-coordinator-dev` на версию для `libs/forms` по
[form-delegation.md](/.claude/rules/form-delegation.md). Нынешняя реализация завязана на
`fieldMeta`/`submissionAttempts` декларативного API (`useDeclarativeForm`) — версия для
библиотеки должна учитывать и headless-API `forms-react`, если у него к тому моменту будет
похожий кейс.

## Смежная ловушка — не только про этот хук

Раз `Tabs.Content` монтирует все панели по умолчанию, **любая** новая многовкладочная
`@letar/forms`-форма в любом приложении наступит на то же — скрытая ошибка валидации — если не
подключит `useFormErrorTab`-подобное решение или явно не включит `lazyMount` (что, в свою
очередь, ломает черновик `useFormPersistence` по полям скрытых вкладок — компромисс, не
бесплатное решение).
