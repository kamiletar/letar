# Кнопка редактирования секции контента, не подключённая к рендеру

## Симптом

Рядом с блоком контента на публичной странице стоит карандаш-кнопка редактирования
(«edit gate»). Клик открывает модалку, в модалке — поля с текущими значениями, сохранение проходит
без ошибок, запись в БД действительно обновляется. Но на самой странице текст остаётся прежним —
тем же, что был захардкожен в JSX изначально.

Ошибки нет нигде: ни в консоли, ни в сети, ни в БД. Модалка честно делает свою работу. Просто
рендерящий компонент эту работу не читает.

## Причина

Компонент-гейт редактирования (кнопка + модалка) и компонент, рендерящий видимый контент, —
это два независимых потребителя одного и того же ключа/группы записей. Их связывает только
визуальное соседство в разметке, а не общий источник данных. Гейт устроен универсально: он умеет
читать и писать любую группу ключей контента, поэтому подключить его к странице — значит просто
поставить его рядом с нужным блоком с правильным именем группы. Ничто не заставляет тут же
проверить, что сам блок вообще запрашивает значения этой группы, а не использует литералы,
написанные до появления системы редактирования.

Типичный сценарий появления: блок контента сначала пишется с захардкоженным текстом (то есть
работает, выглядит готово). Позже добавляется система редактирования секций, и гейт добавляется
рядом «раз уж он есть» — но заменить литералы в JSX на чтение из данных в этот момент забывают,
потому что визуально страница уже и так показывает нужный текст.

## Почему не ловится проверками

- **Типы сходятся.** Гейт типизирован по группе ключей контента в общем виде — компилятору
  неважно, использует ли конкретная страница то, что он читает.
- **Линт молчит.** Нет синтаксической связи между гейтом и JSX-литералами — не за что зацепиться
  правилу.
- **Ручная проверка через клик обманчива в обе стороны.** Открыть модалку, увидеть в ней
  осмысленные текущие значения, закрыть — этого недостаточно: значения в модалке настоящие
  (прочитаны из БД), просто страница их не показывает. А исправить значение и не перезагрузить
  страницу — тоже не покажет расхождения, потому что старый текст и так на месте.
- **Скриншот до/после ничего не скажет**, если проверяющий не знает заранее, какой текст должен
  измениться — до правки и после «непроверенной» правки страница выглядит одинаково.

Обнаруживается только целевой проверкой: изменить значение через модалку и убедиться, что именно
это изменение отразилось на экране — а не полагаться на то, что кнопка рядом с блоком означает
связь с этим блоком.

## Правило

**Наличие кнопки редактирования рядом с контентом — не доказательство, что контент из неё
читается.** Для каждого блока, где стоит edit-гейт, нужно явно проверить связь в обе стороны:

1. Найти, какие ключи/поля гейт умеет писать (group/тип в его пропсах).
2. Грепом по рендерящему компоненту убедиться, что JSX действительно подставляет значения с этими
   ключами, а не литералы:

   ```bash
   rg -n "getContentBlocks|content\[.hero\.|content\[.urgent\." apps/<app>/src/app --glob '*.tsx'
   ```

   Ноль совпадений группы в файле, где стоит гейт с этой группой, — прямой признак разрыва.

3. Живая проверка: поменять значение через модалку → перезагрузить публичную страницу (без кеша,
   см. ниже) → убедиться, что видно именно новое значение, а не то, что было раньше.

## Смежная ловушка: кеширование маскирует и вскрывает баг одновременно

Если рендер страницы кеширован (ISR/`revalidate`), «текст не обновился после сохранения» может
означать любую из двух разных причин:

- контент реально не подключён к рендеру (баг из этого документа);
- контент подключён, но отдаётся из устаревшего кеша.

Не чини вторую причину, не исключив первую: прежде чем менять стратегию кеширования на
`force-dynamic` или сбрасывать кеш, сначала пройди шаг 2 (грep по использованию ключей) — иначе
можно потратить время на настройку инвалидации кеша для блока, который в принципе не читает эти
данные.

## Где ещё искать тот же баг

Класс воспроизводится в любом приложении с системой «редактирование секций контента через общий
ключ/группу вместо отдельной формы на каждое поле» — там разработчик полагается на память о том,
какие компоненты уже переведены на чтение из данных, а какие ещё нет. Кандидаты на проверку —
любой файл, где `ContentGroupEditGate`/аналогичный компонент соседствует с JSX-текстом:

```bash
rg -n "EditGate|EditButton" apps/<app>/src/app/_components --glob '*.tsx' -A3
```

Для каждого совпадения — свериться, что в том же файле выше по коду действительно запрашивается
и используется контент той же группы.
