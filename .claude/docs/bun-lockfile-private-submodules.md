# `bun.lock` и приватные submodule: почему `--frozen-lockfile` не работает

**Короткий вывод:** `bun.lock` этого монорепо описывает дерево **вместе** с приватными
submodule-приложениями. В любом окружении, где submodule не выкачаны, этот lockfile «неверен» по
определению — и любая проверка вида «lockfile совпадает с резолвом» там падает.

## Симптом

```
error: lockfile had changes, but lockfile is frozen
note: try re-running without --frozen-lockfile and commit the updated lockfile
```

Локально при этом всё зелёное: `bun install --frozen-lockfile` проходит без замечаний. Расхождение
выглядит как «lockfile забыли закоммитить», хотя коммитить нечего.

## Механизм

Корневой `package.json` объявляет workspace-глобы `apps/*`, `libs/*`, `libs/shared/*`. Под них
попадают и приватные submodule-приложения — они обычные workspace-члены, ничем не выделенные.

1. `bun.lock` собирается **только** локально, где submodule выкачаны. Значит в нём всегда есть
   записи `apps/aboi`, `apps/driving-school`, `apps/dsperevod`, `apps/domwellbes`,
   `apps/aprel8008`, `apps/poster-microtext-desktop`, соответствующие `*-e2e` — и те транзитивные
   зависимости, которые нужны только им.
2. Окружение без submodule (CI, сервер с неинициализированной частью набора) видит эти каталоги
   пустыми — `package.json` внутри нет.
3. bun считает такого workspace-члена исчезнувшим и убирает его из lockfile. Это и есть «lockfile
   had changes».

Замер на `HEAD` 2026-08-12 (git worktree без submodule + `bun install --lockfile-only`):
diff `bun.lock` = **−236/+47 строк**, все удаления — записи submodule-приложений и их
эксклюзивных зависимостей. Ни одна версия обычного пакета не поменялась.

## Почему чистка lockfile не помогает

Соблазн очевидный: убрать записи приватных приложений из `bun.lock` руками и закоммитить. Так
делалось (`949b81c6`) — и работало ровно **один коммит**.

Первый же локальный `bun install` пересобирает lockfile из фактического дерева, где submodule
есть, и возвращает записи обратно. В августе 2026 это приехало с `f8545c54` (добавили библиотеку
`@letar/forms-vue` — lockfile пересобрался целиком), после чего CI дал восемь красных прогонов
подряд при полностью здоровом коде.

Чистка — это шаг против п.1 механизма, который отменяется штатным действием разработчика. Такой
фикс не держится в принципе, а не «пока не забыли».

## Что делать вместо

**В CI** (`.github/workflows/ci.yml`) — ставить зависимости обычным `bun install`, без
`--frozen-lockfile`. Гарантия «версии те же, что в git» здесь всё равно недостижима, пока
submodule не чекаутятся; флаг давал не гарантию, а стабильно красный прогон.

**На сервере** (`deploy-affected.sh`) — есть фолбэк с `--frozen-lockfile` на обычный `bun install`
плюс диагностика: после фолбэка скрипт печатает `git diff --stat -- bun.lock`. Пустой diff —
расхождение безобидное (те самые отсутствующие workspace-пути), непустой — настоящий дрейф версий,
который нужно смотреть глазами. См. [PLAN-INFRA-3.md §50](/PLAN-INFRA-3.md).

**Общее правило:** любая проверка, сравнивающая lockfile с результатом резолва
(`--frozen-lockfile`, `bun install --dry-run` в пайплайне, будущий lockfile-drift-гейт), обязана
либо выкачивать submodule, либо не запускаться в этом окружении вовсе.

## Как воспроизвести и проверить фикс

Точная модель CI-чекаута — git worktree: он не выкачивает submodule, каталоги остаются пустыми.

```bash
git worktree add --detach /tmp/ci-sim HEAD
cd /tmp/ci-sim && bun install --frozen-lockfile   # воспроизводит падение
bun install --lockfile-only && git diff --stat -- bun.lock   # показывает, что именно уходит
```

⚠️ Каталог worktree создавай **вне** дерева репозитория, иначе Nx подхватит его как часть графа.
На Windows `git worktree remove` может не удалить каталог из-за длинных путей — тогда чистить
руками.
