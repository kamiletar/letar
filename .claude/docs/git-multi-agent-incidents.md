## Дополнение 2026-08-28 (второе за день): неотправленный коммит submodule останавливает деплой ВСЕХ приложений

**Механизм.** Коммит в letar фиксирует submodule указателем на SHA (gitlink, mode `160000`).
Если сам коммит внутри submodule не запушен, а bump SHA в letar — запушен, то любой клон,
тянущий letar, не может выкачать submodule:

```
fatal: remote error: upload-pack: not our ref <sha>
```

На сервере это происходит внутри `git submodule update --recursive` в `deploy-affected.sh` —
то есть **до** выбора приложения. Поэтому встаёт очередь деплоев целиком, включая приложения,
к которым виновный submodule отношения не имеет. Ошибка при этом не называет ни submodule
по-человечески, ни что делать.

**Частота — не гипотеза.** Только за 2026-08-27…28 инцидент повторился минимум пять раз:

- три сообщения deploy-agent-dev в agent-mail (822 «СРОЧНО: непушнутый submodule-коммит
  блокирует ВСЕ деплои», 845, 847) — за один день, каждый раз на новом SHA;
- ночью 2026-08-28 при подготовке push нашлись ещё два: `apps/dsperevod` (`f53b7f2`, `7b992d4`)
  и `apps/svoichuzhie` (`0f3dbef`) были записаны в **уже запушенный** `origin/main`, а самих
  коммитов на их origin не было. Запушены вручную.

**Почему дисциплина не держит.** Правило «сначала push submodule, потом bump SHA в letar»
записано в [.claude/rules/git.md](/.claude/rules/git.md) с самого начала. Но bump обычно делает
**не та** сессия, которая коммитила внутрь submodule: одна сессия закончила работу в
`apps/<app>`, закоммитила и не запушила (push требует одобрения владельца — см. правило
«`git push` — только с одобрения»), а другая позже фиксирует SHA в letar как часть своего
коммита. Ни один существующий барьер этого не видит: scope-guard смотрит на **состав** коммита,
а не на достижимость gitlink, и вообще ничего не знает про origin.

**Барьер (2026-08-28).** `scripts/check-submodule-push-state.sh` + `pre-push` хук
`scripts/hooks/pre-push-submodule-check.sh`, ставится через `scripts/hooks/install.sh`. Проверяет
все gitlink'и отправляемого коммита и блокирует push letar, печатая точную команду push для
каждого отставшего submodule. Аварийный обход — `GIT_ALLOW_UNPUSHED_SUBMODULES=1 git push`
(как у `GIT_ALLOW_MULTI_SCOPE_COMMIT`: не отключает проверку, а превращает блокировку в
предупреждение со списком).

**Почему не штатный `git push --recurse-submodules=check`.** Две причины:

1. Он проверяет только submodule, **изменённые** в отправляемых ревизиях. Второй из ночных
   случаев — SHA уже лежал в `origin/main` и ломал деплой прямо сейчас, ни один текущий push
   его не менял: штатная проверка молчит, наша сообщает и помечает такие строки отдельно
   («этот SHA УЖЕ в origin/main — деплой сломан прямо сейчас, не этим push»).
2. Он сверяется с локальными remote-tracking ветками, а те могут быть устаревшими. Наша
   проверка при подозрении делает реальный `git fetch` и перепроверяет.

**Замеры, из которых выросла двухступенчатость (14 submodule, Windows).**

| Способ                                                        | Стоимость                                    |
| ------------------------------------------------------------- | -------------------------------------------- |
| локальный `git for-each-ref --contains` по всем               | ~2 c суммарно, без сети                      |
| сетевой `git ls-remote` / `git fetch` на один submodule       | ~2.4 c → ~34 c, если гнать по всем           |
| двухступенчато (локально + параллельный fetch подозрительных) | 1.6 c здоровое дерево, ~11 c при 7 проблемах |

Отсюда порядок: быстрый локальный проход → сеть **только** по не подтвердившимся, и все разом
параллельными `git fetch` (разные репозитории, гонки между ними нет). Отдельная мелочь, которая
дала кратный выигрыш на Windows: один `git ls-tree -r` вместо вызова на каждый путь — запуск
процесса стоит ~0.2 c, и 14 лишних вызовов в pre-push заметны на глаз (12 c → 1.6 c).

⚠️ `git ls-remote` как единственный источник правды не годится: он показывает только вершины
веток, а искомый SHA обычно предок вершины. Поэтому `fetch` + `--contains`, а не сравнение с
выводом `ls-remote`.

**Ранняя диагностика на стороне деплоя.** `git submodule update --recursive` в
`deploy-affected.sh` теперь обёрнут проверкой: при падении вызывается
`diagnose_unpushed_submodules()`, которая проходит по gitlink'ам `HEAD`, пробует до-выкачать
каждый и называет те, чьих коммитов нет на origin, — вместо сырого `not our ref` посреди лога.
Барьер на push первичен, эта диагностика — второй эшелон: она нужна для случаев, когда обход
флагом был осознанным или когда сломанный SHA приехал в `origin/main` мимо хука (чужой клон,
`--no-verify`).

**Побочное наблюдение.** Первый же прогон проверки на рабочем дереве 2026-08-28 нашёл **семь**
submodule с неотправленными коммитами одновременно. То есть это не «редкая гонка», а
установившееся фоновое состояние репозитория — деплой в такие моменты не мог пройти в принципе.

## Дополнение 2026-08-28: `git commit -- <каталог>` забрал правку параллельной сессии из рабочего дерева

Коммит `0c55f455` должен был содержать две правки (`PLAN-INFRA-4.md` и один док). В индексе
лежали ровно они — `git diff --cached --name-only` перед коммитом это подтвердил. Но команда была

```bash
git add PLAN-INFRA-4.md .claude/docs/<мой-док>.md
git commit -m "…" -- PLAN-INFRA-4.md .claude/docs      # ← каталог, а не файлы
```

и в коммит уехал третий файл — `.claude/docs/verification-pitfalls.md`, +58 строк, которые в тот
момент писала **другая** сессия (фоновая задача, запущенная отдельным кликом пользователя).

**Механизм — тот же, что у уже описанных здесь граблей, только с другим знаком.**
`git commit -- <pathspec>` берёт содержимое **рабочей копии** по этому pathspec, а не индекса.
Обычно об этом вспоминают в контексте потерь (`git commit -- <путь>` после `git rm --cached`
возвращает файл, см. `git-pathspec-commit-worktree-not-index`). Здесь тот же механизм сработал
на приобретение: каталог в pathspec расширился на все изменённые файлы внутри него, включая
чужой.

**Почему проверка индекса не спасла.** `git diff --cached --name-only` показывает индекс, а
коммит с pathspec индекс частично игнорирует. Эти две вещи расходятся ровно тогда, когда
pathspec шире набора staged-файлов — то есть в самом типичном случае «указал каталог».

**Правило:** в `git commit -- …` перечисляй **файлы**, а не каталоги. Каталог допустим, только
если ты только что убедился, что внутри него нет чужих изменений (`git status --short -- <кат>`),
и понимаешь, что коммитишь рабочую копию. Это ровно то же ограничение, что уже действует для
`git checkout -- <каталог>` (см. дополнение 2026-08-19) — просто раньше оно было записано только
для отката, а не для коммита.

**Проверка после коммита обязательна:** `git show --stat <sha>`. Именно она поймала этот случай
— в статистике оказалось «3 files changed» при двух застейдженных.

**Чем кончилось.** Ничего не потеряно: содержимое чужого файла попало в историю целиком и в
рабочем дереве не тронуто. Откат делать не стали — к моменту обнаружения рабочая копия уже
совпадала с `HEAD`, то есть работа соседней сессии фактически сохранена, просто под чужим
сообщением коммита. Ревертить в такой ситуации хуже, чем оставить: реверт вынул бы чужую работу
из `HEAD` обратно в незакоммиченное состояние, а сессия-владелец к тому времени уже считает файл
сохранённым и второй раз его не закоммитит.

⚠️ Попытка исправить историю аккуратно упёрлась в ещё одну особенность общего чекаута: пока
готовился корректирующий коммит, соседняя сессия успела застейджить свои файлы в **общий индекс**,
и `git commit` без pathspec был заблокирован scope-guard'ом (правильно — иначе забрал бы и их).
То есть «починить индексом» в общем чекауте тоже не всегда возможно. Отсюда следствие: дешевле
не создавать такой коммит, чем потом его разбирать.

### Второй, отложенный эффект того же коммита: мина в индексе

Обнаружен позже, уже сессией-владельцем чужого файла. Автор коммита `0c55f455` его не видел
вообще — после `git add` собственных файлов и коммита с pathspec `git status` для чужого файла
выглядит как обычное «изменён», без единого намёка на проблему.

Механизм: pathspec-коммит взял содержимое из **рабочей копии**, но индекс для этих путей
**не обновил**. Индекс так и остался со старым блобом, а `HEAD` уехал вперёд. Состояние файла
стало `MM`, и `git diff --cached` показывал те самые 58 строк как **удаление**:

```bash
$ git status --porcelain
MM .claude/docs/verification-pitfalls.md

$ git diff --cached --stat -- .claude/docs/verification-pitfalls.md
 .claude/docs/verification-pitfalls.md | 58 +++---------------------------
```

То есть в индексе лежала подготовленная отмена только что закоммиченного раздела. Любой
следующий голый `git commit` (а после чужого pathspec-коммита он вполне вероятен — именно голая
форма остаётся, когда индекс «уже проверен») молча выкинул бы раздел из `HEAD` во второй раз.
Лечится единственным `git add <файл>` — свести индекс с рабочим деревом; направление строго
«рабочее дерево → индекс», `git checkout --`/`git restore` здесь уничтожили бы содержимое.

**Следствие для правил.** Опасность pathspec-коммита с каталогом не заканчивается на самом
коммите. Он оставляет за собой рассинхронизированный индекс, который в общем чекауте достаётся
следующему коммиту — возможно, чужому. Поэтому `git show --stat` после коммита — не
формальность: увидел в статистике лишний файл, сразу `git add` его, не откладывая.

Разбор механизма целиком, со всеми тремя следствиями —
[git-pathspec-commit-worktree-not-index](/.claude/docs/git-pathspec-commit-worktree-not-index.md).

## Дополнение 2026-09-03: `git commit -- <файл>` увёл чужую правку не через каталог, а через совпадение имени файла

Вариант того же механизма, что в дополнении 2026-08-28 выше, но с другой причиной попадания
чужого файла в pathspec. Там расширение было структурным — каталог в pathspec захватил всё, что
внутри него изменено. Здесь pathspec состоял из перечисленных **файлов**, всё по правилу
(«перечисляй файлы, а не каталоги»), и всё равно унёс чужое: один из перечисленных файлов
случайно оказался тем же файлом, который параллельно и независимо правила другая сессия.

**Что произошло.** Сессия `letar-dev` работала над снятием точного пина
`@tanstack/react-devtools` (`PLAN-INFRA-4.md §143`) и по ходу добавила в рабочую копию
`PLAN-INFRA-4.md` абзац «Дополнение 2026-09-03 — рудимент снят» — но коммит этой правки отложила,
пока шли прод-сборки и тесты. Пока абзац лежал незакоммиченным, параллельная сессия закоммитила
не связанную задачу (Service Worker в `libs/hooks`):

```bash
git commit -- PLAN-INFRA-4.md libs/hooks/CHANGELOG.md libs/hooks/README.md \
  libs/hooks/package.json libs/hooks/src/index.ts \
  libs/hooks/src/lib/browser/use-offline-service-worker.ts
```

Результат — коммит `583a468b feat(hooks): useOfflineServiceWorker — общая регистрация/снятие
Service Worker`. `PLAN-INFRA-4.md` в этом pathspec взялся, скорее всего, оттого, что коммитящая
сессия сама что-то в нём писала или просто перечислила через `git status` всё изменённое в
рабочем дереве, не разбирая, что из этого — её. Механизм тот же, что и всегда у
`git commit -- <pathspec>`: команда берёт содержимое **рабочего дерева** по каждому пути в
pathspec, а не только то, что застейджено этой сессией. Абзац про `@tanstack/react-devtools`
уехал в коммит про Service Worker — файл в pathspec совпал не потому, что pathspec был шире, чем
думали, а потому, что оба независимых изменения физически лежали в одном файле.

**Отличие от дополнения 2026-08-28 важно для правила.** Там нарушением была сама форма команды
(каталог вместо файлов) — соблюдение «перечисляй файлы» полностью закрывает тот случай. Здесь
форма была правильной с самого начала, и всё равно не спасла: **любой** общий файл (план,
CHANGELOG, README верхнего уровня) — точка коллизии сама по себе, если две сессии держат в нём
незакоммиченные правки одновременно, независимо от того, как аккуратно каждая из них потом
формирует pathspec. Единственная защита от этого класса — не откладывать коммит готового куска
(см. «коммить сразу после каждого готового куска» в
[.claude/rules/git.md](/.claude/rules/git.md)): чем дольше правка лежит в рабочем дереве
незакоммиченной, тем больше окно, в которое чужой коммит может её подобрать.

**Ничего не потеряно** — как и в 2026-08-28, содержимое корректно оказалось в git-истории, просто
не в «своём» коммите. Откатывать не потребовалось.

**Диагностика: как быстро найти, куда уехала пропавшая с виду правка.** Вместо того чтобы решать,
что работа потеряна, ищи её по содержимому во всей истории, а не только в ожидаемом коммите:

```bash
git log --oneline --all -S'<уникальная фраза из правки>' -- <файл>
```

`-S` (pickaxe) находит коммиты, где число вхождений строки изменилось — то есть коммит, который
её добавил, даже если это коммит с совсем другим по смыслу заголовком. `--all` обязателен: если
предполагаешь, что правка могла уехать через параллельную сессию, у той могла быть своя ветка.
Сработало на этом инциденте быстро и однозначно — предпочтительнее, чем спекулировать по
`git log --oneline` в поисках «похожего» коммита.

## Дополнение 2026-09-03 (второе за день): TOCTOU-гонка между `git diff --cached`-проверкой и `git commit` без pathspec

Третий механизм в этом файле, где чужой файл попадает в коммит, и первый, где виновата не форма
команды (pathspec/каталог), а само **время между двумя отдельными вызовами git**. Найден дважды
подряд в одной сессии документационной работы над `.claude/docs/*` — сессия в этот момент видела
через `ListAgents` порядка 27 одновременных интерактивных сессий в одном и том же чекауте
`C:\web\letar`.

**Что произошло (оба раза одинаково).** Последовательность была ровно та, что рекомендуют
остальные разделы этого файла — проверка перед коммитом, а не вслепую:

```bash
git add <ровно свои файлы>
git diff --cached --stat            # подтверждает: в индексе только свои файлы
git commit -m "..."                 # БЕЗ pathspec — коммитит весь индекс целиком
```

`git show --stat HEAD` после коммита оба раза показал лишние файлы, которых не было на шаге
проверки: первый раз — `bun.lock` и `package.json` (чужой `bun install`), второй раз —
`PLAN-INFRA-4.md` и `PLAN-INFRA.md` (чужая правка плана).

**Механизм.** Индекс — один физический файл (`.git/index`) на весь чекаут, общий для всех
параллельных сессий. `git commit` без pathspec коммитит **состояние индекса на момент своего
вызова**, а не на момент, когда его в последний раз проверяли. Между шагом 2 (`git diff --cached`)
и шагом 3 (`git commit`) прошло несколько секунд — сеть, дисковый I/O, просто время выполнения
инструмента харнесса — и за это окно другая параллельная сессия успела сделать свой `git add` в
тот же индекс. Проверка на шаге 2 была абсолютно честной и правильной в момент, когда её делали;
она просто перестала быть актуальной раньше, чем сработал коммит. Это классический TOCTOU
(time-of-check to time-of-use): **никакая явная проверка индекса перед `git commit` не даёт
гарантии**, если между проверкой и коммитом есть хоть какой-то интервал, а индекс общий.

**Почему это НЕ тот же баг, что pathspec-инциденты выше (2026-08-28, 2026-09-03 первое).** Там
проблема была в форме самой команды коммита — `git commit -- <каталог>` или `git commit --
<файл>`, совпавший по имени с чужим файлом — и она берёт содержимое **рабочего дерева**, обходя
индекс. Здесь коммит был **без pathspec**, то есть работал ровно так, как задокументировано (берёт
индекс целиком) — и именно поэтому «перечисляй файлы, а не каталоги» из тех разделов тут ничем не
помогает: pathspec не участвовал вообще, а гонка произошла на уровне индекса, а не worktree.
Единственное, что здесь общее с прошлыми случаями, — сам факт общего `.git` на всех агентов.

**Recovery — сделан оба раза без потери чьей-либо работы:**

```bash
git reset --soft HEAD~1                    # откатывает коммит, индекс остаётся как был
git restore --staged <чужие файлы>          # убирает их обратно в unstaged, содержимое не трогает
git commit -m "..."                         # тот же коммит, сразу же — без паузы
```

`--soft` принципиален: он трогает только позицию `HEAD` и оставляет индекс нетронутым — ровно то
состояние, которое нужно, чтобы затем точечно снять лишнее через `git restore --staged` (индекс →
не влияет на рабочее дерево) и закоммитить заново. `git reset --hard` здесь недопустим по тем же
причинам, что и везде в этом файле — переписал бы рабочее дерево и мог зацепить то, что другой
агент успел добавить в него за прошедшие секунды.

**Практическая рекомендация — не «добавь ещё одну проверку», а сократи окно.** Дополнительная
проверка перед коммитом не спасает от TOCTOU — она просто сдвигает то же самое окно на несколько
мгновений позже; тот же класс гонки в принципе неустраним лишним `git status`/`git diff --cached`.
Единственный рабочий рычаг — минимизировать время между `git add` и `git commit`: не вставлять
между ними ничего, что тратит время (сетевые вызовы, чтение файлов, размышление вслух между двумя
tool calls), и по возможности отправлять `add` и `commit` подряд, одним блоком инструментов, без
паузы на подтверждение. Диагностика `git diff --cached` перед коммитом всё равно осмысленна (она
ловит ошибки состава со своей стороны — забытый/лишний файл), просто она не защита от параллельной
сессии — эту роль выполняет только `git show --stat HEAD` **после** коммита, и при находке лишнего
— немедленный recovery по рецепту выше, а не смирение с чужим файлом в истории (тот вариант
приемлем только когда откат уже невозможен без риска, см. дополнение 2026-08-28 выше).

## Дополнение 2026-08-19: `git checkout <sha> -- .` стёр чужую незакоммиченную работу

**Прецедент:** агент, правивший дизайн-токены `apps/domwellbes`, коммитил в submodule, где
параллельно работали ещё две сессии (шкала глубины нажатия в теме; логистика L4). Из-за гонки за
общий индекс — чужой коммит подвинул `HEAD` прямо во время его коммита (`fatal: cannot lock ref
'HEAD': is at ... but expected ...`) — агент провёл коммит с `--no-verify`, чтобы не пересобирать
заготовку индекса ещё раз. Затем, чтобы честно закрыть пропущенную проверку, попытался прогнать
pre-commit-хук вручную на файлах уже сделанного коммита:

```bash
git checkout -q 507fbe8 -- .     # ← вот здесь
git add -A src docs
bash .git/modules/apps/domwellbes/hooks/_pre-commit-semgrep.sh
git reset -q
git checkout -q HEAD -- .        # ← и здесь
```

Semgrep отработал с кодом 0 — коммит действительно был чистым. Ценой этого знания стали
незакоммиченные правки третьей сессии в четырёх файлах логистики (`logistics.action.ts`,
`delivery-quote-calculator-form.tsx`, `create-carrier-tariff-form.tsx`, `tariff-labels.ts`) и её
untracked-файл `__repro.ts`.

**Механизм:** намерение было «взять файлы моего коммита». Написано — «взять **всё** из этого
коммита»: pathspec `.` означает весь каталог, а не «те пути, что затронул коммит».
`git checkout <commit> -- <pathspec>` перезаписывает и рабочее дерево, и индекс по всему
pathspec, без вопросов и без бэкапа. Второй вызов, уже с `HEAD`, добил остатки.

**Восстановить не удалось.** `git fsck --lost-found` дал 7 висячих блобов, ни в одном не было
содержимого логистики. Это ожидаемо: висячие объекты остаются только от того, что хоть раз
попадало в индекс (`git add`, `git stash`, прерванный коммит). Чужие правки лежали только в
рабочем дереве, объектов от них в базе не появилось — значит поднять их через git нечем в
принципе. Единственный оставшийся шанс — буфер редактора (`Ctrl+Z`, Local History в панели
Timeline у VS Code), то есть вне git и вне контроля агента.

**Чем этот случай отличался от прежних (на момент инцидента).** Запрет в
[.claude/rules/git.md](/.claude/rules/git.md) был сформулирован как «⛔ `git checkout -- .`» и
подкреплён правилом «откатываешь свои правки — перечисляй файлы, а не каталог». Форма **с
указанием коммита** под буквальный текст запрета не попадала и не блокировалась хуком
`.claude/hooks/validate-bash.js`, который матчил именно голую форму. Субъективно она вдобавок
читается как «безопасная»: раз указан конкретный коммит, кажется, что действие ограничено этим
коммитом. Это неверно — границу задаёт **pathspec**, а коммит только выбирает источник
содержимого.

**Урок для правила:** опасен не синтаксис `--`, а **pathspec-каталог у любой команды, которая
пишет в рабочее дерево**. К тому же классу относятся `git checkout <sha> -- <каталог>`,
`git restore --source=<sha> <каталог>`, `git restore --worktree <каталог>`,
`git checkout <branch> -- <каталог>`. Все они молча заменяют содержимое чужих файлов, попавших в
этот каталог.

**Обновление 2026-08-19 (после инцидента): хук теперь блокирует эти формы.** `validate-bash.js`
расширен — вместо матча голой формы `git checkout -- .` он извлекает каждую инвокацию
`git checkout`/`git restore` в команде и проверяет её pathspec-хвост. Блокируется pathspec,
равный ровно `.` (весь каталог), у любой формы, которая пишет в рабочее дерево:
`git checkout <любой-ref> -- .` (коммит, ветка, `HEAD`, включая голую форму без ref),
`git restore .`, `git restore --worktree .`, `git restore --source=<ref> .` (и вариант с
пробелом `--source <ref>`). Не блокируется точечная работа с одним файлом
(`git checkout <ref> -- <file>`, `git restore <file>`) и `git restore --staged .` без
`--worktree` — она пишет только в индекс, тот же риск-класс, что у уже блокированного
`git reset HEAD`, не в рабочее дерево.

**Урок для практики:** прогонять хук постфактум на файлах уже сделанного коммита в общем чекауте
не нужно и опасно. Если проверка обязательна, она делается на **копии** — `git worktree add` во
временный каталог с нужным коммитом, там прогон, потом `git worktree remove`. Рабочее дерево, где
одновременно живут три сессии, для этого не годится вообще.

**Урок про `--no-verify`:** обход хука выглядел мелким компромиссом ради скорости в гонке, но
породил вторую задачу — «закрыть проверку задним числом», — и уже она стоила чужой работы. Гонка
за индекс решается не обходом хука, а тем же, чем и всё остальное здесь: коммитить мелко и часто,
чтобы окно между `git add` и `git commit` было минимальным.

**Побочное наблюдение 1:** сам разбор не удалось записать через Bash — хук `validate-bash.js`
матчит запрещённую строку в **любом** месте команды, включая текст внутри heredoc. Ложное
срабатывание безобидное (файл пишется редактором), но знать о нём стоит: документировать
запрещённую команду через shell не выйдет.

**Побочное наблюдение 2 — и оно важнее первого.** Пока агент коммитил этот самый разбор, его
собственные два файла (`.claude/docs/git-multi-agent-incidents.md`, `.claude/rules/git.md`) уехали
в чужой коммит `b2122b4d fix(grandslamcup): заменить transition="all" на явный transitionProperty`
— вместе с двумя десятками файлов `apps/grandslamcup`. Сценарий зеркальный к основному инциденту:
там агент затёр чужое, здесь чужой коммит забрал его работу.

Механизм: `git commit` упал на гонке за `HEAD` (`cannot lock ref 'HEAD'`) **после** того, как
хуки отработали, — то есть файлы уже лежали в общем индексе. Через секунды параллельная сессия
закоммитила свой scope. Scope-guard в корне установлен и обязан был это заблокировать
(`.claude` и `apps/grandslamcup` — разные scope), значит был снят флагом
`GIT_ALLOW_MULTI_SCOPE_COMMIT=1`.

Отсюда правило про сам флаг: **`GIT_ALLOW_MULTI_SCOPE_COMMIT=1` снимает единственный барьер, и
всё чужое, что в этот момент лежит в индексе, уезжает в твой коммит молча.** Перед его
использованием обязателен `git diff --cached --name-only` глазами — не «список моих файлов», а
весь индекс целиком. Данные при этом не теряются (содержимое закоммичено), но оказываются под
чужим сообщением и в чужом scope, где их никто не найдёт.

**Фикс 2026-08-19:** `scripts/hooks/pre-commit-scope-guard.sh` теперь не проходит мимо флага
молча. Обнаружив `GIT_ALLOW_MULTI_SCOPE_COMMIT=1` при застейдженных файлах из более чем одного
scope, хук печатает в stderr список этих scope с числом файлов в каждом и явный вопрос «это
осознанно?» — не блокируя коммит (флаг уже дал разрешение, добавлять поверх него ещё один барьер
не нужно). Это не заменяет `git diff --cached --name-only` глазами, а делает риск видимым в
самый момент коммита, а не только по договорённости его проверять.

## Дополнение 2026-08-13: локальная feature-ветка в общем чекауте `main`

**Прецедент:** агент, работавший над `apps/form-docs` (переключатель Framework × Skin, P7 Этап
1), завёл локальную ветку прямо в `C:\web\letar` — `git checkout -b p7-stage1-switcher` — чтобы
собрать проект с реальным (слинкованным) `node_modules`, которого нет в изолированном `git
worktree`. Пока ветка была активна, в этом же каталоге отработал параллельный процесс (похоже на
автоматический бамп submodule `domwellbes` — судя по соседним коммитам `chore: bump domwellbes
submodule`), который переключил `HEAD` обратно на `main`, закоммитил туда своё изменение и следом
сделал cherry-pick. WIP-коммит агента с кодом переключателя едва не ушёл в историю `main`
вперемешку с чужими коммитами.

**Механизм:** в отличие от прежних инцидентов (голый `git commit`/`git add .`, откат по
каталогу), здесь источником риска стал не сам коммит, а **сама ветка**. `.git` в этом
репозитории один на всех агентов — переключение `HEAD` на `p7-stage1-switcher` меняет то, что
видит вообще любой процесс, читающий рабочее дерево в этот момент, не только тот, кто ветку
завёл. Параллельный процесс не был обязан знать о чужой ветке и действовал в предположении «я в
`main`» — что в тот момент было неправдой. `git checkout -b` в общем чекауте — это то же самое,
что и общий индекс при голом `git add .`, только для целого рабочего дерева, а не для одного
коммита.

**Как разобрались:** без потери данных, но не без риска. Порядок действий: `git branch
<recovery> HEAD` **до** любых резких движений — зафиксировали текущее состояние отдельным именем,
на случай если разбор пойдёт не так; затем `git reset --soft origin/main` — вернул `HEAD` и
индекс к последнему известному чистому состоянию upstream, не трогая файлы в рабочем дереве;
затем точечное восстановление нужных файлов агента из `<recovery>`-ветки. Ключевой момент —
именно `--soft`, не `--hard`: `--hard` переписал бы рабочее дерево, стерев в том числе
несвязанные изменения, которые могли успеть накопиться в каталоге от третьих процессов.

**Урок:** ветки — не более безопасная альтернатива голому коммиту, а тот же класс проблемы на
уровень выше. Правило «коммить только своими путями» защищает от смешения в **одном коммите**;
оно не защищает от смешения через **общий HEAD**, если между `checkout -b` и возвратом на `main`
кто-то параллельно менял состояние того же каталога. Вывод закреплён явным запретом в
[.claude/rules/git.md](/.claude/rules/git.md) — не заводить локальные ветки в общем чекауте
`main`, коммитить только напрямую в `main`. Для случаев, где нужна изоляция именно ради реального
`node_modules` (`git worktree` его не даёт — там нет слинкованных зависимостей), рабочей
оказалась связка `git worktree add` + junction/symlink на `node_modules` основного чекаута —
подробности и её пределы там же.

## Дополнение 2026-08-10: барьер стоял не везде, и это было незаметно

Инцидент 2026-08-09 (перемешанные коммиты внутри одного submodule) закрыли командой
`install.sh --all-submodules`. Проверка через год-день показала: хук стоял в 10 submodule из 14.
Не стоял ровно там, где инцидент и произошёл — `apps/studio`, `apps/svoichuzhie`,
`apps/aprel8008`, `apps/poster-microtext-desktop`.

Причина — в самом скрипте: он искал git-dir только по пути `.git/modules/<sm_path>`. Эту форму
создаёт `git submodule update --init`, оставляя в рабочем дереве файл-указатель `.git`. Но
submodule, заведённый обычным `git clone` внутрь `apps/`, держит полноценный каталог `.git` у
себя — такие скрипт молча пропускал со строкой «⚠️ git-dir не найден; submodule не
инициализирован?». Формулировка уводила в сторону: submodule был прекрасно инициализирован.

Починено резолвом через `git -C <path> rev-parse --absolute-git-dir` — git знает обе формы.

**Урок общего свойства:** сообщение «пропущен, вероятно не инициализирован» — это гипотеза
скрипта, а не диагноз. Барьер, установленный «одной командой», нужно проверять по факту его
наличия в целевых точках, а не по успешному выводу установщика. Тот же принцип, что в
[verification-pitfalls](/.claude/docs/verification-pitfalls.md).

## Работа в монорепозитории с другими агентами

⚠️ **КРИТИЧНО:** В этом репозитории могут одновременно работать несколько агентов над разными проектами.

**Прецедент (2026-08-06):** во время уборки накопленных незакоммиченных изменений один агент
вживую поймал гонку — другой агент параллельно делал `git reset`+commit в том же `.git`-каталоге,
`git log`/`reflog` на несколько секунд показывали разное HEAD. Коммиты не потерялись, но был
близкий вызов. Первопричина — не сама параллельность (её не убрать), а то, что несколько агентов
успели накопить часы незакоммиченной работы к моменту, когда кто-то решил всё разом прибрать.
Правило «коммить сразу после готового куска» выше — это и есть основная защита от подобной
гонки: чем короче агент держит изменения незакоммиченными, тем меньше шанс, что чужой коммит
затронет тот же файл в то же окно времени. Полная изоляция через `git worktree` на агента
рассматривалась как альтернатива и отклонена как постоянный режим — добавляет забываемый шаг
мержа обратно в `main` взамен забываемого шага коммита; уместна точечно для рискованных
многофайловых рефакторов, не как дефолт.

**Третий и четвёртый прецедент, тот же день следующей сессии (2026-08-07).** Два параллельных
фоновых агента при бампе SHA submodule выполнили голый `git commit`/`git add` и затянули в свои
коммиты чужие staged-файлы от не связанной с их задачей инфра-сессии (Traefik staging-labels,
`PLAN-INFRA.md` §48 M2): `apps/kami-key-the-landing` уехал в коммит `070d6eb0`, пять
`docker-compose.staging.yml` (archetest/auth-hub/grandslamcup/mandala/time) — в `42f5ac81`.
Данные не потеряны — оба коммита содержат корректный код, просто под чужим commit message — но
письменное правило (уже дважды задокументированное ниже с разбором двух прошлых инцидентов) не
предотвратило третий и четвёртый случай в один день. Вывод: agent'ы физически не перечитывают этот
файл перед каждым коммитом, поэтому вместо третьей попытки усилить формулировку — установлен
технический барьер, см. «Технический барьер: pre-commit scope-guard» ниже.

**Второй прецедент того же дня (2026-08-06), уже с реальной потерей.** Агент, наводивший порядок
с форматированием (переход submodule на собственные `dprint.json`), откатывал ненужные правки
форматтера через `git checkout` по каталогу submodule — и вместе с ними снёс чужую готовую
незакоммиченную работу в `apps/studio`: рабочее дерево оказалось чистым на HEAD, в `git stash`
пусто, в `reflog` никаких новых записей, то есть восстанавливать было нечего. Работу пришлось
писать заново из контекста сессии.

Отсюда два вывода, каждый — отдельная защита:

- **Откатываешь свои правки — откатывай по именам файлов, которые сам менял, а не по каталогу.**
  `git checkout -- <конкретные файлы>` вместо `git checkout .` / `git checkout -- apps/<app>`.
  Форматтер и так знает список изменённых им файлов; каталог целиком забирает и чужое.
- **Перед любым массовым откатом — `git status` и глазами.** Если в выводе есть файлы, которых ты
  не трогал, значит рядом работает кто-то ещё: либо сузь путь, либо спроси владельца. Массовые
  прогоны форматирования по всему репо особенно опасны именно этим — они по своей природе
  затрагивают тысячи файлов и провоцируют «откатить всё разом».

**ЗАПРЕЩЕНО:**

- `git reset HEAD` — сбросит изменения других агентов
- `git reset --hard` — потеряет изменения других агентов
- `git checkout -- .` — откатит изменения других агентов
- `git stash` без явной необходимости — спрячет чужие изменения

**ПРАВИЛЬНЫЙ ПОДХОД:**

```bash
# ✅ Добавляй только свои файлы
git add apps/my-app/

# ✅ Коммить только свои изменения
git commit -m "feat(my-app): описание"

# ❌ НЕ делай reset если видишь чужие файлы в staging
# ❌ НЕ делай git add . в монорепо
```

**Если видишь чужие файлы в `git status`:**

1. Игнорируй их — это работа других агентов
2. Добавляй только свои файлы через `git add apps/<твой-проект>/`
3. Коммить только свои изменения

**Если MCP Agent Mail запущен:**

- Перед редактированием `libs/**` — проверь резервации через `file_reservation_paths`
- Зарезервируй свои файлы при старте сессии

### Технический барьер: pre-commit scope-guard

⚠️ **MCP-инструмент `install_precommit_guard` (Agent Mail) на 2026-08-07 нерабочий** — вызов
возвращает пустой хук (`{"hook": ""}`) и ничего не пишет в `.git/hooks/`. Предупреждение сервера
про «authoritative reservation gate» при конфликте file_reservation — обещание, а не факт: он не
подходит как защита прямо сейчас. Если когда-нибудь начнёт возвращать непустой хук — переоценить
это правило, но не раньше проверки на реальном коммите.

Вместо него — локальный git-хук `scripts/hooks/pre-commit-scope-guard.sh`, установка:

```bash
bash scripts/hooks/install.sh
```

Ставит связку `pre-commit-scope-guard.sh` + `pre-commit-sops.sh` в `.git/hooks/pre-commit`
(подробности шифрования — [secret-manager.md](/.claude/docs/secret-manager.md)). Не требует
переустановки при правках docs — только при изменении самих скриптов в `scripts/hooks/`.

**Что делает:** перед коммитом смотрит `git diff --cached --name-only` и группирует застейдженные
файлы по scope — `apps/<x>`, `libs/<x>`, `infra/<x>`, либо первый сегмент пути для остального
(`.claude`, `PLAN.md` и т.д.). Если файлов из **более чем одного** scope — коммит блокируется с
списком scope и подсказкой (`git reset -- <лишнее>` + `git commit -- <только свои пути>`). Именно
эта проверка поймала бы оба коммита из прецедента выше: `apps/kami-key-the-landing` рядом с чужим
submodule-бампом — два разных `apps/*`; пять `docker-compose.staging.yml` из разных `apps/*` —
пять scope разом.

**Осознанный multi-scope коммит** (bump all submodules, repo-wide format) — явный обход:

```bash
GIT_ALLOW_MULTI_SCOPE_COMMIT=1 git commit -m "..."
```

**Ограничения, о которых надо помнить:**

- Хук стоит только у тех, кто выполнил установку локально — не автоустанавливается для новых
  агентов/клонов, и уже установленный у кого-то старый хук (например только `pre-commit-sops.sh`
  от `cp` по старой инструкции) не обновится сам, нужно перезапустить `install.sh`.
- Ловит только **факт коммита из нескольких scope одновременно** — не отличает «моя чужая правка
  затесалась» от «я осознанно делаю одну логическую multi-app правку». Это и есть причина, почему
  обход существует, а не бесшовный whitelist: явный флаг — тот же принцип, что «коммить только
  явные пути», просто перенесённый на уровень «явно скажи, что это намеренно многоскоуповое».
- Не защищает от того, что чужой файл окажется застейджен **в одном scope** с твоим (например два
  агента одновременно правят разные файлы в одном и том же `apps/<x>`) — это по-прежнему требует
  file reservation через Agent Mail, хук её не заменяет.

## Работа с приватными submodule

Приватные приложения (aboi, driving-school, dsperevod, domwellbes + их e2e и driving-school-db) — это **git submodules**, указывающие на репо `kamiletar/letar-private-*`. Подробнее: [repo-structure](/.claude/docs/repo-structure.md).

### Изменение кода в submodule

```bash
cd apps/driving-school          # внутри submodule
git checkout main               # submodule по умолчанию в detached HEAD
git pull origin main
# ... меняешь код ...
git add . && git commit -m "feat(driving-school): описание"
git push origin main            # пуш в приватный репо

cd ../..                        # назад в letar
git add apps/driving-school     # фиксируем новый SHA submodule
git commit -m "chore: bump driving-school submodule"
git push                        # пуш в публичный letar
```

### Что НЕ делать

- ❌ **НЕ редактируй файлы submodule без `git checkout main`** — изменения попадут в detached HEAD и потеряются при следующем `git submodule update`.
- ❌ **НЕ добавляй пути submodule в корневой `.gitignore`** — Nx уважает gitignore при сканировании проектов и приватные проекты исчезнут из `nx show projects` / `nx affected`. Submodule в Git хранится как gitlink (SHA), физически working tree не закоммитится в родительский репо без `.gitignore` страховки.
- ❌ **НЕ добавляй `src/generated/` в .gitignore submodule** если эта папка раньше была tracked (например, `libs/driving-school-db/src/generated/prisma/` — это типы Prisma, должны быть в репо).

### ⚠️ Два агента одновременно коммитят в ОДИН submodule — scope-guard в корне letar не защищает

Прецедент (2026-08-09, `PLAN-INFRA.md` §69): две параллельные сессии одновременно работали
внутри `apps/aboi` и `apps/svoichuzhie` — оба submodule, оба со своим отдельным `.git`. Архивные
правки одной сессии утекли в чужой коммит другой (например коммит «консолидация
e2e-хелперов гидратации» содержал вперемешку несвязанный код и чужие доки). Содержимое не
потерялось (сверено построчно постфактум), но commit message ввёл в заблуждение о содержимом —
в общем случае это источник потери работы, а не только грязной истории.

Механизм тот же, что описан выше в «Работа в монорепозитории с другими агентами»: голый
`git commit`/`git add .` внутри submodule подхватывает ВСЁ застейдженное в общем индексе —
включая чужую незакоммиченную работу. Разница в том, что **root-репо scope-guard хук эту гонку
не ловит вообще** — submodule виден корню letar только как gitlink (один SHA), сам git-каталог
submodule отдельный и живёт в `.git/modules/apps/<x>/hooks/`, куда установка в корне не
дотягивается.

**Технический барьер:** тот же `pre-commit-scope-guard.sh`, но установленный ВНУТРИ каждого
submodule — `install.sh` уже поддерживает это (`cd apps/<submodule> && bash
../../scripts/hooks/install.sh`, см. комментарий в самом скрипте). Внутри submodule нет
`apps/*`/`libs/*`/`infra/*` префиксов, поэтому скрипт группирует по первому сегменту пути
(`src`, `e2e`, `prisma`, `PLAN.md`, `docker-compose.production.yml` и т.д.) — застейдженные
файлы из двух разных верхнеуровневых путей одновременно блокируют коммит так же, как
`apps/x` + `apps/y` в корне. Массовая установка сразу во все 14 submodule одной командой:

```bash
bash scripts/hooks/install.sh --all-submodules
```

⚠️ Хук по-прежнему ловит только «коммит из нескольких scope одновременно» — не различает
«моя чужая правка затесалась внутри ОДНОГО scope» (два агента правят разные файлы в одном и том
же `src/`). Это не решаемо на уровне git-хука самого по себе; для этого — file reservation ниже.

**Процессный барьер — обязателен, а не опционален, если трогаешь submodule:**
[agent-mail.md](/.claude/rules/agent-mail.md) уже требует `macro_start_session` с
`file_reservation_paths` при начале работы над приложением. Для submodule это не косметика:
`file_reservation_paths` **не блокирует** коммит физически (сервер сообщает о конфликте и всё
равно выдаёт грант — см. agent-mail.md), но это единственный способ УВИДЕТЬ, что кто-то ещё уже
резервировал тот же submodule, до того как начинать работу и заводить чужой код в свою рабочую
копию. Проверяй `fetch_inbox` / резервации по пути `apps/<submodule>/**` перед тем как редактировать
файлы внутри submodule — не только в самом начале сессии, но и если работа в submodule
возобновляется после паузы.

**Push-гонка (кто первый запушил) — отдельная, менее опасная история.** `git push` по
умолчанию отклоняет non-fast-forward — вторая сессия физически не может молча перезаписать
пуш первой. При отказе push: `git pull --rebase origin main` (не `--force`, не `git reset
--hard` на чужой коммит) и повторный push. Инцидент 2026-08-09 — не push-гонка, а
same-working-tree коллизия внутри одного коммита (обе сессии на одной машине делили один и тот
же checkout submodule) — её решает только scope-guard хук и file reservation выше, не push-race
защита.

### ⚠️ Каждому submodule нужен СВОЙ `dprint.json` — они уже заведены, не потеряй при новом

Тот же принцип «корневой конфиг не действует на вложенный независимый git-репозиторий»
применяется не только к `.gitignore`, но и к `dprint.json`. До 2026-08-06 своего конфига не было
ни у одного submodule: `dprint fmt` внутри них поднимался по дереву и подхватывал конфиг летара,
из-за чего форматирование работало только при работе внутри монорепо и молча меняло поведение при
клонировании репозитория в одиночку. Сейчас `dprint.json` есть у всех 14.

**Заводишь новый submodule — клади `dprint.json` рядом с `.gitignore`, до первого `dprint fmt`.**
Образец — любой существующий, например `apps/domwellbes/dprint.json`; он повторяет корневой
летаровский минус монорепо-специфичные `excludes`. Плагины должны быть тех же версий, иначе стиль
разойдётся с остальным репозиторием.

**Заводишь worktree внутри submodule** — добавь его путь в `excludes` этого `dprint.json` до
первого прогона: dprint не различает границы worktree и обойдёт его как обычную директорию.
Стандартный `.claude/worktrees` там уже прописан. Подробности и инцидент, из-за которого это
задокументировано, —
[dprint-worktree-submodule-scope.md](/.claude/docs/dprint-worktree-submodule-scope.md).

### ⚠️ Каждому submodule нужен СВОЙ `.gitignore`

Корневой `.gitignore` монорепо **не действует** на вложенный независимый git-репозиторий.
Submodule видит только собственный `.gitignore`, а его у свежесозданного нет — поэтому первый же
`git add .` внутри него уносит в коммит `node_modules/`, `.next/`, `dist/`, `*.tsbuildinfo`.

Прецедент: `domwellbes` при заведении submodule утащил `dist/tsconfig.tsbuildinfo` в initial commit.

**Заводишь новый приватный submodule — клади `.gitignore` ДО первого `git add`.** Образец — любой
существующий, например `apps/domwellbes/.gitignore`:

```
node_modules/
.next/
next-env.d.ts
out/
dist/
*.tsbuildinfo
.env.local
.env.docker
/coverage
test-results/
playwright-report/
*.log
```

⚠️ `next-env.d.ts` в этом списке не для красоты: файл генерирует сам Next.js, и его содержимое
зависит от режима — `next dev` пишет ссылки на `./.next/dev/types/`, `next build` на
`./.next/types/`. Пока он трекался, каждая сборка меняла его туда-сюда и шумела в `git status`
при деплое. Документация Next 16 требует того же («should not be tracked by version control»),
а корневой `.gitignore` монорепо его уже игнорирует — но на submodule не действует. Вычищен из
шести submodule 2026-08-05; `nx typecheck:tsgo` и `next build` без него работают.

> Обычные (не submodule) приложения монорепо — `apps/archetest`, `apps/kami` и прочие — своего
> `.gitignore` **не требуют**: они часть корневого репо и закрыты его правилами.

### ⚠️ `git commit -- <путь>` после `git rm --cached` возвращает файл

Коммит с pathspec берёт содержимое **рабочей копии**, а не то, что лежит в индексе. Поэтому
последовательность «убрать из индекса → закоммитить по пути» отменяет саму себя:

```bash
git rm -r --cached dist        # удаление подготовлено в индексе
git commit -- .gitignore dist  # ❌ dist добавляется обратно из рабочей копии
```

Правильно — коммитить удаление **без pathspec** (индекс уже содержит только нужное):

```bash
git rm -r --cached dist
git add .gitignore
git commit -m "chore: убрать артефакты сборки из индекса"
```

⚠️ Это единственное законное исключение из правила «коммить только свои пути» (см. ниже
«Работа в монорепозитории»), и оно применимо **только внутри submodule**, где кроме тебя никто
не работает. В корневом репо голый `git commit` заберёт чужие staged-файлы — там сначала
проверь `git status`, а после коммита — `git show --stat`.

### Обновить все submodules до последних коммитов

```bash
git submodule update --remote --recursive
git add .
git commit -m "chore: bump all submodules"
```
