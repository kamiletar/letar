# Chakra v3: кеш `css()` игнорирует порядок ключей → разные классы emotion на сервере и клиенте

## Симптом

В консоли браузера на части страниц:

```
A tree hydrated but some attributes of the server rendered HTML didn't match the client properties.
This won't be patched up.
```

Дифф в сообщении React — ровно одна пара CSS-классов emotion на обычном элементе Chakra:

```
+  className="css-ap60qa"     (клиент)
-  className="css-1rb706t"    (сервер)
```

Оба класса задают **одни и те же** объявления, отличается только их порядок:

```css
.css-1rb706t { color: var(--chakra-colors-fg-muted); font-size: var(--chakra-font-sizes-sm); }
.css-ap60qa  { font-size: var(--chakra-font-sizes-sm); color: var(--chakra-colors-fg-muted); }
```

Визуально разницы нет: правила эквивалентны, конфликтующих свойств в них нет. Ломается только
гидратация — React оставляет серверный `class`, а клиентское правило дополнительно вставляется
в документ и не используется.

## ⚠️ Это НЕ то же самое, что баг Turbopack + Emotion

Похожий на вид дефект разобран в
[nextjs16-turbopack-default-emotion-hydration](/.claude/docs/nextjs16-turbopack-default-emotion-hydration.md):
там `<Global>` Emotion и `<script>` next-themes дают **структурный** мисматч
(«Hydration failed… this tree will be regenerated on the client»), лечится флагом `--webpack`.

Здесь другое:

- сообщение другое — «some **attributes** … didn't match», поддерево **не** пересоздаётся;
- дефект **не зависит от бандлера** — воспроизводится и на `next dev`, и на прод-сборке
  (`next build` + `next start`), под Turbopack;
- `--webpack` не помогает и не имеет отношения к причине.

Не тратьте время на проверку флага бандлера, если дифф — это пара классов `css-*` с одинаковым
набором свойств.

## Причина

`@chakra-ui/react` мемоизирует `css()` (`styled-system/css.js` → `memo(cssFn)`), а ключ кеша
считает `simpleHash` из `utils/memo.js`:

```js
if (type === 'object') {
  const keys = Object.keys(value).sort() // ← ключ НЕ зависит от порядка свойств
  return `o:{${keys.map((k) => `${k}:${simpleHash(value[k])}`).join(',')}}`
}
```

При этом **результат `css()` от порядка зависит**: `walkObject` обходит ключи в порядке вставки,
порядок объявлений доезжает до emotion, а emotion считает имя класса как хеш от сериализованной
строки стилей.

Итого `css({ fontSize: 'sm', color: 'fg.muted' })` и `css({ color: 'fg.muted', fontSize: 'sm' })`
попадают в **одну ячейку кеша**, но дают **разные** имена классов. Кто вызвал первым — тот и
определил результат для обоих вариантов на всё время жизни процесса.

Проверяется в четыре строки:

```js
import { createSystem, defaultConfig } from '@chakra-ui/react'
const s = createSystem(defaultConfig)
s.css({ fontSize: 'sm', color: 'fg.muted' }) // {fontSize, color}
s.css({ color: 'fg.muted', fontSize: 'sm' }) // тоже {fontSize, color} — memo-хит
```

### Почему сервер и клиент расходятся

Кеш — обычный `LRUCache` внутри инстанса system, то есть живёт столько же, сколько JS-процесс:

- **на сервере** это Node-процесс, обслуживающий **все** маршруты и **все** запросы. Достаточно,
  чтобы любая ранее отрендеренная страница один раз вызвала `css()` с этим набором свойств в
  «своём» порядке — и дальше весь процесс отдаёт этот порядок всем страницам;
- **в браузере** кеш свой на каждую загрузку страницы и заполняется в порядке рендера именно
  этой страницы.

Совпадут они или нет — вопрос везения. Отсюда все внешние признаки:

- **«задеты только эти страницы»** — задеты те, чей собственный порядок пропов противоположен
  тому, что успел закешироваться на сервере;
- **«соседняя страница с таким же `<Text>` чистая»** — она просто не рендерила эту комбинацию
  (например, блок в ветке `:` тернарника, которая при текущих данных не выполняется);
- **«откатил свои правки — не ушло»** — правки вообще ни при чём;
- **«на dev есть, на свежем прод-сервере нет»** — dev-процесс живёт часами и успел закешировать
  «неудачный» порядок; холодный прод-процесс закешировал тот же порядок, что считает клиент.
  Прод **не иммунен**: достаточно, чтобы первым отрендерился маршрут с обратным порядком (у
  реального приложения это, например, страница детали, отданная до страницы списка) — и мисматч
  появляется на прод-сборке ровно так же.

Дополнительный источник плавания: `maxSize` кеша — 500 записей, на большом приложении вытеснение
может переигрывать «победителя» уже внутри одного процесса.

### Регрессия 3.29.0

До 3.28.0 включительно ключ кеша считался через `fast-safe-stringify`, то есть **зависел** от
порядка ключей, и коллизии не было:

```js
const key = args.map((v) => stringify(v)).join('|') // 3.28.0 и раньше
```

Проверено распаковкой tarball'ов с npm: 3.2.0 / 3.10.0 / 3.20.0 / 3.28.0 — порядок учитывается,
3.29.0 и всё дальше по 3.36.1 включительно — `Object.keys().sort()`.

## Что НЕ поможет

- **`--webpack` у `next dev`/`next build`** — причина не в бандлере.
- **`suppressHydrationWarning`** — уберёт сообщение, но серверный и клиентский класс так и
  останутся разными.
- **Причесать порядок пропов на «пострадавшей» странице.** Работает ровно до тех пор, пока
  какая-нибудь другая страница не закеширует эту же пару в другом порядке. В одном приложении
  монорепо для единственной пары `fontSize="sm"` + `color="fg.muted"` нашлось 249 мест с одним
  порядком и 78 с обратным — пар свойств много, мест ещё больше, вручную это не удержать.

## Фикс

Ключ кеша обязан различать порядок ключей. В репозитории это сделано патчем зависимости
(`patches/@chakra-ui%2Freact@3.36.1.patch`, подключён через `patchedDependencies` в корневом
`package.json`):

```diff
   if (type === "object") {
-    const keys = Object.keys(value).sort();
+    const keys = Object.keys(value);
     return `o:{${keys.map((k) => `${k}:${simpleHash(value[k])}`).join(",")}}`;
   }
```

Правится и `dist/esm/utils/memo.js`, и `dist/cjs/utils/memo.cjs`. Цена — чуть больше записей в
кеше; корректность важнее.

Патч действует на все приложения монорепо начиная со следующей сборки каждого из них.
При обновлении `@chakra-ui/react` патч придётся пересоздать (`bun patch`) — `patchedDependencies`
привязан к точной версии `3.36.1`.

### ⚠️ Грабля `bun patch` в isolated-раскладке

После `bun patch --commit 'node_modules/@chakra-ui/react'` bun оставляет на месте симлинка
**обычный каталог** с пропатченным пакетом, но **без** его зависимостей. Резолв ломается сразу:

```
Error [ERR_MODULE_NOT_FOUND]: Cannot find package '@emotion/is-prop-valid'
  imported from node_modules/@chakra-ui/react/dist/esm/styled-system/factory.js
```

Обычный `bun install` этого **не** чинит («no changes» — bun считает, что раскладка на месте).
Лечится удалением каталога и повторной установкой:

```bash
rm -rf node_modules/@chakra-ui/react && bun install
```

После этого `node_modules/@chakra-ui/react` снова симлинк в `node_modules/.bun/...`, а сам
store-каталог уже содержит пропатченный `memo.js`.

## Как проверить у себя

Класс `css-*` из диффа React ищется прямо в SSR-ответе — рядом лежит его правило:

```html
<style data-emotion="css 1rb706t">.css-1rb706t{color:…;font-size:…;}</style>
<p class="css-1rb706t">…</p>
```

Если серверное и клиентское правило содержат **один и тот же набор** объявлений в **разном
порядке** — это описанный здесь дефект, а не что-то в коде страницы.

Быстрая проверка «процесс, а не страница»: запросить один и тот же маршрут у долгоживущего
dev-сервера и у только что поднятого прод-сервера. Разные классы у одного маршрута = кеш, а не
разметка.

## Апстрим

Симптом уже приносили в chakra-ui:
[#10730 «Hydration Mismatch Caused by Prop Order in Chakra UI Components»](https://github.com/chakra-ui/chakra-ui/issues/10730)
(3.34.0). Закрыт мейнтейнером как `not_planned` с версией «дело в SSR-обвязке React Router» —
причину тогда не нашли, репро было без разбора. На 3.36.1 (последняя на 2026-08-28) баг живой.

Разбор с причиной, диапазоном регрессии и однострочным фиксом заведён отдельным issue:
[#10952](https://github.com/chakra-ui/chakra-ui/issues/10952) (2026-08-28). Если его примут —
патч из этого репозитория надо будет снять, а не переносить на новую версию.

## Патч прибит к точной версии — и bun об этом молчит

Ключ в корневом `package.json` — `"@chakra-ui/react@3.36.1"`, а сама зависимость стоит по
caret-диапазону `^3.36.1`. Любой bump (`bun update`, `bun update --latest`, `bun add
@chakra-ui/react@latest`, команда `/infra:deps-update`) разводит их, и патч перестаёт
накладываться.

**bun 1.3.14 в этой ситуации не говорит ничего** — проверено эмпирически на песочнице
(PLAN-INFRA-4.md §118):

- `bun install` и `bun update --latest` завершаются кодом 0;
- ни одной строки предупреждения в stdout/stderr;
- файл `patches/*.patch` остаётся на диске, ключ в `package.json` остаётся на месте — в git
  всё выглядит здоровым;
- блок `patchedDependencies` при этом **тихо пропадает из `bun.lock`** — единственный след в
  репозитории, и его легко не заметить в диффе lock-файла на тысячи строк.

Пакет разворачивается стоковым, описанный здесь баг возвращается во все ~30 приложений сразу —
без единой ошибки сборки, lint или typecheck.

Защита — `bun scripts/check-patched-deps.mjs` (шаг чеклиста `/infra:deps-update`, код возврата
1 при расхождении). Скрипт сверяет версию из ключа с версией в `bun.lock` и, если они
разошлись, смотрит в уже установленную (ещё не пропатченную) копию пакета:

- `Object.keys(value).sort()` на месте → патч ещё нужен, скрипт печатает команды `bun patch`
  для пересоздания;
- маркера нет → апстрим, вероятно, принял [#10952](https://github.com/chakra-ui/chakra-ui/issues/10952),
  и патч надо **удалить** вместе с записью в `package.json`, а не переносить на новую версию.

Второй вердикт не окончательный: маркер может пропасть и от рефакторинга, поэтому скрипт просит
сверить `node_modules/@chakra-ui/react/dist/esm/utils/memo.js` глазами. Без установленного дерева
то же самое смотрится через `npm pack @chakra-ui/react@<версия>` и распакованный
`package/dist/esm/utils/memo.js`.
