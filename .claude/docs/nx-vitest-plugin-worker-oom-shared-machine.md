# `nx dev` падает с «Plugin worker "@nx/vitest" exited unexpectedly» — это OOM, не баг воркера

⚠️ Симптом выглядит как нестабильность самого плагина или Windows-специфичная проблема, а на
самом деле это обычный `FATAL ERROR: Reached heap limit — JavaScript heap out of memory` —
просто текст самой V8-ошибки не долетает до пользователя, до него доходит только последствие
(«exited unexpectedly»).

## Симптом

```
NX Failed to process project graph.
An error occurred while processing files for the @nx/vitest plugin (Defined at nx.json#plugins[5]).
  - Plugin worker "@nx/vitest" exited unexpectedly.
```

Через Browser-превью MCP (`nx dev auth-hub`, порт 3014) воспроизводилось 5+ раз подряд:
процесс либо падает за 5–15с, либо висит в «starting» ~50с и падает так же. `nx daemon --stop`
не помогал — следующий запуск тут же повторял ту же ошибку. `nx reset` дополнительно падал с
`EPERM: Permission denied ... .nx\workspace-data` (каталог держит открытым другой процесс).

При этом прямой `nx show projects --with-target=dev` в терминале в тот же момент отработал
без единой ошибки за секунды — см. ниже, почему это не противоречие.

## Корневая причина — подтверждена по логу демона

`.nx/workspace-data/d/daemon.log` печатает полный V8-краш воркера `@nx/vitest` перед строкой
`exited unexpectedly`:

```
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
----- Native stack trace -----
 1: 00007FF7C206B106 node::OnFatalError+1318
 ...
[NX ... Daemon Server] - Failed to forward env to plugin worker "@nx/vitest": Plugin worker "@nx/vitest" exited unexpectedly.
```

Момент краша — `4094.5 (4096.8) MB` перед `Mark-Compact`, что совпадает с дефолтным лимитом
V8 old-space на этой машине (`node -e "console.log(require('v8').getHeapStatistics().heap_size_limit/1024/1024)"` → `4288` МБ). Это настоящий OOM, не таймаут и не сетевая ошибка.

### Почему у воркера дефолтный лимит, а не заданный

`node_modules/nx/dist/src/project-graph/plugins/isolation/isolated-plugin.js` спавнит воркер
голым `child_process.spawn(process.execPath, [...])` без `--max-old-space-size` в `execArgv`.
Единственное, что подмешивается в `env`, — `SWC_NODE_PROJECT` для TS-воркера; сам `env` — это
`{ ...process.env, ... }`, то есть **`NODE_OPTIONS` из окружения, где запущен `nx`, наследуется
воркером как есть**. Значит воркер честно получает дефолтный ~4.3 ГБ лимит, если родитель его
не переопределил, — и это не настраивается никаким флагом `nx`, только через `NODE_OPTIONS`
самого шелла (см. workaround ниже).

### Что именно раздувает heap

`nx.json` регистрирует `@nx/vitest` **дважды**:

```json
{ "plugin": "@nx/vitest", "options": { "testTargetName": "vitest:test", ... } },  // без include — весь воркспейс
{ "plugin": "@nx/vitest", "options": { "testTargetName": "test", ... },
  "include": ["apps/*/{vite,vitest}.config.*", "libs/*/{vite,vitest}.config.*"] }
```

У **первой** записи нет `include` — она матчит `**/{vite,vitest}.config.*` по всему
воркспейсу. Замер на 2026-09-06:

| охват                                                             | `vitest.config.*`/`vite.config.*` |
| ----------------------------------------------------------------- | --------------------------------- |
| только `apps/*`/`libs/*` верхнего уровня (то, что реально нужно)  | 92                                |
| весь репозиторий без `node_modules` и без `.claude/worktrees`     | 206                               |
| весь репозиторий без `node_modules`, `.claude/worktrees` остаётся | 606                               |
| весь репозиторий включая `node_modules`                           | 855                               |

`.nxignore` уже исключает `.claude/worktrees` — обычный `find` его не уважает (тот же класс
ложной тревоги, что в
[verification-pitfalls § grep по копиям репо](/.claude/docs/verification-pitfalls.md)), поэтому
606 и 855 — это верхняя граница «что видит наивный обход диска», не то, что реально попадает в
Nx. Но даже нижняя, честная цифра — **206 файлов** вместо ожидаемых 92 — показывает, что
безусловная (без `include`) регистрация плагина цепляет вложенные `node_modules` внутри
приложений/submodule (bun isolated-linker кладёт `node_modules/.bun/<pkg>/node_modules/<pkg>` —
у каждого пакета своя копия, и часть публикуемых npm-пакетов incidentally шлёт собственный
`vitest.config.ts` для СВОИХ тестов). Каждый такой файл — источник узла графа и записи в
хэш-кеш; на диске это видно по несоразмерному хэш-файлу:

```
.nx/workspace-data/tsc-2568428459166798129.hash        19.9 МБ
.nx/workspace-data/playwright-5186013267177752385.hash 26.0 МБ
.nx/workspace-data/vitest-1551308020969853366.hash     465.7 МБ   ← в 18 раз больше playwright
```

## Отягчающий, но не первопричинный фактор — общая машина под нагрузкой

В момент краша: **305 процессов `node.exe`**, свободно **1.2 ГБ из 32 ГБ RAM**. Это ожидаемо
для этого репозитория — несколько параллельных агентов держат свои dev-серверы и Nx-демоны
(см. `agent-mail.md`, `git.md § Работа рядом с другими агентами`). OOM у V8-процесса определяется
его собственным heap-лимитом, не свободной системной памятью напрямую, — так что перегрузка
машины **не создаёт** этот баг, но:

- делает GC медленнее и с большей вероятностью подводит процесс к лимиту, который в спокойной
  системе он мог бы не набрать за то же время;
- объясняет `nx reset` → `EPERM: .nx\workspace-data` — каталог физически открыт даже не своим
  процессом, а чужим демоном/воркером с другой параллельной сессии;
- объясняет, почему `nx daemon --stop` не спасает: следующий `nx dev` тут же пересоздаёт демон
  и заново гонит тот же дорогой (и падающий) пересчёт графа — сама причина остаётся.

### Почему `nx show projects --with-target=dev` в терминале в тот же момент прошёл

Не противоречие, а разная стоимость операции: `show projects` может обслуживаться уже
посчитанным/частично-кэшированным графом без принудительного полного пересчёта `createNodes`
у всех inferred-плагинов, тогда как `nx dev <app>` требует свежий граф именно для целевого
приложения и с большей вероятностью попадает в путь, который заново гоняет дорогой обход
`@nx/vitest`, особенно сразу после `daemon --stop`/сброса кеша. Одноразовое сравнение в моменте
ничего не доказывает — воспроизводимость важнее (см. `verification-pitfalls`).

## Воркэраунд — поднять heap-лимит воркера через `NODE_OPTIONS`

Рабочее, проверено по исходникам (env форвардится как есть):

```powershell
$env:NODE_OPTIONS = "--max-old-space-size=8192"
nx dev auth-hub
```

```bash
NODE_OPTIONS="--max-old-space-size=8192" nx dev auth-hub
```

Переменная снимается сама с закрытием сессии/вкладки — не тянет побочных эффектов на другие
команды, если не экспортирована в профиль оболочки навсегда.

## Настоящий фикс — не найден и не применён в этой сессии

Симметрично сузить `include` у **первой** регистрации `@nx/vitest` в `nx.json` до тех же
`apps/*/{vite,vitest}.config.*` / `libs/*/{vite,vitest}.config.*`, что и у второй — тогда обе
регистрации перестанут матчить вложенные `node_modules`. Не сделано намеренно: эта регистрация
обслуживает `testTargetName: "vitest:test"` для **всего воркспейса** (в отличие от второй,
скоуп которой — `test` только для приложений/либ верхнего уровня), и сужение `include`
рискует незаметно выключить watch-таргет `vitest:test` там, где он реально нужен за пределами
`apps/*`/`libs/*` верхнего уровня (например у вложенных пакетов внутри `libs/`). Требует
отдельной проверки, кто на этот таргет фактически полагается, прежде чем сужать.

## Что оказалось НЕ причиной

- **Не Windows-специфичный баг worker'а** — сам механизм спавна (`child_process.spawn` без
  `execArgv`) одинаков на всех платформах; Windows тут ни при чём, крашится любой процесс V8
  на любой ОС при достижении дефолтного heap-лимита с таким объёмом входных данных.
- **Не порт 3014 и не Browser-preview MCP конкретно** — ошибка возникает на уровне пересчёта
  графа Nx до старта самого dev-сервера Next.js, воспроизводится с любым способом запуска
  `nx dev` в тот же момент высокой нагрузки.
- **`nx daemon --stop` не «не работает»** — он останавливает демон корректно (проверено), просто
  следующий `nx`-вызов создаёт новый и мгновенно повторяет тот же дорогой пересчёт.
