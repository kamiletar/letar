# Широкий межфайловый флак vitest на реальной БД — root cause и системный фикс

Сводный разбор для случая, когда флак от гонки за общую dev-БД (см. три узких класса ниже)
перестаёт быть редким исключением и начинает задевать заметную долю файлов почти на каждом
полном прогоне. Три уже задокументированных класса — точечные симптомы **одной и той же**
механики раннера:

- [vitest-shared-singleton-row-race.md](/.claude/docs/vitest-shared-singleton-row-race.md) —
  общая singleton-строка настроек.
- [vitest-serializable-transaction-cross-file-flake.md](/.claude/docs/vitest-serializable-transaction-cross-file-flake.md) —
  Postgres SSI 40001 между Serializable-транзакциями разных файлов.
- [hardcoded-unique-lookup-key-test-race.md](/.claude/docs/hardcoded-unique-lookup-key-test-race.md) —
  захардкоженный `@unique`-ключ лукапа внутри функции.

## Симптом (domwellbes, 2026-09-22)

Полный `nx test domwellbes` (392 spec-файла, 2723 теста, реальная Postgres, не моки) флакует
широко: три подряд прогона дали три РАЗНЫХ набора из 7-11 упавших файлов. Ошибки — из разных,
не связанных друг с другом подсистем: FK-violation на вставке/удалении
(`Delivery_warehouseId_fkey`, `NotificationLog_recipientUserId_fkey`,
`ClassifiedListing_houseVersionId_fkey`, `DeliveryLine_orderItemId_fkey`) вперемешку с Postgres
SSI (`40001`, `could not serialize access due to read/write dependencies among transactions`).
Изолированный прогон одного упавшего файла — всегда зелёный.

## Root cause

`vitest.config.mts` не задавал вообще никаких ограничений параллелизма. Vitest 5 по умолчанию
использует пул `forks` с `maxWorkers` = число доступных ядер — **24** на машине, где обнаружен
баг. Все 24 форк-процесса импортируют один и тот же `src/lib/db.ts` с одной и той же
`DATABASE_URL` — ни отдельной схемы, ни отдельной БД на воркер. Из 392 spec-файлов минимум 174
напрямую импортируют `@/lib/db` (реальный нижний предел — транзитивные импорты через
сервис-функции не посчитаны). Это означает: в любой момент полного прогона до ~20 файлов
реально одновременно пишут/читают/удаляют строки в одной Postgres, без единого механизма
изоляции.

При таком масштабе параллелизма даже **узкие** гонки (одна singleton-строка, один
захардкоженный ключ) перестают быть редкостью — а вдобавок обнаружился **четвёртый**,
более широкий класс:

### Новый класс: широкий recipient/role-запрос как псевдо-singleton

`dispatchRoleNotification` (`src/lib/notifications/dispatch.ts`) ищет получателей уведомления
через `prisma.user.findMany({ where: { roles: { hasSome: [...roles] } } })` — **всех**
пользователей с данной ролью в БД на момент вызова, не только тех, что создал текущий тест.
`dispatch.spec.ts` создаёt свой временный `ADMIN`-пользователя, шлёт уведомление роли `ADMIN` и
чистит за собой в `afterEach` — корректно с точки зрения одного файла. Но если **любой другой**
spec-файл в это же окно параллельно создал/содержит своего `ADMIN`-пользователя,
`dispatchRoleNotification` подхватывает его в список получателей и пытается вставить
`NotificationLog` с его `recipientUserId` — а если тот пользователь тем временем удалён
`afterEach`-очисткой своего файла, вставка падает `NotificationLog_recipientUserId_fkey`.

Отличие от `vitest-shared-singleton-row-race.md`: там гонка — за буквально одну строку с
фиксированным `id`. Здесь общий ресурс — не строка, а **множество всех строк, подходящих под
широкий `where`** (`roles: { hasSome: [...] }`), то есть любой тест, создающий пользователя с
той же ролью где угодно в приложении, становится потенциальным участником гонки. Не имеет
точечного фикса без изменения прод-кода `dispatchRoleNotification` (сужать recipient-запрос
тестовым параметром — то же лекарство, что в
[hardcoded-unique-lookup-key-test-race.md](/.claude/docs/hardcoded-unique-lookup-key-test-race.md),
но здесь запрос по ролям — часть реальной продовой семантики, сужать его ради теста нельзя).
`dispatch.spec.ts` — единственный файл, у которого этот класс проявился эмпирически на момент
записи; при возврате к параллельному прогону (см. ниже) он окажется первым кандидатом на
повторный флак.

## Что НЕ является фиксом

Гоняться за каждым из 4-11 файлов по отдельности (добавлять try/finally, сужать lookup) — то,
что уже сделано для трёх узких классов — не масштабируется на 174 DB-файла: это лечение
симптомов одного и того же системного дефекта раннера, а не причины. Новый файл будет флакать
с той же вероятностью, что и уже пофикшенные, до тех пор, пока не тронут сам параллелизм.

## Фикс — `fileParallelism: false` в `vitest.config.mts`

```typescript
test: {
  // ...
  fileParallelism: false,
}
```

При `fileParallelism: false` Vitest переводит `maxWorkers` в `1` — все 392 файла выполняются
последовательно, ни один DB-вызов не пересекается по времени с DB-вызовом другого файла. Это
структурно исключает **все четыре** класса гонки разом (включая ещё не обнаруженные) — не
снижает вероятность, а убирает механизм целиком.

### Замер (2026-09-22, эта же машина — 24 ядра, 392 файла / 2723 теста)

| Конфигурация                    | Длительность | Упавшие файлы / тесты             |
| ------------------------------- | ------------ | --------------------------------- |
| `maxWorkers` по умолчанию (~24) | 129s         | 4 / 8                             |
| `maxWorkers: 4`                 | 262s         | 1 / 2 (`dispatch.spec.ts`)        |
| `fileParallelism: false`        | 762s         | **0 / 0** — воспроизведено дважды |

Ноль падений при полной сериализации — прямое доказательство, что 100% наблюдаемого флака
объясняется параллелизмом раннера, не багом прикладного кода: с ним же самым кодом, тем же
набором тестов, единственная переменная — конкурентность файлов.

### Цена

Полный прогон подорожал с ~2 до ~13 минут. Оценка: приемлемо, т.к. а) приватные submodule (и
`domwellbes` в их числе) не выкачиваются в CI ([repo-structure](/.claude/docs/repo-structure.md)) —
эта команда не на критическом пути CI, только на ручных/агентских полных прогонах; б) разработка
отдельного модуля обычно идёт через прогон одного spec-файла
(`nx test domwellbes -- src/lib/x/y.spec.ts`) — параллелизм полного набора эту петлю не
затрагивает вовсе, там всегда было и остаётся быстро. Сознательный быстрый (но флакующий) полный
прогон — `nx test domwellbes -- --fileParallelism=true` (переопределяет конфиг с CLI).

## Рассмотренные и отклонённые альтернативы

- **`maxWorkers: N` (частичное снижение, не полная сериализация).** Замер показал: сокращает
  число падений примерно пропорционально квадрату отношения воркеров (24→4 дало ~4х меньше
  упавших файлов), но не гарантирует ноль — `dispatch.spec.ts` продолжал падать и при
  `maxWorkers: 4`. Неприемлемо как основной путь для интеграционного набора, где корректность
  важнее скорости; оставлен как возможный компромисс, если `fileParallelism: false` окажется
  слишком медленным на практике — тогда искать минимальное N эмпирически заново.
- **Изоляция БД по воркеру (отдельная Postgres-схема/`search_path` на `VITEST_POOL_ID`).**
  Технически лучший результат (ноль гонок без потери скорости) — Vitest 5 действительно
  прокидывает `process.env.VITEST_POOL_ID` в каждый форк до импорта тестовых файлов, что делает
  идею реализуемой. Отклонено для этого захода как непропорционально дорогое и рискованное:
  требует реплицировать схему БД (`db push`/DDL) на N схем при старте прогона, тронуть общий
  `src/lib/db.ts` (используется и приложением, не только тестами) и проверить совместимость
  `ZenStackClient`+`kysely`+`pg.Pool` с произвольным `search_path`. Кандидат для отдельной задачи,
  если цена `fileParallelism: false` (~13 мин) станет ощутимо мешать.
- **Retry-обёртка на код `40001` на уровне теста.** Отклонено по той же причине, что и в
  [vitest-serializable-transaction-cross-file-flake.md](/.claude/docs/vitest-serializable-transaction-cross-file-flake.md):
  лечит только один из как минимум четырёх классов (SSI), не трогает FK-гонки и новый
  recipient-класс; кроме того `fileParallelism: false` делает retry попросту не нужным — SSI
  40001 физически не может возникнуть без параллельных Serializable-транзакций.
- **Аудит и точечный фикс общих фикстур/singleton-строк.** Не отменяется этим фиксом — уже
  сделанные точечные фиксы (`dispatch.spec.ts`'s R8-паттерн для `pickup-handoff.spec.ts` и т.п.)
  остаются полезны как defense-in-depth и НЕ нужно их отменять, но не масштабируются как
  единственная стратегия на 174 DB-файла.

## Когда применимо

Любое Next.js-приложение монорепо с интеграционными vitest-тестами на реальной (не мокнутой) БД
и без явного ограничения параллелизма в `vitest.config.mts` — не специфично для `domwellbes`.
Проверить перед копированием фикса: `grep -c "fileParallelism\|maxWorkers" vitest.config.mts` в
целевом приложении, и посчитать долю spec-файлов, реально пишущих в БД
(`grep -rl "from '@/lib/db'" src --include="*.spec.ts"`) — если доля заметная (как в
`domwellbes`, ~45%), тот же root cause, скорее всего, применим.
