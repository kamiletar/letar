# Bind mount на «неправильный» cwd — Next.js standalone делает `process.chdir()`

`Dockerfile.production` ставит `WORKDIR /app`, и на первый взгляд `process.cwd()` рантайма
должен быть `/app`. На деле это неверно для standalone-сборки Next.js в монорепо: сгенерированный
`.next/standalone/apps/<app>/server.js` делает `process.chdir()` в свою собственную директорию
при старте (нужно для корректного резолва относительных путей `.next/`, статики и т.п. в
монорепо-раскладке) — то есть реальный `process.cwd()` во время исполнения приложения —
`/app/apps/<app>`, а не `/app`. Разница видна только в рантайме, `WORKDIR` в Dockerfile её не
меняет и не отражает.

## Симптом

`docker-compose.production.yml` монтирует директорию для рантайм-записи по «наивному» пути
(`WORKDIR` + подпапка), приложение пишет туда через `path.join(process.cwd(), 'подпапка')` —
и оба места физически расходятся. Запись при этом **не падает**: путь `process.cwd()/подпапка`
внутри контейнера не существует, `mkdir(..., { recursive: true })` создаёт его прямо в
writable-слое контейнера (владелец — сам процесс приложения, никакого конфликта прав), запись
проходит успешно. Строка в БД (если есть) обновляется как положено — никакой ошибки никуда не
долетает. Файл живёт ровно до следующего деплоя: новый контейнер получает свежий пустой
writable-слой, старые байты пропадают безвозвратно, а бинд-маунт на «неправильный» путь всё это
время указывает на пустую директорию на хосте, которую никто и никогда не трогает.

Найдено 2026-09-15 в domwellbes: `LocalPrivateFileStorage` (`src/lib/private-files/storage-local.ts`)
пишет в `process.cwd()/private-uploads`, а `docker-compose.production.yml` монтировал
`./private-uploads:/app/private-uploads` — то есть ровно в WORKDIR, без поправки на chdir.
Симптом у пользователя: «Файл недоступен для разбора» + отсутствующие превью — `readCleanPrivateFileBytes`
даёт `ENOENT` для файла, который по БД имеет статус `CLEAN` и валидный ключ. Публичная `uploads/`
в том же файле смонтирована ПРАВИЛЬНО (`./uploads:/app/apps/domwellbes/uploads`) — эта поправка
уже была сделана однажды для другого хранилища, но не была перенесена на `private-uploads`,
заведённый позже отдельной сессией.

## Почему это не ловится обычной проверкой

- **Docker-инспекция мимо диагноза.** `docker inspect <container> --format '{{.Mounts}}'`
  показывает бинд-маунт как настроенный и `RW: true` — конфигурация выглядит рабочей. Проблема
  не в том, что монтирование не сработало, а в том, что путь ВНУТРИ контейнера, который
  приложение реально использует, — другой.
- **`docker exec ... pwd` врёт.** Обычная shell-сессия через `docker exec` наследует `WORKDIR`
  образа (`/app`), а не cwd уже запущенного PID 1 — они могут не совпадать, если entrypoint/
  `server.js` меняет cwd себе, но не меняет метаданные образа. Проверять нужно
  `docker exec <container> readlink -f /proc/1/cwd` — это реальный cwd работающего процесса,
  не то, что покажет новый `exec`-шелл по умолчанию.
- **Логи молчат в момент записи.** Ошибка проявляется только при ЧТЕНИИ (`readCleanPrivateFileBytes`
  → `ENOENT`), причём только ПОСЛЕ следующего деплоя — если тестировать «залил → тут же прочитал»
  в рамках одной жизни контейнера, всё работает, потому что запись и чтение используют один и тот
  же (неверный) writable-слой.
- **Простой `chmod`/`chown` директории на хосте не решает проблему** (в отличие от похожего, но
  ДРУГОГО класса — просто ошибочные права владельца на верно указанной директории). Здесь сама
  директория, которую монтирует compose, вообще не та, что видит процесс.

## Диагностика

```bash
# Реальный cwd работающего процесса, а не WORKDIR образа
docker exec <container> readlink -f /proc/1/cwd

# Если ENOENT-ошибки — где приложение реально ищет файл
docker logs <container> --since 1h 2>&1 | grep ENOENT

# Пустая директория с момента создания = бинд-маунт никогда не получал ни одной записи
ls -la <host-path-из-compose>   # mtime не двигается с момента добавления строки в compose
```

## Фикс

Целевой путь монтирования в `docker-compose.production.yml` должен буквально совпадать с тем,
что печатает `readlink -f /proc/1/cwd` + относительный путь, который использует код — не с
`WORKDIR` образа:

```diff
- - ./private-uploads:/app/private-uploads
+ - ./private-uploads:/app/apps/domwellbes/private-uploads
```

Тот же паттерн уже был in-repo как рабочий образец — публичная `uploads/` в этом же файле:
`./uploads:/app/apps/domwellbes/uploads`. Заводишь новую директорию для рантайм-записи в
Next.js standalone-приложении монорепо — сверяйся именно с этой строкой, а не с `WORKDIR`.

## ⚠️ Восстановлению не подлежит

Все файлы, записанные ДО фикса, физически потеряны — они были в writable-слое давно удалённых
контейнеров. Запись в БД (если приложение хранит статус вроде `CLEAN`/successful) переживает
потерю байтов и превращается в «висячую» ссылку — единственный способ узнать масштаб
проблемы — сверить дату создания записи с историей деплоев/образов
(`docker images <app> --format '{{.Tag}}\t{{.CreatedAt}}'`, где тег — короткий хеш коммита
`chore: bump <app> submodule`) и считать битыми все записи старше последнего деплоя, случившегося
до фикса. Пользователю нужно явно сообщить о необходимости перезалить файлы — тихого автоматического
восстановления не существует.
