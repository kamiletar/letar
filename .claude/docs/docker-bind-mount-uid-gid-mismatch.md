# Bind mount на верный путь, но с расходящимся uid/gid — запись падает EACCES

Соседний, но другой класс проблемы, чем [nextjs-standalone-bind-mount-wrong-cwd](/.claude/docs/nextjs-standalone-bind-mount-wrong-cwd.md):
там путь монтирования был неверным (реальный cwd standalone-сборки отличается от `WORKDIR`), и
чинился сам путь в compose. Здесь путь в `docker-compose.production.yml` указывает ровно туда,
куда пишет код — но хостовая директория и рантайм-пользователь контейнера не совпадают по
uid/gid, и права `other` на хостовой директории блокируют запись.

## Симптом

Найдено 2026-09-15 в domwellbes: контейнер `domwellbes-app` не мог писать в bind-mounted
`/home/deploy/letar/apps/domwellbes/private-uploads` на сервере s2. Путь монтирования был
правильным (уже с поправкой на `process.chdir()` standalone-сборки — см. документ выше). В UI —
красный тост с `EACCES: permission denied, open '/app/apps/domwellbes/private-uploads/<hash>'`,
та же ошибка в `docker logs`.

Причина: хостовая директория была `deploy:deploy` (1000:1000), а рантайм-пользователь образа
`nextjs` (стандартный непривилегированный пользователь Next.js-образов на базе `node:alpine`) —
uid 1001, gid 65533 (`nogroup`). uid и gid оба не совпадают ни с владельцем, ни с группой
директории на хосте, поэтому применяются права `other` — `r-x`, без записи.

## Почему это не ловится обычной проверкой

- **Путь монтирования выглядит правильным — и это правда.** `docker inspect` покажет корректный
  бинд-маунт на верный путь, `docker exec <container> readlink -f /proc/1/cwd` совпадёт с тем,
  что ожидается по предыдущему документу. Диагностика того класса ошибки здесь ничего не найдёт —
  путь не сломан, сломаны права.
- **`ls -la` на хосте показывает «нормальные» права `drwxr-xr-x deploy deploy`** — выглядит как
  обычная директория деплой-пользователя, ничего подозрительного на глаз, если не сверять с
  фактическим uid рантайм-пользователя образа.
- **Права `rwx` у владельца/группы директории ничего не говорят о процессе внутри контейнера** —
  Next.js standalone-образы почти всегда запускают процесс не от root (типовой `USER nextjs` в
  `Dockerfile.production`), и этот пользователь имеет к хостовому bind-mount ровно те права,
  которые дают ему uid/gid при сравнении с владельцем/группой/`other` директории на хосте —
  namespace пользователей контейнера здесь роли не играет, bind mount не переписывает uid.

## Диагностика

```bash
# uid:gid рантайм-пользователя ВНУТРИ контейнера
docker exec <container> id
# пример: uid=1001(nextjs) gid=65533(nogroup) groups=65533(nogroup)

# uid:gid директории СНАРУЖИ, на хосте
stat -c '%u:%g (%U:%G)' <host-path>
# пример: 1000:1000 (deploy:deploy)

# Быстрая прямая проверка — короче, чем сверять числа руками
docker exec <container> sh -c 'touch <path>/testwrite && rm <path>/testwrite'
# EACCES здесь при заведомо ВЕРНОМ пути монтирования — это именно класс "uid/gid mismatch",
# не класс "неправильный путь" (тот дал бы success — запись тихо уйдёт в writable-слой
# контейнера, а не ENOENT/EACCES)
```

Отличить от класса «неправильный путь монтирования» одной командой: там `touch` внутри
контейнера **успевает пройти** (директория существует локально в writable-слое, просто не та,
что на хосте) — там ошибка проявляется позже, на чтении после следующего деплоя. Здесь `touch`
падает EACCES сразу, в момент диагностики.

## Фикс

```bash
# от root на хосте — привести владельца хостовой директории к uid:gid рантайм-пользователя образа
chown -R 1001:1000 /home/deploy/letar/apps/domwellbes/private-uploads
```

Число gid здесь — не gid контейнера (`65533`/`nogroup`), а gid хостового `deploy`-пользователя
(`1000`), чтобы деплой-пользователь сохранял доступ к тем же файлам для бэкапов/обслуживания;
для записи важен только uid. Проверять фиксом, а не предположением — живым тестом внутри
контейнера:

```bash
docker exec <container> sh -c 'touch <path>/testwrite && cat <path>/testwrite > /dev/null && rm <path>/testwrite && echo OK'
```

## ⚠️ Повтор 2026-09-23: фикс руками не переживает новый сервер и новые подкаталоги

Разовый `chown` от 2026-09-15 закрыл только `private-uploads` на s2. Через неделю та же ошибка
всплыла дважды:

- **Staging на новом s1** (разнос s3, 2026-09-18): checkout заведён заново от `deploy`, и
  `uploads/` + `private-uploads/` снова стали 1000:1000. В e2e это выглядело не как ошибка прав, а
  как 15 «продуктовых» падений: после выпуска КП статус «Выпущено» не появлялся, потому что PDF
  не записывался. Причину выдали только `docker logs <app> | grep EACCES`.
- **Прод на s2**: `private-uploads` был исправлен, но все подкаталоги `uploads/*` (картинки
  каталога, портфолио, блог) остались 1000:1000. Загрузка картинок из админки прода была
  сломана, и никто не жаловался, потому что ею ещё не пользовались.

Вывод: проверять **весь** смонтированный каталог рекурсивно, не только тот, где упало, и
перепроверять после переезда checkout на новый сервер. Однострочная проверка всех подкаталогов:

```bash
docker exec <container> sh -c 'for d in /app/apps/<app>/uploads /app/apps/<app>/uploads/* /app/apps/<app>/private-uploads; do [ -d "$d" ] && (touch "$d/.w" 2>/dev/null && rm "$d/.w" && echo "ok $d" || echo "FAIL $d"); done'
```

Если e2e на новом стенде массово падает на шагах, которые пишут файл (выпуск документа, загрузка),
сначала `docker logs --since 20m <app> | grep -i eacces`, потом разбирать тесты.

Разовый обход всех запущенных контейнеров на s1 и s2 (скрипт — в «Разовом аудите» ниже) сразу
после ручного фикса нашёл ещё **4 прод-приложения на s2** с тем же дефектом в `uploads/`: у трёх
каталог `deploy:deploy` (1000:1000), у одного — `root:root` (каталога не было к первому
`compose up`, и Docker создал его сам от root). EACCES в их логах за 30 дней — ноль: дефект
скрытый, туда просто никто не загружал. Ручной фикс по одному каталогу не масштабируется —
каталоги заводятся заново на каждом сервере, в каждом новом приложении и bind-mount. Поэтому шаг
теперь в самом деплое.

## Автоматический фикс: `scripts/ensure-writable-mounts.sh` (с 2026-09-23)

Шаг вызывается перед rollout в обоих путях деплоя — `deploy-affected.sh` (локальный деплой,
staging на s1) и `scripts/deploy-release.sh` (релиз на s2 образа, собранного на s1):

```bash
scripts/ensure-writable-mounts.sh <каталог приложения> <compose-файл> <образ>
```

1. Разбирает compose-файл: берёт **только сервис `app`** и только относительные bind-mount
   (`- ./X:/путь`, в том числе в кавычках), пропуская `:ro` и закомментированные строки.
   Сервисы `db`/`redis` не трогает — у postgres свой uid, чужой `chown` сломал бы БД.
2. `mkdir -p` каждого каталога от `deploy` — чтобы его не создал сам `compose` от root.
3. Запускает одноразовый контейнер **из образа самого приложения** с `--user 0:0` и там
   `find ! -user <uid> -exec chown <uid>:<gid deploy> {} + -exec chmod ug+rwX {} +`. uid берётся
   по имени из `Config.User` образа и резолвится внутри образа — 1001 в скрипт не зашит. Образ
   уже локальный, поэтому ничего не тянется из сети (alpine с Docker Hub доступен не везде).
   `find ! -user` трогает только чужие объекты: повторный деплой почти бесплатен даже на
   тысячах картинок.
4. Проверяет запись вторым контейнером **от пользователя образа по умолчанию** — ровно так, как
   будет писать приложение.

Образ без `USER` (или `root`, как у `dashboard`) — шаг ничего не делает. Не прошла проверка
записи — деплой приложения **останавливается** (`FAILED_APPS` / `die` в release-фазе), а не
пишет предупреждение: старый контейнер пишет в тот же каталог и сломан так же, а предупреждения
в логе деплоя за полгода не прочитал никто.

Почему не `sudo chown`: деплой бежит от `deploy` без sudo (см. `server-provision`), а доступ к
Docker у него есть — root внутри одноразового контейнера меняет владельца на хосте через
bind-mount.

⚠️ **Первый релиз на s2 после коммита фикса пройдёт ещё без шага**: forced-command запускает
`deploy-release.sh`, который сам делает `git pull`, но уже прочитанная `main` — старая. Шаг
заработает со второго релиза приложения. Нужно раньше — прогнать скрипт руками от `deploy`.

⚠️ **Не покрывает `user:` в compose**: скрипт смотрит на `Config.User` образа. Если сервису `app`
когда-нибудь переопределят пользователя в compose — учти это в скрипте.

⚠️ **Обратная сторона: после `chown` пишущий с хоста `deploy` получает EPERM на `copyFile`.**
Шаг отдаёт файлы uid контейнера, группе `deploy` оставляет запись (`ug+rwX`). Открыть такой файл
на запись `deploy` может, но `fs.copyFile` Node после копирования вызывает `fchmod` целевого
файла, а менять права чужого файла нельзя даже при праве на запись. Сид domwellbes (`nx db:seed`
на хосте после деплоя) копировал фото в `uploads/` и падал с `EPERM ... copyfile` при каждом
повторном деплое с `seed: true`. Деплой при этом зелёный: в логе только
`⚠️ Seed failed for <app> (deploy succeeded)`, а всё, что сид делал после упавшего шага, не
досеяно (2026-09-23). Код, который пишет в смонтированный каталог с хоста, пишет через
`readFile`/`writeFile`, не через `copyFile`/`chmod`/`utimes`. После деплоя с сидом проверяй
строку `Seed failed` в логе (`deploy_status` с `grep`), а не только `exitCode`.

### Разовый аудит всех приложений

```bash
# на сервере от root: все RW bind-mount в apps/*, проба записи изнутри контейнера
for c in $(docker ps --format '{{.Names}}'); do
  docker inspect "$c" --format '{{range .Mounts}}{{if and (eq .Type "bind") .RW}}{{.Source}}|{{.Destination}}{{"\n"}}{{end}}{{end}}' \
  | grep '^/home/deploy/letar/apps/' | while IFS='|' read -r src dst; do
    [ -z "$src" ] && continue
    docker exec "$c" sh -c "f='$dst/.w-probe-\$\$' && touch \"\$f\" && rm \"\$f\"" >/dev/null 2>&1 \
      && echo "OK      $c $dst" || echo "EACCES  $c $dst"
  done
done
```

## ⚠️ Общий класс, не специфика domwellbes

Любой bind-mounted volume, требующий записи из контейнера (не только `private-uploads` —
`uploads/`, каталоги кешей, каталоги экспортов), подвержен этой же ловушке при первом заведении:
дефолтный `chown` для новой директории на хосте — это владелец, создавший её вручную (обычно
`deploy`), а не uid непривилегированного пользователя, под которым фактически бежит образ
приложения. Заводишь новый bind-mounted каталог для записи — сразу проверяй uid/gid совпадением
с `docker exec <container> id`, не полагайся на то, что «директория существует и доступна
`deploy`-пользователю по SSH» само по себе означает доступность на запись изнутри контейнера.

С 2026-09-23 относительные bind-mount сервиса `app` готовит сам деплой
(`scripts/ensure-writable-mounts.sh`, см. выше). Руками проверять осталось то, что он не видит:
абсолютные пути (`/home/deploy/...:/...`), long-syntax `volumes` и сервисы кроме `app`.
