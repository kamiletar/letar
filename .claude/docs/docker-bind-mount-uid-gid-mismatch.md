# Bind mount на верный путь, но с расходящимся uid/gid — запись падает EACCES

Соседний, но другой класс проблемы, чем [nextjs-standalone-bind-mount-wrong-cwd](/.claude/docs/nextjs-standalone-bind-mount-wrong-cwd.md):
там путь монтирования был неверным (реальный cwd standalone-сборки отличается от `WORKDIR`), и
чинился сам путь в compose. Здесь путь в `docker-compose.production.yml` указывает ровно туда,
куда пишет код — но хостовая директория и рантайм-пользователь контейнера не совпадают по
uid/gid, и права `other` на хостовой директории блокируют запись.

## Симптом

Найдено 2026-09-15 в domwellbes: контейнер `domwellbes-app` не мог писать в bind-mounted
`/home/deploy/letar/apps/domwellbes/private-uploads` на сервере s2. Путь монтирования был
правильным (уже с поправкой на `process.chdir()` standalone-сборки — см. документ выше). В UI —
красный тост с `EACCES: permission denied, open '/app/apps/domwellbes/private-uploads/<hash>'`,
та же ошибка в `docker logs`.

Причина: хостовая директория была `deploy:deploy` (1000:1000), а рантайм-пользователь образа
`nextjs` (стандартный непривилегированный пользователь Next.js-образов на базе `node:alpine`) —
uid 1001, gid 65533 (`nogroup`). uid и gid оба не совпадают ни с владельцем, ни с группой
директории на хосте, поэтому применяются права `other` — `r-x`, без записи.

## Почему это не ловится обычной проверкой

- **Путь монтирования выглядит правильным — и это правда.** `docker inspect` покажет корректный
  бинд-маунт на верный путь, `docker exec <container> readlink -f /proc/1/cwd` совпадёт с тем,
  что ожидается по предыдущему документу. Диагностика того класса ошибки здесь ничего не найдёт —
  путь не сломан, сломаны права.
- **`ls -la` на хосте показывает «нормальные» права `drwxr-xr-x deploy deploy`** — выглядит как
  обычная директория деплой-пользователя, ничего подозрительного на глаз, если не сверять с
  фактическим uid рантайм-пользователя образа.
- **Права `rwx` у владельца/группы директории ничего не говорят о процессе внутри контейнера** —
  Next.js standalone-образы почти всегда запускают процесс не от root (типовой `USER nextjs` в
  `Dockerfile.production`), и этот пользователь имеет к хостовому bind-mount ровно те права,
  которые дают ему uid/gid при сравнении с владельцем/группой/`other` директории на хосте —
  namespace пользователей контейнера здесь роли не играет, bind mount не переписывает uid.

## Диагностика

```bash
# uid:gid рантайм-пользователя ВНУТРИ контейнера
docker exec <container> id
# пример: uid=1001(nextjs) gid=65533(nogroup) groups=65533(nogroup)

# uid:gid директории СНАРУЖИ, на хосте
stat -c '%u:%g (%U:%G)' <host-path>
# пример: 1000:1000 (deploy:deploy)

# Быстрая прямая проверка — короче, чем сверять числа руками
docker exec <container> sh -c 'touch <path>/testwrite && rm <path>/testwrite'
# EACCES здесь при заведомо ВЕРНОМ пути монтирования — это именно класс "uid/gid mismatch",
# не класс "неправильный путь" (тот дал бы success — запись тихо уйдёт в writable-слой
# контейнера, а не ENOENT/EACCES)
```

Отличить от класса «неправильный путь монтирования» одной командой: там `touch` внутри
контейнера **успевает пройти** (директория существует локально в writable-слое, просто не та,
что на хосте) — там ошибка проявляется позже, на чтении после следующего деплоя. Здесь `touch`
падает EACCES сразу, в момент диагностики.

## Фикс

```bash
# от root на хосте — привести владельца хостовой директории к uid:gid рантайм-пользователя образа
chown -R 1001:1000 /home/deploy/letar/apps/domwellbes/private-uploads
```

Число gid здесь — не gid контейнера (`65533`/`nogroup`), а gid хостового `deploy`-пользователя
(`1000`), чтобы деплой-пользователь сохранял доступ к тем же файлам для бэкапов/обслуживания;
для записи важен только uid. Проверять фиксом, а не предположением — живым тестом внутри
контейнера:

```bash
docker exec <container> sh -c 'touch <path>/testwrite && cat <path>/testwrite > /dev/null && rm <path>/testwrite && echo OK'
```

## ⚠️ Общий класс, не специфика domwellbes

Любой bind-mounted volume, требующий записи из контейнера (не только `private-uploads` —
`uploads/`, каталоги кешей, каталоги экспортов), подвержен этой же ловушке при первом заведении:
дефолтный `chown` для новой директории на хосте — это владелец, создавший её вручную (обычно
`deploy`), а не uid непривилегированного пользователя, под которым фактически бежит образ
приложения. Заводишь новый bind-mounted каталог для записи — сразу проверяй uid/gid совпадением
с `docker exec <container> id`, не полагайся на то, что «директория существует и доступна
`deploy`-пользователю по SSH» само по себе означает доступность на запись изнутри контейнера.
