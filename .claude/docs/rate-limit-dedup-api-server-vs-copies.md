# Rate limiting — `@letar/api-server` вместо своей копии

`libs/api-server`'s `createRateLimiter` (sliding window, in-memory, whitelist/blacklist,
кастомные лимиты) — единственная рекомендуемая in-process реализация rate limit в монорепо.
Не переизобретай `Map<string, {count, resetAt}>` или массив таймстампов внутри приложения —
проверь сначала, нет ли уже готового экземпляра здесь.

## Аудит 2026-09-27

Найдено две самодельные копии одного и того же паттерна (in-memory sliding/fixed window по
ключу):

- **`apps/dashboard/src/lib/rate-limit.ts`** — не имела ни одного вызывающего кода нигде в
  приложении (`checkRateLimit`/`resetRateLimit`/`cleanupRateLimits` не импортировались). Мёртвый
  код, оставшийся, судя по докстрингу («для продакшена рекомендуется Redis»), от раннего наброска
  защиты API-роутов, так и не подключённого. Удалена вместе с неиспользуемой константой
  `RATE_LIMIT` из `apps/dashboard/src/lib/constants.ts` — не мигрировалась, мигрировать было
  нечего.
- **`apps/dsperevod/src/lib/file-upload/rate-limit.ts`** — использовалась единственным вызывающим
  кодом (`POST /api/uploads`, публичный анонимный аплоад файлов к заявке `/zakaz/`). Контракт уже
  был узким (`checkUploadRateLimit(key): boolean`), поэтому мигрирована без изменения вызывающего
  кода: внутри теперь `createRateLimiter({ windowMs: 3600000, maxRequests: 15 })` из
  `@letar/api-server`, обёртка сузила его `RateLimitResult` до булева `allowed`. `@letar/api-server`
  добавлен в реальные `dependencies` (было только в `implicitDependencies` — симлинк в
  `node_modules` для bun без этого не создаётся, см.
  [libs.md](/.claude/rules/libs.md#подключение-к-приложению)), `bun install` прогнан.

## ⚠️ Исключение — `apps/svoichuzhie/src/lib/redis.ts`'s `checkRateLimit`

**Не мигрировать.** Другое требование, не дублирование: реализация на Redis `INCR`+`EXPIRE`,
персистентная между рестартами процесса и (потенциально) между несколькими инстансами одного
приложения. `createRateLimiter` — in-memory, состояние живёт в процессе и обнуляется при рестарте
контейнера; для одноинстансных приложений это осознанный компромисс (см. докстринг
`dsperevod`'s обёртки), для `svoichuzhie` разработчик сознательно выбрал персистентность. Два
разных набора требований, не копия одного и того же кода.

## Когда своя in-memory копия оправдана

Практически никогда для нового кода — `createRateLimiter` покрывает стандартный случай
«ограничить публичный эндпоинт по IP/ключу в рамках одного процесса». Пиши свою реализацию,
только если нужна персистентность между рестартами/инстансами — тогда это Redis-паттерн
`svoichuzhie`, не ещё одна in-memory `Map`.
