# Корзина и заказы — общий паттерн для e-commerce приложений

> Не привязан к конкретному приложению. Несколько магазинов в монорепо независимо приходили
> к одному и тому же набору решений — этот документ фиксирует паттерн заранее, чтобы следующий
> магазин не проходил тот же путь с нуля (см. `PLAN-INFRA.md` §29).

## Когда это нужно

Как только у приложения появляется `Cart`/`Order` с реальными деньгами и хотя бы намёк на то,
что товары могут редактироваться или исчезать после того, как на них уже оформлен заказ.
Простейший случай (один товар без вариантов, цена не меняется задним числом) может обойтись
минимальной моделью — см. пример ниже. Разрастание начинается, когда добавляются варианты
товара (размер/формат/цвет) или когда встаёт вопрос «а что если товар из старого заказа удалят».

## 1. Вариант товара — отдельная модель, не поле

Если у товара больше одного покупаемого варианта (размер, формат, комплектация) — заводи
`ProductVariant` как отдельную модель с собственным `id`, а не набор полей на `Product` или
enum на `OrderItem`. Корзина и заказ ссылаются на `variantId`, а не на комбинацию полей.

```zmodel
model Product {
  id       String           @id @default(cuid())
  name     String
  variants ProductVariant[]
}

model ProductVariant {
  id        String  @id @default(cuid())
  productId String
  product   Product @relation(fields: [productId], references: [id])
  label     String  // "A4", "50×70 см" и т.п. — что показывается покупателю
  price     Int     // копейки — у вариантов может быть разная цена
}
```

**Почему не enum/поле на товаре:** у enum нет своего `id`, на который можно сослаться из
`CartItem`/`OrderItem` — а без стабильной ссылки нельзя корректно посчитать «сколько раз купили
именно этот вариант» и негде вешать снэпшот (см. п. 2).

## 2. Снэпшоты в `OrderItem` — заказ не должен зависеть от текущего состояния каталога

`OrderItem` копирует к себе то, что покупатель увидел на момент оформления: имя товара/варианта,
картинку, цену. Не читает их каждый раз из `Product`/`ProductVariant` через relation.

```zmodel
model OrderItem {
  id        String   @id @default(cuid())
  orderId   String
  order     Order    @relation(fields: [orderId], references: [id])

  // Ссылки — nullable и SetNull при удалении, а не Cascade/Restrict
  productId String?
  product   Product? @relation(fields: [productId], references: [id], onDelete: SetNull)
  variantId String?
  variant   ProductVariant? @relation(fields: [variantId], references: [id], onDelete: SetNull)

  // Снэпшот — то, что покупатель реально видел и оплатил
  nameSnapshot  String
  imageSnapshot String?
  priceSnapshot Int      // копейки, на момент заказа — НЕ текущая цена товара

  quantity Int
}
```

**Зачем именно так:**

- Если карточку товара отредактируют (переименуют, поменяют цену, перезальют фото) — старые
  заказы в истории покупателя и в админке не должны задним числом «переписаться». Покупатель
  увидит именно то, что купил.
- `productId`/`variantId` **nullable** с `onDelete: SetNull` — потому что товар из старого заказа
  может быть снят с продажи или удалён (см. п. 4), а сам факт покупки должен остаться в истории.
  Жёсткая ссылка (`Restrict`/обязательное поле) заблокировала бы удаление товара, пока жив хоть
  один заказ с ним — то есть навсегда.
- Отображай покупателю снэпшот, а не текущее состояние товара по `productId`. `productId` нужен
  только для ссылки «посмотреть товар ещё раз» (если он ещё существует) — это вторичная функция,
  не источник данных для самой строки заказа.

## 3. Слияние анонимной корзины при логине

Корзина до логина обычно живёт в cookie/localStorage или в БД под анонимным `sessionId`. При
входе её нужно слить с уже существующей корзиной пользователя (если он раньше что-то туда клал
с другого устройства), а не просто затереть одну другой.

**Рабочая стратегия:** для каждого `variantId` анонимной корзины — если такой вариант уже есть
в корзине пользователя, суммировать `quantity`; если нет — перенести строку целиком. После
переноса анонимную корзину/сессию удалить.

```typescript
async function mergeAnonymousCart(userId: string, anonymousCartId: string) {
  const [userCart, anonymousItems] = await Promise.all([
    getOrCreateCart(userId),
    db.cartItem.findMany({ where: { cartId: anonymousCartId } }),
  ])

  for (const item of anonymousItems) {
    const existing = userCart.items.find((i) => i.variantId === item.variantId)
    if (existing) {
      await db.cartItem.update({
        where: { id: existing.id },
        data: { quantity: existing.quantity + item.quantity },
      })
    } else {
      await db.cartItem.update({ where: { id: item.id }, data: { cartId: userCart.id } })
    }
  }

  await db.cart.delete({ where: { id: anonymousCartId } })
}
```

Это операция с гонкой (пользователь может логиниться параллельно в двух вкладках) — оборачивай
в транзакцию БД, если фреймворк это позволяет, а не полагайся на порядок await.

## 4. «Снять с продажи», а не удалить

Как только на товар/вариант сослался хоть один `CartItem` или `OrderItem`, обычное `delete`
превращается в проблему: либо падает на FK-constraint, либо (если FK nullable, см. п. 2) молча
обнуляет ссылку в чужих корзинах и заказах.

**Правило:** перед удалением товара/варианта проверять, есть ли на него живые ссылки. Если
есть — не удалять, а помечать `isActive: false` / снимать с публикации (скрывать из каталога,
запрещать добавление в новые корзины), оставляя запись существовать для старых ссылок.
Удаление — только если ссылок действительно нет.

```typescript
async function retireVariant(variantId: string) {
  const hasReferences = await db.orderItem.count({ where: { variantId } })
  if (hasReferences > 0) {
    return db.productVariant.update({ where: { id: variantId }, data: { isActive: false } })
  }
  return db.productVariant.delete({ where: { id: variantId } })
}
```

Цена ошибки здесь — не крэш, а тихая потеря чужих данных (обнулённая ссылка в чужой корзине или
заказе), поэтому мимо этого правила нельзя пройти «просто добавив каскадное удаление позже».

## 5. Простой случай — без вариантов, без снэпшотов кроме цены

Не любому магазину нужен полный паттерн выше. Если у товара нет вариантов и правки каталога
задним числом не меняют уже оформленные заказы (например, цена в заказе фиксируется, но имя/фото
разрешено брать из актуального `Product` через relation) — минимальной модели достаточно:
`Order` → `OrderItem` с обязательным `productId` (без nullable/SetNull) и одним полем-снэпшотом
`price`. Не усложняй заранее до появления реальной причины (варианты товара, риск удаления
товара с историей заказов).

## 6. Разросшийся компонент формы чекаута — выносить async-расчёт в отдельный хук

Форма чекаута тянет к себе больше ответственностей, чем любой другой компонент магазина: Zod-схему
валидации, `onSubmit`, расчёт доставки (обычно с дебаунсом и внешним API вроде СДЭК), выбор
ПВЗ/адреса, промокоды. Компонент незаметно дорастает до 300–600+ строк, и это не всегда сам
`checkout-form.tsx` — вынесенный «под-компонент» одной секции формы (например, блок выбора
доставки) может незаметно стать таким же по объёму и болезни.

**Признак, что пора выносить:** в одном файле одновременно есть (а) `useState`/`useEffect` для
асинхронного расчёта с дебаунсом, (б) чистая логика вычисления цены/стоимости по результату
расчёта и (в) JSX вёрстки. Такой файл нельзя протестировать без монтирования React-дерева и
мока сетевого вызова — а сама формула расчёта (например, «какой тариф выбрать при недоступности
метода») заслуживает юнит-теста отдельно от UI.

**Решение — хук + чистые функции внутри:**

```typescript
// _hooks/use-shipping-calculation.ts
export function getShippingCost(method: ShippingMethod, costs: ShippingCostResult | null): number {
  // чистая функция — тестируется без React и без сети
}

export function useShippingCalculation({ packageItems, onShippingCostChange, ... }) {
  const [shippingCosts, setShippingCosts] = useState<ShippingCostResult | null>(null)
  // дебаунс + вызов Server Action внутри useEffect
  // наружу — только сериализованный результат и колбэки
  return { shippingMethod, shippingCosts, isCalcShipping, getEffectiveCost, ... }
}
```

Хук принимает на входе данные корзины (позиции/индекс), отдаёт наружу тарифы и состояние
загрузки — сам компонент формы про дебаунс и структуру ответа API ничего не знает. Чистые
хелперы (`getShippingCost`, форматирование лейбла) вынесены из хука отдельными экспортами и
покрываются юнит-тестами без монтирования компонента.

**Референс — `apps/aboi/src/app/[locale]/(shop)/checkout/`:** здесь этот хук
(`_hooks/use-shipping-calculation.ts`) вынесен из `checkout-form.tsx` (632 → 351 строка), а сама
форма дополнительно разбита на три презентационных шага
(`_components/contacts-step.tsx`, `delivery-step.tsx`, `payment-step.tsx`) — оркестратор остался
тонким: схема валидации, `onSubmit`, сборка шагов.

**Разбиение на шаг-компоненты — не всегда применимо.** Это решение для форм, устроенных как
пошаговый wizard (aboi). У `apps/svoichuzhie` чекаут — не wizard, а одна страница с секциями
(контакты → доставка → состав заказа), поэтому там разбивать на «шаги» нечего. Но тот же недуг
(async-расчёт+дебаунс+вёрстка в одном файле) там есть — в
`apps/svoichuzhie/src/app/merch/checkout/_components/delivery-section.tsx` (350 строк): дебаунс
поиска города по DaData, расчёт стоимости СДЭК, обработка клика вне дропдауна подсказок и вся
вёрстка выбора ПВЗ/курьера смешаны в одном компоненте без выноса хука. Сам `checkout-form.tsx`
там уже тонкий (236 строк, `SvoichuzhieForm` + сборка секций) — расти начала именно секция
доставки, что и подтверждает: расти будет то место, где есть async-расчёт, а не обязательно
корневой файл формы.

**Вывод:** выносить async-расчёт с дебаунсом в отдельный хук с чистыми тестируемыми хелперами —
подтверждённый дважды паттерн (aboi сделал, svoichuzhie ещё нет). Разбиение формы на
шаг-компоненты — паттерн для wizard-структуры конкретно, пока один пример (aboi); не переносить
на svoichuzhie насильно, там форма устроена иначе.

## Смежное

- **Расчёт посылки/доставки** — если у товара есть физические габариты и вес, влияющие на
  стоимость доставки, см. `PLAN-INFRA.md` §23 (расчёт упаковки, дублирование логики СДЭК).
- **Цены — Int в копейках, не Float.** Плавающая точка накапливает ошибку округления на
  агрегатах (сумма заказа, скидка в процентах) — стандартное правило, не специфичное для этого
  документа.
