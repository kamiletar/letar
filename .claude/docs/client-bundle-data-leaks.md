# Утечка больших данных в клиентский бандл — и как её честно проверить

Крупные JSON-справочники (банки вопросов, словари, таблицы коэффициентов) обычно живут рядом
с чистой логикой в `_lib`/`_data`. Один неосторожный **value-импорт** из клиентского компонента
затягивает такой файл целиком в бандл, который скачивает браузер. Проблема тихая: типы сходятся,
тесты зелёные, страница работает — просто пользователь грузит лишние сотни килобайт.

## Правило

Модуль, который импортируется клиентским компонентом (`'use client'`), берёт из «тяжёлых»
модулей **только типы**:

```ts
// ✅ стирается при компиляции, данные не тянутся
import type { ScaleConfidence } from './scoring-core'

// ❌ scoring-core делает `import maxScoresData from '../_data/max-scores-per-question.json'`
//    → 462 КБ уезжают в клиентский бандл
import { confidenceFromCount } from './scoring-core'
```

Следствие для проектирования: если чистой функции нужна величина, которую считает «тяжёлый»
модуль, — **эту величину передают снаружи параметром**, а не импортируют. Серверный код
(server action, RSC) считает её и прокидывает в пропсах.

> Прецедент: `archetest`, индекс «Тёмное ядро» (v0.24.0). `dark-core.ts` нужен
> `ScaleConfidence`, но `confidenceFromCount` живёт в одном модуле с 462-КБ JSON.
> Поэтому `confidence` и `relevantCounts` приходят в модуль извне — их отдаёт
> `getClientDetailAction`.

## ⚠️ Как проверять — и почему наивная проверка врёт

Естественный первый шаг — грепнуть клиентские чанки по имени ключа из JSON:

```bash
grep -rl "per_question_max" .next/static/   # → пусто
```

**Пустой результат здесь ничего не доказывает.** Webpack применяет к JSON-модулям
tree-shaking: при доступе вида `data.per_question_max` обёртка выбрасывается, а сами данные
инлайнятся. Имя ключа исчезает из бандла даже тогда, когда все данные в нём лежат. Так же
пусто будет и в серверном бандле, где данные точно есть.

### Правильная процедура

1. Взять сигнатуру **самих данных**, а не имя ключа: редкое значение, последние ключи,
   характерную пару «ключ-значение».
2. Искать её в клиентских **и** серверных чанках.
3. **Положительный контроль обязателен**: если сигнатура не нашлась и там, где данные
   заведомо есть, — сигнатура плохая, проверку надо переделать, а не считать пройденной.

```bash
# сигнатуры из хвоста JSON — их нет ни в одном другом источнике
for sig in '"SPEC_INT":3' '"2126"' '"2125"'; do
  echo "$sig → клиент: $(grep -rlF "$sig" .next/static/ | wc -l), сервер: $(grep -rlF "$sig" .next/server/ | wc -l)"
done
```

Здоровый результат — `клиент: 0, сервер: >0`. Результат `клиент: 0, сервер: 0` означает,
что проверка не работает.

Проверять надо по **production-сборке** (`nx build <app>`): в `.next/dev/` лежат dev-чанки
Turbopack, у них другая раскладка, и выводы по ним переносить нельзя.

## Приём обхода: литерал + тест-сверка вместо импорта ради одного числа

Частый случай — из тяжёлого справочника нужна **одна производная величина**: сколько
в нём записей, какая версия, сумма по колонке. Соблазн написать
`Object.keys(bigJson).length` в компоненте велик, но value-импорт тянет весь файл
в бандл каждой страницы, которая эту величину показывает.

Рабочее решение — держать число литералом в маленьком модуле, а от рассинхрона
защищаться unit-тестом: тест **может** импортировать тяжёлый файл, потому что в рантайм
он не попадает.

```ts
// _data/bank-stats.ts — в бандл уедет только это число
export const TOTAL_QUESTIONS = 2126

// _data/bank-stats.test.ts — тяжёлый импорт живёт здесь и никуда не утекает
import maxScores from './max-scores-per-question.json'
expect(TOTAL_QUESTIONS).toBe(Object.keys(maxScores.per_question_max).length)
```

Так число остаётся в одном месте (иначе оно расползается по текстам страниц), бандл
не растёт, а при вливании новых данных тест падает и напоминает обновить константу.

Прецедент: `archetest` — справочник максимумов баллов весит 462 КБ, а «2126 вопросов»
упоминается в метаданных обеих локалей, на публичной странице методологии и в презентации.
До введения константы числа успели разойтись с реальностью на 30 вопросов, и никто
этого не заметил.

## Когда проверять

- добавили клиентский компонент, который тянет расчётную логику из `_lib`;
- вынесли «чистое ядро» из server action в общий модуль;
- заметили необъяснимый рост First Load JS в выводе `next build`.

Быстрый ориентир без грепа — таблица маршрутов в выводе сборки: скачок First Load JS на
сотни килобайт по одному роуту почти всегда означает затянутый данными модуль.

## Второй канал утечки: публичное/партнёрское API

Всё выше — про утечку через клиентский бандл. У той же проблемы (приватное поле сущности —
закупочная цена, маржа, внутренний комментарий — уходит наружу) есть **второй, независимый
канал**: публичный HTTP API для внешних контрагентов (партнёров, поставщиков, встраиваемых
виджетов).

Защита от утечки через бандл — не передавать приватные поля из серверного компонента
в клиентский — здесь **не работает вообще**. API-хендлер не рендерит React-дерево и не
проходит через клиентский компонент: он получает ORM-сущность и сериализует её в JSON
напрямую. Если хендлер отдаёт `prisma.product.findMany()` целиком (или ZenStack-клиент без
дополнительных ограничений) — приватные поля уезжают в ответ вне зависимости от того, что
происходит с бандлом.

### Рекомендация: field-level access policies, а не ручной `select` в каждом хендлере

Ручной `select: { ... }` в каждом API-роуте работает, но легко забыть при добавлении нового
эндпоинта — ничего не сигналит, что поле нужно скрыть, пока кто-то не заметит его в ответе
постфактум. Надёжнее — описать приватность поля один раз в `schema.zmodel` как
field-level `@allow`/`@deny`, и дать API-слою всегда работать через enhanced-клиент
(`getEnhancedPrisma`), а не через сырой Prisma-клиент в обход политик.

```zmodel
model Product {
  id            String   @id @default(cuid())
  name          String
  price         Decimal                                    // публичная розничная цена
  purchasePrice Decimal  @deny('read', true)                // закупочная цена — не читается никем через enhanced-клиент
  margin        Decimal  @allow('read', auth().isOwner)     // маржа видна только владельцу

  @@allow('read', true)       // остальные поля модели — публичные
  @@allow('all', auth().isOwner)
}
```

```typescript
// ✅ API-роут для партнёров — идёт через enhanced-клиент, политика применяется автоматически
import { getEnhancedPrisma } from '@/lib/db'

export async function GET(request: Request) {
  const db = await getEnhancedPrisma() // без auth() — партнёрский токен, не сессия пользователя
  const products = await db.product.findMany() // purchasePrice/margin вырезаются политикой, а не select'ом
  return Response.json(products)
}

// ❌ Опасно — сырой Prisma-клиент игнорирует политики схемы
import { prisma } from '@/lib/db'
const products = await prisma.product.findMany() // purchasePrice и margin в ответе
```

Field-level `@allow`/`@deny` — это defense-in-depth именно потому, что защита не зависит от
того, вспомнил ли автор нового эндпоинта про приватные поля: enhanced-клиент вырезает их
всегда, а не только там, где кто-то явно написал `select`.

### Тест: грепать тело HTTP-ответа по значениям, не по именам полей

Та же ловушка, что с бандлом: грепать JSON-ответ API по имени ключа (`"purchasePrice"`)
можно, но это не доказательство отсутствия утечки — сериализатор мог отдать значение под
другим именем (алиас поля, вложенный объект), а ключ при этом не встретится. Нужен тот же
положительный контроль — сигнатура по **значению**, которое заведомо приватное и не
встречается больше нигде в ответе.

```typescript
// apps/<app>/src/app/api/partner/products/route.spec.ts
test('партнёрский эндпоинт не отдаёт закупочную цену', async () => {
  const product = await createTestProduct({ purchasePrice: 4173.5, margin: 0.42 })

  const res = await fetch('/api/partner/products', {
    headers: { Authorization: `Bearer ${partnerToken}` },
  })
  const body = await res.text() // текст, а не распарсенный JSON — иначе мимо пройдёт вложенность

  expect(body).not.toContain('4173.5') // сигнатура приватного значения
  expect(body).not.toContain('0.42')
  expect(body).toContain(product.name) // положительный контроль: сериализация вообще работает
})
```

Без положительного контроля (`toContain(product.name)`) тест может молча деградировать —
например, если эндпоинт вообще перестал отдавать данные (500, пустой массив), проверка на
`not.toContain` пройдёт «зелёной», ничего не проверив.
