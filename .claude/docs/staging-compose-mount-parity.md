# Staging-compose без bind-mount из production — тихо, без единой ошибки

Соседний класс к [docker-bind-mount-uid-gid-mismatch](/.claude/docs/docker-bind-mount-uid-gid-mismatch.md):
там каталог смонтирован, но не пишется. Здесь на staging его не смонтировали вовсе.

## Симптом

Никакого. В этом и ловушка:

- Контейнер пишет `uploads/` в свой writable-слой. Запись проходит, e2e зелёный.
- При следующем деплое контейнер пересоздаётся, и файлы пропадают. На staging их никто не ищет.
- Staging перестаёт ловить поломки прав каталога (EACCES на bind-mount): ему нечего проверять.
  Тест загрузки на staging пройдёт, даже когда на проде тот же код падает.
- Файлы, которые кладёт на хост `db:seed` (он бежит на хосте, не в контейнере), до контейнера
  не доходят: картинки отдают 404.

## Как это случилось

Staging-compose заводили под e2e-гейт вручную, копированием, пачкой за несколько дней
(2026-07-14…18). Генератора для них нет. Из production переносили порты, env, healthcheck и
Traefik-label'ы, а `volumes` сервиса `app` выпал у пяти приложений разом (у одного — два
каталога).

Дальше ошибку находили по одному приложению и чинили точечно:

| Когда      | Где                          | Как нашли                                                                                                                                                          |
| ---------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 2026-07-22 | mandala                      | seed отработал, картинки на staging — 404                                                                                                                          |
| 2026-09-05 | приватное приложение         | 7 недель маскировалось: Next.js по ошибке трассировал весь `uploads/` в standalone-сборку, файлы лежали прямо в образе. После фикса трассировки SSR упал на ENOENT |
| 2026-09-23 | ещё три приватных приложения | при разборе EACCES на проде                                                                                                                                        |

Сообщение фикса от 2026-09-05 прямо называло остальные staging-compose «без volume» как
исключение — но сверять их никто не пошёл. Та же картина, что с правами каталогов: чинили
место, а не класс.

## Защита: `scripts/check-compose-mount-parity.mjs`

Gate в `bun scripts/check-all.mjs` (id `compose-mount-parity`, группа `deploy`). Для каждого
приложения, у которого есть оба файла, сверяет сервис `app`:

- каждый относительный (`./…`) bind-mount без `:ro` из `docker-compose.production.yml` должен
  быть и в `docker-compose.staging.yml` — по пути **внутри контейнера**;
- смонтирован в staging как `:ro`, а в production на запись — тоже ошибка.

Понимает короткую (`./a:/b`, в кавычках тоже) и длинную (`type: bind`) запись. Абсолютные пути,
`${VAR}`, именованные тома и сервисы кроме `app` не сверяет: у staging законно свои БД, сокеты и
секреты.

Осознанное исключение — `ALLOWED_MISSING` в скрипте, с причиной строкой. Без причины
исключение неотличимо от забытой строки.

⚠️ В CI покрытие неполное: большинство staging-compose лежит в приватных submodule, которые CI
не выкачивает. Полную картину даёт только локальный прогон.

## Заводишь staging-compose для нового приложения

Начинай с копии `services.app.volumes` из production, а не с пустого места. Потом —
`bun scripts/check-all.mjs --only=compose-mount-parity`. Права на смонтированные каталоги
деплой выставит сам (`scripts/ensure-writable-mounts.sh`).
