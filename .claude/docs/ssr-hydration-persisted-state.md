# SSR-гидратация: чтение persistent-состояния в инициализаторе рендера

## Проблема

Если компонент читает значение выбора пользователя (`localStorage`, `sessionStorage`, cookie) прямо
в инициализаторе состояния — `useState(() => localStorage.getItem(...))`, или в теле компонента до
`useEffect` — то сервер рендерит с дефолтным значением, а клиент при **первом** рендере (та же
фаза, что и гидратация) может прочитать другое значение.

Это не просто «моргание». React сверяет клиентское дерево с HTML от сервера один раз, на
гидратации. Если на этот момент состояние уже другое (`useState`-инициализатор успел прочитать
`localStorage` до сверки), React может решить, что видимый DOM уже соответствует новому
состоянию — «поженить» серверную разметку с клиентским значением без предупреждения об ошибке.
Дальше клик пользователя по видимому элементу может не производить эффекта: `setState` в то же
значение, которое React уже считает текущим — no-op, а реальный DOM ему не соответствует.

Отличие от классического hydration mismatch (см.
[nextjs16-turbopack-default-emotion-hydration.md](nextjs16-turbopack-default-emotion-hydration.md)):
там React **обнаруживает** расхождение и ругается в консоль. Здесь расхождение — не в самой
разметке (текст/атрибуты могут совпасть), а в логическом состоянии, которое эту разметку
контролирует — предупреждения не будет, баг выглядит как «кнопка перестала работать».

Класс бага хорошо задокументирован за пределами этого репозитория:

- [docusaurus#5653](https://github.com/facebook/docusaurus/issues/5653) — тот же баг на табах,
  открыт с 2021 года.
- Nuxt UI, `FrameworkTabs.vue` — независимо пришли к тому же выводу, комментарий в коде объясняет,
  почему нельзя читать реальную cookie в `setup()` до монтирования.
- TanStack, `usePersistedEnumStore.ts` — эталонная реализация с отложенной гидратацией: чтение в
  `useEffect`, одинаковый дефолт на сервере и при первом клиентском рендере.

## Неправильно

```tsx
// ❌ Читает localStorage синхронно в инициализаторе — на клиенте типично `typeof window`
// уже defined, поэтому чтение происходит на первом (гидратирующем) рендере, не после него
const [trackMode, setTrackMode] = useState<TrackMode>(() => {
  if (typeof window === 'undefined') { return 'RUSSIAN_DUB' }
  return (localStorage.getItem(TRACK_MODE_KEY) as TrackMode) || 'RUSSIAN_DUB'
})
```

`typeof window === 'undefined'` защищает только от краша на сервере (см.
[nextjs-ssr-browser-only-libs.md](nextjs-ssr-browser-only-libs.md) — там та же проверка решает
другую проблему, падение модуля). От гидратационного мисматча она не защищает: на сервере ветка
даёт дефолт, а на клиенте — уже сохранённое значение, в первом же рендере.

## Правильно

```tsx
// ✅ Одинаковый дефолт на сервере и при первом клиентском рендере.
// Реальное значение подставляется в useEffect — уже после гидратации.
const [trackMode, setTrackMode] = useState<TrackMode>('RUSSIAN_DUB')

useEffect(() => {
  const saved = localStorage.getItem(TRACK_MODE_KEY) as TrackMode | null
  if (saved) { setTrackMode(saved) }
}, [])
```

Если из-за подмены после монтирования заметно «моргание» — это ожидаемый и безопасный компромисс
(лечится CSS-переходом при необходимости), в отличие от мисматча, который ломает интерактивность
без визуальных следов.

### `useSyncExternalStore` — альтернатива с явным SSR fallback

Для чтения, которое должно синхронно следить за внешним изменением storage (не только один раз при
монтировании), в репозитории уже используется `useSyncExternalStore` с корректным
серверным fallback (см. `apps/pravda/src/hooks/use-bookmarks.ts`,
`libs/hooks/src/lib/browser/use-offline-consent.ts`) — третий аргумент (`getServerSnapshot`)
обязан возвращать тот же дефолт, что первый клиентский рендер до синхронизации с реальным
storage.

### next-themes — образец готового решения для более сложного случая (цветовая тема)

`libs/chakra-provider/src/lib/use-color-mode.ts` — не самописная логика, а обёртка над
`next-themes`. Библиотека решает ту же задачу иначе: инлайновый блокирующий `<script>` в `<head>`
выставляет класс на `<html>` **до** гидратации (без flash неверной темы), а хук держит
собственный флаг `mounted` и до монтирования отдаёт `'system'`/`undefined` — то есть тоже не
доверяет `localStorage` в первом рендере, просто источник правды для DOM — не React-состояние, а
атрибут, выставленный синхронным скриптом. Не считать этот файл багом и не переписывать на паттерн
выше — здесь это другая, более тонкая техника, оправданная тем, что от темы зависит вся страница
целиком, а не один компонент.

## Как быстро найти подозрительные места

```bash
grep -rn "useState(() =>.*\(localStorage\|sessionStorage\)" apps/*/src libs/*/src
grep -rn "useState(.*\(localStorage\|sessionStorage\)\.getItem" apps/*/src libs/*/src
```

Ищет инициализаторы `useState`, читающие storage синхронно. Не ловит чтение внутри `useCallback`
для обработчиков событий (безопасно) и чтение внутри `useEffect` (безопасно) — их нужно
просматривать вручную, паттерн даёт только кандидатов.
