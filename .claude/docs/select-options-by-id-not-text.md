# Варианты списка — отдельные записи со ссылкой по `id`, а не текст

⚠️ **Ловушка, которая выглядит как рабочая схема.** Варианты выпадающего списка хранятся массивом
строк (`options String[]`), а выбранное значение — той же строкой в другой таблице. Всё работает,
пока никто не переименовывает вариант.

Пример без привязки к приложению — «характеристика материала» (например «Порода дерева»):

```zmodel
// ❌ связь по тексту
model AttributeDefinition {
  id      String   @id @default(cuid())
  name    String
  options String[]            // ["Сосна", "Ель", "Лиственница"]
}

model MaterialAttributeValue {
  materialId   String
  definitionId String
  value        String         // "Сосна" — просто копия текста из options
}
```

## Симптом

- Переименовал вариант «Сосна» → «Сосна обыкновенная»: в карточках материалов остаётся «Сосна», в
  фильтре каталога — уже другой текст, счётчик у варианта ноль.
- Удалил вариант из списка: значения в материалах остались, но выбрать их снова нельзя, а фильтр их
  не показывает. Форма редактирования открывается с «неизвестным» значением.
- Опечатку в варианте («Ельь») исправить нельзя одним действием.

Признак в коде — функция «переписать значение по всем строкам» рядом с переименованием варианта. Это
заплатка над схемой, не решение.

## Почему текст — ловушка

| Место                        | Что ломается                                                                                                                        |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **Переименование**           | Правится в двух местах: в списке и во всех значениях. Забыл одно, пропустил часть строк, прервалась транзакция — данные разошлись   |
| **Удаление**                 | БД не знает о связи: внешнего ключа нет, значения тихо становятся «сиротами»                                                        |
| **Фильтры в URL**            | `?attr=Сосна` — текст в адресе. Переименование ломает все сохранённые ссылки и закладки, кириллица и пробелы требуют кодирования    |
| **Индексируемые комбинации** | Страница «категория × вариант» ссылается на текст — при переименовании адрес и содержимое расходятся                                |
| **Импорт**                   | `"сосна"`, `"Сосна "`, `"Сосна"` — три разных значения; сравнение по строке не спасает от регистра, пробелов и неразрывных пробелов |
| **Уникальность**             | `@@unique([..., value])` сравнивает строки байт в байт, а не «тот же вариант»                                                       |
| **Порядок**                  | Порядок вариантов — порядок массива; хранить у значения нечего, сортировка по тексту даёт алфавит, а не задуманный порядок          |

## Рекомендуемая схема

Вариант — отдельная модель. Значение ссылается на неё по `id`; текст живёт в одной строке.

```zmodel
model AttributeDefinition {
  id      String            @id @default(cuid())
  name    String
  options AttributeOption[]
}

/// Значения и комбинации ссылаются на вариант по `id`: переименование правит одну строку `label`,
/// а удаление используемого варианта блокирует внешний ключ (Restrict)
model AttributeOption {
  id           String @id @default(cuid())
  definitionId String
  label        String
  order        Int    @default(0)

  definition AttributeDefinition @relation(fields: [definitionId], references: [id], onDelete: Cascade)

  @@unique([definitionId, label])
  @@index([definitionId, order])
}

model MaterialAttributeValue {
  id           String  @id @default(cuid())
  materialId   String
  definitionId String
  value        String?   // для характеристик без списка (текст, число); у списка пусто
  optionId     String?   // для списка

  option AttributeOption? @relation(fields: [optionId], references: [id], onDelete: Restrict)

  @@unique([materialId, definitionId])
  @@index([optionId])
}
```

Правила выбора `onDelete`:

- **Значение → вариант: `Restrict`.** Удалить вариант, которым кто-то пользуется, нельзя — БД
  отвечает ошибкой, а не осиротевшими значениями. В интерфейсе ловим её и показываем «используется
  в N материалах», предлагаем сначала заменить.
- **Комбинация фильтра (производная запись, её можно пересоздать) → вариант: `Cascade`.** Исчез
  вариант — исчезла и комбинация.
- **Вариант → характеристика: `Cascade`.** Удалили характеристику — уходят её варианты.

Не забыть про политики ZenStack: `optionId` — обычное поле значения, права на запись те же, что у
самого значения; читать варианты нужно всем, кому показывается каталог.

⚠️ Если у значения два вида хранения (`value` для свободных типов и `optionId` для списка), `value`
надо сделать необязательным и явно договориться, что для списка он **пуст** — иначе снова появится
два источника правды.

## Миграция с бэкфиллом

Порядок шагов важен: каждый следующий опирается на результат предыдущего. Всё в одной миграции
(`migration.sql`), пример — `apps/domwellbes/prisma/migrations/20260927000000_attribute_option_by_id`
(приватный submodule, файл открыть там).

1. **Создать таблицу вариантов** с уникальным индексом `(definitionId, label)` и внешним ключом на
   характеристику.
2. **Перенести варианты из массива** — `unnest(options) WITH ORDINALITY`: порядок массива станет
   полем `order`. Только для характеристик типа «список». `id` детерминированный
   (`'ao_' || md5(definitionId || '|' || label)`) — миграция идемпотентна, повторный прогон не
   создаёт дубликаты; `ON CONFLICT (definitionId, label) DO NOTHING`.
3. **Осиротевшие значения → завести для них вариант.** Возьмите `DISTINCT` тех текстов из значений
   (и из других таблиц, хранящих текст варианта — комбинации фильтров), которых нет в массиве
   `options`. Без этого шага `UPDATE` в п. 5 пропустит их, а п. 6 удалит — данные потеряны молча.
   Порядок таким вариантам даём после основных (`1000 + row_number()`), чтобы они не вклинивались в
   заданный порядок.
4. **Добавить колонку `optionId`**, сделать `value` необязательным (`DROP NOT NULL`).
5. **Проставить `optionId` по совпадению** `(definitionId, label = value)` и обнулить `value`.
6. **Удалить остаток:** значения списка, у которых `optionId` так и не нашёлся (пустая строка =
   «не задано»). Прежде чем `DELETE` — посчитать их `SELECT count(*)` на копии прод-данных; ненулевое
   число, кроме пустых строк, значит, шаг 3 что-то пропустил.
7. **Создать индекс и внешний ключ** (`Restrict` на значении, `Cascade` у комбинаций). Уникальный
   индекс комбинаций — по `optionId`, старый по тексту можно оставить, пока колонка допускает
   `NULL`.
8. **Удалить старый массив** `options` — в самом конце, после того как все чтения переведены на
   таблицу. Откатиться после этого можно только из бэкапа.

⚠️ Порядок с кодом: сначала миграция и код, который умеет читать оба вида (если деплой не
атомарный), потом чистка. Внешний ключ ставим **после** заполнения, не до.

Проверка результата — SQL по копии данных, не «глазами»:

```sql
-- значения списка без варианта: должно быть 0
SELECT count(*) FROM "MaterialAttributeValue" v
JOIN "AttributeDefinition" d ON d.id = v."definitionId"
WHERE d."valueType" = 'SELECT' AND v."optionId" IS NULL;

-- число вариантов равно сумме элементов старых массивов + заведённые для осиротевших
SELECT count(*) FROM "AttributeOption";
```

## Что меняется в URL фильтров

Параметр несёт `id` варианта: `?attr_<id характеристики>=<id варианта>`, а не текст.

- **Старые ссылки с текстом перестают работать** (значение не найдётся как `id`). Если прежние
  адреса были в публичном доступе или в индексе поисковиков — либо добавить разбор legacy-текста с
  редиректом на `id`, либо сознательно принять потерю. Прежде чем решать, проверьте, есть ли такие
  адреса в живой выдаче (индексируемые комбинации, sitemap, закладки в маркетинге). Если нет —
  проще принять разрыв и записать его в CHANGELOG.
- Разбор параметра — только через существующие варианты характеристики: неизвестный `id` игнорируем
  (или 404 для индексируемой страницы), а не подставляем в запрос.
- `id` в адресе не читается человеком. Если для SEO нужен красивый адрес — отдельный `slug` у
  варианта с `@@unique([definitionId, slug])`, но не текст `label`: он переименовывается.
- Подпись выбранного фильтра, `<title>` и хлебные крошки берём из `label` по `id` — тогда
  переименование мгновенно доезжает до всех страниц.

## Тест-чеклист

- [ ] **Переименование:** правка `label` — одна строка; карточки и фильтр показывают новый текст,
      значения не менялись (`SELECT` по `optionId` тот же).
- [ ] **Удаление используемого варианта** — отказ БД (`Restrict`), в интерфейсе понятное сообщение;
      неиспользуемого — успешно.
- [ ] **Удаление характеристики** — варианты и комбинации уходят каскадом.
- [ ] **Фильтр по `id`:** известный вариант фильтрует, неизвестный/чужой (вариант другой
      характеристики) игнорируется.
- [ ] **Один вариант у двух характеристик** с одинаковым `label` — независимые записи, значения не
      путаются.
- [ ] **Миграция:** прогнать на копии прод-данных; SQL-проверки выше; пустые значения; значения,
      которых не было в старом массиве; порядок вариантов сохранён.
- [ ] **Форма/импорт:** значение приходит как `optionId`; импорт по тексту сначала находит вариант по
      `(definitionId, label)` (регистр и пробелы нормализуем один раз, в одном месте), а не создаёт
      строку-значение.
- [ ] **Права:** роль без права записи не может создать/переименовать вариант (политика на
      `AttributeOption`).

## Находки по другим приложениям (2026-09-27, только grep, ничего не менялось)

Команда: `grep -rnE "^\s*\w+\s+String\[\]" apps --include=*.zmodel`. Приложения приватные, поэтому
ниже — категории и признаки, а не их доменные детали; точные места воспроизводятся командой выше.

Найдено ~40 полей `String[]`. Большинство — не варианты списка (URL, адреса, теги, свободные
метки, scope-ы OAuth) и под паттерн не подпадает. Кандидаты с текстовой связью:

1. **Ключи «причин» из настраиваемого списка** (CRM, `lostReasonKeys`, дефолт — список ключей в
   верхнем регистре). Это уже ключи-константы, а не человекочитаемый текст: переименовывать подпись
   можно без миграции данных, если подпись хранится в словаре (i18n), а не в самом значении. Риск
   только в удалении ключа из настроек, пока на него ссылаются записи. **Приоритет: низкий,
   проверить**, что подписи не хранятся в ключе.
2. **Списки «названий», которые потом сопоставляются по тексту** (оценка/смета: массивы названий
   пропущенных материалов и материалов с устаревшей ценой). Хранят копию текста для отчёта на
   момент расчёта — снапшот, это допустимо; ловушка появится, если по ним начнут искать или
   фильтровать живые записи. **Приоритет: низкий.**
3. **Свободные метки/специализации/бейджи** (автошкола `specializations`, `channels` со значениями в
   комментарии `["push", "email", "telegram"]`; турнирная платформа `badges`). `channels` — по
   существу enum, заведён строками: лучше `enum` или таблица. `specializations` и `badges` —
   редактируемые справочники по тексту: при первом требовании «переименовать» или «показать всех, у
   кого есть …» подойдёт паттерн. **Приоритет: средний для `channels` (→ `enum`), низкий для
   остальных.**
4. **Обременения участка** (недвижимость, `restrictions`) — свободный текст из внешнего источника;
   справочник вариантов не нужен, пока нет фильтра по значению.
5. **Причины отказа/неопределённости** (`reasons` в двух моделях проверок) — человекочитаемый
   снапшот на момент расчёта; по тексту не связываются. Не трогать.

Остальное — теги/жанры/технологии контентных приложений (`tags`, `genres`, `techStack`,
`technologies`): свободные метки без справочника. Станут кандидатами, если появится
«страница тега» с переименованием.

Настоящего дубля этой схемы (список вариантов + значения-копии текста) в других приложениях
grep не нашёл: `options String[]` встречается только там, где уже перешли на модель. Полей
`Json` с вариантами списка среди `options|choices|variants|values` тоже нет.
