# Chakra `theme:typegen` — общий файл в `node_modules`, гонка между приложениями

**Симптом:** `nx typecheck:tsgo <app>` вдруг падает на `variant="primary"` (или любом другом
кастомном варианте recipe/slot recipe), хотя сам `theme/recipes/*.ts` не менялся и минуту назад
typecheck был зелёным. Ошибка указывает на
`node_modules/.bun/@chakra-ui+react@.../node_modules/@chakra-ui/react/dist/types/styled-system/generated/recipes.gen.d.ts`
— тип `variant` откатился к дефолтному набору Chakra (`solid | subtle | outline | ...`), кастомные
варианты пропали. Задевает не только файл, который редактировался — падают все файлы приложения,
использующие тот же recipe (наблюдалось разом на `hero.tsx`, `state-message.tsx`, `error.tsx` —
ни один из последних двух не был тронут в той же сессии).

## Причина

`bunx @chakra-ui/cli typegen ./src/theme/index.ts` (таргет `theme:typegen`) генерирует типы **в
общий физический файл в `node_modules`**, который у всех приложений монорепо — один и тот же
пакет `@chakra-ui/react` (Bun isolated install кладёт его один раз). Файл не namespaced по
приложению.

Если в это же время (параллельная сессия/агент, `bun install`, dev-сервер другого приложения при
старте) кто-то ещё вызывает `theme:typegen` для **другого** приложения — тот запуск перезаписывает
файл своим набором recipe-вариантов, и типы твоего приложения молча пропадают, хотя исходники не
менялись.

## Диагностика

Ошибка типа `TS2322: Type '"primary"' is not assignable to type '"solid" | "subtle" | ...'` на
recipe/slot recipe, где `primary`/`secondary`/другой кастомный вариант точно объявлен в
`theme/recipes/*.ts` — и падает больше одного файла разом, включая незатронутые.

## Разовый фикс (если гонка уже ударила прямо сейчас)

```bash
nx theme:typegen <app> --skip-nx-cache
```

`--skip-nx-cache` обязателен для разового запуска — обычный запуск может отдать закэшированный
(уже неактуальный) результат вместо реальной перегенерации, если `src/theme/**/*.ts` (вход кэша)
не менялся с последнего запуска для этого приложения — хотя физический файл на диске тем временем
подменили.

## Структурный фикс — `dependsOn: ["theme:typegen"]` (внедрено 2026-08-25)

Гонку нельзя устранить полностью — файл в `node_modules` физически общий, это ограничение самого
`@chakra-ui/cli typegen` (см. ниже, почему `--outdir` не спасает). Но окно гонки можно сжать с
«сколько угодно долго с последнего ручного прогона» до «доли секунды между своим typegen и своим
typecheck» — этого достаточно, чтобы гонка требовала выполнения чужого `theme:typegen` ровно в эту
узкую щель, а не когда угодно за всё время сессии.

Паттерн (уже был у `domwellbes` — распространён на `aboi`, обе правки в
[project.json](/apps/aboi/project.json)):

```jsonc
// apps/<app>/project.json
"typecheck": { "dependsOn": ["theme:typegen"], /* ... */ },
"typecheck:tsgo": { "dependsOn": ["theme:typegen"], /* ... */ },
"theme:typegen": {
  "cache": false, // не "cache": true — см. ниже, почему
  /* ... */
}
```

⚠️ **`theme:typegen` обязан быть `"cache": false`, а не `"cache": true` с `inputs` на исходники
темы.** У таргета нет `outputs` (выход — файл вне `{projectRoot}`, Nx не может отслеживать его как
артефакт кэша), поэтому кэш-хит с `inputs`-инвалидацией по исходникам темы кэширует только
факт «команда завершилась успехом», не факт «физический файл на диске актуален». Если исходники
темы не менялись с прошлого прогона **этого** приложения, а конкурентный прогон **другого**
приложения тем временем подменил файл — `nx run-many`/`dependsOn` увидит кэш-хит и **не
перегенерирует** файл вообще, дыра остаётся открытой несмотря на `dependsOn`. `cache: false`
гарантирует, что каждый прогон `typecheck`/`typecheck:tsgo` реально перезаписывает файл своими
типами непосредственно перед чтением. Проверено воспроизведением: `nx theme:typegen domwellbes`
(подменяет общий файл) → `nx typecheck:tsgo aboi` зелёный, `theme:typegen` в логе `Running`, не
`cache hit`.

**Предел фикса:** `dependsOn` защищает только сам вызов `nx typecheck(:tsgo) <app>` целиком как
атомарную операцию с точки зрения этого таргета. Если внутри тех же нескольких секунд, что `tsgo`
физически читает файл после того, как свой `theme:typegen` его перезаписал, **другой** агент
успеет прогнать свой `theme:typegen` — гонка всё ещё теоретически возможна. На практике окно
сократилось с «часов между сессиями» до «секунд одного nx-прогона», что и наблюдалось на 30+
воспроизведениях в этой сессии — методом хватило.

### Почему `--outdir` не решает проблему в принципе

У `@chakra-ui/cli typegen` есть флаг `--outdir <dir>` — выглядит как решение «пиши типы
приложения в свою папку, а не в общий `node_modules`». Не работает: сгенерированные файлы
(`recipes.gen.d.ts` и соседние) — не ambient-декларации (`declare module "@chakra-ui/react"`), а
обычные `.d.ts` с именованными экспортами, на которые **сам пакет `@chakra-ui/react`** ссылается
относительными импортами из соседних файлов внутри своего `dist/types/`
(`import type { ButtonVariant } from "./generated/recipes.gen"` и т.п., см. компонентные `.d.ts`
пакета). Переместить выход в `--outdir` вне этого дерева — значит сломать резолв этих
относительных импортов у всего пакета `@chakra-ui/react`, а не изолировать типы приложения. Файл
обязан физически лежать по дефолтному пути внутри `node_modules/@chakra-ui/react/dist/types/...`,
и этот путь — один на весь монорепо при Bun isolated install.

## Что не помогает

- Кэш Nx с `inputs` на исходники темы (`cache: true`) — см. разбор выше, не защита, а источник
  ложного «зелёного», если конкурентный прогон подменил файл в промежутке.
- `--outdir` у `@chakra-ui/cli typegen` — ломает относительные импорты пакета, см. выше.
- Флаг `--projects` в `nx run-many` не поможет — гонка происходит между **отдельными** запусками
  `theme:typegen` разных приложений, не внутри одного мульти-проектного прогона.

## Когда актуально

Обнаружено у `aboi` (2026-08-25) — приложение с кастомными recipe-вариантами
(`Button variant="primary"` и т.п., см. `theme:typegen`-таргет из §11.6 PLAN.md).

Таргет `theme:typegen` на 2026-08-25 есть только у трёх приложений: `aboi`, `domwellbes`,
`driving-school`. `domwellbes` уже имел `dependsOn` до этого разбора (первоисточник паттерна).
`aboi` и `driving-school` донастроены в рамках этой сессии — оба теперь имеют
`dependsOn: ["theme:typegen"]` на `typecheck`/`typecheck:tsgo` и `theme:typegen: cache: false`.

У `driving-school` дополнительно была отдельная, не связанная с гонкой проблема: `theme:typegen`
падал с `npm error EOVERRIDE` — команда была `npx @chakra-ui/cli typegen ...`, `npx` запускает
резолвер npm, который конфликтует между корневым `overrides.kysely` (`0.29.3`) и прямой
зависимостью `kysely@0.29.5` в корневом `package.json` (тянется Better Auth-плагинами). Фикс —
команда переведена на прямой вызов бинарника
(`node ../../node_modules/@chakra-ui/cli/bin/index.js typegen ...`, по образцу `domwellbes`),
минуя npm-резолвер целиком.

Любое новое приложение с собственным `theme/recipes`/`theme/slotRecipes` и таргетом
`theme:typegen` — заводить `dependsOn: ["theme:typegen"]` на `typecheck`/`typecheck:tsgo` и
`cache: false` на самом `theme:typegen` сразу, по образцу `aboi`/`domwellbes` выше, а не ждать
повторного попадания в этот баг.
