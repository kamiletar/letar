# `tsgo --noEmit` со сталым `tsconfig.tsbuildinfo` держит старые диагностики после правки `target`/`lib`

## Симптом

Правишь `compilerOptions.target` (или `lib`) в `tsconfig.json` приложения, чтобы починить ошибку
компилятора (например `TS2737: BigInt literals are not available when targeting lower than
ES2020`) — `nx typecheck:tsgo <app>` или прямой `tsgo --noEmit` в каталоге приложения **продолжает
показывать ту же ошибку**, будто правка не применилась. `tsgo --noEmit --showConfig` при этом
честно показывает уже новый `target` — конфиг прочитан верно, дело не в нём.

## Причина

Приложение держит `"incremental": true` без явного `tsBuildInfoFile` — TypeScript кладёт кэш
рядом с `tsconfig.json` как `tsconfig.tsbuildinfo` (в корне `apps/<app>/`, не в `dist/`/`.next/`).
`tsgo` (как и `tsc`) переиспользует этот кэш между запусками ради скорости и **не инвалидирует
записанные семантические диагностики только из-за смены `target`/`lib`** — сигнатуры файлов,
которые физически не менялись (как `libs/format-utils/src/lib/money.ts` в этом случае), считаются
неизменными, и старая диагностика по ним всплывает повторно из кэша вместо пересчёта под новый
компилятор.

Это не баг конкретно в правке — файл, вызвавший ошибку, обычно вообще не в текущем приложении
(лежит в общей `libs/*`, подключён через `paths`), поэтому у агента, чинящего `tsconfig.json`
потребителя, нет мотива заподозрить кэш именно потребителя.

## Диагностика

`tsgo --noEmit --showConfig 2>&1 | grep -i target` — если резолвленный `target` уже верный, а
ошибка держится, ищи файл кэша:

```bash
find apps/<app> -iname "*.tsbuildinfo" -not -path "*/node_modules/*"
```

Типично находится `apps/<app>/tsconfig.tsbuildinfo` (и иногда `.next/cache/.tsbuildinfo` —
Next.js использует отдельный собственный кэш, тоже стоит удалить на всякий случай).

## Фикс

```bash
rm -f apps/<app>/tsconfig.tsbuildinfo apps/<app>/.next/cache/.tsbuildinfo
```

Пересобранный на следующем запуске файл уже не мешает — проблема разовая, привязанная к
конкретной смене `target`/`lib`, а не к постоянному свойству кэша. Удалять кэш профилактически
перед каждым запуском не нужно — только когда типчек воспроизводимо не совпадает с показаниями
`--showConfig`.

## Почему это стоит перепроверять при любом «упрямом» typecheck-фейле

Симптом неотличим на глаз от «правка не подействовала» или «есть ещё одно место с тем же
override» — обе гипотезы правдоподобнее «дело в кэше» и уводят в сторону. Разбор
[tsgo-tsc-stale-project-reference-redirect](/.claude/docs/tsgo-tsc-stale-project-reference-redirect.md)
описывает другой механизм с похожим внешним видом (устаревший `.d.ts`-редирект по `references`) —
там причина в конфиге, здесь в кэше рядом с ним; проверяй оба, если типчек «врёт».

## Прецедент

`animatrona-landing`/`kami-key-the-landing` (2026-09-27): `target: "ES2017"` → `"ES2022"` в
`tsconfig.json` для совместимости с BigInt-литералом в `@letar/format-utils`
(`formatKopecks`, `TS2737`). Прямой `tsgo --noEmit --showConfig` в каталоге приложения
подтверждал `target: "es2022"`, но `tsgo --noEmit` без флага показывал прежний `TS2737` — исчез
только после `rm -f tsconfig.tsbuildinfo`.
