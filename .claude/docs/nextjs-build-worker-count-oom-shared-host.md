# `next build` падает системным OOM на фазе "Collecting page data" — воркеры сайзятся по CPU, не по памяти

⚠️ Симптом выглядит как утечка/баг конкретного приложения («стало тяжелее собираться»), а
корень — в том, как Next.js по умолчанию решает, сколько параллельных воркеров поднять для сбора
данных страниц, и это решение вообще не смотрит на реально свободную память хоста.

## Симптом

На production-хосте `s2` (15GB RAM + 8GB swap, ~40 параллельных production-контейнеров, базовая
нагрузка ~5–6GB) `nx build domwellbes` падал дважды подряд (2026-09-10) на одном и том же
коммите: `Compiled successfully` (Turbopack) отрабатывает штатно за 17–19 минут, а следом
`Collecting page data using 7 workers` обрывается системным OOM-killer. `dmesg` подтверждает
system-wide OOM (не cgroup-лимит контейнера — сборка идёт на хосте до `docker build`), убитый
процесс — `next-build`, anon-rss **8.6GB** в первом прогоне и **9.5GB** во втором подряд на том
же коммите. Своп заполнялся почти полностью перед каждым падением, но не спасал.

## Корневая причина

`node_modules/next/dist/build/index.js` → `getNumberOfWorkers(config, maxTasks)`:

```js
function getNumberOfWorkers(config, maxTasks) {
  let workers
  if (config.experimental.cpus && config.experimental.cpus !== defaultConfig.experimental.cpus) {
    workers = config.experimental.cpus // пользовательское переопределение
  } else if (config.experimental.memoryBasedWorkersCount) {
    workers = Math.max(Math.min(config.experimental.cpus || 1, Math.floor(os.freemem() / 1e9)), 4)
  } else if (config.experimental.cpus) {
    workers = config.experimental.cpus
  } else {
    workers = 4 // fallback
  }
  if (maxTasks !== undefined && maxTasks > 0) { workers = Math.min(workers, maxTasks + 1) }
  return Math.max(workers, 1)
}
```

Дефолт `experimental.cpus` (`node_modules/next/dist/server/config-shared.js`):

```js
cpus: Math.max(1, (Number(process.env.CIRCLE_NODE_TOTAL) || os.cpus().length) - 1)
```

То есть без явного оверрайда воркеров ровно `os.cpus().length - 1` — на 8-ядерном `s2` это 7,
что и видно в логе (`Collecting page data using 7 workers`). `memoryBasedWorkersCount` **по
умолчанию `false`** — Next не пытается ограничить число воркеров по факту свободной памяти хоста
вообще, если явно не включить эту опцию (а включённая всё равно держит пол в 4 воркера
безусловно — `Math.max(..., 4)`).

Каждый воркер — отдельный процесс Node, который на этой фазе загружает модульный граф
назначенных ему страниц (~185 `page.tsx` + 37 `route.ts` у domwellbes, включая общие тяжёлые
зависимости — chakra-тема, `@letar/forms`, `pdfjs-dist` и т.д.). Пиковая RSS одного воркера тут
не ограничена V8 heap-лимитом (в отличие от
[nx-vitest-plugin-worker-oom-shared-machine.md](/.claude/docs/nx-vitest-plugin-worker-oom-shared-machine.md)
— там причина другая, дефолтный ~4.3GB лимит V8 heap одного процесса) — суммарная RSS 7
параллельных процессов на общей машине и даёт наблюдаемые 8.6–9.5GB, что на хосте с 15GB RAM и
базовой нагрузкой ~5–6GB от других контейнеров не помещается даже со свопом (своп реального
рабочего множества не спасает — просто отодвигает падение и трэшит диск).

**Рост пиковой RSS между двумя прогонами на одном и том же коммите** — не признак утечки в коде:
воркеры Next.js — свежие процессы на каждый `next build`, состояние между прогонами не
наследуется. Правдоподобнее — общая нагрузка хоста и фрагментация page cache/swap между двумя
попытками деплоя подряд, не код приложения.

## Что НЕ было причиной

- **Не SSG/`generateStaticParams` над большими наборами данных.** У domwellbes ни один
  динамический маршрут (`houses/[slug]`, `materials/item/[sku]`, `blog/[slug]` и т.д., включая
  все `opengraph-image.tsx`) не использует `generateStaticParams` — это чисто динамические
  (`ƒ`) роуты, на билде для них не enumerируются параметры и не выполняется рендер по каждой
  записи БД.
- **Не `sitemap.ts`.** Запросы к БД там — только `select: { slug, updatedAt }`, без тяжёлых
  полей (геометрия DXF и т.п.).
- **Не DXF-геометрия / `HouseMetricKind` / волна D7.** Библиотеки парсинга DXF
  (`src/lib/drawings/*.ts`) — серверные server-action-модули, не импортируются на верхнем уровне
  публичных страниц/layout, в build-time не выполняются и не тянут большие данные в память сами
  по себе.

## Фикс

Явный низкий потолок `experimental.cpus` в `next.config.mjs` приложения — единственный способ
переопределить дефолт `cpus-1`, `memoryBasedWorkersCount` тут не помогает (пол в 4 воркера всё
равно выше того, что безопасно на этом хосте):

```js
experimental: {
  cpus: 2,
},
```

Применено у `apps/domwellbes/next.config.mjs` (2026-09-10). Снижает пиковую RSS фазы сбора
данных страниц ценой её длительности (сама компиляция Turbopack не замедляется — воркеры
относятся только к следующей фазе). Компиляция и так самая долгая часть сборки (17–19 минут);
удлинение сбора данных страниц в разумных пределах — приемлемая цена за отсутствие OOM.

Точное число (2) — консервативный выбор под конкретную наблюдаемую нагрузку хоста `s2`
(15GB RAM, ~5–6GB занято другими контейнерами), не универсальная константа. Если приложение
вырастет по числу маршрутов или хост получит больше памяти, значение стоит пересмотреть, а не
копировать бездумно в другие приложения — большинству приложений монорепо с меньшим числом
маршрутов этот лимит не нужен вовсе.

### Аудит других приложений (2026-09-11)

По той же методике проверены `dsperevod` (67 маршрутов, Turbopack) и `driving-school` (160
маршрутов, **webpack** — `next build --webpack`, тяжелее по памяти, чем Turbopack) — ни у
одного своих падений сборки в CHANGELOG не зафиксировано.

- **`dsperevod`** — риск низкий (67 маршрутов, втрое меньше domwellbes), фикс не применён.
- **`driving-school`** — риск заметный (160 маршрутов, близко к 222 у domwellbes, вдобавок
  webpack-сборка), применён превентивно тот же `experimental.cpus: 2` в `next.config.js`
  (2026-09-11), до фактического падения — не как реакция на инцидент.

Число маршрутов — не единственный сигнал риска; бандлер (webpack тяжелее Turbopack) и текущая
нагрузка хоста в момент билда так же значимы. Проверять эти три фактора вместе, не по одному.

## Диагностика на будущее — как отличить этот класс OOM от других

- `dmesg | grep -i "oom\|killed process"` — если жертва `next-build`/`node` и упоминания cgroup
  нет — это system-wide OOM, не лимит контейнера.
- Момент падения (`Compiled successfully` уже напечатан, крах позже, на "Collecting page data")
  указывает именно на фазу сбора данных, не на саму компиляцию — компиляция другим механизмом
  параллелизма (Turbopack, свой пул) и другой профиль памяти.
- `Collecting page data using N workers` в логе — N и есть число процессов, между которыми делится
  память; сравнить с `nproc`/числом vCPU хоста, чтобы подтвердить дефолт `cpus-1`, а не
  пользовательский оверрайд.

## Подтверждено в проде (2026-09-10)

После двух подряд системных OOM на дефолте (7 воркеров) фикс (`cpus: 2`) прошёл прод-деплой
domwellbes на s2 без единого падения: `Collecting page data` завершилась штатно, лог показал
`· cpus: 2` в блоке `Experiments`, полный билд занял ~25.5 минуты (компиляция + сбор данных),
rollout/smoke-test/health-check — зелёные.
