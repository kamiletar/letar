# `DEV_SESSION_TOKEN` с `+` в query-параметре — 403 при корректном токене

⚠️ **Почищено 2026-09-09.** `create-dev-session-route.ts` теперь сам восстанавливает пробел
обратно в `+` для query-параметра `token` перед сравнением (заголовок `x-dev-session-token` не
трогается — там декодирования нет и не было). Раздел «Фикс» ниже описывает воркэраунды, актуальные
только для версий библиотеки до этого коммита или если правка почему-то не докатилась (например
приложение держит несмёрженный форк роута вместо общей фабрики — на 2026-09-09 таких нет, см.
`.claude/rules/libs.md`). Раздел «Причина» остаётся верным описанием механизма бага.

`createDevSessionRoute` (`@letar/auth/server`, [libs/auth/src/server/factories/create-dev-session-route.ts](/libs/auth/src/server/factories/create-dev-session-route.ts))
принимает токен как `?token=<...>` или заголовок `x-dev-session-token`. Токен генерируется как
обычно — `openssl rand -base64 32` (см. [security.md](/.claude/rules/security.md)) — и base64
регулярно содержит `+`.

## Симптом

`GET /api/auth/dev-session?token=<токен из .env.local>` даёт `403 {"error":"Invalid token"}`,
хотя токен в URL визуально совпадает со значением `DEV_SESSION_TOKEN` в файле, `ALLOW_DEV_SESSION`
стоит, `authSecret` не пуст, dev-сервер перезапущен после правки `.env.local`.

## Причина

`+` в query-строке — это стандартное (RFC 1866/`application/x-www-form-urlencoded`) обозначение
пробела. `new URL(request.url).searchParams.get('token')` в `create-dev-session-route.ts:158`
декодирует `+` как пробел, а не как буквальный символ. Токен `AAA+BBB=` долетает до сервера как
`AAA BBB=` — `timingSafeEqualStr` сравнивает его с настоящим `DEV_SESSION_TOKEN` и честно
получает несовпадение (плюс, если длина строк после этой порчи разъехалась, конкатенация — falls
через ветку `bufA.length !== bufB.length`).

Symptom маскируется тем, что сам вызывающий (браузер по вставленному URL, `navigate` в Browser
pane, curl без кавычек в shell, где `+` не спецсимвол) не подсвечивает никакой ошибки — строка
визуально идентична.

## Диагностика: не только этот баг даёт те же внешние признаки

Прежде чем чинить именно эту причину — исключи два соседних кандидата, которые дают тот же 403:

1. **Дубли `ALLOW_DEV_SESSION`/`DEV_SESSION_TOKEN` в `.env.local`.** `dotenv` при парсинге одного
   файла берёт **последнее** вхождение ключа — если пара вписана дважды (например, второй раз
   при повторной настройке бэкдора в другой сессии, не заметив первую), процесс видит только
   вторую пару. Токен, который человек скопировал из первого, более заметного блока — не тот,
   что реально в `process.env`. Держать в файле только одну пару.
2. **Dev-сервер не перезапущен после правки `.env.local`.** Next.js читает `.env*` один раз при
   старте процесса — правка файла на лету не подхватывается ни в dev, ни тем более в
   `next start`.

Если оба пункта уже проверены, а 403 сохраняется — смотри на символы `+`/`/`/`=` в токене.

## Фикс

Два независимых способа, оба рабочие:

- **URL-кодировать `+` как `%2B`** при формировании query-строки:
  `?token=AAA%2BBBB%3D` вместо `?token=AAA+BBB=`. Работает и в `navigate`, и в `curl`, и в ручной
  вставке в адресную строку браузера (некоторые браузеры сами кодируют при вставке, некоторые —
  нет, полагаться на это нельзя).
- **Передать токен заголовком** `x-dev-session-token: <токен>` вместо query-параметра — заголовки
  не проходят через `application/x-www-form-urlencoded`-декодирование, `+` остаётся буквальным.
  Предпочтительно для скриптовой/curl-проверки, где заголовок добавить не сложнее query-параметра.
