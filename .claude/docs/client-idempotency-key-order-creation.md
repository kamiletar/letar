# Клиентский idempotency key при создании заказа — паттерн монорепо

## Проблема

E-commerce/booking чекаут-формы обычно защищены от двойного клика на уровне UI (кнопка сабмита
дизейблится на `isSubmitting` — так уже устроен `ButtonSubmit` в `@letar/forms`). Этого
**недостаточно**: повторный запрос после `back`/reload/навигации назад приходит от нового
рендера формы, где `isSubmitting` снова `false`. Server action, создающий заказ/бронирование из
корзины и одним `$transaction` очищающий её, не имеет встроенной защиты от такой гонки — два
параллельных вызова могут оба прочитать непустую корзину до того, как первый закоммитит
транзакцию, и создать два независимых заказа из одних и тех же позиций.

## Отличие от двух уже описанных паттернов идемпотентности

Не путать с уже существующими в монорепо:

- [payment-webhook-idempotency-pattern](/.claude/docs/payment-webhook-idempotency-pattern.md) —
  дедуп **входящих внешних событий** (вебхук может прийти дважды с одним и тем же
  provider-generated ID). `select`-then-`create`.
- [idempotency-key-terminal-transition-pattern](/.claude/docs/idempotency-key-terminal-transition-pattern.md) —
  защита **одного перехода уже существующей сущности** (append-only событийная модель), ключ
  **детерминирован** и строится из id этой сущности + вида перехода. `try{create}catch`.

Здесь — третий случай: сущности (`Order`) на момент запроса ещё не существует, а ключ
неизбежно **не детерминирован** (нет server-side id, из которого его вывести) — генерируется
клиентом случайно (`crypto.randomUUID()`), один раз на попытку чекаута, и должен пережить
`reload`/`back` той же вкладки, поэтому хранится не только в памяти компонента, а в
`sessionStorage`.

## Форма решения

1. **Уникальная колонка** `idempotencyKey String? @unique` (nullable — старые заказы и
   заказы без online-оплаты могут обходиться без ключа) на самой сущности, не на отдельной
   таблице событий.
2. **Ключ генерируется и хранится клиентом**, не сервером: `crypto.randomUUID()` при первом
   обращении, дальше переиспользуется из `sessionStorage` (переживает reload, не переживает
   закрытие вкладки — короткоживущий "черновик попытки", а не постоянный идентификатор).
   Очищается вместе с остальным черновиком формы после успешного завершения (на странице успеха,
   не в самом server action — action может не успеть отработать до конца из-за `redirect()`).
3. **Двухслойная защита на сервере**, оба слоя нужны:
   - **Fast-path** — `findUnique` по ключу **до** входа в тяжёлую транзакцию (валидация
     промокода/сертификата, пересчёт доставки). Покрывает типичный случай: второй запрос
     приходит уже после того, как первый успешно закоммитил. Экономит работу, не даёт гарантии
     сама по себе.
   - **`try { $transaction(...) } catch`** — настоящая защита от гонки: если два запроса
     одновременно проходят fast-path (оба видят "ключа ещё нет"), второй `tx.<model>.create()`
     упадёт на нарушении `@unique` уже на уровне БД. Перехват ищет по тексту ошибки
     (`"Unique constraint"` — независимо от того, классический `@prisma/client` это бросает как
     `P2002` или ZenStack v3 ORM как raw `SQLSTATE 23505`, см.
     [zenstack-v3-orm-error-codes](/.claude/docs/zenstack-v3-orm-error-codes.md)) и в обоих
     случаях просто перезапрашивает уже созданную запись по тому же ключу.
4. **Редирект на результат существующей записи, не ошибка.** Для повторного запроса корректный
   ответ пользователю — не "что-то пошло не так", а тот же результат, который он получил бы,
   останься первый запрос единственным: страница успеха (если платить больше не нужно) либо
   страница "оплата не прошла" с кнопкой повторной оплаты (если платёж ещё требуется — безопасно
   переинициировать, не создавая новый заказ).

## Реализация в монорепо

`apps/aboi/src/lib/checkout.ts` (`placeOrderAction`) + `Order.idempotencyKey` в
`apps/aboi/models/orders.zmodel` (R6.12, PLAN.md §11.11, 2026-08-26). Ключ генерируется в
`checkout-form.tsx` через `getOrCreateCheckoutIdempotencyKey()`
(`apps/aboi/src/app/[locale]/(shop)/checkout/_lib/checkout-draft.ts`) — там же живёт черновик
контактов/адреса (R6.7a), у обоих одинаковый жизненный цикл (`sessionStorage`, очистка на
success-странице).

## Куда смотреть при добавлении нового order/booking-чекаута

Любой server action, который **одной транзакцией** и создаёт сущность из корзины/формы, и
опустошает/переводит в терминальный статус источник (корзину, слот бронирования) — кандидат на
ту же гонку double-submit. На момент написания не проверено на других e-commerce/booking-потоках
монорепо (`driving-school` — запись на занятие, `domwellbes` — заявки, `svoichuzhie` — билеты) —
не факт, что там тот же пробел (могут быть закрыты иначе, например уникальным слотом времени),
но стоит явно свериться при следующей работе с их checkout/booking-кодом.
