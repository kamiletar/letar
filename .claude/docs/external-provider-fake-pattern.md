# Паттерн «интерфейс провайдера + fake-реализация»

Устоявшийся приём для внешних сервисов, поставщик которых **ещё не выбран**, а контур вокруг них
нужно писать уже сейчас. В `apps/domwellbes` он воспроизведён независимо в десяти контурах
(логистика, маркировка, фискализация, эквайринг, банковское финансирование, телефония, email,
Telegram, классифайды, антивирусный сканер) — каждый раз заново, потому что нигде не был описан.
Этот файл — описание приёма, а не пересказ одной из реализаций.

## Когда применять

Триггер один, и он не про тестируемость:

> внешний платный/договорной сервис, **поставщик которого не выбран или контракт не подписан**,
> а бизнес-контур вокруг него (заказы, склад, чеки, отгрузки) нужно строить прямо сейчас.

Тестируемость и подменяемость получаются побочно — они приятны, но сами по себе не повод
заводить интерфейс. Признаки, что случай именно тот:

- поставщик услуги ещё выбирается владельцем (оператор ЭДО, банк-эквайер, ESP, коллтрекинг);
- доступ к API требует заявки/договора, которых пока нет;
- сервис платный, и подключать его ради разработки бессмысленно;
- есть шанс, что поставщиков в итоге будет **два** (разные каналы, разные регионы, миграция).

**Когда НЕ применять.** Библиотека, которую просто ставишь из npm; сервис, который уже
подключён и менять его никто не собирается; внутренняя функция без сети. Интерфейс ради
интерфейса — лишний слой: в монорепо уже принято, что чистая функция расчёта тестируется
фикстурами напрямую, без абстракции над ней.

## Из чего состоит

Четыре части, и все четыре обязательны — три из четырёх дают протекающую абстракцию.

### 1. Узкий интерфейс — глагол домена, а не обёртка над API поставщика

```typescript
export interface MarkingProvider {
  readonly name: string
  withdrawFromCirculation(input: WithdrawMarkingCodesInput): Promise<WithdrawMarkingCodesResult>
}
```

Один-два метода, названные словами предметной области («вывести коды из оборота», «зарегистрировать
чек», «получить расстояние»), а не терминами будущего вендора. `name` — обязателен: он уезжает в
БД (`DeliveryDistanceCache.source`, `FiscalReceipt`, `IntegrationEvent`) и через полгода отвечает
на вопрос «кто на самом деле посчитал эту цифру».

Тип результата — **размеченное объединение**, а не исключение:
`{ ok: true; … } | { ok: false; errorMessage: string }`. Отказ внешнего сервиса — штатная ветка
домена, вызывающий обязан её увидеть в типе. Исключение оставляют только там, где отказ
обрабатывается выше по стеку целиком (см. `DistanceProvider` ниже).

### 2. Fake-реализация с предсказуемым поведением

Не «мок в тесте», а обычный файл рядом с интерфейсом, живущий в dev и на staging:
[`fake-marking-provider.ts`](/apps/domwellbes/src/lib/marking/fake-marking-provider.ts),
[`fake-fiscal-provider.ts`](/apps/domwellbes/src/lib/fiscal/fake-fiscal-provider.ts),
[`fake-acquiring.ts`](/apps/domwellbes/src/lib/payments/fake-acquiring.ts).

Требования к ней:

- **детерминированность** — никаких случайных задержек и «иногда падает»;
- **отсутствие сети**;
- **имя, кричащее о своей ненастоящести** — `FAKE_MARKING`, `FAKE_ACQUIRING`, `FAKE_FISCAL_CLOUD`.
  Имя попадает в БД, и по проду видно, каким провайдером записана строка;
- **переход состояния — явным действием, а не таймером.** Эталон:
  `FAKE_ACQUIRING` отдаёт `paymentUrl` на внутреннюю страницу `/checkout/pay/[paymentId]` с
  кнопками «Оплатить»/«Отменить», которые бьют в тот же вебхук, что бил бы банк;
  подтверждение фискального чека — ADMIN-действие в админке. Так пайплайн проверяется кликом, а
  не угадыванием задержки.

### 3. Точка выбора реализации — ровно одна функция

```typescript
export function resolveFiscalProvider(channel: FiscalChannel): FiscalProvider {
  return channel === 'CLOUD' ? fakeCloudFiscalProvider : fakeOnSiteFiscalProvider
}
```

Пока вариант один, `resolve*` выглядит бессмысленной — она и есть смысл паттерна: подключение
реального поставщика правит **только этот файл**. Резолвер живёт рядом с реализацией, вызывается
из оркестратора ([`issue-receipt.ts`](/apps/domwellbes/src/lib/fiscal/issue-receipt.ts),
[`dispatch.ts`](/apps/domwellbes/src/lib/delivery/dispatch.ts),
[`pickup-handoff.ts`](/apps/domwellbes/src/lib/retail/pickup-handoff.ts)), и больше нигде.

### 4. Вызывающий код не знает, какая реализация активна — это и есть проверка

Самое частое место, где паттерн ломают: где-нибудь появляется
`if (provider.name === 'FAKE_ACQUIRING')`. С этой строкой абстракции больше нет — dev-ветка
поведения расползлась по домену, и подключение настоящего поставщика перестало быть заменой
одного файла.

Правило проверяемое: **имя провайдера сравнивать с литералом можно только внутри `resolve*`.**
Всё остальное — оркестратор, server action, вебхук-роут, UI — ветвится по `result.ok`, статусу
домена и настройкам, но не по тому, кто провайдер. В domwellbes это выдержано: чистые функции
расчёта (`applyShipmentMarkingCodes`, `resolveDeliveryDistance`) принимают провайдера
**параметром**, а не импортируют резолвер — заодно бесплатно тестируются.

## Поведение при недоступности: две разные стратегии

Здесь чаще всего ошибаются, потому что «правильный ответ» зависит от того, останавливает ли отказ
бизнес-операцию. В domwellbes есть оба случая, и они устроены по-разному намеренно.

### Деградация — расчёт продолжается в ручном режиме

[`DistanceProvider`](/apps/domwellbes/src/lib/logistics/distance-provider.ts) при отсутствии ключа
**бросает ошибку сразу** — это штатный случай «провайдера нет», а не авария. Ловит её оркестратор
[`resolveDeliveryDistance`](/apps/domwellbes/src/lib/logistics/resolve-distance.ts):

```typescript
} catch (err) {
  return { distanceKm: null, source: 'manual', error: err instanceof Error ? err.message : String(err) }
}
```

Расчёт доставки не падает — расстояние становится `null`, источник помечается `'manual'`
(менеджер вобьёт километраж руками), текст ошибки сохраняется для разбора. Отдельно важно:
**неудача не пишется в кеш** — иначе первая же ошибка сети зафиксировала бы «расстояния нет» для
этой пары адресов навсегда.

Признак, что нужна именно деградация: у операции есть **человеческий обходной путь**. Тогда роль
провайдера — ускорить, а не разрешить.

### Пропуск по настройке — вызова вообще может не быть

У маркировки внешний вызов делается **не всегда**:
[`applyShipmentMarkingCodes`](/apps/domwellbes/src/lib/marking/apply-shipment-codes.ts) дёргает
`withdrawFromCirculation` только при `ofdAutoWriteOff === false`. При включённом автосписании
коды снимает ОФД на кассе, и наш вызов привёл бы к **отклонению двойного списания** — то есть
лишний вызов здесь не «страховка», а ошибка.

Отказ, когда вызов всё-таки был, не роняет отгрузку: `reportError` пишется в строку
`MarkingCode`, товар отгружается, расхождение разбирается отдельно. Общее правило: **отказ
внешнего сервиса не откатывает уже совершённое физическое движение** — он оставляет след в данных.

## ⚠️ Грабля: fake, который всегда успешен, делает тесты зелёными на несуществующем сценарии

Все fake-реализации по умолчанию возвращают успех — иначе на них невозможно разрабатывать. Отсюда
следствие, которое легко не заметить:

> тесты, прогоняющие оркестратор поверх fake-провайдера, **никогда не заходят в ветку отказа**.
> Она компилируется, покрывается глазами при ревью — и остаётся ни разу не выполненной до того
> дня, когда настоящий поставщик впервые ответит ошибкой. Покрытие при этом выглядит приличным:
> строки-то исполняются, просто всегда по счастливой ветке.

Замер по domwellbes на 2026-08-21: ветка `!result.ok` у `MarkingProvider` (запись `reportError`) и
ветка `!result.ok` у `FiscalProvider` не выполняются **ни в одном** тесте — оба spec-файла ходят
через штатный резолвер, который отдаёт всегда-успешную заглушку.

**Что делать — вторая fake-реализация с задаваемым результатом.** Готовый образец в том же
приложении: [`scanner-fake.ts`](/apps/domwellbes/src/lib/private-files/scanner-fake.ts) отдаёт две
штуки — `FakeCleanScanner` (для разработки) и `FakeFixedResultScanner`, принимающий нужный исход
конструктором. `upload.spec.ts` гоняет через него `INFECTED` и `SCAN_FAILED`, и путь отказа
оказывается настоящим исполняемым кодом.

Минимум на каждый провайдер:

- [ ] тест «провайдер вернул `ok: false`» — операция завершается, ошибка сохранена в данных;
- [ ] тест «провайдер бросил исключение» — если интерфейс допускает исключение;
- [ ] тест «вызова не было» — для контуров с тумблером (см. `ofdAutoWriteOff`);
- [ ] оркестратор принимает провайдера **параметром** — иначе первые два теста писать нечем.

## Выбор провайдера и тумблеры — из БД, не константы в коде

Всё, что владелец может захотеть переключить — включён ли контур, автосписание, какой провайдер
активен — живёт в настройках (`ShopSettings` и её аналоги-синглтоны), а не литералом в `.ts`.
Это правило §0.8 плана магазина domwellbes: «всё, что владелец может захотеть поменять, —
настройка в админке, а не константа в коде»; исключение одно — `@default` в самой схеме.

Практическое следствие для этого паттерна: `resolve*` в итоге будет выбирать реализацию **по
значению из БД**, а не по `process.env`. Env-переменная остаётся уместной для секрета (ключ API),
но не для решения «каким провайдером работаем» — смена поставщика не должна требовать деплоя.
Тумблеры вроде `markingOfdAutoWriteOff` читаются оркестратором и передаются вниз явным полем
(`ofdAutoWriteOff: shopSettings.markingOfdAutoWriteOff`), чтобы чистая функция оставалась чистой и
проверяемой обоими значениями.

## Чеклист при заведении нового провайдера

- [ ] Интерфейс в `provider.ts` (или `types.ts`), метод назван глаголом домена, есть `name`
- [ ] Результат — размеченное объединение с явной веткой отказа
- [ ] Fake-реализация: детерминированная, без сети, имя `FAKE_*`, переходы — явным действием
- [ ] `resolve*` — единственное место, знающее конкретную реализацию
- [ ] Ни одного сравнения `provider.name` с литералом вне `resolve*`
- [ ] Оркестратор принимает провайдера параметром
- [ ] Решено и записано в комментарии: отказ → деградация или след в данных (что именно не падает)
- [ ] Тест на путь отказа существует и действительно в него заходит
- [ ] Тумблеры контура — в настройках БД, а не в коде
- [ ] В шапке файла — почему поставщик ещё не подключён и что именно заменит реальная реализация

Последний пункт не формальность: в domwellbes комментарии-шапки — единственное место, где
зафиксировано, чего ждёт каждый контур. Без них следующий исполнитель видит `FAKE_*` и не может
отличить «временно, ждём договора» от «так и задумано».
