# Кросс-реплика реестр через Redis pub/sub — тестируемый без реального Redis

Прецедент: `apps/domwellbes/src/lib/assist/registry.ts` (миграция 2026-09-22, 0.301.11).

## Задача

Модуль держал состояние (открытые сессии + ожидающие запросы) в `globalThis.<key>` — стандартный
приём против дублирования модуля в dev-режиме Turbopack (см. `src/lib/db.ts` в любом приложении).
Это работает только в одном процессе. На проде с несколькими репликами за балансировщиком без
sticky-сессий два запроса одного логического потока (например долгоживущий SSE-коннект и короткий
HTTP-запрос команды к нему) могут попасть на разные реплики — данные из `globalThis` одной реплики
не видны другой.

## Решение — три приёма вместе

1. **Факторизация модульного синглтона в фабрику.** `export function createRegistry(deps)`
   возвращает все методы; дефолтный экспорт — по-прежнему один вызов фабрики, задеплоенный на
   `globalThis` (дедуп Turbopack сохраняется). Фабрика даёт возможность создать **несколько
   независимых инстансов в одном процессе теста** — это и есть способ симулировать «две реплики» с
   общим хранилищем без поднятия настоящего Redis.

2. **Узкие структурные интерфейсы вместо прямого импорта типов клиента.** Не
   `import type { Redis } from 'ioredis'` (в бане — `ioredis` не прямая зависимость приложений под
   bun isolated linker, см. `apps/dashboard-agent/src/lib/redis.ts`), а свой интерфейс с ровно теми
   методами, что реально нужны (`get/set/expire/keys/mget/publish` для команд,
   `subscribe/on('message')` для подписки). Реальный `ioredis`-клиент удовлетворяет интерфейсу
   структурно — каст не нужен, `tsgo` резолвит сам. Эти интерфейсы и есть точка инъекции
   (`deps.getCommandClient`/`deps.getSubscriberClient`), через них тесты подставляют fake.

3. **Fake-брокер вместо `ioredis-mock` или реального Redis.** Минимальный `Map`-based объект,
   реализующий ровно эти же несколько методов (`store: Map`, `channels: Map<string, Set<listener>>`
   для pub/sub). Два вызова фабрики с **одним и тем же брокером** — это «две реплики с общим
   Redis»: одна пишет `set`/`publish`, другая через `subscribe`/фоновый polling видит изменения.
   Ни CI, ни локальная машина не имеют доступа к настоящему Redis (проверено: нет сервиса в
   `.github/workflows/ci.yml`, `Test-NetConnection 127.0.0.1:6379` падает) — fake обязателен, не
   опционален.

## Асимметрия команды и метаданных

Датаплейн для _команд_ (что-то произошло прямо сейчас, доставить любой живой реплике с этим
слушателем) — чистый **pub/sub**: `publish`/`subscribe`, никакого хранения после доставки.

Датаплейн для _метаданных сессии_ (какие вкладки сейчас открыты — читается синхронно из
существующего кода, `listSessions()` не `async`) — **key-value с TTL** плюс **фоновый poll**, не
pub/sub: подписка на канал не даёт снимок «что есть сейчас», только будущие события. Фоновый
интервал (`CROSS_REPLICA_POLL_MS` в примере — 2 секунды) читает `KEYS`+`MGET` в кеш, читаемый
синхронно. Если бы `listSessions()` можно было сделать `async` — этот слой был бы не нужен, но
переписывать сигнатуру ради одной миграции не стали (все вызывающие места не `await`-ят её).

## Когда браться за этот паттерн, а не за sticky-сессии на прокси

Sticky-сессии по IP/cookie дешевле в моменте, но: (а) не переживают рестарт/скейлинг реплики
прозрачно, (б) требуют доступа к настройке прокси (Traefik/NPM) на каждый такой путь отдельно,
(в) не масштабируются на «долгий SSE + много коротких запросов с разных клиентов к той же
вкладке» без привязки уже самого запроса, а не только сессии автора вкладки. Redis pub/sub решает
на уровне приложения, не инфраструктуры — предпочтительно, когда решение принимает не тот, кто
настраивает прокси.

## Where to look

- `apps/svoichuzhie/src/lib/redis.ts` — образец `createRedisClient()`-обвязки с `fallbackUrl`.
- `apps/domwellbes/src/lib/redis.ts` — тот же паттерн **без** `fallbackUrl` (осознанно: чтобы
  тестовое/dev-окружение без `REDIS_URL` вело себя идентично исходному коду до миграции).
- `libs/auth/src/server/redis-storage.ts` — более ранний пример узкого интерфейса для DI.
- `apps/dashboard-agent/src/lib/redis.spec.ts` — `FakeRedis extends EventEmitter`, альтернативная
  форма fake-клиента (там нужен `EventEmitter`, здесь — план в `Map`, зависит от того, насколько
  богат используемый API реального клиента).
