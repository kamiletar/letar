# Паттерн «детектор поломки периодического источника»

Извлечён из реализации в `apps/domwellbes` (волна L11, парсер прайс-страниц перевозчиков). Этот
файл описывает приём абстрактно — без деталей бизнес-логики domwellbes, см.
[public-repo-hygiene](/.claude/rules/public-repo-hygiene.md).

## Когда применять

Триггер: в системе есть периодический источник данных, который **не роняет исключение при
поломке**, а тихо начинает отдавать пустоту или мусор — типично для:

- scraping/парсинга чужой веб-страницы (сайт сменил вёрстку, начал отдавать капчу, изменил
  структуру цен/данных);
- синхронизации с внешним API, который вместо ошибки отдаёт `200 OK` с пустым или урезанным
  телом;
- любого крон-джоба, который «работает», но по факту перестал находить то, что должен.

Без явного детектора деградация обнаруживается только тогда, когда кто-то вручную заметит, что
данные не обновлялись N дней — то есть поздно и случайно.

**Когда не применять:** источник, который при отказе бросает исключение и это исключение уже
обрабатывается (алертинг/ретраи на уровне инфраструктуры) — там поломка и так видна. Паттерн
нужен именно для класса «формально успешный, содержательно пустой» результата.

## Идея

Чистая функция без сети и БД, сравнивающая агрегаты **текущего** прогона с агрегатами
**предыдущего**, и по набору признаков присваивающая источнику статус:

```
ACTIVE    — источник работает штатно
DEGRADED  — один прогон вызвал подозрение
DISABLED  — два подозрительных прогона подряд, нужно ручное вмешательство
BLOCKED   — источник сам сообщил о блокировке (капча, бан) — это входные данные прогона,
            не производная от статистики; функция это состояние не вычисляет, только принимает
```

Сигнатура вида `evaluateHealth(prevRunSummary, currentRunStats) → { status, reason }`.
`reason` — человекочитаемая строка для лога/админки, а не код ошибки: следующий, кто разбирает
инцидент, должен понять причину без похода в код.

## Сигналы деградации, которые стоит проверять

Не все обязательны — набор зависит от природы источника, но эти три покрывают большинство
случаев scraping/sync:

1. **Пусто после непустого.** Прошлый прогон нашёл что-то, текущий — ноль. Самый дешёвый и самый
   надёжный сигнал: пустой результат после пустого — это не тревога (нечего терять), а вот
   непустой → пустой почти всегда значит «страница перестала парситься».
2. **Резкое падение доли извлечённых значений.** Источник находит записи, но доля тех, где
   удалось извлечь целевое значение (цену, дату, статус), упала в разы относительно прошлого
   прогона. Порог «упала более чем вдвое» — рабочая эвристика: защищает от ложных срабатываний
   на естественных колебаниях рынка/данных, но ловит структурный слом парсинга.
3. **Значения вообще не меняются при непустом результате.** Если прогон нашёл записи, но ни одно
   отслеживаемое значение не изменилось — это чаще подозрение на то, что парсер зациклился на
   кэше/заглушке страницы, чем на «рынок стабилен». Стабильный рынок и сломанный парсер выглядят
   похоже только в моменте одного прогона; накопленная история отличает их надёжно.

Каждый сработавший признак добавляет причину в список `reasons` — финальный `reason` не
единственная причина, а объединение всех, что сработали в этом прогоне.

## Эскалация: один DEGRADED — предупреждение, два подряд — выключение

Правило asymmetric: единичный подозрительный прогон переводит источник в `DEGRADED`, но не
отключает его — единичный сбой может быть флуктуацией (таймаут, временная недоступность
страницы). Только если **следующий** прогон снова подозрителен (`prev.status === 'DEGRADED'`
на входе), статус эскалирует в `DISABLED`.

Смысл: одна ложная тревога не должна останавливать сбор данных, а вот два подряд — почти
наверняка не совпадение, и дальнейшие прогоны при сломанном источнике только зашумляют данные
мусором. `DISABLED` — терминальный статус, требующий ручного вмешательства (не автоматический
возврат в `ACTIVE` при следующем удачном прогоне), потому что причина поломки (смена вёрстки,
новый формат страницы) сама себя не чинит — молчаливый автовозврат замаскировал бы то, что
источник всё ещё сломан и просто иногда что-то находит.

## Какую историю прогонов нужно хранить

Функция чистая и принимает `prev` параметром — значит истории прогонов нужна ровно одна запись
на источник: сводка предыдущего прогона, а не полный лог. Минимальная модель вида `SourceRun`
(или поле-сводка на самом источнике):

- агрегаты прогона, по которым считаются сигналы (найдено записей, из них с извлечённым
  значением);
- вычисленный `status` этого прогона — он же становится `prev.status` для следующего вызова,
  на нём держится эскалация;
- `reason` — для истории/аудита, не участвует в вычислении следующего статуса;
- timestamp прогона — для «источник не запускался N дней» отдельно от «источник запускался, но
  деградировал».

Для полноценного аудита полезно хранить не только последнюю сводку, а короткую историю прогонов
(последние N), но для самой функции детектора достаточно одной предыдущей записи.

## Куда встраивать вызов

Вызывается сразу после прогона источника, до записи результата в БД: новый статус пишется вместе
с данными этого прогона, а не отдельным проходом. При `DISABLED` — down-stream код, использующий
данные источника (например, формирование списка кандидатов), должен явно проверять статус и
пропускать отключённые источники, а не полагаться на то, что они сами перестанут отдавать данные.
