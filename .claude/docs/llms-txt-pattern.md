# `llms.txt` — когда заводить, статикой или роутом, что туда писать

[llmstxt.org](https://llmstxt.org) — плоский указатель для LLM-краулеров и агентов, лежащий в
корне домена (`/llms.txt`), рядом с `robots.txt` и `sitemap.xml`. Формат намеренно бедный:
заголовок первого уровня, блок-цитата с одним абзацем описания, дальше разделы `##` со списками
ссылок с пояснением после двоеточия. Смысл — дать агенту компактный обзор за один запрос, чтобы
он не выяснял структуру сайта обходом страниц.

В монорепо на 2026-09-02 файл есть у двух приложений, реализован двумя разными механизмами:

- [`apps/form-docs/src/app/llms.txt/route.ts`](/apps/form-docs/src/app/llms.txt/route.ts) —
  route handler;
- `apps/aboi/public/llms.txt` — статический файл (приватный submodule).

Ниже — по какой оси между ними выбирать и что в файле уместно.

## Когда файл нужен, а когда нет

**Нужен** публичному приложению, у которого есть содержимое, которое агенту имеет смысл читать:
документация библиотеки, магазин с каталогом, лендинг с описанием продукта, публичный
контент-сайт. Признак — у приложения уже есть `sitemap.ts`/`robots.ts` и его страницы
рассчитаны на индексацию.

**Не нужен:**

- админкам и внутренним инструментам (`dashboard`, `studio`, `auth-hub`) — там нет публичного
  контента, а описывать структуру закрытого приложения означает бесплатно отдать разведданные;
- приложениям целиком за авторизацией — агенту всё равно нечего прочитать без сессии;
- приложениям, у которых публична одна страница: обзор длиннее самой страницы бессмыслен.

Отсутствие файла — не пробел, который нужно закрывать «до полного покрытия». Файл окупается
там, где у сайта есть структура, которую нужно объяснить.

## Ось выбора: статика или роут

**По умолчанию — статика: `public/llms.txt`.** Роут нужен ровно в двух случаях:

1. **содержимое зависит от БД** — например, список разделов строится по опубликованным
   сущностям, а не по фиксированному набору страниц;
2. **в тексте нужны абсолютные URL, зависящие от окружения** — прод/staging отдают разные
   `BASE_URL`, и ссылки должны совпадать с тем доменом, откуда файл отдаётся.

Во всех остальных случаях роут — лишний слой: тот же текст, но собранный конкатенацией строк в
TypeScript, с потерей читаемости при правках копирайта.

⚠️ **Пункт 2 чаще всего снимается относительными ссылками.** Если писать `- [Каталог](/catalog/)`
вместо `- [Каталог](https://example.com/catalog/)`, файл корректен и на проде, и на staging, и
локально — а значит статики достаточно. Абсолютные URL обязательны только там, где `llms.txt`
указывает **наружу**: на документацию, живущую на другом домене, на npm, на GitHub. Именно
поэтому `form-docs` сделан роутом с константой `PRODUCTION_URL`: все его ссылки абсолютные и
ведут на прод-домен независимо от того, откуда отдан сам файл.

Файл в `public/` Next.js отдаёт как есть с `Content-Type: text/plain`. Роут должен выставить
заголовок сам:

```ts
return new NextResponse(body, {
  headers: { 'Content-Type': 'text/plain; charset=utf-8' },
})
```

## Что писать, а что нет

Формат по llmstxt.org:

```markdown
# Название

> Один абзац: что это и для кого. Без маркетинга — агент читает это как справку.

Необязательные абзацы прозой: правила, которые нельзя вывести из карты ссылок.

## Разделы

- [Каталог](/catalog/): что там лежит
- [Доставка](/delivery/): сроки и стоимость
```

**Список курируется руками.** Соблазн сгенерировать его из уже существующего источника (дерева
MDX через Fumadocs source API, роутов, `sitemap.ts`) — ровно то, чего формат не просит: полное
дерево на 90+ файлов, да ещё с локализованными дублями, превращает обзор в карту сайта.
Карта сайта уже есть, и она машиночитаема лучше — `sitemap.xml`. Дублировать её в `llms.txt`
не нужно. Разбор этого решения — в докстринге
[`route.ts`](/apps/form-docs/src/app/llms.txt/route.ts) form-docs.

**Что уместно кроме ссылок:** правила, которые агент иначе выведет неверно. Например: «цена
считается как площадь формата × ставка бумаги, поэтому у одного товара столько цен, сколько пар
формат+бумага» — это спасает от вопроса «а почему цен несколько». Или: «товар печатается после
оплаты, готовых остатков нет». Ровно то, что человек узнаёт со страницы, а агент — нет.

**Чего не писать:**

- перечисление всех страниц (это `sitemap.xml`);
- маркетинговые формулировки — читатель этого файла на них не реагирует, а место тратится;
- ничего непубличного: файл отдаётся всем, гейта по домену у него нет (см. ниже).

## Машинный контракт — его место именно здесь

Если у приложения есть способ взаимодействия, рассчитанный на программного клиента (structured
data с идентификаторами, `window`-API, публичный JSON-эндпоинт), его описание должно лежать в
`llms.txt`. Иначе агент либо не найдёт его вовсе, либо будет разбирать DOM ради значений,
которые ему готовы отдать явно.

Образец — `apps/aboi/public/llms.txt`, где кроме карты разделов описано:

- где в JSON-LD карточки товара лежат идентификаторы, нужные для покупки (`identifier` каждого
  `offer` — пара `PropertyValue`), и как они соотносятся с выбором формата и бумаги;
- как вызвать `window.__aboi.addToCart(variantId, paperTypeId, quantity)`, что она возвращает
  (`{ ok: true }` / `{ ok: false, error }`) и что вызовы должны идти с сохранением cookies —
  корзина живёт в сессии браузера;
- что это **та же** операция, что делает кнопка на странице, с теми же серверными проверками, и
  отдельного доступа для агентов нет.

Последний пункт — не вежливость, а суть подхода: window-API должен быть тонкой обёрткой над тем
же server action, что дёргает обычная кнопка, а не параллельным путём в обход валидации.
Описание в `llms.txt` тогда честное — оно не обещает привилегий, которых нет. Разбор задачи и
решений — `apps/aboi/PLAN.md` §12 (и там же — почему отдавать карточку товара упрощённым
markdown по `Accept`-заголовку решили **не** делать: `Vary: Accept` ломается о любой слой кеша,
который его не учтёт, а второй рендер тех же фактов расходится с первым молча).

## ⚠️ Текст `llms.txt` — публичный, и подчиняется тем же запретам, что страницы сайта

Файл отдаётся по HTTP кому угодно и индексируется. Поэтому если у приложения есть юридические
ограничения формулировок, они действуют и здесь — а не только в вёрстке, письмах и meta-тегах.

Прецедент: у `aboi` запрещён набор слов из области медицинских утверждений (ФЗ «О рекламе»
ст. 24, точный список — в `.claude/commands/aboi.md`, раздел «Юридические запреты»). Соблазн
написать в `llms.txt` «прозой для агента, это же не витрина» — ошибка: для ФАС это такая же
публичная страница сайта, как любая другая.

То же касается ограничений 152-ФЗ и рекламного законодательства у остальных приложений
([personal-data](/.claude/docs/personal-data.md),
[advertising-law-boundaries](/.claude/docs/advertising-law-boundaries.md)). Правило простое:
всё, что нельзя написать на странице, нельзя написать и в `llms.txt`.

⚠️ **У статического `public/llms.txt` нет env-гейта.** `robots.ts` умеет закрыть staging целиком
(`isProductionDomain()` → `disallow: '/'`), а файл в `public/` отдаётся одинаково на проде, на
staging и локально. Не описывай в нём то, чего ещё нет в проде, и то, что не должно быть видно
до запуска. Нужен гейт — это третья причина сделать роут.

## Ловушки маршрутизации

**next-intl не должен переписывать `/llms.txt`.** В отличие от метаданных-роутов
(`icon`, `apple-icon`, `opengraph-image` — они отдаются **без** расширения в URL и требуют явного
перечисления в matcher, см.
[nextjs-intl-matcher-metadata-routes](/.claude/docs/nextjs-intl-matcher-metadata-routes.md)),
у `llms.txt` расширение в URL настоящее, поэтому стандартное исключение `.*\\..*` в matcher его
уже покрывает. Отдельно добавлять ничего не нужно — но если в приложении matcher написан
перечислением разрешённого, а не исключением, проверь, что `/llms.txt` не уезжает на
`/ru/llms.txt`.

**Route handler в App Router — каталог с точкой в имени.** Путь именно
`src/app/llms.txt/route.ts`: сегмент называется `llms.txt`, точка в имени каталога допустима.
Класть роут в `src/app/llms/route.ts` и надеяться на редирект не нужно — потребители запрашивают
ровно `/llms.txt`.

**Ссылка из `robots.txt` не требуется.** Конвенции «Llms:» в robots нет; агенты запрашивают
`/llms.txt` по фиксированному пути. Достаточно не запрещать его в `disallow`.

## Проверка

```bash
curl -sS http://localhost:<порт>/llms.txt | head -20
curl -sSI http://localhost:<порт>/llms.txt | grep -i content-type   # text/plain
```

Для статики этого достаточно. Для роута дополнительно убедись, что прод-сборка отдаёт его
статически, а не превращает в динамический маршрут: `nx build <app>` и проверить, что маршрут
попал в prerender-манифест (динамический `llms.txt` без причины — лишний рендер на каждый
запрос краулера).

## Статус по приложениям (2026-09-02)

Первая волна — приложения с публичным контентом, у которых уже были `sitemap.ts`/`robots.ts`
(критерий «нужен» выше). Все статикой, все относительными ссылками, кроме случаев, где ссылка
осознанно ведёт наружу (form-example → GitHub, letar-landing → studio/kami как отдельные домены).

**Заведён `public/llms.txt`:** `aboi` (образец, машинный контракт JSON-LD+window-API),
`form-docs` (роут — единственный обоснованный случай, абсолютные URL на прод-домен), `form-example`,
`letar-landing`, `mandala`, `grandslamcup`, `aira-web`, `animatrona-landing`,
`kami-key-the-landing`, `kami`, `archetest`, `dsperevod`, `svoichuzhie`, `aprel8008`, `domwellbes`,
`studio` (граница публичное/кабинет проверена по коду — какие route group реально не читают
`auth()`/`cookies()` на сервере, а не по названиям папок; личный кабинет, бэк-офис и API в файл
не попали), `driving-school` (нет `sitemap.ts`/`robots.ts` — отдельный пробел, зафиксирован
здесь, не устранён), `synth` (честно отражает пустую пока витрину — `gallery` без опубликованных
патчей).

**Сознательно НЕ заведён — противоречит решению владельца:** `animatrona-tracker`. Его
`robots.ts` ставит безусловный `disallow: '/'` — по `PLAN-INFRA-2.md` §33 «каталог/плеер, вся
публичная индексация не задумана» (решение владельца, не техническое упущение). `llms.txt` —
явное приглашение агентам читать и перемещаться по сайту, оно прямо противоречит этому решению.
Черновик файла остался незакоммиченным в рабочем дереве (`apps/animatrona-tracker/public/
llms.txt`) — заводить его нужно только отдельным осознанным решением, не заодно с остальной
пачкой.

**Не нужен:** desktop/Electron без веб-контента, внутренние инструменты (`auth-hub`, `dashboard`,
`dashboard-agent`), dev/test-каркасы, `pravda` (назначение приложения пока не описано).
