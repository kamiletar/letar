# Playwright `testMatch`/`testIgnore`: якорный `RegExp` (`^`) не матчит относительно `testDir`

## Симптом

`project` в `playwright.config.ts`, использующий `testMatch`/`testIgnore` вида `/^staging\//`
(или любой другой якорный `^`-паттерн, рассчитанный на путь относительно `testDir`), либо:

- находит **0 тестов**, хотя файлы физически существуют и лежат ровно там, где ожидается
  (`--list` подтверждает `Total: 0 tests in 0 files`);
- либо, если этот же паттерн стоит в `testIgnore` другого project — **не исключает** файлы,
  которые должен был исключить, и они утекают в project, для которого не предназначены.

## Причина

Playwright матчит `RegExp` (в отличие от glob-строки) против **абсолютного пути файла**, не
против пути, относительного `testDir`. Якорь `^staging\/` подразумевает «путь начинается с
`staging/`» — но абсолютный путь вида `/home/deploy/letar/apps/<app>-e2e/src/staging/foo.spec.ts`
никогда не начинается с `staging/`, поэтому регэксп с этим якорем не совпадает вообще ни с одним
файлом, где бы он ни лежал.

Второй эффект того же корня: `testMatch`/`testIgnore` без якоря (например
`/0[0-3]-.*\.spec\.ts$/`) матчится по **хвосту** абсолютного пути — и файл `staging/00-public-
smoke.spec.ts` случайно совпадает с этим паттерном по имени файла (`00-` в начале basename), хотя
логически должен принадлежать только project'у для `staging/`. Если у соседнего project'а в
`testIgnore` стоит тот же нерабочий якорный regex — он не отсекает этот файл, и тот утекает в
чужой набор тестов.

## Диагностика

```bash
nx e2e <app>-e2e -- --project=<project-name> --list
```

`Total: 0 tests in 0 files` при физически существующих файлах — прямой признак. Сравнить с
`--project` соседнего project'а, который матчит по хвосту без якоря: если целевые файлы
неожиданно там — подтверждает эффект №2.

## Фикс

Заменить якорный `RegExp` на glob-строку — Playwright резолвит glob-строки в `testMatch`/
`testIgnore` относительно `testDir` корректно:

```ts
// ❌ Не работает — RegExp матчится против абсолютного пути
testMatch: /^staging\/.*\.spec\.ts$/,
testIgnore: /^staging\//,

// ✅ Работает — glob-строка резолвится относительно testDir
testMatch: 'staging/**/*.spec.ts',
testIgnore: 'staging/**',
```

`testIgnore`/`testMatch` принимают `string | RegExp | Array<string | RegExp>` — можно
свободно смешивать glob-строки с уже рабочими безъякорными regex в одном массиве (как в
`chromium` project ниже).

## Прецедент

`apps/driving-school-e2e/playwright.config.ts` (2026-08-25, §18.7 M4 — первый живой прогон
staging e2e для `driving-school`): `staging-smoke` project (предназначен именно для прогона
против staging — логин через `dev-session`, не пишет в БД напрямую, в отличие от остальных
ролевых projects) находил 0 тестов из-за `testMatch: /^staging\/.*\.spec\.ts$/`. Одновременно
`shard-core` (`testMatch: /0[0-3]-.*\.spec\.ts$/`, `testIgnore: /^staging\//`) случайно
захватывал `staging/00-public-smoke.spec.ts` по совпадению хвоста имени файла. Оба симптома
исчезли после замены обоих regex на glob-строки (коммит submodule `fa18aa3`).

Найдено живым прогоном через `deploy-agent-dev` — сначала выглядело как «полный набор не
укладывается в 15-минутный таймаут e2e-раннера», и лишь после сужения до одного project'а
вскрылась настоящая причина (0 тестов, а не таймаут одного большого набора).

## Профилактика

При заведении отдельного staging-only project'а (по образцу `auth-hub`/`archetest` —
dev-session вместо прямой записи в БД) — сразу проверять `--list` на реальном числе найденных
тестов, не полагаться на «зелёный `exitCode`» (`--pass-with-no-tests` — поведение Playwright по
умолчанию — даёт `exitCode 0` и на пустом наборе, это ложный зелёный).
