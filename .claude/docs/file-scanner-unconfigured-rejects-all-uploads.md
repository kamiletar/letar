# Ненастроенный `@letar/file-scan` отклоняет ВСЕ загрузки, маскируясь под отказ валидации

Приложение, которое пропускает пользовательские файлы через `receivePrivateFile()`, на стенде без
переменных антивируса отвергает **каждую** загрузку с ответом вида «Файл не прошёл проверку»
(HTTP 422). Выглядит это как придирка к формату файла — проверяют расширение, MIME-тип, magic
bytes, переделывают фикстуру. Формат ни при чём.

## Механизм

`resolveFileScanner()` (`libs/file-scan/src/lib/scanner-resolver.ts`) выбирает сканер по одному
признаку — задан ли адрес настоящего сканера:

```ts
const host = process.env.CLAMAV_HOST?.trim()
if (host) { return new ClamAvScanner({ host, port }) }
if (process.env.ALLOW_FAKE_FILE_SCANNER === 'true') { return new FakeCleanScanner() }
return new UnavailableScanner() // ← сюда попадает любой недонастроенный стенд
```

`UnavailableScanner.scan()` всегда отдаёт `{ status: 'SCAN_FAILED', resultCode:
'SCANNER_NOT_CONFIGURED' }`. Это **намеренное** поведение: «не настроен — значит не пропускаем»,
fail-closed. Файл остаётся в карантине, `stored.status !== 'CLEAN'`, роут отвечает 422.

Ловушка — в тексте ответа. Пользователю (и агенту, который гоняет живой сценарий) видно только
«Файл не прошёл проверку», без различия между «антивирус нашёл заразу», «антивирус недоступен» и
«антивируса нет вовсе». Первое прочтение всегда неверное.

## Почему это не ловится ничем, кроме живого прогона

- Сборка зелёная: переменных окружения она не касается.
- Типы зелёные: сканер резолвится в рантайме.
- Юнит-тесты зелёные: в них `FakeCleanScanner` передаётся явно.
- Локально всё работает: в `.env.local` обычно стоит `ALLOW_FAKE_FILE_SCANNER=true`.
- Прод работает: там настоящий `CLAMAV_HOST`.

Ломается ровно одно окружение — то, чей compose писали копированием прод-файла **до** появления
антивируса либо без внимания к блоку `environment`.

## Что проверять

Симптом — 422 на любом файле, включая заведомо валидный. Проверка за секунду:

```bash
docker exec <app>-staging-app sh -c 'env | grep -E "CLAMAV_HOST|ALLOW_FAKE_FILE_SCANNER"'
```

Пусто — диагноз подтверждён. В `docker-compose.staging.yml` нужна одна из двух строк:

- `CLAMAV_HOST: letar-clamav` — если контейнер антивируса доступен стенду **по сети** (он живёт в
  `kami-network` на s2; стенд в своей сети до него не достанет — мало прописать имя);
- `ALLOW_FAKE_FILE_SCANNER: "true"` — заглушка «всё чисто» для стенда без антивируса.

⛔ Вторая строка не должна появиться в `docker-compose.production.yml` ни при каких обстоятельствах:
там она молча отключает антивирусную проверку живых загрузок. Сравнение строго со `'true'` в
резолвере — защита ровно от этого: случайная `ALLOW_FAKE_FILE_SCANNER=1` в чужом окружении
заглушку не включит.

## Соседний дефект того же деплоя

Стенд, чей compose-файл отстал от прод-версии, обычно отстал не в одном месте. Здесь вместе со
сканером не хватало и тома `private-uploads` — без него `LocalPrivateFileStorage` пишет байты в
writable-слой контейнера, `PrivateFileObject.status` при этом остаётся `CLEAN`, а файлы исчезают
на следующем деплое. Проверяя `environment`, сверь заодно `volumes:` целиком со своим
`docker-compose.production.yml`.

⚠️ И помни про uid: свежесозданный docker'ом bind-mount принадлежит `root:root`, а контейнер
ходит под непривилегированным пользователем — первая же запись упрётся в `EACCES`
([docker-bind-mount-uid-gid-mismatch](/.claude/docs/docker-bind-mount-uid-gid-mismatch.md)).
