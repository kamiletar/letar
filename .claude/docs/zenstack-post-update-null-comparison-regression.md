# ZenStack: nullable post-update, ошибка типов 3.9.8 и обход запрета 3.10.3

## Наблюдение 2026-11-21

Общий test-прогон при обновлении зависимостей выявил падение Flora
`src/platform/db/policies.int.spec.ts`: пользователь смог назначить себе OPERATOR.
Схема разрешает обновлять собственный User, но запрещает смену роли:

```zmodel
platformRole PlatformRole?
@@allow('read,update', auth() != null && auth().id == this.id)
@@deny('post-update', (auth() == null || !auth().isOperator) && before().platformRole != platformRole)
```

Проверка на одной локальной БД и одной сгенерированной схеме с двумя установленными
версиями ORM/PolicyPlugin, отдельным пользователем на каждый запрос:

| Версия | Запрос `null → OPERATOR` | Роль после запроса |
| ------ | ------------------------ | ------------------ |
| 3.9.8  | отклонён                 | null               |
| 3.10.3 | выполнен                 | OPERATOR           |

Auth содержит `isOperator: false`. Временные записи удалены в `finally`.
Первоначальное репро не различало отказ политики и ошибку БД. Разбор 2026-11-22 ниже
уточняет причину: у 3.9.8 это SQLSTATE 42883, а у 3.10.3 — пропущенный запрет при NULL.
Сохранность строки на 3.9.8 сама по себе не доказывает работоспособность политики.

## Уточнение 2026-11-22: две разные проблемы

В npm у `@zenstackhq/orm`, `@zenstackhq/plugin-policy` и `@zenstackhq/cli` канал `latest`
по-прежнему указывает на 3.10.3. Более новый опубликованный фикс не найден.
[Release notes 3.10.3](https://github.com/zenstackhq/zenstack/releases/tag/v3.10.3)
описывают исправление Better Auth; исправления nullable post-update там нет.

Минимальное воспроизведение не использует модели приложения: `User(id, name, role Role?)`,
`Role = MEMBER | ADMIN`, auth-контекст `{ id, isAdmin }` и правила:

```zmodel
@@allow('read,update', auth() != null && auth().id == id)
@@deny('post-update', !auth().isAdmin && before().role != role)
```

Обе версии ORM и PolicyPlugin запускались согласованными парами на одной сгенерированной
схеме. В PostgreSQL создавалась отдельная случайно именованная схема; она удалялась в `finally`.
После каждого запроса проверялись и роль, и имя. Ошибка различалась по `reason`/`dbErrorCode`.

| Операция обычного пользователя                       | 3.9.8           | 3.10.3            | 3.10.3 с явными NULL-проверками  |
| ---------------------------------------------------- | --------------- | ----------------- | -------------------------------- |
| `null → ADMIN`                                       | ошибка БД 42883 | разрешена — обход | отказ политики, строка сохранена |
| `ADMIN → null`                                       | ошибка БД 42883 | разрешена — обход | отказ политики, строка сохранена |
| `MEMBER → ADMIN`                                     | ошибка БД 42883 | отказ политики    | отказ политики, строка сохранена |
| Изменение имени, роль остаётся `null`                | ошибка БД 42883 | разрешено         | разрешено                        |
| Изменение имени без передачи поля роли               | ошибка БД 42883 | разрешено         | разрешено                        |
| Изменение имени, роль остаётся `ADMIN`               | ошибка БД 42883 | разрешено         | разрешено                        |
| Разрешённая смена `null → ADMIN` при `isAdmin: true` | разрешена       | разрешена         | разрешена                        |

В исходной 3.9.8 сравниваются `text` из таблицы значений `$before` и нативный enum:

```sql
coalesce("$before"."role" != "User"."role", false) = false
```

PostgreSQL возвращает `operator does not exist: text <> "Role"` (42883).
Это блокирует также разрешённые изменения имени, пока требуется вычислить этот запрет.

В поставке 3.10.3 `ExpressionTransformer._binary()` обнаруживает `before()` enum-поля
через `isBeforeEnumField()` и приводит обе стороны к `text`:

```sql
coalesce(cast("$before"."role" as text) != cast("User"."role" as text), false) = false
```

Ошибка типов исчезает. Но сравнение двух SQL-выражений с одним NULL даёт NULL;
`buildIsFalse()` превращает его в false через `coalesce`, и запрет считается невыполненным.
Специальная обработка в `transformNullCheck()` есть для сравнения с **литералом** null,
а не для двух nullable выражений. Поэтому явные проверки null устраняют обход в данном репро.
Это объясняет наблюдаемый эффект обновления; оно не доказывает, что проблема NULL впервые
возникла именно в 3.10.3 или что она ограничена enum-полями.

## Проверенный обход для 3.10.3

```zmodel
@@deny('post-update', !auth().isAdmin && (
  (before().role == null && role != null) ||
  (before().role != null && role == null) ||
  (before().role != null && role != null && before().role != role)
))
```

На 3.10.3 все семь сценариев таблицы дали ожидаемый результат. Этот же вариант на 3.9.8
сохраняет ошибку enum-сравнения 42883: он не является универсальным исправлением старой версии.
Для действительно неизменяемого поля альтернативой служит полевой `@deny('update', ...)`;
его семантику, включая отправку прежнего значения, нужно проверить отдельно.

Исходники и SQL из npm-поставок разобраны локально. Материалы:
`.claude/artifacts/zenstack-post-update-repro/{schema.zmodel,guarded.zmodel,compare.ts,results.json}`.
Итоговый прогон — 28 комбинаций: две версии × две политики × семь сценариев.
Логи содержат только синтетические данные. Доступ к БД нужен вне sandbox; отказ соединения
в sandbox не доказывает, что локальный контейнер остановлен.

Это диагностика и проверка обхода, **не** разрешение обновить всё монорепо.
Политики приложений, nested/bulk writes и весь набор тестов Flora с кандидатом ещё не проверены.
Перед снятием пина нужно выбрать upstream-фикс или провести отдельный аудит nullable-сравнений,
применить защиту в затронутых схемах и проверить разрешённые/запрещённые операции.

## Защита обновлений

Семейство `@zenstackhq/*` закреплено на 3.9.8 в корневых dependencies/devDependencies,
overrides и resolutions. Одного точного корневого пина недостаточно: workspace-потребители
с caret-диапазоном могут получить отдельную новую копию.
Причины и условие снятия каждого пина зарегистрированы в `scripts/intentional-pins.json`.

Отслеживание исправления — LT-087. Пин остаётся временной мерой с известным функциональным
дефектом 42883, а не доказанной исправной реализацией nullable post-update.
Перед снятием пинов проверить именно отказ политики (не произвольный catch),
неизменность строки после отказа и успешное разрешённое обновление пользователя.
Снимать все пины и overrides семейства одновременно. До этого обычный deps-update
не должен возвращать 3.10.3 автоматически.

Локальные материалы: `.claude/artifacts/deps-nov21-flora-policy-compare.ts` и логи LT-086.
Исходный тест и схема остаются в приватном submodule Flora; его исходники в рамках
обновления зависимостей не изменялись.
