# Traefik → Node: пачки 502 из-за гонки keep-alive

⚠️ Симптом выглядит как «флакающий e2e» или «иногда не грузится страница», а не как ошибка прокси.

## Симптом

- Traefik отвечает `502` за 10–600 мс, **пачками**: несколько запросов в одну миллисекунду, в
  том числе на статические JS-чанки `/_next/static/chunks/*` и на server actions (`POST`).
- Контейнер приложения жив: `RestartCount=0`, не OOM, healthcheck зелёный.
- В логе приложения ничего нет. В логе Traefik на уровне `INFO` есть только строка access-лога
  с `502`, причину он не пишет.
- Последствия в браузере зависят от того, какой запрос попал под 502:
  - JS-чанк → страница не гидратируется: вкладки не переключаются, клик по карточке не
    навигирует, `toBeVisible` у элементов на другой вкладке ждёт до таймаута теста;
  - RSC-запрос (`?_rsc=`) → клиентская навигация не происходит;
  - server action → действие молча не выполнилось.

Замер 2026-09-23 на staging (s1), одно приложение под полным e2e в 4 воркера: **225 ответов 502
за 3 часа**. Оба воспроизводимых падения прогона (длинный сценарий воронки и переход в карточку
каталога) упирались в 502 на чанках, баги приложения там не было.

## Механизм

| Сторона          | Что делает с простаивающим соединением              | Дефолт |
| ---------------- | --------------------------------------------------- | ------ |
| Traefik → бэкенд | держит в пуле и переиспользует (`idleConnTimeout`)  | 90 с   |
| Node HTTP-сервер | закрывает после простоя (`server.keepAliveTimeout`) | 5 с    |

Между 5-й и 90-й секундой простоя Traefik считает соединение живым, а Node его уже закрыл или
закрывает прямо сейчас. Запрос, отправленный в такой сокет, получает `EOF`/`ECONNRESET`, и Traefik
отдаёт клиенту `502`. Пачками потому, что соединения открываются пачками: браузер при загрузке
страницы запрашивает десятки чанков сразу, через 5 секунд простоя Node закрывает их все
одновременно.

Под нагрузкой проявляется чаще: больше соединений в пуле, чаще паузы ровно около 5 секунд.

## Фикс

Одна из сторон должна закрывать простаивающее соединение **раньше** другой: либо Node держит
дольше, чем Traefik, либо Traefik — меньше, чем Node.

**На стороне приложения** (Next.js standalone читает переменную в `server.js`,
`node_modules/next/dist/build/utils.js`):

```yaml
# docker-compose.{production,staging}.yml → services.app.environment
KEEP_ALIVE_TIMEOUT: '95000' # больше 90 с Traefik
```

Литерал в `environment:` допустим: это не секрет и не `NEXT_PUBLIC_*`, на этапе сборки не нужен.

**На стороне Traefik** (статический конфиг, для всех бэкендов разом, требует перезапуска
контейнера Traefik — см. [traefik README](/infra/traefik/README.md)):

```yaml
serversTransport:
  forwardingTimeouts:
    idleConnTimeout: 4s # меньше 5 с Node
```

Системно правильнее второй вариант: он закрывает гонку для всех Node-приложений за прокси, а не
только для того, у кого прописана переменная. С 2026-09-23 он стоит во всех трёх статических
конфигах (`infra/traefik/traefik.{s1,s2,}.yml`, решение владельца). `KEEP_ALIVE_TIMEOUT` у одного
приложения остался вторым рубежом: если `serversTransport` когда-нибудь уберут, это приложение
гонку не получит.

⚠️ Статический конфиг смонтирован **файлом** из git-чекаута сервера. Правка доезжает так: push →
`git pull` на сервере → `docker restart traefik` → в `docker logs traefik` свежая строка
`Traefik version …` и нет `ERR` про конфиг.

## Как проверить

```bash
# число 502 по бэкендам (access-лог Traefik в CLF, имя роутера — предпоследнее поле)
docker logs --since 3h traefik 2>&1 | grep '" 502 ' | awk '{print $(NF-2)}' | sort | uniq -c
# действует ли переменная в контейнере
docker exec <app>-app sh -c 'env | grep KEEP_ALIVE'
```

⚠️ На s2 access-лог Traefik в stdout не пишется, так что посчитать 502 на проде этой командой
нельзя. Отсутствие строк там не значит, что 502 нет.

В трассе Playwright (`trace.zip` → `*.network`) 502 на `/_next/static/chunks/*` сразу объясняет
«элемент есть в DOM, но hidden» и «клик не навигирует».
