# ZenStack v3: обязательная relation через nested select тихо резолвится в `null`, если запрещена policy связанной модели

## Симптом

Модель A открыта на чтение всем (`@@allow('read', true)`) и имеет **обязательную** (не
`optional`) связь на модель B, у которой read-политика уже уже (например `isPublished`/staff-only).
Запрос вида:

```typescript
db.a.findMany({
  where: { ... },
  select: { b: { select: { id: true, ... } } },
})
```

под клиентом, которому политика B запрещает конкретную связанную строку, возвращает строку A как
обычно — но поле `b` в ней равно `null`. Сгенерированный TypeScript-тип при этом обещает
non-null объект, потому что в `schema.zmodel` связь объявлена обязательной. Ни исключения, ни
предупреждения, ни отличия в форме ответа от «всё ок» — просто `null` там, где типы говорят
«не бывает».

## Причина

Та же механика, что в [zenstack-self-only-user-policy-staff-picker](/.claude/docs/zenstack-self-only-user-policy-staff-picker.md):
read-политика ZenStack — построчный WHERE, подмешиваемый в запрос, а не проверка допуска перед
операцией. В этом случае WHERE подмешивается не в сам запрос к A (у A `read: true`, там фильтровать
нечего), а в **JOIN на relation внутри `select`** — и там же и применяется. Если строка B не
проходит политику, JOIN просто не находит совпадения — ровно как обычный `LEFT JOIN` без строки
справа. Разница с self-only-находкой по `User`: там непрошедшие политику строки **исчезают** из
`findMany`-результата целиком; здесь непрошедшая строка **связанной** модели не может утащить за
собой родителя (у родителя своя, более широкая, политика) — поэтому родитель остаётся в выдаче,
а его поле-связь превращается в `null` вопреки объявленной в схеме обязательности.

## Практические следствия — оба неочевидны из одного взгляда на код

1. **Краш на конкретных данных, не на коде.** Любое место, которое наивно делает `row.b.id` без
   проверки на `null` (типы это разрешают — TypeScript верит схеме, а не рантайм-политике),
   получает `TypeError: Cannot read properties of null` только тогда, когда рядом с опубликованной
   записью B появляется черновик/неопубликованная. Это типичная ситуация постепенного наполнения
   каталога, а не гипотетический edge case — баг не ловится ни при разработке на пустой БД, ни при
   тестах с одними опубликованными фикстурами.
2. **`take`/лимит в запросе считает по строкам родителя (A), не по видимым после политики строкам
   B.** Отфильтрованные (обнулённые) связи всё равно съедают слот лимита — на выходе можно
   получить меньше элементов, чем `take`, даже если данных в БД достаточно для полного набора.
   Это не пропадающие строки (их и не было в смысле «должны были быть» — A прочитан правильно),
   а недобор относительно ожидания «лимит = N видимых результатов».

## Решение

Не полагаться на `take` в самом запросе, если у relation внутри `select` политика уже, чем у
корневой модели:

1. Выбрать **с запасом** (например ×3 от нужного количества — эмпирически достаточно, если доля
   отфильтрованных строк невелика; для гарантии в худшем случае нужен отдельный подсчёт или цикл
   дозапроса).
2. `.filter(row => row.b !== null)` **после** выборки, до применения лимита в коде.
3. `.slice(0, LIMIT)` — уже после фильтрации, не в запросе.

```typescript
const CROSS_SELL_LIMIT = 8
// WorkMaterialNorm.read открыт всем и не знает о Material.isPublished — черновой материал
// в той же работе съедает слот take, а под анонимной policy-фильтрацией его material
// резолвится в null (не отфильтровывается на уровне запроса). Берём с запасом и
// фильтруем/обрезаем уже после выборки.
const CROSS_SELL_OVERFETCH_LIMIT = CROSS_SELL_LIMIT * 3

const related = await db.workMaterialNorm.findMany({
  where: { workId: { in: workIds }, materialId: { not: materialId } },
  select: { material: { select: { id: true /* ... */ } } },
  take: CROSS_SELL_OVERFETCH_LIMIT,
})

return related
  .map((row) => row.material)
  .filter((material): material is NonNullable<typeof material> => material !== null)
  .slice(0, CROSS_SELL_LIMIT)
```

Типизировать это явно (`NonNullable<typeof material>` в type guard `filter`), а не полагаться на
сгенерированный тип поля — он лжёт относительно рантайм-поведения под policy-фильтрацией.

## Где искать похожие места

Любая модель с `@@allow('read', true)` (или другой широкой read-политикой), у которой есть
**обязательная** relation на модель с более узкой read-политикой, и код делает `select`/`include`
этой связи внутри `findMany`/`findFirst` с `take`/лимитом. Признак в схеме — открытая политика на
одной стороне связи и `isPublished`/staff-only/`isActive`-подобная на другой, без `?` у поля
связи.
