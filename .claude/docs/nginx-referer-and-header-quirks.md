# nginx: `valid_referers` через `include` не парсится, `proxy_ignore_headers` не убирает заголовок

⚠️ Две независимые находки на образе `nginx:alpine` (проверено на 1.31) — обе всплыли при
добавлении access-control в `infra/gateway-cache/nginx.conf` (§57 `PLAN-INFRA-3.md`), обе не
дают ошибки на этапе, где их естественно было бы поймать (конфиг валиден по `nginx -t`, билд
образа проходит) — ловятся только на реальном запросе.

## 1. `valid_referers` внутри `include` — `directive is not allowed here`

### Симптом

```
nginx: [emerg] "valid_referers" directive is not allowed here in /etc/nginx/conf.d/referers.conf:1
```

Ошибка указывает на include'нутый файл, хотя синтаксически директива стоит в допустимом для неё
контексте (`server`/`location`) — просто попадает туда не напрямую, а через `include`.

### Воспроизведено

Минимальный пример, дважды подтверждённый на `nginx:alpine` 1.31:

```nginx
# referers.conf
valid_referers none blocked *.example.com;
```

```nginx
# conf.d/default.conf
location / {
    include /etc/nginx/conf.d/referers.conf;   # ❌ падает при старте
    if ($invalid_referer) { return 403; }
}
```

Та же строка, объявленная напрямую в файле (без `include`) — работает:

```nginx
location / {
    valid_referers none blocked *.example.com;   # ✅ работает
    if ($invalid_referer) { return 403; }
}
```

При этом `include` с другими директивами в том же месте (проверено на `add_header`) отрабатывает
нормально — квирк не в `include` вообще, а специфичен для парсинга `ngx_http_referer_module`:
похоже, что этот модуль при разборе конфига требует контекст, который include-механизм не
сохраняет так же корректно, как у большинства директив.

### Фикс/обход

Не выносить `valid_referers` в отдельный `include`-файл. Если значение директивы должно
подставляться без коммита в git (домены-потребители, секретные значения) — использовать
`envsubst`-шаблон (официальный механизм образа `nginx`, `/etc/nginx/templates/*.template` →
`docker-entrypoint.sh` рендерит в `conf.d/*.conf` при старте контейнера), а не `include`
отдельного файла с директивой внутри:

```nginx
# default.conf.template — сам файл коммитится, значение подставляется из переменной окружения
valid_referers none blocked ${GATEWAY_VALID_REFERERS};
if ($invalid_referer) {
    return 403;
}
```

Реализация — `infra/gateway-cache/nginx.conf` (комментарий на месте директивы).

## 2. `proxy_ignore_headers` не убирает заголовок из ответа клиенту

### Симптом

Клиент получает в ответе **два** заголовка `Cache-Control` одновременно — свой (заданный через
`add_header` в конфиге) и пришедший от апстрима нетронутым. Браузер/curl показывают дублирующийся
заголовок, поведение кеширования непредсказуемо (зависит от того, какой из двух клиент учтёт).

### Причина

`proxy_ignore_headers <Header>` управляет только тем, **ориентируется ли сам nginx** на этот
заголовок при принятии внутренних решений (например, при `proxy_cache` — не начинать кеширование
из-за `Cache-Control: no-cache` от апстрима). Он не убирает заголовок из ответа, который nginx
проксирует клиенту дальше — апстримный заголовок как пришёл, так и уходит в ответ, просто
**вдобавок** к тому, что добавляет сам nginx через `add_header`.

Если цель — не просто игнорировать заголовок апстрима внутри nginx, а полностью **заменить** его
своим значением в ответе клиенту, нужна отдельная директива:

```nginx
proxy_ignore_headers Cache-Control Expires Set-Cookie;   # не решать на основе заголовков апстрима
proxy_hide_header Cache-Control;                          # не пропускать заголовок апстрима клиенту
add_header Cache-Control "public, max-age=31536000, immutable";  # свой заголовок вместо него
```

Без `proxy_hide_header` клиент реально получал бы `Cache-Control: public, max-age=31536000,
immutable` (свой) и `Cache-Control: public, max-age=29030400, immutable` (от Kubo) одной строкой
через запятую или как два отдельных заголовка — обнаружено вживую на реальном постере
IPFS-шлюза, не в синтетическом тесте.

### Смежная ловушка: `add_header` и коды ошибок

`add_header` по умолчанию применяется только к ответам `200`/`201`/`204`/`206`/`301`/`302`/`303`/
`304`/`307`/`308` — **не** к `4xx`/`5xx`, если не указан флаг `always`. Это можно принять за баг
(«почему мой заголовок не долетает до 403»), но здесь это скорее подстраховка: `add_header
... always` на кеш-заголовке навесил бы `Cache-Control: public, max-age=31536000, immutable` и на
`403` от `valid_referers`/`if` — то есть браузер закешировал бы отказ доступа как immutable на
год. Для заголовка, который должен относиться только к реально отданному контенту (не к отказам
доступа), `always` использовать не нужно — это единственный случай в этом же конфиге, где
отсутствие `always` осознанно, а не недосмотр.

## Применимость

Оба квирка воспроизведены и закрыты в `infra/gateway-cache/nginx.conf` (кеширующий прокси перед
IPFS-шлюзом animatrona-tracker, §57 `PLAN-INFRA-3.md`) — единственное место монорепо на 2026-09-08,
где `valid_referers` подставляется динамически и где `proxy_pass` идёт на апстрим с собственными
кеш-заголовками. `infra/media-server/nginx.conf` использует похожий access-control по Referer, но
без `proxy_ignore_headers`/`add_header Cache-Control` — там второй квирк не проявляется.
