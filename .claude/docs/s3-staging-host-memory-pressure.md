# s3 (staging/e2e-хост) — узкое место RAM, не CPU

**Дата находки:** 2026-08-27/28. Разбор долгих и нестабильных staging-сборок/e2e на s3
(наблюдалось на dsperevod: 1м22с локально → 4.8 мин на s3 → 14.4 мин на s3 под пиком).

## Root cause

s3 держит **42 контейнера** и до **16 постоянных `next-server`** (штатные staging-инстансы всех
приложений, не утечка — проверено предметно: у каждого `cwd` внутри контейнера
`/app/apps/<app>`, это обычный `next start`). На хосте 15Gi RAM.

Сборка запускается с `NODE_OPTIONS=--max-old-space-size=8192` — просит до 8Gi при обычно
~8.6Gi `available`. При параллельной нагрузке (staging-контейнеры + сборка, или сборка + e2e)
система уходит в **swap** (замерено: `Swap 7.7/8.0Gi`, почти исчерпан), а не упирается в CPU —
`vmstat` в этот момент показывает **~80% простоя CPU**, при этом `load average` 5-13, потому что
процессы стоят в `D`-состоянии (uninterruptible sleep, ждут диска под свопом).

`ipfs daemon` — не узкое место: `20.8% CPU` в `ps aux` — это доля **одного** ядра при 12 ядрах
на хосте, то есть ~1.7% машины. Ранняя гипотеза (CPU s3 слабее — Broadwell 2014-15 против
Cascade Lake на s2) частично верна (частота ниже), но не объясняет разброс в разы — при живом
CPU-простое разница не может быть в CPU-мощности.

## Практическое следствие

- Видишь неожиданно долгую сборку/e2e на s3 — сначала `free -h`, потом `uptime`/`load`, а не
  наоборот. Load без насыщенного CPU (`vmstat` `id` высокий) — верный признак свопа, не
  вычислительной нагрузки.
- **Не запускай staging-деплой и e2e на s3 одновременно** — оба процесса просят до ~8Gi,
  вместе не помещаются в ~8.6Gi available. s3 и так залочен на одну операцию через deploy-mcp
  (`deploy_app`/`run_e2e` отклоняют друг друга сообщением «Хост занят другой операцией»), но при
  ручном SSH-обходе агента эта защита не действует — держи то же правило вручную.
- Полученная проблема с приложением (например «dsperevod долго собирается») почти всегда не
  про приложение — сравнение сборки одного и того же коммита на одной машине (locally vs s2 vs
  s3) даёт разброс в разы только за счёт хоста, не кода. Прежде чем копать в приложении —
  сравни билд на другом хосте.

## Известные меры

- Плановая проверка `free -h`/`uptime` перед постановкой очередной s3-операции в очередь —
  практика, принятая deploy-agent-dev после этого инцидента.
- Возможные будущие шаги (не реализованы на момент записи): добавить RAM на s3, сократить число
  одновременно живых staging-контейнеров, вынести e2e-раннер на отдельный хост.
