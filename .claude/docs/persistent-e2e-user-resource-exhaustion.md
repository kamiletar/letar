# Персистентный e2e-пользователь исчерпывает конечный ресурс приложения

## Паттерн

E2E-тест, который логинится под одной и той же фиксированной identity (email/аккаунт,
захардкоженный в тесте) против персистентного окружения (staging-БД, которая не
пересоздаётся между прогонами CI), со временем исчерпывает **любой** конечный ресурс,
который приложение отслеживает per-identity как «уже использовано/показано/потрачено».

Вопросы квиза (см. ниже) — только один конкретный случай. Тот же механизм ломает
что угодно с той же формой «список того, что этому пользователю больше не выдаём»:
одноразовые купоны, инвайт-коды, rate-limited действия, строки с уникальным
constraint («один отзыв на заказ», «одна попытка в день»), лимитированные квоты.

## Почему это коварно

Симптом неотличим от настоящей регрессии в коде, который тест должен проверять:

- падение детерминированное — воспроизводится на каждом прогоне, не флейк;
- падает конкретно на финальной проверке (assertion), а не на таймауте внутри
  сценария — весь пользовательский флоу до этого момента отрабатывает штатно;
- падает одинаково на всех браузерах сразу (не webkit-specific гонка).

Все три признака — ровно то, что обычно означает «сломался код, который задеплоили».
Настоящая причина — накопленное за десятки ПРОШЛЫХ прогонов состояние одного и того же
тестового пользователя, а не изменение в текущем коммите. Расследование в эту сторону
(git blame, бисект коммитов, чтение диффа) тратит время впустую, пока кто-то не
догадается посмотреть на данные конкретно этого тестового аккаунта.

## Две стратегии фикса

**(a) Новая identity на каждый прогон.** Проще всего реализовать — тест сам создаёт
свежего пользователя/аккаунт перед стартом. Минус: в персистентной staging-БД такие
одноразовые сущности накапливаются бесконечно («плодятся») — растёт объём БД, шум в
админке, сложнее отличить реальные тестовые данные от мусора прошлых прогонов.

**(b) Сброс состояния фиксированной identity перед каждым прогоном** — если у
приложения уже есть легитимная продовая функция для этого (самообслуживание,
удаление своих данных, сброс прогресса). Плюс: одна каноническая тестовая identity,
без разрастания БД. Минус: работает только если такая функция у приложения
действительно есть — специально ради теста создавать её не стоит, это уже другой
компромисс (тестовый код получает эксклюзивный доступ к продовой мутации).

Выбор между (a) и (b) — не универсальный: если у приложения нет пригодного
self-service сброса, придётся либо заводить его, либо смириться с (a) и чистить БД
отдельным процессом.

## Прецедент: safety-net e2e archetest (2026-09-05)

`apps/archetest-e2e/src/safety-net.spec.ts` (коммит `69bf1ac7`) проверяет, что при
высоких DPR/BAR/BOR (кризисные шкалы) на экране результатов появляется блок с
телефонами доверия. Тест логинится через staging-only `/api/auth/dev-session` под
фиксированным `TEST_EMAIL`, персистентным между прогонами (staging-БД не ресетится).

`getRandomQuestionsAction` (`apps/archetest/src/app/[locale]/_actions/quiz.action.ts`)
собирает `excludeIds` — все вопросы, на которые этот пользователь уже отвечал или
которые пропускал за все прошлые сессии — и исключает их из выборки НАВСЕГДА для
этого пользователя. `stratifiedSelect`
(`apps/archetest/src/app/[locale]/_lib/stratified-shuffle.ts`) гарантирует минимум
1 слот на каждую непустую корзину шкалы при формировании порции вопросов — то есть
каждый прогон детерминированно съедает ≥1 вопрос именно из DPR/BAR/BOR, пока в банке
для этого пользователя ещё есть вопросы этих шкал.

DPR/BAR/BOR — маленькие шкалы (43/17/53 вопроса из 2126 в банке, BAR особенно
уязвима). После многих диагностических прогонов подряд против staging (см. тред
`797` в Agent Mail, `project_key c-web-letar`) все три корзины для этого пользователя
опустели одновременно: сессия получала 0 вопросов из триггерных шкал, вычисленный
максимум по ним равнялся 0, нормализованный балл (защищённое деление) — тоже 0.
Safety-net не мог сработать ни при каком выборе ответов в тесте — не потому, что
сломался `showSafetyNet` или сломался текст локатора, а потому, что сам набор
вопросов сессии больше не содержал нужных шкал.

**Отвергнутая альтернатива:** заводить нового тестового пользователя на каждый
прогон — решение (a) выше. Осознанно отклонено ещё раньше, в отдельной сессии
2026-07-29 (см. `apps/archetest/PLAN_COMPLETED.md`): «без плодения тестовых
пользователей в staging».

**Применённый фикс** — решение (b): тест перед стартом квиза вызывает уже
существующую продовую функцию самообслуживания — `deleteMyQuizDataAction`,
реализующую право на удаление по 152-ФЗ, доступную пользователю на `/settings`.
Она полностью сбрасывает прогресс (`QuizSession` и каскадно `QuizAnswer`/
`QuizSkippedQuestion`), `excludeIds` снова пуст, весь банк вопросов — включая
DPR/BAR/BOR — снова доступен для выборки.

## Как заметить заранее

Если e2e-тест логинится под захардкоженным email/логином и приложение где-то ведёт
список «что этот пользователь уже видел/использовал/получил» с исключением по этому
списку — стоит сразу решить, какой из двух подходов применяется, а не ждать, пока
маленький сегмент этого списка исчерпается сам по себе через недели диагностических
прогонов.
