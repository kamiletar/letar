# Локальный скаут: справка агенту на первое сообщение

Скаут по тексту первого сообщения сессии собирает короткую справку: какие доки прочитать, какие
⚠️-ловушки рядом, какой скил, команда или субагент подходит. У каждого пункта `файл:строка`.
Справка — выбор из карточек индекса, а не генерация, поэтому ссылки верны по построению.
План и этапы — [PLAN-INFRA-7.md § §207](/docs/plans/PLAN-INFRA-7.md).

## Почему хук, а не инструмент

`libs/letar-consultant` (удалён в `6aee2e129`) был инструментом «спроси при сомнении» с
правилом в каждой сессии — за 487 сессий его не вызвали ни разу. Агент не зовёт то, о чём его
не спрашивают. Поэтому справку приносит `UserPromptSubmit`-хук, а MCP-инструмент (этап Э2) — только
дополнение, и его вызовы тоже меряются.

**Карточки:** док (slug, заголовок, аннотации из `INDEX.md` и `AGENTS.md`, заголовки секций),
секция дока (заголовок + тело, ссылка на её строку), правило `.claude/rules/*`, скил, субагент
(frontmatter), поле формы (строка каталога `libs/forms/docs/fields.md`, ссылка на подробный раздел
о компоненте), паттерн формы (реестр `libs/form-mcp/src/data/pattern-registry.ts`, читается
текстом). Доки `libs/forms/docs/*` и `libs/forms/README.md` индексируются как обычные.
`.claude/docs/external/` не индексируется.

**Скилы** берутся из `.agents/skills/*/SKILL.md` (источник). `.claude/skills` — производная копия
(`bun scripts/sync-agent-skills.ts`), её не читаем, иначе каждый скил был бы в индексе дважды.
Вида «команда» больше нет: `.claude/commands` удалён при миграции инструкций 2026-09-30.
В советы **не попадают** (карточка есть, `scope` задан — `collect.ts`, `skillScope`):

- `app` — скил приложения (есть каталог `apps/<имя>`): у приложений своя статическая справка по
  голой `/<app>`;
- `service` — имя в `SERVICE_COMMANDS` (роли агентов, `end-session`, `letar`, `repo`…) или слово
  «устарел» в описании: эти скилы запускает человек;
- `user-only` — `disable-model-invocation: true` во frontmatter: модель такой скил вызвать не может.

Старые имена (`infra:deploy`, `deployment-assistant`…) остались в эталоне `tool-gold.jsonl`,
`eval-cases.jsonl` и истории `sessions-live.jsonl`. Файлы данных не переписываются: имена
переводятся при чтении таблицей `scripts/scout/tool-names.ts` (`TOOL_RENAMES`: новое имя или `null`
для удалённых пунктов — такой ответ эталона считается пустым).

Каждая строка `logs/briefs.jsonl` несёт `scoutVersion` (`INDEX_VERSION` + 8 символов хеша
`libs/scout/src` без тестов и `hook-core.ts`). `report.ts` печатает число справок по версиям и, если
версий несколько, сводку по каждой; `--since <дата>` отрезает период.

**Где лежит состояние** — вне репозитория, в `SCOUT_HOME` (по умолчанию `C:\ai\scout` на Windows):
`index-<hash>.json` (на корень репо, ~3,6k карточек), `vectors.json` + `vectors.f32` (1024 измерения,
~15 МБ), `phrases.jsonl` + `phrase-vectors.*` (формулировки доков и их векторы), `state/<session_id>.json`
(маркер), `logs/briefs.jsonl` и `logs/asks.jsonl` (ротация при 5 МБ или раз в неделю; в логах сырые запросы, поэтому архивы удаляются так, чтобы ни одна строка не жила дольше 90 дней — решение владельца 2026-09-30), `bench/`, `config.json`.

⚠️ **Сменил набор или вид карточек — подними `INDEX_VERSION`** (`libs/scout/src/lib/types.ts`).
Сохранённый индекс пересобирается, только если исходники новее него. Карточки полей форм
добавились кодом, а `fields.md` не менялся — хук полдня отдавал индекс без них, и полка форм
была пустой при зелёном замере (замер собирает индекс заново). Проверочные данные — `SCOUT_DATA` (`C:\ai\data`).

## Хук

- Срабатывает на первое **содержательное** сообщение: короче 15 символов («продолжай», «?») —
  тратит одну из трёх попыток; служебные вставки и голая `/команда` без аргументов — не тратят.
  У `/app задача` ищется по аргументам. Одна справка на сессию.
- Режимы — `SCOUT_HOME/config.json` `{"mode": "shadow" | "on" | "ab"}` или env `SCOUT_MODE`.
  **По умолчанию `shadow`:** справка считается и пишется в лог, агенту не уходит. `ab` — справку
  видит группа A (`sha1(session_id)` чётный), B — контроль, в логе у всех поле `group`.
- **Справка приложения (голая `/<app>`, в тени).** Первое сообщение сессии часто — просто `/<app>`: запроса нет,
  искать не по чему. Тогда, если есть каталог `apps/<app>`, хук берёт из `SCOUT_HOME/app-briefs.json` до 8 доков,
  которые чаще всего читали в сессиях этого приложения (частота — число сессий, не чтений; правила `loaded`
  не входят; у приложения меньше 3 сессий в истории — общий список), с аннотациями из индекса. Состояние сессии
  получает `appBriefed`, `briefed` не трогается: первое содержательное сообщение получит обычную справку. Лог —
  строка `kind: app` с `command` и без `query`; режим и группа те же (в `shadow` только лог). `report.ts` считает
  её отдельной группой `<режим>/<тень|показана>/app`. Замер (`bench.ts --suite app`, деление по дате 70/30,
  K = 8): полнота по приложению ~38%, по общему списку ~33%, сессий с попаданием 58% против 53%.
- Показанная справка: `additionalContext` агенту, одна строка владельцу через `systemMessage`
  («🔎 скаут: 3 дока, 2 ловушки, скил form-pipeline»).
- **Доки и ловушки — гибрид:** BM25 + эмбеддинги + формулировки доков (`phrases`), слияние RRF `k=60`,
  глубина 100. Полка форм — косинус по полям (эмбеддинги), инструмент — BM25. Эмбеддинг запроса ждётся до 1,5 с
  (`EMBED_TIMEOUT_MS`). В логе `forms`: `dense` | `no-vectors` | `embed-down` | `stale-vectors` (векторы
  не сходятся с индексом по хешу — полка по BM25, фоном идёт досчёт); `docs_by` — каким путём найдены доки.
- **Не советуются:** доки, названные в запросе по имени файла (`mentionedIn`), и правила без `paths:`
  (харнесс грузит их сам, `Card.loaded`) — раньше это была треть справки.
- **Справка v2:** один список по очкам (ловушки не уезжают в конец), первые 3 пункта с аннотацией,
  остальные строкой «путь — заголовок»; ~1,3 тыс. символов.
- Задержка (последний прогон бенча): `scoutQuery` p95 68 мс; хук целиком p50 ~190 мс с эмбеддингом и стартом bun
  (сьют `hook`), холодный (пересборка индекса) ~0,7 с.

⚠️ **Внутренний бюджет — `setTimeout` на 2,5 с, но синхронную работу он не прерывает:** таймер
сработает только после неё. Жёсткий предел — `"timeout": 5` у хука в `settings.json`; по нему
харнесс убивает процесс и выбрасывает вывод. Тяжёлого синхронного кода в хуке быть не должно.

⚠️ **Хук запускается через `bun -e` с `await import(...)`, не через `node -e` + `require`** как
остальные: он на TypeScript и импортирует `libs/scout` из исходников. Поиск `.claude/hooks/` вверх
от `cwd` тот же, что у соседей.

## Как мерить и что намерено

⚠️ **67% эталонных доков названы в запросе по имени файла.** Эталон — доки, которые агент прочитал до
первой правки, а первые сообщения — в основном задания-делегирования («по образцу `.claude/docs/x.md`»).
Обычный R@5 (~70%) мерит поиск по имени. Честная метрика — **`нов. R@5`** (только неупомянутые эталоны)
и судейская «по делу@3». Колонки R@5/MRR журнала после прогона `hybrid-docs` несравнимы с прежними:
раньше они считали пропуском док, который агент и так видит.

Последний прогон журнала (`phrases`): нов. R@5 **37,7%** dev / **47,8%** test (BM25 как есть —
30,7 / 37,0), суд. по делу@3 51,3% / 52,7%, справка 1288 символов, `scoutQuery` p95 68 мс.

- **Гибрид +5…+9 п.п. на неупомянутых.** Прежний вывод «гибрид не обогнал BM25» — артефакт смещённого
  эталона. Реранкер 0.6B полноту по неупомянутым снижает — в хук не идёт. Параметры слияния (`k`,
  глубина, вес) и `k1` у BM25 — плато в пределах шума, узкое место не в слиянии.
- **Формулировки (doc2query)** третьим списком: судейская метрика растёт (по делу@3 dev 48,8 → 51,3),
  нов. R@5 +1,7…+2,1 п.п. Прогон без них — `bench.ts --no-phrases`.
- **Судья:** пул как в TREC (первые 5 пунктов вариантов; упомянутые и всегда загруженные не входят),
  эталон — Sonnet, дешёвый — 9B. У 9B κ «по делу» с Sonnet 0,47, но **порядок вариантов у них
  совпадает** → 9B годится для сравнения вариантов, не для абсолютных чисел.
- **Точность по позиции** (гибрид, Sonnet, «по делу»): #1 80%, #2 67%, #3 37%, #4 32%, #5 31% —
  полезны первые два пункта; хвост нужен для полноты, но без полной аннотации.
- Эталон «что агент прочёл» зашумлён: 36% неупомянутых эталонов лежат дальше 50-го места, в основном
  это шум разметки (документирование «по соседству», смена задачи по ходу), а не промах поиска.

⚠️ **Короткая человеческая фраза — слабое место** (R@5 ~32% на фразах < 400 символов): слова
пользователя не совпадают со словами дока. Эмбеддинги и формулировки помогают, но не закрывают.

⚠️ **Эталон инструментов из транскриптов почти бесполезен.** `end-session` агент зовёт в конце любой
сессии, `auth-policy-validator` — в автономных «набери себе задач»: по тексту задачи не предсказать.
Считаются только советуемые эталоны (39 случаев): top-1 15,4%, точность показанного инструмента 25%.

Поэтому есть второй эталон — **судья Sonnet вслепую** размечает, какой инструмент сэкономит работу
в задаче (`C:\ai\data\tool-gold.jsonl`, сьют `tools`). Пересборка: `tool-gold.ts --prepare` пишет
пачки задач без ответов скаута, разметка — руками судьи. Непустой эталон всего у 45 из 438 задач
(10%): большинство задач — «задокументируй», «почини гейт», им инструмент не помогает. Один случай
≈ 2,2 п.п., поэтому сравнивать можно только крупные разрывы. Текущий выбор (первый инструмент
BM25-раскладки, эмбеддинги в нём не участвуют): hit@1 46,7%, hit@3 60%, ложный совет на пустых 18%.

### CLM-8B (2026-09-30): без дообучения проигрывает

[CLM](https://github.com/Contrastive-LM/CLM) — кодировщик Qwen3-8B (вектор последнего токена) +
обученная голова «ситуация ↔ действие». Сьют `clm` гоняет её через наш llama-server без vLLM и WSL:
кодировщик — `llama-server -m Qwen3-8B-Q8_0.gguf --embedding --pooling last` на 8093 (~10 ГБ
видеопамяти, только на время замера), голова перенесена в TS (`scripts/scout/clm.ts`, веса —
`C:\ai\models\clm\head.{json,f32}`, выгружены через `torch.load(weights_only=True)`).

- Инструменты: hit@1 dev 22,9% против 48,6% у текущего, ложный совет 84% против 20% — кандидат
  «ничего» почти никогда не выигрывает.
- Доки: четвёртым списком в слиянии — нов. R@5 dev 35,1% против 37,7%; сама по себе — 11%.
- Голые векторы Qwen3-8B без головы — на уровне случайного: последний токен языковой модели
  не эмбеддинг.
- Задержка кодировщика p95 83 мс — дело не в скорости.

⚠️ **Сверка связки ≠ пригодность для задачи.** Пример из README воспроизводится (0,996 при 0,997 у
авторов), то есть векторы llama.cpp совместимы с головой. Но по-русски тот же вопрос — 0,861:
модель училась на английских траекториях, а у нас русские задачи и описания скилов.

### Что подобрано замером

- `b = 0.9` у BM25 (не стандартные 0,75) и **не больше трёх** дополнительных секций одного дока
  с весом 0,1. Без ограничения длинный док-хаб (`git-multi-agent-incidents.md`, 800+ строк)
  набирал очки с десятков секций и стоял в топ-5 у 347 запросов из 438.
- Карточки секций нужны: без них R@5 падает на 8 пунктов, и ссылка ведёт на начало дока.
- Отсев коротких секций (< 150 / 400 символов) ничего не даёт.

### Полка «Поля формы» и паттерн

На запрос про формы справка начинается с полки компонентов `Form.Field.*`/`Form.Document.*` и
строки «Паттерн формы: `name` — …; код — MCP `get_form_pattern("name")`». Проверочные наборы вне
репозитория: `SCOUT_DATA/forms-probes.jsonl` (36 проб) и `forms-probes-holdout.jsonl` (40 проб,
написаны отдельным агентом вслепую, не видя кода скаута).

| Контрольный набор, 40 проб | полнота полей | полка целиком | паттерн | ложная полка |
| -------------------------- | ------------- | ------------- | ------- | ------------ |
| BM25                       | 59,2%         | 22/40         | 6/14    | 1,2%         |
| эмбеддинги                 | 79,6%         | 31/40         | 11/14   | 4,7%         |

«Ложная полка» — доля из 169 реальных задач не про формы, где полка всё же появилась.

- **Поля ранжируются отдельно от доков.** В общей выдаче тонкие карточки полей тонут среди
  секций доков: только по полям полнота@4 — 88,6% против ~66% из общей выдачи.
- **Порог «запрос про формы» — косинус лучшего поля ≥ 0,55**, или ≥ 0,5 вместе со словами про
  формы в запросе. Одних слов мало: «поле» в длинном поручении — чаще поле БД, с одним словесным
  сигналом ложная полка была 17,8%.
- **У паттернов русские подсказки** (`PATTERN_HINTS` в `libs/scout/src/lib/collect.ts`): описания
  в реестре form-mcp английские, BM25 по-русски их не находил вовсе. Новый паттерн без подсказки
  ловит `scout-smoke`.
- ⚠️ Пороги (`fieldMargin 0,12`, `patternMinCosine 0,53`) подобраны сеткой по обоим наборам —
  контрольный набор после этого уже не вполне слепой. Следующая проверка — онлайн.

Ни один не дал +2 п.п. на test <400 и ни один не уложился в «не хуже −0,5 на всём»; судью 9B

## llama-server

```bash
llama-server -m C:/ai/models/Qwen3-Embedding-0.6B-Q8_0.gguf --embedding --pooling last -ngl 99 -c 8192 -b 2048 -ub 2048 -np 2 --cache-ram 0 --host 127.0.0.1 --port 8090
# необязательно, для судьи и формулировок (~11 ГБ видеопамяти — держать только на время замеров/генерации)
llama-server -m C:/ai/models/Qwen3.5-9B-Q8_0.gguf -ngl 99 -c 8192 -np 1 --cache-ram 0 --host 127.0.0.1 --port 8092
```

Эмбеддер стартует сам при входе в Windows: задача Планировщика `scout-embedder` запускает
`C:\ai\scout\start-embedder.vbs` (та же команда без окна консоли, вывод — `logs/embedder.log`).
Порт занят — второй экземпляр завершается сам. 9B автозапуска нет.

Адрес эмбеддера переопределяется `SCOUT_EMBED_URL`; ~0,7 ГБ видеопамяти. Реранкер боевым путём не
используется (файл модели оставлен для экспериментов, `SCOUT_RERANK_URL`, порт 8091).

⚠️ **`--cache-ram 0` обязателен.** По умолчанию llama-server держит кеш промптов в ОЗУ до 8 ГБ
(`--cache-ram 8192`) и заполняет его и на сервере эмбеддингов: после расчёта векторов процесс
занимал 10,7 ГБ рабочего набора при 0,7 ГБ модели в видеопамяти. Снаружи это выглядит как утечка
памяти «лламы». С `0` — ~1 ГБ на сервер.

## Команды

```bash
bun scripts/scout/build-index.ts            # собрать индекс руками (хук делает это сам)
bun scripts/scout/mine-transcripts.ts       # транскрипты → C:\ai\data\sessions.jsonl (~30 с на 5,7 ГБ)
bun scripts/scout/eval.ts --show 10 --out C:/ai/data/eval-cases.jsonl   # --backend bm25|dense|hybrid|rerank (rerank — эксперимент)
bun scripts/scout/vectors.ts                # досчитать векторы новых и изменённых карточек (секунды)
bun scripts/scout/forms-eval.ts --backend hybrid --probes C:/ai/data/forms-probes-holdout.jsonl --show
bun scripts/scout/ask.ts "<запрос>"          # спросить скаута руками
bun scripts/scout/bench.ts --label <имя> --compare last   # бенч; --compare принимает и метку прогона; --suite judge — судья (нужна 9B на 8092)
bun scripts/scout/tool-gold.ts --prepare    # пачки задач для слепой разметки инструментов судьёй
bun scripts/scout/clm.ts --check            # перенос головы CLM совпадает с эталоном torch (нужен 8093)
bun scripts/scout/warmup.ts                 # прогреть эмбеддер и досчитать векторы
bun scripts/scout/phrases.ts [--generate]   # векторы формулировок; --generate пишет их докам без них (9B)
bun scripts/scout/report.ts --since <дата> [--show 5]   # онлайн: открыл ли агент подсказанное; в режиме ab — строки «A−B» с бутстрэп-интервалом
bun scripts/scout/report.ts --judge [--sample 60]       # онлайн-судья 9B по живым справкам: «по делу@3» с интервалом Уилсона (9B на 8092 поднять и остановить)
bun scripts/scout/app-briefs.ts --build [--sessions <файл>]   # справки приложений; с --app <имя> вместо --build — показать список
bun test scripts/scout                      # тесты скриптов и хука
nx typecheck:tsgo @letar/scout              # типы либы И scripts/scout + хуков (bun-types)
nx test @letar/scout                        # тесты библиотеки
tail -5 C:/ai/scout/logs/briefs.jsonl       # что скаут насчитал в тени
```

⚠️ **`scripts/scout` типизирован через `bun-types`, не `@types/bun`.** Пакет из `@types/*` TS
подключает сам во все tsconfig без поля `types` (их в монорепо десятки) — глобальные типы Bun
разъехались бы по чужим проектам. `bun-types` виден только там, где назван явно
(`scripts/scout/tsconfig.json`).

⚠️ **Разбор транскриптов — только `JSON.parse` по строкам.** В путях Windows внутри JSON `\\`, и
регулярка по сырой строке молча находит ноль совпадений.

⚠️ **Хук `security-guidance` блокирует `Write` файла, где есть `RegExp.prototype.exec`** — он
принимает `re.exec(text)` за `child_process.exec`. В новых файлах скаута использован
`text.match(re)`: для регулярки без флага `g` результат тот же.

## Чек-лист перед включением A/B

⚠️ Режим `ab` этим чек-листом не включается: `{"mode":"ab"}` в `SCOUT_HOME/config.json` — решение
владельца. До него проверь:

1. Индекс свежий: `bun scripts/scout/build-index.ts` (или хук пересобрал сам), `bun scripts/scout/smoke.ts` зелёный.
2. `scoutVersion` одинаков у всех записей периода: `bun scripts/scout/report.ts --since <дата начала>` →
   строка «Версии скаута» показывает ровно одну версию. Правка `libs/scout/src` посреди периода
   меняет её — период надо начинать заново.
3. Эмбеддер на 8090 жив (без него справка собирается по BM25 и группы A и B несопоставимы с базой).
4. `report.ts` на пустом `ab`-логе не падает (проверено тестом `report-stats.test.ts` и прогоном на
   пустом `SCOUT_HOME`).
5. Строка «разница A−B» появляется, когда в логе есть и A, и B. Интервал — бутстрэп по сессиям, при
   десятках сессий он широкий: решение принимать по интервалу, а не по точке.
6. Базовые цифры тени и онлайн-судьи зафиксированы заранее (`report.ts --judge`), чтобы сравнивать с чем-то.
7. Тень пройдена (решение владельца 2026-10-01): полнота по новым ≥ 0,3 и судейская «по делу@3» ≥ 0,4.
   Стоп — верхняя граница интервала Уилсона судьи < 0,4; точка ниже 0,4, а граница выше — тень
   продлевается, пока интервал не сузится.
   Точность «по открытию» здесь не порог: агент открывает ~0,6 дока за сессию, и даже идеальная
   справка из ~8 пунктов упирается в ~7–8%. Она годится только для сравнения A против B.

## Связка сеньор → мидл

Задания скаута пишет сеньор в `.claude/artifacts/tasks/scout-NN-*.md`: цель, решения, файлы, проверка,
запреты. Исполняет агент `middle-dev` ([`.claude/agents/middle-dev.md`](/.claude/agents/middle-dev.md)):
решений не принимает, не коммитит, в конце пишет «Находки» — сеньор заносит их в бэклог
`.claude/artifacts/tasks/BACKLOG.md`. Историю итераций и таблицы держит `bench/lab-notes.md` в
`SCOUT_HOME` (вне репо); здесь — только выводы.
