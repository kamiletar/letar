# Storage backend в @letar/image-upload

## Зачем

Место на диске серверов (s2/s3) уже приходилось разгружать — сборки перенесены на s3, чтобы
кеши/`node_modules` не жили на боевом диске. Рост `uploads/` в приложениях — следующий кандидат
на ту же проблему, но пока некритично: объём небольшой. Чтобы не откладывать архитектурное
решение до момента, когда место реально кончится, `@letar/image-upload/server` получил шов, за
которым позже можно спрятать S3-совместимое хранилище (Minio/Cloudflare R2), не переписывая
бизнес-код приложений.

Аналогия — уже существующий [media-server](/.claude/docs/media-server.md) для видео, но без его
тяжёлой инфраструктуры (очередь BullMQ, ffmpeg-транскодинг): картинкам это не нужно, они не
требуют преобразования нескольких разрешений при загрузке.

## Что есть сегодня

`libs/image-upload/src/server/storage-backend.ts` определяет интерфейс `StorageBackend`
(`stat`/`createReadStream`/`write`/`delete`/`read`) и единственную реализацию —
`createLocalDiskBackend(root)`, тонкую обёртку над той же fs-логикой, что была раньше разбросана
по `serve-uploads.ts` и `image-upload-route.ts`. `createUploadsRoute` и `createImageUploadRoute`
принимают необязательный `backend`; без него подставляется `createLocalDiskBackend`, и поведение
всех текущих потребителей не меняется ни на бит.

**S3/R2-backend не реализован.** Нет выбранного провайдера, нет срочности — реализовывать его
заранее означало бы поддерживать код, который никто не проверил на реальном трафике. Когда
дойдёт очередь, вторая реализация `StorageBackend` подключается точечно, без правок в
приложениях (они не знают о backend'е, если явно не передали свой).

`getVersionedUploadUrl()` (`versioned-upload-url.ts`) в эту абстракцию сознательно **не введён**
— остаётся синхронной функцией на локальном `readFileSync`. Перевод в асинхронный интерфейс
потребовал бы топ-левел `await` в единственном потребителе (`apps/aprel8008/src/lib/comic-assets.ts`,
~30 констант на топ-уровне модуля) ради функции, которая используется только на этапе билда/рендера
для хэширования содержимого, а не в рантайме запроса. Если когда-нибудь понадобится (например,
`aprel8008` переедет на S3), делать это отдельной точечной задачей, не заодно с этой.

## Что осталось вне абстракции — известный долг

Разведка по монорепо (аудит консьюмеров при введении этого шва) показала, что
`@letar/image-upload/server` — не единственный путь записи файлов. Абстракция покрывает только
то, что уже проходит через `createUploadsRoute`/`createImageUploadRoute`. Вне неё:

- **`resolveUploadPath()` + ручной `fs`** — `apps/aboi` (2 места: `lib/print-source.ts`,
  `lib/images/upload.ts`), `apps/domwellbes/src/app/api/upload/route.ts`,
  `apps/grandslamcup/src/app/my/poems/_actions/album.action.ts`,
  `apps/mandala/src/app/api/og-image/route.ts`.
- **Полностью ручная реализация, без библиотеки вообще** — `apps/svoichuzhie` (photo/audio
  upload+stream), `apps/driving-school` (доп. роуты `api/upload/locations`, `vehicles`,
  `student-document`), `apps/grandslamcup` (доп. роуты `api/upload/entity-photo`, `poem-cover`,
  `album-cover`, `match-poster`, `team-logo`, `user-avatar`).

Мигрировать эти места на общий backend сейчас — не задача этого дока и не было целью: это
кампания на 30+ файлов в разных приложениях. Правильный момент — когда эти приложения и так
трогают по другой задаче, переводить конкретный роут на `createImageUploadRoute`/`StorageBackend`
попутно, не отдельным проектом.

## IPFS — рассмотрели, отклонили для приватного контента, не навсегда

При обсуждении всплыл вопрос: раз в монорепо уже есть `animatrona-tracker` с IPFS-раздачей, не
стоит ли пустить через IPFS и `uploads/`? Причины не делать этого сейчас — для контента,
несущего персональные данные (документы студентов `driving-school`, аватары):

1. **152-ФЗ** ([personal-data.md](/.claude/docs/personal-data.md)) — право на удаление по запросу
   пользователя. IPFS не гарантирует стирание: анпиннинг убирает копию с твоего узла, но не с
   узлов чужих пиннеров/гейтвеев, которые уже могли забрать контент.
2. **Раздача всё равно идёт через свой прокси.** `createUploadsRoute` расставляет
   security-заголовки на каждый файл (`X-Content-Type-Options: nosniff`, CSP-sandbox на SVG) —
   голый IPFS-гейтвей их не проставит. Если прокси нужен в любом случае, смысл P2P-раздачи
   (обойтись без своего сервера) пропадает.

**Не отклонено навсегда.** Для по-настоящему публичного контента без персональных данных —
фото/видео с концертов `svoichuzhie`, медиа `grandslamcup` — оговорка про 152-ФЗ не действует, и
такие файлы уже сегодня получают уникальные неизменяемые имена (не перезаписываются в рамках
одной загрузки, кроме отдельного случая «постоянных имён» — см. `getVersionedUploadUrl` выше).
Когда дойдёт очередь до этих двух приложений — обсудить IPFS отдельно, именно как backend для их
публичных медиа-галерей, вне общей абстракции `@letar/image-upload` (у которой большинство
потребителей — приватный/персональный контент).

## Как добавить свою реализацию backend позже

```ts
import type { StorageBackend } from '@letar/image-upload/server'

export function createS3Backend(/* ... */): StorageBackend {
  return {
    async stat(segments) {/* ... */},
    createReadStream(segments, range) {/* ... */},
    async write(segments, data) {/* ... */},
    async delete(segments) {/* ... */},
    async read(segments) {/* ... */},
  }
}
```

Подключается точечно на приложение, которому нужен именно этот backend:

```ts
export const GET = createUploadsRoute({ backend: createS3Backend() /* ... */ })
```

Остальные приложения продолжают использовать дефолтный `createLocalDiskBackend` без изменений.
