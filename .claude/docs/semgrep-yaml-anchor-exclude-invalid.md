# Semgrep не понимает YAML-якоря в `paths.exclude` — не пытайся DRY-ить так

`.semgrep/letar-rules.yml` содержит три правила (`letar-forms-raw-select-combobox-outside-lib`,
`letar-forms-native-select-deprecated`, `letar-forms-hand-rolled-footer-use-formactions`), у
которых `paths.exclude` дословно повторяет один и тот же список из 7 путей (`/libs/forms/**`,
`/libs/forms-core/**`, …). Выглядит как учебный случай для YAML-якоря (`&anchor`/`*alias`) —
это оказалось не так, проверено эмпирически 2026-09-22.

## Что сломалось

`&anchor`/`*alias` на простом списке технически валиден как YAML и `uvx semgrep scan` без
`--validate` его даже отрабатывает (алиас в `exclude:` реально исключает файлы на живом скане).
Но:

- `uvx semgrep scan --config <file> --validate` на правиле, где `exclude: *alias`, падает:
  `[ERROR] Rule parse error in rule <id>: Expected a list for exclude` — при exit code 2, то
  есть конфиг считается невалидным целиком, хотя тот же список литералом проходит `--validate`
  чисто (0 errors).
- Слияние alias + доп. элемент через `exclude: [*alias, '/libs/ui/**']` (нужно для третьего
  правила, у которого список — те же 7 путей плюс `/libs/ui/**`) ломается иначе и хуже:
  `['/libs/forms/**', '/libs/forms-core/**'] is not of type 'string'` — семгреп не разворачивает
  вложенный список из alias, а видит его как один элемент `exclude`, что не список строк.
  YAML вообще не даёт стандартного способа «взять список по alias и дописать элемент» — merge-key
  `<<:` определён спецификацией только для mapping, не для sequence.

Раз `--validate` — часть штатного ручного прогона (см. шапку `letar-rules.yml`) и часть
проверки перед коммитом такого файла, `--validate`-ошибка на алиасе достаточна, чтобы не
применять подход: расхождение между «сработает на скане» и «не пройдёт validate» — риск, который
не стоит экономии на дублировании 7 строк.

## Что делать вместо этого

Ничего — оставить три идентичных литеральных списка как есть. Дублирование безопасно в том
смысле, что `--validate` и полный `scan` с ним гарантированно консистентны (проверено: 444
findings, идентичный набор `(check_id, path, line)` до и после теста). Если список из 7 путей
когда-нибудь изменится, менять во всех трёх местах руками — альтернатива (генерировать
`.semgrep/letar-rules.yml` из шаблона перед прогоном) не стоит сложности ради трёх правил.

## Как проверялось

Минимальный конфиг из двух/трёх тестовых правил в scratch-каталоге, `uvx semgrep scan --config
... --validate` в обоих вариантах (только alias; alias + доп. элемент), плюс контрольный конфиг с
теми же путями литералом для сравнения (прошёл `--validate` чисто). Версия: `semgrep 1.177.0`.
