# Класс бага: проверка в памяти рантайма по полю, которого нет в SELECT

Обобщение из [[better-auth-1.7-account-issuer-field]] (Better Auth 1.7 `Account.issuer`) —
проверка условий сравнения показала, что это не частность одной библиотеки, а воспроизводимый
класс бага у любой зависимости, которая **сама** решает, что сравнивать после чтения из БД, не
делегируя сравнение самой БД (`WHERE`).

## Форма бага

Библиотека читает запись через ORM (`findUnique`/аналог), затем в коде на JS/TS сравнивает поле
этой записи с ожидаемым значением (`record.field === expected`). Если поле:

- отсутствует в схеме модели (Zod/Prisma validate его отбрасывает или роняет запрос ошибкой), либо
- присутствует, но у существующих строк `NULL` (не заполнено обратным заполнением после миграции),

сравнение не совпадает — `false`/`undefined`. Ветка «не найдено» срабатывает **без исключения**:
это не `throw`, а обычный отрицательный результат обычного `if`.

## Почему это не ловится ни одним штатным способом проверки

- **Логи** — по построению их не будет: код не считает это ошибкой, а закономерным «текущие
  данные не подходят под условие», ровно как задумано для случая, когда условие сравнения
  действительно не выполняется. Отличить «баг» от «легитимный отказ» по логам невозможно.
- **Typecheck** — ORM-клиент (Prisma/ZenStack) сгенерирован из текущей схемы БД и ничего не знает
  о новом рантайм-инварианте, который библиотека начала требовать в новой версии. Типы не меняются
  — меняется только то, что зависимость делает со значением поля после чтения.
- **Ручное тестирование в браузере** — внешний симптом (для better-auth это был `401 INVALID_
  EMAIL_OR_PASSWORD`) неотличим от штатной ошибки пользователя («опечатался в пароле»). Разработчик
  либо не подозревает миграцию как причину вообще, либо тратит время на проверку пароля/хеша,
  прежде чем заподозрить схему.
- **Миграция schema.zmodel сама по себе** — добавление колонки чинит только новые записи (свежий
  код теперь пишет значение при создании). Существующие строки остаются с `NULL`, и сравнение
  `NULL === expected` не проходит точно так же, как отсутствующая колонка — баг выживает первую,
  самую очевидную попытку исправления.

## Как диагностировать, если подозревается этот класс

1. Прочитать исходники зависимости (`node_modules/<lib>/dist/**`) в поисках `===`/`find()`/
   `.filter()` над полями, прочитанными через ORM — не полагаться на документацию библиотеки,
   она обычно описывает только API, не внутренние инварианты хранения.
2. Проверить changelog минорного/патч-апгрейда зависимости на предмет security-хардненинга —
   такие проверки чаще всего добавляют именно в патчах, не в мажорных релизах, потому что с точки
   зрения публичного API ничего не меняется.
3. Сравнить количество затронутых строк прямым SQL, а не полагаться на «похоже, починилось»:
   `SELECT count(*) FROM "<table>" WHERE "<column>" IS NULL AND <остальные условия, при которых
   инвариант обязателен>`. Ненулевой результат — нужен backfill, а не повторный `db:push`/`migrate
   generate`.

## Практический вывод

При любом апгрейде зависимости, отвечающей за аутентификацию/авторизацию/платежи (то есть за
рантайм-инварианты, которые сама библиотека проверяет над уже существующими данными) — читать не
только миграционный гайд по API, но и искать в дистрибутиве новые сравнения над полями модели,
которыми управляет наша схема. Добавление колонки без отдельного backfill-шага — заведомо
неполный фикс для этого класса бага, даже если typecheck/lint/сборка проходят зелёными.
