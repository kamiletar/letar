# Проверки, которые врут в успокаивающую сторону

Отдельный документ, потому что это не список частных багов, а **один повторяющийся класс**: проверка
отвечает «всё хорошо», хотя система сломана. Такие ошибки опаснее падений — падение видно сразу, а
ложное «зелено» закрывает вопрос и уводит внимание.

За одну инфра-сессию (2026-08-07/08) этот класс сработал **семь раз подряд**, каждый раз на новом
инструменте. Отсюда документ.

## Каталог случаев

| Проверка                            | Что показала   | Что было на самом деле                                                      |
| ----------------------------------- | -------------- | --------------------------------------------------------------------------- |
| `ufw status`                        | `active`       | не фильтрует ничего из опубликованного Docker'ом — трафик идёт мимо `INPUT` |
| `iptables -S` содержит правило      | правило есть   | правило в цепочке, которую ядро не проходит для этого трафика               |
| `docker ps`                         | `Up (healthy)` | снаружи недоступно — healthcheck ходит внутрь контейнера, а маршрута нет    |
| `du -sh <чужой каталог>`            | `68K`          | `1.3G` — `Permission denied` на подкаталогах `700` молча схлопнул сумму     |
| `.conf` на диске (NPM)              | конфиг такой   | источник истины — SQLite; файл перегенерируется и правку затрёт             |
| проба порта по имени хоста          | «закрыт»       | имя резолвится только в AAAA — проверяли не тот протокол                    |
| `nx typecheck`                      | зелёный        | `references` вёл в несобираемый проект, модуль стал `any`, проверок нет     |
| `docker compose up -d` после правки | «применено»    | compose сравнивает описание сервиса, а не содержимое смонтированных файлов  |
| резолв имени в зоне `letar.best`    | имя резолвится | в зоне корневой wildcard — резолвится **любое** имя, включая опечатки       |
| замер IMAP-прохода с рабочей машины | 426мс из 90с   | из контейнера на s2 канал до другого датацентра — там таймаут исчерпывался  |

Десятый случай стоит особняком: там проверка была верной по существу, но **выполнена не с того
хоста**. Разбиралась причина, по которой канарейка не укладывалась в 90-секундный таймаут;
гипотеза «накопился backlog, обход стал слишком долгим» была верной, но замер прохода по всем 1695
письмам сделали с рабочей машины и получили 426мс — гипотезу закрыли как несостоятельную. Код,
который тормозил, жил в контейнере на s2 и ходил через канал до другого датацентра. Полный разбор —
`PLAN-INFRA.md` §62.

Отсюда следствие, которого нет в остальных случаях: **замер, сделанный не тем путём, опаснее
отсутствия замера**. Отсутствие замера оставляет гипотезу живой; неверный замер выглядит как факт
и закрывает её — а вместе с ней и правильное направление поиска. Прежде чем опровергать гипотезу
числом, спроси: этот код выполняется там же, откуда я мерю?

Зеркальный случай — ложно-**красный**: `run_e2e` вернул код `1` при зелёных тестах
(гонка за общий `.nx/cache` с параллельным деплоем). Механика та же: результат проверки не связан с
тем, что проверяли.

## Почему это происходит

Во всех случаях проверка отвечала на **соседний вопрос**, а не на заданный:

- «правило существует» вместо «трафик через него проходит»;
- «контейнер жив» вместо «сервис доступен потребителю»;
- «файл на диске такой» вместо «система работает по этому файлу»;
- «сумма посчиталась» вместо «сумма посчиталась по всем данным».

Соседний вопрос почти всегда дешевле проверить — поэтому инструменты по умолчанию отвечают именно
на него.

## Что с этим делать

### 1. Проверяй тем же путём, которым ходит настоящий потребитель

Порт наружу — пробой снаружи, не `ss -tulnp` на самом хосте. Сайт — HTTP-запросом с чужой машины, не
`docker ps`. Конфиг применился — по логу самого сервиса, не по содержимому файла.

### 2. Всегда два контроля, а не один

Отрицательный контроль (заведомо мёртвый порт/адрес) ловит «дошли ли мы вообще». **Положительный
контроль (заведомо живой) ловит «дошли ли мы туда, куда думаем»** — и именно он спасал чаще.

Прецедент: все порты показали «закрыто», вывод «провайдер фильтрует» идеально ложился на данные.
Положительный контроль на `443` показал, что проверка ушла по другому протоколу — фильтрации не
существовало вовсе.

### 3. Проверяй права, если считаешь чужое

`du`, `find`, `grep` по каталогам другого владельца **молча пропускают** недоступное. Разница между
`68K` и `1.3G` — это не погрешность, это противоположный вывод: «убирать нечего» против «убрать
надо». Считаешь чужое — считай от root или изнутри контейнера.

### 4. В зоне `letar.best` резолв не доказывает ничего

Все имена `*.letar.best` — CNAME на s2 (корневой wildcard). Следствия, неочевидные до первого
столкновения:

- ⛔ **`NXDOMAIN` в нашей зоне недостижим.** Любая опечатка, выдуманное имя, давно удалённый
  поддомен — всё резолвится в адрес s2. «Имя резолвится» не значит, что оно заведено.
- **Признак живого сервиса — TLS-handshake и HTTP-ответ, не резолв.** Проверка через `dig`/
  `Resolve-DnsName` в этой зоне всегда успешна и потому бесполезна.
- **TLS `unrecognized name` = «имени нет в конфиге прокси»**, а не «сервер лежит». Различие мы
  дважды принимали за аварию: сервер отвечает штатно, просто у него нет vhost под этот SNI.

Исключение — имена с явной записью (`gateway`, `ipfs`): они перекрывают wildcard, поэтому их можно
переставлять поштучно, и только у них резолв что-то означает.

### 5. Найди настоящий источник истины

Прежде чем править конфиг — выясни, кто его порождает. NPM генерирует `.conf` из SQLite; Docker
перечитывает не файлы, а описание сервиса; Next.js берёт первый найденный `next.config.*`, игнорируя
остальные. Правка производного артефакта выглядит как успех ровно до следующей перегенерации.

### 6. Меняй по одной переменной

Тест, в котором изменилось два условия сразу, не подтверждает гипотезу — он лишь **не противоречит**
ей. Разбор этого отдельно —
[docker-bind-mount-pitfalls.md](/.claude/docs/docker-bind-mount-pitfalls.md).
