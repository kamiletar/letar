# `git commit -- <pathspec>` коммитит рабочее дерево, а не индекс

Одна особенность, три разных исхода — два из них молчаливые, а третий оставляет мину, которая
срабатывает через один коммит.

## Механизм

`git commit -- <pathspec>` — это **не** «закоммить то, что уже застейджено и подходит под
pathspec». Под капотом это ближе к «`git add <pathspec>` (по текущему содержимому рабочего
дерева) плюс `git commit`»: команда неявно **переопределяет** содержимое для путей, подпадающих
под pathspec, беря его из рабочей копии, а не из индекса. При этом сам индекс после такого
коммита **не обновляется** — он остаётся ровно в том состоянии, в каком был.

Отсюда три следствия ниже. Они выглядят как разные баги, но причина одна.

## Следствие 1: молча теряется `git rm --cached`, если путь уже в `.gitignore`

### Симптом

Untrack ранее закоммиченного файла — обычная связка:

```bash
git rm --cached playwright/.auth/admin.json
git commit -m "..." -- playwright/.auth/admin.json
```

`git status --short` перед коммитом честно показывает застейдженное удаление (`D`). Коммит
проходит без ошибок. Но после него файл **снова трекается** — `git ls-files` показывает его как
ни в чём не бывало, `git status` для него пуст (чисто), а сам коммит в `git show --stat`
не содержит этого файла вообще. Ни ошибки, ни предупреждения — просто застейдженное удаление
исчезает, будто его не было.

Если в том же коммите ещё и добавляли `.gitignore`-паттерн, покрывающий этот путь (частый случай:
untrack идёт рука об руку с игнорированием) — молчаливая потеря происходит именно из-за этого.

### Почему

Пока путь ничем не игнорируется, разницы не видно: рабочее дерево и индекс для untracked-но-
присутствующего-на-диске файла синхронизируются в то же состояние, что дал `git rm --cached`
(файл остаётся вне индекса, `git add` на untracked-но-неигнорируемый файл добавил бы его
**обратно** — но именно поэтому голый рабочий сценарий тоже ломается, если файл не игнорируется).

Как только путь подпадает под `.gitignore`, неявный `git add` внутри pathspec-коммита превращается
в no-op — `git add` на игнорируемый путь ничего не делает без `-f`. Итог: pathspec-коммит
«переисполняет» add для этого пути, ловит тишину от `git add`, и застейдженное `git rm --cached`
удаление остаётся вне итогового коммита — молча, без диагностики.

### Как проверить, что именно это

```bash
git status --short -- <path>     # до коммита: "D <path>" — удаление застейджено
git commit -m "..." -- <path>
git show --stat HEAD -- <path>   # пусто — путь не попал в коммит
git ls-files -- <path>           # путь снова числится tracked
git check-ignore -v -- <path>    # если что-то печатает — вот источник
```

### Фикс

Не ограничивать коммит pathspec'ом, если среди застейдженных путей есть уже игнорируемые.
Либо коммитить без pathspec (когда в индексе гарантированно единственный логический scope —
проверить `git diff --cached --name-only` перед этим), либо явно развести на два отдельных
коммита: один с pathspec на `.gitignore`/новые файлы, второй — bare `commit` только с
удалением, когда в индексе не осталось ничего постороннего.

```bash
git rm --cached playwright/.auth/admin.json
git diff --cached --name-only        # убедиться, что в индексе ровно то, что нужно
git commit -m "chore: untrack playwright/.auth/*.json"   # без pathspec
```

## Следствие 2: в коммит уезжают чужие незакоммиченные правки внутри твоих путей

Тот же механизм с другим знаком. Если pathspec шире набора застейдженных файлов — а «шире» это
любой **каталог** вместо перечисления файлов, — в коммит попадёт всё изменённое в рабочем дереве
внутри этого каталога. В общем чекауте `C:\web\letar`, где параллельно работают другие сессии,
«всё изменённое» включает и чужой WIP.

```bash
git add PLAN-INFRA-4.md .claude/docs/мой-док.md
git diff --cached --name-only                       # два файла — как и задумано
git commit -m "…" -- PLAN-INFRA-4.md .claude/docs   # ← каталог
git show --stat HEAD                                # три файла: приехал чужой док
```

⚠️ **Проверка индекса перед коммитом здесь не помогает по построению.**
`git diff --cached --name-only` показывает индекс, а коммит с pathspec индекс частично
игнорирует. Единственная работающая проверка — `git show --stat` **после** коммита.

Это ровно то же ограничение, что уже действует для `git checkout -- <каталог>`: опасен каталог
в pathspec, а не синтаксис `--`. Разбор конкретного случая (коммит `0c55f455`, 2026-08-28) —
[git-multi-agent-incidents § Дополнение 2026-08-28](/.claude/docs/git-multi-agent-incidents.md).

## Следствие 3: после такого коммита в индексе остаётся мина

Побочный эффект того же коммита, который замечают обычно не сразу, а через один шаг. Индекс для
путей из pathspec **не обновился** — там лежит старый блоб (то, что было застейджено раньше или
что стояло в `HEAD` до коммита). Файл при этом уже закоммичен из рабочей копии.

Получается расхождение из трёх состояний: `HEAD` = новое содержимое, индекс = старое, рабочее
дерево = новое. Git показывает это как `MM`:

```bash
$ git status --porcelain
MM .claude/docs/verification-pitfalls.md
```

Первая `M` — «индекс отличается от HEAD», вторая — «рабочее дерево отличается от индекса».
Выглядит как обычный «файл изменён», и именно поэтому мимо этого легко пройти. Но диффы
показывают, что происходит на самом деле:

```bash
$ git diff --cached --stat -- .claude/docs/verification-pitfalls.md
 .claude/docs/verification-pitfalls.md | 58 +++---------------------------
```

**Застейджено удаление тех самых строк, которые ты только что закоммитил.** Любой следующий
`git commit` без pathspec (или с pathspec, накрывающим этот файл, но по старому содержимому
индекса) молча откатит раздел из `HEAD`.

### Лечение

Свести индекс с рабочим деревом **до** любого следующего коммита:

```bash
git add .claude/docs/verification-pitfalls.md
git status --porcelain -- .claude/docs/verification-pitfalls.md   # пусто — расхождения нет
```

⛔ Не `git checkout --` и не `git restore` — они бы взяли содержимое из индекса, то есть
уничтожили бы в рабочем дереве ровно то, что мина и собиралась откатить. Направление
восстановления здесь строго «рабочее дерево → индекс».

⚠️ **Если файл чужой** (это чужой WIP, который приехал в твой коммит) — `git add` всё равно
правильное действие: оно фиксирует в индексе то, что уже лежит в `HEAD`, и обезвреживает откат.
Ревертить сам коммит, чтобы «вернуть чужое владельцу», хуже: реверт вынет чужую работу из `HEAD`
обратно в незакоммиченное состояние, а сессия-владелец к тому моменту уже считает файл
сохранённым и второй раз его не закоммитит.

## Итоговое правило

- В `git commit -- …` перечисляй **файлы**, а не каталоги.
- После коммита с pathspec — `git show --stat HEAD`, всегда. Это единственная проверка, которая
  ловит следствия 1 и 2.
- Увидел лишний файл в статистике — сразу `git add <этот файл>`, пока следствие 3 не сработало.

⚠️ Это не отменяет общее правило [git.md](/.claude/rules/git.md) — «коммить только через
`git commit -- <явные пути>`», чтобы не утащить чужие staged-файлы параллельного агента. Оба
правила совместимы: pathspec защищает от чужих файлов **вне** твоих путей, но не от чужих правок
**внутри** них. Перед bare-коммитом обязательно проверять `git diff --cached --name-only`, а не
полагаться на то, что в индексе «наверное, только моё».
