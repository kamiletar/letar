# Динамический путь в `fs`-вызове раздувает standalone-сборку

`Next.js`/Turbopack статически анализирует аргументы вызовов вида `fs.readFile`, `fs.stat`,
`fs.writeFile`, `fs.mkdir`, `fs.unlink` и т.п., чтобы понять, какие файлы нужно скопировать в
`.next/standalone` (`output: 'standalone'`). Если аргумент — не литерал, а рантайм-значение
(пользовательский ввод, поле формы, значение из БД), анализ не может определить границы пути и
трассирует **весь проект целиком**, включая каталоги вроде `uploads/`, где реально лежат
загруженные пользователями файлы. Сборка печатает предупреждение:

```
Warning: Dynamic filesystem access causes tracing of the whole project
```

## Как нашли

`libs/image-upload/src/server/image-upload-route.ts` строил путь загрузки так:

```ts
const categoryFolder = category.toLowerCase() // рантайм-значение из FormData
const uploadsDir = path.join(uploadsRoot, categoryFolder)
await mkdir(uploadsDir, { recursive: true })
```

Библиотеку через этот роут подключают минимум `aprel8008` и `dsperevod`. У `aprel8008` это
привело к реальному инциденту 2026-09-05: `.next/standalone` разросся до 3.47GB (у сравнимых
приложений — 400–800MB), потому что в трассировку попали реальные файлы из
`apps/aprel8008/uploads/`. Деплой на s2 упал `ResourceExhausted`/«no space left on device» при
копировании `.next/standalone` — диск сервера был забит под завязку.

## Фикс

Next.js сам подсказывает решение в тексте предупреждения — комментарий
`/* turbopackIgnore: true */` перед аргументом, который бундлер не должен пытаться
статически резолвить:

```ts
const uploadsDir = path.join(/* turbopackIgnore: true */ uploadsRoot, categoryFolder)
await mkdir(/* turbopackIgnore: true */ uploadsDir, { recursive: true })
```

⚠️ **Комментарий обязан стоять сразу после открывающей скобки вызова, перед первым
аргументом** — не перед тем аргументом, который фактически динамический. Первая попытка
поставить его перед вторым аргументом (`path.join(uploadsRoot, /* turbopackIgnore: true */
categoryFolder)`) не убрала предупреждение вообще; перенос перед первым аргументом
(`path.join(/* turbopackIgnore: true */ uploadsRoot, categoryFolder)`) убрал. Похоже, комментарий
отключает анализ всего вызова целиком, а не конкретного аргумента, и работает только с позиции
сразу после `(`.

Тот же паттерн уже использовался в `libs/image-upload/src/server/serve-uploads.ts` (раздача
файлов, `GET`-роут) — оттуда и взят как образец.

## ⚠️ Не панацея: похожий, но статически ограниченный вызов остаётся дорогим

Отдельный от библиотеки код `apps/aprel8008/src/app/admin/_actions/photos.action.ts` удаляет
файл так:

```ts
await unlink(join(process.cwd(), 'uploads', 'estates', photo.estateSlug, photo.filename))
```

Этот вызов **не** печатает предупреждение — литеральные сегменты `'uploads'`/`'estates'` перед
динамическими дают трассировщику точный статический якорь, ровно тот паттерн, что сам Next
называет правильным («`path.join(process.cwd(), 'data', bar)`»). Но статическая ограниченность
не значит малый размер: трассировщик копирует **весь** каталог `uploads/estates/` целиком (он не
может знать заранее, какой конкретно файл понадобится в рантайме) — а там лежат все реальные
фотографии баз. Отсутствие предупреждения тут не признак отсутствия проблемы.

Так что для приложений, где `uploads/` физически хранит реальные пользовательские файлы,
`turbopackIgnore`/статическое сужение пути решает только часть — трассировка одной конкретной
директории всё ещё утаскивает её содержимое в образ, даже если сам вызов дополнительно обёрнут
`turbopackIgnore` (проверено: добавление комментария к `unlink()` в `photos.action.ts` не
изменило размер `.next/standalone` ни на байт — тrassировщик и до этого корректно резолвил
область до `uploads/estates/`, комментарий не про эту часть).

**Настоящий фикс для этого случая — `outputFileTracingExcludes` в `next.config.mjs`:**

```js
outputFileTracingExcludes: {
  '/**/*': ['./uploads/**'],
},
```

Оправдан он там, где `uploads/` — Docker volume, монтируемый в рантайме (см.
`docker-compose.production.yml` приложения): содержимое, которое трейсер копирует в образ,
всё равно будет перекрыто монтированием при старте контейнера, то есть скопированные файлы —
чистый балласт. Результат на `aprel8008` (2026-09-05): `.next/standalone` — с 1.6GB (все
реальные фото внутри `uploads/`) до 51MB после добавления исключения, при сохранении зелёного
`typecheck:tsgo` и отсутствии предупреждения о трассировке.

⚠️ Если `uploads/` в конкретном приложении НЕ вынесена в volume (файлы реально должны попасть
в образ, например для readonly-контейнера без монтирования) — этот фикс не подходит, нужно
искать другой путь (readonly-копия при билде, отдельный слой и т.п.).

## Проверка

```bash
nx build <app> --skip-nx-cache 2>&1 | grep -i "dynamic filesystem"
du -sh apps/<app>/.next/standalone
```

Пустой grep — предупреждения нет. Размер `standalone` всё равно нужно сверять отдельно: он не
обязан упасть до нормы, если в приложении остались свои статически-ограниченные, но объёмные
трассировки (см. предупреждение выше).
