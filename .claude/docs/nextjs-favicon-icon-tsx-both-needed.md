# Next.js App Router: `icon.tsx` не заменяет `favicon.ico`

## Симптом

Приложение генерирует иконку через `src/app/icon.tsx` (`ImageResponse`) и не заводит физический
`favicon.ico` — выглядит как современная и полная замена: Next.js сам выводит нужный `<link>` в
`<head>`, иконка видна во вкладке браузера при разработке. Но предпросмотр ссылки в Telegram/VK,
часть краулеров, читалки лент и менеджеры закладок показывают либо дефолтную иконку, либо ничего.
В логах сервера при этом видны обращения `GET /favicon.ico → 404`.

## Причина

Часть потребителей не читает `<head>` вообще — они запрашивают `/favicon.ico` в корне домена по
жёсткой конвенции, независимо от того, какие теги `<link rel="icon">` отдаёт разметка. `icon.tsx`
генерирует иконку и тег на неё, но не создаёт файл по пути `/favicon.ico` — это два независимых
механизма. Нужны **оба**:

- `src/app/favicon.ico` — статический файл, Next.js кладёт его на путь `/favicon.ico` и сам
  добавляет `<link rel="icon" sizes="any">`. Закрывает ботов, краулеров и старые браузеры.
- `src/app/icon.tsx` — `ImageResponse`, современный путь с поддержкой динамики (тема, состояние).
  Закрывает браузеры, которые действительно читают `<head>`.

## Как собрать ICO с несколькими размерами

`favicon.ico` — контейнер на несколько размеров (16/32/48 — минимум, годами устоявшийся набор).
Внутрь с Vista кладут PNG, отдельный BMP не нужен. ⚠️ Каждый размер нужно рисовать под себя, а не
масштабировать один кадр — на 16 px размытие/гало в один пиксель превращает тонкую деталь в пятно,
которое на 32-48 px было бы уместно.

Готовая реализация (структура ICO-заголовка, таблица записей, PNG-кадры) —
[`apps/studio/design/make-icons.mjs`](/apps/studio/design/make-icons.mjs): генерирует SVG под
каждый размер через `sharp`, кладёт кадры в `ICO_SIZES = [16, 32, 48]` и вручную собирает
бинарный контейнер (заголовок 6 байт + таблица записей по 16 байт + PNG-данные подряд). Можно
использовать как образец для другого приложения — логика не завязана на конкретную палитру.

## Ловушка: `favicon.ico` + `icon.tsx` вместе дают ДВА тега `link[rel~="icon"]`

Если в приложении есть оба источника, Next.js выводит в `<head>` два независимых
`<link rel="icon">`. Это не проблема само по себе — но ломает наивную динамическую подмену
фавикона (например, «фавикон-индикатор»: иконка вкладки меняется по состоянию — идёт фоновый
процесс, просрочен счёт и т.п.).

```ts
// ❌ находит и меняет только ПЕРВЫЙ тег — браузер не обязан использовать именно его,
// может продолжать показывать второй (не изменённый) tab-иконку не переключит
const link = document.querySelector('link[rel="icon"]') as HTMLLinkElement | null
link?.setAttribute('href', dataUrl)
```

Симптом: код отрабатывает без единой ошибки, `href` у найденного узла меняется — а вкладка
браузера иконку не обновляет, или обновляет непредсказуемо в зависимости от браузера.

### Фикс — менять все узлы, а не первый найденный

```ts
// ✅ проходим по ВСЕМ link[rel~="icon"] — под таким селектором попадают и
// rel="icon", и rel="shortcut icon"
const setFaviconState = (dataUrl: string) => {
  document.querySelectorAll<HTMLLinkElement>('link[rel~="icon"]').forEach((link) => {
    link.setAttribute('href', dataUrl)
  })
}
```

Альтернатива — при инициализации подмены удалить оба существующих тега и вставить единственный
свой `<link rel="icon">`, дальше менять `href` только у него. Это надёжнее, если состояний иконки
много и код меняет её часто, но требует явного шага «убрать теги Next.js», который легко забыть
при рефакторинге head-разметки.

Проверять в Safari отдельно — WebKit исторически агрессивнее кеширует фавикон и может не
подхватить смену `href` даже у единственного правильно обновлённого тега без принудительного
пересоздания узла (`remove()` + `appendChild()` вместо `setAttribute()`).
