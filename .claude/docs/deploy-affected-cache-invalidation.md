# `deploy-affected.sh`: три независимых сброса кэша, из-за которых деплой был холодным

⚠️ Класс проблемы: деплой небольшого приложения занимает 50+ минут, и по логу кажется, что
виноват Nx project graph — потому что перед сборкой печатаются десятки предупреждений про
`vitest.config.ts` совершенно посторонних проектов. Это ложный след.

Замеры сделаны на s3 2026-08-28 на живом дереве.

## Что НЕ является причиной

**Построение project graph.** Замер: холодный граф (пустой `workspace-data`,
`NX_DAEMON=false`) — **17.5 секунды**, тёплый — 4–6 секунд.

Предупреждения вида «ESM syntax in a file loaded as CommonJS (libs/…/vitest.config.ts)» по
десяткам чужих проектов печатаются при **каждом** построении графа: плагин `@nx/vitest`
зарегистрирован в `nx.json` дважды, второй раз с 74 `include`-паттернами. Это шум на 17
секунд, а не на 17 минут.

`NX_DAEMON=false` в шапке скрипта тоже оставлен намеренно — комментарий там объясняет краш
plugin workers на серверах. Цена — те же ~15 с на каждый из ~6 вызовов `nx` за деплой.

## Причина 1 — typecheck всех 67 библиотек без кэша (~15 минут)

Шаг «🔧 Rebuilding libs/*/dist declarations (typecheck)» гоняет
`nx run-many -t typecheck` по **всем** библиотекам монорепо, а не по зависимостям
деплоимого приложения. Сам шаг обоснован (инцидент TS6305 2026-08-06, устаревшие
`dist/*.d.ts` — объяснение прямо в скрипте), но выполнялся с `--skip-nx-cache`.

Замер: **5 библиотек = 2 мин 06 с**, всего библиотек — 67.

Причина, по которой кэш был выключен, — `SKIP_NX_CACHE=true` по умолчанию с пометкой
«избегаем ошибок "File exists"». Та ошибка была следствием файлов с владельцем root в `.nx/`
и закрыта отдельно — re-exec скрипта под пользователя `deploy`.

⚠️ Второе, без чего первое не работает: после `git pull` скрипт делал
`rm -rf .nx/cache .nx/workspace-data`. Включить кэш и продолжать удалять `.nx/cache` — то же
самое, что не включать. Теперь сбрасывается только `workspace-data` (граф), кэш вычислений
переживает деплой.

⚠️ Третье: `dashboard-agent` собирает команду как
`[script, '--app', name, ...staging, ...seed]` (`apps/dashboard-agent/src/routes/deploy.ts`) —
флаг `--use-cache` существовал в скрипте, но не передавался **никогда**. Смотреть надо было
не на набор флагов скрипта, а на то, кто его реально вызывает.

## Причина 2 — `rm -rf .next` убивал persistent cache Turbopack

В Next 16 `experimental.turbopackFileSystemCacheForBuild` **включён по умолчанию**
(`defaultConfig` в `next/dist/server/config-shared.d.ts`), кэш живёт в
`apps/<app>/.next/turbopack`. Шаг «Clearing build caches» сносил весь `.next` целиком, то есть
каждая сборка была холодной.

Насколько это дорого: dsperevod печатал `✓ Compiled successfully in 14.4min` на приложении из
109 `.tsx`, 63 роутов и 627 KB `src/app`, без единого `generateStaticParams` и без тяжёлых
зависимостей. То есть размер приложения тут ни при чём.

Теперь чистятся только выходные артефакты (`standalone`, `static`, `server`, `build`,
`types`); полная чистка осталась под флагом `--clean`.

⚠️ Оговорка: удаление `.next` было страховкой от stale-состояния, и Next не даёт формальных
гарантий при частичной чистке. Первые деплои после этой правки стоит сверять — если появятся
необъяснимые артефакты сборки, подозревать в первую очередь именно её.

## Причина 3 — сервер загружен

На момент замеров: `load average: 5.28, 7.27, 10.68` при 12 ядрах. Косвенный признак в любом
замере — `real 2m06s` при `user 0m31s`: три четверти времени процесс ждал CPU. Сборка
дополнительно ограничена `--parallel=1` (защита от OOM).

Поэтому абсолютные числа отсюда воспроизводятся только на сопоставимой загрузке; порядок
величин — воспроизводится.

## Как мерить самому, не ломая рабочее дерево

```bash
NX_DAEMON=false NX_WORKSPACE_DATA_DIRECTORY=/tmp/nxwd-probe nx show projects --type=app
```

`NX_WORKSPACE_DATA_DIRECTORY` уводит граф в отдельный каталог — получаешь честный холодный
замер, не сбрасывая кэш идущих рядом деплоев.
