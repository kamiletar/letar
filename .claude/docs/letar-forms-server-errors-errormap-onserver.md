# `applyServerErrors` должен писать в `errorMap.onServer`, не в `meta.errors` напрямую

⚠️ Прямой push серверной ошибки в `field.state.meta.errors` (TanStack Form,
`@tanstack/form-core`) выглядит как рабочее решение в unit-тесте с мокнутым `formRef`, но не
переживает реальный рендер — ошибка исчезает раньше, чем пользователь успевает её увидеть.

## Симптом

`mapServerErrors`/`applyServerErrors` (`@letar/forms-core`) отрабатывают верно (можно убедиться
консоль-логом сразу после вызова), toast с сообщением об ошибке показывается, но поле формы
визуально не подсвечивается — ни рамки, ни текста ошибки под инпутом. `aria-invalid` на инпуте
остаётся `null`/`false`.

## Причина

`field.state.meta.errors` в `@tanstack/form-core` — не самостоятельное мутируемое поле, а
**производное** значение. Оно пересчитывается из `field.state.meta.errorMap` при каждом
обновлении стора (`Object.values(errorMap).reduce(...)`, см. `FieldApi.js`/`FormApi.js` в
исходниках пакета). Прямой `push`/переприсваивание `errors` переживает ровно до следующего
пересчёта — на живой странице это тот же тик, поэтому в браузере эффект выглядит так, будто
ошибка вообще не применилась, хотя код её применения отработал без исключений.

`ValidationErrorMap` (`@tanstack/form-core`) держит отдельные ключи под разные источники
ошибок: `onMount`/`onChange`/`onBlur`/`onSubmit`/`onDynamic` — под обычные валидаторы формы, и
**`onServer`** — специально под внешне применяемые (не через встроенный цикл валидации) ошибки
(`getErrorMapKey('server') === 'onServer'` в `FieldApi.js`). Этот ключ не пересекается ни с
одним обычным циклом валидации, поэтому переживает следующий ре-рендер и любую нормальную
проверку поля.

## Фикс

```ts
// ❌ Не так — прямой push в производное значение
form.setFieldMeta(field, (prev) => ({
  ...prev,
  errors: [...(prev.errors ?? []), message],
}))

// ✅ Так — через errorMap, ключ onServer
form.setFieldMeta(field, (prev) => ({
  ...prev,
  errorMap: { ...prev.errorMap, onServer: message },
}))
```

Реализовано в `applyServerErrors` (`libs/forms-core/src/lib/server-errors/map-server-errors.ts`,
с `@letar/forms-core` v0.12.4) — фикс общий для всех потребителей функции, не только
`useFormServerAction`.

## Почему это не поймали unit-тесты

Спека мокает `formRef` голым `{ setFieldMeta: vi.fn(), setErrorMap: vi.fn() }` — такой мок
только фиксирует факт вызова с каким-то аргументом, не прогоняет `updater` через реальный стор и
не воспроизводит пересчёт `errors` из `errorMap`. Баг был найден только живой проверкой в
браузере (ввод значения → сабмит → инспекция `aria-invalid`/DOM поля), после чего добавлен
отдельный тест с мини-моделью стора, реально прогоняющей `updater` через сохранённое состояние
поля (см. `map-server-errors.spec.ts` → `applyServerErrors` → `createFakeForm()`) — такой мок
уже отличает правильный `errorMap.onServer` от регресса обратно на плоский `errors`.

## Смежная ловушка того же расследования

Отдельный (не связанный по коду, но найденный в той же сессии) баг — обёртка над `run()`, которая
глотает ошибку после применения `applyServerErrors` (`return`/резолв без rethrow), даёт тот же
внешний симптом («поле не показывает ошибку»), но по другой причине: декларативный `<Form>`
(`libs/forms/src/lib/declarative/form-root/form-simple.tsx`) делает `commitPostSubmitReset` сразу
после того, как его `onSubmit`-проп резолвится без исключения — сброс стирает только что
применённую ошибку раньше следующего рендера. Если ошибка не отображается — проверять оба места:
(1) `errorMap` ли применена ошибка, (2) не глотает ли обёртка исключение из `action`, из-за чего
`<Form>` считает сабмит успешным.
