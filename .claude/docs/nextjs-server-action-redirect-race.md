# Next.js Server Actions: гонка со SSR-редиректом того же маршрута

## Симптом

Форма/визард на странице X вызывает Server Action, который мутирует данные (например, очищает
корзину при оформлении заказа). Страница X сама содержит SSR-редирект-guard, завязанный на эти же
данные (например, `redirect('/cart')`, если корзина пуста). После успешного выполнения action'а
клиентский код должен уйти на другую страницу (`window.location.href` / `router.push`), но вместо
этого браузер иногда попадает на URL из guard'а самой страницы X — притом что action по всем
признакам отработал успешно (данные в БД изменены корректно).

Отказ обычно:

- **воспроизводится не всегда** — стабильнее на WebKit и/или под параллельной нагрузкой (несколько
  Playwright-воркеров/браузерных контекстов бьют по одному staging-контейнеру одновременно);
- в логе навигации видно промежуточный визит на исходный URL страницы X перед ложным редиректом,
  например: `navigated to /checkout → /cart → /cart` вместо ожидаемого `/checkout/success/...`.

## Причина

Next.js Server Actions по протоколу возвращают вместе с HTTP-ответом свежий RSC-рендер
**вызывающего маршрута** — это часть механизма, которым Next синхронизирует Router Cache клиента
после мутации, без явного `revalidatePath()`/`router.refresh()` от разработчика. Если action был
вызван со страницы X, и на странице X есть SSR-логика (`redirect()`), зависящая от тех же данных,
которые action только что изменил — эта логика срабатывает **как часть ответа action'а**, до того,
как клиентский код успевает выполнить свою собственную навигацию на успех.

На быстрых браузерах/без нагрузки клиентский `window.location.href`/`router.push` обычно успевает
первым, и баг не проявляется. Под нагрузкой (несколько параллельных e2e-воркеров на один staging-
контейнер) или на браузерах с иной моделью планирования задач (в частности, WebKit) встроенная
гонка Next'а стабильно выигрывает.

## Диагностика

1. Убедиться, что мутация в action'е реально прошла (данные в БД корректны) — если да, это
   подтверждает, что дело не в самой бизнес-логике, а в навигации после неё.
2. В логе Playwright `waitForURL`/`page.on('framenavigated')` посмотреть полную последовательность
   визитов — характерный паттерн: URL страницы-источника появляется снова непосредственно перед
   ложным финальным URL, хотя код, вызвавший action, не должен был туда возвращаться.
3. Проверить, есть ли в Server Component той же страницы `redirect()`, зависящий от данных, которые
   мутирует вызываемый с неё action — это и есть источник гонки.

## Фикс

Вызывать `redirect()` **изнутри самого Server Action**, а не возвращать данные для клиентской
навигации:

```typescript
// ❌ Гонка: клиентская навигация может проиграть встроенному RSC-рефрешу вызывающей страницы
export async function placeOrderAction(input: Input): Promise<Result> {
  const order = await createOrder(input) // мутирует данные, от которых зависит redirect() на странице
  return { ok: true, accessToken: order.accessToken }
}
// клиент: const result = await placeOrderAction(...); window.location.href = `/success/${result.accessToken}`

// ✅ redirect() внутри action — NEXT_REDIRECT Next обрабатывает отдельно от обычного RSC-мерджа
// текущей страницы, гонки не возникает в принципе
import { redirect } from 'next/navigation'

export async function placeOrderAction(input: Input): Promise<Result> {
  const order = await createOrder(input)
  redirect(`/success/${order.accessToken}`) // либо внешний URL (paymentUrl) — redirect() поддерживает оба
}
```

`redirect()`, вызванный внутри Server Action, бросает специальный `NEXT_REDIRECT`, который framework
обрабатывает как терминальный сигнал навигации — он не участвует в обычном цикле RSC-мерджа
вызывающей страницы, поэтому конкурирующий `redirect()` из Server Component этой же страницы уже
не успевает вмешаться.

⚠️ Тип результата action'а после этого должен описывать только пути отказа (`{ ok: false, ... }`)
— успешный путь больше не возвращает обычное значение клиенту, он либо кидает `NEXT_REDIRECT`
(перехватывается рантаймом Next), либо (реже) `redirect()` кидает наружу неперехваченным, если
что-то в вызывающем коде обёрнуто в свой `try/catch` — не оборачивай вызов action'а с `redirect()`
внутри в `try/catch`, который может случайно поймать `NEXT_REDIRECT`.

## Известные случаи в монорепо

- **`aboi`** (2026-07-19/20, PLAN.md §18.7) — `checkout/page.tsx` редиректил на `/cart` при пустой
  корзине; `placeOrderAction`, вызванный с `/checkout`, опустошал корзину и тащил за собой
  ре-рендер `checkout/page.tsx` как часть своего ответа — гонка стабильно проявлялась на WebKit
  под 6-воркерной параллельной e2e-нагрузкой (`checkout.spec.ts:140`). Первая гипотеза (гонка
  cookie-сессии из авто-регистрации гостя, вызываемой до навигации) была отправлена на
  подтверждение живым staging-прогоном и **опровергнута** — сам баг был глубже, в протоколе
  Server Actions, а не в порядке клиентского кода. Фикс — `redirect()` внутри `placeOrderAction`
  (`lib/checkout.ts`).
