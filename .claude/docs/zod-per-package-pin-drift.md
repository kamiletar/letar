# zod: caret-диапазон в package.json потребителя не дедупает с точным корневым пином

Корень (`package.json`) держит намеренный точный пин `"zod": "4.4.3"` (без `^`), зарегистрирован
в `scripts/intentional-pins.json` — причина: дедуп с `@modelcontextprotocol/sdk`, тянущим свой
zod диапазоном `^3.25 || ^4.0` (`PLAN-INFRA-6.md §134`).

## Механизм

Bun isolated linker резолвит caret-диапазон потребителя **независимо** от корневого пина, в
максимальную satisfying версию реестра — даже если эта версия технически входит в диапазон
`^4.4.3`. На момент находки (2026-09-13) это `4.6.2`. Дедуп с корневым бакетом случается только
при **буквальном совпадении строки версии** — потребитель должен держать тот же точный пин
`"zod": "4.4.3"` (без `^`), а не просто совместимый диапазон.

Проверено экспериментально на `libs/form-mcp`:

- было `"zod": "4.6.2"` (свой точный пин, разъехавшийся с корнем) — изолированная копия в дереве;
- пробовал `"zod": "^4.4.3"` (казалось бы «правильный» паттерн, как у `libs/deploy-engine`) —
  `bun install --force` всё равно резолвил в изолированную `4.6.2`;
- поставил `"zod": "4.4.3"` (точно, без `^`) — только это задедуплило в общий корневой бакет.

## Симптом

Изолированная копия зависимости с независимой версией — несовместимые номинальные типы
(`ZodObject`/`$ZodType` из двух копий не совпадают) везде, где схемы потребителя пересекаются с
чем-то, типизированным против корневого zod (например `@letar/forms`). `TS2769: No overload
matches this call`, typecheck красный без единой строки в `bun install`/CI по дефолту.

## Найдено repo-wide (2026-09-13, thread `forms-zod-version-drift`, msg 1543 от deploy-agent-dev)

8 пакетов держали собственный разъехавшийся точный пин `"zod": "4.6.2"`: `libs/form-mcp`
(починено, коммит `0def61e3`), `apps/domwellbes` (починено владельцем, блокировало деплой),
`libs/deploy-mcp`, `libs/glitchtip-mcp`, `libs/mcp-test-kit`, `libs/studio-mcp`,
`libs/studio-time-mcp`, `libs/umami-mcp` (не починены на момент записи — вне владения
`forms-coordinator-dev`, репортнуты broadcast'ом остальным агентам).

Мимоходом: `libs/deploy-engine`'s `"^4.4.3"` тоже был тихо развалившимся экземпляром той же
болезни (просто не всплывал раньше — не типизирован против `@letar/forms`). Его изолированная
копия почистилась сама побочным эффектом `bun install --force`, без правки package.json — потому
что это была стелс-копия по `bun-install-stale-isolated-cache`, а не свой явный пин.

## Фикс

В `package.json` затронутого пакета — точная строка **без `^`**, совпадающая с корневым пином
буквально:

```diff
- "zod": "4.6.2"
+ "zod": "4.4.3"
```

Затем `bun install --force` из корня (обычный `bun install` без `--force` не всегда чистит уже
существующую изолированную копию — см.
[bun-install-stale-isolated-cache](/.claude/docs/bun-install-stale-isolated-cache.md)).

## Отличие от общего правила `root-pin-peer-drift`

[root-pin-peer-drift](/.claude/docs/root-pin-peer-drift.md) описывает дрейф в одном направлении
(корень уезжает вперёд/назад без пары в `overrides`/соседних пакетах). Здесь — обратное: сам
корень стабилен, а несколько **разных** нижестоящих пакетов независимо друг от друга завели
собственный точный пин и со временем разъехались с ним. `scripts/check-all.mjs`/
`intentional-pins` на 2026-09-13 сверяют только сам корневой пин против реестра причин — per-
workspace-package дрейф (чужой package.json держит свой пин той же зависимости) не проверяется
вообще. Кандидат на отдельную проверку — не сделано, см. `libs/forms/PLAN.md` не имеет отношения,
задача вне владения forms-coordinator-dev.
