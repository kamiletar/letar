# Идемпотентность платёжных вебхуков — паттерн монорепо

## Проблема

Провайдер эквайринга ретраит вебхук, если не получил ответ вовремя (T-Bank — 30 секунд), либо
шлёт несколько уведомлений об одном и том же событии по своей же логике (Точка — статус +
отдельное событие). Обработчик обязан быть безопасен при повторной доставке одного и того же
события и при доставке "не по порядку" (например, `FAILED` после уже применённого `SUCCEEDED`).

## Общая форма решения

Два независимых элемента, оба нужны:

1. **Уникальный внешний ID события** — колонка с `@unique` в Prisma/ZenStack-схеме, хранящая ID,
   который провайдер прислал для конкретного события/платежа (не ID заказа/счёта — тот
   переиспользуется между попытками оплаты).
2. **Guard по терминальному статусу домена** — обработчик не переводит сущность (`Payment`,
   `Order`, `Invoice`) из уже терминального состояния в другое, даже если событие формально новое.
   Защищает от гонки/переупорядочивания доставки, которую одна только проверка уникального ID не
   ловит (например, `FAILED` пришёл вторым после уже обработанного `SUCCEEDED`).

## select-then-create, а не catch-P2002

Проверка дубликата — `findUnique` по уникальной колонке, и только если записи нет — `create`,
всё внутри одной `prisma.$transaction`. Не ловить ошибку уникального ограничения (`P2002`) как
способ обнаружить дубликат.

**Почему:** так уже сделан существующий в монорепо прецедент идемпотентности не для платежей —
`recordInboundEvent()` в `apps/domwellbes/src/lib/integration/inbox.ts` (телефония/email/банк,
M7B). Платёжный код это решение унаследовал ради единообразия — не переизобретать способ
идемпотентности для каждого нового источника событий. Отдельно: поведение классов ошибок Prisma 7
под ZenStack/Kysely-движком (`PrismaClientKnownRequestError` и код `P2002`) для этого стека
монорепо на момент написания не проверено — `select`-then-`create` не зависит от точной формы
исключения конкретной версии клиента и остаётся рабочим независимо от того, как Prisma 7 это
исключение бросает.

## Известные реализации в монорепо

### domwellbes — `PaymentEvent.providerEventId`

[`src/lib/payments/apply-webhook-event.ts`](/apps/domwellbes/src/lib/payments/apply-webhook-event.ts) —
эталонная реализация паттерна. Отдельная таблица `PaymentEvent` с `@unique providerEventId`,
единая для реального вебхука и dev-симуляции оплаты. Внутри одной транзакции: `findUnique` по
`providerEventId` → если найдено, `{ duplicate: true }` без побочных эффектов; иначе `create`
события, затем проверка `payment.status` на терминальность (`SUCCEEDED`/`FAILED`/`CANCELED`) перед
`update`.

### studio — `Payment.tochkaPaymentId`

[`src/app/api/webhooks/tochka/route.ts`](/apps/studio/src/app/api/webhooks/tochka/route.ts) +
[`src/lib/tochka/webhooks.ts`](/apps/studio/src/lib/tochka/webhooks.ts) — три типа события
(`incomingPayment`/`acquiringInternetPayment`/`incomingSbpPayment`), каждый вычисляет свой ключ
идемпотентности (`paymentId`/`transactionId`/`operationId`/`qrcId` — провайдер называет поле
по-разному в зависимости от типа события и не документирует форму вебхука вовсе, только форму
собственного REST API), затем `findUnique` по `Payment.tochkaPaymentId` (`@unique`) вне явной
транзакции — `findUnique` и `create` идут последовательно, без `prisma.$transaction`. Терминального
guard в форме domwellbes здесь нет: `Invoice.status` не хранит "уже обработано", а пересчитывается
суммированием всех строк `Payment` при каждом новом платеже (частичная/полная оплата, несколько
платежей на один счёт — легитимный сценарий, не дубликат). Защиту от двойного учёта одного и того
же события даёт исключительно уникальность `tochkaPaymentId` на уровне `Payment`.

### aboi — `OrderPaymentEvent.providerPaymentId` ✅ закрыто 2026-08-21

[`src/app/api/webhooks/tinkoff/route.ts`](/apps/aboi/src/app/api/webhooks/tinkoff/route.ts) →
[`src/lib/order-paid.ts`](/apps/aboi/src/lib/order-paid.ts) (`finalizeOrderPayment`) — до
2026-08-21 идемпотентность держалась только на `if (order.status === 'PAID') return`, без
отдельной таблицы событий и без транзакционной изоляции от параллельного вызова (подробности
компромисса — см. историю файла). Приведено к общей форме: таблица `OrderPaymentEvent` с
`@unique providerPaymentId` (PaymentId из тела вебхука T-Bank, не путать с `OrderId` заказа —
тот переиспользуется между попытками оплаты), `findUnique` → `create` внутри
`prisma.$transaction`, старая проверка статуса оставлена второй линией защиты. Используется и
вебхуком, и ручной синхронизацией из `admin/payments` — оба пути идут через один и тот же
`finalizeOrderPayment`.

## Куда смотреть при добавлении нового провайдера эквайринга

1. Уникальная колонка под внешний ID события в `schema.zmodel` (`@unique`).
2. `findUnique` → `create` внутри `prisma.$transaction`, не catch на `P2002`.
3. Guard по терминальному статусу перед изменением статуса домена — если модель допускает только
   один финальный переход (как `Payment`/`Order` в domwellbes/aboi); при накопительной модели
   платежей на счёт (как `Invoice` в studio) — пересчёт суммы, а не guard по статусу.

## Почему не унифицировано в libs/ (оценка 2026-08-21)

Три реализации разошлись сильнее, чем кажется на первый взгляд — общего осталось ровно
`findUnique` → `create` по уникальному внешнему ID, три-пять строк. Всё вокруг них — как раз та
часть, где легко ошибиться, — оказалось непереносимо:

- **Разная форма guard'а, не только разные условия.** domwellbes и aboi проверяют терминальный
  статус (`SUCCEEDED`/`FAILED`/`CANCELED` vs просто `PAID`) и обновляют один и тот же ряд.
  У studio guard'а в этом смысле нет вовсе — `Invoice.status` пересчитывается суммированием всех
  `Payment` по счёту, повторный/частичный платёж это легитимный сценарий, а не дубликат. Общий
  хелпер с опциональным `statusGuard` не покрыл бы studio без второго опционального параметра
  «режим пересчёта», который по факту содержит всю бизнес-логику приложения — то есть был бы не
  переиспользуемым кодом, а разветвлённым конфигом на один вызов каждый.
- **У studio нет транзакции вокруг пары find→create вообще** (`route.ts:117-118` и `:283` —
  раздельные вызовы `prisma.payment.findUnique`/`prisma.payment.create`, без `$transaction`).
  Обёртка хелпера в `tx` параметр здесь ничего не даёт — вызывающий код и так не передаёт `tx`,
  и это отдельный, самостоятельный дефект (не предмет этой оценки), а не повод подгонять сигнатуру
  хелпера под текущее — ошибочное — состояние вызывающего кода.
- **Разные типы клиента БД у остальных двух.** domwellbes использует enhanced ZenStack-клиент
  (`getEnhancedPrisma`/`prisma` из `@/lib/db`), aboi — сырой `PrismaClient` (`prismaAuth` из
  `@/lib/prisma`). Внутри `$transaction` оба дают Prisma-совместимый `tx` с одинаковой формой
  делегатов, так что типизация сама по себе не блокер — но название модели-таблицы события у
  каждого своё (`paymentEvent` vs `orderPaymentEvent`), и добраться до него можно только через
  колбэк `(tx) => tx.paymentEvent`. Такой колбэк — ровно тот же объём кода, что инлайновый
  `findUnique`/`create`, только на один уровень косвенности глубже.
- **Побочные эффекты после коммита различаются по домену**, а не по количеству строк:
  фискализация чека (domwellbes) vs СДЭК/сертификат/email/зачёт баланса образца (aboi) vs
  ничего дополнительного (studio, пересчёт суммы делает сам вызывающий код). Хелпер, вынесенный
  только ради find→create, не касался бы этой части — то есть закрывал бы наименее рискованный
  кусок паттерна и оставлял бы риск (guard, побочные эффекты) там же, где он был.

Итог: три строки, вынесенные в `libs/`, стоили бы отдельного пакета, версии, импорта и
документации ради экономии, которая по факту не покрывает ни один реальный источник ошибок в этом
классе кода. Раздел «Куда смотреть» выше остаётся источником истины как чек-лист для нового
провайдера — воспроизводить паттерн копированием с сознательной проверкой guard'а под конкретную
модель, не тянуть общий хелпер.

**Что стоит сделать отдельно (не в рамках этой оценки):** обернуть studio-реализацию в
`prisma.$transaction`, как у domwellbes/aboi — это реальный пробел в самой studio, не аргумент
за или против общего хелпера.
