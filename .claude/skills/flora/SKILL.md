# Flora: рабочий процесс

Приложение — приватный submodule `apps/flora`. Источник текущей работы —
[`tasks/README.md`](/apps/flora/tasks/README.md), статусы — в `tasks/`, а не в исторических планах.
Публичный исходник этого навыка не должен содержать реквизиты, коммерческие условия и записи интервью.

## Начало и учёт времени

1. В Codex возьми `CODEX_THREAD_ID` текущего чата и передавай его явно как `sessionRef`
   во все принимающие этот параметр `time_*`. После сжатия/возобновления первым действием —
   `time_status({ sessionRef })`; закрытый по простою таймер сам не восстановится.
2. Для работы над Flora начни `time_start({ app: "flora", description, sessionRef, stage })`;
   смена задачи — `time_switch` с новым предметом работы. Описание видит заказчик.
   Обслуживание навыков/инфраструктуры относится к внутреннему контексту Letar, а не к счёту Flora.
3. Прочитай `apps/flora/AGENTS.md`, `tasks/README.md` и выбранную задачу. Из корня letar:

   ```powershell
   bun scripts/tasks.mjs next flora
   # Если пользователь назвал FL-NNN, сразу show вместо поиска следующей задачи.
   bun scripts/tasks.mjs show FL-NNN
   ```

4. Зарегистрируй сессию через `macro_start_session`. Фиксированная identity — `flora-dev`;
   используй существующий токен из приватной памяти, не печатай его и не создавай identity заново
   на основании устаревшего текста навыка. Перед регистрацией проверь занятость по
   [agent-mail.md](/.claude/rules/agent-mail.md); отдельной одновременной сессии нужна временная identity.
   Резервируй только изменяемые пути.

Полные правила таймера — [time-tracking.md](/.claude/rules/time-tracking.md).
Обычный конец ответа не останавливает таймер. При `/end-session` сначала закрой завершённые этапы
через `time_stage_close`, затем отдельно останови таймер с `sessionRef`: закрытие этапа не делает stop.
Фиксированную identity не ретирить; временную завершать по навыку `end-session`.

## Задача и результат

- Запусти `bun scripts/tasks.mjs start FL-NNN --owner <identity>`, запиши план в задаче и выполняй
  уже порученную работу. Не добавляй обязательное согласование каждого обратимого шага.
- `PLAN*.md`, `TASKS.md`, `BACKLOG.md`, `SESSION-STATE.md`, `SESSION-FINDINGS.md` заморожены.
  При необходимости читай только участок из поля `source`; итоги туда не дописывай.
- Новую самостоятельную находку добавляй через `bun scripts/tasks.mjs new flora "<заголовок>"`
  с размером/статусом и проверяемой приёмкой. Существующую задачу не дублируй.
- Применяй профильные правила перед изменением кода. Для Next.js прочитай нужные локальные docs
  пакета и [nextjs-apps.md](/.claude/rules/nextjs-apps.md); документационному исследованию этот кодовый
  маршрут не требуется.

### Интервью и кабинетное исследование

В отчёте `apps/flora/docs/research/` разделяй ответы участников, предложения архитектуры,
подтверждённые источниками возможности и фактически выполненные проверки. Сохраняй дату, первичные
ссылки, ограничения проверки и следующий измеримый эксперимент. Новые отчёты добавляй в документацию
`apps/flora/AGENTS.md`; коммерческие данные остаются внутри приватного submodule.

Исследование не является разрешением покупать подписки, вызывать платный API, загружать документы
поставщику или публиковать приложение. Уже выданное разрешение учитывай в его фактических пределах.
Установка, точность OCR, звук в фоне и скорость считаются проверенными только после реального опыта,
а согласование денежных условий — после ответа ответственного участника. Предложенные пороги
производительности не выдавай за результаты замеров.

Если кабинетная часть готова, но исходная приёмка включает непроверенный телефон, внешнюю интеграцию
или несогласованные условия, оставь задачу `review` и запиши остаток/следующие S/M-задачи:

```powershell
bun scripts/tasks.mjs set FL-NNN status=review
bun scripts/tasks.mjs note FL-NNN "Что исследовано; что ещё не проверено; где следующий шаг"
```

`done` — только когда выполнена вся приёмка выбранной задачи. Закрытие архивирует файл автоматически:

```powershell
bun scripts/tasks.mjs done FL-NNN --summary "Проверенный результат"
```

Актуальные исследования находятся через `apps/flora/AGENTS.md`; не копируй их изменяемые продуктовые
и финансовые решения в постоянные инструкции навыка.

## Submodule, проверки и фиксация

Перед правками проверь `git -C apps/flora status --short` и текущую ветку.
Рабочая ветка приложения — `main`; при detached HEAD или чужих правках не делай автоматический
checkout/pull поверх них. Порядок из [git.md](/.claude/rules/git.md) важнее старого шаблона синхронизации.

По `tasks/README.md` без поручения владельца **не выполнять push, bump SHA submodule в letar,
bun install/изменение bun.lock, deploy-request или генерацию публичного flora-e2e**.
Локальный scoped-коммит готового результата делай внутри приложения. Согласованный push выполняется
сначала для submodule; только затем можно фиксировать и публиковать его SHA в родительском репо.
Самостоятельный деплой запрещён; согласованный запрос маршрутизируется `deploy-agent-dev`
по [app-workflow.md](/.claude/rules/app-workflow.md).

Для кода: TDD и проверки затронутого проекта — `nx run-many -t format --projects=flora`,
`nx lint flora`, `nx typecheck:tsgo flora`, релевантные тесты. Никогда не используй голую `nx format`.
Docs-only исследованию не нужны bump версии и прогон приложения; проверь изменённые файлы dprint,
локальные ссылки, `git diff --check` и `bun scripts/tasks.mjs check` **из корня letar**.
Не объявляй проверку успешной, если hook лишь сообщил об отсутствующем скрипте и пропустил её.

Коммить точными файлами, не каталогом и не `git add .`; перед коммитом смотри staged-список,
после — `git show --stat HEAD` и статус. Если собственные связанные docs разделены scope-guard,
сначала проверь список файлов и применимость документированного исключения в `git.md`;
не включай `GIT_ALLOW_MULTI_SCOPE_COMMIT` по умолчанию и не отключай остальные проверки.

## Типичные ошибки и подводные камни

- Автоматические `git pull`/push из старого шаблона нарушают отдельные правила приложения.
  Получай актуальные ограничения из `tasks/README.md`, а не из старых статусов навыка.
- Отчёт, test fixture или готовый Dockerfile не подтверждают работающий боевой провайдер,
  реальные уведомления, установку на iPhone или настроенный деплой.
- `time_stage_close` и `time_stop` — независимые операции; PID общего MCP-процесса не заменяет
  идентификатор текущего чата.
- `.agents/skills/` — источник навыка, `.claude/skills/` — производная копия. При обновлении
  самого навыка используй [правила зеркала](/.claude/docs/agent-skills-mirror.md), не редактируй копию
  независимо и не захватывай чужие изменения при синхронизации.

Сценарии регрессии самого навыка — `evals/evals.json`. При изменении этих правил выполняй сценарии
в изолированном каталоге; реальные телефоны/оплата/публикация не должны быть побочными эффектами теста.
