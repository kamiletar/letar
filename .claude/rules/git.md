# Правила Git

## Формат коммитов

```
<type>(<scope>): <description>

[optional body]
```

### Типы

| Тип        | Описание                            |
| ---------- | ----------------------------------- |
| `feat`     | Новая функциональность              |
| `fix`      | Исправление бага                    |
| `refactor` | Рефакторинг без изменения поведения |
| `docs`     | Документация                        |
| `test`     | Тесты                               |
| `chore`    | Обслуживание (deps, config)         |
| `style`    | Форматирование кода                 |
| `perf`     | Оптимизация производительности      |

### Scope

- `premium-rosstil`, `imot`, `dashboard` — приложения
- `ui`, `form-components`, `label-printer-core` — библиотеки
- `deps` — зависимости
- `config` — конфигурация

## Ветки

```
main                    # Production
├── feature/<name>      # Новые фичи
├── fix/<name>          # Баг-фиксы
├── refactor/<name>     # Рефакторинг
└── chore/<name>        # Обслуживание
```

## Правила

- Коммиты на русском или английском (единообразно в проекте)
- Один коммит = одно логическое изменение
- Не коммитить `.env`, `node_modules`, `dist`
- ⚠️ **Коммить сразу после каждого готового куска — не копить изменения до конца сессии.**
  «Готовый кусок» — это законченная логическая единица (один файл починен, один тест написан,
  одна доработка внесена), а не «вся задача целиком». Не жди явной просьбы пользователя
  закоммитить и не оставляй несколько готовых кусков висеть незакоммиченными «чтобы закоммитить
  разом в конце». Чем дольше изменения лежат в рабочем дереве, тем больше окно для гонки с
  другими агентами (см. ниже) и тем больше риск потерять их, если сессия оборвётся.
- Перед push: lint + typecheck + test

## Работа рядом с другими агентами

В этом репозитории одновременно работают несколько агентов над разными проектами. Отсюда все
правила ниже — они не про гигиену, а про то, чтобы не забрать чужую работу в свой коммит.

**Коммить сразу после каждого готового куска.** «Готовый кусок» — законченная логическая единица
(файл починен, тест написан), а не «вся задача целиком». Не жди просьбы пользователя и не копи
изменения до конца сессии: чем дольше правки лежат в рабочем дереве, тем больше окно для гонки.
Это основная защита, всё остальное — страховка.

**Коммить только своими путями:**

```bash
git add apps/my-app/
git commit -m "feat(my-app): описание" -- apps/my-app/
```

⛔ **Запрещено:** `git reset --hard`, `git reset HEAD`, `git checkout -- .`, `git add .`,
`git stash` без явной необходимости, `git push --force`. Всё это забирает или уничтожает чужие
незакоммиченные изменения. Первые четыре блокирует хук `.claude/hooks/validate-bash.js`.

**Откатываешь свои правки — перечисляй файлы, а не каталог.** `git checkout -- <файлы>`, не
`git checkout -- apps/<app>`. Каталог заберёт и чужое.

**Видишь в `git status` чужие файлы** — игнорируй их, добавляй только свои. Перед любым массовым
откатом сначала посмотри `git status` глазами.

### Технический барьер: pre-commit scope-guard

```bash
bash scripts/hooks/install.sh --all-submodules
```

Ставит хук в корень letar и во все 14 submodule. Хук блокирует коммит, если застейджены файлы из
более чем одного scope (`apps/<x>`, `libs/<x>`, `infra/<x>` или первый сегмент пути). Осознанный
multi-scope коммит — явным флагом:

```bash
GIT_ALLOW_MULTI_SCOPE_COMMIT=1 git commit -m "..."
```

⚠️ **Исключение:** корневые док-файлы одного приложения/submodule (`PLAN.md`,
`PLAN_COMPLETED.md`, `PLAN_TESTING.md`, `CHANGELOG.md`, `README.md`) считаются одним scope
`docs-root`, а не форкаются по имени файла. Без этого исключения обычное «обновить план +
changelog после сессии» (см. `app-workflow.md` § «После завершения задачи») ловило бы ложное
срабатывание — `PLAN.md` и `PLAN_COMPLETED.md` в корне submodule не имеют общего сегмента пути
(`первый сегмент` = само имя файла), поэтому без спецкейса считались бы разными scope. Правило
остаётся строгим для настоящего multi-scope — `apps/appA/PLAN.md` + `apps/appB/PLAN.md`
по-прежнему блокируется, потому что их scope (`apps/appA`, `apps/appB`) вычисляется до попадания
в спецкейс `docs-root`.

Хук не автоустанавливается для новых клонов и не ловит случай «чужая правка внутри одного scope» —
от этого защищает только file reservation через Agent Mail.

⚠️ MCP-инструмент `install_precommit_guard` (Agent Mail) на 2026-08-07 нерабочий — возвращает
пустой хук. Не полагайся на него.

## Работа с приватными submodule

Приватные приложения — git submodules на репозитории `kamiletar/letar-private-*`
([repo-structure](/.claude/docs/repo-structure.md)).

```bash
cd apps/driving-school          # внутри submodule
git checkout main               # submodule по умолчанию в detached HEAD
git pull origin main
# ... меняешь код ...
git add . && git commit -m "feat(driving-school): описание"
git push origin main            # пуш в приватный репо

cd ../..                        # назад в letar
git add apps/driving-school     # фиксируем новый SHA submodule
git commit -m "chore: bump driving-school submodule" -- apps/driving-school
git push
```

**Обязательно перед правками внутри submodule:** проверь `fetch_inbox` и существующие file
reservation на `apps/<submodule>/**`. Резервация не блокирует чужие действия физически, но это
единственный способ увидеть, что в том же submodule уже кто-то работает.

⛔ **Не делай:**

- Не редактируй файлы submodule без `git checkout main` — правки в detached HEAD теряются при
  следующем `git submodule update`.
- Не добавляй пути submodule в корневой `.gitignore` — Nx уважает gitignore и проекты исчезнут из
  графа.
- Не добавляй `src/generated/` в `.gitignore` submodule, если папка была tracked.

**Каждому submodule нужен свой `.gitignore`** — корневой `.gitignore` на вложенный независимый
репозиторий не действует. Заводишь новый submodule — клади его **до** первого `git add`.
Образец — `apps/domwellbes/`.

⚠️ **`dprint.json` — другое: наличие своего файла необязательно.** dprint ищет конфиг, поднимаясь
по дереву каталогов от `cwd`, независимо от границ git-репозитория — submodule без собственного
`dprint.json` (на 2026-08-12: `archetest`, `auth-hub`, `mandala`, `dsperevod-e2e`,
`svoichuzhie-e2e`) прозрачно наследует корневой `dprint.json`, если сам не входит в его
`excludes`. Свой `dprint.json` нужен только submodule, которому требуются настройки, отличные от
корневых (12 остальных submodule — именно поэтому они и перечислены в `excludes` корневого
файла). Если заводишь его — держи синхронным с корневым по всем правилам, которые не являются
намеренным расхождением (прецедент рассинхрона — `useBraces`, §20 `PLAN-INFRA.md`).

⚠️ **`git commit -- <путь>` после `git rm --cached` возвращает файл.** Коммит с pathspec берёт
содержимое рабочей копии, а не индекса. Удаление из индекса коммить **без** pathspec:

```bash
git rm -r --cached dist
git add .gitignore
git commit -m "chore: убрать артефакты сборки из индекса"
```

Это единственное законное исключение из «коммить только свои пути», и только внутри submodule.

**Обновить все submodules:**

```bash
git submodule update --remote --recursive
GIT_ALLOW_MULTI_SCOPE_COMMIT=1 git commit -m "chore: bump all submodules"
```

### Почему эти правила такие подробные

За 2026-08-06…09 произошло пять инцидентов подряд: потерянная чужая работа при массовом откате,
чужие staged-файлы в четырёх коммитах, перемешанные правки двух сессий внутри одного submodule.
Разбор каждого, с механизмом и следствиями —
[git-multi-agent-incidents](/.claude/docs/git-multi-agent-incidents.md). Читай его, если правила
выше кажутся избыточными или если собираешься их менять.
