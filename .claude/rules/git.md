# Правила Git

## Формат коммитов

```
<type>(<scope>): <description>

[optional body]
```

### Типы

| Тип        | Описание                            |
| ---------- | ----------------------------------- |
| `feat`     | Новая функциональность              |
| `fix`      | Исправление бага                    |
| `refactor` | Рефакторинг без изменения поведения |
| `docs`     | Документация                        |
| `test`     | Тесты                               |
| `chore`    | Обслуживание (deps, config)         |
| `style`    | Форматирование кода                 |
| `perf`     | Оптимизация производительности      |

### Scope

- `premium-rosstil`, `imot`, `dashboard` — приложения
- `ui`, `form-components`, `label-printer-core` — библиотеки
- `deps` — зависимости
- `config` — конфигурация

## Ветки

```
main                    # Production
├── feature/<name>      # Новые фичи
├── fix/<name>          # Баг-фиксы
├── refactor/<name>     # Рефакторинг
└── chore/<name>        # Обслуживание
```

## Правила

- Коммиты на русском или английском (единообразно в проекте)
- Один коммит = одно логическое изменение
- Не коммитить `.env`, `node_modules`, `dist`
- ⚠️ **Коммить сразу после каждого готового куска — не копить изменения до конца сессии.**
  «Готовый кусок» — это законченная логическая единица (один файл починен, один тест написан,
  одна доработка внесена), а не «вся задача целиком». Не жди явной просьбы пользователя
  закоммитить и не оставляй несколько готовых кусков висеть незакоммиченными «чтобы закоммитить
  разом в конце». Чем дольше изменения лежат в рабочем дереве, тем больше окно для гонки с
  другими агентами (см. ниже) и тем больше риск потерять их, если сессия оборвётся.
- Перед push: lint + typecheck + test

## Работа в монорепозитории с другими агентами

⚠️ **КРИТИЧНО:** В этом репозитории могут одновременно работать несколько агентов над разными проектами.

**Прецедент (2026-08-06):** во время уборки накопленных незакоммиченных изменений один агент
вживую поймал гонку — другой агент параллельно делал `git reset`+commit в том же `.git`-каталоге,
`git log`/`reflog` на несколько секунд показывали разное HEAD. Коммиты не потерялись, но был
близкий вызов. Первопричина — не сама параллельность (её не убрать), а то, что несколько агентов
успели накопить часы незакоммиченной работы к моменту, когда кто-то решил всё разом прибрать.
Правило «коммить сразу после готового куска» выше — это и есть основная защита от подобной
гонки: чем короче агент держит изменения незакоммиченными, тем меньше шанс, что чужой коммит
затронет тот же файл в то же окно времени. Полная изоляция через `git worktree` на агента
рассматривалась как альтернатива и отклонена как постоянный режим — добавляет забываемый шаг
мержа обратно в `main` взамен забываемого шага коммита; уместна точечно для рискованных
многофайловых рефакторов, не как дефолт.

**Третий и четвёртый прецедент, тот же день следующей сессии (2026-08-07).** Два параллельных
фоновых агента при бампе SHA submodule выполнили голый `git commit`/`git add` и затянули в свои
коммиты чужие staged-файлы от не связанной с их задачей инфра-сессии (Traefik staging-labels,
`PLAN-INFRA.md` §48 M2): `apps/kami-key-the-landing` уехал в коммит `070d6eb0`, пять
`docker-compose.staging.yml` (archetest/auth-hub/grandslamcup/mandala/time) — в `42f5ac81`.
Данные не потеряны — оба коммита содержат корректный код, просто под чужим commit message — но
письменное правило (уже дважды задокументированное ниже с разбором двух прошлых инцидентов) не
предотвратило третий и четвёртый случай в один день. Вывод: agent'ы физически не перечитывают этот
файл перед каждым коммитом, поэтому вместо третьей попытки усилить формулировку — установлен
технический барьер, см. «Технический барьер: pre-commit scope-guard» ниже.

**Второй прецедент того же дня (2026-08-06), уже с реальной потерей.** Агент, наводивший порядок
с форматированием (переход submodule на собственные `dprint.json`), откатывал ненужные правки
форматтера через `git checkout` по каталогу submodule — и вместе с ними снёс чужую готовую
незакоммиченную работу в `apps/studio`: рабочее дерево оказалось чистым на HEAD, в `git stash`
пусто, в `reflog` никаких новых записей, то есть восстанавливать было нечего. Работу пришлось
писать заново из контекста сессии.

Отсюда два вывода, каждый — отдельная защита:

- **Откатываешь свои правки — откатывай по именам файлов, которые сам менял, а не по каталогу.**
  `git checkout -- <конкретные файлы>` вместо `git checkout .` / `git checkout -- apps/<app>`.
  Форматтер и так знает список изменённых им файлов; каталог целиком забирает и чужое.
- **Перед любым массовым откатом — `git status` и глазами.** Если в выводе есть файлы, которых ты
  не трогал, значит рядом работает кто-то ещё: либо сузь путь, либо спроси владельца. Массовые
  прогоны форматирования по всему репо особенно опасны именно этим — они по своей природе
  затрагивают тысячи файлов и провоцируют «откатить всё разом».

**ЗАПРЕЩЕНО:**

- `git reset HEAD` — сбросит изменения других агентов
- `git reset --hard` — потеряет изменения других агентов
- `git checkout -- .` — откатит изменения других агентов
- `git stash` без явной необходимости — спрячет чужие изменения

**ПРАВИЛЬНЫЙ ПОДХОД:**

```bash
# ✅ Добавляй только свои файлы
git add apps/my-app/

# ✅ Коммить только свои изменения
git commit -m "feat(my-app): описание"

# ❌ НЕ делай reset если видишь чужие файлы в staging
# ❌ НЕ делай git add . в монорепо
```

**Если видишь чужие файлы в `git status`:**

1. Игнорируй их — это работа других агентов
2. Добавляй только свои файлы через `git add apps/<твой-проект>/`
3. Коммить только свои изменения

**Если MCP Agent Mail запущен:**

- Перед редактированием `libs/**` — проверь резервации через `file_reservation_paths`
- Зарезервируй свои файлы при старте сессии

### Технический барьер: pre-commit scope-guard

⚠️ **MCP-инструмент `install_precommit_guard` (Agent Mail) на 2026-08-07 нерабочий** — вызов
возвращает пустой хук (`{"hook": ""}`) и ничего не пишет в `.git/hooks/`. Предупреждение сервера
про «authoritative reservation gate» при конфликте file_reservation — обещание, а не факт: он не
подходит как защита прямо сейчас. Если когда-нибудь начнёт возвращать непустой хук — переоценить
это правило, но не раньше проверки на реальном коммите.

Вместо него — локальный git-хук `scripts/hooks/pre-commit-scope-guard.sh`, установка:

```bash
bash scripts/hooks/install.sh
```

Ставит связку `pre-commit-scope-guard.sh` + `pre-commit-sops.sh` в `.git/hooks/pre-commit`
(подробности шифрования — [secret-manager.md](/.claude/docs/secret-manager.md)). Не требует
переустановки при правках docs — только при изменении самих скриптов в `scripts/hooks/`.

**Что делает:** перед коммитом смотрит `git diff --cached --name-only` и группирует застейдженные
файлы по scope — `apps/<x>`, `libs/<x>`, `infra/<x>`, либо первый сегмент пути для остального
(`.claude`, `PLAN.md` и т.д.). Если файлов из **более чем одного** scope — коммит блокируется с
списком scope и подсказкой (`git reset -- <лишнее>` + `git commit -- <только свои пути>`). Именно
эта проверка поймала бы оба коммита из прецедента выше: `apps/kami-key-the-landing` рядом с чужим
submodule-бампом — два разных `apps/*`; пять `docker-compose.staging.yml` из разных `apps/*` —
пять scope разом.

**Осознанный multi-scope коммит** (bump all submodules, repo-wide format) — явный обход:

```bash
GIT_ALLOW_MULTI_SCOPE_COMMIT=1 git commit -m "..."
```

**Ограничения, о которых надо помнить:**

- Хук стоит только у тех, кто выполнил установку локально — не автоустанавливается для новых
  агентов/клонов, и уже установленный у кого-то старый хук (например только `pre-commit-sops.sh`
  от `cp` по старой инструкции) не обновится сам, нужно перезапустить `install.sh`.
- Ловит только **факт коммита из нескольких scope одновременно** — не отличает «моя чужая правка
  затесалась» от «я осознанно делаю одну логическую multi-app правку». Это и есть причина, почему
  обход существует, а не бесшовный whitelist: явный флаг — тот же принцип, что «коммить только
  явные пути», просто перенесённый на уровень «явно скажи, что это намеренно многоскоуповое».
- Не защищает от того, что чужой файл окажется застейджен **в одном scope** с твоим (например два
  агента одновременно правят разные файлы в одном и том же `apps/<x>`) — это по-прежнему требует
  file reservation через Agent Mail, хук её не заменяет.

## Работа с приватными submodule

Приватные приложения (aboi, driving-school, premium-rosstil, imot + их e2e и driving-school-db) — это **git submodules**, указывающие на репо `kamiletar/letar-private-*`. Подробнее: [repo-structure](/.claude/docs/repo-structure.md).

### Изменение кода в submodule

```bash
cd apps/driving-school          # внутри submodule
git checkout main               # submodule по умолчанию в detached HEAD
git pull origin main
# ... меняешь код ...
git add . && git commit -m "feat(driving-school): описание"
git push origin main            # пуш в приватный репо

cd ../..                        # назад в letar
git add apps/driving-school     # фиксируем новый SHA submodule
git commit -m "chore: bump driving-school submodule"
git push                        # пуш в публичный letar
```

### Что НЕ делать

- ❌ **НЕ редактируй файлы submodule без `git checkout main`** — изменения попадут в detached HEAD и потеряются при следующем `git submodule update`.
- ❌ **НЕ добавляй пути submodule в корневой `.gitignore`** — Nx уважает gitignore при сканировании проектов и приватные проекты исчезнут из `nx show projects` / `nx affected`. Submodule в Git хранится как gitlink (SHA), физически working tree не закоммитится в родительский репо без `.gitignore` страховки.
- ❌ **НЕ добавляй `src/generated/` в .gitignore submodule** если эта папка раньше была tracked (например, `libs/driving-school-db/src/generated/prisma/` — это типы Prisma, должны быть в репо).

### ⚠️ Каждому submodule нужен СВОЙ `dprint.json` — они уже заведены, не потеряй при новом

Тот же принцип «корневой конфиг не действует на вложенный независимый git-репозиторий»
применяется не только к `.gitignore`, но и к `dprint.json`. До 2026-08-06 своего конфига не было
ни у одного submodule: `dprint fmt` внутри них поднимался по дереву и подхватывал конфиг летара,
из-за чего форматирование работало только при работе внутри монорепо и молча меняло поведение при
клонировании репозитория в одиночку. Сейчас `dprint.json` есть у всех 14.

**Заводишь новый submodule — клади `dprint.json` рядом с `.gitignore`, до первого `dprint fmt`.**
Образец — любой существующий, например `apps/domwellbes/dprint.json`; он повторяет корневой
летаровский минус монорепо-специфичные `excludes`. Плагины должны быть тех же версий, иначе стиль
разойдётся с остальным репозиторием.

**Заводишь worktree внутри submodule** — добавь его путь в `excludes` этого `dprint.json` до
первого прогона: dprint не различает границы worktree и обойдёт его как обычную директорию.
Стандартный `.claude/worktrees` там уже прописан. Подробности и инцидент, из-за которого это
задокументировано, —
[dprint-worktree-submodule-scope.md](/.claude/docs/dprint-worktree-submodule-scope.md).

### ⚠️ Каждому submodule нужен СВОЙ `.gitignore`

Корневой `.gitignore` монорепо **не действует** на вложенный независимый git-репозиторий.
Submodule видит только собственный `.gitignore`, а его у свежесозданного нет — поэтому первый же
`git add .` внутри него уносит в коммит `node_modules/`, `.next/`, `dist/`, `*.tsbuildinfo`.

Прецедент: `domwellbes` при заведении submodule утащил `dist/tsconfig.tsbuildinfo` в initial commit.

**Заводишь новый приватный submodule — клади `.gitignore` ДО первого `git add`.** Образец — любой
существующий, например `apps/domwellbes/.gitignore`:

```
node_modules/
.next/
next-env.d.ts
out/
dist/
*.tsbuildinfo
.env.local
.env.docker
/coverage
test-results/
playwright-report/
*.log
```

⚠️ `next-env.d.ts` в этом списке не для красоты: файл генерирует сам Next.js, и его содержимое
зависит от режима — `next dev` пишет ссылки на `./.next/dev/types/`, `next build` на
`./.next/types/`. Пока он трекался, каждая сборка меняла его туда-сюда и шумела в `git status`
при деплое. Документация Next 16 требует того же («should not be tracked by version control»),
а корневой `.gitignore` монорепо его уже игнорирует — но на submodule не действует. Вычищен из
шести submodule 2026-08-05; `nx typecheck:tsgo` и `next build` без него работают.

> Обычные (не submodule) приложения монорепо — `apps/archetest`, `apps/kami` и прочие — своего
> `.gitignore` **не требуют**: они часть корневого репо и закрыты его правилами.

### ⚠️ `git commit -- <путь>` после `git rm --cached` возвращает файл

Коммит с pathspec берёт содержимое **рабочей копии**, а не то, что лежит в индексе. Поэтому
последовательность «убрать из индекса → закоммитить по пути» отменяет саму себя:

```bash
git rm -r --cached dist        # удаление подготовлено в индексе
git commit -- .gitignore dist  # ❌ dist добавляется обратно из рабочей копии
```

Правильно — коммитить удаление **без pathspec** (индекс уже содержит только нужное):

```bash
git rm -r --cached dist
git add .gitignore
git commit -m "chore: убрать артефакты сборки из индекса"
```

⚠️ Это единственное законное исключение из правила «коммить только свои пути» (см. ниже
«Работа в монорепозитории»), и оно применимо **только внутри submodule**, где кроме тебя никто
не работает. В корневом репо голый `git commit` заберёт чужие staged-файлы — там сначала
проверь `git status`, а после коммита — `git show --stat`.

### Обновить все submodules до последних коммитов

```bash
git submodule update --remote --recursive
git add .
git commit -m "chore: bump all submodules"
```
