# Правила для .env файлов

> Правило намеренно без frontmatter `paths:` — оно должно действовать и в момент создания нового
> файла окружения, когда никакой `.env` ещё не открыт. Не «чини» это добавлением `paths:`.
> Прежде здесь стоял `alwaysApply: true` — поле **из Cursor**, Claude Code его не знает.

## Какой файл для чего

| Файл              | Коммитится | Содержимое                                                     |
| ----------------- | ---------- | -------------------------------------------------------------- |
| `.env`            | ✅         | ⛔ **только** `PORT=XXXX`, ничего больше                       |
| `.env.local`      | ❌         | секреты локальной разработки, переопределяет `.env`            |
| `.env.docker`     | ❌         | реальные секреты production                                    |
| `.env.docker.enc` | ✅         | SOPS-шифровка `.env.docker` — **источник истины** для прода    |
| `.env.staging`    | ❌         | staging, единственное место для `ALLOW_DEV_SESSION` (см. ниже) |

Причина запрета секретов в `.env`: он коммитится в git. Даже dev-only секреты туда не попадают.

⚠️ **Правило про «только порт» описывает желаемое, а не текущее состояние.** Девять приложений
`.env` не имеют вовсе: у лендингов порт прямо в команде (`"command": "next dev -p 3008"` в
`project.json`), у части — `PORT=` в `.env.local`. **Любой код, которому нужен порт приложения,
обязан проверять все три места** — готовый обход в `libs/generators/src/utils/ports.ts`
(`collectAppPorts`). Прецедент: автоподбор порта в генераторе считал занятыми только `apps/*/.env`
и ронял `e2e-suite` на лендингах.

## Прод-секреты: `.env.docker.enc` — источник истины

Локальная копия `.env.docker` рабочая, серверная производная — её перезаписывает расшифровка
`.enc` при каждом деплое, править на сервере руками бессмысленно.

```bash
sops apps/<app>/.env.docker.enc          # штатная правка: расшифрованный текст в $EDITOR
```

Требует `SOPS_AGE_KEY_FILE=$HOME\.age\letar-key.txt` (ключ из KeePassXC). Подробнее —
[secret-manager](/.claude/docs/secret-manager.md).

**Новый секрет на прод:** правишь `.enc` → коммитишь → обычный deploy-request к `deploy-agent-dev`.

⚠️ **Точечная правка одного ключа скриптом** (не человеком в редакторе) — только через
`scripts/sops-env-set.sh <app> <staging|docker> <KEY> <VALUE>`. Голый `sops --encrypt --output`
на временном файле ломается двумя способами: `.sops.yaml` матчится по **входному** пути, а
формат `.enc` бывает и dotenv-построчным, и JSON-блобом — разбор в
[sops-env-encrypt-input-path-matching](/.claude/docs/sops-env-encrypt-input-path-matching.md).

⚠️ **Отсутствие переменной в `.env.docker` на сервере — не диагноз**, а чаще всего отставший
checkout. Проверяй `.enc` в актуальном `main`. И **никогда не генерируй недостающий секрет
заново**, не проверив вторую сторону: секреты OIDC-клиентов общие для Ключницы и приложения,
новый ключ ломает вход.

⛔ **`/sync-env` устарел** — команда и скрипты `sync-env-docker.sh`/`pull-env-docker.sh` возили
`.env.docker` по SSH до перехода на SOPS и ходят на выведенный из эксплуатации s1.

## ⚠️ Новая переменная окружения — ДВА места обязательно

1. **`.env.docker` / `.env.docker.enc`** — само значение.
2. **`apps/<app>/docker-compose.production.yml` → `services.app.environment`** — строка
   `MY_VAR: ${MY_VAR}`.

**Почему оба:** `--env-file .env.docker` делает переменные доступными только для интерполяции
`${VAR}` внутри compose-файла и **не** прокидывает их в контейнер. В контейнер попадает лишь то,
что явно перечислено в `environment:`.

**Симптом пропущенного шага 2:** значение в `.env.docker` есть, контейнер падает или отдаёт 500,
будто переменной нет. Проверка: `docker exec <app>-app sh -c 'env | grep MY_VAR'` → пусто.

⚠️ **Для `NEXT_PUBLIC_*` двух мест мало** — значение должно физически лежать в `.env.docker`
**до** сборки, иначе Next инлайнит в клиентский бандл `undefined` без единой ошибки в логах:
[nextjs-public-env-build-time-inlining](/.claude/docs/nextjs-public-env-build-time-inlining.md).

## ⛔ `ALLOW_DEV_SESSION` / `DEV_SESSION_TOKEN` — ТОЛЬКО в `.env.staging`

Пара открывает эндпоинт `/api/auth/dev-session` — создание сессии для **любого** email без
пароля и OIDC.

- **Никогда не попадают в `.env.docker`/`.env.docker.enc`** — даже временно, даже случайно.
  Вместе в прод-конфиге они означают открытый бэкдор на реальном проде.
- `DEV_SESSION_TOKEN` генерировать только инструментом и в base64url-алфавите (`+` в query
  декодируется в пробел), см. [security.md](/.claude/rules/security.md).
- Копируешь `.env.staging` как шаблон для прод-окружения — вручную вычисти эту пару.

**Почему отдельное правило:** проверка `NODE_ENV === 'production'` защитой не является — см. ниже.

## ⚠️ `NODE_ENV === 'production'` не отличает прод от staging

`next build`/`next start` всегда выставляют `NODE_ENV=production` — и на staging, и в локальной
прод-сборке. Любое решение «это прод или нет» (индексация, дев-бэкдоры, debug-панели, verbose-логи)
проверяет **явный домен/URL** (`BASE_URL`/`NEXT_PUBLIC_BASE_URL` против списка продакшен-доменов),
а не `NODE_ENV`. Есть уже такая проверка в приложении (как `IS_PRODUCTION_DOMAIN` в `robots.ts`) —
вынеси в общую константу, не пиши вторую похожую рядом.

Найдено трижды с разными следствиями (открытый бэкдор, противоречивая индексация, падающая
локальная сборка): [node-env-not-production-signal](/.claude/docs/node-env-not-production-signal.md).
