# Правила для библиотек

⚡ **Не создавай библиотеку руками** — используй `nx g @letar/generators:new-lib <name>`, он раскладывает
всю структуру ниже (включая `tsconfig.spec.json`, обязательный для vitest 4 + vite 8 oxc) и уже сверен с
актуальными `libs/format-utils`/`libs/validation-utils`. Ручной процесс ниже — для справки/понимания, что
генератор делает под капотом.

## Структура библиотеки

```
libs/my-lib/
├── src/
│   ├── index.ts          # Главный экспорт
│   └── lib/
│       ├── feature.ts    # Реализация
│       └── feature.spec.ts
├── package.json          # @letar/my-lib
├── project.json          # Nx конфигурация
├── tsconfig.json         # composite: true
├── tsconfig.lib.json
└── README.md             # Документация API
```

## package.json

```json
{
  "name": "@letar/my-lib",
  "version": "0.1.0",
  "main": "./src/index.ts",
  "types": "./src/index.ts"
}
```

## Подключение к приложению

📍 **Это единственное место, где процедура описана полностью.** README библиотек и
`.claude/commands/create/new-lib.md` дают одну фразу «что обязательно» и ссылаются сюда —
не копируй туда подробности. Расползшаяся копия 2026-08-04 стоила пяти одинаковых правок
подряд (корневой `PLAN.md` §29).

**Обязательное — одно:** чтобы Nx видел ребро графа. Если библиотеки нет в `dependencies`
приложения — пропиши её в `nx.implicitDependencies` его `package.json`. Это даёт корректные
`nx affected`, порядок сборки и инвалидацию кэша.

**Резолв самого импорта `@letar/*` от настроек приложения не зависит.** Он держится на
`customConditions: ["@letar/source"]` в корневом `tsconfig.base.json` + `exports` с этим условием
в `libs/<name>/package.json` (генератор `new-lib` их проставляет). Поэтому `dashboard` импортирует
`@letar/forms` и `@letar/chakra-provider`, не имея для них ни одной записи в `paths`.

**`paths` и `references` в `tsconfig.json` приложения — вспомогательные, не обязательные.**
Они безвредны и помогают редактору, но обязательными их считать не надо:

- `paths` нужны там, где линка в `node_modules` нет (подключение только через
  `implicitDependencies`), и отдельной строкой на каждый подпуть — см. раздел ниже;
- `references` **собирает** только `tsc --build`, а его ни одно приложение в `apps/` не
  запускает. Рассинхрон `paths` ↔ `references` **не является дефектом** и выравнивания «ради
  симметрии» не требует. ⚠️ Но «не собирает» ≠ «не читает»: обычный `tsc --noEmit -p` и
  `tsgo --noEmit` references **читают** — ради редиректа исходника библиотеки на её
  скомпилированный `.d.ts`. Отсюда весь класс поломок ниже.

⛔ **`nx sync` этого не чинит** — `@nx/js:typescript-sync` отключён в `nx.json`
(`sync.disabledTaskSyncGenerators`), а `nx sync`/`nx sync:check` не вызываются ни в CI, ни в
git-хуках. `references` правятся руками либо не правятся вовсе.

Детали и замер 2026-08-04 — [Окружение](/.claude/docs/environment.md#разработка-shared-библиотек),
раздел «⚠️ Всё вышесказанное относится к `tsc --build` — а приложения его не используют».

### ⚠️ Исключение: устаревший `libs/<name>/dist/*.d.ts` ломает именно `tsgo`

Утверждение выше («`references` не используются приложениями») верно, пока у библиотеки нет
локального `dist/` (генерируется её собственным таргетом `typecheck`, не `typecheck:tsgo` —
см. `libs/ui/project.json`). Если `dist/*.d.ts` физически существует и разошёлся с
`src/index.ts`, `tsgo --noEmit` приложения-потребителя делает project-reference редирект на
устаревший скомпилированный `.d.ts` вместо исходника — новый экспорт из библиотеки тихо не
виден (`TS2305: has no exported member`), а при удалении `dist/` — требует его пересборки
(`TS6305`). `tsc` (не `tsgo`) в такой ситуации ведёт себя иначе и на новый экспорт не жалуется,
поэтому баг всплывает только в быстром `typecheck:tsgo`, который и гоняют приложения.

Наступили 2026-08-04 при добавлении `FileTrigger` в `@letar/ui` — `dist/index.d.ts` библиотеки
был собран ранее (кем/чем — не установлено, `dist/` не в git) и не содержал новый экспорт.

### ⚠️ Тот же редирект под обычным `tsc`: ссылка на solution-конфиг библиотеки резолвится в `out-tsc/spec/`

Оговорка «`tsc` (не `tsgo`) ведёт себя иначе» выше касается только _устаревшего_ `.d.ts`. От
_отсутствующего_ обычный `tsc --noEmit -p` не застрахован ровно так же — и промахивается ещё
неприятнее.

Ссылка вида `{ "path": "../../libs/<name>" }` ведёт на **solution-конфиг** библиотеки
(`files: []` + `references` на `tsconfig.lib.json` и `tsconfig.spec.json`). Оба подпроекта
включают `src/**/*.ts`, то есть претендуют на один и тот же исходник, и TypeScript выбирает
**последний** в списке. Порядок в `libs/*/tsconfig.json` никем не выровнен:

- `libs/email` — `spec`, затем `lib` → редирект в `dist/` (лежит рядом, собирается таргетом
  `typecheck` библиотеки);
- `libs/redis-client` — `lib`, затем `spec` → редирект в `out-tsc/spec/`, **который не
  собирает ни один таргет вообще**.

Второй случай — вечно красный `TS6305: Output file '…/out-tsc/spec/src/index.d.ts' has not
been built`. Первый зелёный только по случайности: `dist/` в `.gitignore`, так что на свежем
клоне он падает точно так же.

Дальше идёт каскад, который легко принять за отдельные баги: провалившийся редирект делает
весь модуль `any`, и любой колбэк по его значению получает `TS7006: implicitly has an 'any'
type`. **Аннотации типов в этих местах — не починка, а маскировка**: они гасят симптом и
оставляют библиотеку нетипизированной. Проверяется позитивным контролем — присвоить результат
функции библиотеки заведомо неверному типу и убедиться, что `tsc` ругается по существу
(`TS2322`), а не молчит.

**Фикс (`dashboard-agent`, 2026-08-07): убрать `references` на библиотеки из
`apps/<app>/tsconfig.json`** — тогда редиректа нет, библиотека проверяется по исходникам, и
никаких предварительно собранных артефактов не требуется. Это совпадает и с тем, как приложение
собирается в проде (esbuild/Next.js бандлят исходники через `customConditions`).

⚠️ Вместе с `references` придётся убрать и `rootDir` — исходники библиотек лежат вне него, и
включённые в программу файлы дают `TS6059: not under 'rootDir'`. Триггер именно `rootDir`;
`outDir` заставляет TypeScript вывести `rootDir` самостоятельно, поэтому уходит следом.
`declaration` при этом **оставить**: `@nx/esbuild` без него не резолвит entry point и таргет
`build` падает с `Could not resolve "apps/<app>/src/index.ts"`.

**Фикс:** после добавления/переименования публичного экспорта в библиотеке, у которой уже есть
локальный `dist/`, пересобрать декларации — `nx typecheck <lib>` (не `typecheck:tsgo`,
у него нет `--emitDeclarationOnly`). Проверить наличие `dist/` быстро: `ls libs/<name>/dist`.

### ⚠️ Тот же фикс на приложениях, наследующих `outDir`/`include` из общего пресета

Прогон того же фикса на шести Next.js/Electron-приложениях (`aboi`, `aira-web`,
`animatrona-landing`, `animatrona-tracker`, `animatrona`, `aprel8008`, 2026-08-07) вскрыл три
варианта побочных эффектов сверх `dashboard-agent` — там `rootDir`/`outDir` были заданы прямо в
`apps/<app>/tsconfig.json` и просто удалялись. У приложений на `../../tsconfig.next-app.json`
`outDir` унаследован из пресета и там не убрать без порчи 18 других приложений — нужен другой
обходной путь на уровне самого `apps/<app>/tsconfig.json`:

1. **`TS6059: not under rootDir` без собственного `rootDir` в файле.** `outDir` из пресета всё
   равно форсирует строгую проверку `rootDir`, даже если приложение его не переопределяло —
   TypeScript выводит `rootDir` из общего предка входных файлов программы.
   ~~Фикс — явный `"rootDir": "../.."` (корень репо) в `compilerOptions` приложения, не трогая
   пресет.~~ **Устарело (2026-08-07):** правило «`rootDir` не выносится в пресет, ни на что не
   влияет при `noEmit`» (см. `.claude/docs/tsconfig-presets.md`) оказалось неверным именно для
   этого случая — `TS6059` работает и при `noEmit: true`. Точечный `rootDir` был продублирован в
   16 `apps/*/tsconfig.json`, все на одинаковой глубине (`apps/<app>/tsconfig.json` → пресет в
   корне репо). Консолидировано в сам пресет: `"rootDir": "${configDir}/../.."` в
   `tsconfig.next-app.json` — `${configDir}` резолвится относительно наследующего конфига
   приложения, поэтому одна строка в пресете эквивалентна `"../.."` в каждом из 19 приложений на
   пресете. Проверено `typecheck:tsgo` на всех 19 (после `rm -rf libs/*/dist apps/*/dist` и
   `--skip-nx-cache`) + `build` на 3 репрезентативных (`aboi`, `driving-school`, `kami`) — падений
   от `rootDir` не найдено. `declaration`/`outDir` из пресета не мешают: `noEmit: true` там уже
   стоит, реального вывода файлов нет.
2. **`TS6307: File is not listed within the file list`** — когда путь-алиас на библиотеку
   раньше резолвился только через снятый `references`, а не через `include` (в отличие от
   остальных библиотек этого же приложения, уже включённых «смешанной моделью» через
   `../../libs/X/src/**/*.ts`). Фикс — добавить такой же glob для этой библиотеки в `include`,
   не полагаясь на то, что `paths` в `compilerOptions` сама протащит файл в программу.
3. **Взрыв на сотни посторонних ошибок компиляции `*.spec.ts(x)` библиотек**, если приложение
   уже использовало «смешанную модель» (`include: ["../../libs/X/src/**/*.ts"]`) до фикса.
   Раньше `*.spec.ts(x)`-файлы библиотек не заходили в программу приложения — их отсекал сам
   механизм `references` (компилировался только `tsconfig.lib.json`-таргет), а `include`-glob'ы
   приложения тем временем формально совпадали и с тестовыми файлами. Без `references` эта
   защита исчезает, и `*.spec.tsx` библиотек компилируются в контексте приложения — там нет
   тестового `tsconfig.spec.json` со своими типами (`@testing-library/jest-dom` и т.п.), отсюда
   `TS2339`/`TS2593`/`TS2304` пачками. Фикс — добавить `../../libs/**/*.spec.ts(x)` и
   `*.test.ts(x)` в `exclude` приложения, тем же паттерном, что уже обычно стоит для
   `src/**/*.spec.ts(x)` самого приложения.

Ни один из трёх пунктов не специфичен библиотеке — это общие следствия перехода с
project-references-модели на путь-алиасы, применимые к любому приложению со схожим пресетом.

## Несколько точек входа (`./server`, `./client`)

Библиотека может нести код под разные рантаймы: React-компоненты в `.` и Node-only код в
`./server` (образцы — `@letar/auth`, `@letar/pin-auth`, `@letar/image-upload`).

- Серверный код — только в `src/server/`, клиентский — в `src/client/` или `src/lib/`.
  На этом соглашении держатся правила `no-restricted-imports` в корневом `eslint.config.mjs`:
  они не пускают React/Chakra в `src/server/` и `@letar/*/server` — в клиентский код.
- Тег `type:*` в `project.json` описывает **точку входа по умолчанию** (`.`), а не всю
  библиотеку. `@nx/enforce-module-boundaries` подпути не различает вообще — для него
  `@letar/x` и `@letar/x/server` один узел графа.
- Каждый подпуть прописывается отдельной строкой в `paths` приложения-потребителя.

### ⚠️ Потребителю нужны `paths` и на **транзитивные** `@letar/*`, и на **все** их подпути

Приложение компилирует не `.d.ts` библиотеки, а её **исходники** (через `customConditions`).
Значит любой `@letar/*`-импорт, встречающийся внутри этих исходников, обязан резолвиться у
потребителя — даже если сам потребитель этот пакет не упоминает. Два следствия, оба всплыли
разом в Фазе 7.3 `@letar/forms` (2026-08-09):

1. **Новый внутренний слой ломает всех потребителей сразу.** Когда `@letar/forms` начал
   импортировать новый `@letar/forms-react`, 17 приложений получили `TS2307` (а где тип попал
   в сигнатуру — каскад `TS2322` вида «`{ name: string }` не совместим с `StringFieldProps`»,
   по которому причина совсем не читается). Лечится строкой `paths` в каждом потребителе.
2. **Неполный набор подпутей — мина замедленного действия.** Те же приложения держали 9
   подпутей `@letar/forms-core` из 15. Пока библиотека не импортировала недостающие — всё было
   зелёное; первое же использование `/uikit`, `/i18n`, `/address` во внутреннем слое положило
   всех. Поэтому прописывать **полный** набор из `exports` библиотеки, а не только тот, что
   нужен сегодня.

⛔ `paths` в `tsconfig.base.json` эту работу не сократят: `paths` наследуемого конфига
**перекрываются** целиком, а не мержатся — приложение со своим блоком `paths` базовый просто не
увидит.

Два побочных момента того же перехода:

- **Симлинк в `node_modules` создаёт `bun install`**, и лежит он в `<пакете>/node_modules/@letar/`,
  а не в корневом (корневого `node_modules/@letar` в этом репо нет вовсе). Добавил
  workspace-зависимость в `package.json` библиотеки — запусти `bun install`, иначе потребители
  без своих `paths` (например `dashboard`) не отрезолвят пакет.
- **Приложения на «смешанной модели» `include`** (`../../libs/X/src/**/*.ts` вместо `references`)
  требуют ещё и glob на новую библиотеку — иначе `TS6307 File is not listed within the file
  list`. Таких в репо два: `animatrona`, `label-printer-desktop`.

Подробнее (включая ловушку с `files`-глобами в ESLint 10):
[lib-entry-points.md](/.claude/docs/lib-entry-points.md).

## Правила

- Каждая библиотека должна иметь README.md с API документацией
- Используй `composite: true` в tsconfig.json
- Экспортируй всё через `src/index.ts`
- ⛔ Не полагайся на `nx sync` — в этом репо он отключён и references не обновит (см.
  «Подключение к приложению» выше)
