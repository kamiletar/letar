# Тайм-трекер studio — когда стартовать, переключать и останавливать

> Правило без `paths:` — грузится в каждую сессию, поэтому здесь только порядок действий.
> Разборы четырёх способов потерять время (и почему хуки их не ловят) —
> [time-tracker-drift-incidents](/.claude/docs/time-tracker-drift-incidents.md).

Инструменты сервера `letar`: `time_start`, `time_switch`, `time_stop`, `time_discard`,
`time_pause`/`time_resume`, `time_status`, `time_note`, `time_log`, `time_stage_close`.

## Главное правило

⛔ **НЕ останавливай таймер в конце каждого ответа.** Одна работа = одна запись, а не десяток
огрызков по три минуты. `Stop` в Claude Code срабатывает после каждой реплики агента, а не в
конце сессии — это не сигнал завершения работы.

Останавливай **только** в трёх случаях:

1. Пользователь прямо просит («останови таймер», «стоп», «на сегодня хватит»);
2. Команда `/end-session`;
3. Начинается **другая по смыслу** работа — тогда не `time_stop`, а `time_switch`.

Между репликами таймер продолжает идти. Это нормально: работа не заканчивается оттого, что ты
закончил абзац.

## Начало работы

```
time_start({ app: "<проект>", description: "<что делаешь, языком клиента>" })
```

⚠️ `description` видит заказчик. Только предмет работы по этому проекту: никаких других
клиентов, чужих проектов и внутренней кухни.

## Смена вида работы

```
time_switch({ app: "<проект>", description: "<новая задача>" })
```

Переключать при смене **предмета** работы, а не на каждом шаге внутри одной задачи.

⚠️ **«Другой по смыслу» = другой пункт плана, а не только другая фаза или другое приложение.**
Пользователь сформулировал новую задачу — переключайся **в этот момент**, даже если её ещё
предстоит уточнять вопросами, даже если работа идёт внутри того же `apps/<app>/`. Обнаружил,
что прежняя задача не нужна (уже сделана, отменена, не та) — это тоже смена предмета.

Переключить второй раз, когда формулировка уточнится, дешевле, чем не переключить вовсе. Хук на
`Stop` ловит только межпроектный случай (сравнивает число задетых `apps/<x>/` с числом
`time_switch`) — смену задачи внутри одного приложения он не видит по построению.

## ⛔ `time_status` обязателен там, где сервер мог закрыть запись сам

Сервер закрывает запись по простою (`autoClosedIdle`) молча: heartbeat-хук продлевает **идущую**
запись, а закрытую не воскрешает и не предупреждает. Два окна, где это уже происходило:

- **Возобновление после сжатия/разрыва контекста.** «Continue as if the break never happened» —
  про нить задачи, не про пропуск проверки таймера. `time_status` **первым действием**, до
  любого Bash/Read/Edit. Не идёт — сразу `time_start` с прежним описанием, не дожидаясь, пока
  пользователь заметит.
- **Длинная работа с редкими инструментами** — серия `nx typecheck`/`lint`/`test`, ожидание
  `AskUserQuestion`, делегирование субагенту. Периодически вызывай `time_status`: вызов дешёвый
  и заодно перезапускает таймер при `autoClosedIdle`.

Напоминание от пользователя — признак, что правило нарушено, а не способ его соблюдать.

## Пауза и небиллируемое время

**Пауза.** Пользователь пишет «пауза» → `time_pause`. Запись остаётся открытой, время не капает.
Как только он снова начинает взаимодействовать → `time_resume`, **не дожидаясь отдельной
просьбы** и не сообщая об этом отдельной репликой. Оба вызова идемпотентны.

**`time_discard`** — стоп с пометкой «не для счёта» (`billable: false`, `nonBillReason:
INTERNAL`): копался из любопытства, пробовал подход, который не пойдёт в работу.

**Что не биллится вообще:** работа над инфраструктурой студии (хуки, MCP-серверы, монорепо) и
некоммерческие/личные проекты. Либо не запускать таймер, либо закрывать через `time_discard` —
биллинг считается по флагу записи, а не по тексту `description`.

**Небиллируемое время задним числом** — `time_log({ …, billable: false })` (причина —
`nonBillReason`: `GIFT`/`REWORK`/`BARTER`/`INTERNAL`, по умолчанию `INTERNAL`; без
`billable: false` причина отвергается). `time_discard` для этого не годится — он закрывает только
идущий таймер.

## Запись задним числом (`time_log`)

Знаешь реальное время события (созвон, встреча) — передавай `startedAt`/`endedAt` (ISO-8601,
без зоны = МСК), а не `minutes`: один `minutes` ставит запись на `[сейчас − minutes, сейчас]` и
перекрывает идущий таймер. Строка `⚠️` в ответе — пересечение с другой записью: проверь, не
учтено ли время дважды. Подробнее —
[mcp-servers § time_log](/.claude/docs/mcp-servers.md#time-log-interval).

⛔ **Встреча, которую ты разбираешь по записи, — это оплачиваемое время само по себе, отдельно
от твоей работы над разбором.** Пользователь прислал запись созвона/встречи (`.webm`, `.aac`,
Телемост и т.п.) — **первым же действием после `time_start`**, до расшифровки и разбора, внеси
саму встречу:

```
time_log({ app: "<проект>", kind: "MEETING", description: "Созвон: <тема языком клиента>",
           startedAt: "<начало встречи>", endedAt: "<конец встречи>" })
```

Время берётся из **имени файла** (`Встреча в Телемосте 24.09.26 20-02-02` → старт 20:02:02 МСК) и
**длительности записи** (`ffprobe`), а не из твоего таймера. Конец — старт + длительность.
Таймер разбора и запись встречи — две независимые записи: первая считает твой труд, вторая —
время заказчика и команды на созвоне. Пропустишь — встреча нигде не отразится, и это заметят
только на сверке счёта (2026-09-24: `/domwellbes` разобрал 34-минутный созвон с Денисом и
внёс его лишь после вопроса владельца).

Проект неочевиден по имени файла — определи по содержанию после первых минут расшифровки, но
запись создай сразу с рабочим предположением и поправь, если ошибся; отложенная запись — это
забытая запись.

## Этапы (`ProjectStage`)

Работа укладывается в отдельную именованную задачу проекта (пункт плана, milestone, кусок,
который имеет смысл показать клиенту строкой) — передавай её название в `stage`:

```
time_switch({ app: "<app>", description: "...", stage: "<название этапа>" })
```

Studio заведёт `ProjectStage` с этим названием или найдёт уже открытый. Сделано —
`time_stage_close({ app: "<app>", stage: "<то же название>" })`.

⚠️ **Название должно быть дословно одинаковым** во всех вызовах — поиск открытого этапа идёт по
точному совпадению `title`, опечатка заведёт второй несвязанный этап. Для рутинных действий
(правка опечатки, ответ на вопрос) `stage` не заводить.
