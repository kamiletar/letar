# Тайм-трекер studio — когда стартовать, переключать и останавливать

Инструменты: `studio-time-mcp` (`time_start`, `time_switch`, `time_stop`, `time_pause`,
`time_status`, `time_note`, `time_log`).

## Главное правило

⛔ **НЕ останавливай таймер в конце каждого ответа.** Одна работа = одна запись, а не десяток
огрызков по три минуты.

Останавливай **только** в трёх случаях:

1. Пользователь прямо просит («останови таймер», «стоп», «на сегодня хватит»);
2. Команда `/end-session`;
3. Начинается **другая по смыслу** работа — тогда не `time_stop`, а `time_switch` с новым
   описанием.

Во всех остальных случаях таймер продолжает идти между репликами. Это нормально: работа над
задачей не заканчивается оттого, что ты закончил абзац.

## Почему это отдельное правило

Хук `time-stop-check.js` висит на событии `Stop`, а `Stop` в Claude Code срабатывает **в конце
каждого ответа агента**, а не при завершении сессии. Первая версия хука блокировала Stop при живом
таймере с текстом «останови перед завершением сессии» — и агент честно останавливал таймер после
каждой реплики (найдено 2026-07-30).

Блокировка снята. Забытый таймер ловится не приставанием, а двумя механизмами:

- `time-heartbeat.js` на `PostToolUse: *` обновляет `lastSeenAt` при каждом вызове инструмента;
- сервер закрывает запись по простою (`autoClosedIdle`).

## Начало работы

```
time_start({ app: "<проект>", description: "<что делаешь, языком клиента>" })
```

⚠️ `description` видит заказчик. Только предмет работы по этому проекту: никаких других клиентов,
чужих проектов и внутренней кухни.

## Смена вида работы

```
time_switch({ app: "<проект>", description: "<новая задача>" })
```

Переключать при смене **предмета** работы (исследование → написание кода → деплой), а не при
каждом шаге внутри одной задачи.

⚠️ Смена проекта без `time_switch` — время уйдёт не туда. Хук на `Stop` ловит это эвристикой:
сравнивает число задетых `apps/<x>/` с числом вызовов `time_switch`/`time_start`.

### ⚠️ «Другая по смыслу работа» — это смена пункта плана, а не только смена фазы

Прецедент 2026-08-10 (domwellbes): таймер переключили на «форма заявки + согласие», задача
оказалась уже сделана в коде — доки просто отстали. Дальше без единого `time_switch` два часа
делалась совсем другая задача (генерация и привязка фото материалов: ChatGPT → скачивание →
сопоставление SKU → сид). Заметил не агент, а пользователь.

Правило: если следующий шаг — **другой пункт плана/бэклога**, а не продолжение того же
изменения, `time_switch` вызывается **в момент, когда становится понятно, что делаешь именно
это** — не после того, как задача найдена и подтверждена, не «когда будет пауза», и не по
напоминанию пользователя. Обнаружил, что предыдущая задача не нужна (уже сделана, отменена,
не та) → это тоже смена предмета работы, переключайся сразу, даже если новая задача ещё не
сформулирована окончательно (переключить ещё раз, когда сформулируется, дешевле, чем не
переключить вовсе).

### ⚠️ Смена предмета работы внутри ОДНОГО приложения — хук её не видит

Прецедент 2026-08-18 (aboi): P9.1 (цена за м²) была закрыта и закоммичена. Пользователь тут же
предложил новую фичу — реестр бумаги. Работа над ней (уточняющие вопросы, exploration,
Plan Mode) шла без `time_switch` до тех пор, пока пользователь не напомнил.

Прецедент 2026-08-10 ловился эвристикой хука («число `apps/<x>/` ≠ число `time_switch`»), потому
что задевал **разные** приложения. Этот — нет: всё время работы внутри одного `apps/aboi/`, хук
по определению не может отличить «продолжаю P9.1» от «начал реестр бумаги» — оба выглядят как
«коммиты в aboi». Единственная защита — то же правило выше («другой пункт плана → переключайся
в момент, когда стало понятно»), применённое явно и к внутриприкладным пивотам, не только
межпроектным. Триггер: пользователь сформулировал новую задачу/фичу (даже если её ещё предстоит
уточнить вопросами) — это уже смена предмета, `time_switch` вызывается тогда, а не после того,
как план для неё готов.

## Пауза

Владелец пишет «пауза» → `time_pause`. Запись остаётся открытой, время перестаёт капать.

Как только он снова начинает взаимодействовать → `time_resume`, **не дожидаясь отдельной просьбы**.
Отдельно сообщать «возобновил» не нужно, достаточно продолжить работу.

Оба вызова идемпотентны: повторная пауза или возобновление не в том состоянии ничего не ломают.

## `time_discard` — стоп с пометкой «не для счёта»

Останавливает запись и помечает её небиллируемой (`billable: false`,
`nonBillReason: INTERNAL`). Для случаев, когда копался из любопытства или пробовал подход, который
не пойдёт в работу.

⚠️ **До 2026-07-30 этот выключатель назывался `time_pause`** и вводил в заблуждение — он ничего не
приостанавливал. Имя освобождено под настоящую паузу. Если где-то встретишь `time_pause` в старом
смысле «останови и не считай» — это `time_discard`.

## Что не биллится

Работа над самой инфраструктурой студии (хуки, MCP-серверы, монорепо) — это не время клиента.
Либо не запускать таймер вовсе, либо закрывать через `time_discard`.
