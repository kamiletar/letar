# Статус монорепо

Прочитай **оба** файла — корневой `PLAN.md` И `PLAN-INFRA.md` (авторизация/верификация и
инфраструктурные треки — это два раздельных плана, `PLAN.md` только ссылается на `PLAN-INFRA.md`
через раздел «Инфраструктурные треки», сам его не пересказывает; не пропускай второй файл) —
и выведи краткий отчёт по структуре:

## Учёт времени

Если это начало рабочей сессии (а не разовая проверка статуса) — стартуй таймер:
`time_start({ app: "letar", description: "статус монорепо и постановка задачи" })`. Когда
направление работы прояснится (выбрана конкретная задача/приложение) — обнови через
`time_switch` на это приложение. Правила переключения и остановки — `.claude/rules/time-tracking.md`.

## 1. Текущий статус

Вырви шапку `PLAN.md` (первые ~15 строк): последняя выполненная сессия, указатель «Следующий
старт», активные риски 🔴.

## 3. Здоровье зависимостей (§25 PLAN-INFRA.md)

1. Выполни `git log -1 --format=%cI -- bun.lock` — дата последнего изменения lock-файла.
2. Выполни `git log -5 --format='%cI %h %s' -- bun.lock` — определи, был ли последний коммит
   реальным обновлением зависимостей или lock задело попутно (например, бампом submodule). Если
   попутно — возьми ближайший коммит, похожий на настоящее обновление, и отметь расхождение строкой.
3. Посчитай возраст в днях от даты из шага 1 и выведи строку: `Зависимости: последнее обновление
N дней назад (<коммит>, <дата>)`.
4. Условная логика по возрасту N: ≤ 7 — «в норме», ничего не предлагать; 7 < N ≤ 14 — 🟡 «пора
   запланировать проверку»; N > 14 — 🔴 баннер, предложи `bun scripts/deps-scan.ts`, затем
   `/infra:deps-analyze`. **Спроси, запускать ли сканер. Не запускай без ответа.**
5. Если файл `.claude/state/deps-last-scan.json` существует — прочитай и добавь строку с датой
   скана и счётчиками (`riskScore`, `outdatedCount`, `vulnCount`); если файла нет — выведи «скан
   ни разу не запускался».

## 4. Следующий шаг

Конкретная задача + приложение + скоуп работы (из `PLAN.md`).

## 5. Открытые вопросы / Блокеры

Список из §9 (открытые развилки) и §10 (риски 🔴) `PLAN.md`.

## 6. Инфраструктурные треки (`PLAN-INFRA.md`, §15–§39)

Пройди по всем `## §NN` секциям файла и раздели на две группы:

- **Открытые** (нет `✅ ЗАКРЫТО` в заголовке секции или заголовок помечен `🆕`) — краткая строка
  на каждый: номер, суть, статус одной фразой.
- **Недавно закрытые** — только заголовки, без деталей.

Отдельно вынеси наверх этой группы то, что реально активно прямо сейчас (по журналу/памяти) —
например тираж e2e-гейта (§18.7) или `.env.staging.enc` (§18.8), если по ним есть свежие пометки.

## 7. Приватные детали — не в этом отчёте

Корневой `PLAN.md` — публичный. С 2026-07-28 (§27) детали конкретных коммерческих приложений
(aboi, driving-school, dsperevod и т.п.) и сквозной журнал сессий вынесены из него:

- **По одному приложению** → `apps/<app>/PLAN.md` / `PLAN_COMPLETED.md` внутри приватного submodule
  этого приложения.
- **Сквозные записи** (несколько приложений сразу, rollout/деплой-кампании) → приватный репозиторий
  `.claude/private/PLAN-JOURNAL.md` (submodule `letar-private-docs`).
- **Реквизиты 152-ФЗ/РКН, домены, привязка к ИП** → `.claude/private/COMPLIANCE.md`.

Если нужен статус конкретного коммерческого приложения или деталь конкретной сессии деплоя — читай
эти файлы отдельно, этот отчёт их не пересказывает. Правило, что можно/нельзя писать в публичный
`PLAN.md` — `.claude/rules/public-repo-hygiene.md`.
