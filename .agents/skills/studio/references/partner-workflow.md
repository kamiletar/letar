# Работа с партнёрской программой Studio

Читай при проектировании или изменении подключения партнёров, ссылок, начислений,
оферты и выплат. Для других задач Studio этот файл не нужен.

## Обязательные источники и действия

1. Сначала прочитай [устройство партнёрки](../../../../apps/studio/docs/partner-program.md):
   согласованную основу, нужный раздел и очередь в §9. Для вывода и договоров дополнительно
   прочитай [исследование выплат](../../../../apps/studio/docs/partner-payout-options.md).
   Проверь связанные задачи в `apps/studio/tasks/`, включая завершённую ST-064 и открытые
   решения ST-069. Статусы задач и документы могли измениться после этой сессии.
2. Отличай регистрацию партнёра, право на начисления и готовность к выплате. Не переноси
   проверку налогового статуса в онбординг и не добавляй ручное одобрение без нового решения
   владельца. Срок вознаграждения считай от события, указанного в спецификации, а не от
   регистрации партнёра, перехода по ссылке или первой выплаты ему.
3. В исследовании банка связывай каждое подтверждение с конкретным продуктом: способ
   перевода, полномочия на чек, API, подключение и тариф. Эквайринг, обычный исходящий
   перевод и расчёты с самозанятыми не подтверждают возможности друг друга. Для новой
   рекомендации проверь актуальные официальные источники; дата старого исследования
   не делает цену или доступность актуальной сегодня.
4. При фиксации решений обновляй затронутые задачи и спецификацию. В Studio `PLAN.md`,
   `PLAN_COMPLETED.md`, `PLAN_TESTING.md` заморожены. В `REFERRAL_PLAN.md` ниже актуальной
   вводной сохранена история реализации: она не отменяет поздние решения владельца.
   Открытые вопросы записывай в соответствующую существующую задачу, избегай дубликатов.

## Рекомендованный порядок исследования выплат

По умолчанию продолжай сравнение имеющихся у владельца банков из исследования выплат.
Сначала ищи профильный сервис с проверкой статуса и чеком, затем проверяй канал перевода,
подключение исполнителя, получение документов и обработку неизвестного исхода.
Выбор этого порядка вызван вопросом владельца: как получать чек без ручного ожидания
действий получателя. Наличие API у банка само по себе этот вопрос не закрывает.

Итог сравнения — «подтверждено / не подтверждено / что проверить до интеграции» с датой
и источниками. Не превращай исследованный сервис в уже подключённую функцию Studio.
Перед реализацией сверяй конкретный договорный и технический маршрут с текущими задачами.

## Типичные ошибки и подводные камни

- **Вернуть заявку, одобрение или ИНН в форму входа.** Владелец отменил эти барьеры:
  действующий путь и проверка статуса при выводе описаны в спецификации. Изменение требует
  нового решения, а не восстановления старого исторического плана.
- **Вернуть пожизненный процент.** Владелец ограничил его годом с первой оплаты клиента;
  повторные заказы и первая выплата партнёру не начинают новый срок. Границы и legacy — в §4.1.
- **Объявить любые услуги привлечения запрещёнными для НПД либо просто переименовать
  агентский договор.** В сессии найден путь через реальные услуги продвижения/привлечения,
  но конкретная оферта и фактические обязанности остаются предметом ST-065. Выплаты обычным
  физлицам с НДФЛ/взносами владелец исключил; не возвращай их как запасной маршрут.
- **Сложить возможности двух продуктов Точки.** В исследовании от 26.10.2026 авточек найден
  у платформы, СБП — отдельно в Cyclops; совместимость не подтверждена. Связка СБП/чека
  описана у Альфы, но её подключение и тариф для студии также не подтверждены. Перепроверяй
  эти сведения перед новой рекомендацией, не копируй тариф платформы на другое API.
- **Просить чек заранее или повторять перевод, если чек не получен.** Целевой маршрут —
  профильный банковский сервис с полномочием на чек. Подтверждение денег и документа
  учитываются отдельно; неизвестный исход сначала сверяется, повторная выплата его не лечит.
- **Принять ошибку вложенного входа за запрет политики.** В ST-089 поле
  `originalCommissionId` убрано из `refunds.create` под уже выбранной комиссией.
  Корректный вход сначала успешно записан базовым ORM, затем отклонён PolicyPlugin.
  Один `rejects.toThrow()` без такого контроля не доказывает запрет доступа.
- **Принять пустой schema diff за проверку CHECK.** В ST-089 знаки сумм и пустой ID
  проверены реальными INSERT-тестами PostgreSQL, отдельно от сравнения схемы.
- **Назвать таблицу готовым возвратом.** Чистый расчёт и защищённое хранилище не
  подтверждают запись под блокировками, учёт в последующих начислениях/выплатах или
  готовность банка. Проверяй каждый путь в текущем коде и задачах.
- **Проверять create на занятом ID.** Отказ уникальности может скрыть разрешённую
  запись. Сначала тем же входом успешно создай запись базовым ORM, освободи ID,
  затем проверь отказ PolicyPlugin; для nested create нужен собственный контроль.
- **Создать работу без её выставления.** В `advance-refund-service.integration.test.ts`
  `fixture.work(hours)` возвращает команду. Для проверки нехватки нужно выполнить
  `await (await f.work(hours))()`: один TimeEntry ещё не расходует номинал.
- **Пропустить денежный возврат без уменьшения аванса.** При резервировании работ
  сравниваются ID обоих журналов исходного счёта, а не только имеющиеся AdvanceRefund.
- **Положиться на permissive Date-парсер.** Невозможная дата должна отклоняться,
  а не переходить на следующий месяц. Для формы ST-094 время МСК проверено при
  America/New_York на устройстве; ввод и вывод не зависят от его часового пояса.

## Возвраты и проверка журнала

Читай при продолжении ST-023, изменении журнала возвратов или проверке его миграции/политик.

### Обязательные проверки

- Перед продолжением сверяй §6 спецификации, ST-023, ST-069, завершённые ST-088–094
  и текущий Git. Срез 0.115.0 (`22951d4`): учёт возвратов в последующих начислениях,
  серверный сервис REGULAR/зачисленного ADVANCE, уменьшение номинала, сводка долга
  и форма/история в карточке счёта готовы локально. Выплаты/распределения, банк
  возвратов, импорт пропусков и исправление старых привязок остаются отдельными этапами.
- Для политики журнала проверяй OWNER/CLIENT/AGENT/анонимного, прямой CRUD,
  вложенные create/update/delete и чтение через relation. Политика родителя не
  заменяет проверку дочерней записи. Проверенный образец:
  `apps/studio/src/lib/partner-refund-ledger.integration.test.ts`.
- Миграцию проверяй в отдельной локальной БД: перед изменениями проверь адрес и имя
  базы. Не запускай `db:push`/`migrate deploy` в рабочей БД ради этих тестов.
  В этой сессии использована только `studio_partner_20261026` на localhost.
  Отдельно проверь уникальность события, FK, SQL CHECK, rollback и конкурентный дубль.
- Принятые решения о номинале и зачёте долга уже отмечены в ST-069 и §6. Не задавай
  эти вопросы повторно и не возвращай им статус открытых. Формулу/границы бери из §6
  и `advance-refund.ts`, не восстанавливай из денежной суммы без исходного источника.
- Запись через `recordPartnerRefundAction` требует OWNER из сессии и повторной
  проверки роли по БД. Расчёт комиссии/номинала клиент не задаёт. Под блокировками
  Client → PartnerCustomer → Invoice → Project (ADVANCE) → Agent сохраняются оба
  журнала и остаток. Для будущих выплат общий Agent-lock всех writers ещё gate ST-006.

### Повтор ручного возврата

Форма ST-094 фиксирует уже состоявшийся перевод, не отправляет деньги. Исходная
оплата, номер возврата из выписки, сумма и время МСК обязательны; подтверждение —
явное. Ключ `manual:<номер>` стабилен. При неизвестном исходе проверь историю и
повтори те же данные с тем же номером. Другое содержание — сверка, новый номер —
новое событие. Будущий банковский импорт должен сверяться с ручными записями:
другой namespace сам по себе не предотвращает повтор того же перевода.

### Проверенные команды и границы

Из корня монорепо с глобальным `nx`, при уже настроенном окружении отдельной
локальной БД и маркере. Для нового изменения схемы сначала генерация клиента
и проверка нужной миграции только в этой БД:

```powershell
$env:NX_ISOLATE_PLUGINS='false'
$env:NX_DAEMON='false'
nx test studio --output-style=static -- partner-refund.action.test.ts partner-refund-service.integration.test.ts advance-refund-service.integration.test.ts partner-refund.test.ts advance-refund.test.ts --run
```

Эти команды проверены с окружением из игнорируемого
`.claude/artifacts/studio-partner/check.mjs`: он проверяет localhost, выбирает
отдельную БД и задаёт `STUDIO_PARTNER_ISOLATED_DB=studio_partner_20261026`.
Это локальный артефакт сессии, его наличие в другом checkout не гарантировано.
Без отдельной БД/маркера интеграционные тесты пропускаются: проверь фактический
счётчик выполненных тестов, прежде чем сообщать о проверке PostgreSQL.
На `22951d4` выполнено 146 тестов/5 файлов, включая 50 PostgreSQL. На `05eb999`
отдельный прогон: 283 теста/9 файлов, включая 114 PostgreSQL. Эти счётчики не складывать
как уникальные тесты. Миграция `20261027153000_advance_refund` дала пустой schema diff,
CHECK/FK/rollback проверены отдельно в PostgreSQL.

В изолированной БД `migrate deploy` остановился на старой уже существующей колонке
из-за неполной истории миграций. ST-093 проверили применением конкретного нового SQL
и отметкой applied с последующим schema diff. Это разовый факт тестовой базы, а не
универсальная инструкция исправления миграций: не повторяй полный deploy вслепую
и не переноси обход в рабочую/production-БД.

Рабочая/production-БД, живые банковские переводы, полный staging gate, исторический
backfill и публикация этими прогонами не проверялись.
