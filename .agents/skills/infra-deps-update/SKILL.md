# Обновление зависимостей

По умолчанию обновляй существующие semver-диапазоны. Major-миграции требуют отдельной
проверки breaking changes; `bun update --latest` игнорирует диапазоны, а не ограничивается minor.

## Исходное состояние

Проверь Git и резервации по правилам репозитория. Веди задачу проекта, логи сохраняй
в `.claude/artifacts/`; чужие изменения не включай в коммит.
Прочитай текущие `package.json`, `scripts/intentional-pins.json` и `patchedDependencies`.
Сними `bun outdated`, `bun audit` и `bun scripts/check-all.mjs --group=deps`.

## Установка и целостность

```bash
bun update
bun install
bun scripts/check-all.mjs --group=deps
```

Сначала устраняй совместимые security-находки. Прочитай вывод установки, сравни audit,
peer-отчёт и diff lockfile с исходным состоянием. `check-peer-deps.mjs` всегда возвращает 0:
это отчёт, а не gate; Bun install может вообще не предупредить о peer-конфликте.
Pre-commit повторяет часть проверок. Зелёный CI не покрывает отсутствующие приватные submodules.

### Пины

- Сверяй `unpinWhen` до снятия точного пина. Условие выполнено — меняй диапазон и удаляй
  запись реестра тем же коммитом. Иначе сохраняй пин, даже если outdated предлагает новый.
- Новый пин сопровождай `reason`, `doc`, `unpinWhen` в реестре. Записи `unexplained`
  можно возвращать на диапазон после проверки потребителей.
- При регрессии семейства верни согласованные версии и проверь копии в lockfile.
  Точный корневой пин не всегда удерживает workspace-потребителей с caret-диапазоном;
  при необходимости используй overrides/resolutions и зарегистрируй причину.
- Не подменяй несовместимую ветку API глобальным override ради пустого audit.
  Нужную миграцию и остаточные уязвимости сохрани отдельной задачей.

Контекст: [root-pin-peer-drift](/.claude/docs/root-pin-peer-drift.md).

### Патчи

Перед переносом патча проверь свежий upstream: маркер дефекта, используемые варианты
поставки (например ESM/CJS) и короткое репро. Исправлено — удали старый patch-файл
и запись `patchedDependencies`, обнови lockfile. Не исправлено — пересоздай патч
на точную новую версию через `bun patch` / `bun patch --commit`, удали старый файл.

После изменения: `bun scripts/check-all.mjs --only=patched-deps`.
Для нового патча добавь upstream-маркер в `scripts/check-patched-deps.mjs`.
Успешный install не доказывает применение патча: Bun уже молча терял его при расхождении версий.
При таком обновлении прочитай [references/verification.md](references/verification.md#патчи).

## Поведение и безопасная сборка

При обновлении ORM или policy-plugin проверь значимые разрешённые и запрещённые операции
и неизменность строки после отказа. Типизация и обычный CRUD не доказывают сохранение прав.
При обходе доступа останови продвижение кандидата, сравни версии на одинаковом
изолированном сценарии и верни безопасную версию с условием снятия пина.
Для этого шага прочитай [references/verification.md](references/verification.md#права-orm).

Запусти typecheck, lint и тесты через Nx в объёме изменения. Перед широким build получи граф:

```bash
nx run-many -t build --graph=.claude/artifacts/deps-build-graph.json
```

Проверь `tasks.tasks`, пути `tasks.dependencies` и команды сомнительных prerequisites.
Исключение проекта не исключает транзитивно востребованный `db:template`.
Шаг сброса пользовательской dev-БД ради шаблона изолируй либо исключи зависящие
от него build-targets; затем пересоздай и проверь итоговый граф.
Разбор: [транзитивный build и dev-БД](/.claude/docs/nx-build-transitive-dev-db-reset.md).

После проверки графа запускай build с выбранными `--projects`/`--exclude`.
Проверь запуск представительного собранного приложения по HTTP и останови свой временный сервер.

### Прерванный прогон

Сохрани граф, stdout/stderr и доступные статусы. Раздели успешные, неуспешные и задачи
без подтверждённого результата. Строка начала задачи и отсутствие итоговой сводки не доказывают успех.
Перед повтором проверь, не работает ли прежний процесс.

Выбери неуспешные и непроверенные build-проекты по исходному графу, учти prerequisites,
получи и проверь граф повтора. Успешные проекты повторяй при новых изменениях или
недостаточном доказательстве успеха. Своди результаты по уникальным target IDs,
не складывай счётчики перекрывающихся прогонов.
Для продолжения и диагностики среды прочитай
[references/verification.md](references/verification.md#повторы-и-среда).

## Типичные ошибки и подводные камни

- Minor ORM может нарушить права: в LT-086 сравнение 3.9.8/3.10.3 обнаружило реальный обход.
  Защита и условия снятия пинов — LT-087.
- Не переноси патч механически: Chakra 3.38.0 уже исправил порядок ключей memo.
- Общий `theme:typegen` перезаписывает одну копию Chakra. `run-many --parallel=1` не гарантирует
  пару генерация+проверка; проверенный повтор — отдельные последовательные команды по приложениям.
- Не отключай `NX_ISOLATE_PLUGINS` как постоянный рецепт: это ломало относительный next-intl config.
- Не применяй db:push ради исправления отсутствующей колонки в тестовом dependency-прогоне.
- Успешный отдельный повтор flaky-теста не превращает общий gate в зелёный.
- Проверяй конкретный отсутствующий бинарник Electron; не разрешай все lifecycle scripts подряд.

## Завершение

Обнови версию/CHANGELOG и задачу по правилам проекта, закоммить собственные файлы.
Отчёт должен содержать исключения, audit до/после, новые peer-конфликты, охват проверок,
отдельные повторы и непроверенные части. Не объявляй зелёный gate при остатках;
сохрани продолжение в задачах и оставь исходную на review, если её приёмка не выполнена.
