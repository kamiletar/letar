### Предыстория — не новая идея, а продолжение уже открытого вопроса (из §80, заведена 2026-08-14)

- **§65 первым назвал вынос сборки «следующим кандидатом»** после того, как своп на s2 был введён
  как страховка от OOM, а не решение конкуренции за память: «Приложений на s2 становится больше,
  базовые 7 Gi растут вместе с ними, а пик сборки от этого не уменьшается» (на сессию §65,
  2026-08-10, `S2_APPS` — уже 23 приложения). Та же сессия зафиксировала и дисковую сторону:
  `df -h /` на s2 — 149G из 174G (86%) уже тогда.
- **§17 (пилот Kamal) держит открытым тот же вопрос доставки образа** (GHCR vs self-hosted
  registry vs `kamal build push` + `deploy --skip-build`) — решать один раз на оба трека, не
  дважды; учтено в разделе «Доставка образа: registry на s3» ниже.
- **Технически сборка была жёстко привязана к серверу деплоя** ещё до всякого плана:
  `deploy-affected.sh` определяет `SERVER_NAME` по hostname и на этой же машине выполняет
  `docker build` — для всех приложений `S2_APPS` это происходило прямо на s2, рядом с их же живыми
  контейнерами. Разрез конвейера (см. «Разрез конвейера: где проходит граница» ниже) устраняет
  именно эту привязку.

**Проблема:** s2 (прод) кончился местом на диске — сборка (`bun install`, `nx build`,
`nx typecheck:tsgo`, `docker build`) идёт прямо на нём, значит там же живут `node_modules`, bun
cache, `.next` cache, Nx cache для всего монорепо. Разбор конкретного инцидента с местом —
вне скоупа этой секции (занимается deploy-agent-dev самостоятельно).

**Решение (согласовано с владельцем 2026-09-06):** перенести всю сборку на s3, оставить s2
только раскладку готовых образов. Механика:

1. **Remote BuildKit builder.** `docker buildx create --name s3builder --driver remote
   ssh://deploy@s3.letar.best` (или `docker-container` driver поверх SSH-контекста) — сборка
   физически идёт на s3, вывод стримится обратно.
2. **Registry.** Нужен self-hosted `registry:2` (за Traefik, с базовой аутентификацией — по
   аналогии с уже существующей SOPS/age-дисциплиной) — буилдер пушит образ по тегу коммита,
   `deploy-affected.sh` на s2 делает `pull` по тому же тегу.
3. **Прод-БД во время сборки (пререндер).** Часть страниц использует `getStaticProps`/
   `generateStaticParams` с прямым запросом к прод-БД на этапе `next build`. Раз сборка теперь
   физически на s3 — узкое firewall-правило s3→s2 на порт Postgres, **отдельный read-only**
   пользователь БД для сборки (не рантайм-креденшл), по аналогии с `postgres-*-prod` MCP.
4. **`deploy-affected.sh`:** шаг `docker build`/`nx build`/`nx typecheck:tsgo` заменяется на
   диспетч на s3-буилдер (`docker buildx build --builder s3builder --push`); на s2 остаётся
   только `docker compose pull && docker compose up -d` + применение миграций внутри уже
   пришедшего контейнера (`docker compose run --rm app npx prisma migrate deploy` — не требует
   node/bun на хосте, Prisma CLI уже внутри образа).
5. **`nx affected`** (расчёт списка приложений под пересборку) тоже логично считать на s3, а не
   на s2 — иначе `node_modules` на s2 всё равно понадобится ради графа Nx.
6. **Итог для s2:** `node_modules`/`.bun`/Nx-кэш убираются с хоста полностью — остаётся только
   git-чекаут ради `docker-compose.production.yml`, `.env.docker.enc` и файлов миграций, плюс
   уже готовые Docker-образы (это и сейчас так, новой нагрузки не добавляет).

**Взаимодействие с §19.1 (Трек 1/1b — typecheck-гейт в деплое):** после переезда сборки на s3
typecheck для staging и production физически будет выполняться на одной и той же машине — логика
Трека 1b (пропуск typecheck на проде для `HARD_GATED_APPS`, раз staging того же коммита уже
прошёл) не меняется концептуально, но теперь обе стадии буквально соседствуют на s3, а не
разнесены по разным серверам — реализацию `deploy-affected.sh` нужно будет свести с этим планом,
а не делать independently.

**Не начато. Аудит выполнен 2026-09-06 (см. ниже) — план в этой редакции к реализации не принят.** ⚠️ Перед реализацией — план ниже составлен
одной сессией с ходу (первый набросок по запросу владельца, не проверен второй парой глаз) и
может содержать недочёты, которые не видны без повторного прохода. Обязательный шаг **до** любого
кода: свежий аудит этого плана целиком — перепроверить каждый пункт 1–6 выше на предмет
пропущенных ограничений/рисков (сеть между s2/s3, авторизация registry, что именно ломается при
недоступности s3 в момент деплоя прод, откат при неудачной сборке на буилдере, совместимость с
уже существующим hard e2e-гейтом §18.7/§19.1, приватные submodule в билд-контексте буилдера) и
только затем — при необходимости — выработать более удачное решение вместо/поверх изложенного
здесь, а не реализовывать план как есть.

Первый практический шаг после аудита (если он подтвердит механику) — поднять `registry:2` +
`s3builder` и обкатать на одном некритичном приложении (staging target) до переноса продовых.

Sources (best-practice для remote-buildx и разделения build/runtime для Next.js) —
[docker/buildx](https://github.com/docker/buildx),
[Next.js: Deploying](https://nextjs.org/docs/pages/building-your-application/deploying),
[Next.js: Production checklist](https://nextjs.org/docs/app/guides/production-checklist).

### Аудит плана §157 (2026-09-06, `letar-dev`) — ⛔ план в текущем виде реализовывать нельзя

Обязательный шаг «свежий аудит плана целиком», затребованный автором записи выше. Проверка шла
по исходникам (`deploy-affected.sh`, `apps/*/Dockerfile.production`,
`apps/*/docker-compose.production.yml`) и живьём по обоим серверам (SSH, read-only команды).
**Вывод: план основан на неверной модели того, как сейчас устроена сборка, и переносит нагрузку
на машину, которая для сборки хуже.** Ниже — по находке на пункт, от блокирующих к второстепенным.

#### 🔴 1. `nx build` идёт на хосте, а не внутри Docker — remote buildx не переносит почти ничего

Пункт 4 плана («шаг `docker build`/`nx build`/`nx typecheck:tsgo` заменяется на диспетч на
s3-буилдер») предполагает, что всё это — части одной Docker-сборки. Это не так:

- `deploy-affected.sh:1130` — `nx $BUILD_TARGET $app` выполняется **на хосте**, до всякого Docker
  (кроме `IS_NODE_APP`, строка 1088 — те действительно собираются внутри образа);
- `deploy-affected.sh:1234` — `docker build -f "$APP_DIR/Dockerfile.production"` берёт **уже
  готовый** результат. Сам `Dockerfile.production` (проверено по всем приложениям) — это
  `FROM letar-node-runtime:24` плюс несколько `COPY` из `apps/<app>/.next/standalone`,
  `.next/static`, `public`. Никакой компиляции внутри нет, шаг занимает секунды.

Значит remote-буилдер унёс бы на s3 только эти `COPY`-слои, а всё, что реально ест память и
диск — `bun install`, `nx zenstack:generate`, `nx build`, `nx typecheck:tsgo`, кеш `.nx`, выхлоп
`apps/*/.next` — осталось бы на s2 ровно как сейчас. Заявленная цель («`node_modules`/`.bun`/
Nx-кэш убираются с хоста полностью») пунктом 4 не достигается.

Чтобы buildx-вариант вообще имел смысл, пришлось бы сначала переписать все
`Dockerfile.production` в многостадийные (сборка внутри образа) — отдельная крупная задача, в
§157 не упомянутая, и она конфликтует с текущей моделью «собрали один раз в монорепо, упаковали
готовое».

#### 🟡 2. s3 для сборок **медленнее** s2 в 3–10 раз — снято с блокеров решением владельца (2026-09-06)

Замер 2026-08-28 (один и тот же `dsperevod`): 1 м 22 с локально → 4.8 мин на s3 → 14.4 мин на s3
под пиком. Причина не в CPU (`vmstat` показывал `id 77-93` при load 5–8), а в I/O: нехватка RAM
плюс диск HDD с SSD-кешем против NVMe на s2. Тогда же владелец решил взять сервер на 32 ГБ RAM.

**Проверено живьём 2026-09-06 — апгрейд не сделан:**

| Параметр           | s2 (185.28.85.195)               | s3 (188.127.235.141)                      |
| ------------------ | -------------------------------- | ----------------------------------------- |
| RAM                | 15 Gi, swap 2.4/8.0 занято       | 15 Gi, swap **5.7/8.0** занято            |
| CPU                | 8 ядер                           | 12 ядер                                   |
| Диск               | 174 G, занято 165 G (95 %), NVMe | 2.0 T, занято 1.1 T (60 %), HDD+SSD-cache |
| Docker build cache | 17.0 GB (16.1 GB reclaimable)    | 95.9 GB (88.0 GB reclaimable)             |

s3 уже сидит в свопе на 5.7 ГБ при 20 запущенных контейнерах — до всякой прод-сборки. Перенос
туда сборки двух десятков приложений без апгрейда памяти означает не «разгрузили s2», а «сделали
каждый деплой в 3–10 раз дольше и добавили swap-thrashing машине, которая ночью гоняет e2e».

**Апгрейд RAM s3 — предусловие, а не деталь реализации.** Не назван ни в §157, ни в §80.

**Решение владельца 2026-09-06 (после этого аудита):** замедление сборок на s3 временно
приемлемо, терпим как есть; переезд на сервер с большим объёмом RAM запланирован примерно на
**2026-09-20** («через две недели» от даты решения). Пункт понижен с 🔴 до 🟡: это не блокер, а
известный временный компромисс с датой снятия.

⚠️ **Апгрейд памяти не чинит п. 1.** Ошибка в механике («remote buildx перенесёт только
`COPY`-слои») от объёма RAM на буилдере не зависит — сколько бы её ни было, `nx build` продолжит
идти на s2, пока `Dockerfile.production` остаётся упаковщиком готового выхлопа. К 2026-09-20
снимается только ограничение «переносить некуда», сам план всё равно требует переписывания
пунктов 1 и 4 (либо перехода к постановке §80: на новую машину едет весь конвейер, а не один
шаг `docker build`).

**Дополнение 2026-09-08 (решение владельца) — не апгрейд RAM у существующего s3, а отдельный
новый сервер `s4` под сборку/e2e.** Вместо смены характеристик текущего s3 владелец решил взять
отдельную машину (условно `s4`, 12 vCPU / 32 ГБ / 340 ГБ NVMe) и перенести на неё весь конвейер
сборки/e2e из §157, оставив s3 под то, что на нём и так постоянно крутится (GlitchTip, IPFS
`kubo`+`pin-queue`, `media-server`, staging-стенд `studio`, self-hosted `registry`, `traefik`,
`dashboard-agent`).

Разбор s3 живьём (2026-09-08, `docker stats`): устоявшаяся нагрузка без build/e2e — **~3 ГБ RAM,
пиковый CPU не выше ~19% одного ядра** (у `kubo`). Диск — 1.1 ТБ из 2.0 ТБ, это данные IPFS/
media-server, к RAM/CPU отношения не имеет. Из этого — план понизить характеристики s3 **после**
реального переезда build/e2e на `s4`, не раньше (сейчас swap 5.6/8.0 ГБ занят — вероятно хвост от
сборок/e2e, ещё идущих на s3; проверять `free -h`/`docker stats` заново уже после отключения этой
нагрузки, не по сегодняшнему снимку).

⚠️ **Видеотранскодинг (`media-worker`, ffmpeg, `WORKER_CONCURRENCY=2`) остаётся на s3, не
переносится на `s4`.** Хранилище `/data/raw`/`/data/processed` локальное на s3, `nginx` раздаёт
файлы прямо с диска — разнесение воркера и хранилища на разные хосты добавляет сетевой шаг ради
нагрузки, которой по факту почти нет (логи `media-worker` за 30 дней не содержат ни одного
реального job'а транскода). Держать на s3 не меньше **4 vCPU / 6–8 ГБ RAM**, чтобы редкие
всплески encode не голодали рядом с GlitchTip/kubo — не резать сервер под голый idle-снимок
сервисов.

**Побочная находка:** `media-redis` (BullMQ-очередь `media-worker`) настроен с
`maxmemory-policy allkeys-lru` вместо `noeviction` — под нагрузкой это грозит молчаливой потерей
заданий транскода. Сейчас безвредно (очередь пустая), фикс вынесен отдельной задачей
(`task_d0111e96`, спавнута 2026-09-08).

#### 🔴 3. Дисковое давление на s2 на ~3/4 — это кеши, чистятся сегодня, без реорганизации деплоя

Разбор занятого места на s2 (`du`, 2026-09-06):

```
/home/deploy/letar   120 G
  ├─ .nx/cache        64 G   ← крупнейший потребитель на всём сервере
  ├─ apps             44 G   ← преимущественно apps/*/.next после каждого деплоя
  ├─ node_modules     8.8 G
  └─ .git             1.1 G
/var/lib/docker       17 G   (из них 16.1 G — reclaimable build cache)
```

Из 165 G занятых **порядка 124 G — артефакты и кеши**, а не данные. `.nx/cache` в 64 ГБ — это не
норма, а отсутствие ретеншна: Nx не ограничивает размер локального кеша по умолчанию, а
`deploy-affected.sh` чистит его только точечно (`rm -rf ".nx/cache"` под `--clean`, строка ~1121).
`apps/<app>/.next` после успешного `docker build` больше не нужен — образ собран, но каталог
остаётся до следующей сборки этого приложения.

То есть заявленная первопричина («s2 кончился диск») снимается несколькими часами работы по
ретеншну, а не многонедельным проектом с registry и remote-буилдером. Это не довод «ничего не
делать» — это довод, что §157 не должен обосновываться дисковым давлением: после наведения
порядка остаётся только мотивация по RAM/CPU, а по ней см. п. 2.

#### 🔴 4. §157 дублирует §80 — ту же задачу от 2026-08-14, с более проработанным разбором

[§80](/docs/plans/PLAN-INFRA-5.md) «Вынос прод-сборки с s2 на s3, подключение к БД s2 удалённо» — тот же
запрос владельца, та же цель. §157 её не упоминает и заново, хуже, проходит те же вопросы. В §80
уже зафиксировано то, чего в §157 нет:

- доставка образа — **тот же вопрос, что §17** (Kamal: GHCR vs self-hosted registry), решать один
  раз на оба трека; §157 назначает self-hosted `registry:2` в одиночку, не сверяясь с §17;
- вариант **без registry вообще** — `docker save` + `scp` + `docker load` (для полутора десятков
  приложений на один целевой хост может оказаться дешевле, чем поднимать и охранять registry);
- риск: прод-деплой перестаёт быть однохостовой операцией — падение s3 блокирует деплой **всех**
  приложений `S2_APPS` разом, тогда как сегодня каждое независимо. В §157 риск не назван (вопрос
  «что ломается при недоступности s3» автор поставил себе в чеклист аудита, но ответа в плане нет);
- ресурсы s3 уже заняты ночным e2e (`0 2 * * *`) и staging-контейнерами — нужно разводить по времени.

**Действие:** §157 и §80 свести в одну секцию (старшая — §80, §157 переподчинить ей), иначе
третья сессия заведёт §158 про то же самое.

> Итоговое решение (см. врезку в начале секции выше, 2026-09-06): физически объединение пошло
> наоборот — §157 остаётся основной записью, §80 в PLAN-INFRA-5.md сведена к указателю.
> «Старшая — §80» здесь про номер и дату заведения, а не про то, где дешевле держать текст: к
> моменту слияния §157 была на порядок подробнее и уже процитирована из кода.

#### 🟠 5. «Prisma CLI уже внутри образа» — неверно; и план инвертирует порядок «миграции → сборка»

Пункт 4 предлагает применять миграции на s2 внутри пришедшего контейнера
(`docker compose run --rm app npx prisma migrate deploy`, «не требует node/bun на хосте, Prisma
CLI уже внутри образа»). Оба утверждения не подтверждаются:

- ни один `apps/*/Dockerfile.production` не копирует `prisma/` или `prisma/migrations` — проверено
  грепом по всем файлам, совпадений ноль. В образ едет только `.next/standalone` (плюс static,
  public и точечные исключения вроде `src/content` у kami). Standalone-трейсер тянет то, что
  импортирует сервер — CLI-пакет `prisma` и каталог миграций в это не входят;
- сейчас миграции применяются **до** сборки, и именно осознанно: `deploy-affected.sh:941` —
  «Apply migrations before build (so Next.js can pre-render with actual schema)». План переносит
  их на s2 **после** прихода образа, то есть после пререндера — приложения из п. 7 собирались бы
  на непримигрированной схеме.

Чтобы схема заработала, нужно отдельно: класть миграции и Prisma CLI в образ (растит его и меняет
все Dockerfile) **и** переставить порядок так, чтобы миграции применялись до старта сборки на s3.
То есть шаг миграций всё равно не уезжает с s2 и всё равно требует сетевого доступа буилдера к уже
мигрированной БД.

#### 🟠 6. БД не одна: 16 отдельных Postgres на `127.0.0.1:<свой порт>`, и доступ нужен не read-only

Пункт 3 плана говорит про «узкое firewall-правило s3→s2 на порт Postgres» и «отдельный read-only
пользователь БД для сборки». По факту (`apps/*/docker-compose.production.yml`):

```
animatrona-tracker 5439   dsperevod      5442   mandala      5434
aprel8008          5447   form-example   5443   studio       5455
archetest          5441   grandslamcup   5453   svoichuzhie  5446
auth-hub           5440   kami           5437   time         5445
dashboard          5436   driving-school 5438   umami        5435
domwellbes         5456
```

Каждая БД — свой контейнер, свой порт, и **все опубликованы только на loopback** (`127.0.0.1:…`),
как и отмечал §80. Значит это не одно правило, а шестнадцать (или один туннель с 16 форвардами),
плюс 16 пользователей вместо одного. И read-only не годится: `prisma migrate deploy` выполняет
DDL — либо пользователь с правом менять схему, либо миграции остаются на s2 (см. п. 5, там же —
почему это ломает порядок).

#### 🟠 7. Пререндер с обращением к БД реален, но точечен — 5 приложений, а не «часть страниц» вообще

Уточнение к пункту 3 (в плане сформулировано расплывчато). `generateStaticParams` с прямым
запросом к БД — у `aprel8008`, `grandslamcup`, `kami`, `mandala`, `svoichuzhie`. Остальные
`generateStaticParams` в монорепо — статические списки локалей. Это меняет оценку: сетевой путь
s3 → БД s2 нужен пяти приложениям из двух с лишним десятков, а не всем — перенос можно начинать с
тех, кому он не нужен вовсе, и не блокироваться на туннеле.

#### 🟠 8. Базовый образ `letar-node-runtime:24` собирается локально и в registry не публикуется

`deploy-affected.sh:734` собирает общий базовый образ на демоне того же сервера, комментарий рядом
прямо говорит «в registry не публикуется». Все `Dockerfile.production` начинаются с
`FROM letar-node-runtime:24` — локального тега. Удалённый буилдер этого тега не увидит и упадёт на
`FROM` (или, хуже, подтянет одноимённый образ ниоткуда). В плане шаг не упомянут: базовый образ
обязан ехать через тот же канал доставки первым, со своей политикой версионирования.

#### 🟠 9. В репозитории нет `.dockerignore` — контекст сборки это весь workspace

Проверено: ни корневого, ни пер-приложенческого `.dockerignore` нет вообще, а `docker build`
вызывается с контекстом `.` (корень workspace). Сегодня это терпимо — демон локальный, — но всё
равно означает, что в контекст на каждую сборку упаковываются `node_modules` (8.8 G), `.nx` (64 G)

каждый деплой, что хоронит вариант buildx сам по себе.

Как отдельная находка — ещё и дешёвый самостоятельный фикс: `.dockerignore` с `node_modules`,
`.nx`, `.git`, `**/.next/cache` ускорит и текущие локальные сборки, независимо от судьбы §157.

⚠️ **Уточнение после переработки плана (2026-09-06): вес этой находки снизился.** Формулировка
«обязателен для любого remote-варианта завтра» относилась к buildx-схеме, где контекст стримится
на чужой демон по сети. В принятой схеме («весь конвейер на s3») `docker build` выполняется
локально на той же машине, где лежит чекаут, — то есть `.dockerignore` остаётся **только**
локальной оптимизацией обхода дерева контекста, а не предусловием переезда. Брать как отдельную
мелкую задачу, не тащить в критический путь §157.

### Переработка §157 (2026-09-06, решение владельца после аудита) — «весь конвейер на s3, на s2 только релиз»

Владелец после аудита: `nx build` и всё, что до него, выполняем **только** на s3 — там же и кеши,
от них на выделенной сборочной машине становится только лучше; на s2 заливаем готовый образ. Это
снимает п. 1 аудита не заплаткой, а сменой формы: **remote buildx из плана исключается**, вместо
него — постановка §80 (переезжает весь конвейер, а не один шаг `docker build`).

Ниже — проработка «как это организовать». Механика §157 пунктов 1–6 заменяется целиком.

#### Разрез конвейера: где проходит граница

Сегодня `deploy-affected.sh` делает всё на одной машине. Разрез — сразу после того, как образ
собран, и до того, как он запускается:

| Фаза        | Где | Шаги                                                                                                                                                                                |
| ----------- | --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Build**   | s3  | `git pull` + submodules · `bun install` · `nx zenstack:generate` · миграции (см. ниже) · `nx build` · `nx typecheck:tsgo` · sourcemaps → GlitchTip · `docker build` · `docker push` |
| **Release** | s2  | тонкий `git pull` (compose-файлы) · `docker compose pull` · rollout / `up -d` · health-check · опциональный `db:seed`                                                               |

`nx affected` тоже считается на s3 — граф Nx требует `node_modules`, и именно ради того, чтобы их
на s2 не было, вся детекция уезжает вместе со сборкой (п. 5 исходного §157 — верный, сохраняем).

**Что остаётся на s2:** git-чекаут (compose, файлы миграций для аварийного пути), Docker,
per-app Postgres, `uploads/`. Уезжают: `node_modules` (8.8 G), `.nx` (33 G после чистки),
`apps/*/.next` (основная часть 44 G).

#### 🔴 Блокирующее предусловие, найденное при проработке: Nx-кеш не учитывает переменные окружения

**Это главное, что нужно починить до переезда, и оно контринтуитивно** — ровно там, где кажется,
что общий кеш только помогает.

Проверено 2026-09-06:

- `nx.json` → `namedInputs.sharedGlobals` = **пустой массив**, `targetDefaults.build` **отсутствует**.
  Ни одного `{"env": ...}`-инпута в конфиге нет. Значит ключ кеша таргета `build` считается только
  по файлам проекта и зависимостей.
- `deploy-affected.sh` подкладывает окружение **через шелл**, не через инпуты Nx: `set -a; source
  "$BUILD_ENV_FILE"; set +a` (строки ~1020 и ~883), где `BUILD_ENV_FILE` — это `.env.staging` для
  стейджа и `.env.docker` для прода (строки 265/272).
- `NEXT_PUBLIC_*` инлайнятся в клиентский бандл **на этапе сборки**
  ([nextjs-public-env-build-time-inlining](/.claude/docs/nextjs-public-env-build-time-inlining.md)).
  Такие переменные есть у **16 приложений** (1–5 штук на приложение): например у `kami` —
  `NEXT_PUBLIC_APP_URL`, `NEXT_PUBLIC_GLITCHTIP_ENVIRONMENT`; у `grandslamcup` — ещё и
  `NEXT_PUBLIC_UMAMI_WEBSITE_ID`, `NEXT_PUBLIC_YANDEX_MAPS_API_KEY`.

Сложив: сборка стейджа и сборка прода **одного и того же коммита** дают Nx одинаковый ключ кеша.
Сегодня это ничем не грозит только потому, что машины физически разные — у стейджа кеш на s3, у
прода на s2. Перенос прод-сборки на s3 эту случайную изоляцию убирает, и первый же прод-деплой
коммита, который до этого собирался на стейдже, получает **cache hit на staging-артефакт**: в
прод уезжает бандл со staging-овым `NEXT_PUBLIC_APP_URL`, staging-овым Umami и
`GLITCHTIP_ENVIRONMENT=staging`. Ни сборка, ни typecheck, ни health-check этого не заметят —
контейнер поднимется здоровым, ошибка видна только в браузере пользователя.

**Фикс (обязателен до переноса, порядок именно такой):**

1. **Немедленный и надёжный — разные каталоги кеша под окружение.** `NX_CACHE_DIRECTORY=.nx/cache-prod`
   против `.nx/cache-staging`, выставляется в `deploy-affected.sh` рядом с выбором `ENV_FILE_NAME`.
   Пересечение исключено по построению, ни одной переменной не нужно перечислять, места на s3
   хватает. Ретеншн `nx-cache-cleanup` придётся научить обходить оба каталога.
2. **Правильный по сути — объявить env-инпуты** (`{"env": "NEXT_PUBLIC_..."}` в `targetDefaults.build.inputs`
   или в `sharedGlobals`). Точнее, но требует перечислить переменные и не забыть при добавлении
   новой — то есть сам по себе становится источником той же ошибки. ⚠️ Поддерживает ли Nx 23
   glob-паттерн в `env`-инпуте (`NEXT_PUBLIC_*`) — **не проверено**, проверить до выбора этого
   варианта; если нет, то только полное перечисление.

Рекомендация: (1) как гейт переезда, (2) — отдельной задачей поверх, не блокируя.

#### Миграции: порядок «миграции → сборка» сохраняется, но выполняются они с s3

Ограничение из аудита (п. 5): миграции обязаны примениться **до** `nx build`, иначе пререндер
пятерых приложений соберётся на старой схеме. Значит перенести их «на s2 после прихода образа»
(как предлагал §157) нельзя. Порядок внутри Build-фазы:

```
s3: открыть туннель к БД приложения на s2
s3: → триггер pre-migrate dump на s2 (pg_dump живёт рядом с БД, там и остаётся)
s3: prisma migrate deploy   (через туннель)
s3: nx build                (пререндер видит уже новую схему)
s3: docker build && docker push
s2: docker compose pull && rollout
```

**Почему DDL-доступ с s3 не расширяет периметр:** s3 уже держит age-ключ SOPS
(`~/.age/letar-key.txt` у `deploy` — проверено) и, значит, уже способен расшифровать `.env.docker`
любого приложения, то есть уже владеет всеми прод-креденшлами. Выполнение миграций оттуда не даёт
ему прав, которых у него нет. Это же снимает вопрос «read-only пользователь для сборки» из §157:
read-only не годится для миграций, а для пререндера отдельный пользователь избыточен, раз полные
креды и так там.

**Альтернатива на потом (не для первой итерации):** отдельный `migrator`-образ на приложение
(prisma CLI + сгенерированная схема + `prisma/migrations`), который s2 запускает рядом с БД. Тогда
туннель нужен только пятерым пререндерным приложениям вместо семнадцати, а DDL выполняется на той
же машине, где БД. Это и есть корректная форма идеи §157 «миграции внутри контейнера» — но именно
**отдельным** образом: в прикладной образ они не входят (ни один `Dockerfile.production` не копирует
`prisma/`, см. аудит п. 5). Стоимость — ещё один артефакт на приложение; отложить до тиража.

#### Сетевой путь s3 → БД s2: SSH-туннель на время шага, без правок firewall

Все 17 прод-Postgres опубликованы только на loopback (`127.0.0.1:<свой порт>`, аудит п. 6).
Ничего открывать наружу не нужно: Build-фаза на время работы с конкретным приложением поднимает
`ssh -L <port>:127.0.0.1:<port> deploy@s2`, а `DATABASE_URL` на s3 указывает на свой `localhost:<port>`.
Биндинги на s2 остаются как есть, правила firewall не меняются, постоянного канала между серверами
не появляется. Это первый кандидат из §80, и он подтверждается: дешевле WireGuard ради одного порта.

Нужен туннель: всем 17 приложениям с БД (миграции) + пятерым из них дополнительно на время
`nx build` (пререндер: `aprel8008`, `grandslamcup`, `kami`, `mandala`, `svoichuzhie`).

#### Доставка образа: registry на s3

Выбор из §80 («registry vs `docker save`/`scp`») — в пользу registry:

- откат становится кросс-хостовым и переживает чистку диска: сегодня теги `<app>:<sha>` живут
  локально на s2 и подрезаются до трёх последних (`deploy-affected.sh` ~1237); в registry ретеншн
  настраивается один раз и не зависит от места на целевом хосте;
- `docker save`/`load` гонит образ целиком на каждый деплой — слоевого переиспользования нет;
- §17 (Kamal) упирается ровно в тот же вопрос — решается один раз на оба трека.

Параметры: `registry:2` на s3 за Traefik (TLS уже есть), basic-auth, хранение на диске s3
(760 G свободно). **Бэкап не нужен** — образы воспроизводимы из git, registry здесь кеш, а не
источник истины; нужен только GC/ретеншн по тегам.

**Базовый образ `letar-node-runtime:24` — правка Dockerfile не требуется.** Аудит (п. 8) назвал это
проблемой для варианта с remote-буилдером, где `FROM` резолвит чужой демон. В варианте «весь
конвейер на s3» `FROM` резолвится **на s3 при сборке**, где образ локальный — ровно так же, как
сегодня на s2. На s2 `FROM` не резолвится вообще: туда приезжает готовый образ со всеми слоями.
Шаг «собрать базовый образ» просто переезжает на s3 вместе с остальным (`deploy-affected.sh:734`).

#### Оркестрация: кто кого запускает

Сегодня цепочка — `deploy-mcp` → `dashboard-agent` на целевом сервере → `nsenter` →
`deploy-affected.sh`. После разреза:

- **Build-фазой владеет s3**, потому что там граф Nx и `nx affected`. `deploy-affected.sh`
  становится сборочным скриптом и заканчивается `docker push` + вызовом Release-фазы;
- **Release-фаза — отдельный тонкий скрипт на s2** (`deploy-release.sh`): `git pull`, `compose pull`,
  rollout/`up -d`, health-check, seed. Ему не нужны ни `node_modules`, ни Nx, ни bun;
- вызов s3 → s2 идёт через уже существующий `dashboard-agent` на s2 (у него есть эндпоинты и
  nsenter-спавн), а не новым SSH-каналом — меньше новых прав и путей;
- `deploy-mcp` снаружи не меняет контракт: `deploy_app({app, target})` по-прежнему одна команда,
  просто внутри — две фазы. `deploy_status` должен научиться показывать, в какой из них деплой.

⚠️ **`DEPLOY_SERVER_NAME`** (§81) становится критичнее: скрипт на s3 теперь работает и «за себя»,
и «за s2», а резолв через `hostname -f` на s3 не матчится в принципе. Проверить, что переменная
доезжает до обеих фаз, — до пилота, а не после.

#### Взаимодействие с e2e-гейтом и §19.1

Гейт `checkE2eGate` ключуется на `commitSha` и от места сборки не зависит — контракт сохраняется.
Трек 1b §19.1 (пропуск typecheck на проде для `HARD_GATED_APPS`) остаётся обоснованным по прежней
причине — «staging того же коммита уже прошёл», — а **не** по тому, что кеш общий: после фикса
изоляции кеша (см. выше) прод-прогон typecheck будет отдельной записью, и полагаться на cache hit
между окружениями нельзя. Формулировку в §19.1 при реализации не менять.

#### Режимы отказа — то, чего в §157 не было

- **s3 или registry недоступны** (они на одной машине — SPOF общий): прод-деплой невозможен
  **для всех** приложений сразу, тогда как сегодня каждое независимо. ✅ **Решение владельца
  2026-09-06: аварийного пути не делаем — просто не деплоим, пока s3 лежит.** Если случится
  ситуация, где деплой действительно нельзя отложить, решение принимается по факту, вручную
  (git-чекаут на s2 остаётся, `bun install` + старый однохостовый путь физически возможен —
  но как разовая мера, не как поддерживаемый режим). Автоматический фолбэк сознательно не
  строится: он потребовал бы постоянно держать `node_modules` на s2 и отменил бы цель переезда.
- **Сборка прошла, миграция применена, Release упал** — схема впереди кода. Не регресс: сегодня
  ровно то же самое (миграции идут до сборки, которая длится минуты).
- **Обрыв `docker push` посередине** — повтор идемпотентен, слои докачиваются.
- **Конкуренция за s3** — ночной e2e (`0 2 * * *`) и staging-контейнеры уже там (см. «Предыстория»
  выше). После переезда добавляются прод-сборки; развести по времени или принять.

#### Задача №1 к исполнению — гейт: изоляция Nx-кеша по окружению (передача, 2026-09-06)

Постановка для следующей сессии. Первый пункт порядка работ, от железа не зависит, делается до
переезда s3. **Цель — закрыть риск, описанный выше: после переноса прод-сборки на s3 прод-билд
получит cache hit на staging-артефакт с чужими `NEXT_PUBLIC_*`.**

⚠️ **Это не «добавить переменную».** Приёмка — доказанное отсутствие cache hit между окружениями,
а не «команда отработала». Ниже — почему именно так и где точно врут промежуточные проверки.

##### Что уже установлено (перепроверять не нужно, но и не противоречить)

- `nx.json` **уже задаёт** `"cacheDirectory": ".nx/cache"` явным полем верхнего уровня. То есть
  каталог кеша сейчас берётся оттуда, а не из дефолта.
- `namedInputs.sharedGlobals` — пустой массив, `targetDefaults.build` отсутствует. Ни одного

- Nx поддерживает и `cacheDirectory` в `nx.json`, и переменную `NX_CACHE_DIRECTORY`
  (подтверждено по `nx_docs`, дефолт `.nx/cache`). Env-инпуты объявляются как `{ "env": "API_KEY" }`

2. **`.gitignore` — добавить новые каталоги.** Сейчас там `.nx/cache` **точным путём** (строка 56),

##### Приёмка — сначала воспроизвести баг, потом починить (Red → Green)

Обычный прогон `nx build` ничего не докажет: cache hit виден только при **повторной** сборке того
же коммита с другим окружением. Порядок:

1. **Red.** Локально, на любом приложении с `NEXT_PUBLIC_*` (`kami` — 3 переменные, из них
   `NEXT_PUBLIC_APP_URL` наглядна): собрать с одним значением `NEXT_PUBLIC_APP_URL`, затем, ничего
   не меняя в коде, собрать с другим. Ожидание до фикса — **вторая сборка попадает в кеш** (Nx
   печатает про чтение результата из кеша), и в выхлопе лежит URL от первой. Это и есть баг —
   зафиксировать вывод, он же доказательство, что задача не выдумана.
2. **Green.** Применить правки, повторить тот же сценарий с разными `NX_CACHE_DIRECTORY` —
   cache hit исчезает, в каждом выхлопе свой URL.
3. **Проверить приоритет.** `nx.json` уже содержит `cacheDirectory`. Убедиться **эмпирически**,
   что переменная окружения его перебивает (создался именно `.nx/cache-prod`, а не `.nx/cache`),
   а не полагаться на то, что «обычно env выигрывает». Если не перебивает — переключиться на
   передачу каталога другим способом, но **не** оставлять молчаливо неработающий экспорт: это
   ровно тот сценарий, который в репозитории описан как «зелёная команда, нулевой эффект».
4. `nx lint` + `nx typecheck:tsgo` на `dashboard-agent`, тесты `nx-cache-cleanup.spec.ts` зелёные.

**Чего делать НЕ надо в этой задаче:** объявлять env-инпуты (`{"env": ...}`) вместо разделения
каталогов. Это правильный по сути фикс, но как первый шаг он хуже: требует перечислить переменные
поимённо и забыть новую можно так же легко, как сейчас, а glob-поддержка не подтверждена. Завести
отдельной задачей поверх, когда разделение каталогов уже стоит.

1. **Фрагмент.** Парсит все `.zmodel`-файлы приложения (корневой и доменные — импорты между

   покрывающий глоб в `inputs`. Это ловит и регрессию «доменные файлы схемы вне inputs» из §162,

3. Отсутствие `inputs` у таргета целиком — отдельная находка.

## §186 Три submodule блокировали деплой ВСЕГО монорепо — push без владельца (2026-09-16)

При старте `/domwellbes`-сессии `scripts/check-submodule-push-state.sh` показал: `domwellbes`,

update --recursive` в `deploy-affected.sh` падает с `upload-pack: not our ref <sha>` **до выбора

Корневой `letar` тоже отставал на 79 коммитов.

**Сделано:** с явного одобрения владельца (спрошено отдельно, до пуша) — `git push origin main`
во всех трёх submodule, затем `git push origin main` в корне `letar`, порядок соблюдён
(submodule → letar, [git.md](/.claude/rules/git.md)). `check-submodule-push-state.sh` повторно
дал «✅ синхронны с origin: 14 из 14».

**Почему не биллилось ни одному клиентскому проекту:** починка затрагивает деплой всего
монорепо, не конкретное приложение — время внесено как `time_discard` (`INTERNAL`), не записано
на `domwellbes`, хотя найдено в его сессии.

⚠️ **Не расследовано:** кто и когда закоммитил эти три submodule-бампа без последующего push —
не входило в объём этой сессии (инфраструктурная авария устранена, причина возникновения не
