# Свой mask-движок: исследование и предлагаемая архитектура

**Статус:** исследование завершено, архитектура — на согласовании. Реализация не начата.
**Дата:** 2026-08-12
**Задача:** `PLAN.md` → Backlog → «[2026-08-11] Свой mask-движок вместо use-mask-input»

---

## 0. Краткая сводка для нетерпеливых

1. **Существующие библиотеки брать не во что.** `imask` без коммитов с октября 2024, `react-input-mask` мёртв с 2018, `Inputmask` — 645 открытых issue с багами 2015–2020 годов, `use-mask-input` — обёртка над `Inputmask`, наследующая всё.
2. **Ключевые боли — архитектурные, а не баги реализации.** Мейнтейнеры трёх разных проектов независимо написали, что чинить это не будут и не могут.
3. **Цена вопроса конкретна:** `use-mask-input` весит 91.3 KB raw / **25.5 KB brotli** — больше, чем весь `@letar/forms` с 56 полями (109 KB raw / 20 KB brotli).
4. **У нас уже есть баг с потерей данных в проде** — не в чужой библиотеке, а в собственном `formatPhoneNumber` (§4).
5. **Главный вывод исследования не технический, а продуктовый:** живая маска — доказанно худший из режимов форматирования. Правильный дефолт — форматирование по `blur`, а маска «на каждое нажатие» должна включаться осознанно.

## 1. Что у нас есть сейчас

### 1.1 Два несовместимых механизма

| Механизм                            | Где                                                                  | Как работает                                     |
| ----------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------ |
| `use-mask-input` (Inputmask)        | `FieldMaskedInput`, 8 документных полей, generic-тип `'maskedInput'` | мутирует DOM через `ref` в обход React           |
| `formatPhoneNumber` (`forms-core`)  | `FieldPhone` (Chakra + shadcn)                                       | чистый JS на каждый `onChange` — **с багом**, §4 |
| `formatCardNumber` / `formatExpiry` | `FieldCreditCard`                                                    | чистый JS, алгоритмическая группировка           |
| `formatPhone` (`format-utils`)      | `PhoneInput` в `driving-school`                                      | чистый JS, **корректно** обрабатывает `8` → `7`  |
| `InputPlateNumber`                  | `driving-school`, госномер РФ                                        | позиционные правила + транслитерация, см. §1.4   |

Первый — источник WebKit-инцидента v1.4.4. Остальные — то, чем его заменяли по частям, каждый раз
заново.

⚠️ **Телефон реализован в монорепо трижды и по-разному.** `@letar/forms-core/phone` и
`@letar/format-utils/phone` решают одну задачу, но `format-utils` делает это правильно, а
`forms-core` — с потерей данных (§4). Консолидация этих двух — обязательная часть работ.

### 1.2 Реальный масштаб использования

- `Field.Phone` (собственный форматтер) — **30 файлов** приложений.
- `FieldMaskedInput` и `Form.Document.*` (`use-mask-input`) — **ноль продуктовых применений**. Только 4 демо/доковых страницы.

Собственное решение разошлось по монорепо, покупное не прижилось нигде. Это снимает вопрос обратной совместимости: ломать нечего.

### 1.3 Насколько сложны наши реальные маски

Все восемь документных полей — фиксированные шаблоны из **двух токенов** (`9` — цифра, `*` — буква или цифра) и литералов:

```
ИНН     999999999999        КПП      *********
БИК     999999999           Паспорт  99 99 999999
ОГРН    9999999999999       СНИЛС    999-999-999 99
Счёт    ×20 цифр            Корр.счёт ×20 цифр
```

Ни дат с валидацией диапазонов, ни валют с плавающим разделителем, ни alternation, ни regex-масок. То есть ~95% возможностей `Inputmask` мы не используем.

### 1.4 Госномер РФ — прецедент, задающий планку

`apps/driving-school/src/driving-school-form/inputs/input-plate-number.tsx` — самая проработанная
реализация ввода в монорепо, и она требует того, чего **не умеет ни одна изученная mask-библиотека**:

```ts
const VALID_LETTERS = 'АВЕКМНОРСТУХ'                    // не «любая буква», а 12 конкретных
const LATIN_TO_CYRILLIC = { A: 'А', B: 'В', E: 'Е', ... } // печатаешь латиницей — получаешь кириллицу
const SPACE_POSITIONS = [1, 4, 6]                        // пробелы и авто-, и пользовательские
```

Формат: `А 123 ВС 77` — буква, 3 цифры, 2 буквы, **2 или 3** цифры региона.

Отсюда четыре требования к движку сверх «шаблон из токенов»:

1. **Токен с собственным алфавитом.** `a` = «любая буква» недостаточно: нужен токен, принимающий
   заданный набор символов.
2. **Трансформация символа при вводе.** Латиница → кириллица, приведение к верхнему регистру.
   Это не фильтрация (символ не отвергается), а замена. У `Inputmask` и `imask` такого нет;
   у `maska` есть `transform`-хуки — единственный аналог из обзора.
3. **Переменная длина хвоста.** Регион 2 или 3 цифры — маска обязана принимать оба варианта,
   не дорисовывая третью позицию принудительно.
4. **Разделители, введённые пользователем, сохраняются**, если попали в допустимую позицию, а не
   затираются авто-форматированием.

Плюс уже реализованное там же разделение «то, что видно» и «то, что в БД»
(`formatPlateNumberDisplay` / `stripPlateNumberSpaces`) — ровно то `value` / `displayValue`,
которое предлагается в §6.6.

**Вывод:** госномер — не экзотика, а эталонный приёмочный тест для движка. Если движок его
выражает декларативно (без отдельного компонента на 230 строк), значит модель токенов достаточна.

### 1.5 Что сломано прямо сейчас

- **Документные поля не покрыты тестами вообще.** `document-fields.spec.ts` не импортирует ни одного компонента — в нём локальные копии `validate`, местами расходящиеся с продовым кодом (ИНН-12 и СНИЛС в тестах возвращают `undefined` с комментарием «упрощённая проверка»).
- **`field-masked-input.spec.tsx` не проверяет маскирование** — только рендер.
- **E2E использует `.fill()`**, а не `pressSequentially` — то есть посимвольный ввод, на котором ловили WebKit-баг, не воспроизводится.
- **Документация обещает несуществующую фичу:** `apps/form-docs` показывает `ui: { mask: '...' }` в Zod-мете, но ключа `mask` в `FieldUIMeta` нет, и `field-type-mapper` его не читает.
- **`PHONE_MASKS` продублированы** в Chakra- и shadcn-скинах дословно.

## 2. Почему не взять готовое

### 2.1 Состояние проектов

| Проект             | Последний релиз      | Последний коммит | Вывод                           |
| ------------------ | -------------------- | ---------------- | ------------------------------- |
| `imask`            | 7.6.1, май 2024      | октябрь 2024     | ~22 месяца тишины               |
| `react-input-mask` | 2.0.4, сентябрь 2018 | —                | мёртв 8 лет                     |
| `Inputmask`        | stable 5.0.9         | активен          | 645 открытых issue, беты годами |
| `use-mask-input`   | активен              | активен          | обёртка над `Inputmask`         |

### 2.2 Мейнтейнеры сами объясняют, почему это не чинится

**Про undo** — автор `imask`, issue #942, закрыт как `wontfix`:

> «I don't think it's a mask issue, but a web standards issue… **So probably this never be fixed.**»

Автор issue проверил и подтвердил, что проблема классовая: он посмотрел около десяти разных mask-библиотек, и у всех обнаружилось похожее поведение.

**Про Android** — автор `Inputmask`, файл `README_android.md`:

> «**the problem is the predictive text functionality. There is no way to prevent or control the input**… I tried several ways multiple times. Compositionevents, inputevent only masking, all with partial success… **Inputmasks with alphanumeric input will all fail.**»

**Про paste** — автор `use-mask-input`, issue #176, май 2026, закрыт как `not_planned`:

> «Its internal paste handler reads the clipboard value, applies the mask logic manually, and then calls `event.preventDefault()` by design… **For that reason, I do not think this can be fixed correctly in `use-mask-input` itself at the moment.**»

**Про доступность** — `Inputmask` #981 открыт с 2015 года, 11 лет. Вывод участников: пока шаблон маски лежит в `value`, `aria-*` атрибуты не помогают.

### 2.3 Отдельно про нашу аудиторию

`imask` #1055 — «маска применяется только после blur при вводе с **Яндекс-клавиатуры**». PR с исправлением висит без ревью с октября 2025. Комментарий оттуда:

> «I was surprised when I saw **how many keyboards use composition events by default for no reason even for Latin characters** (especially Android devices from 2-3 years old).»

Это ровно наши пользователи.

## 3. Фундаментальные ограничения подхода «перехвати и перепиши»

То, что не чинится патчами, и что мы обязаны обойти архитектурно.

### 3.1 Программная запись `value` уничтожает undo

Браузер ведёт свой undo-стек и пополняет его только «нативными» правками. `el.value = x` в стек не попадает. Ctrl+Z либо не делает ничего, либо откатывает к состоянию до маски — и маска об этом не узнаёт.

`setRangeText()` стек **сохраняет** (Safari — с 14.1). Но есть подвох: маска переформатирует **всё** значение, а не диапазон. Когда в середине появляется разделитель, локальной замены не хватает, и приходится звать `setRangeText(newValue, 0, oldValue.length)` — это одна крупная запись вместо естественной посимвольной.

Все четыре изученные библиотеки присваивают `.value` напрямую. То есть нативный undo в маскированном поле в индустрии уже сломан повсеместно.

### 3.2 Не весь ввод проходит через клавиши

Три источника ввода не дают содержательного `keydown`:

1. **IME-композиция** — `keyCode 229`, реального символа в событии нет. Включается не только на японском/китайском, но и на многих Android-клавиатурах для латиницы и кириллицы.
2. **Предиктивный ввод Android** — клавиатура заменяет слова целиком; Backspace приходит как `insertCompositionText`.
3. **Автозаполнение** — `keydown` не приходит вовсе.

Критично: **`beforeinput` с `inputType: 'insertCompositionText'` не отменяем по спецификации** (`w3c/input-events#115`). Это значит, что архитектура «перехватили → отменили → вставили сами» разваливается на IME принципиально, а не по недосмотру.

### 3.3 Автозаполнение не проходит через `beforeinput`

Браузер при автозаполнении `beforeinput` не шлёт вовсе, `inputType` в `input` приходит `undefined`, а Safari, бывает, не шлёт и `input` (`maska#238`). Движок, слушающий только `beforeinput`, теряет автозаполнение целиком.

### 3.4 Прямая запись `value` невидима для React

React ставит свой сеттер на `HTMLInputElement.prototype.value` и трекает последнее известное значение. Сторонняя запись `el.value = x` для React «не изменение» — `onChange` не вызывается. Отсюда целое семейство симптомов, выглядящих как разные баги.

Автор `imask`: «there is no legal way to create SyntheticEvent manually».

### 3.5 Шаблон маски внутри `value` ломает три вещи сразу

- **Скринридер** зачитывает подчёркивания как содержимое поля.
- **Автозаполнение Chrome** не показывает выпадашку — поле считается непустым.
- **Валидация** вынуждена всюду различать «маску» и «данные».

## 4. Найденный баг в нашем коде

Воспроизведено вживую в `form-develop-app`, Chrome 148:

| Ввод          | Получилось           | Должно быть          |
| ------------- | -------------------- | -------------------- |
| `89185568172` | `+7 (891) 855-68-17` | `+7 (918) 556-81-72` |

Пользователь набирает номер с привычной восьмёрки. Она попадает в номер как первая цифра кода региона, последняя цифра **молча отбрасывается**. Результат выглядит правдоподобно — маска заполнена целиком, ошибки нет.

Причина в `formatPhoneNumber`: он отбрасывает ведущую `7` (литерал маски) через эвристику `leadingLiteralDigits`, но про российский междугородний префикс `8` не знает.

Это не теория: `Field.Phone` используется в 30 файлах приложений. Точно такой же класс поломки описан для маски `+7` в независимых источниках — вставка `89201234567` в маску `+7` может оставить `+81`.

**Отдельно:** `formatPhoneNumber` не обрабатывает позицию каретки вообще — ни `selectionStart`, ни `setSelectionRange`. При вводе слева направо это незаметно, при правке середины курсор прыгает в конец.

## 5. Что говорят исследования об уместности масок

Здесь исследование дало неожиданный результат: **консенсуса нет, и это не от невежества.** Две крупные государственные дизайн-системы пришли к противоположным выводам.

### 5.1 GOV.UK — против

Паттерн Phone numbers прямо советует избегать масок и подстановки шаблонов, потому что это усложняет ввод. Наблюдение команды GOV.UK Notify: пользователи терялись, когда система возвращала им их же номер в изменённом виде (например, с дописанным кодом страны).

Сломало людей не разделение цифр, а **то, что система молча изменила введённое**.

### 5.2 USWDS — за, но сами поймали свой компонент на нарушении

У USWDS компонент маски есть. Но их собственное модерируемое тестирование (5 участников со вспомогательными технологиями) показало: когда пользователь вводил недопустимый символ, **4 из 5 не понимали, что произошло** — символ молча съедался без обратной связи. Issue открыт, компонент признан провалившим WCAG 3.3.3 (Error Suggestion).

### 5.3 Водораздел

Расхождение объясняется типом данных, а не вкусами:

|         | GOV.UK                                       | USWDS                                            |
| ------- | -------------------------------------------- | ------------------------------------------------ |
| Данные  | телефоны со всего мира, **переменная длина** | SSN, ZIP — **фиксированный национальный формат** |
| Решение | маски нет                                    | маска есть                                       |

**Маска оправдана там, где длина фиксирована и разбиение канонично. Где длина плавает — вредит.**

Российская дизайн-система Контур формулирует тот же критерий точнее всех:

> Маску показывать, когда нужно ввести определённое количество символов и когда в формате есть разделители. Если количество символов может быть разным, **как в ИНН, маска не показывается**.

Это прямо про нас: **ИНН (10 или 12 цифр, без разделителей) маскировать не нужно** — маска там даёт только риск обрезки. СНИЛС (`999-999-999 99`, фиксированная длина, разделители) — нужно.

### 5.4 Где маска доказанно помогает

Baymard Institute на юзабилити-тестировании чекаутов: неверный ввод длинного номера карты был прямой причиной отказов от оплаты, а автоформатирование пробелами заметно повышает точность и позволяет свериться глазами. Срок действия — строго `MM / YY`, один в один с физической картой.

Важная деталь оттуда же: **89% испытуемых не следовали примерам формата**, показанным в подсказке. То есть аргумент «просто напиши формат в hint вместо маски» слабее, чем кажется.

И их же формулировка, которую стоит взять дословно:

> …the **default implementation for all users is a normal empty form field that accepts any formatting**.

### 5.5 Альтернатива, выигрывающая по совокупности

**Форматирование по `blur`** (подход Politespace / Labelmask, есть в продакшн-дизайн-системе CMS): во время набора поле ведёт себя как обычное — курсор не прыгает, вставка не ломается, скринридер не получает подменённого значения. Форматирование применяется при уходе из поля, а формат заранее показан рядом с label.

| Подход                   | Формат известен заранее | Курсор цел | Вставка цела | SR не врёт |
| ------------------------ | ----------------------- | ---------- | ------------ | ---------- |
| Живая маска (наивная)    | да                      | **нет**    | **нет**      | **нет**    |
| Живая маска (правильная) | да                      | да         | да           | условно    |
| Форматирование по blur   | да                      | да         | да           | да         |
| Без форматирования       | из hint                 | да         | да           | да         |

## 6. Предлагаемая архитектура

### 6.1 Расположение

```
libs/forms-core/src/lib/mask/     →  subpath  @letar/forms-core/mask
```

По образцу уже работающих `./phone` и `./credit-card` — оба framework-free, оба потребляются и Chakra-, и shadcn-скином. `./phone` становится тонкой обёрткой над движком.

> ⚠️ Новый subpath требует прописать `paths` в **каждом** приложении-потребителе — см. `.claude/rules/libs.md`.

### 6.2 Слои

```
1. pure   format(raw, opts) / unformat(value, opts) / formatToParts(value, opts)
          caretBoundary(value, opts): boolean[]            ← переопределяемо скином

2. pure   applyChange({ previousValue, inputType, addedValue, changeStart, changeEnd, ... })
             → { value, selectionStart, selectionEnd }     ← вся семантика, включая каретку

3. DOM    MaskController(el) — события, трекинг выделения, запись value, каретка,
          composition-guard, autofill-детект, история undo

4. skins  React (ref + хук), Vue (директива) — только связывание
```

**Слой 2 — ключевой.** Это единственная точка, где семантика маски выражена без DOM, но уже с позицией каретки. Именно так устроен `@react-input/mask`, и это единственная библиотека в обзоре, у которой граница проведена по-настоящему (её ядро работает из CDN вообще без React).

У `maska` курсорная логика утекла в DOM-слой и не тестируется без браузера — эту ошибку не повторяем.

### 6.3 Модель событий

Отказываемся от `keydown` как перехватчика символов. Оставляем его только для undo-хоткеев.

| Событие                                          | Роль                                                          |
| ------------------------------------------------ | ------------------------------------------------------------- |
| `input` (с guard `composing \|\| e.isComposing`) | основной путь: применить маску                                |
| `compositionend`                                 | применить маску после IME — единственная точка при композиции |
| `beforeinput`                                    | **только** `historyUndo` / `historyRedo`                      |
| `keydown`                                        | **только** fallback undo-хоткеев + трекинг каретки            |
| `animationstart` + CSS `:-webkit-autofill`       | детект автозаполнения (Safari не шлёт `input`)                |

Жёсткие правила:

- **Никогда** не звать `preventDefault()` на композиции — не сработает и сломает IME.
- **Никогда** не писать `value` и не двигать каретку во время композиции.
- `type="text"` + `inputmode="numeric"`, **никогда** `type="number"` (там недоступен selection API).
- `inputmode="numeric"` — заодно самая дешёвая защита от Яндекс-клавиатуры и Gboard: на цифровой раскладке композиция практически не включается.

### 6.4 Каретка

Не дельта длины (`newPos = oldPos + Δlen`) — она ломается везде, где символы появляются не в конце.

Алгоритм: посчитать **значащие символы слева от каретки** до форматирования, после форматирования пройти по новому значению до того же счётчика, «примагнитить» к ближайшей допустимой позиции.

Критично: **три разные ветки** для `insert` / `deleteBackward` / `deleteForward` — при вставке каретка встаёт после последнего вставленного, при удалении назад — после последнего уцелевшего слева, при удалении вперёд — перед первым уцелевшим справа. Дельта длины эту разницу не выражает в принципе.

Плюс два обязательных костыля, которые есть у всех серьёзных библиотек: повторная установка каретки через `setTimeout` (мобильный Chrome сбрасывает позицию) и «не трогать каретку, если выделено всё значение».

### 6.5 Автозаполнение

Три механизма вместе, иначе не ловится:

1. `inputType === undefined` при `input` → считать, что заменили всё значение целиком.
2. CSS `:-webkit-autofill` + `animationstart` → для Safari, где `input` может не прийти.
3. Сверка значения в `queueMicrotask` при инициализации.

### 6.6 Публичный API

Режим форматирования — первоклассный параметр:

```ts
formatMode:
  | 'live'      // маска на каждое нажатие                        ← ДЕФОЛТ (решение владельца)
  | 'blur'      // формат при уходе из поля, снятие при возврате
  | 'off'       // только нормализация
```

> **Решение 2026-08-12 (Ками):** дефолт — `'live'`, вопреки исходной рекомендации исследования
> (`'blur'`). Режим `'blur'` остаётся доступным параметром.
>
> **Что из этого следует.** USWDS провалили WCAG 3.3.3 не потому, что режим живой, а потому что
> маска **молча** съедала недопустимый символ — 4 из 5 участников со скринридером не понимали,
> что произошло. Живой режим сам по себе это не предопределяет. Поэтому при дефолтном `'live'`
> перечисленные ниже требования перестают быть «желательными» и становятся условием
> работоспособности:
>
> - объявление отвергнутого символа через `aria-live="polite"` — **обязательно и включено по
>   умолчанию** (без него мы буквально воспроизводим их баг);
> - шаблон маски не попадает в `value` — иначе скринридер зачитывает подчёркивания, а Chrome
>   не показывает автозаполнение;
> - каретка с тремя раздельными ветками (§6.4) — в живом режиме её прыжки видны на каждом
>   нажатии, а не только на blur;
> - IME-guard (§6.3) — в живом режиме композиция ломается сразу, а не откладывается до ухода
>   из поля.
>
> Иначе говоря: выбор `'live'` не добавляет риска сам по себе, но переносит всю нагрузку на
> корректность реализации. Это увеличивает объём работ по сравнению с `'blur'`.

Дальше — то, что API должно делать **невозможным**:

| Требование                                | Как обеспечивается                                                                          |
| ----------------------------------------- | ------------------------------------------------------------------------------------------- |
| Шаблон никогда не попадает в `value`      | нет способа передать его туда через API                                                     |
| Молчаливая обрезка при вставке            | `onPaste: 'normalize' \| 'reject'`, варианта `truncate` нет                                 |
| Отвергнутый символ должен быть объявлен   | `onRejectedInput` + `aria-live="polite"`, включено по умолчанию                             |
| Формат известен до ввода (WCAG 3.3.2)     | `formatDescription` обязателен, иначе ошибка в dev                                          |
| `aria-live="assertive"` на форматировании | недоступен через API                                                                        |
| Блокировка вставки                        | недоступна                                                                                  |
| Маска не является валидацией              | `value` (сырое) и `displayValue` (отформатированное) разделены; валидация всегда по `value` |

Переменная длина — первоклассный случай, а не край:

```ts
mask: string | string[] | ((raw: string) => string | null)
// null = «для этого ввода маски нет, работаем как свободное поле»
```

Это же закрывает и телефонный кейс: по началу номера выбрать маску, а `8` в начале распознать как эквивалент `+7`, а не как цифру номера.

## 7. Объём и границы

**В скоупе:**

- Токены `9` (цифра), `a` (буква), `*` (буква или цифра), экранирование литералов.
- **Пользовательские токены** с собственным алфавитом и функцией трансформации символа —
  требование госномера (§1.4), без него он не выражается декларативно.
- **Опциональные позиции** (переменная длина хвоста — регион `77` или `777`).
- Фиксированные шаблоны с литералами — покрывает все 8 документных полей.
- Телефон (с исправлением бага `8`), номер карты, срок действия, госномер РФ.
- Три режима форматирования, каретка, IME-guard, autofill, вставка.

**Приёмочные тесты движка** (если выражаются декларативно — модель достаточна):

| Кейс        | Что проверяет                                      |
| ----------- | -------------------------------------------------- |
| СНИЛС       | базовый шаблон с литералами                        |
| Госномер РФ | свой алфавит + трансформация + переменная длина    |
| Телефон РФ  | нормализация `8`/`+7`, выбор маски по началу ввода |
| Номер карты | группировка по бренду, пользовательские пробелы    |
| ИНН         | маска **не** применяется (переменная длина), §5.3  |

**Вне скоупа (сознательно):**

- Даты с валидацией диапазонов (`MaskedRange` у imask) — у нас для этого есть `Field.Date`.
- Валюты с плавающим разделителем — есть `Field.Currency` и алгоритмический форматтер.
- Regex-маски и alternation произвольной сложности.

**Что нужно починить попутно:**

- Баг `8` в телефоне (§4) — можно отдельным фиксом, не дожидаясь движка. **Логику не изобретать:**
  корректная реализация уже есть в `@letar/format-utils/phone` (`formatPhone`, `normalizePhone`),
  где `8` → `7` обрабатывается явно и покрыто JSDoc-примерами. Задача — консолидация двух
  реализаций, а не написание третьей.
- Фантомные тесты документных полей.
- Дубль `PHONE_MASKS` между скинами.
- `ui.mask` в документации — либо реализовать, либо убрать из доков.
- **ИНН** по критерию §5.3 маску получать не должен — только ограничение длины и валидация контрольной суммы.
- После появления движка — проверить, сводится ли `InputPlateNumber` (230 строк в
  `driving-school`) к декларативному описанию маски. Если да — заменить, оставив компонент только
  как тонкую обёртку.

## 8. Принятые решения (2026-08-12, Ками)

| # | Развилка                    | Решение                   | Следствие                                                                                                                                                               |
| - | --------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1 | Дефолтный режим             | **`'live'`**              | Вся нагрузка переносится на корректность реализации: объявление отвергнутых символов, каретка, IME-guard становятся обязательными (§6.6). Режим `'blur'` — параметром.  |
| 2 | Undo                        | **свой стек состояний**   | ~100 записей `{value, selection}`, перехват `historyUndo`/`historyRedo` + хоткеев в `keydown`. Не покрывает системные жесты (меню Правка → Отменить).                   |
| 3 | API `MaskedInputFieldProps` | **спроектировать заново** | Опции imask (`showMaskOnFocus`, `showMaskOnHover`, `clearIncomplete`, `autoUnmask`, мультимаска массивом) не переносятся. Продуктовых потребителей нет — ломать нечего. |

Решения 1 и 2 вместе заметно увеличивают объём против минимального варианта: живой режим требует
безупречной каретки на каждом нажатии, а свой undo-стек — отдельной подсистемы со своим состоянием.

### Что ещё требует решения перед реализацией

- **Судьба `showMaskOnFocus`.** Опция удаляется, но стоящая за ней потребность («показать
  пользователю формат») остаётся. Варианты: визуальная подсказка отдельным слоем с `aria-hidden`
  (приём USWDS) или текст формата рядом с label. Первое ближе к текущему поведению, второе —
  к рекомендациям исследования.
- **Порядок работ.** Движок целиком одним заходом либо поэтапно (ядро + документные поля →
  телефон → карта).
