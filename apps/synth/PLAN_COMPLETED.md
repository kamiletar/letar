# PLAN_COMPLETED — synth

## Сессия 2026-07-29 (продолжение 16) — Вокальный тракт (начало Фазы 5)

### Что сделано

- **`src/lib/audio/voice-chain.ts`** (новый) — чистый граф вокального тракта:
  `input(трим) → highpass(рокот, фикс. 80Гц) → де-эссер(band-split: lowpass+highpass 5.5кГц,
компрессор только на высокой полосе, сумма обратно) → компрессор(threshold/ratio) →
EQ(low-shelf/peaking/high-shelf) → output`. `output` веткой уходит в `monitorGain → destination`
  (репетиция), `levelAnalyser` (индикатор), `reverbSendGain` (подключается снаружи к `convolver`
  мастер-шины — голос в той же «комнате», что инструмент) и `delaySendGain → delay → feedback-петля
→ delayOut → monitorGain` (эхо тоже слышно в наушниках). `applyVoiceChainParams` — живой твик
  без пересборки узлов, тот же приём, что `useMasterBus`/`buildBus`. Настоящий sidechain-EQ Web
  Audio нативно не даёт (нужен был бы AudioWorklet) — band-split компрессия достаточно честно
  ловит «с/ш», решил не усложнять до AudioWorklet ради MVP.
- **`src/lib/audio/level-meter.ts`** (новый) — `createLevelReader(analyser)`: переиспользуемый
  `Float32Array`-буфer (не аллоцируется каждый кадр), считает пик и RMS по `getFloatTimeDomainData`,
  флаг `clipping` при пике > 0.98.
- **`src/lib/audio/recorder.ts`** — новый класс `MixRecorder` рядом с `MasterRecorder`: принимает
  массив `AudioNode`-источников, каждый веткой подключается к общему
  `MediaStreamAudioDestinationNode` — Web Audio сам микширует, отдельной логики сложения не
  понадобилось. Нужен для записи «голос поверх бита» — раньше `MasterRecorder` умел только один
  источник.
- **`use-voice-chain.ts`** (новый хук, `app/_components/studio/`) — устройства (переиспользует
  `listAudioInputDevices` из `hardware-recorder.ts`), старт/стоп микрофона (`getUserMedia` с
  `echoCancellation`/`noiseSuppression`/`autoGainControl: false` — та же причина, что в
  `hardware-recorder.ts`/`external-audio-input.ts`: это голосовые фичи, портят вокал), параметры
  тракта (React state + `applyVoiceChainParams` на изменение), уровень через rAF-цикл
  (`createLevelReader`), запись комбинированного дубля (`MixRecorder` на `[masterBus.masterGain,
voiceOutput]`) — отдельная от инструментальной записи в шапке студии (`useRecording`), не мешают
  друг другу. Принимает `MasterBus | null` параметром — без запущенной студии (нет `convolver`)
  включить микрофон нельзя, явная ошибка вместо тихого поведения.
- **`voice-panel.tsx`** + **`level-meter-bar.tsx`** (новые UI) — по образцу
  `hardware-recording-panel.tsx`/`external-audio-input`: выбор микрофона → монитор вкл/выкл →
  секции «Компрессор» (2 нoба: порог/сила), «EQ» (3 ноба: низ/середина/верх), «Де-эссер»
  (тумблер + чувствительность), «Отправки и монитор» (реверб/эхо/громкость мониторинга),
  кнопка записи. Все ручки — `Knob` (тот же компонент, что у SUB/FM-панелей), подсказки —
  ear-first метафоры (компрессия — «рука, что сама придавливает крик и отпускает шёпот»,
  де-эссер — «та же рука, но глухая ко всему, кроме свиста»). `LevelMeterBar` — горизонтальная
  полоса: RMS-заливка + тонкая пиковая метка, красный цвет при `clipping`.
- **`studio-client.tsx`** — `useVoiceChain(masterBus.bus)` + рендер `VoicePanel` рядом с
  `HardwareRecordingPanel` (только когда `started`) — минимальная правка, вся логика в хуке.

### Технические детали

- Настройки вокального тракта (компрессор/EQ/де-эссер/sends) сознательно **не сохраняются** ни в
  патче, ни в `localStorage` — тот же прецедент, что `use-harmony.ts`: это инструмент момента
  сессии, не часть звучания патча. При перезагрузке страницы сбрасывается на дефолт (умеренный
  компрессор + плоский EQ + включённый де-эссер) — если понадобится persist, добавить по тому же
  паттерну, что `pad-midi-map.ts` (`localStorage`).
- Attack/release компрессора зафиксированы в дефолтах (5мс/150мс), не выведены в UI — решил не
  перегружать вокальную панель четырьмя ручками компрессора сразу; порог+сила достаточно для
  «выровнять громкость», тонкая настройка атаки/релиза — если владелец попросит после реальной
  проверки на голосе.
- Монитор голоса подключён к `ctx.destination` напрямую (не через `masterBus.panner`/HRTF) —
  голос слушателя не должен «летать» по комнате как инструмент, это разные роли сигнала.

  остальное почти неподвижно), «Минимал» (искры выключены, свечение приглушено — для сцены с
  голосом/текстом). Каждый пресет — множители на уже существующую реактивность, не новый
  рендер-движок: `rotationSpeed`/`orbitSpread`/`bassSensitivity`/`trebleSparkle`/`glowIntensity`/
  `ringSpeed`.
- **`SpinGraphCanvas`** — новый опциональный `sceneRef: RefObject<VjScene>` (тот же паттерн, что
  `patchRef`/`pulseRef`/`beatRef` — ref, не проп, чтобы переключение сцены не пересоздавало
  rAF-эффект). Внутри `draw()`: `bass = smoothBass * scene.params.bassSensitivity` заменил прямое
  использование `smoothBass` везде, где бас влияет на визуал (раздувание ядра, фоновое свечение,
  яркость обводки узлов); `rotationSpeed` масштабирует приращения `coreAngleA/B`/`outerAngle`
  целиком; `orbitSpread` масштабирует итоговый `orbitRadius`; `glowIntensity` домножает альфу
  фонового свечения; `trebleSparkle` домножает яркость искр и может выключить их полностью (порог
  `> 0`); `ringSpeed` масштабирует скорость расширения колец-метронома (Фаза 4, прошлая сессия).
  Без `sceneRef` (пропущен) используется `DEFAULT_VJ_SCENE` — поведение идентично сессии до этой
  вехи, обратная совместимость не ломается.
- **`VjOverlay`** — `sceneId`/`sceneRef` (state для подсветки активной кнопки + ref для чтения в
  канве), ряд из 5 кнопок в левом верхнем углу (`mood` каждой сцены — нативный `title`-tooltip, тот
  же паттерн, что и у `HarmonyPanel`/`theoryName`). Активная кнопка — золотая рамка/фон, тот же
  визуальный язык, что у переключателя движка SUB/FM/DRUM в шапке студии.

## Сессия 2026-07-29 (продолжение 14) — VJ: beat/tempo-синхронизация

### Что сделано

- **`use-drum-sequencer.ts`** — новая опция `onBeat?: (stepIndex: number) => void`, вызывается из
  `handleStep` на каждый 4-й 16-й шаг (`stepIndex % 4 === 0`) через тот же `setTimeout`-таймер
  визуальной синхронизации, что и `setCurrentStep` — независимо от того, набит ли на этом шаге
  реальный удар пэда.
- **`use-piano-roll.ts`** — та же опция `onBeat`, дёргается из уже существующего колбэка
  `onStepVisual`, который `MelodicSequencer.start()` вызывает на каждый шаг вне зависимости от
  наличия ноты — переиспользован без изменения сигнатуры `MelodicSequencer`.
- **`use-melodic-performance.ts`** — принимает `onBeat` и прокидывает в оба пиано-ролла
  (`subPianoRoll`/`fmPianoRoll`), чтобы VJ получал единый бит-сигнал независимо от активного
  движка (SUB/FM).
- **`studio-client.tsx`** — новый `vjBeatRef = useRef(0)` (тот же паттерн, что уже был у
  `vjPulseRef` — без `setState`, читается прямо в rAF-цикле графа) + `handleBeat`, подключённый
  и к `useDrumSequencer`, и к `useMelodicPerformance`. Проброшен в `VjOverlay` как `beatRef`.
- **`SpinGraphCanvas`** — новый опциональный проп `beatRef`. Внутри `draw()`: `beatRings` — список
  фаз (0..1) уже родившихся колец; на каждый новый бит (счётчик изменился с прошлого кадра)
  добавляется новое кольцо с фазой 0, все существующие продвигаются на `+0.02`/кадр и удаляются
  по достижении фазы 1. Рисуются как окружности вокруг центра с радиусом `phase * maxRingRadius`
  и убывающей по фазе непрозрачностью — расширяются от ядра к краю канвы и гаснут, визуально
  отличимы от локальной вспышки узлов на удар ноты/пэда (`pulseEnergy`/`pulseRef`), которая ярче,
  но не расширяется геометрически.

### Технические детали

- Осознанно не стал разруливать конфликт нескольких одновременно играющих секвенсоров с разным
  BPM (например, драм-кит на 120 и пиано-ролл SUB на 90 одновременно) — `vjBeatRef` это общий
  счётчик, инкрементируется от любого источника бита. Для типового сценария (играет один секвенсор
  за раз, остальные — тишина/ручная игра) это корректно; при одновременной игре нескольких темпов
  кольца будут рождаться от обоих источников вперемешку — не тестировался и не является багом,
  честный побочный эффект простой модели «любой бит рождает кольцо».
- `beatRings` — обычный `let`-массив в замыкании `useEffect`, не `useState` — та же причина, что и
  у `pulseEnergy`/`coreAngleA` рядом: состояние анимации живёт внутри rAF-цикла, не в React-рендере.

## Сессия 2026-07-29 (продолжение 13) — VJ: реактивность к патчу/пульсу + внешний аудиовход

### Что сделано

- **`SpinGraphCanvas`** — новые опциональные пропсы `patchRef: RefObject<SubtractivePatch>` и
  `pulseRef: RefObject<number>`. Внутри `draw()`:
  - `azimuth`/`depth` из `patch.engine.fx.space` (уже реально управляют HRTF-панорамой звука в
    `use-master-bus.ts`) поворачивают орбиту 6 узлов (`azimuthOffset`) и сжимают её радиус
    (`depthScale = 1 - depth * 0.25`) — та же ручка одновременно двигает звук и картинку.
  - `cutoff`/`resonance` из `patch.engine.filter` подмешиваются в яркость рёбер и скорость
    вращения ядра соответственно.
  - `pulseRef` — счётчик, сравнивается с прошлым кадром (`lastPulseSeen`); при изменении
    `pulseEnergy` мгновенно прыгает (клип до 1.6), дальше экспоненциально затухает
    (`pulseEnergy *= 0.88` каждый кадр) — даёт резкую вспышку радиуса узлов/ядра/фонового свечения
    синхронно с атакой ноты, раньше, чем аудио-анализатор успеет её увидеть через FFT.
  - Все новые входы опциональны (`?:`) с безопасными дефолтами (`?? 0`/`?? 0.5`) — компонент
    остаётся рабочим и без патча/пульса (например, если понадобится использовать граф отдельно
    от студии).
- **`studio-client.tsx`** — `vjPulseRef = useRef(0)`, инкремент в `soundNoteOn` (SUB/FM-ноты) и
  `handlePadHit` (драм-удары) — **без** `setState`, чтобы не плодить лишние ре-рендеры студии на
  каждый удар (граф читает `.current` сам в своём `requestAnimationFrame`-цикле). `patchRef`
  (уже существовавший ref для аудио-коллбэков) и `vjPulseRef` прокинуты в `VjOverlay`.
- **`src/lib/audio/external-audio-input.ts`** (новый) — `ExternalAudioInput`: обёртка над
  `getUserMedia` (echoCancellation/noiseSuppression/autoGainControl явно выключены, как в
  `hardware-recorder.ts` — это голосовые фичи, портят музыкальный сигнал) →
  `MediaStreamAudioSourceNode` → собственный `AnalyserNode`, который **никуда дальше не
  подключается** — не пишет на диск и не подмешивает чужой звук в наши колонки (в отличие от
  `HardwareRecorder`, у которого есть выход в файл). Реэкспортирует `listAudioInputDevices` и тип
  `AudioInputDevice` из `hardware-recorder.ts` — не дублирует список устройств.
- **`use-external-audio-input.ts`** (новый хук, в `vj/`) — devices/selectedDeviceId/active/error,
  `refreshDevices`/`toggle`; `analyser` вычисляется на каждый рендер из `inputRef.current` (ref, не
  state — но `setActive` уже триггерит нужный ре-рендер, когда analyser появляется/пропадает).
- **`VjOverlay`** — UI повторяет уже устоявшийся в приложении двухшаговый паттерн выбора
  устройства (как `HardwareRecordingPanel`): кнопка «🎤 внешний вход» (пока список пуст) →
  `<select>` + «● подключить/отключить вход» (когда список получен). Активный источник для
  `SpinGraphCanvas` переключается (`external.active ? external.analyser : analyser`) — своя студия
  по умолчанию, внешний вход по явному выбору.

### Технические детали

- Точность note-on/off для SUB/FM в обоих новых модулях **не sample-accurate** (в отличие от
  драм-триггеров, которые планируют огибающую на аудио-часах через

  текущего момента до аудио-времени шага. Тот же компромисс, на который уже пошёл FM-движок
  (управление через `postMessage` в AudioWorklet, тоже не sample-accurate). Для мелодических нот
  с собственной ADSR-атакой погрешность (доли периода lookahead, ~100мс) не слышна — в отличие от
  драм-транзиента, где она была бы заметна. Явно задокументировано в коде обоих модулей.
- Пиано-ролл и арпеджиатор — независимые системы, оба вызывают общие `soundNoteOn`/`soundNoteOff`;

  явно edge-case, оставлен как есть ради простоты.
- Диапазон строк пиано-ролла (2 октавы от C2, MIDI 36-59) продублирован из констант `keyboard.tsx`
  вручную (те не экспортированы) — если диапазон виртуальной клавиатуры изменится, надо поправить

  индекс ≥ i, кроме ровно одного feedback-ребра, которое естественно берёт значение операторов
  предыдущего сэмпла — без zero-delay петель). Feedback применяется к `alg.fbOp` вместо
  захардкоженного `op0`.
- **`src/lib/patch/dx7-sysex.ts`** — `encodeSingleVoiceSysex`/`decodeVoiceParams`/`decodePackedVoice`
  читают/пишут feedback-байт в/из `operators[fbOp]` текущего алгоритма (`getAlgorithm().fbOp`) вместо
  хардкода `operators[0]` — критично для интеропа с реальным железом, где feedback не всегда на
  первом операторе.
- **`src/app/_components/studio/fm-panel.tsx`** — кнопки алгоритма 1-32 (было 5), описание схемы
  через `describeAlgorithm()`, feedback-ручка (`OpCard.isFeedbackOp`) показывается на правильном
  операторе для текущего алгоритма вместо жёсткого `index === 0`.
- **`src/lib/patch/fm-defaults.ts`** — `FM_BASS` (алгоритм 1) и `FM_GLASS_BELLS` (алгоритм 2)
  перестроены под настоящую топологию (два независимых пути на несущую вместо старых
  приближений): feedback перенесён с op0 на реальный `fbOp` каждого алгоритма (op5 и op1
  соответственно).
- **Тесты:** `dx7-algorithms.spec.ts` (новый) — структурные инварианты всех 32 алгоритмов (ровно
  одно обратное ребро, совпадающее с `fbOp`), `getAlgorithm`/`describeAlgorithm` на граничных
  случаях. `dx7-sysex.spec.ts` — feedback round-trip проверяется на `fbOp` текущего алгоритма
  вместо хардкода `i === 0`.

### Технические детали

- Ключевое упрощение движка: поскольку DX7 конструирует все 32 алгоритма так, что модулятор
  оператора i всегда имеет индекс ≥ i (кроме единственного feedback-ребра), фиксированный порядок
  обработки `6→1` без топологической сортировки корректен универсально — раньше под каждый из 5
  алгоритмов-приближений явно вычислялся свой `order`.
- Проверено вручную вне юнит-тестов: отдельный Node-скрипт прогнал ноту через `Voice.tick()` для
  всех 32 алгоритмов (feedback=5 на `fbOp` каждого) — конечный, не клиппингующий, не тихий сигнал

## Сессия 2026-07-28 (продолжение 2) — Детерминированный WAV-рендер (OfflineAudioContext)

### Что сделано

- **`src/lib/audio/render.ts`** (новый) — `renderPatchToWav(patch)`: строит ту же мастер-шину (сухой + reverb-send), что и живая студия, но целиком внутри `OfflineAudioContext`, прогоняет через неё нужный движок и кодирует результат в WAV (PCM 16-bit) без сторонних зависимостей.
  - SUB/FM: одна нота (C3) держится 2с + release движка + хвост реверба, затем офлайн-рендер.
  - DRUM: проигрывает по очереди все непустые пэды кита с шагом 180мс — демо-«прогон» кита одним файлом.
- Типы движков (`SubtractiveEngine`, `DrumEngine`, `FmEngine`, `buildReverbIR`) ослаблены с `AudioContext` до `BaseAudioContext` — им реально нужны только методы `createOscillator`/`createGain`/`createBiquadFilter`/`createBufferSource`/`currentTime`/`audioWorklet`, которые есть и в `OfflineAudioContext`. Без этого рендер не собрался бы по типам.
- Кнопка «⇄ рендер WAV» в шапке студии (`studio-client.tsx`) рядом с записью; после рендера — ссылка «↓ скачать .wav».

### Технические детали / грабли

- **Дедлок suspend/startRendering**: `OfflineAudioContext.suspend(t)` возвращает promise, который разрешается только когда рендер реально дойдёт до момента `t` — а рендер запускается исключительно `startRendering()`. Первая версия кода делала `await ctx.suspend(t).then(...)` **до** `ctx.startRendering()` — гарантированный дедлок (зависшая кнопка «рендер» навечно). Починено: `suspend()` планируется без ожидания, `startRendering()` вызывается сразу же, и только потом дожидаемся promise от `suspend()`.
- **Тишина в FM-рендере**: `FmEngine` управляется через `postMessage` в `AudioWorkletNode` (`'patch'`/`'noteOn'`). `OfflineAudioContext` рендерит «на максимальной скорости» без пауз реального времени — сообщения иногда не успевали доехать до воркслета раньше, чем рендер стартовал и закончился, итог — валидный WAV с полной тишиной (`maxAbsSample: 0`). Починено явным `await` на 50мс между отправкой сообщений движку и вызовом `startRendering()`. SUB и DRUM (прямое управление узлами, без воркслета/сообщений) этой проблеме не подвержены.
- Проверено вручную в превью для всех трёх типов движков — извлечён реальный WAV из blob-ссылки, побайтово проверен RIFF-заголовок и пиковые сэмплы: SUB `maxAbsSample: 29983`, FM `12408`, DRUM `19732` (не тишина, не клиппинг). `nx lint synth` + `nx typecheck:tsgo synth` чисто.

- **Найдено (важный техдолг):** наш `fm-processor.js` реализует только 5 собственных алгоритмов-приближений вместо всех 32 настоящих топологий DX7 (точные графы модуляции + per-алгоритм feedback найдены в `Dexed/Source/AlgoDisplay.cpp`, но не перенесены). Согласовано с владельцем: сначала SysEx-инфраструктура, точность алгоритмов — отдельным шагом.
- **`src/lib/patch/dx7-sysex.ts`** (новый) — `encodeSingleVoiceSysex`/`decodeSingleVoiceSysex` (155-параметровый unpacked single-voice dump, F0 43 0n 00 01 1B...F7) и `decodeBulkDump` (32-голосый packed bulk dump, F0 43 0n 09 20 00...F7). Общий checksum-helper (masked two's complement). Известные лоссовые поля (keyboard scaling, rate scaling, amp mod sensitivity, oscillator detune/key sync, LFO sync, pitch mod sensitivity, transpose) задокументированы прямо в коде — используются DX7-дефолты при кодировании, отбрасываются при декодировании.
- **`src/lib/patch/__fixtures__/`** (новый) — реальный банк пресетов SMK-37 (`smk37-pro-presets-1.syx`, Apache-2.0, атрибуция в README) как эталонная тестовая fixture.
- **`src/lib/patch/dx7-sysex.spec.ts`** (новый) — round-trip тесты на `FM_BASS`/`FM_GLASS_BELLS` + разбор реального заводского банка (32 голоса, включая точное имя последнего голоса `E.GUITAR 1`, проверенное побайтово по hex-дампу).
- **`apps/synth/tsconfig.spec.json`** (новый) + reference из `tsconfig.json` — первые тесты в synth потребовали тиражирования fix'а для vitest+vite8/oxc (см. `.claude/docs/unit-testing.md`).

### Технические детали

- Наш `operators[0..5]` = DX7 `OP1..OP6`; в байтовом потоке DX7 хранит операторы в обратном порядке (OP6 первым) — конвертер учитывает это при кодировании/декодировании.
- Feedback в реальном DX7 — один глобальный параметр (не per-оператор, как в нашей схеме); используется/восстанавливается только на `operators[0]`, что соответствует тому, как `fm-processor.js` фактически применяет feedback (только к op0).
- Ratio↔coarse/fine — стандартное линейное приближение (`ratio = coarse' × (1 + fine/100)`), используемое большинством DX7-клонов; не 100% идентично оригинальной нелинейной таблице Yamaha, но достаточно для музыкального использования.
- Поле `algorithm` — сквозной проход байта без валидации/маппинга топологии (осознанное упрощение, см. техдолг в PLAN.md).

- FM движок lazy: создаётся только при первом нажатии кнопки FM, а не при старте аудио.
- Voice stealing: самый старый голос (по `startTime` — монотонный счётчик сэмплов).
