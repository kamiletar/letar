## Overview

Relation fields automatically load options from related database models. Powered by `RelationFieldProvider` and ZenStack's `form.relation` directive.

## Schema Setup

```prisma
model Recipe {
  categoryId String @meta("form.title", "Category") @meta("form.relation.labelField", "name")

  category Category @relation(fields: [categoryId], references: [id])
}
```

⛔ `@meta("form.relation", { labelField: "name" })` with an object literal breaks
`zenstack generate` entirely (`Unsupported attribute arg value: ObjectExpr`) — always use the
flat dot-path form shown above, one `@meta` call per key.

## RelationFieldProvider

Wrap your form to provide relation data:

```tsx
import { RelationFieldProvider } from '@letar/forms'

;<RelationFieldProvider
  relations={[{ model: 'Category', useQuery: useFindManyCategory, labelField: 'name' }]}
>
  <Form schema={RecipeCreateFormSchema} onSubmit={save}>
    <Form.Field.String name="title" />
    <Form.Field.Select name="categoryId" />
    <Form.Button.Submit>Save</Form.Button.Submit>
  </Form>
</RelationFieldProvider>
```

## Relations from the schema: useZenStackRelations

Writing `relations` by hand means one `useFindMany` adapter per model. With ZenStack, `useZenStackRelations` from
`@letar/forms-query/zenstack` builds the list from the form schema itself: it walks the fields that have
`fieldProps.relation` and takes `useFindMany` of the model from the ZenStack schema.

```tsx
import { schema } from '@/generated/schema'
import { useZenStackRelations } from '@letar/forms-query/zenstack'

// Outside the component: a literal in JSX would rebuild the array on every render
const overrides = { Category: { queryArgs: { orderBy: { name: 'asc' } }, descriptionField: 'note' } }

function RecipeForm() {
  const relations = useZenStackRelations(schema, RecipeCreateFormSchema, { overrides })

  return (
    <RelationFieldProvider relations={relations}>
      <Form schema={RecipeCreateFormSchema} onSubmit={save}>
        <Form.AutoFields />
      </Form>
    </RelationFieldProvider>
  )
}
```

- One model used by several fields is loaded once.
- Fields with a `createForm` registry key (`Select.Category`) are skipped: that component loads its own data.
- A model missing from the ZenStack schema throws with the list of available models.
- Two fields asking for different `labelField` of the same model: the first wins and a warning is printed — set the
  label in `overrides`.
- The third argument takes `overrides`, `exclude` and `clientOptions` (the second argument of `useClientQueries`).

## Second option line: descriptionField

`descriptionField` is the record field that `Select` and `Combobox` (Chakra and shadcn) draw as a **second line under
the label in the dropdown list**. The trigger and the input after a pick keep the label only. Set it in the schema,
no field code:

```prisma
categoryId String @meta("form.relation.labelField", "name") @meta("form.relation.descriptionField", "note")
```

`descriptionField` in `RelationConfig` (or in `overrides` of `useZenStackRelations`) wins over the schema. An empty
value means no second line. The local search also matches the description; `searchInDescription={false}` on the field
turns that off. Live example: `/relation-demo` in `form-develop-app`.

## useRelationOptions Hook

Access relation options from custom components:

```tsx
const { options, isLoading } = useRelationOptions('category')
```

## withRelations HOC

Alternative to wrapping with RelationFieldProvider:

```tsx
const RecipeForm = withRelations(BaseRecipeForm, {
  category: { useQuery: useFindManyCategory, labelField: 'name' },
})
```
