## Когда использовать

[Гайд про свой UIKit](/docs/guides/custom-uikit) — о рестайлинге внутри React. Этот гайд — про
шаг покрупнее: перенос логики сборки полей на *другой* фреймворк целиком. `@letar/forms-vue` и
`@letar/forms-vue-shadcn` — реальный, отгруженный результат такого переноса, и это честный рассказ
о его создании, не причёсанный референс постфактум. Читайте, если оцениваете, насколько такой же
шаг реалистичен для Svelte, Solid или чего угодно ещё.

## Где это реально проверяется

`@letar/forms-core` заявляет себя framework-agnostic: ни одного импорта React внутри, обобщённый
`TNode` вместо «что бы ни рендерил ваш фреймворк». Такое заявление легко написать и легко оставить
непроверенным — «framework-agnostic ядро», которое ни разу не запускалось под вторым фреймворком,
это гипотеза, не факт.

Портирование на Vue и было этой проверкой. Результат: **ноль изменений в `forms-core`.**
`getFieldMeta()` (чтение meta схемы) и типовой контракт `UIKit<TNode>` заработали из Vue без
единой модификации — то, что `TNode` обобщённый (не захардкожен на `ReactNode`), позволило
подставить туда Vue `VNode`, и ничего не сломалось. Если бы портирование потребовало хоть
однострочной правки `forms-core` — это была бы главная находка всей задачи, а не сноска: шов,
который держится только для того фреймворка, под который его строили, — не шов.

## Что приходится строить заново, а что нет

| Слой | React (`forms-react`/`forms-shadcn`) | Vue (`forms-vue`/`forms-vue-shadcn`) |
| --- | --- | --- |
| `forms-core` (схема, meta, валидаторы, i18n) | общий | **не изменился, переиспользован как есть** |
| Контракт `UIKit<TNode>` (`forms-core/uikit/types.ts`) | общий | **не изменился, переиспользован как есть** |
| Реализация UIKit (Chakra/shadcn vs Reka UI) | специфична фреймворку | построена заново — другая библиотека компонентов, другие пропы |
| Композиционный слой `createField`/`createFieldPrimitives` | React-хуки + JSX | построен заново — Composition API, другая идиома (см. ниже) |
| Отдельные поля (`FieldString`, `FieldSelect`, ...) | React-компоненты | построены заново — та же форма, новый синтаксис |

Два слоя переносятся без изменений, два — нет. Это соотношение и есть настоящий ответ на вопрос
«насколько это порт» — не «всё» и не «только стилизация».

## Решения, не очевидные заранее

### `defineComponent` + `h()`, не `.vue` однофайловые компоненты

Идиоматичный формат авторства в Vue — `.vue`-файлы с `<script setup>`. Мы их не использовали.
TypeScript-тулинг репозитория (`tsc --build` / `tsgo`) типизирует `.ts`-файлы напрямую; `.vue`
требует `vue-tsc` — отдельный тулчейн, которого в монорепо ещё не было. Написание компонентов как
`defineComponent({ setup() { return () => h(...) } })` в обычных `.ts`-файлах позволило проверять
каждый Vue-компонент той же командой, что и всё остальное. Компромисс реальный — render-функции
многословнее шаблонов — и его стоит называть прямо, а не подавать «только `.ts`» как единственно
верный способ.

### Примитивы UIKit как обычные функции, не Vue-компоненты

Тип контракта — `FieldRoot: (props: UIKitFieldRootProps<TNode>) => TNode` — обычная сигнатура
функции. В React функциональный компонент — это буквально такая сигнатура, поэтому примитивы
`forms-shadcn` — просто функции. Vue не требует того же соответствия — примитивы могли быть
обёртками `defineComponent` — но написание их как обычных функций `(props) => VNode` оказалось
буквальнее удовлетворяющим контракту и избавило от границы инстанса компонента вокруг каждого
вызова примитива. Это стало видно только тогда, когда реальная форма контракта (не «UIKit-компонент
`Select`», а буквально «функция») была воспринята всерьёз.

### Одна морщина со строками/VNode: `TNode` не совсем бесплатен в Vue

React-овский `ReactNode` включает `string` — проп типа `label?: ReactNode` спокойно принимает
обычную строку. Тип `VNode` в Vue — нет. Инстанцирование контракта как
`UIKitCorePrimitives<VNode>` сломалось в тот момент, когда поле передало строковую метку напрямую.
Фикс — маленький локальный тип `UINode = VNode | string | null`, используемый везде, где `TNode`
контракта проходит через Vue-скин. Это не изменение `forms-core` — обобщённый `TNode` контракта и
так допускал любой тип; это деталь Vue-скина — *какой именно* тип подставить.

### Error boundary: `onErrorCaptured`, не классовый компонент

Error boundary поля в React (`FieldErrorBoundary` в `forms-react`) — классовый компонент:
`getDerivedStateFromError`/`componentDidCatch` — паттерн, специфичный только React, копировать
в Vue было не с чего. У Vue свой механизм — `onErrorCaptured`, вызываемый внутри `setup()`
компонента. Перенести это 1:1 было невозможно, и это не было целью — *поведение* (сломанное поле
рисует fallback вместо краша всей формы) перенеслось; *механизм* — нет, потому что не мог.

### `FieldSelect`/`FieldCombobox` обходят фабрику поля

У `createField()` (и React-, и Vue-версии) фиксированный контракт пропов: `name`/`label`/
`placeholder`. Поля, которым нужен дополнительный проп — `options`, для `Select`/`Combobox` — в
эту фабрику не помещаются. В React это решается через параметр обобщённого типа у `createField<P>`.
В Vue более простым и идиоматичным фиксом оказалось пропустить фабрику для этих двух полей и
собрать `useAppFormContext()` + `form.Field` напрямую — тем же паттерном, что использует сама
фабрика внутри. Ни один вариант не «более правильный» — суть в том, что механическое копирование
React-решения (борьба с системой типов Vue ради параметра обобщённого типа) вышло бы хуже, чем
просто признать, что фабрика покрывает не все случаи, и обойти это.

## Тестирование через границу фреймворков

Radix (React) и Reka UI (Vue, те же примитивы, перенесённые на Vue мейнтейнерами Reka) оба
позиционируют выпадающие списки через `ResizeObserver` и логику позиционирования floating-UI,
которых jsdom не реализует. Под Vitest + `@vue/test-utils` тесты `Select`/`Combobox` требуют
заглушек `ResizeObserver`, `Element.prototype.hasPointerCapture`,
`Element.prototype.scrollIntoView` перед монтированием — стандартное требование для тестирования
компонентов семейства Radix вне настоящего браузера, не специфика этого переноса. Если портируете
на фреймворк, чья библиотека компонентов оборачивает эквивалент Radix/Reka-примитивов —
ожидайте тех же заглушек.

## Чего этот гайд не покрывает

Этот гайд — про перенос UI-скина (Vue + headless-слой сборки полей). Он не покрывает: перенос
управления состоянием целого приложения, портирование на фреймворк с принципиально другой моделью
реактивности (fine-grained сигналы vs. proxy-реактивность Vue vs. модель React
«перерисовать всё дерево» — шов держится именно для модели Vue, не доказан для других), и
достижение паритета по полям (`forms-vue-shadcn` поставляет 6 из 61 поля, которые есть в
Chakra-скине — см. раздел «Что не входит в скоуп» в его README, что именно это за граница и почему).
