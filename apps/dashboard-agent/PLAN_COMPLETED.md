## Версия 0.15.1 → 0.15.2 — миграция acme-dns-backup/nginx-backup на tar-backup.ts (2026-08-08)

Продолжение работы из 0.15.0 (см. запись ниже) — там `tar-backup.ts` был вынесен, но старые
`acme-dns-backup.ts`/`nginx-backup.ts` сознательно оставлены немигрированными «до появления
тестов». Тесты появились в том же 0.15.0 (`tar-backup.spec.ts`), поэтому миграция стала
безопасной и выполнена следующей сессией.

Оба файла переписаны на `createTarBackup`/`listTarBackups`. Публичный API не менялся —
`backupAcmeDns`/`getAcmeDnsBackupsList` и `backupNginx`/`getNginxBackupsList` остались теми же
функциями с теми же сигнатурами, роуты (`routes/acme-dns.ts`, `routes/nginx.ts`) и cron-задачи
не трогались.

`nginx-backup.ts` не мог полностью уйти на дефолтный архиватор общего модуля — старый код
исключал из архива `*/nginx/ipfs-cache` и `*/nginx/proxy_host/*/access.log` через `tar
--exclude`, а `tar-backup.ts` таких флагов не поддерживает и не должен (это специфика именно
NPM). Решено через существующий шов `TarBackupOptions.archive` — кастомная функция упаковки
передаётся как есть, вся остальная механика (проверка источников, права 600, ротация, список)
идёт через общий модуль.

Унаследованный дефект (`spawn('mkdir', …)` без обработки ошибки запуска процесса — при `ENOENT`
промис не резолвился никогда, бэкап не падал, а зависал) устранён на обоих файлах вместе с
переходом на общий модуль.

`nx typecheck`/`lint`/`test`/`format` — зелёные. Задеплоено на s2 (BlackCove, коммит `d2a0ba6b`).
Обе ручные проверки подтверждены живьём:

```
POST /api/acme-dns/backup → 200 {"success":true,"file":"acme-dns_auto_2026-08-08-22-34-02.tar.gz","size":2212}
POST /api/nginx/backup    → 200 {"success":true,"file":"nginx_auto_2026-08-08-22-34-02.tar.gz","size":17070379}
```

Оба файла на диске — `rw-------` (600). Побочно замечено (не регресс): `nginx_auto_*` лежит
плоско в `backups/`, а не в `backups/nginx/`, как `acme-dns` — так было и раньше, у nginx
исторически нет подпапки.

## Версия 0.14.0 → 0.15.1 — бэкап секретов Traefik на s3 + хотфикс старта без Redis (2026-08-08)

Работа пришла из инфра-трека `PLAN-INFRA.md` §48 M2 (остановка NPM на s3). Ни одна из двух задач
не планировалась заранее — обе вскрылись по ходу.

### 1. Бэкап секретов Traefik на s3 (0.15.0)

**Пробел создан самим переездом, а не забывчивостью.** До M2 утверждение «на s3 бэкапить нечего —
там нет прод-БД» было верным и записано в `backup-architecture.md`. После M2 на s3 появились три
per-name аккаунта acme-dns (`media`/`ipfs`/`gateway`), `acme.json` с ключами всех сертификатов и
`basicAuth` дашборда.

⛔ Первый источник **невосстановим без владельца**: регистрация в acme-dns закрыта, новый аккаунт
выдал бы новые `fulldomain` и потребовал бы вручную переделать три `CNAME` у регистратора. То есть
восстановление упирается и в человека, и во внешний сервис одновременно.

Добавлено: `lib/traefik-backup.ts`, `routes/traefik.ts`, отдельная цель проверки свежести
(`traefikTarget()`), две cron-задачи с `server: 's3'`, монтирование `/home/deploy/lego` в
`docker-compose.s3.yml`.

**Почему отдельная цель проверки, а не расширение `acmeDnsTarget()`:** это другой сервер. Общая
проверка дала бы ложное «свежо» — архив на s2 закрывал бы отсутствие архива на s3.

### 2. `lib/tar-backup.ts` — вынос общей механики (0.15.0)

В агенте уже лежали две почти идентичные реализации tar-бэкапа (`acme-dns-backup.ts`,
`nginx-backup.ts`), **обе без единого теста**. Третья копия превратила бы совпадение в систему.

Общая часть вынесена и покрыта тестами; сохранены оба инварианта — «отсутствие любого источника
даёт ошибку, а не неполный архив» и права `600` на архиве с секретами.

⚠️ **Две старые реализации пока НЕ мигрированы.** Переписывать работающие прод-бэкапы без тестов
на их текущее поведение опаснее временного дублирования. Тесты `tar-backup.spec.ts` — как раз то
условие, при котором миграция станет безопасной.

**Тесты сразу окупились** — нашли унаследованный дефект: каталог создавался через
`spawn('mkdir', …)`, а ошибка **запуска процесса** не обрабатывалась вовсе (висел только
`mkdir.on('close')`). При `ENOENT` промис не резолвился никогда — бэкап не падал, а молча зависал.
На Linux `mkdir` всегда есть, поэтому в проде не стреляло. В новом модуле починено, в двух старых
остаётся до миграции.

Побочно: тесты стали в ~50 раз быстрее (20с → 0.4с) — архиватор сделан внедряемым, потому что
`tar` это внешняя платформенная зависимость, а вся содержательная логика от способа упаковки не
зависит.

### 3. Хотфикс 0.15.1 — недоступный Redis ронял агента на старте

0.15.0 ушёл в crash loop на s3. **Причина не в 0.15.0:** `routes/deploy.ts:262` делал
`await rehydrateFromRedis()` при регистрации плагина. При недоступном Redis команда не падает — у
ioredis `enableOfflineQueue: true` по умолчанию, команда уходит в очередь до подключения, а
`retryStrategy` в `@letar/redis-client` переподключается бесконечно. `await` не завершался никогда
→ Fastify убивал плагин по 10-секундному таймауту (`AVV_ERR_PLUGIN_EXEC_TIMEOUT`).

⚠️ **`try/catch` от такого не защищает** — исключения не происходит вовсе, происходит зависание.
Поэтому обещанная библиотекой graceful degradation на старте не работала: не «работаем без Redis»,
а смерть приложения.

Добавлен `lib/with-timeout.ts` с тестами; восстановление истории ограничено 3 секундами.

**Правило шире случая:** сетевой вызов на пути старта приложения обязан иметь границу по времени.
Без неё любая внешняя зависимость получает право не пустить сервис подняться — включая
необязательную, без которой он спроектирован работать.

**Почему вскрылось только сейчас:** s3-инстанс стоял на версии двухнедельной давности — он не
передеплоивался при бампах на s2. Отсюда отдельный вывод: **редко обновляемая инстанция копит не
«отставание», а непроверенные пути.**

### Не закрыто

- `enableOfflineQueue: false` в `libs/redis-client` — корневой фикс, но меняет поведение всех
  потребителей, включая хранилище сессий `@letar/auth`. Отдельное решение, не хотфикс.
- Миграция `acme-dns-backup.ts`/`nginx-backup.ts` на `tar-backup.ts` (вместе с их дефектом `mkdir`).
- `deploy-affected.sh` не знает про `docker-compose.s3.yml` — до починки агент на s3 деплоится
  только вручную (`PLAN-INFRA.md` §66).

## Версия 0.13.0 → 0.14.0 — аудит health-check.ts/log-scan.ts на дефект класса §62 (2026-08-08)

Целевой аудит по итогам починки email-канарейки (§62) и `backup-freshness.ts` (0.13.0, параллельная
сессия): оба файла зовут `postDashboardAlert()`, но грепом по слову `alerted` — чистые, значит
используют другой механизм дедупликации. Нужно было проверить, не тот же ли это класс бага.

### Что нашли

Тот же класс дефекта в обоих файлах, но не идентичный прежним — сама схема дедупликации в
`health-check.ts` в отличие от старой email-canary и от `backup-freshness.ts` **не
"замолкает навсегда"**: она level-triggered/edge-triggered и сама сбрасывается при выздоровлении
метрики/контейнера/БД (см. комментарий в `lib/json-state-file.ts`, который уже описывал эту
разницу). Реальный дефект был уже, но того же типа:

- **`health-check.ts` — все три механизма** (`checkMetricThresholds`, `checkContainers`,
  `checkDatabases`) вызывали `postDashboardAlert()` без проверки boolean-возврата и продвигали
  состояние дедупа безусловно. Если конкретная попытка доставки не удавалась, состояние всё равно
  помечалось «уже уведомили» — и до следующего перехода (метрика упала ниже порога и снова выросла,
  контейнер снова стал running и снова упал) повтора не было. Не «молчание навсегда», а «одна
  потерянная попытка на эпизод остаётся потерянной».
- **`log-scan.ts`** — курсор `lastSeenAt` продвигался до конца новых строк независимо от исхода
  `postDashboardAlert()`. Недоставленный алерт об ошибках терял эти конкретные строки навсегда:
  курсор уже ушёл вперёд, при следующем сканировании они не считаются «новыми».
- **`CONTAINER_RESTARTED`** — единственный механизм без дедупа вообще (алертит каждый прогон, пока
  `restarting`), поэтому недоставленная попытка и так повторяется на следующем прогоне без правок.

### Что сделано

Точечный фикс под каждый механизм — состояние/курсор продвигается только при `delivered === true`
(возврат `postDashboardAlert()`), без изменения самой логики "когда алертить" и без переноса
общего `shouldRepeatAlert` из `lib/alert-policy.ts` (0.13.0): та формула — счётчик подряд-неудач с
удвоением порога — рассчитана на другую форму дедупа (email-canary/backup-freshness), а не на
level-triggered/edge-triggered механизмы `health-check.ts`. Перенос сюда добавил бы сложность,
которую документированный design decision в `json-state-file.ts` уже отклонял для четвёртой
cron-проверки.

Тесты — `health-check.spec.ts` (12 кейсов) и `log-scan.spec.ts` (4 кейса), новые файлы: раньше
покрытия у этих модулей не было вовсе. Подробности фикса — `CHANGELOG.md` 0.14.0.

## Версия 0.12.0 → 0.13.0 — та же тишина алертов, перенесённая в проверку свежести бэкапов (2026-08-08)

Прямое следствие починки email-канарейки (версия 0.11.2 → 0.12.0 ниже, §62 `PLAN-INFRA.md`):
один из системных выводов той сессии — в `backup-freshness.ts` (Maddy + acme-dns) была
ровно та же пара дефектов в канале оповещения, только замеченная заранее, а не по факту
17-дневного инцидента.

### Что было не так

- **Алерт уходил ровно один раз и замолкал навсегда.** `runFreshnessCheck` читал плоский
  `{ alerted: boolean }`, взводил его при первом обнаружении и не сбрасывал, пока не появится
  свежий файл — даже если бэкап продолжал стареть дальше эпизод за эпизодом.
- **Факт вызова `postDashboardAlert` не отличался от факта доставки.** Состояние писало
  «уже алертили» независимо от того, принял ли dashboard алерт.

### Что сделано

- Общая **формула** повтора вынесена из `email-canary.ts` в `lib/alert-policy.ts`
  (`shouldRepeatAlert` + `defaultAlertRepeatState`) — используется обоими модулями. Вынос
  сознательно узкий: только чистая функция принятия решения «слать ли алерт», а не
  персистентность или структура состояния — оценка 2026-07-30 против единого
  `runDebouncedCheck<TState>` (комментарий в `lib/json-state-file.ts`) не пересматривалась,
  остаётся в силе для `health-check.ts` (edge-triggered переходы контейнеров туда не ложатся).
- `FreshnessState` заменён с `{ alerted: boolean }` на `{ consecutiveFailures, alertedAtFailures,
  lastAlertDelivered }` — тот же набор полей, что у ноги email-канарейки. Порог первого алерта
  оставлен `1` (алертить сразу, как было раньше) — проверка и так гоняется раз в 6 часов, а не
  раз в час; дальше — удвоение (1, 2, 4, 8… подряд-неудач).
- `loadJsonState` мержится с дефолтом (`{ ...defaultFreshnessState(), ...loadJsonState(...) }`),
  а не подставляется как есть — на диске может лежать состояние старой формы без новых полей,
  тот же приём, что уже был в `email-canary.ts` при аналогичной миграции.
- Тесты: `alert-policy.spec.ts` (5, формула в отрыве от потребителя) + расширенный
  `backup-freshness.spec.ts` (удвоение, ретрай недоставленного алерта, слияние старой формы
  состояния — по образцу `email-canary.spec.ts`).

## Версия 0.11.2 → 0.12.0 — email-канарейка была красной 17 дней, и никто не узнал (2026-08-08, BlueCliff)

Коммиты `15563ca5`, `6359344c`. Полный разбор инцидента — `PLAN-INFRA.md` §62.

### Что оказалось сломано

Задача ставилась как диагностика: различить «почта не работает две недели» и «сломан датчик».
Ответ — **датчик**. Почта работала всё это время; красными были два независимых дефекта самой
канарейки, и оба остались незамеченными из-за третьего — неработающего канала оповещения.

**1. External-нога не была зелёной ни разу с рождения.** 1682 неудачи — это все прогоны с 22.07.
Gmail исправно принимал письма и клал их в спам: 1684 письма в папке «Спам», ноль во входящих.
Искали только в INBOX. Причина спама тоже нашлась: внешний получатель приходил скрытой копией,
и отсутствие его адреса в `To:`/`Cc:` при теме, повторяющейся каждые 15 минут, — готовый признак
для фильтра.

**2. Internal-нога задохнулась в собственном мусоре** (сломалась 02.08 после 11 дней зелёного).
Старый код на каждой итерации опроса тянул `fetch({ seen: false })` — конверты **всех**
непрочитанных писем ящика — и перебирал их на клиенте. Ящик рос на 96 писем в сутки и не чистился
ничем; к 2 августа ~1050 писем перестали укладываться в 90-секундный таймаут.

**3. Канал оповещения молчал по двум независимым причинам.** Булев `alerted` взводился при первом
пересечении порога и сбрасывался только успехом, которого не было, — то есть алерт уходил ровно
один раз за всю историю. А `postDashboardAlert` глотал ошибку и возвращал `void`, поэтому даже
этот единственный алерт записался в состояние как отправленный, хотя в БД dashboard нет ни одной
записи `Alert` за 22.07 и 02.08.

**4. `\Seen` не проставлялся ни разу** — 1695 писем, все непрочитанные. `messageFlagsAdd` вызывался
внутри активного `for await (… client.fetch())`, за ним сразу шли `return` и `logout()`.

### Что сделано

- Поиск письма — **во всех папках**, приоритетно INBOX и спам, полный обход один раз в конце
  таймаута. Найденное в спаме считается доставленным, но поднимает отдельный сигнал
  `deliveredToSpam`: доставка формально есть, до человека письмо не дойдёт.
- Поиск переведён с клиентского перебора конвертов на серверный `SEARCH` по теме — размер ящика
  на проверку больше не влияет. Это же вылечило internal-ногу.
- Оба получателя — в `To:` одного письма вместо скрытой копии.
- `alertedAtFailures` вместо булева `alerted`: повтор при каждом удвоении числа неудач (3, 6, 12…).
- `postDashboardAlert` возвращает `boolean`; исход пишется в `lastAlertDelivered`, недоставленный
  алерт повторяется на каждом прогоне.
- `messageFlagsAdd` вынесен из цикла итерации, выполняется отдельным локом.
- Служебный ящик чистится за собой: найденное письмо + канареечный мусор старше суток. Чужой
  внешний ящик не трогается — только пометка прочитанным.
- Расписание — раз в час вместо каждых 15 минут, порог алерта снижен с 3 до 2.
- Состояние старой формы на диске подхватывается **слиянием с дефолтом**, а не `?? default()`:
  иначе новые поля были бы `undefined`, сравнение ушло бы в `NaN` и логика повторов молчала бы
  навсегда — ровно тот отказ, который здесь чинится.

### Проверка на живом проде

Деплой 16:16 и 16:25 MSK (BlackCove). Проверено **независимо от файла состояния**, прямо по ящикам:

- свежее письмо во внешнем ящике лежит **прочитанным** — пометку ставит только код канарейки при
  найденном письме, за 17 дней этого не случалось ни разу;
- во внутреннем ящике осталось **54 письма вместо 1695** — чистка вызывается исключительно из
  ветки «письмо найдено», так что её срабатывание само доказывает работу internal-ноги.

Заодно подтверждён Gmail-фильтр владельца положительным контролем: письмо 16:15 (до правила) —
в спаме, 16:30 (после) — во входящих, при вычищенном ящике и одинаковых письмах.

### Тесты

`email-canary.spec.ts` — 10 тестов на логику повторного алерта (порог, удвоение, ретрай
недоставленного, несконфигурированная нога) и распознавание спам-папки по IMAP special-use
`\Junk` независимо от языка имени. Плюс 3 теста в `dashboard-alert.spec.ts` на то, что доставка
подтверждается только по 2xx. Всего 65/65.

### Урок методологии

Гипотезу про backlog я выдвинула первой и **сама же ошибочно закрыла**: замер полного прохода по
1695 письмам дал 426мс против таймаута 90с. Замер был сделан **с рабочей машины**, а канарейка
ходит из контейнера на s2 через канал до другого датацентра — мерился не тот путь. Та же ловушка,
о которой я в том же треде писала BlackCove по поводу `nc -z`.

**Замер, сделанный не тем путём, опаснее отсутствия замера: он выглядит как факт и закрывает
верную гипотезу.** Пополняет `.claude/docs/verification-pitfalls.md`.

```
src/lib/cron.ts:133:28 - TS7006: Parameter 'i' implicitly has an 'any' type
```

### Причина — одна на все три ошибки

`references` в `tsconfig.json` содержал `{ "path": "../../libs/redis-client" }` — ссылку на
**solution-конфиг** библиотеки. Тот, в свою очередь, ссылается сразу на `tsconfig.lib.json` и
`tsconfig.spec.json`. Оба включают `src/**/*.ts`, то есть претендуют на один и тот же исходник,
и TypeScript при выборе цели редиректа берёт **последний** в списке.

У `libs/redis-client` последним стоит `spec` → редирект уходил в `out-tsc/spec/src/index.d.ts`,
который **не собирает ни один таргет вообще** (`typecheck` библиотеки собирает только
`tsconfig.lib.json` → `dist/`). Отсюда вечный `TS6305`.

Оба `TS7006` — каскад: провалившийся редирект делал модуль `any`, `getRedis()` терял тип,
`r.smembers()` возвращал `any`, параметры `.forEach` становились неявными `any`. Подтверждено
экспериментом — после снятия ссылок обе ошибки исчезли сами, без единой аннотации. Расставить
там типы вручную означало бы замаскировать причину и оставить библиотеку нетипизированной.

### Побочная находка: соседняя ссылка была зелёной случайно

У `libs/email` порядок references обратный (`spec`, затем `lib`), поэтому редирект попадал в
`dist/`. Но `dist/` в `.gitignore` — на свежем клоне упало бы и на email. То есть техдолг был
шире, чем выглядел по трём строчкам вывода.

Проверено прямым экспериментом: перестановка порядка в `libs/redis-client/tsconfig.json` делает
исходный конфиг зелёным. Файл возвращён как был — это ненадёжный «фикс», он держится на
gitignore'нутом артефакте.

### Фикс

Из `tsconfig.json` убраны `references` на библиотеки. Типы проверяются по исходникам — ровно
так, как их бандлит прод-сборка (esbuild через `customConditions: ["@letar/source"]`), и никаких
предварительно собранных артефактов не требуется.

Вместе с ними пришлось убрать:

- `rootDir: "./src"` — исходники библиотек лежат вне него, их попадание в программу даёт `TS6059`;
- `outDir: "./dist"` — заставляет TypeScript вывести `rootDir` самостоятельно, тот же эффект.

⚠️ `declaration` **оставлен намеренно**: без него `@nx/esbuild` не резолвит entry point и таргет
`build` падает с `Could not resolve "apps/dashboard-agent/src/index.ts"`. Выглядит мёртвой опцией
для бандлящегося приложения, но таковой не является. Установлено бисектом — первая попытка
приписала это `rootDir`, потому что тест менял две переменные разом.

### Проверки

`typecheck`, `lint`, `test` (47/47), `build` — все зелёные, прогнаны с `--skip-nx-cache` **при
полностью снесённых `libs/*/dist`**, то есть на состоянии свежего клона.

**Позитивный контроль:** временное присваивание `getRedis()` заведомо неверному типу даёт
`TS2322: Type 'Redis | null' is not assignable to type 'number'` — типы библиотеки реально видны,
а не замаскированы под `any`. Отдельная проверка нужна потому, что зелёный typecheck после такого
фикса мог бы означать и просто ослабленную проверку.

Рантайм-код не тронут — правка только в `tsconfig.json`.

### Документация

Поправлен `.claude/rules/libs.md`: там утверждалось, что `references` читает только
`tsc --build`. Неверно и вводит в заблуждение — `--build` их только **собирает**, а обычный
`tsc --noEmit -p` и `tsgo --noEmit` их **читают** ради редиректа. Именно на этом утверждении
сломанную ссылку можно было списать как безобидную.

### Осталось незакрытым

`libs/redis-client/tsconfig.spec.json` расходится с `libs/email/tsconfig.spec.json` (у email есть
`composite`/`noEmit`/`emitDeclarationOnly`/`tsBuildInfoFile`/`exclude`, у redis-client, `ui`,
`format-utils`, `validation-utils` — нет). Сейчас инертно: spec-проект не собирает ни один таргет.
Но расхождение в 4+ библиотеках — почва для повторения истории у другого потребителя. Отдельная
задача по всем библиотекам разом.

1. **0.9.8 (коммит `fd1f8c6a`):** обобщён на `dashboard-agent` уже существовавший для

   `deploy` подтверждён рабочим). Живой деплой прошёл полностью автоматически: контейнер

interrupted/error»: `deployHistory` в `routes/deploy.ts` (0.8.3) и `executionLogs` в
`lib/cron.ts` (0.9.4).

**Вывод: преждевременно, не унифицировано.** Формы хранения расходятся по существу, а не
случайно:

- `deploy.ts` — один плоский **глобальный** ring-buffer (`MAX_DEPLOY_HISTORY` деплоев
  суммарно), каждый элемент — свой Redis-ключ (`deploy:item:<id>`), индекс — **LIST** (порядок
  важен для истории), персист построчного `output` **дебаунсится** (1с) отдельно от
  немедленного `flushPersist()` при значимых переходах статуса.
- `cron.ts` — **N независимых** ring-buffer (по `MAX_LOGS_PER_JOB` на `jobId`), каждый `jobId`
  — один ключ с целым JSON-массивом логов (`cron:logs:<jobId>`), индекс — **SET** job-id
  (порядок не нужен), персист **немедленный** на каждый `addLog`/`updateLog` без дебаунса.

Обобщённый хелпер пришлось бы параметризовать сразу по трём осям (indexType list/set,
гранулярность ключа элемент/группа, стратегия персиста дебаунс/немедленно) — на двух
потребителях это не сокращает код, а прячет реальную разницу за конфигом. Решение и явный
критерий пересмотра (третий Redis-backed ring-buffer с формой хранения, совпадающей с одним
из этих двух вариантов) зафиксированы комментарием в `lib/redis.ts`. Код логики `deploy.ts`/
`cron.ts` не менялся — только документация решения (`PLAN.md`, `CHANGELOG.md`, `lib/redis.ts`).

## Версия 0.7.1 — e2e-раннер: nsenter вместо прямого spawn, закрыта command injection (§18 Сессия D, 2026-07-11)

Первый живой staging-пилот (grandslamcup, домен `grandslamcup-stage.s3.letar.best`) сразу вскрыл баг в `routes/e2e.ts` (реализован в предыдущей сессии, но ни разу не запускался вживую).

### `spawn nx ENOENT`

`POST /api/e2e/run` спавнил `nx` напрямую в процессе dashboard-agent — но внутри контейнера нет ни воркспейса, ни бинарника `nx` (они существуют только на хосте s3). Симметрично багу, который уже чинили в `deploy.ts` (Сессия C) — деплой уже использовал `nsenter -t 1 -m -u -n -i` для выхода в host-namespace, e2e.ts этот приём не переиспользовал.

**Фикс:** `spawn('nsenter', ['-t','1','-m','-u','-n','-i','--','bash','-c', 'cd <repo> && bunx nx e2e <app>-e2e ...'], { env })`. `env: { ...process.env, BASE_URL: baseUrl }` — nsenter наследует env спавна (тот же приём, что `SOPS_AGE_KEY_FILE` в deploy.ts).

### Command injection, найденная по пути

Переход на `bash -c` со строковой интерполяцией сделал параметр `project` из POST-body (ранее безобидный — шёл в `args` массивом для `spawn`) точкой command injection в **root-контекст хоста** (`nsenter -t 1` — полный выход из контейнера). Добавлена валидация `project` тем же regex, что у `app` (`^[a-z0-9-]+$`), до всякой интерполяции.

### Результат первого живого прогона

Инфраструктурно успешен (пайплайн `deploy_app(staging)` → `run_e2e` → `e2e_status` отработал end-to-end впервые). Содержательно 3/28 passed — не относится к dashboard-agent, см. `PLAN.md` §18 в корне репо и `apps/grandslamcup/PLAN.md`.

`docker stop`/`docker rm` все процессы в cgroup контейнера убиваются вместе с ним независимо
от сессии. Detached-скрипт обрывался ровно на "Recreate".

**Решение (0.9.9):** заменено на `systemd-run --unit=... --collect` — транзиентный
systemd-юнит выполняется в `system.slice`, полностью отдельной от cgroup докера, с fallback
на nohup+setsid если `systemd-run` недоступен (явное предупреждение в логе, что fallback не
решает self-deploy). Заодно исправлен сопутствующий баг: цикл ожидания healthcheck перед
reload nginx вычислял имя контейнера как `${app}-app`, но `dashboard-agent` в
`docker-compose.production.yml` задаёт `container_name: dashboard-agent` без суффикса —
добавлен явный кейс.

**Вторая попытка (0.9.9, коммит `d689a8d6`) тоже не сработала:** живой прогон упал сразу
после warning-строки, ни разу не дойдя до `✅ ... restart scheduled via systemd-run`.
Диагноз (BlackCove, message #875, проверено вручную на s2): голый `systemd-run` без `sudo`
требует polkit-авторизацию (`Interactive authentication required`) — непривилегированный
`deploy` не может стартовать unit в `system.slice` без интерактивной сессии. Хуже того,
вызов стоял в `then`-блоке `if`, поэтому его ненулевой exit-код под `set -e` (действует всю
жизнь скрипта) убивал весь `deploy-affected.sh`, а не только уходил в fallback.

**Решение (0.9.10) — подтверждено живым прогоном:** вызов перенесён в условие `if`
(падение внутри условия не триггерит `set -e`) + добавлен `sudo -n systemd-run`. Деплой
коммита `12b2ac30` прошёл **полностью автоматически, без ручного вмешательства** (BlackCove,
message #879): контейнер `dashboard-agent` пересоздался штатно (чистое имя, не завис в
`Created`), `/tmp/dashboard-agent-restart-*.log` (владелец `root` — подтверждает, что unit
запущен через `sudo systemd-run`) показывает полный цикл `Creating → Created → Starting →
Started` + успешный старт крон-планировщика и сборщика метрик.

**Три бага, которые пришлось найти по очереди (типичный паттерн detached-процессов в
Docker+systemd): (1) cgroup-принадлежность не меняется `setsid`/`nohup` — нужен реальный
выход через `systemd-run`; (2) polkit требует `sudo` для `system.slice`; (3) вызов внутри
`then`-блока под `set -e` убивает весь скрипт при первой же ошибке, а не только эту ветку —
каждая правилась по факту падения на реальном сервере, ни одна не была очевидна заранее.**

прячет разницу за конфигом. Решение и критерий возврата (третий Redis-backed ring-buffer с
совпадающей формой) — комментарий в `lib/redis.ts`. Код не менялся.
