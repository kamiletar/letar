## Сессия 2026-07-07 — E2E: триггер safety-net (v0.15.1) 🛟

### Что сделано

- **`archetest-e2e/src/safety-net.spec.ts`** (1 тест, этап 5.8) — единственный оставшийся
  непроверенный E2E-сценарий safety-net (5.6.4): полный квиз (50 вопросов) → на каждом
  вопросе выбирается вариант, максимизирующий суммарный балл DPR+BAR+BOR (справочник —
  `questions-dump.json`, поиск по тексту сценария) → экран результатов показывает
  `SafetyNetBlock` (заголовок «Ваши ответы отражают заметное эмоциональное напряжение» +
  телефон 8-800-333-44-34). Формула нормализации TZ v2 (`raw/actualMax` по отвеченным
  вопросам) гарантирует ~100% по целевым шкалам при таком выборе — надёжно выше порога 60%.
- **Авторизация в тесте** — `submitQuizAction` доступен только залогиненным, а archetest
  поддерживает исключительно OIDC-логин через ключницу (auth.letar.best); прогонять реальный
  OAuth-редирект в E2E нестабильно и требует поднятого auth-hub. Вместо этого: тестовый юзер +
  строка `Session` создаются напрямую в БД (`pg`), cookie `better-auth.session_token`
  подписывается тем же HMAC-SHA256 алгоритмом, что использует better-call/Better Auth
  (`${token}.${signature}` в base64, затем `encodeURIComponent`) — воспроизведено по исходникам
  `better-call/dist/crypto.mjs`. Тестовый юзер удаляется в `afterAll`.
- Добавлен `data-testid="quiz-scenario"` на заголовок вопроса (`quiz-question-card.tsx`) —
  нужен, чтобы сопоставить показанный вопрос с банком и выбрать нужный вариант ответа.
- Прогон chromium: 5/5 passed (2 express + 2 mood-check-in + 1 safety-net, ~42s).

### Находка при прогоне

- Порт 3012 уже занят Docker-контейнером `archetest-app`, отвечающим 500 (та же поломка

### Находки

- **form-mcp паттерн устарел:** `get_form_pattern('server-action')` показывает пример с
  `useAppForm` + `<Form form={form}>` — реальный текущий API `createForm()` (см.
  `create-form.spec.tsx` в `libs/forms`) декларативный: `<AppForm initialValue={...}
onSubmit={...}>`, без ручного `useAppForm`. Ориентировался на спеки библиотеки, а не
  только на form-mcp паттерн.
- **⚠️ ZenStack: `getEnhancedPrisma().create()` падает при read-политике уже ADMIN.**
  Гостевая заявка сохранялась в БД (проверено напрямую через `pg`), но клиент получал
  `{ error: 'submit_failed' }` и экран успеха не показывался — обнаружено только браузерным
  E2E-прогоном полного сабмита (unit/typecheck этого не поймали бы). Причина: enhanced-клиент
  после `create()` делает read-back созданной записи, чтобы вернуть её вызывающему, а
  read-back проходит через политику `@@allow('read', ADMIN)` — для анонимного гостя падает,
  хотя сама запись уже создана. Тот же паттерн уже решён в `auth-hub` для `ConsentLog`
  (`@@allow('create', true)` + `@@allow('read', ADMIN)`): там `api/consent/route.ts` пишет
  через **raw `prisma.consentLog.create()`**, а не `getEnhancedPrisma()`. Применил тот же
  подход к `submitProfessionalLeadAction`. **Общий вывод для будущих guest-write моделей:**
  если read-политика уже write-политики (гость создаёт, но не может читать) — писать через
  raw prisma, не enhanced-клиент.
- **Окружение сессии:** параллельно другой агент обновлял зависимости (`bun.lock`/`package.json`,
  включая `@oxc-project/types` 0.133.0→0.138.0) — `nx test archetest` (vitest/oxc-плагин) не
  запускался стабильно весь остаток сессии (`TSCONFIG_ERROR` на `vitest.setup.tsx`, не

### v0.17.0 — Этап 5.9.3 «Кулдаун ретестов», решение Kami «гибрид»

Скоуп-вопрос, блокировавший задачу с 2026-07-06 («сессия» = порция из 50 или полный
ретест?), решён Kami 2026-07-08 в пользу **гибрида**:

- **`countUniqueUtcDays` + новая семантика `calculateXp`** (`_data/ranks.ts`): XP =
  уникальные UTC-дни с валидными сессиями × 100 + ачивки. Анти-ферма: 5 порций в день =
  100 XP; спейсинг: та же активность в 5 дней = 500 XP. 9 unit-тестов (TDD red→green),
  включая границу UTC-суток.
- **Повторы вопросов структурно невозможны** — `getRandomQuestionsAction` всегда исключал
  отвеченные/пропущенные (`excludeIds`), «Продолжить» скрывается при `availableCount === 0`.
  Поэтому жёсткий суточный запрет и «окно точности через N дней» не реализуются сейчас,
  а отложены в Фазу 3 вместе с самим механизмом ретестов после исчерпания банка.
- **`xpCountedToday` в `SubmitQuizResult`**: первая ли это валидная сессия за UTC-сутки
  (count сессий дня до текущей, сама сессия исключается по id). В `QuizResults` под CTA
  «Пройти ещё N вопросов» при `xpCountedToday === false` — подпись «XP за сегодня уже
  получены — каждый новый ответ уточняет профиль» (ru/en, inline-локализация как у
  соседней кнопки). Сброс флага при старте/продолжении/рестарте порции.
- **Попутный фикс**: `recalcLeaderboardEntry` считал XP по всем завершённым сессиям без
  фильтра `isValid` — невалидный протокол добавлял +100 XP при следующем валидном
  пересчёте (вопреки решению 5.1). Добавлен фильтр `isValid: true`.

Итог: 105 unit + 5 E2E, lint (0 errors), `typecheck:tsgo` — зелёные. Из 5.9 остался
только 5.9.5 (нормативная гигиена — ждёт механизма норм из 5.6.2/Фазы 3).
