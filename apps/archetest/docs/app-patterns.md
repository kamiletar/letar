# Паттерны archetest

> Два соглашения, которые в приложении уже устоялись, но нигде не были записаны.
> Оба локальны для archetest — в общие `.claude/docs/` намеренно не выносятся.

---

## 1. Производный индекс в `_lib`

Всё, что вычисляется поверх готового профиля — ipsative-ранги, тёмное ядро,
«Броня и Радар», геометрия гексаграммы, safety-net, валидность протокола, —
живёт отдельным модулем в `src/app/[locale]/_lib/` и подчиняется одной догме.

**Правила паттерна:**

1. **Чистая функция поверх `normalized`.** Вход — уже посчитанные баллы
   (и `relevantCounts`, если нужны интервалы), выход — новый объект. Никаких
   обращений к БД, `next/*` или окружению: модуль обязан быть unit-тестируемым
   без поднятия приложения.
2. **Вход не мутируется.** Проверяется тестом «вход не мутируется» —
   он есть в `scoring-core.test.ts` и повторяется в новых модулях.
3. **`raw`/`normalized` в БД не затрагиваются.** Индекс — производный слой,
   он не меняет то, из чего посчитан. Поэтому появление нового индекса
   не требует миграции и не трогает `QUESTION_BANK_VERSION`.
4. **Тест рядом, с проверкой полноты обоих языков.** Файл `<модуль>.test.ts`
   в той же папке; если модуль отдаёт тексты — тест обходит все ветки и требует
   непустых `ru` и `en`.
5. **Оговорка приезжает вместе с числом.** Если у индекса есть методологическое
   ограничение, оно возвращается полем результата (как `caveat` в `dark-core`),
   а не остаётся на совести компонента. Компонент не должен «знать», когда
   показывать предостережение.

**Модули, следующие паттерну:** `ipsative`, `interpretation-rules`, `armor-radar`,
`hexagram-geometry`, `safety-net`, `validity`, `dark-core`, `scoring-core`.

**Почему так.** Ядро скоринга изначально жило в `quiz.action.ts`, а `'use server'`
тянет next-зависимости и не поддаётся unit-тестам. После выноса в `_lib`
server action остался тонкой обёрткой: грузит вопросы из БД и передаёт готовые
данные. Это же позволяет инжектировать справочник максимумов в тестах
(параметр `ScoringData`) вместо мока файловой системы.

**Чего избегать:** value-импорт из `'use server'`-модуля в клиентском компоненте.
Типы импортируются из `_lib/scoring-core`, а не реэкспортом из `quiz.action`
(реэкспорт убран в v0.25.2 именно поэтому — см.
[client-bundle-data-leaks](/.claude/docs/client-bundle-data-leaks.md)).

## 2. Двуязычие психологического контента — парами полей `x` / `xEn`

Тексты шкал, практик роста, интерпретаций, названий индексов хранятся
**в TypeScript-данных парами полей**: `label`/`labelEn`, `description`/`descriptionEn`,
`whenHigh`/`whenHighEn`. `messages/ru.json` и `messages/en.json` держат только
обвязку интерфейса — кнопки, заголовки экранов, подписи навигации.

**Почему не next-intl для контента:**

- Содержательные тексты меняются **вместе со структурой данных**: добавили шкалу —
  нужны её название, архетип, суперсила, ловушка, практики. Пара полей рядом
  с кодом шкалы делает пропуск невозможным: тип не соберётся без второго языка.
- Полнота проверяется unit-тестом, обходящим `ALL_SCALE_CODES` (`growth-practices.test.ts`
  требует покрытия 1:1). С ключами в JSON такую проверку пришлось бы писать
  отдельно и она ловила бы только отсутствие ключа, а не отсутствие перевода.
- Психологический текст осмыслен только в связке со шкалой. В общем словаре
  переводов он теряет контекст, и его легко «улучшить», не понимая конструкта.

**Практическое следствие.** Новый агент, добавляющий контент, естественно тянется
к `messages/*.json` — и заводит третий способ локализации. Не надо: контент шкалы
идёт в `_data/*.ts` парой полей, интерфейсная строка — в `messages/*.json`.

**Как выбрать язык в компоненте:**

```tsx
const isRu = useLocale() === 'ru'
const text = isRu ? scale.description : scale.descriptionEn
```

**Исключение — RU-first к фестивалю (решение 2026-07-08).** EN поддерживается
и не выпиливается, но при нехватке времени RU-формулировка вычитывается первой;
EN-паритет не блокирует фестивальные задачи.

## 3. Именование шкалы — только через `getScaleName`

Смежное с двуязычием правило, добавлено в v0.25.2. Раньше «как назвать шкалу
для этой аудитории» решали четыре локальные функции в разных компонентах,
и политика «клиническая лексика только психологу» держалась на том, что автор
нового компонента выберет правильное поле.

Теперь есть единственная точка — `getScaleName(code, { audience, triadAlias }, isRu)`
в `_data/personality-types.ts`:

| `audience`  | Что отдаёт                              | Где применяется             |
| ----------- | --------------------------------------- | --------------------------- |
| `user`      | `label` + архетип                       | результаты, тизер шкал      |
| `construct` | `clinical`, но только для белого списка | гексаграмма (термины триад) |
| `clinician` | `clinical` без ограничений              | кабинет психолога           |

Белый список `PUBLIC_CONSTRUCT_SCALES` — восемь шкал гексаграммы. Шкала вне списка
в пользовательском контексте молча падает на юзерское имя, то есть показать
клиническое название пользователю нельзя даже по ошибке. Проверяется
`_data/scale-naming.test.ts`.
