# Changelog (Архив до 2026-07-28)

> Продолжение основного CHANGELOG.md
> Версии: 0.25.5 — 0.21.0

## [0.25.5] - 2026-07-28

### Fixed

- **CRITICAL: сайт был сломан для всех посетителей — `CookieBanner` рендерился вне `ChakraProvider`.**
  В `[locale]/layout.tsx` `<CookieConsent />` стоял сиблингом `<Providers>` (снаружи), а не
  внутри — `CookieBanner` (`libs/ui`) использует `Box`/`Button`/`Checkbox` из `@chakra-ui/react`,
  что бросало `ContextError: useContext returned undefined` на КАЖДОЙ странице сайта. Баг жил
  с деплоя v0.25.0 (152-ФЗ CookieBanner, тем же днём) — не пойман раньше, потому что верификация
  деплоев шла через HTTP `fetch` (статус-коды), а не через реальный рендер в браузере. Обнаружен
  пользователем в реальном Brave, воспроизведён и починен в течение сессии. Перенос `<CookieConsent />`
  внутрь `<Providers>` — единственное изменение.

## [0.25.4] - 2026-07-28

### Fixed

- **Настоящий источник бага 0.25.3 — плагин `@serwist/next`, не наш компонент.**
  Проверка деплоя 0.25.3 показала: `service-worker-registration.tsx` больше не единственная
  точка регистрации. `@serwist/next` по умолчанию (`register: true`) сам инжектит клиентский
  скрипт, который безусловно, на КАЖДОЙ странице, вызывает
  `navigator.serviceWorker.register('/sw.js', { scope: '/' })` — в обход консент-гейта
  `useOfflineConsent`. Именно этот авто-инжект, а не наш компонент, реально брал сайт
  под контроль SW. Теперь `withSerwistInit({ ..., register: false })` в `next.config.mjs` —
  единственная точка регистрации снова `service-worker-registration.tsx` (фикс 0.25.3
  остаётся в силе как defense-in-depth, но сам по себе не закрывал проблему).

## [0.25.3] - 2026-07-28

### Fixed

- **Service Worker перехватывал весь сайт, а не только `/express`.** `service-worker-registration.tsx`
  регистрировал `/sw.js` со `scope: '/'` — после одного согласия на офлайн-баннере
  (`archetest-offline-consent`) на `/express`, SW получал контроль (`clientsClaim: true`)
  над навигацией по всему домену, хотя `runtimeCaching` в `sw.ts` целенаправленно кэширует
  только `/express`/`/en/express`. Теперь регистрируются два отдельных SW-инстанса со scope
  `/express` и `/en/express` вместо одного на `/`. Требует передеплоя; у пользователей,
  уже давших согласие, старая широкая регистрация снимется только при отзыве согласия
  или обновлении SW-скрипта браузером.

## [0.25.2] - 2026-07-28

Разбор техдолга: закрыто девять пунктов из списка, три дефекта найдено по ходу.

### Fixed

- **Пороги достоверности шкал были инвертированы.** `confidenceFromCount` считала
  достоверность как долю банка, а вопросов на шкалу различается в 100+ раз (RES_PHYS — 10,
  SAD — 21 против AVD — 1192): «высокая точность» набиралась за 6 ответов по редкой шкале
  и за 715 — по населённой. Человек, прошедший 4 порции, видел «высокую точность» по редким
  шкалам и «Недостаточно данных» по самым населённым. Теперь **абсолютные пороги 5 / 15 / 30**,
  выведенные из полуширины интервала Уилсона при p = 0.5 (±33 / ±23 / ±17 п.п.).
  Прежняя величина сохранена отдельной функцией `bankCoverage` — это «покрытие», не «точность».
- **Ачивка «Полная карта» стала бы недостижимой** после смены порогов: она требовала
  достоверности `high` по всем шкалам ядра, а по SAD в банке 21 вопрос при новом пороге 30.
  Переведена на покрытие банка (`FULL_MAP_COVERAGE = 0.6`) — по смыслу она про полноту
  прохождения, а не про точность оценки; достижимость осталась прежней.
- **Числа «22 шкалы / 2096 вопросов» уже разошлись с реальностью** — банк вырос до 2126
  ещё на этапе 5.5. Публичные страницы обещали 2096.
- **merge-скрипт: защита от изменения баллов пропускала часть правок.** Первая версия
  сравнивала только максимум вопроса, поэтому правка балла варианта с 1 на 3 при соседнем
  варианте-«тройке» проходила молча — максимум не двигается, но `raw` каждого, кто выбрал
  этот вариант, меняется, включая уже записанные сессии.
- **merge-скрипт не обновлял `global_max_scores` для новой шкалы** — код, которого ещё нет
  в справочнике, не попадал в список обновляемых. Шкала HON молча не получила бы максимума,
  и нормализация по ней поехала бы с первого прохождения.

## [0.24.0] - 2026-07-28

### Added

- **Индекс «Тёмное ядро» (Фаза 3)** — приближение D-фактора (Dark Factor of Personality)
  из четырёх уже существующих шкал ядра (MAC/NAR/ANT/SAD). Новых вопросов, миграций БД
  и изменения `QUESTION_BANK_VERSION` не потребовал — производный слой поверх `normalized`.
  - `_lib/dark-core.ts` — чистая функция `computeDarkCore`. Считает уровень ядра
    (unit-weighted composite), «вкусы» по Bader et al. (2023) — отклонение каждой шкалы
    от ядра, размах, интервалы Уилсона, агрегированную достоверность (минимум по
    измеренным) и ipsative-контекст (где тёмные шкалы стоят внутри профиля человека).
  - **Структурный вывод вместо ярлыка уровня**: `even` / `flavored` / `polarized` /
    `muted` / `insufficient`. Поля абсолютного уровня в типе нет намеренно — `normalized`
    это процент от максимума, а не перцентиль, и утверждение «высокое тёмное ядро»
    некорректно до накопления норм (5.6.2).
  - **Анализ чувствительности к нарциссизму**: второе значение ядра без NAR. Порог
    выводится из тождества `core − core₃ = deviation(NAR) / 3`, а не назначается.
    Основание — Hilbig et al. (2023): просадку приближения даёт именно нарциссическое
    «восхищение».
  - **Измеренность шкалы — по `relevantCounts >= 3`, а не по «балл > 0»**: `normalized = 0`
    бывает и при отсутствии данных, и при честном нуле, и различает их только число
    ответов. Банк асимметричен (SAD — 21 релевантный вопрос против 987 у ANT), поэтому
    при n = 1 один ответ двигал бы ядро на десятки пунктов.
  - `DarkCoreBlock` на странице клиента — только кабинет психолога, клиенту не показывается.
    Порядок блоков: структурный вердикт → вкусы → число → чувствительность → оговорка;
    обязательное поле `caveat` приходит из модуля вместе с числом.
  - Dev-превью `/dev/dark-core` — все пять структурных веток.
  - +24 unit-теста. Итого **171 unit**.
- **`generateMetadata` для `/for-professionals`** — у главной B2B-страницы не было
  собственных метаданных вовсе (она наследовала общий title из layout). Добавлены
  title/description/OpenGraph на обе локали и canonical.
- **Кликабельные источники в разделе «Методология»** — все 15 DOI сверены вручную
  (у SSIS в справочных материалах ходит неверный DOI). Плюс блок «Тёмное ядро: общий
  фактор и «вкусы»» с явными ограничениями: r ≈ .85 против полного D, предостережение
  авторов против трактовки тетрады как главного представления ядра, и критика
  Vize/Lynam о неотличимости D от антагонизма (шкалы Доброжелательности в тесте нет,
  проверить на своих данных невозможно в принципе).
- Якорь `#methodology` на секции «Методология» — для ссылок из презентации и раздатки.

### Changed

- `getClientDetailAction` отдаёт в кабинет `scoreRelevantCounts` и `scoreConfidence`
  (оба уже считались в `calculateScores`, но наружу не выходили). Побочный эффект:
  в `ProfileDetails` кабинета заработало ipsative-ранжирование — до этого оно молча
  не срабатывало без `relevantCounts`, и топ-3 сортировался просто по баллу, без
  интервалов и tie-групп.
- Раздел «Методология» больше не утверждает, что MAS — единственный конструкт без
  валидированного прототипа: добавлено описание трёх экспериментальных шкал
  (RES_PHYS/RES_AFF/SPEC_INT) и индекса «Броня и Радар». Долг тянулся с v0.23.0,
  где реализация была, а маркировка на публичной странице — нет.

### Fixed

- `ExperimentalScalesBlock` скрывал индекс «Броня и Радар» при истинном нуле по одной
  из осей: условие `phys > 0 && aff > 0` не отличало «шкала не отвечена» от честного
  нулевого балла. Теперь измеренность считается по числу ответов.
