## Что и зачем

После регистрации посетитель может запросить дружбу, владелец получает уведомление и вручную принимает решение. Нужны степень близости и несколько кругов общения, например творческие круги. Регистрация сама по себе не даёт дружбу.

Источник: лог владельца от 25 октября 2026 года. Скриншот сохранён локально в
`.claude/artifacts/kami-feedback-2026-10-25/mobile-footer.png`.
Сырые сообщения и персональные контакты в публичную задачу не копируются.

## Проектное решение — 2026-10-26

### Что уже есть в коде

- `src/lib/auth.ts`: `createAuth({ mode: 'hub-client' })`, OIDC через Ключницу;
  локальная сессия Kami и локальный `User`. Новая регистрация/пароль не нужны.
- `schema/organization.zmodel`: Organization — компания работодателя, Member и Invitation
  управляются Better Auth. Это членство в организации и приглашение по email, не личная дружба.
  Их повторное использование смешало бы роли компании с доступом к личному разделу.
- `schema/auth.zmodel`: USER/ADMIN — роли приложения. Не давать друзьям ADMIN
  и не включать приватные сведения о близости в общедоступное чтение User.
- `src/lib/email/email-service.ts` и `@letar/email`: есть email-инфраструктура
  уведомлений по обращениям. Использовать существующий провайдер с отдельным типом письма.
  Моделей дружбы и кругов в просмотренных схемах нет.

### UX посетителя

| Состояние         | Что видит и может сделать человек                                                  |
| ----------------- | ---------------------------------------------------------------------------------- |
| Не вошёл          | Что даёт дружба; «Войти и отправить заявку», возврат из Ключницы на этот раздел    |
| Вошёл, заявки нет | Короткое объяснение ручного решения; явная кнопка «Отправить заявку»               |
| PENDING           | «Заявка отправлена. Решение появится здесь»; без обещания срока                    |
| ACCEPTED          | Подтверждённая дружба и только реально подключённые преимущества                   |
| DECLINED          | Нейтральное «Заявка пока не принята»; без публикации причин                        |
| REVOKED           | «Доступ для друзей сейчас не активен»; льготы больше не показываются как доступные |

**Автосоздание после регистрации:** лог допускает два прочтения: любая регистрация
или регистрация из раздела друзей. Предлагается фиксировать намерение на кнопке
«Войти и отправить заявку» и после возвращения показывать подтверждение отправки.
Произвольный вход в блог не должен создавать заявку без намерения пользователя.
Окончательный выбор автоотправки после регистрации — открытый вопрос владельцу.
До ответа KM-021 реализует явную отправку и не заявляет это согласованным поведением.

Льготы показывать по состоянию права доступа, а не по факту входа.
Публичного списка друзей и механизма поиска чужих заявок нет.
Приватные причины отказа и оценки близости пользователю не показываются.

### Действия владельца

Админка: очередь ожидающих → карточка → принять/отказать; принятый друг → отозвать.
В той же карточке: приватная заметка, близость и несколько кругов.
Круги — произвольные метки владельца, например «Поэты»; один человек может входить в несколько.
Близость предлагается хранить как nullable число 1–5 с подписями, где null = не оценено.
Эта шкала — предложение, а не психологическая характеристика или утверждённая классификация.
Круги и близость в MVP не меняют льготы автоматически.

### Минимальная модель (не миграция)

- `Friendship`: id, уникальный userId → локальный User, status
  PENDING/ACCEPTED/DECLINED/REVOKED, requestedAt, decidedAt, decidedBy, revokedAt,
  privateNote, closeness nullable 1–5, version/updatedAt.
  Одна текущая запись на человека; локальный id не считать общим id всех сервисов.
- `FriendCircle`: id, name; только владелец создаёт/переименовывает/удаляет.
- `FriendCircleMember`: friendshipId + circleId, составной unique.
- Для истории решений — журнал событий без копирования email/текста заметок в логи.
  Конкретный журнал/outbox выбрать после проверки общей инфраструктуры jobs в KM-021.
  Повтор доставки уведомления не создаёт новую заявку.
- В интеграциях KM-022 использовать проверенный общий subject Ключницы и серверное
  сопоставление учётных записей. Не сопоставлять друзей по отображаемому имени или email.

### Уведомления и защита

Проектный канал MVP — email владельцу через существующий провайдер.
Адрес берётся из отдельной конфигурации `FRIENDS_NOTIFY_EMAIL`; не угадывать его из SMTP login.
Письмо содержит минимальную информацию и ссылку в админку, где нужна сессия владельца.
Заявка сохраняется до отправки письма; ошибка доставки отображается в админке и
повторяется фоновым заданием с ключом `friendshipId + requestedAt`.
Не показывать пользователю «уведомление доставлено» до подтверждения провайдера.
Telegram-бот не нужен для MVP; его можно добавить отдельно по выбору владельца.

- Создание: только вошедший пользователь с подтверждённой учётной записью.
- Уникальность userId + идемпотентная повторная отправка возвращают текущую PENDING.
- Предлагаемый лимит: 3 попытки за час на пользователя; повтор PENDING не шлёт письма.
  Повтор после DECLINED/REVOKED в MVP доступен только по решению владельца.
- Решения меняются транзакционно с проверкой версии; принять старую заявку повторно нельзя.
- Любой ввод заметок/названий имеет длину и серверную валидацию; кнопка не заменяет проверку прав.

### Матрица доступа

| Данные/операция           | Гость  | Пользователь                     | Владелец       | Подключённый сервис                  |
| ------------------------- | ------ | -------------------------------- | -------------- | ------------------------------------ |
| Описание раздела          | Читать | Читать                           | Читать         | —                                    |
| Отправить заявку          | Нет    | Только себе                      | Не требуется   | Нет                                  |
| Читать статус             | Нет    | Только свой, безопасная проекция | Все            | Только право по проверенному subject |
| Принять/отказать/отозвать | Нет    | Нет                              | Да             | Нет                                  |
| Близость, круги, заметка  | Нет    | Нет, в том числе свои            | Читать/править | Нет                                  |
| Получить льготу           | Нет    | Только ACCEPTED + правило льготы | По правилу     | Проверять на своём сервере           |

«Владелец» — явно назначенный аккаунт Kami, а не любой USER или произвольный ADMIN.
В KM-021 требуется определить проверку владельца из действующей модели полномочий;
если она отличается от isAdmin, добавить отдельную проверку владельца.
Доступ к Friendship нельзя наследовать от публичного @@allow('read', true) модели User.
Сырые записи дружбы не выдавать generic CRUD без отдельной проверки и полевой проекции.

### Дальнейшая реализация и вопросы

- **KM-021:** миграция минимальной модели, server actions, страница, админка,
  email с повтором, транзакции и тесты отрицательных прав.
- **KM-022:** конкретные льготы и общий subject, отзыв доступа и отдельные задачи сервисов.
- До миграции определить срок хранения заявок/журнала и удаление вместе с аккаунтом;
  тексты обработки данных и нужное согласие согласовать в контексте действующей политики.
- Владелец выбирает: автоматическую заявку при регистрации или явное подтверждение,
  шкалу близости, публичность названий кругов (предложение: всё приватно),
  канал уведомлений (предложение: email).
  Для реализации спорных пунктов это вопросы, не разрешение придумать предпочтения.
