# KamiKeyThe — План развития

## Текущая версия: 1.7.2

## Черновик (новые идеи)

Системная утилита для ввода типографских символов через AltGr (ремейк TypeItEasy).
Electron + React + Chakra UI v3 (main process: koffi Win32, renderer: Vite SPA).

_Название созвучно с «Камикадзе», что подчеркивает молниеносную скорость ввода._

## Инвентаризация физических клавиш вне основного блока

Результат задачи из бэклога (2026-09-06) — какие клавиши вне alpha-блока в принципе можно
хукать через `RegisterHotKey` с `AltGr` (`MOD_CONTROL | MOD_ALT`) и стоит ли. Основано на
документированном поведении Win32 API, не на эмпирическом прогоне каждой комбинации в этом
приложении — если что-то из «доступна» на практике не сработает на конкретном железе, это повод
дополнить таблицу, а не считать её ошибочной целиком.

⚠️ **Главная находка: `AltGr+Delete` в принципе невозможен.** AltGr на Windows — это не
самостоятельный модификатор, а физическая клавиша Right Alt, которую драйвер клавиатуры (для
раскладок, где AltGr определён) синтезирует как одновременное **Left Ctrl + Right Alt**. Значит
`AltGr+Delete`, нажатый физически, неотличим от `Ctrl+Alt+Delete` — Secure Attention Sequence,
которую перехватывает не приложение и даже не `RegisterHotKey`/low-level hook, а сам Winlogon на
уровне ядра ещё до того, как событие клавиатуры вообще становится видно пользовательскому
процессу. Никакой код в этом приложении не может это обойти (и не должен — это единственная
защита от подмены экрана входа). Клавиша `Delete` из кластера ниже — исключается из плана
использования полностью, не временно.

| Клавиша / кластер          | VK (hex)                           | Доступна для AltGr-хука?                                                        | Стоит ли использовать                                                                                                                                                                                                                                                                                                  |
| -------------------------- | ---------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Отдельно: `Caps Lock` (`0x14`) уже в `MODIFIER_VKS` (`keyboard-data.ts`) как немаппируемая
спецклавиша — тот же класс побочного эффекта переключения состояния, что у NumLock/Scroll Lock
выше, уже учтён в существующем коде.

## Архитектурные решения

### Почему Koffi, а не keysender?

Исследование показало критическую проблему: **keysender `GlobalHotkey` не поддерживает модификаторы**. В C++ коде `RegisterHotKey(NULL, 0, NULL, keyCode)` — третий параметр (модификаторы) всегда `NULL`. Это значит:

- ❌ Нельзя зарегистрировать `AltGr+A` (т.е. `Ctrl+Alt+A`)
- ❌ Можно только одиночные клавиши → блокирует ВСЮ обычную печать
- ❌ `LowLevelHook` мониторит, но **не блокирует** оригинальное нажатие

Альтернативы (все хуже Koffi):

| Подход                                  | Проблема                          |
| --------------------------------------- | --------------------------------- |
| keysender GlobalHotkey на каждую букву  | Блокирует обычную печать          |
| keysender LowLevelHook + Backspace hack | Мерцание, ненадёжно               |
| Форк keysender                          | Требует node-gyp, мёртвый проект  |
| node-lowlevel-keyboard-hook-win         | Только мониторинг, без блокировки |

**Koffi** решает все проблемы:

- ✅ `RegisterHotKey(NULL, id, MOD_CONTROL | MOD_ALT, vk)` — именно AltGr+клавиша
- ✅ Блокировка оригинального нажатия (поведение RegisterHotKey API)
- ✅ `SendInput` + `KEYEVENTF_UNICODE` — прямой Unicode вывод
- ✅ Без node-gyp — предкомпилированные бинарники
- ✅ Активно развивается (2025+)
- ✅ Единая зависимость для всей клавиатурной логики

### Механизм работы (message pump)

```
┌─────────────────────────────────────────┐
│  Node.js event loop                      │
│                                          │
│  setTimeout(pumpMessages, 5)             │
│    └── PeekMessageW() ──► WM_HOTKEY?    │
│          ├── Да → keymap.get(id)         │
│          │        └── SendInput(unicode)  │
│          └── Нет → continue              │
│                                          │
│  RegisterHotKey × N (при старте)         │
│  UnregisterHotKey × N (при выходе)       │
└─────────────────────────────────────────┘
```

Задержка ~5мс polling + <1мс SendInput = **суммарно <10мс** — незаметно при печати.

## Технический долг

### `src/stats.ts` не унифицирован с `@letar/electron-storage`

`config.ts` мигрирован на `createJsonStore` (2026-07-28, коммит `033e69a4`), `stats.ts` — нет.
Причина: `stats.ts` держит данные в `Map<string, number>` в памяти и сбрасывает на диск раз в
60 секунд (`initStats`/`incrementStat`/`shutdownStats`) — это не «загрузить объект → сохранить
объект» как у `createJsonStore`, а накопитель с ленивым flush. Прямая миграция потребовала бы
либо городить накопитель поверх стора, либо терять lazy-write (писать на каждый инкремент —
не годится, инкремент на каждый вставленный символ).

Стоит унифицировать, если у `@letar/electron-storage` появится штатная поддержка
паттерна «накопитель в памяти + периодический flush» (актуально не только для
`kami-key-the` — если такой же паттерн понадобится другому Electron-приложению,
тогда есть смысл выносить абстракцию, а не раньше — сейчас это единственный случай).
До этого — `stats.ts` остаётся с ручной атомарной записью (tmp + renameSync) как есть.

## Технический долг

### ~~electron-builder тащил весь node_modules монорепо в инсталлятор~~ ✅ 2026-09-06

Первая сборка релиза (`nx build:win`) дала инсталлятор **511 МБ** (2.3 ГБ распакованный,
`app.asar` — 1.2 ГБ). Причина: `files` в `electron-builder.yml` не исключал `node_modules` —
без явного `!node_modules`/`!node_modules/**/*` electron-builder не смог построить дерево
зависимостей под bun-изолированным линкером (лог: «no node modules found in collection,
utilizing file traversal collector») и просто сгрёб **весь общий `node_modules` монорепо**:
Electron (368 МБ), `@next`, React Native/`hermes-compiler`, `canvas`, `better-sqlite3`, `ssh2`
и десятки других пакетов, ни один из которых kami-key-the не использует.

Фикс — тот же паттерн, что уже применён в `apps/animatrona/electron-builder.yml`: исключить
`node_modules` целиком из `files`, единственную реально нужную рантайму нативную зависимость
(`koffi` — external в `main/webpack.config.js`, `require()` не бандлится) прописать точечно
через `extraResources` с прямым путём в `.bun/koffi@<версия>/node_modules/koffi` (симлинк
верхнего уровня `node_modules/koffi` electron-builder не разворачивает при копировании).

**Вторая грабля на том же фиксе:** копии одного `node_modules/koffi` недостаточно — сам
`koffi.node` лежит не в пакете `koffi`, а в отдельном опциональном платформенном пакете
`@koromix/koffi-{platform}-{arch}`, который koffi ищет по фиксированному относительному пути
(`resolveNative()` в `koffi/src/koffi/index.cjs`: `${__dirname}/../../../@koromix/koffi-${pkg}`).
Без него собранный инсталлятор проходит сборку без единой ошибки, но **падает при запуске**:
`Uncaught Exception: Error: Cannot find the native Koffi module; did you bundle it correctly?`
— не ловится ни на этапе `electron-builder`, ни линтом/тайпчеком, только живым запуском
собранного `.exe`. Добавлен второй `extraResources`-блок с тем же паттерном пути под
`.bun/@koromix+koffi-win32-x64@<версия>/...`.

Итог: инсталлятор **511 МБ → 108 МБ**. Проверено живым запуском собранного
`dist-electron/win-unpacked/KamiKeyThe.exe` — процесс стабильно живёт (было: падение с
error-диалогом сразу после старта main-процесса).

⚠️ **Урок для будущих обновлений koffi:** путь в `electron-builder.yml` захардкожен на точную
версию (`koffi@3.2.1`, `@koromix/koffi-win32-x64@3.2.1`), как и в `animatrona` — при апгрейде
koffi через `bun update` эти два пути надо обновить вручную, иначе `nx build:win` упадёт с
ENOENT на `from:`-пути (громкий сбой сборки, не тихий баг в рантайме).

## Бэклог

### ~~Роутинг в редакторе маппингов~~ ✅ 2026-09-06

**Сделано.** Адресуемое состояние экрана вынесено в `editor-route.ts` (`EditorRoute {keyVk,
category}`), зеркалится в `location.hash` через `history.replaceState` (не ломает
top-level `App.tsx`, который проверяет только точное совпадение с `#settings` — любой другой
hash, включая наши `#key=..&picker=..`, резолвится как страница редактора). Клик по клавише
теперь **переходит на отдельную страницу** (`key-page.tsx`) с крупным изображением клавиши
(EN сверху, RU снизу, hex VK) вместо инлайнового разворачивания панели под клавиатурой —
клавиатура и страница клавиши взаимоисключающие view. Категория пикера символов
(`symbol-search.tsx`) стала управляемым пропом вместо локального `useState`. Функция `stepBack`
сворачивает уровни по одному: сначала категория пикера → null, потом клавиша → null (клавиатура).
Escape теперь вызывает тот же `stepBack`, а не жёсткий сброс всего состояния разом.

Принцип общий для вебстудии (см. `/webstudio`) — не частность kami-key-the: любой UI, который
на одном экране прячет несколько логических «экранов» через condition-рендер, должен разводить
их через адресуемое состояние, чтобы «назад» вело себя предсказуемо.

Не входило в объём: ручной ввод юникода (`direct-input.tsx`) остался с локальным состоянием —
пока не разросся настолько, чтобы требовать отдельного адреса.

и `highlightIndex` сбрасывается тем же эффектом, что и раньше.

### ~~Аудит свободных слотов и категорий символов~~ ✅

Пройден основной блок (буквы, цифровой ряд, пунктуация) и физический блок стрелок (добавленный
этой же сессией задачей выше) на предмет свободных VK-слотов. Дефолтная раскладка «Типографика»
выросла с 14 до 25 маппингов (`src/config.ts` `getDefaultConfig()`), добавлены только слоты с
понятной мнемоникой — по образцу уже существующих (`E`→€, `D`→°):

- `C`+Shift → ¢ (цент) — второй слот той же клавиши, что и © (валютная пара)
- `Y` → ¥ (иена), `L` → £ (фунт) — первая буква названия, как у €
- `/` → ÷ — визуальное сходство клавиши со знаком деления
- `P` → ± (плюс-минус) — свободная клавиша, устоявшейся мнемоники нет, выбрана как единственный
  подходящий кандидат
- `8` → • (маркер списка) — по аналогии с Option+8 на macOS (там тоже даёт •)
- Стрелки на физическом блоке (↑←↓→, VK 0x25-0x28) — прямое попадание символа в направление
  клавиши, закрывает ровно то, ради чего блок стрелок появился в UI редактора

Сознательно НЕ тронуты (оставлены на усмотрение пользователя через поиск, чтобы не перегружать
дефолт): `√` (нет однобуквенной мнемоники без конфликта), `Tab`/`;`/`\`/цифровой ряд/большинство
свободных букв (Q W T Y⁻ U I O P⁻ / A F G H J K L⁻ / Z V B M, за вычетом уже занятых Y/L/P),
`≤`/`≥` и весь объём категорий «Технические»/«Рамки»/«Геометрия»/«Разные» (256+129+96+448 ≈ 930
символов, ни один не имеет очевидной мнемоники под одну клавишу).

### ~~Предупреждение о конфликте символов между клавишами~~ ✅

Новый модуль `editor/symbol-conflict.ts` (`findSymbolConflict`/`describeSymbolConflict`) ищет,
назначен ли уже символ на другую клавишу/слот **активной раскладки**, кроме той пары
(клавиша, слот), в которую его сейчас записывают — так переприсвоение символа тому же месту не
считается конфликтом. Проверка подключена в обоих путях назначения в `editor-page.tsx`
(`assignSymbol` — через панель, `dropOnKey` — через drag-and-drop): при конфликте показывается
некритичный toast `warning` («Символ уже назначен на AltGr+X» / «AltGr+Shift+X»), назначение
всё равно происходит — предупреждение не блокирует.

Решено, что проверка **только внутри активной раскладки**, не между раскладками — разные
раскладки уже сами по себе способ иметь разные наборы символов (пользователь может специально
завести вторую раскладку с частично пересекающимися символами), кросс-раскладочная проверка
добавила бы шум без явной пользы.

### ~~Производительность поиска по общей базе символов~~ ✅

Debounce (300мс) уже существовал. Проблема была не в частоте поиска, а в повторной работе на
каждый вызов: `symbols.filter(s => s.n.toLowerCase()...)` и `parseInt(s.c, 16)` пересчитывались
для всех ~1700 символов при каждом фильтре — на поиск, на смену категории, на подсчёт
`categoryCounts`. Добавлен `searchIndex` (`useMemo` от `symbols`) — `nameLower`/`synLower`/
`codepoint` считаются один раз при загрузке базы, дальше `search()`/`categoryCounts`/показ
категории целиком фильтруют уже готовые поля.

Полноценный инвертированный индекс по ключевым словам сознательно не заведён: линейный скан по
1700 предвычисленным строкам — операция на доли миллисекунды, а токенизация + инвалидация индекса
добавили бы сложность без измеримой выгоды на таком объёме данных.

### ~~Сигнализация о несовместимой раскладке при показе overlay~~ ✅

`src/layout.ts` теперь различает три категории раскладок, а не две: `ALTGR_LAYOUTS` (AltGr есть,
но конфликтует с системными маппингами — немецкая/французская/венгерская/польская/чешская),
`SAFE_LAYOUTS` (AltGr есть и без конфликтов — русская, украинская) и новую `NO_ALTGR_LAYOUTS`
(AltGr в драйвере раскладки не определён вовсе — US English). `LayoutInfo` получил поле
`hasAltGr: boolean`; `logLayoutInfo()` при старте теперь предупреждает и про этот случай тоже.

Проверка перенесена в рантайм, в точку показа overlay: `setOverlayCallbacks` в
`main/background.ts` вызывает `getCurrentLayout()` при каждом удержании AltGr > 500мс (не
только при старте) и, если `!layout.hasAltGr`, показывает предупреждение через существующий
`notification.ts` (`showNotification`) — модуль расширен опциональными `width`/`durationMs`
(по умолчанию — прежние 300px/1000мс, старые вызовы не меняются), для этого предупреждения
взяты 480px и 2500мс, чтобы длинный текст поместился и было время прочитать.

**Решено показывать предупреждение при каждом удержании AltGr в неподходящей раскладке**, не
один раз за сессию: оно триггерится в точности в момент попытки использовать утилиту (удержание
AltGr) — если пользователь работает в английской раскладке осознанно и не трогает AltGr, он
предупреждение просто не увидит. Разовое «за сессию» предупреждение было бы либо не в тему
(показано в произвольный момент при переключении раскладки без намерения печатать символ), либо
пропущено бы при возврате в проблемную раскладку позже в той же сессии.

### ~~Персистентность списка «Недавние»~~ ✅

Зафиксировано поведение: список «Недавние» (`symbol-search.tsx`, `localStorage` ключ
`kami-key-the-recent-symbols`) **уже переживал перезапуски** — окно редактора создаётся без
`partition` в `BrowserWindow` (`main/background.ts`), значит использует дефолтную persistent-сессию
Electron, чьё `localStorage` физически хранится в `userData` и не зависит от перезапуска процесса.
Список **общий для всех раскладок** (один глобальный ключ, не привязан к имени раскладки) — решено
оставить так: «недавно использованный символ» — это про пользователя и его текущую задачу, а не
про конкретную именованную раскладку, разделение по раскладкам добавило бы путаницу без явной
пользы.

Найден и исправлен реальный дефект в рамках той же задачи: `recentCodes` читался один раз при
монтировании (`useState(loadRecent)`) и не обновлялся после `pushRecent()` — назначив символ на
одну клавишу, пользователь не видел его в «Недавние» при переходе к другой клавише в той же
сессии редактора, пока компонент не перемонтируется. Теперь `recentCodes` — обычный state,
обновляемый сразу после записи в `handleAssign`.

⚠️ Символы, назначенные исключительно через drag-and-drop сразу на клавишу клавиатуры (минуя
кнопки «AltGr+X»/«+Shift+X» в самом пикере), не попадают в «Недавние» — `pushRecent()` вызывается
только из `handleAssign`. Отдельный, не блокирующий эту задачу нюанс.
