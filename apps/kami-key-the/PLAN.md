# KamiKeyThe — План развития

## Текущая версия: 1.2.3

## Черновик (новые идеи)

- [ ] **⚠️ Локальный пин `electron: 43.3.0` расходится с корневым `^43.4.0`** (аудит
      2026-08-20) — привести к корневой версии. `bun.lock` подтверждает физический дубль
      резолвленной версии в дереве (та же ситуация в `animatrona`, `label-printer-desktop`,
      `poster-microtext-desktop`).

Системная утилита для ввода типографских символов через AltGr (ремейк TypeItEasy).
Electron + React + Chakra UI v3 (main process: koffi Win32, renderer: Vite SPA).

_Название созвучно с «Камикадзе», что подчеркивает молниеносную скорость ввода._

## Архитектурные решения

### Почему Koffi, а не keysender?

Исследование показало критическую проблему: **keysender `GlobalHotkey` не поддерживает модификаторы**. В C++ коде `RegisterHotKey(NULL, 0, NULL, keyCode)` — третий параметр (модификаторы) всегда `NULL`. Это значит:

- ❌ Нельзя зарегистрировать `AltGr+A` (т.е. `Ctrl+Alt+A`)
- ❌ Можно только одиночные клавиши → блокирует ВСЮ обычную печать
- ❌ `LowLevelHook` мониторит, но **не блокирует** оригинальное нажатие

Альтернативы (все хуже Koffi):

| Подход                                  | Проблема                          |
| --------------------------------------- | --------------------------------- |
| keysender GlobalHotkey на каждую букву  | Блокирует обычную печать          |
| keysender LowLevelHook + Backspace hack | Мерцание, ненадёжно               |
| Форк keysender                          | Требует node-gyp, мёртвый проект  |
| node-lowlevel-keyboard-hook-win         | Только мониторинг, без блокировки |

**Koffi** решает все проблемы:

- ✅ `RegisterHotKey(NULL, id, MOD_CONTROL | MOD_ALT, vk)` — именно AltGr+клавиша
- ✅ Блокировка оригинального нажатия (поведение RegisterHotKey API)
- ✅ `SendInput` + `KEYEVENTF_UNICODE` — прямой Unicode вывод
- ✅ Без node-gyp — предкомпилированные бинарники
- ✅ Активно развивается (2025+)
- ✅ Единая зависимость для всей клавиатурной логики

### Механизм работы (message pump)

```
┌─────────────────────────────────────────┐
│  Node.js event loop                      │
│                                          │
│  setTimeout(pumpMessages, 5)             │
│    └── PeekMessageW() ──► WM_HOTKEY?    │
│          ├── Да → keymap.get(id)         │
│          │        └── SendInput(unicode)  │
│          └── Нет → continue              │
│                                          │
│  RegisterHotKey × N (при старте)         │
│  UnregisterHotKey × N (при выходе)       │
└─────────────────────────────────────────┘
```

Задержка ~5мс polling + <1мс SendInput = **суммарно <10мс** — незаметно при печати.

### Переход на Electron (v1.0.0)

> В v0.14.0 редактор открывался в браузере (localhost:24680), настройки — нативное Win32 окно, трей через systray2 (Go). В v1.0.0 всё заменено на Electron: настоящее десктопное приложение с React + Chakra UI. GDI overlay и notification остаются — они лучше Electron для always-on-top transparent click-through окон.

## Технический долг

### `src/stats.ts` не унифицирован с `@letar/electron-storage`

`config.ts` мигрирован на `createJsonStore` (2026-07-28, коммит `033e69a4`), `stats.ts` — нет.
Причина: `stats.ts` держит данные в `Map<string, number>` в памяти и сбрасывает на диск раз в
60 секунд (`initStats`/`incrementStat`/`shutdownStats`) — это не «загрузить объект → сохранить
объект» как у `createJsonStore`, а накопитель с ленивым flush. Прямая миграция потребовала бы
либо городить накопитель поверх стора, либо терять lazy-write (писать на каждый инкремент —
не годится, инкремент на каждый вставленный символ).

Стоит унифицировать, если у `@letar/electron-storage` появится штатная поддержка
паттерна «накопитель в памяти + периодический flush» (актуально не только для
`kami-key-the` — если такой же паттерн понадобится другому Electron-приложению,
тогда есть смысл выносить абстракцию, а не раньше — сейчас это единственный случай).
До этого — `stats.ts` остаётся с ручной атомарной записью (tmp + renameSync) как есть.

## Бэклог

### Роутинг в редакторе маппингов

Сейчас редактор клавиши (клавиатура → панель клавиши → пикер символов по категориям → ручной
ввод юникода) — это один стек экранов на одном View без адресуемых состояний. Кнопка «назад»
не может корректно свернуть только пикер символов или только панель клавиши — либо ничего не
делает, либо уводит из редактора целиком.

Задача: завести роуты/URL-состояния (или history-стек через `history.pushState`, если полноценный
роутер избыточен для Electron SPA) под ключевые состояния экрана:

- открытая панель конкретной клавиши (`?key=0xDE`)
- открытый пикер символов с активной категорией (`?key=0xDE&picker=Стрелки`)
- ручной ввод юникода как отдельное состояние, если он тоже разрастётся

Принцип общий для вебстудии (см. `/webstudio`) — не частность kami-key-the: любой UI, который
на одном экране прячет несколько логических «экранов» через condition-рендер, должен разводить
их через адресуемое состояние, чтобы «назад» вело себя предсказуемо.

**Конкретика по экрану клавиши:** после клика по клавише на клавиатуре — не разворачивать панель
инлайново под ней (как сейчас), а переходить на отдельную страницу/роут с крупным увеличенным
изображением этой клавиши (сам символ, обе раскладки — EN/RU — крупно видны) и уже под ней —
панель назначения AltGr/AltGr+Shift и пикер. Крупная клавиша — такая же адресуемая часть роута
(`?key=0xDE`), что и остальное состояние выше; кнопка «назад» с неё возвращает на клавиатуру.

### Стрелки — задействовать физический блок стрелок

Сейчас `←`/`→` висят на `,`/`.` основного блока — суррогат. Правильное решение: использовать
настоящие физические клавиши-стрелки (Left/Right/Up/Down) и вешать AltGr прямо на них —
мнемонически однозначно, символ стрелки на клавише со стрелкой.

Сейчас в UI редактора этот блок вообще не отрисовывается (виден только основной alpha-блок,
Left/Right/Up/Down на скриншотах не показаны) — нужно:

- добавить блок физических стрелок в раскладку редактора (визуально отдельно от основного блока,
  как на реальной клавиатуре)
- перевесить `←`/`→` с `,`/`.` на Left/Right, добавить `↑`/`↓` на Up/Down
- решить, что вешать через AltGr+Shift на тех же клавишах (`⇐`/`⇒`/`⇑`/`⇓` или `↔`/`↕`)
- освободившиеся `,`/`.` в основном блоке — кандидаты для аудита свободных слотов (пункт ниже)

### Инвентаризация доступных физических клавиш за пределами основного блока

Блок стрелок — не единственная зона клавиатуры вне alpha-блока, которую утилита сейчас не видит
и не использует. Нужно установить полный список физических клавиш, которые в принципе можно
хукать через RegisterHotKey (не системные/не занятые ОС) и решить, какие из них стоит задействовать:

- **Стрелки** — Left/Right/Up/Down (задача выше)
- **Кластер Insert/Home/PageUp/Delete/End/PageDown** — 6 клавиш, сейчас нигде не учтены
- **Numpad** — цифры, `NumLock`, `+`/`-`/`*`/`/`, `.` — отдельная зона, потенциально много слотов
  (но многие ноутбуки без физического numpad — вопрос охвата аудитории)
- **F1–F12** — часто заняты системой/приложениями (яркость, звук на ноутбуках) — проверить, какие
  реально свободны и не конфликтуют
- **Prnt Scrn / Scroll Lock / Pause** — редкие, но физически существуют
- Отдельно сверить: какие из перечисленных клавиш Koffi/RegisterHotKey вообще может перехватить
  (некоторые системные комбинации ОС резервирует и не отдаёт приложениям)

Результат — таблица «клавиша → доступна для хука? → стоит ли использовать» рядом с картой
символов в начале файла, чтобы не проектировать раскладки вслепую.

### Виртуализация/бесконечная прокрутка в списке пикера символов

Списки категорий (особенно крупные — Технические 256, Разные 448, Математика 255) сейчас
рендерятся не бесконечной прокруткой — список должен подгружаться/виртуализироваться по мере
скролла, а не рендерить разом все элементы категории. Нужно:

- завести виртуализацию (windowing) для списка результатов пикера — рендерить только видимые
  строки + запас, а не всю категорию целиком
- сохранить работающую клавиатурную навигацию (стрелки вверх/вниз, Enter, Shift+Enter — уже
  есть, судя по подсказке «11 навигация, Enter — AltGr, Shift+Enter — +Shift») при переходе на
  виртуализированный список — прокрутка к выбранному элементу должна работать корректно
- проверить, что поиск/фильтр по категории сбрасывает скролл-позицию и не оставляет виртуальный
  список в невалидном состоянии

### Аудит свободных слотов и категорий символов

Пикер уже содержит большие категории (Пунктуация 111, Валюты 37, Стрелки 112, Математика 255,
Буквенные 140, Технические 256, Рамки 129, Геометрия 96, Разные 448, Latin-1 96) — то есть база
символов широкая, а предустановленных маппингов на клавиатуре — единицы (см. карту символов
выше). Стоит системно пройтись по свободным слотам (клавиша × AltGr × AltGr+Shift) и решить,
что предустановить в дефолтной раскладке «Типография», а что оставить на усмотрение
пользователя через поиск:

- какие клавиши из основного блока ещё свободны (буквы без назначения, `Tab`, цифровой ряд,
  `;`, `\`)
- по каким категориям есть смысл предустановить 1-2 самых частых символа (например, из
  «Математика» — `±`, `÷`, `√`; из «Технические» — что-то реально используемое, не весь список)
- не превращать дефолтную раскладку в перегруженную — часть находок может остаться примером/
  рекомендацией в доке, а не обязательным маппингом

### Предупреждение о конфликте символов между клавишами

Сейчас, судя по UI пикера, ничто не мешает назначить один и тот же символ на две разные клавиши
(или на AltGr и AltGr+Shift одной клавиши) без предупреждения. Нужно:

- при выборе символа, который уже назначен на другую клавишу/слот текущей раскладки, показывать
  явную подсказку («уже используется на клавише N, AltGr+Shift») — не блокировать, но не давать
  повторить незаметно для себя
- решить, нужна ли такая проверка только внутри раскладки или и между раскладками (раз есть
  переключение «Типография» / другие раскладки через `+ Новая`)

### Производительность поиска по общей базе символов

Суммарно по категориям в пикере — около 1700 символов (Пунктуация 111 + Валюты 37 + Стрелки 112

- Математика 255 + Буквенные 140 + Технические 256 + Рамки 129 + Геометрия 96 + Разные 448 +
  Latin-1 96). Нужно проверить: поиск по названию/описанию символа (кириллические подписи, судя по
  скриншотам — «Стрелка вправо — Импликация, функция из... в, предел...») не тормозит по мере ввода
  на таком объёме — при необходимости завести debounce и/или индекс по ключевым словам вместо
  линейного фильтра по всей базе на каждое нажатие.

### Персистентность списка «Недавние»

Сейчас пикер показывает список «Недавние» с последними использованными символами. Нужно
зафиксировать (и, если ещё не так, реализовать) поведение: сохраняется ли этот список между
перезапусками приложения и между раскладками, или это чисто сессионное состояние — сейчас
неочевидно из UI, стоит явно решить и задокументировать.

## Безопасность

- Антивирусы могут реагировать на RegisterHotKey + SendInput → в будущем подписать .exe
- Минимальная задержка (нативный SendInput через Koffi)
- Автозагрузка через реестр (`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`)
- systray2 Go-бинарник может блокироваться антивирусом → исключение в Defender
