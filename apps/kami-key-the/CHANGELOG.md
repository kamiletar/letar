## [1.9.17] - 2026-09-16

### Fixed

- Найдена настоящая причина, по которой релончер (фикс с 1.9.10) не переживал `app.quit()`:
  Electron/Chromium оборачивает свой процесс в Windows Job Object с
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, а `child_process.spawn(..., { detached: true })` не
  выставляет `CREATE_BREAKAWAY_FROM_JOB` — наш `cmd.exe` и через него перезапущенный
  `KamiKeyThe.exe` оставались в этой job и гибли вместе с ней в момент выхода. Диагностический
  лог из 1.9.15 (живой тест 1.9.15→1.9.16) зафиксировал: `ren` и `start` отрабатывали с
  errorlevel=0, но процесс не выживал ни секунды — подтверждено изолированным
  воспроизведением через `AssignProcessToJobObject`. Фикс — запуск `.bat` через Планировщик
  задач (`schtasks /create` + `/run`), процесс которого создаётся вне job-дерева вызывающего
  приложения в принципе. Проверено тем же изолированным тестом: пережил закрытие job-процесса.

### Changed

## [1.9.10] - 2026-09-16

### Fixed

- `quitAndInstall(true, true)` (см. 1.9.8) не перезапускал приложение после тихой установки —
  живым тестом цикла 1.9.8→1.9.9 подтверждено, что процесс не поднимался 10+ секунд после
  завершения install. Причина — NSIS-макрос `doStartApp` запускает Start Menu-ярлык
  (`$launchLink`), а не exe напрямую, и попадает в ту же гонку «файл ещё не готов», что уже
  ловили на финише обычной установки (см. 1.9.8, запись про `.lnk`); в тихом режиме гонка не
  показывает ошибку, а просто ничего не запускает. Флаг `--force-run` при этом распознаётся
  штатно — проверено эмулированным NSIS-скриптом на том же `StdUtils.dll`. Фикс:
  `scheduleRelaunchAfterSilentInstall` в `main/updater.ts` сама планирует перезапуск через
  detached `cmd.exe` (ждёт освобождения файла, запускает `process.execPath` напрямую, минуя
  `.lnk`), `quitAndInstall` теперь вызывается с `isForceRunAfter=false`.

## [1.7.5] - 2026-09-15

### Fixed

- **Критично:** production-сборка (`--mode production`) падала сразу после установки с
  `TypeError: Cannot set properties of undefined (setting 'options')` — webpack
  `optimization.concatenateModules` (scope hoisting, включён по умолчанию только в production)
  ломал циклическую CJS-загрузку внутри `js-yaml` (транзитивная зависимость `electron-updater`,
  `main/updater.ts`): конструктор `Type` вызывался без `new`, `this` оказывался `undefined`. В
  dev-сборке webpack не проявлялось — concatenation там не включён. Фикс —
  `concatenateModules: false` в `main/webpack.config.js`.
- Категория «Индексы» в редакторе символов не показывала верхние индексы 1/2/3 (`¹²³`,
  `U+00B9`/`U+00B2`/`U+00B3`) — они лежат в блоке Latin-1 (наследие ISO-8859-1), а не в блоке
  `U+2070–209F`, где категория искала остальные над-/подстрочные знаки. Символы были в данных,
  просто не попадали под фильтр диапазона (`renderer/src/editor/symbol-categories.ts`).

### Added

- Вторая встроенная раскладка «Индексы»: цифры 0-9 и операторы формул (`+ - = ( )`) в виде
  над-/подстрочных знаков — без Shift подстрочный вариант (`₀₁₂...`), с Shift надстрочный
  (`⁰¹²...`). Переключение — как у существующих раскладок, `AltGr+Ё`.
  У уже установленных версий (существующий `keymap.json`) раскладка добавляется автоматически
  при следующем запуске — `migrateBuiltInLayouts()` в `src/config.ts` дописывает недостающие
  встроенные раскладки в уже сохранённый конфиг, не трогая раскладки, которые пользователь
  создал сам под тем же именем.

## [1.7.4] - 2026-09-13

### Added

- Автообновление через `electron-updater` (`main/updater.ts`). Тихая проверка при старте
  (задержка 10с, без диалога «обновлений нет»), плюс пункт меню трея «Проверить обновления» для
  ручной проверки с явным результатом. Скачивание и установка — только по подтверждению
  пользователя в диалоге (`autoDownload: false`), по образцу `label-printer-desktop`
  (`main/services/updater.service.ts`) — не toast/renderer-интеграция, как у animatrona:
  приложение живёт в трее без постоянно открытого окна, стримить статус в renderer было бы
  некуда.

  ⚠️ **Не встроенный `GithubProvider`.** `kamiletar/letar` — общий репозиторий, где animatrona
  тоже публикует релизы. Штатный `GithubProvider` electron-updater всегда бьёт в repo-wide
  `GET /releases/latest` — в общем репозитории это самый свежий релиз ЛЮБОГО приложения, не
  обязательно kami-key-the. Если бы оставили как есть, следующий релиз animatrona заставил бы
  автообновление KamiKeyThe предложить скачать и установить инсталлятор Animatrona. Вместо этого
  сами находим свой релиз через список `GET /releases` (не `/latest`) по префиксу тега
  `kami-key-the-v` и подставляем electron-updater `generic`-провайдер с URL конкретного релиза —
  дальше стандартная механика (sha512, blockmap-diff, `quitAndInstall`) работает как обычно.

  Релиз публикуется **не** через `electron-builder --publish always` (он вычисляет тег как
  `v${version}` без префикса приложения — так и родился баг: первая попытка публикации создала
  ошибочный релиз с тегом `v1.7.4`, пришлось удалять и переделывать), а вручную:
  `nx build:win kami-key-the` (публикация `--publish never`) → `git tag kami-key-the-vX.Y.Z` →
  `gh release create` с явным тегом и загрузкой `.exe`/`.exe.blockmap`/`latest.yml` из
  `dist-electron/`. ⚠️ Имена файлов при загрузке должны совпадать **дословно** с тем, что написано
  внутри `latest.yml` (там дефисы: `KamiKeyThe-Setup-X.Y.Z.exe`) — `gh release create`/`upload` с
  оригинальным именем, содержащим пробелы (`KamiKeyThe Setup X.Y.Z.exe`, как их пишет
  electron-builder), сам заменяет пробелы на точки, а не на дефисы — было расхождение с
  `latest.yml`, `electron-updater` не смог бы скачать файл (404). Переименовывать локальные копии
  под дефисы перед загрузкой, не полагаться на автоматическую санитайзацию имени сборщиком
  релизов.
